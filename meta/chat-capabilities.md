First inventory of everything a user should be able to do in DorkOS chat, across all four chat surfaces, with the current test coverage for each. This is the contract our chat tests should check against. When a capability ships, it gets a row here; when a row has no coverage, that is a named gap, not an unknown one.

Coverage legend — where each capability is verified today:

- **U** = unit/route tests (`apps/server`, `apps/client`, vitest)
- **E** = Playwright e2e (`apps/e2e`, deterministic, test-mode runtime where possible)
- **S** = agentic self-test (`/chat:self-test`, `/chat:session-switch-test`, `/chat:rooms-test` — live model, evidence report)
- **—** = no automated coverage found (2026-08-13 audit)

## The four chat surfaces

1. **Direct agent session** (`/session`) — one human, one agent, runtime-owned transcript.
2. **Channel** (`/channels`, and `#team` on `/`) — many humans and agents in one room.
3. **Thread** — a reply chain inside a channel (`?thread=` param, `RoomThreadPanel`).
4. **DM** — a one-to-one room between two members (human↔agent, agent↔agent).

A capability is only "done" when it behaves correctly on the surface(s) it applies to, on desktop **and** mobile, live **and** after reload-from-history.

**C-09 is shipped end to end and honest about where it works — and it is two rows, because the two paths do different things with the same button.** On the resume path a steer cannot cut in (C-09a: the row is hidden and an API steer queues with a reason); on the pump it does (C-09b) — and C-09b now has its first live evidence, mixed. The pieces landed in this order: `AgentRuntime.deliverIntoTurn` and `deliverSteer` (P4.1); the fold-into-next stage fallback in PR #1028 (P4.2, DOR-1194); the `turn_input` transcript carrier that renders a delivered steer inline in PR #1026 (P4.3, DOR-1195); and the composer affordance itself — the Steer row in `DispositionMenu`, tucked beside Queue — in PR #1041 (P4.6, DOR-1198). Claude-code and test-mode declare `supportsSteer: true`; codex and opencode declare it `false`. Two things about it are worth knowing:

- **A steer only cuts in on a session that holds its agent process open between messages** (`runtimes.claudeCode.persistentSession`, which ships OFF). For one release the composer asked only the runtime's static `supportsSteer`, which is a claim about the ADAPTER — so on a default install it offered "Steer", the runtime found no held process to push into, and the message ran as an ordinary follow-up turn with the UI saying nothing (`/chat:self-test` 20260816-155308 finding 1). **DOR-1268 closed that.** The runtime now answers per session (`AgentRuntime.canSteerSession`), the server publishes the answer on the session's own status, and the composer shows the Steer row only when it is not `false`. A steer that still cannot land on a turn that IS open comes back `degradedBecause: 'not-steerable'` and the chip says so in words, instead of the silent `session-idle` that used to swallow it. So the affordance no longer promises something the session cannot do, and the two cases the older note ran together — "the turn ended, nothing was lost" and "it could not cut in" — are now told apart.
- **The same confusion existed for Add context, and its failure was worse (DOR-1307, PR #1087).** `supportsContextStaging` is a claim about the adapter too, and the dispatcher read it as a claim about the session — so on a default install one click of Add context took the native path, where the adapter's only way to honour it was to BOOT a warm process the operator had not turned on and register the session, after which every later message ran on the pump and the composer began offering Steer. One click had silently opted a session into the experiment. Closed the same way (PR #1087, in flight as this is written): `AgentRuntime.canStageSession` answers per session, a `false` folds the words into the next reply with `degradedBecause: 'not-stageable'` (a real answer, so Add context stays offered on both paths), and conformance case C9 mirrors C7.
- **Coverage is unit-level in three places** — the dispatcher's fork between the two reasons (`message-dispatcher.test.ts`), the resume-path receipt and the per-session signal (`persistent-dispatch.test.ts`), the composer gate and the chip (`SessionComposer.test.tsx`, `queue-chips.test.ts`) — plus conformance case C7 (and C9 once #1087 lands), which hold any runtime that answers per session to narrowing its own flag rather than widening it. **A steer joining a live turn now has live evidence, and it is mixed (2026-08-17, the first flag-ON runs):** the self-test's steer landed inside a running turn and rendered inline (`chat-self-test/20260817-134100.md` C-09b PASS), and one did in the session-switch run too (19:14:57Z, into a turn in its tool phase); that run's two steers from a SECOND window, sent 4 s and 8 s into uninterrupted text, never landed — no `turn_input`, no chip, a plain "1 queued", and each ran as its own turn 30–39 s later (`session-switch-test/20260817-134500.md` finding 5, **DOR-1315**). And there is an e2e now (**DOR-1326**): test-mode holds a scripted process per session, so the browser leg can finally stage the shape that bites — a runtime that declares the capability paired with a session that cannot use it. `apps/e2e/tests/chat/held-process.ts` drives both sides: a steer joining a live turn on a held session, and, on a session without one, the Steer row absent and an API steer returning `not-steerable`.

Two guarantees ride every row, and are what the S runs should look at after each Stop, whatever the phase: **nothing typed is destroyed** — a Stop empties the queue and hands the messages back to the composer, and when messages are waiting it says how many before it does (`StopConfirmDialog`; the route returns `cancelledQueued`; `POST /interrupt` clears the queue synchronously before it awaits the runtime, so a turn ending under it cannot drain the head) — and **the settle is honest**: the Stop button and the streaming indicator go, the composer comes back, and the turn settles as one the operator stopped — `turn_end{terminalReason:'interrupted'}`, the `interrupted` lifecycle, no red failure card. That last part is not free where the interrupt was never delivered: the CLI names its own terminal in `result.terminal_reason`, and a turn ended by `query.close()` produces no further `result`, so until DOR-1244 the wind-down closed with no reason at all and settled `idle` — indistinguishable from a reply that finished by itself. The send loop now supplies the reason the CLI cannot (`message-sender.ts`), gated so a Stop RACING a natural end cannot rewrite a turn that had already completed. **The one thing a reload does lose** is the marker inside the CLI's own transcript. `[Request interrupted by user]` is written by the CLI when it receives the interrupt, which on an escalated close by definition did not happen — so the transcript TEXT reads as an ordinary reply. The FACT that the turn was stopped survives: it rides the durable `turn_end{terminalReason}` and the projector settles a cold hydrate to `interrupted` from it (`session-state-projector.ts`, "a cold hydrate shows it was cut short"). Named limit, follow-up, not fixed here. **Two scopes to keep straight, both about the persistent path** (`runtimes.claudeCode.persistentSession`, ships OFF). It has no wind-down of this kind — it never ends the CLI's stdin between turns — but it does have the starting phase, which is where DOR-1191 lived, and it pays the full `STOP_ACK_TIMEOUT_MS` on every Stop because only the resume path records an ended stdin. And the interrupted SETTLE above is the resume path's too: the pump does not run `message-sender`, so a `query.close()` there is a process death that the windower settles as `turn_end{terminalReason:'error'}` and the session reports `crashed` (`sessions/session-turn-windows.ts`, `sessions/persistent-dispatch.ts`) — DOR-1302, not yet observed live. **What the first flag-ON runs saw instead (2026-08-17):** every one of the four Stops driven on the pump was ACKED — process survived, no red card, next message worked, two room halts in a row and both agents answered normally — and each settled `turn_end{terminalReason:'aborted_streaming'}` preceded by an `error{code:'error_during_execution', [ede_diagnostic] result_type=user}` frame the durable record keeps (**DOR-1320**; the resume path logs the same CLI diagnostic — `[sendMessage] stream error … [ede_diagnostic]`, `message-sender.ts` — but settles `interrupted` and writes no durable error frame, per the 2026-08-16 self-test). Three settled inside 3.2 / 5.7 / 1.3 s; one took 7.6 s with another session streaming (**DOR-1319**). And a room halt pressed 0.7 s in — the STARTING phase — wrote the halted notice and still let the agent post its full answer 23 s later (**DOR-1313**), while the same halt 10 s into streaming was clean.

## 7. Agent context in channels — can they find what they need?

Your question: is there a way to **check** an agent gets all the right context in a channel? Today: `room-context.ts` (ADR-0273) assembles what a triggered agent is told — room, roster with addressable handles, recent entries, thread subject excerpts, its own last 5 posts, up to 5 reactions on them — and it is unit-tested (`room-context.test.ts`, `room-context-handles`). But that only proves the **payload is assembled**, not that the agent can actually **use** it. Nothing verifies comprehension.

The check we're missing is a **context-recall probe suite** (natural fit: a `rooms` suite in `packages/evals`): seed a channel with known history, then ask the agent questions whose answers require each context source, and oracle-judge the replies:

| ID   | Probe                                                                 | Verifies                                     |
| ---- | --------------------------------------------------------------------- | -------------------------------------------- |
| X-01 | "What did @kai say about the deploy earlier?"                         | recent-entries window depth                  |
| X-02 | "Who else is in this room and what are their handles?"                | roster + addressable handles                 |
| X-03 | Ask inside a thread about the thread's opening message                | thread subject excerpt                       |

## 8. Edge cases the tests should force

- **Concurrency**: two sessions streaming at once while switching (covered by `/chat:session-switch-test`); an agent active in a **room and a direct session at the same time**; two humans posting in one thread simultaneously.
- **Interruption**: refresh mid-stream; network drop mid-stream; server restart mid-turn; stop pressed during tool execution; **stop pressed in wind-down** — after the `result` DorkOS closed the CLI's stdin on, when the CLI reopens the turn (a background shell's notification, a hook) and the UI shows Stop again while the SDK control stream is already gone, so a graceful `interrupt()` can never be acked (DOR-1244; the C-10 matrix under §1 has the row); queued message pending when the turn errors.
- **Compaction**: compaction firing **while** a message is queued; compaction mid-multi-turn task; compaction in a room-bound session. (Transcript rendering across the boundary is now covered — DOR-1215.)
- **Prompts**: approval pending during a session switch, a refresh, a compaction, and a second incoming prompt; question prompt answered from a second window; approval answered outside DorkOS. **A prompt nobody answers is now covered on the reload path** (I-07/L-03, DOR-1293): a question that expires, is dismissed, fails, or was never resolved at all reads honestly instead of leaving a green "Question answered", and a tool refused or expired outside DorkOS — the bare CLI, or a permission rule — reads as a refusal rather than as a tool that ran. Four limits ride it, and none is a test gap that more testing would close:
  - An APPROVAL that expires is proven only by parser unit tests; the browser leg drives the question half.
  - **MCP elicitation carries no outcome at all.** An elicitation is not a `tool_use` block, so no runtime transcript records how one ended, and nothing can be read back.
  - **For LOG-BACKED runtimes (codex, opencode, test-mode) an ANSWERED question reloads without its answers.** The event stream carries the fact that a question was answered but never the values, so a reopened transcript shows the generic "Question answered" row rather than the choice. claude-code keeps the values (they are in its JSONL). Closing it means putting answers on `interaction_resolved`, not a better fold.
  - **`errored` is unreachable from the event fold** — a log-backed runtime has no way to report that the ask itself failed. So "every runtime says the same thing" holds for the UNANSWERED endings (expired / denied / cancelled / unresolved), which is the set this fix is about, and not for the other two.
- **Scale**: 500+ message session reload; very long single message; rapid-fire sends; many rooms with unread counts.
- **Identity**: URL session id ≠ SDK session id (the JSONL mapping trap); duplicate session titles in the sidebar; placeholder ids in `room_sessions`.
- **Mobile**: every capability above on a phone viewport (composer, thread panel via room-sheet-phone, approval cards).
- **Runtime spread**: C-07 queueing and I-01 approvals on codex and opencode, not just claude-code. L-04 compaction on **opencode** — codex declares `compact` unsupported and emits no boundary, so there is nothing to spread there.
- **Persistent path (the pump)** — the second implementation of most of the rows above; every item here is a named gap until a row's coverage cell says otherwise: Stop on a warm-but-idle session; a Stop that goes unacked (settles as a crash, and two in a row refuse the next message — DOR-1302, not yet observed) versus one that is acked (settles `aborted_streaming` with a spurious error frame — DOR-1320); a halt in the STARTING phase (DOR-1313); a chat reaped mid-queue; a slot reclaimed by the ceiling while a message waits; the thirteenth chat asking when nothing is reclaimable; a steer 4–8 s into uninterrupted text, and from a second window (DOR-1315 — the retired-id half closed by DOR-1309, 2026-08-18; the timing half stays open); a stage on an idle session (DOR-1318 — the shared raw-id-keying root cause is closed by DOR-1309, 2026-08-18; not re-verified against DOR-1318's own literal repro); the "turn nobody asked for" every steer and stage leaves behind (DOR-1314); Add context on a default install (DOR-1307 — closed); the flag flipped on with a chat already streaming, and off with twelve chats warm; account / model / folder / credential switched mid-chat (L-12); a chat whose id is re-minted mid-first-turn — does the second message reach the SAME warm agent (DOR-1309 — closed 2026-08-18: yes, resolved through the session's alias chain; the id mismatch's worst shape, caught by the fix's own regression test, was not merely an orphaned second process but a RECLAIM: with the warm ceiling full, a phantom duplicate for the same session reclaimed and killed the live conversation's process to clear its own room); a server killed hard with twelve warm agents (DOR-1310); compaction on a warm process and the turn after; a room turn on a warm process (halt, collect/fold, budget); staged words held in memory under a durable receipt across a restart (DOR-1324).
- **Autonomy** (new, from §6): mention loops (A mentions B mentions A — budget must break it, and the break must be visible); two agents answering the same mention at once; a human answering a question while an agent is mid-compose on it; a message **deleted or edited** after an agent started replying to it; an agent mentioned inside a thread (does it get thread scope or channel scope?); a reaction used as an answer ("👍 to approve?") — is that ever an approval signal, and if not, is that explicit; an `engaged`-mode agent in a high-traffic channel (does restraint hold at volume); bridged-room members with external identities mentioning a local agent; prompt-injection posted by a bridged external user (A-15).

## 11. Run modes and the single entry point

**Run-mode convention for agentic self-tests** — wired into `/chat:self-test`, `/chat:session-switch-test`, and `/chat:rooms-test` (DOR-1218), and required of any future self-test:

- `mode:sandbox` — run against the **test-mode runtime** (throwaway data dir, no model spend, deterministic). Verifies UI plumbing. Ports and data dir are the e2e suite's: API 4243, Vite 4248, `DORK_HOME=/tmp/dorkos-test-mode-4243`. Anything whose verdict is a judgment about what the agent chose to say is `N/A (sandbox)`, never a pass.
- `mode:live` — run against the dev environment with a real runtime. **Default model: Haiku** (`claude-haiku-4-5`) unless the run is explicitly about model behavior. Verifies streaming feel, real tool loops, timing.
- If the invocation doesn't state a mode, the command **asks the user** before spending anything.
- **Path is not a mode; it is the stack's.** A live run inherits whichever path the stack under test is on (`runtimes.claudeCode.persistentSession` in that stack's config); the report header should say which (the 2026-08-17 reports do; the commands do not require it yet). Testing the other path means the operator flips the experiment (or a scratch server is booted with it set before the first session — `research/20260817_persistent-session-flag-measurement.md` Appendix D), never the test writing config.

**Run-everything entry point**: `/test:all` (DOR-1218) runs the whole ladder and produces a single report at `test-results/test-all/<timestamp>.md` —

1. `pnpm verify` (typecheck + lint + affected unit tests)
2. `pnpm test -- --run` (full unit suite)
3. `apps/e2e` Playwright (mock leg always; cockpit leg if a stack is up)
4. `pnpm evals -- --suite core --tier test-mode` (free structural evals)
5. **Gated, ask-first**: live evals (`pnpm evals:local`), the agentic self-tests, `/multiwindow`, Docker smokes

Steps 1–4 are free and deterministic; step 5 spends money or needs a live stack, so it is opt-in per run — `/test:all` runs 1–4, then **stops and asks** about 5, and writes one summary with pass/fail per tier. Its one hard rule: a tier that did not execute is never green, because turbo's cache replay prints a full-run summary in a few hundred milliseconds (which is why `scripts/assert-tests-executed.sh` exists in CI). Step 4's `--suite rooms` half becomes real once DOR-1217 registers rooms eval cases; until then that selector matches nothing and the command reports it as unavailable rather than passing.

## 12. How this list is used

- New chat feature → add its rows here in the same PR.
- Each gap above should become a deterministic e2e spec against the **test-mode runtime** where possible (free, CI-able), with the agentic self-tests reserved for what only a real model shows (timing, streaming feel, real tool loops). Autonomy (§6) and context-comprehension (§7) capabilities are judgment-shaped — their natural home is a `rooms` suite in `packages/evals` (oracle-judged, budget-capped, with a free structural tier).
- The self-tests (`/chat:self-test`, `/chat:session-switch-test`) should cite the IDs here in their verification matrices, so a run maps back to this contract.
