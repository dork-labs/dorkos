Coverage legend — where each capability is verified today:

- **U** = unit/integration tests (vitest, real temp dirs — `packages/harness`, `apps/server/src/services/harness`)
- **C** = CLI end-to-end (`packages/cli/src/__tests__/harness-sync.test.ts`, real engine, real temp repo, exit codes + tree snapshots)

- **H** = real-harness smoke: an actual `claude` / `codex` / `opencode` / `cursor-agent` / `gemini` / `copilot` binary reads the projected tree and reports the artifact — **none exists**; every test today is file-shape only

`State` is honest, as in chat-capabilities §6: **built** / **partial** / **not built** / **stale** (the engine says one thing, the harness now does another) / **silent** (the artifact is never scanned, so it is neither projected nor reported — the one state the "honest drop list" promise forbids) / **false-native** (the engine reports `native` for a file or link that does not exist). Where a State cell would need a paragraph, the paragraph is in a note under the table and the cell carries a phrase and a pointer.

## The shape of the problem

Every coding agent stores the same handful of project config kinds under a different name in a different place. DorkOS keeps **one canonical source** and **projects** it into each harness's layout (ADR-0301), so one edit — or one install, or one skill an agent writes — reaches every agent a person runs. Four axes decide what a projection is:

1. **Harness** (the target): Claude Code, Codex, OpenCode, Cursor, Gemini CLI, GitHub Copilot (`HARNESS_IDS`, `packages/harness/src/manifest/schema.ts:7`).
2. **Artifact kind**: skills, instructions, hooks, commands, and — not yet in the engine's vocabulary — subagent definitions, path-scoped rules, MCP server config, and whole plugins.
3. **Source class** (where it came from, ADR-0303): authored `.agents/`, marketplace-installed `.dork/plugins/`, adopted from a harness-native dir — plus five classes the ADR never named that §3 adds: a skill an agent writes mid-session, a package installed by Claude Code's own `/plugin`, a skill Codex's `$skill-installer` drops into `.agents/skills`, a package installed at both scopes, and the Operating DorkOS pack DorkOS seeds itself.
4. **Scope** (which directory tree): a project checkout, an agent workspace under `~/.dork/agents/<name>/`, a room worktree, and the global layer (`~/.dork/plugins`, `~/.claude`, `~/.agents/skills`, `~/.codex`, …). A fifth tier sits above all of them for Claude Code — enterprise/managed settings — which a projection can never win against and this doc otherwise does not model.

A capability is only "done" when it behaves correctly on every harness it applies to, from every source class, in every scope — **and the harness actually loads the result** (the H tier). A symlink nobody reads is not a projection. And there is one property that rides every row, from ADR 260706-192819: **the bare CLI and the DorkOS-managed session see the same thing** (AP-14). It is currently false for Codex (SK-14).

The one fact that shapes everything: **Claude Code is the only harness that does not read `.agents/skills`.** Every other harness reads the canonical directory natively. So the symlink into `.claude/skills/` is the whole reason the skills half of the engine exists, and every other harness's **authored** skill projection is `native`. Cursor, Gemini and Copilot were DROPPED with "not auto-projected in v1; see DOR-143" until DOR-1847; that reason was true when written, stale by the time it was found, and is now gone (SK-05). The **installed** skill was a different story: it reached `.agents/skills` only through the link the Codex target planned, so with Codex disabled no other harness saw it either — the drop for Cursor/Gemini/Copilot was honest and OpenCode's `native` was not. DOR-1847 made the link unconditional (`planCanonicalSkillLinks`), which turns all four of those cells into an honest `native` (SK-05 note).

The second fact: **OpenCode, Cursor and Copilot read BOTH `.claude/skills` and `.agents/skills`**, so an installed skill linked into both dirs is reachable twice there. Claude Code documents loading a shared target once; OpenCode keyed on frontmatter `name` at the 2026-07 source check, which would collapse the pair; what Cursor and Copilot do with a `pkg__name` folder whose frontmatter says `name` — a name that cannot match the folder and, on OpenCode's and Cursor's stated rules, cannot even be a valid name — is unverified (SK-09, SK-12).

Reading notes. **The drop list is honest about what it finds and blind to what it does not.** The four **silent** rows are the kinds the scanner never enumerates (`ArtifactType`, `plan/types.ts:21`, has no `agent`, `rule` or `mcp`), so `dorkos harness sync --check` on this very repo says nothing about its 13 rules and 7 subagent files (5 top-level, 2 nested) staying Claude-only. Two more silences live **inside** the one kind it does scan: `scanSkillDirs` (`scan/scanner.ts:60-71`) keeps only `Dirent.isDirectory()` entries — false for a symlink — and skips any name containing `__`, so a skill whose source is a symlink and an authored dir named `my__helper` both vanish with no drop line (SK-13, reproduced). **The manifest's policy half is decorative**: the engine reads `harnesses` and `claudeOnlySkills` and nothing else (`grep 'manifest\.' packages/harness/src` — 2 fields); `skillWrappers`, `commandMappings`, `instructionProjections`, `hookPolicies`, `skillBundles` are validated and unread. This repo's one `skillWrappers` entry has `status: "planned"` and its target does not exist; `hookPolicies[cursor].projection: "none"` would contradict the `.cursor/hooks.json` the engine generates the moment Cursor were enabled. **This repo's counts**, for the record: `.agents/skills` holds 32 entries — 17 authored dirs and 15 `flow__*` links into the installed flow plugin; `.claude/skills` holds 45 — 32 links and 13 real Claude-only dirs.

**What DOR-1847 changed (2026-09-07).** All four false natives, the `claudeOnlySkills` blind spot, the three stale skill drops, the two short hook maps and the stale command reasons are fixed; the rows above are the state after it, and each says which. What remains open in §2 is the four **silent** rows and the manifest's decorative half.

**What the review corrected (2026-09-07) — a log of what the audit found, not the current state.** Round two found the Codex hooks file is the wrong shape (HK-01) and that the commands `native` is a fourth false-native. Round one found eleven wrong cells, each now fixed above: the installed-skill `native` for OpenCode (false unless Codex is enabled — reproduced with `harnesses: ['opencode']`); the installed-skill drops for Cursor/Gemini/Copilot (honest, not stale — only the authored row is stale); instructions `native` for Codex/Cursor/OpenCode with no `AGENTS.md` (reproduced: the same plan carries `codex native AGENTS.md` and `claude-code drop … no AGENTS.md to point at`); Claude-only skills "untouched" (they are unplanned when they live only in `.claude/skills`, and a conflict when they live in both — reproduced); the MCP drop reason; a `shapes` layer that does not exist beside two (`lsp-servers`, `agents`) that do; Claude's event count (30, not 29); the source of authored hooks (one file, not three); and the counts of rules, subagents and skills.

**HK-07, the consent gate, in full.** A card names the package, each command and when it fires; yes is recorded as `<pkg>@<digest>` in `harness.approvedHooks`; a changed command, matcher or event re-asks; a reorder does not; a refused package is not re-asked this process; an unanswered card is asked again; the withheld package's skills and commands still project; a rewrite mid-decision installs nothing the card did not show. Three stated holes: `dorkos harness sync` bypasses the gate entirely and installs refused hooks (documented in `docs/getting-started/configuration.mdx`; a "no" lives only in process memory, `hook-approval.ts:62-64`, so the CLI has nothing to consult); the digest binds the command text, not the script it runs; nothing in the app can revoke or list an approval.

**HK-11, the data-loss bug, in full (reproduced by the review against `packages/harness/dist`).** `applyGenerate` (`apply.ts:130-136`) rewrites unconditionally, and `sweepGeneratedOrphans` (`apply.ts:381-402`) deletes every path in `GENERATED_HOOK_TARGETS` the plan does not regenerate — **for every harness, enabled or not**, with no marker or content guard, on the stated assumption (`apply.ts:391-397`) that every such file is engine-owned. Codex's and Cursor's own docs tell people to author exactly those files. A staged Codex-first repo with hand-written `.codex/hooks.json`, `.cursor/hooks.json` and `.github/hooks/copilot-hooks.json` lost **all three** on the first marketplace install — Copilot's while Copilot was not in the manifest. With any plugin hook present the file is overwritten instead of deleted. Through `runAutoProjection` the delete lands on pass 1, **before the DOR-522 card is raised** (pass 1 has zero hook contributors by design, `auto-project.ts:165-186`). `--check` cannot warn: the file is not in the plan, so `checkPlan` never looks at it. Fix shape (settled in review round two): ownership by **sidecar**, not by an unknown key — `<target>.dorkos-generated` beside each generated file holding the sha256 of the bytes written, so the engine owns a target iff the sidecar exists and its digest matches the file (a hand-edited generated file is then a conflict too, which an in-file marker could never tell apart); for Codex, additionally the documented top-level `description` string ("Generated by DorkOS Harness Sync — run `dorkos harness sync` to regenerate"), which reads as a comment and is the same edit as the `hooks` wrapper HK-01 needs; conflict — not merge — on a file without a matching sidecar, with a message naming the way out (move the hooks into `.claude/settings.json`, the one canonical hook source, or delete the file); sweep only files with a matching sidecar, together with the sidecar, and only for enabled harnesses. Merging a hand-written Codex file stays a follow-up gated on the H tier proving Codex tolerates a per-group extra key.

## 13. Edge cases the tests should force

- **Identity**: an authored `foo` and an installed `pkg__foo` whose frontmatter says `foo` (SK-06); a frontmatter `name: 12`; a skill dir with a space, uppercase, or `--`; a `SKILL.md` with no frontmatter; two plugins shipping the same skill name; a skill and a command with the same leaf name (CM-05); a nested `.claude/skills` in a monorepo package (SK-15); two skills differing only by case on macOS (AP-16).
- **Symlinks**: a dangling managed link (SK-10); a dangling link at a generate/scaffold target (AP-05); a **symlink at the source** — silently skipped today (SK-13), while Codex follows it; a symlink loop; an absolute symlink a person made by hand at a managed target (wrong link text → replaced — is that right for a link that resolves?); a dork home reached through a symlink (covered); Windows junction vs. `core.symlinks=false` checkout (J-10).
- **Ownership**: a hand-written `.codex/hooks.json` / `.cursor/hooks.json` / `.github/hooks/copilot-hooks.json`, with and without a harness in the manifest (HK-11); a hand-written `.opencode/commands/.gitignore`; a `.claude/commands/<pkg>/` holding both a wrapper and an authored file; a user hook in `settings.local.json` that copies the `_dorkosHarness` key by hand; a `.gemini/settings.json` — the file the sweep comment says must never be a generated target — to make sure it never becomes one; a person's own hooks in `settings.local.json` (HK-14).
- **Hooks**: an event Claude has and no target does (drop names the harness); `SessionEnd` (HK-13); a matcher of `*` vs. absent vs. a regex; `timeout` and unknown fields riding through; `${CLAUDE_PROJECT_DIR}` (warned) vs. `$CLAUDE_PROJECT_DIR` without braces (not caught — is that right?); a package that moves a command between events (re-asks); a package rewritten while its card is open (covered); the same package approved in project A and installed in project B (asks again); `dorkos harness sync --fix` after a refusal (§16 D5).
- **Scope**: a global install of a plugin with a scheduled skill (SK-03 global half); the same package at both scopes (SRC-12); a project inside `<dorkHome>/agents` that is also a registered agent's repo; an agent created at a path outside dork home then booted (DOR-664); a room worktree whose committed manifest enables Gemini; `.agents/` gitignored (AP-15); `~/.claude/CLAUDE.md` (IN-08); an enterprise-managed skill shadowing a projected one (Claude Code's top tier).
- **Manifest**: a stale `sharedSkills` array (rejected — covered); `harnesses: []` (accepted by the schema; `--check` projects nothing and says "no projected actions"); a manifest enabling a harness whose dir does not exist; `claudeOnlySkills` naming a skill that is not there, or one that is only in `.claude/skills` (SK-04); a repo that grows a `.cursor/` after scaffolding (TR-11).
- **Concurrency**: two auto-projections into one repo (AP-10); a sync racing a Claude Code session mid-write in `.claude/skills`; a watcher firing between `mkdir` and the `SKILL.md` write (TR-06); the server booting while a `dorkos harness sync --fix` runs in an agent home.
- **The reader, not the writer**: for every projected artifact, the harness's own discovery reports the artifact under the name the person will type. That is the H tier and it is empty.

## 14. Known coverage gaps (2026-09-07), ranked by user pain if broken

1. **J-02 destroys a Codex or Cursor user's hooks (HK-11, AP-07) — reproduced.** The engine owns three vendor-documented user files by path alone, sweeps them for harnesses that are not enabled, and does it before the consent card. No test stages a hand-written file at a generated target; the CLI snapshot helper's own docstring (`harness-sync.test.ts:40-49`) predicted this blind spot ("an in-place rewrite of a file that already existed would pass it"). ## 16. Positions this document takes

The audit asked five product questions. Each is answered as a recommendation with its reason, revised after the review, so the eventual ADR has something to push against. None is settled by this file.

**D1 — First contact must be safe, honest, and re-runnable.** An existing project's skills "just projecting" is not the current behaviour for any of the three entry cases: J-01 enables nothing but Claude Code and never re-detects, J-02 loses files, J-03 is silent about two kinds. In order: the generated-file ownership sidecar and the Codex file shape (HK-11, HK-01 — one edit), the vocabulary and inventory (§8, SK-13), a detection pass that re-offers newly present harnesses (TR-11), and only then adoption.

**D2 — A skill an agent creates in the canonical location is projected automatically.** Yes, and it is a trigger problem only: a watcher on `.agents/skills` (the scheduler already has one) or a turn-end re-project makes J-05 true with no new policy — provided the trigger inherits the hook gate and debounces a directory that has no `SKILL.md` yet (TR-06). The restart caveat in §1.1 is said in the output, not discovered.

**D3 — Adopt is reported everywhere and automatic only where DorkOS owns the directory.** The first draft proposed auto-moving skill directories out of `.claude/skills` into `.agents/skills` by default. The review is right that this does not hold: once a directory is physically in `.agents/skills`, five harnesses read it natively, and a `drop` line has no power over that — so an auto-move is a one-way, unrevocable exposure of exactly the skills a person kept Claude-only on purpose (`context: fork`, `disable-model-invocation`, `paths`); `manifest.claudeOnlySkills` cannot un-expose it, and per SK-04 only fires after the move anyway. "`git status` shows a rename" is false for a directory (N deletions + N additions) and false twice when `.agents/` is gitignored (AP-15), where a teammate's clone would lose the skill outright. And with SK-13 unfixed, the non-destructive shape (leave the dir, link from `.agents/skills`) is impossible. Round two took the last step too: **report-only everywhere in v1, DorkOS-owned directories included.** An agent is runtime-agnostic (`runtimeRegistry` binds a session, not an agent), so a skill auto-moved inside an agent home is exposed to that same agent's next Codex session; a frontmatter denylist of "Claude-only fields" is a guard that must be remembered every time Claude Code adds a field; Claude-only-ness often lives in the body (`${CLAUDE_*}` tokens, `/reload-plugins`), which SK-07 already knows and a frontmatter guard ignores; and an agent home has no `git status` and no reader — the boot pass runs unattended, so the one mitigation a move relies on, visibility, is weakest exactly there. So: compute `unmanaged (adoptable)` (VC-01) and **report** it in every sync and boot summary; `dorkos harness adopt <name>` moves one skill, refusing when `.agents/` is gitignored and, in a room worktree, when the name is one of the seven seeded ones (SRC-11's reap); `harness.autoAdopt` defaults **false everywhere** and is merely _permitted_ in agent homes and room worktrees — and when it is on, the guard is an **allowlist**: move only a skill whose frontmatter holds nothing outside the agentskills.io base fields and whose body carries no `${CLAUDE_*}` token; everything else is reported, never moved. That inverts the failure mode from "adopts unless the danger was recognised" to "adopts only what was recognised as safe", which is the only version that survives a vendor adding a field. The status surface (D6) should exist before the flag does.

**D4 — Claude Code's own `/plugin` installs are detected through the public half and re-installed through DorkOS's own transaction, never projected from the cache.** `~/.claude/plugins/` is a private, versioned cache (`installed_plugins.json` carries a version field DorkOS does not control; `blocklist.json` and the catalog cache are 0600) that has already migrated formats once. Projecting out of it would also break the one rule the sweep depends on — the engine only ever deletes what it wrote. The sound source is `enabledPlugins` in `~/.claude/settings.json` (user-owned, documented): read it, report "installed in Claude Code, not visible to other agents", and offer to install the same package through the DorkOS marketplace at global scope, which is the same work DOR-174 needs. Resolving the marketplace a plugin came from needs either `known_marketplaces.json` (private again) or the person's answer; prefer asking.

**D5 — Ask, or just do it?** Do it for anything that **does not spawn a process** (skills, commands, pointers, rules, subagents, `.gitignore` lines, drift repair) — with the honesty that pointers and rules are not harmless, they change what every future session reads, which is why they are reported line by line. Ask once per exact content per project for anything that runs unattended (hooks — shipped; MCP servers — when projected). Do it visibly for lossless moves only where DorkOS owns the directory (D3); ask for every other move and for every lossy merge. And close the CLI hole properly: `dorkos harness sync --fix` **withholds** a package's unapproved hooks, projects everything else, and says so in a terminal block per package and in the summary counts (`codex: 3 native, 1 generate, 2 hooks withheld`) — silence is the failure mode, not the exit code. It exits **0** (a withheld hook is a recorded decision being obeyed, the opposite of a conflict, and exit 1 on a mostly-done sync teaches bootstrap scripts `|| true`), with `--strict` for the CI user who wants a stop. `--allow-hooks <pkg>` installs **and records** the same `<pkg>@<digest>` entry the card writes into `harness.approvedHooks` — one store, one digest, never a per-run override. Refusals become durable beside them (`harness.refusedHooks`, keyed by the same digest so a refusal expires the moment the package changes what it wants to run), and `dorkos harness hooks --list` / `--revoke <pkg>` give VC-05 its first surface. A notice after the write is not consent; a withheld hook that is printed is.

**D6 — How to show it.** VC-01's eight-state model, computed by one read-only call (`GET /api/harness/status?projectPath=…`, as specced), rendered in three places: a **Skills** page on the agent profile that lists every skill (authored, installed, adopted, harness-native) with a per-harness chip row, replacing the skill-pack-only list; a **drift/adoptable banner** with one action; and the drop list as a "Not shared with <harness>" panel with reasons. The CLI already prints most of it; the UI is a projection of the same plan plus the inventory.
