Where a State cell would need a paragraph, the paragraph is in a note under the table and the cell carries a phrase and a pointer.

## The shape of the problem

Every coding agent stores the same handful of project config kinds under a different name in a different place. DorkOS keeps **one canonical source** and **projects** it into each harness's layout (ADR-0301), so one edit — or one install, or one skill an agent writes — reaches every agent a person runs. Four axes decide what a projection is:

1. **Harness** (the target): Claude Code, Codex, OpenCode, Cursor, Gemini CLI, GitHub Copilot (`HARNESS_IDS`, `packages/harness/src/manifest/schema.ts:7`).
2. **Artifact kind**: skills, instructions, hooks, commands, and — not yet in the engine's vocabulary — subagent definitions, path-scoped rules, MCP server config, and whole plugins.
3. **Source class** (where it came from, ADR-0303): authored `.agents/`, marketplace-installed `.dork/plugins/`, adopted from a harness-native dir — plus five classes the ADR never named that §3 adds: a skill an agent writes mid-session, a package installed by Claude Code's own `/plugin`, a skill Codex's `$skill-installer` drops into `.agents/skills`, a package installed at both scopes, and the Operating DorkOS pack DorkOS seeds itself.
4. **Scope** (which directory tree): a project checkout, an agent workspace under `~/.dork/agents/<name>/`, a room worktree, and the global layer (`~/.dork/plugins`, `~/.claude`, `~/.agents/skills`, `~/.codex`, …). A fifth tier sits above all of them for Claude Code — enterprise/managed settings — which a projection can never win against and this doc otherwise does not model.

A capability is only "done" when it behaves correctly on every harness it applies to, from every source class, in every scope — **and the harness actually loads the result** (the H tier). A symlink nobody reads is not a projection. And there is one property that rides every row, from ADR 260706-192819: **the bare CLI and the DorkOS-managed session see the same thing** (AP-14). It is currently false for Codex (SK-14).

**The user-scope half of that table is measured, not just compiled** (DOR-1924, free run, `meta/harness-smoke/20260909-103643.543-claude-user-tier.md` and `meta/harness-smoke/20260909-103636.210-codex-user-tier.md`). In an **empty** project with `HOME` pointed at a throwaway sandbox, a real `codex` 0.145.0 listed a package linked into `~/.agents/skills`, and a real `claude` 2.1.266 did **not** — it listed the same package linked into `<claudeRoot>/skills` and ignored the shared directory entirely. So the two user directories slice A3 writes are two, not one, and neither is redundant. The same run found a **sixth** Codex read path nobody had asked about: a package linked into `$CODEX_HOME/skills/<pkg>__<name>` is listed too, beside the five skills Codex ships there under `.system/`. It is reported as a finding and deliberately NOT added to the table, because no vendor page documents it — the `codex` row's notes say what a refresh has to find.

The one fact that shapes everything: **Claude Code is the only harness that does not read `.agents/skills`.** Every other harness reads the canonical directory natively. So the symlink into `.claude/skills/` is the whole reason the skills half of the engine exists, and every other harness's **authored** skill projection is `native`. Cursor, Gemini and Copilot were DROPPED with "not auto-projected in v1; see DOR-143" until DOR-1847; that reason was true when written, stale by the time it was found, and is now gone (SK-05). The **installed** skill was a different story: it reached `.agents/skills` only through the link the Codex target planned, so with Codex disabled no other harness saw it either — the drop for Cursor/Gemini/Copilot was honest and OpenCode's `native` was not. DOR-1847 made the link unconditional (`planCanonicalSkillLinks`), which turns all four of those cells into an honest `native` (SK-05 note).

The second fact: **OpenCode, Cursor and Copilot read BOTH `.claude/skills` and `.agents/skills`**, so an installed skill linked into both dirs is reachable twice there. Claude Code documents loading a shared target once; OpenCode keyed on frontmatter `name` at the 2026-07 source check, which would collapse the pair; what Cursor and Copilot do with a `pkg__name` folder whose frontmatter says `name` — a name that cannot match the folder and, on OpenCode's and Cursor's stated rules, cannot even be a valid name — is unverified (SK-09, SK-12).

Reading notes. **The drop list is honest about what it finds and blind to what it does not.** That blindness is what DOR-1845 closed: `ArtifactType` grew `agent`, `rule` and `mcp`, `inventory/` walks a source tree per kind, and the rows that used to read **silent** are honest per-harness lines. What the engine still does not do is PROJECT any of them. Until then, `dorkos harness sync --check` on this very repo said nothing at all about its 13 rules and 7 subagent files (5 top-level, 2 nested); it now names each one, and says which harnesses already read it where it sits. Two more silences live **inside** the one kind it does scan: `scanSkillDirs` (`scan/scanner.ts:60-71`) keeps only `Dirent.isDirectory()` entries — false for a symlink — and skips any name containing `__`, so a skill whose source is a symlink and an authored dir named `my__helper` both vanish with no drop line (SK-13, reproduced). **The manifest's policy half was decorative and is not any more** (DOR-1858): the engine read `harnesses` and `claudeOnlySkills` and nothing else, while `skillWrappers`, `commandMappings`, `instructionProjections`, `hookPolicies` and `skillBundles` were validated and unread. `hookPolicies` is now honoured per harness — `none` and `native` stop the engine writing that harness's hooks file and turn each contributing source into a drop naming the manifest, `generate` is what it already did, an absent entry is the default. A `native` line is never suppressed: it is a fact about the harness, not an engine action, so Claude Code goes on reading `.claude/settings.json` under a `none` policy while the installed-plugin merge into `.claude/settings.local.json` stops. The other four are retired — accepted, ignored, and named once per `--check`/`--fix` when a manifest still carries them. **HK-11, the data-loss bug, in full (reproduced by the review against `packages/harness/dist`).** `applyGenerate` (`apply.ts:130-136`) rewrites unconditionally, and `sweepGeneratedOrphans` (`apply.ts:381-402`) deletes every path in `GENERATED_HOOK_TARGETS` the plan does not regenerate — **for every harness, enabled or not**, with no marker or content guard, on the stated assumption (`apply.ts:391-397`) that every such file is engine-owned. Codex's and Cursor's own docs tell people to author exactly those files. A staged Codex-first repo with hand-written `.codex/hooks.json`, `.cursor/hooks.json` and `.github/hooks/copilot-hooks.json` lost **all three** on the first marketplace install — Copilot's while Copilot was not in the manifest. With any plugin hook present the file is overwritten instead of deleted. Through `runAutoProjection` the delete lands on pass 1, **before the DOR-522 card is raised** (pass 1 has zero hook contributors by design, `auto-project.ts:165-186`). `--check` cannot warn: the file is not in the plan, so `checkPlan` never looks at it. Fix shape (settled in review round two): ownership by **sidecar**, not by an unknown key — `<target>.dorkos-generated` beside each generated file holding the sha256 of the bytes written, so the engine owns a target iff the sidecar exists and its digest matches the file (a hand-edited generated file is then a conflict too, which an in-file marker could never tell apart); for Codex, additionally the documented top-level `description` string ("Generated by DorkOS Harness Sync — run `dorkos harness sync` to regenerate"), which reads as a comment and is the same edit as the `hooks` wrapper HK-01 needs; conflict — not merge — on a file without a matching sidecar, with a message naming the way out (move the hooks into `.claude/settings.json`, the one canonical hook source, or delete the file); sweep only files with a matching sidecar, together with the sidecar, and only for enabled harnesses. Merging a hand-written Codex file stays a follow-up gated on the H tier proving Codex tolerates a per-group extra key.

**Two Windows facts the first real runner turned up (DOR-1855) — the first is still open (follow-up: DOR-1883), the second is fixed here.** (1) **A junction is a DIRECTORY to git.** A projection made on Windows is a junction, and `git add` walks into it: the skill's files are committed a second time under `.claude/skills/<name>/` and the tree holds no symlink at all. ## 11. Visibility and consent — what a person sees, and what they are asked

The spec promised a Harnesses page: target toggles, a per-artifact status table (`native · projected · drift · dropped`), a drift banner with Re-sync, and a "Not projected" panel as "Priya's honesty gate" (`specs/harness-sync/02-specification.md:273-290`). **Most of it exists now**, on the agent profile's Skills page rather than on a page of its own (spec `harness-sync-status`, DOR-1891…1896): one row per agent file with a chip per tool and the plan's own reason under each, a "Not shared with `<harness>`" panel per tool, a "Project-level notices" panel, the drift banner and its Sync now button, and — before any click that would delete something — every path it removes with the reason it goes. **What is still missing is the target toggles**, deliberately: turning a tool on writes a file everybody on the project shares, and a side-panel button with no diff and no undo promises more than it fixes (§16 D24), so the page prints the one command instead. The page replaced a list of installed marketplace `skill-pack` packages that told a person with 17 authored, 15 installed and 13 Claude-only skills "No skills installed". **Five of those pieces are now driven in a real browser** (DOR-1896, `apps/e2e/tests/harness/skills-page.spec.ts`): a repository is staged on disk and an agent registered at it, and the spec reads the skill ROWS and their per-tool CHIPS (`projected`, `native`, `dropped`, and the adoptable advice), opens the "Not shared with Codex" PANEL and compares the sentence it draws against the one the API returned, then reads the drift BANNER's removal disclosure, clicks Sync now and reads the "what changed" SUMMARY, checking the named file is gone from disk. What it does not reach, and what therefore rests on the client suite alone: the "Project-level notices" panel, the not-enabled notice, the `conflict`, `pending-approval` and `warned` states, and the two banner branches that offer no action (a conflict, and an adoptable-only tree).

## 13. Edge cases the tests should force

- **Identity**: an authored `foo` and an installed `pkg__foo` whose frontmatter says `foo` (SK-06); a frontmatter `name: 12`; a skill dir with a space, uppercase, or `--`; a `SKILL.md` with no frontmatter; two plugins shipping the same skill name; a skill and a command with the same leaf name (CM-05); a nested `.claude/skills` in a monorepo package (SK-15); two skills differing only by case on macOS (AP-16).
- **Symlinks**: a dangling managed link (SK-10); a dangling link at a generate/scaffold target (AP-05); a **symlink at the source** — silently skipped today (SK-13), while Codex follows it; a symlink loop; an absolute symlink a person made by hand at a managed target (wrong link text → replaced — is that right for a link that resolves?); a dork home reached through a symlink (covered); Windows junction vs. `core.symlinks=false` checkout (J-10).

## 16. Positions this document takes

The audit asked five product questions. Each is answered as a recommendation with its reason, revised after the review, so the eventual ADR has something to push against. None is settled by this file.

**D1 — First contact must be safe, honest, and re-runnable.** An existing project's skills "just projecting" is not the current behaviour for any of the three entry cases: J-01 enables nothing but Claude Code and never re-detects, J-02 loses files, J-03 is silent about two kinds. In order: the generated-file ownership sidecar and the Codex file shape (HK-11, HK-01 — one edit), the vocabulary and inventory (§8, SK-13), a detection pass that re-offers newly present harnesses (TR-11), and only then adoption.

**D2 — A skill an agent creates in the canonical location is projected automatically.** Settled and SHIPPED (DOR-1850). It was a trigger problem only, and the trigger inherits the hook gate, never sweeps, and never scaffolds a manifest — so it only ever writes into a project already set up for sync. Two things the design note did not anticipate. A directory with no `SKILL.md` yet is not "debounced", it is simply never a trigger: `addDir` is not wired up at all, so the projection that matters is the one the file itself causes. And a watcher is not sufficient, for a reason sharper than a loss rate: chokidar cannot watch a directory that does not exist, so a project's FIRST skill is missed 100% of the time until something opens the watch — a one-second re-arm, with a ten-second shape comparison behind it. (Events dropped just after a watch opens are real too, at 13-40%, but that is a startup window a settle closes, not the steady state.) The restart caveat in §1.1 is said in the output, once per project and only when the run created `.claude/skills/`, quoting its page and its date.

**D3 — Adopt is reported everywhere, and moves one skill only when a person asks.** Settled and SHIPPED (DOR-1853). The first draft proposed auto-moving skill directories out of `.claude/skills` into `.agents/skills` by default. The review is right that this does not hold: once a directory is physically in `.agents/skills`, five harnesses read it natively, and a `drop` line has no power over that — so an auto-move is a one-way, unrevocable exposure of exactly the skills a person kept Claude-only on purpose (`context: fork`, `disable-model-invocation`, `paths`); `manifest.claudeOnlySkills` cannot un-expose it, and per SK-04 only fires after the move anyway. "`git status` shows a rename" is false for a directory (N deletions + N additions) and false twice when `.agents/` is gitignored (AP-15), where a teammate's clone would lose the skill outright. And the non-destructive shape (leave the dir, link from `.agents/skills`) is not available either — though NOT because of SK-13, which this round attributed it to in error: R5 refuses a symlinked SOURCE because DorkOS cannot tell whether a person meant the link or the folder behind it, which is a question about intent rather than about the scanner's blind spot (spec `harness-sync-adopt` Deviation 14). Round two took the last step too: **report-only everywhere in v1, DorkOS-owned directories included.** An agent is runtime-agnostic (`runtimeRegistry` binds a session, not an agent), so a skill auto-moved inside an agent home is exposed to that same agent's next Codex session; a frontmatter denylist of "Claude-only fields" is a guard that must be remembered every time Claude Code adds a field; Claude-only-ness often lives in the body (`${CLAUDE_*}` tokens, `/reload-plugins`), which SK-07 already knows and a frontmatter guard ignores; and an agent home has no `git status` and no reader — the boot pass runs unattended, so the one mitigation a move relies on, visibility, is weakest exactly there. So: compute `unmanaged (adoptable)` (VC-01) and **report** it in every sync and boot summary; `dorkos harness adopt <name>` moves one skill, refusing when `.agents/` is gitignored and, in a room worktree, when the name is one of the seven seeded ones (SRC-11's reap); `harness.autoAdopt` defaults **false everywhere** and is merely _permitted_ in agent homes and room worktrees — and when it is on, the guard is an **allowlist**: move only a skill whose frontmatter holds nothing outside the agentskills.io base fields and whose body carries no `${CLAUDE_*}` token; everything else is reported, never moved. That inverts the failure mode from "adopts unless the danger was recognised" to "adopts only what was recognised as safe", which is the only version that survives a vendor adding a field. The status surface (D6) shipped first, as this said it should. **Two clauses the code corrected as it landed.** The move does NOT need the marketplace transaction's stage → backup → rename → restore shape: that module stages because it BUILDS content and backs up because it OVERWRITES an occupied target, and adopt does neither — R4 refuses an occupied target outright and the content it moves is already whole, so one `rename(2)` with a restore on failure is both smaller and stronger (spec Deviation 4, AP-17). And `harness.autoAdopt` is not "merely permitted" by a runtime check that could be forgotten: it is read at exactly two call sites, both of which have already established DorkOS owns the directory, so a `true` anywhere else is inert by construction and `dorkos harness sync` says so once (S8).

Two clauses the code corrected on the way in. The move is **never** automatic, in a DorkOS-owned directory either — round two took the last step to report-only everywhere — and the non-destructive shape this position once called impossible (leave the directory, link into it from `.agents/skills`) is possible today, since SK-13 shipped; the move still wins, on three stated grounds rather than on impossibility (`specs/harness-sync-adopt/02-specification.md` §1.3). Adoption also produces an **authored** skill rather than a third provenance: `Provenance`'s `'adopted'` value is retired (SRC-10).

**D4 — Claude Code's own `/plugin` installs are detected through the public half and re-installed through DorkOS's own transaction, never projected from the cache.** `~/.claude/plugins/` is a private, versioned cache (`installed_plugins.json` carries a version field DorkOS does not control; `blocklist.json` and the catalog cache are 0600) that has already migrated formats once. Projecting out of it would also break the one rule the sweep depends on — the engine only ever deletes what it wrote. The sound source is `enabledPlugins` in `~/.claude/settings.json` (user-owned, documented): read it, report "installed in Claude Code, not visible to other agents", and offer to install the same package through the DorkOS marketplace at global scope, which is the same work DOR-174 needs. Resolving the marketplace a plugin came from needs either `known_marketplaces.json` (private again) or the person's answer; prefer asking. **Built in DOR-1921, and two clauses were corrected by what the code turned out to hold.** Asking was not needed after all: the public half carries `extraKnownMarketplaces`, so a plugin's marketplace resolves to a repository and matches a DorkOS source on THAT rather than on a local name — measured, that folds Claude Code's `dorkos` and DorkOS's `dorkos-community` into one repository, which a name match misses. And the offer points at **project** scope, not global: a DorkOS global install today reaches only the Claude Code sessions DorkOS itself runs, so somebody who already has the plugin in Claude Code would trade one Claude-Code-only copy for another, while a project install reaches every enabled agent tool through the projection that already works. The position itself stands: the private cache is still never opened.

**D5 — Ask, or just do it?** Do it for anything that **does not spawn a process** (skills, commands, pointers, rules, subagents, `.gitignore` lines, drift repair) — with the honesty that pointers and rules are not harmless, they change what every future session reads, which is why they are reported line by line. Ask once per exact content per project for anything that runs unattended (hooks — shipped; MCP servers — when projected). Do it visibly for lossless moves only where DorkOS owns the directory (D3); ask for every other move and for every lossy merge. And close the CLI hole properly: `dorkos harness sync --fix` **withholds** a package's unapproved hooks, projects everything else, and says so in a terminal block per package and in the summary counts (`codex: 3 native, 1 generate, 2 hooks withheld`) — silence is the failure mode, not the exit code. It exits **0** (a withheld hook is a recorded decision being obeyed, the opposite of a conflict, and exit 1 on a mostly-done sync teaches bootstrap scripts `|| true`), with `--strict` for the CI user who wants a stop. `--allow-hooks <pkg>` installs **and records** the same `<pkg>@<digest>` entry the card writes into `harness.approvedHooks` — one store, one digest, never a per-run override. Refusals become durable beside them (`harness.refusedHooks`, keyed by the same digest so a refusal expires the moment the package changes what it wants to run), and `dorkos harness hooks --list` / `--revoke <pkg>` give VC-05 its first surface. A notice after the write is not consent; a withheld hook that is printed is.

**D6 — How to show it.** VC-01's eight-state model, computed by one read-only call (`GET /api/harness/status?projectPath=…`, as specced), rendered in three places: a **Skills** page on the agent profile that lists every skill (authored, installed, adopted, harness-native) with a per-harness chip row, replacing the skill-pack-only list; a **drift/adoptable banner** with one action; and the drop list as a "Not shared with <harness>" panel with reasons. The CLI already prints most of it; the UI is a projection of the same plan plus the inventory. **Shipped as** the agent profile's Skills page (`?profilePage=skills`, DOR-1891…1896): all three places, in one page rather than a route of its own — the drift banner with its Sync now button at the top, one row per skill with a chip per tool, a "Not shared with `<harness>`" panel per tool carrying the plan's own reasons, and a "Project-level notices" panel for the entries that are about a package rather than about any tool. Two pieces of the recommendation did NOT ship, both deliberately: the target toggles (§16 D24 — turning a tool on writes a file the whole project shares, so the page prints the command instead), and `adopted` provenance, which has no producer until `dorkos harness adopt` exists (SRC-10).

## 17. How this list is used

- A harness feature adds its rows here in the same PR, and a stale/silent/false-native row that becomes built flips its state and cites the test.
- **The Coverage cells are checked, not trusted.** `packages/harness/src/__tests__/capabilities-census.test.ts` requires that every row claiming `U`/`C`/`E` has a test whose title carries its ID, that every `built` row has a coverage cell, that no title names a row this document does not define, and that every gap §14 struck through as closed has a test. A test whose subject is a row therefore starts with that row's ID: `it('SK-04: …')`. `pnpm verify` is affected-only, so an edit to THIS file runs nothing locally — run `pnpm vitest run packages/harness/src/__tests__/capabilities-census.test.ts` by hand; the merge queue's full sweep is what catches it otherwise, and a `turbo.json` `inputs` override keeps that sweep from replaying a cached green over a changed document.
- The testing plan that accompanies this inventory (`plans/harness-sync-test-plan.md`) turns §9 into property tests, §12 into journey fixtures with exact before/after tree diffs, §1 into a dated per-cell `vendor-facts` table plus a source-tree inventory the completeness check reads, and the H tier into a scripted, flag-and-key-gated, not-in-CI smoke per harness binary whose oracle is the harness's own listing or an activation side effect, never a model's say-so.
- The self-test convention from chat-capabilities §11 applies unchanged when an S tier exists: `mode:sandbox` for the file-shape half, `mode:live` for a real harness, and a report that cites these IDs.
