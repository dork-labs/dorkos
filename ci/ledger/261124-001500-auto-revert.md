Dorian, Nov 23 (DOR-5122): auto-revert of a merge that turns main red is approved, never the
release commit. When a push-to-main workflow fails, `auto-revert.yml` re-runs the failed jobs once.
If it fails again, the same workflow was green on the parent commit, main has not moved on, and no
revert is open, it opens a revert PR with auto-merge on, and tells the author to fix forward. It
skips release commits and reverts of reverts.

Nov 25 fix: a ROLLING workflow's first failure (browser-test's push run, listed in
`ROLLING_WORKFLOWS` in `auto-revert.sh`, pinned to rolling-bisect.yml's `workflows:` by the
fixtures) is re-run before the green-parent rule. browser-test failed at 7878dda (attempt 1) and
`decide` answered `skip red-before-this-merge` because the parent had no run of its own, so attempt
2 never happened and rolling-bisect never started. A non-rolling run keeps the order above.

It lands switched off: the revert job runs only when the repo variable `AUTO_REVERT` is `on`. It
pushes with the merge-tail app token, the same one dependabot-lockfile-repair uses, because a
GITHUB_TOKEN push starts no workflows. Until then the decision is logged on every failure, which is
the dry run.

Baseline (Nov 23): main stayed red for hours across several merges (83c296b6e4) until people fixed
it by hand.
Target: with AUTO_REVERT on, a merge that breaks a push-to-main check is reverted, through the
queue, within 60 minutes, and no good merge is reverted.
Evaluate: Dec 1, against the logged decisions.

Revert if it ever reverts a merge whose parent was already red, or a release commit.
