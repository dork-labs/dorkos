Pull request pushes were starving the merge queue of runners. The plan has 60 concurrent jobs, a
queue build needs about 30 of them, and one PR push started about 25 jobs, so every push competed
with every queue build and usually won. On 2026-10-30 at 23:30 UTC, 46 PR runs were active while a
queue build that started at 22:45 had not been given a runner.

Two changes in `test.yml`, both on the `pull_request` leg only. The queue and the main canary run
exactly what they ran before.

- `test-shard` runs 2 shards on a pull request instead of 6. The PR leg is still affected-only and
  still reports the required `test` context. Two, not one: the unsharded PR leg ran 37 minutes on a
  PR touching `@dorkos/shared` and was killed at its ceiling (DOR-1731), so a single runner would
  bring that back. Two runners keep the widest PR sweep near 20 minutes against the 30-minute limit.
- `community-pg` is skipped on a pull request. It was the one unscoped suite on the PR leg: 10 to 15
  minutes, a Postgres service and a Chromium install on every push, whatever changed. The `test`
  fan-in accepts `skipped` on `pull_request` only; on `merge_group` and the canary it still demands
  `success`.

Together that is 5 fewer runners per push (25 to about 20) and, on a wide PR, roughly 70 fewer
runner-minutes. Kept on the PR leg on purpose: lint, typecheck, and every job that is already scoped
to what a change touches (`community-packaged`, `harness-windows`, `site-build`, `openapi-fresh`,
the `harness` fixtures). `credential-free-build` is a candidate for the next change; its PR-only
turbo cache makes it its own experiment.

What this can make worse, and the revert condition, written before the result: a broken community
suite or a test the 2-shard PR leg would have caught is now found in the queue, where it ejects a
build. Watch `gate.wf.test.community-pg.ejections_caused` (baseline 6 in the 7 days to 10-29, most
of them one hang #3271 has since fixed) and `wasted-queue-builds`. Revert either half if
`wasted-queue-builds` rises past its floor while `queue-build` does not improve, or if
`community-pg` causes more than 3 ejections a week that a PR run would have caught first. Report
`pr-feedback` beside it: two shards make a wide PR's feedback slower, and that is the price.
