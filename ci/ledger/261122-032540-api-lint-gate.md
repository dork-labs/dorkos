The REST API review found the API drifting with nothing to stop it: no operation carried an
`operationId` (DOR-4980 has since given every operation one, so that rule starts at zero),
many paths end in a command word, error responses use inline shapes, most
list GETs are unpaged, and hundreds of served routes are missing from the OpenAPI document.
Two of seven recent HTTP merges shipped routes with no document entry, and no gate noticed
(DOR-4996, parent DOR-4977).

This adds `API lint gate (DOR-4996)` to the required `typecheck` job, beside the file-size
ratchet. `scripts/api-lint/check-api-lint.ts` reads two committed JSON files (the OpenAPI
document and the route census) plus the `registerPath(` calls in the hand-written registry,
and holds nine rules to `scripts/api-lint/baseline.json` per route group: a count may only
fall, and two operations may never share an `operationId`. One rule,
`hand-registered-path`, is advisory until the capability HTTP mount (DOR-4978) merges: it
is measured and printed but never fails, and that merge flips it to blocking. `--base` refuses a baseline
raised by hand, with the base chosen as the file-size ratchet chooses it.

Hypothesis: a static read of two committed JSON files (and the few dozen hand registry
files) adds no measurable time to the required job, so a new API guardrail costs no CI
capacity. The target allows 0.1 minute of
noise over the baseline median. The quality claim (no new undocumented route, unpaged
list or command-word path merges) is enforced by the ratchet itself on every run, and
`tracked.escaped` is not scored here.

Revert, or move the step, if the job's median grows past the target, or if the step reds a
PR for a reason the step's own message does not name.
