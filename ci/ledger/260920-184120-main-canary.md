## What was wrong

Nothing watched `main`. `test` and `browser-test` run their real suites on
`merge_group` only, and the push-to-main legs were retired on 2026-09-19
(`260919-175509-retire-push-main-legs.md`) on the correct argument that the
queue already tested the byte-identical tree. Both statements are true and
together they leave a hole: once a commit is on `main`, nothing ever looks at it
again.

So a break that lands is found by the next PR being ejected by it. On
2026-09-17 a fixture pinned the browser clock past Today's 04:00 boundary
(#1916). It was green in every queue build outside 00:00–02:00 UTC, hid for
three days, and then ejected #1930, #1932 and #1933 about nine times in one
evening before a person diagnosed it (#1934). 66 hours to detect, and the
detection cost three blameless pull requests.

## What this does

The required suites now also run against `main` HEAD on a schedule:
`test.yml`, `browser-test.yml`, `typecheck.yml` and `lint.yml` gained
`schedule:` (four slots a day) and `workflow_dispatch:`.

**One definition of each suite.** There is no canary workflow. The steps that
read `github.event_name == 'merge_group'` now read `!= 'pull_request'`, which is
the same two-way split those workflows always had — full sweep everywhere but a
PR — with the canary on the full side. A second file re-stating `turbo test` or
the Playwright suite could drift from what the queue runs, and a canary that
disagrees with the gate is worse than no canary.

**It cannot touch a pull request or the queue.** A required context is required
on the `pull_request` and `merge_group` events. A `schedule` run reports on
neither, belongs to no PR and to no queue build, opens nothing and arms nothing.
The worst a red canary can do is print a red run and a line in the daily report.
It is not a required check and must not become one.

`credential-free-build` is deliberately out: it is an affected-only build that
reads a base SHA no scheduled run carries, and at a 21% failure rate it would
cry wolf daily. `copy-spec-drift` is out for the same reason — it diffs against
a base. The PR-diff checks (`fragment-present`, `no-fragment-under-skip-label`,
`version-outranks-base`, `db-check`) measure a diff, and `main` has none.

## Keeping the SLO populations clean

The canary reuses the existing jobs, so its runs carry the **same gate ids** as
the PR and queue legs and are told apart only by the run's event. Three changes
keep that from polluting anything:

- **`gateDays(gates, gate)` with no event now skips `CANARY_EVENTS`**
  (`schedule`, `workflow_dispatch`). That one change fixes the two readers that
  aggregated a gate across every event: the `headroom` tripwire in `slo.ts`
  (rank 1 in the constraint precedence, so the worst thing to false-flag) and
  the ratios half of `gateWindow` in `triggers.ts`. Asking for a canary event by
  name still returns it, so `…@schedule` reads the canary leg on purpose.
- **`gateWindow`'s main loop skips them too**, so `gate-failure-spike` and
  `gate-cost` describe what merging costs and nothing else. Without this, a
  canary doing its job — going red on a broken `main` — would fire a spike
  trigger against the queue's leg of the same gate.
- **`main-green` is untouched.** `mainCommits` filters `event === 'push'`, and
  that filter is now load-bearing and commented as such: folding the canary in
  would redefine the SLO in the middle of the experiment that added it (plan
  §4.9, round-5 follow-up 4). A regression test pins it.

`pr-feedback`, `queue-green`, `queue-build`, `wasted-queue-builds`,
`review-completes` and `review-recovery` were already clean by construction —
each filters strictly on `r.event` in `series.ts`.

The canary's own results live in a new `canary: []` array on each snapshot, from
`ci/config.yaml`'s `canary.workflows` list. That list is exhaustive on purpose:
`ci-steward.yml`, `evals.yml` and `codeql.yml` also run on `schedule` against
`main`, and reading the collector's own tick as a canary result would report the
pipeline healthy on the strength of the run that said so.

## The metric, and why it is this one

`tracked.time-to-detect`: per canary result, the minutes since the previous
result of the **same** canary workflow; reported as p90. A break lands between
two canary runs, so that gap is the upper bound on how long it can hide.

The obvious metric — merge of the breaking commit to first red canary — cannot
be read on a healthy week, and `main` is usually green. A metric with no value
until something breaks produces `inconclusive` verdicts forever and tells you
nothing about whether the canary is still running. This one is readable every
day, and it degrades in exactly the way that matters: if GitHub stops delivering
the schedule, p90 blows up and the experiment fails.

**Baseline 3964 minutes** is the 09-17 → 09-20 incident, cited above, and it is
one observation rather than a distribution — because before this change nothing
was measuring. **Target 720 minutes (12 h) p90.** Four slots six hours apart,
plus the skew below, plus a ~30-minute run: 12 h is reachable and not free. If
it lands at 15 h the verdict is `partial`, which is the honest answer.

## What four crons buy, given the throttling

**The evidence is `evals.yml`, not merge-tail.** merge-tail asks for a run every
ten minutes and gets about seven a day; the "162-minute median" from it is the
gap between DELIVERED runs — a statement about how many requests GitHub drops,
not about how late any one is. The right comparable for a low-frequency cron is
`evals.yml`'s `0 8 * * *`: **57 runs, 100% delivered, lateness p50 2.60 h, p90
5.61 h, max 11.88 h.**

Two consequences, pulling opposite ways:

- a low-frequency cron is **not dropped**, so all four rounds arrive and the
  canary does not quietly stop;
- each arrives hours late, and the delay is **shared across the day's slots**
  rather than drawn fresh per slot, because it tracks how busy the Actions
  scheduler is. Four slots are four correlated shots at a window, not four
  independent ones.

So no cron schedule here can promise a run inside a named two-hour window. The
slots (`0,5,10,21` UTC, minutes 29/33/37/41 for typecheck/lint/test/browser)
are chosen against the skew rather than the clock face: a run fired at hour H
lands near H+2.6 at the median, so `0` hits the 00:00–02:00 window when close to
on time and `21` hits it at the median, `5` lands near 07:36 in the queue's
07:00–11:00 trough, and `10` fills the afternoon. Nothing is fired inside the
queue's busiest stretch (17:00–02:00) except the slot whose landing zone is the
dark window.

What that buys:

- a break on `main` found in **hours rather than days**;
- the 00:00–02:00 UTC window hit on **about one day in three**, and **about six
  days in seven** (86.3% empirical). Not the ~95% independence would give:
  lag-1 autocorrelation of the daily lateness is **0.754**, and the longest
  measured blind streak is **12 days**. **Two weeks is the honest
  near-certainty**, and that is why `after_days` is 14.

Deliberately weaker than "we watch the dark window". A real time-of-day bug is
caught here by repetition over a fortnight, not by an appointment. The stronger
fix — a leg that runs the browser suite under an injected clock — is a separate
change and is not claimed here.

## Cost

**The first numbers I wrote were low, and here is why.** A 7-day window ending
2026-09-19 straddles #1912, which changed what a `test` run costs, so its 53.5
job minutes describe a shape that no longer exists. On the CURRENT shape the
median `test` run is **67.0** minutes. With `browser-test` ≈ 67.3, `typecheck`
≈ 5.2 and `lint` ≈ 6.3, one canary round is **≈ 150 job minutes** and four a
day is **≈ 600**. In jobs it is 13 a round (seven in `test`, four in
`browser-test`, one each in `typecheck` and `lint`), so 52 a day against 1,841.

Against what, though — the denominator decides the headline, so all three:

| Denominator                        | Job minutes/day | The canary is |
| ---------------------------------- | --------------- | ------------- |
| 2026-09-15, the day I first quoted | 9,196           | +6.5%         |
| the 8-day mean                     | ~5,400          | **+11%**      |
| a quiet day                        | ~1,200          | **+50%**      |

**+11% is the honest figure**, and +50% is what a quiet Sunday looks like,
because the canary's cost is FIXED while everything else's is proportional to
how much was merged. That is also exactly why its minutes are kept out of
`job_minutes` and carried as `tracked.canary-minutes`: charged to merged PRs,
the canary would make per-PR cost rise on the weeks the pipeline did least.

The repository is public, so these are unbilled runner-minutes; the real price
is contention on the pool the queue shares, which is why the slots are spread,
the minutes staggered, and one round aimed at the 07:00-11:00 trough.

If that price shows up — as `gate-cost:job-minutes-per-merged-pr`, as
`tracked.canary-minutes` growing, or as queue wait — the cheaper canary to fall
back to is the full vitest sweep plus `playwright test --grep @smoke` on ONE
shard instead of the full browser suite on three: roughly 45 job minutes a
round cheaper, about a third off. It is defensible rather than arbitrary: the
spec that broke on 09-20 is inside a
`test.describe('Mobile tabs — 390×844 @smoke', …)` block, so `@smoke` would have
caught that exact incident. Take the full suite off only under measured
pressure, and record it here.

## How this could be wrong

- **The schedule stops and nobody notices.** A canary that never runs reads
  exactly like a healthy `main` in every other number. That is why the trigger
  has a silence arm at 18 hours and the daily report prints "0 main-canary
  runs — nothing checked main today" rather than omitting the line.
- **The canary cries wolf, and I have pre-committed to the number that will.**
  At the measured **5.1% per-shard failure rate**, one red round out of four a
  day fires the rank-2 red trigger on **about 46% of days**. That is the
  arithmetic of `canary_red_min_runs: 1`, it is written here BEFORE the data
  comes in, and it is still the right setting: the 09-20 break was
  deterministic inside its window, and waiting for a second round costs another
  six hours of cron for a signal the first already gave. A red costs one line
  in a report and never a merge, and clears itself on the next green round.
  `browser-test` also ran at a 56% queue failure rate over 09-03 → 09-07 (#1664
  / DOR-1818) and the analysis meant to separate flakes from breaks was never
  done, so if 46% turns out to be noise rather than signal, raise the threshold
  to 2 **with an entry here**, accepting that it doubles detection latency — or
  fix the flake. Do not widen it quietly; `ci/config.yaml` is inside the fence
  for exactly this.
- **The guard had to be inline, and the first version was not.** The ref check
  shipped as `bash scripts/assert-canary-ref.sh` as step 1 of all eight jobs —
  before `actions/checkout`, where the workspace is still empty. It would have
  exited 127 on every event and reddened four required checks on every pull
  request and every queue build, and its fixtures could not see it because they
  resolved the script by absolute path. It is inline now, and
  `canary-ref-guard.test.ts` extracts the shipped `run:` block, executes it,
  and pins that it stays step 1 and reads no file from the workspace. The same
  127 killed a required check on 2026-07-29, which is why "Prove the browser
  suite actually executed" carries a `[ -f ]` guard.
- **A skipped job is not evidence a gate runs on the merge path.** The first
  `mergePathGates` counted any key with `runs > 0`, which on live data is inert:
  `wf.evals.structural@pull_request` carries `runs: 32` with
  `{skipped: 32}` on all 15 days it appears, and there is no zero-run
  merge-event key anywhere. So the gate joined the merge-path set on 32 jobs
  that never ran and every scheduled duration was still dropped — headroom n
  unchanged at 8727, `wf.evals.structural` still at 0. The guard subtracts
  skipped now, and the test is pinned on the shape the data actually has
  rather than on a hand-built zero-run key.
- **`canary_since` cannot rest on the data branch.** It lives in
  `triggers.json`, and `readData` returns null for a MISSING file exactly as it
  does for a fresh one — so a rewrite, or a prepare step from an empty tree,
  while the canary was dead and its last result had aged out, would have
  returned the arm to the silence it exists to break. The floor is this entry's
  own id date, read from `main`: one silence threshold after the day it landed,
  "nothing in the whole window" is red whatever the data branch says.
- **Silence takes about 39 hours to notice, not 18.** A day is collected the
  morning after, and every trigger rule reads the reported day's end rather
  than the wall clock so a page rebuilt by hand reaches the same answer. So an
  18-hour threshold plus the rest of the day plus the collector's own delay is
  ~39 hours worst case. Tightening the threshold does not fix that; collecting
  more often would, and that is a different change. The number is stated in
  `ci/config.yaml`, in `contributing/ci.md` and in `canary.ts` so nobody reads
  18 as a promise.
- **The target is unreachable because GitHub drops runs.** Then the verdict is
  `failed` and the answer is event-driven dispatch (plan §4.9's targeted
  canary, which this change's `workflow_dispatch` leg already exposes), not a
  looser target.
