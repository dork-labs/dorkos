Three shards were cut at the 30-minute limit on 2026-11-03, and no test hung. Queue run 41686006176 shard 4/6 passed its whole sweep and was cancelled during its last upload, which ejected #3479. The other two: PR run 41680621824 attempt 2 shard 1/6 and PR run 41682618978 shard 3/6.

Two things stack up. The figures are queue shards, the newest 12 runs per day, from the GitHub API.

- **New on Nov 3: slow checkout.** `actions/checkout` with `fetch-depth: 0` fetches every branch and tag of a 600 MB repo. It took p50 0.3, p90 0.4 minutes through Nov 2, then p50 0.8, p90 3.6 on Nov 3, from about 14:00 UTC, with 15.6 minutes in the worst PR run. Other setup steps did not move. The same slow checkout used 9m42s of `openapi-fresh`'s 10-minute limit in run 41691476608. GitHub's status page shows a Git incident from 13:25 to 13:56 UTC, which ended before this began, so the cause is not known.
- **Slow growth: the suite.** Sweep p50 went from 19.2 minutes (Oct 16) to 23.5 (Nov 3). All six shards grew by about the same amount, so no one slow file explains it (test files were not ranked). In one shard's logs from Oct 18 to Nov 3, the server suite grew from 5650 tests to 6736.

Sweep speed also varies: shards in one run differ by about 9 minutes, and the same shard ran its server suite in 390 s on one run and 675 s on another with about the same tests. Builds slowed by a similar ratio, which points at runner speed, but nothing in the logs proves it.

45 covers the worst parts seen on one day: 15.6 of checkout, 26 of sweep, 1.5 of the rest, about 43 minutes. It puts Nov 2's p90 of 26.1 minutes at 58% of the limit and Nov 3's p90 of 28.4 at 63%, against the 60% headroom objective. The merge queue's own check limit is 120 minutes, so that is unaffected. The cost: a truly stuck shard holds its runner for 15 more minutes.

This is a stopgap, and it goes against entry 261016-121046, which said not to raise this ceiling. It is raised only because a slow checkout is not something work division can fix. It does not shorten anything, so job duration is the wrong metric here. `ejections_caused` is the closest in the catalogue, but real reds dominate it, so also read cancelled-at-limit shards by hand when the window closes: the target is zero. Revert to a lower limit once DOR-3769 lands (a narrower checkout and more work division). Revert sooner, or re-plan, if the sweep's p90 passes 30 minutes: then the suite is outgrowing the stopgap.
