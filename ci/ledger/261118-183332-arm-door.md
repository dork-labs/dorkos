The local arm script is the one place that runs every gate before a pull request is queued:
Security's label at the head, QA's and the designer's sign-offs, and a verify proof or a logged
waiver. Nothing on GitHub enforced that. Every agent acts as one login, so a bare
`gh pr merge --auto`, a GraphQL enqueue or merge-tail's schedule queued a pull request exactly as
the script does, and two did in two days.

The change: the arm script stamps the head with an `arm-record` commit status (agent, session,
proof) just before it enqueues. `.github/workflows/arm-door.yml` runs on
`merge_group: checks_requested`, the one event every queue entry raises whoever queued it, and
`scripts/arm-door.sh` takes the entry back out when the head's newest `arm-record` is missing or not
`success`. It tells the author once per head. Like queue-repeat-guard, it dequeues only on proof
and stays green, so it never adds a red to a merge-group build. It is not a required check, so the
ruleset is unchanged.

Limits: a stamp is not a signature. Any session holding the shared login can post one by hand.
This stops the mistakes seen so far, not a session set on lying; per-role GitHub Apps (DOR-3183)
are the real fix. Merge-tail's arms are dequeued too until it runs the same gates as the arm
script, which is the condition for re-enabling it.

Revert, or narrow it, if it takes out a pull request the arm script did arm (a stamp lost between
the status write and the queue's read) more than once in the window.
