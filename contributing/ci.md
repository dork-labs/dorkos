# CI Pipeline Guide

## Overview

This guide covers everything between an agent's edit and a change on `main`: the local hooks, the GitHub Actions checks, auto-merge, the merge queue, and CI Steward, the system that records and judges every change to the pipeline itself. Merges into `main` are fully autonomous, with no human approval ever, so the pipeline is the only thing between an agent and `main`. It is written for agents first: exact commands, exact paths, and the rules that stop twenty agents from making one incident twenty times worse.

## When to Use What

| Situation                                                                                                                             | Do this                                                                                                                                                         | Why                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| You changed a workflow, `lefthook.yml`, `turbo.json`, `.claude/settings.json`, a gate script, `ci/**` or `packages/ci-steward/src/**` | Add a ledger entry with a hypothesis in the same commit                                                                                                         | Every pipeline change is an experiment; the coverage step checks for the entry                                   |
| You want a check to become required                                                                                                   | Land the job (reporting on `pull_request` **and** `merge_group`, no `paths:`) plus `ci/required-checks.json` plus a ledger entry first; edit the ruleset second | A required check that never reports deadlocks the queue                                                          |
| You want to stop requiring a check                                                                                                    | Ledger entry and `ci/required-checks.json` first, ruleset edit second, delete the job last                                                                      | The ruleset must never require something the declared intent does not                                            |
| Your PR is behind `main`                                                                                                              | Nothing                                                                                                                                                         | The queue tests the combined tree; being behind blocks nothing                                                   |
| A PR check failed and it is yours                                                                                                     | Fix and push                                                                                                                                                    |                                                                                                                  |
| A PR check failed and it is not yours (red elsewhere, infra)                                                                          | `gh run rerun <run-id> --failed`, once                                                                                                                          | One job, not a 19-to-25-job round                                                                                |
| Your PR was ejected from the queue for failed checks, first time                                                                      | Read the failing job; once it is plainly not yours, re-queue once: `gh pr merge --auto <n>`                                                                     | 85% re-pass unchanged                                                                                            |
| Same check ejected it twice on the same head commit                                                                                   | Stop re-queueing. It is a regression only the queue can see: read the log, fix, push                                                                            | The queue tests your change on top of everything ahead of it; `queue-repeat-guard.yml` takes it out again anyway |
| The queue itself is broken or backed up                                                                                               | Say so; do not push, rerun or re-queue                                                                                                                          | Load is the problem. Incident mode (freeze, shed, break-glass) is phase 1b                                       |
| A run sits in `queued` and looks stuck                                                                                                | Leave it. Never cancel a queued run and re-run it                                                                                                               | Queued means waiting for a runner; a re-run goes to the back of the line (about 55 a week did this, Oct 23–30)   |
| You are tempted to merge with admin rights                                                                                            | Don't. Auto-merge (`gh pr merge --auto`) only                                                                                                                   | Admin merges skip every required check; reserved for `/ci-break-glass` (phase 1b)                                |

## How a change reaches `main`

```
EDIT     Claude Code hooks: four PreToolUse guards on every Bash call; typecheck, eslint and an any-ban on every edit
TURN END prettier --write on changed files (Stop hook); checkpoint in worktrees
COMMIT   lefthook pre-commit: prettier, drizzle generate, dir-size, turbo lint --affected (under the machine-wide slot cap). No typecheck at commit
PUSH     lefthook pre-push: changed-file formatting, fragment validity, file-size ratchet, pipeline ledger coverage, CI still running from the last push. No tests run at push (DOR-2160)
PR       ~19-25 Actions jobs; the required checks below must pass ON THE PR before it may enter the queue
AUTO     open-pr.sh turns on auto-merge at open; GitHub queues the PR once every required check (pr-gates: Security) is green
DOOR     queue-repeat-guard reads each queue entry and takes out a head that failed the same check twice
QUEUE    merge_group: the required checks re-run on main + everything ahead, up to 5 PRs per group, ALLGREEN (browser: the scoped @smoke shards)
MAIN     squash merge; push-to-main legs: the full browser suite and first-run (a rolling run), db-check, CLI smoke, scripts-test, desktop smoke
```

### Security approval per commit

`security-gate` verifies `security-review=success` on every exact PR head in a
queue group. Sensitive diffs require the newest success creator to be the
workflow-pinned numeric Security bot user ID; a later user success invalidates an older App
success. The numeric ID remains zero until Dorian creates the App.
Use the compiled `tools/security-approve` helper with its exact cdhash-pinned
Keychain item; setup is in [Security gate promotion](../ci/security-gate-promotion.md).
Complete nonsensitive diffs keep the trusted initializer's automatic success.
Labels grant no approval. A new sensitive head needs Security's
status; automatic "no security paths" success cannot approve a sensitive diff
against a different base. Missing or stale membership fails closed.

Both verifier legs check out the event's immutable base commit and have only
contents/statuses/pull-requests read permission. Only `security-review-initialize.yml` can write,
from trusted base code: on `pull_request_target` it writes the `security-review` verdict on every
label, push and edit (`.github/scripts/security-verdict.mjs`), and on `merge_group` it writes the
queue's verdict on the group's SHA. It comments once per observed
SHA/state transition, recording that observation's status author and ID. Replacing
a status with the same state adds no comment. It never renders `target_url`.
After Security approves, rerun the PR verifier. While a PR is only waiting (no
Security label yet, or `hold` on and no Security label on it is wrong), the PR
run of `security-gate` succeeds with a "Waiting for Security" annotation instead
of failing, and main's `security-review` status says `pending` rather than `failure`
(a P0 path still lacking `security-deep-reviewed` is waiting too; a workflow or
judge-file edit lacking it stays `failure`). It approves nothing: `security-review` stays short of `success`, so
`pr-gates` stays red, and the merge-queue run still refuses (DOR-4459).
A stale label with no `hold`, or a label a bot added, still fails. A fully classified nonsensitive
PR with no security-review status can pass read-only as "no security paths
(computed)". The queue can do the same using `base...queuedHead`, never the current
PR's files. An explicit pending/failure cannot use computed clearance. Incomplete
file lists, the PR endpoint's 3,000-file cap and the compare endpoint's 300-file
cap fail closed. Both sides of renames are checked. The initial bootstrap PR fails closed while base lacks the code.

Enforcement requires **Require workflows to pass**, sourced from
`dork-labs/dorkos` at `refs/heads/main`, path
`.github/workflows/security-gate.yml`. A named `security-gate` context alone lets
a PR replace its own workflow. `ci/required-checks.json` keeps main-sourced
workflows separately from named contexts. Offline census validates their source
and every job/trigger. `pnpm ci:census --live` also compares the organization rule,
source repository identity, active enforcement, exact repository/main scope and
visible empty bypass list. Missing rules or unreadable evidence fail. The daily
collector uses the same live comparison; it correctly reports missing enforcement
until the coordinator promotes the rule. No admin credential is added to Actions.
The coordinator's rollout, source pin, local malicious-branch fixture and live
proof requirements are in [Security gate promotion](../ci/security-gate-promotion.md).

The multi-entry queue chain and rebuild timing remain unproven until a real
capture. Shared owner credentials still permit external approval posting;
DOR-3181 / posture item 22 and DOR-3183 own that remaining identity boundary.

## Two gates: local and Actions

**The local hooks are a smell test. The queue is the guarantee.** Say it that way round, because the two are not the same kind of thing and treating them as one is what made the local gates unusable (DOR-2160).

There are exactly three things now, and no more:

| when      | what                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------- |
| at commit | prettier on staged files, Drizzle migrations, a directory-size check, and `lint` of the affected packages |
| at push   | a formatting check on the changed files, and a validity check on the changelog fragments the push carries |
| at merge  | everything, on the real merged tree                                                                       |

**Nothing at push claims to have tested anything**, and that is a decision rather than an omission.

**Why the test gate left `pre-push`.** Measured on the operator machine over 2026-09-19/20, 68 runs of that command:

| runs | duration                                     |
| ---- | -------------------------------------------- |
| 58   | under 50 s                                   |
| 0    | 50 s to 579 s                                |
| 10   | over 579 s (worst 2604 s; 2 killed outright) |

A cliff, not a slope. The 58 are pushes whose affected set was empty or trivial, where the gate ran nothing and proved nothing; the 10 are pushes that had real work and, on this machine, none of them finished in anything a person waits for. Any budget you put on that distribution lands in the empty band: a two-minute bound returns no verdict on a single push that had work to do, while charging two minutes to every one of them. Raising it only walks back toward the 26.6-minute p90 that made agents type `--no-verify`. So the gate went, rather than getting a bound it could not use.

Nothing that reaches `main` reaches it with less checking. The queue runs the full unit-test sweep and the browser smoke against `main` plus everything ahead of your PR and refuses the merge if they fail, `main` runs the full browser suite after every merge, and the PR's affected-only `test` leg reports a break in about 14 minutes with nobody waiting at a terminal. What went away is a local step that either tested nothing or could not finish. The entry that records it, with the revert condition and the counter-metrics, is `ci/ledger/260919-175505-*`.

**Why the formatting check stays.** It is the one local check whose verdict is both certain and cheaper than hearing it from CI: p90 10 s, deterministic, and it preempts `prettier --check .` inside the required `lint` job — which seven PRs across five sessions went red on in a single week, every one a single `prettier --write` from green.

**Why the fragment check joined it.** Same shape: about 0.1 s, deterministic, and it runs the exact validity command of the required `fragment-present` check (`changelog_backfill.py --validate --changed-only`). Its usual catch is a seeded fragment nobody rewrote, which five PRs found out from CI in the week to 2026-10-30. The commit hook also stops seeding once the branch has a hand-written fragment: it adds the new commit to that fragment's `covers:` list instead.

**Why the mid-run check joined it.** Pushing to a PR branch cancels the `test` and `browser-test` runs still going on the previous head, and that threw away 74 job-hours from 2026-11-12 to 2026-11-15. `scripts/pre-push-midrun-check.mjs` asks `gh run list` about this branch and refuses the push while one of those runs is queued or running and under ten minutes old. Push anyway with `CI_PUSH_ANYWAY=1 git push`; each override of a real refusal adds a line (time, git user, `$USER`, branch, head SHA) to `ci-midrun/overrides.jsonl` in the clone's common git dir, outside the work tree. It tests nothing. If gh is missing, signed out, offline or slower than 4 s, it prints one line and lets the push through. The entry is `ci/ledger/261115-173750-pre-push-midrun.md`.

**Why typecheck left `pre-commit`.** Over the week to 2026-09-24 it ran 838 times on the operator machine, for 12.9 hours in total (p90 139 s), and failed 35 times, 9 of them in 3 s or less, which is a lock or a stale dist rather than a type error. Commits outnumber merged PRs about 8 to 1, so it re-checked the same change about eight times per PR, while `typecheck` is a required check on the PR and in the queue and no type error can merge. **To typecheck locally while debugging, run `pnpm verify:preopen` (affected-only), or `pnpm --filter <pkg> typecheck` for one package.** Claude Code sessions also typecheck the edited file's package after every edit. The entry, with the revert condition (the PR-side `typecheck` failure rate), is `ci/ledger/260919-175506-*`.

**The local verify has two levels** (DOR-4728, `ci/ledger/261119-002145-*`). Both are optional debugging tools, not a step before opening a PR (2026-11-24): when the work is done, open the PR with `scripts/open-pr.sh` and let CI judge. `pnpm verify:preopen`, the lighter one, runs the affected typecheck and lint; the whole scripts suite when your change can reach it, and otherwise the repo-wide scripts suites (`scripts/vitest.repo.config.ts`), which any change can break; and ESLint on the files you changed, or the full root `eslint .` when the root lint setup changed or more than 200 files did. It runs no package tests, because CI's six test shards run them at the exact head. `pnpm verify` is the full gate: the whole scripts suite, `eslint .`, and the affected typecheck, lint and tests. Each records a proof for the exact commit in the common git directory, the full one as `<sha>` and the preopen one as `<sha>.preopen`, and neither run touches the other's file. A proof needs a run that finished: one stopped by a signal, or whose turbo run summary (each turbo step runs with `--summarize`) shows a task that started and never finished, records none even when it exits 0, and `check` refuses a proof that does not say it finished, which every proof from before DOR-4616 is. Each refusal is a line in `refusals.jsonl` beside the proofs. `node scripts/verify-proof/cli.ts check <sha>` never opens the preopen file; `--level preopen` accepts either proof and has no `--no-verify-proof` escape. Neither proof is a merge gate any more: since auto-merge at open (DOR-5124), the required checks are what a PR merges on. A PR touching `.github/` needs no local full verify either: the org-required checks run from main's copy of their workflows, and the after-merge alerts and auto-revert back them up.

**Heavy local runs: there is one line for heavy jobs on this computer, DorkOS's load gate** (DOR-4209). Every agent's heavy shell command in a DorkOS chat waits in it (Claude Code, Codex and OpenCode alike), and so do the repo's own heavy scripts. Briefs do not restate these rules; this section is the source.

**What counts as heavy.** A build, a typecheck, a test run of more than one file, a lint of the whole repo, an install, Playwright, Docker builds, and `git commit`/`git push` (their hooks lint and test). The gate's classifier (`apps/server/src/services/core/load-gate/heavy-classifier.ts`) is the full list. One test file (`pnpm vitest run <file>`), one package's `typecheck` or `lint`, `git` reads and `gh` are light and run at once.

**How a job takes its turn.**

- In a DorkOS chat: nothing to do. The server holds a heavy command until its turn and says the place in line every minute.
- In a terminal or a bare `claude` session: run the root scripts as usual (`pnpm build`, `pnpm test`, `pnpm typecheck`, `pnpm verify`, `pnpm test:browser`), which join the gate themselves, and put anything else heavy behind `pnpm heavy <command>` (for example `pnpm heavy pnpm turbo build --filter='@dorkos/server^...'`). In Claude Code, `.claude/hooks/heavy-command-guard.mjs` refuses a raw whole `vitest run`, `playwright test` or heavy `turbo` task and names the `pnpm heavy` line instead (fixtures: `scripts/test-heavy-command-guard.sh`).

`pnpm heavy` is `scripts/heavy-run-lock.sh --job`. A job runs `scripts/load-gate/turn.ts` (by `tsx`), which takes a ticket in `/tmp/dorkos-load-gate-<uid>` through the server's own `TicketQueue`, under the installed app's `runtimes.loadGate` settings (`$DORK_HOME/config.json`, else `~/.dork/config.json`): by default one heavy job at a time, waiting while the five-minute load is at or over 16, and running anyway after the hard cap (four hours). Once the turn comes, the command runs at once: the turn already judged the load and the slot count, so nothing is asked twice. The ticket names the program only (`turbo`, `pnpm`). A run nested inside a job the gate already let run (an agent's gated `pnpm build`, or a `pnpm heavy` whose child runs `pnpm test`) goes straight through. A Ctrl-C during the wait runs nothing.

**Exit 75 means "try again later", not a failure.** Nothing ran. Wait and rerun the same command.

**What a person can do.** The app shows the waiting jobs, and a person can let one through now, mark it urgent, or move it to the front (#4003). Those marks are audited. `DORKOS_LOAD_GATE_LINE=0` skips the gate for one run (recorded as a `line_off` note); `DORKOS_HEAVY_LOCK=0` skips every cap (a `lock_off` note).

**A coordinator's order line** (DOR-4209, DOR-4901; `scripts/lib/heavy-order.sh`). The gate is first come, first served. To say which jobs go first before they exist (a release gate, then PRs in a chosen order), the line is `heavy-order`, one label per line, in the order folder: `$DORK_HOME/load-gate/`, else `~/.dork/load-gate/` (`DORKOS_HEAVY_ORDER_DIR` overrides it; it is made with mode 700 on first use, and a symlink or a folder someone else owns turns the order off with one line). Then:

- **Write it by command, never by hand** (DOR-5079; `scripts/lib/heavy-order-write.sh`). `--list` (with each label's rank: `in flight`, `rank N`, `unranked`, `no ticket`, `release`, or `unknown` when flow could not be asked); `--insert <label>` (`--top`, `--after <label>`, `--before <label>`, `--at <N>`, or no position); `--move <label>` with one of those positions; `--remove <label> --reason "<why>"`. **With no position, the work order places it** (DOR-5065; `scripts/lib/heavy-order-rank.sh`): a release row (`rel-*`, `qa-gate-*`, `qa-row*`) goes right behind the last release row in the line (and any running line just behind it), or first when there is none; a label naming a ticket (`DOR-1234`, any case, not glued to a letter or digit before it) goes behind the last release row and the last running line, then in front of the first line whose ticket ranks lower in `flow order` (Flow 0.100.0+). Work in flight (In Progress, In Review) ranks ahead of every queued issue, since those are the PRs whose checks the line runs; a line with no ticket, or a ticket that is held, needs triage or is on Dorian's list, counts as lowest. Anything else goes to the end with a note. Name the ticket, not the PR number: `#1234` is not looked up. The ranks come from one `flow order --json` call for the whole line, kept as `heavy-order.ranks` in the order folder for 30 minutes (`DORKOS_HEAVY_RANKS_MAX_AGE`), because a real call pulls the whole backlog and can take minutes. Older ranks start one refresh in the background (one at a time: its marker is made atomically and counts as stale 30 s past the cap; capped at `DORKOS_HEAVY_FLOW_REFRESH_TIMEOUT`, 300 s), and the command waits up to `DORKOS_HEAVY_FLOW_TIMEOUT` (10 s) for it, outside the lock; past that it uses ranks up to a day old, said to be old. Flow missing, old, failing or slow with no such ranks puts the label at the end with a note and never blocks the write. The listing printed after a write shows kept ranks only and never waits. The log says who placed each label: `by rank: …` or `by hand: …` (a `--move`, or an `--insert` that named its place). Each write takes the order lock (a kernel lock on `heavy-order.lock`, freed the moment its holder dies, DOR-5082), re-reads the file, and refuses any result that would lose or double a label. Exit codes: 2 refused (a duplicate, an unknown label or anchor, a label outside `ORDER_LABEL_RE`), 3 the verify refused the write, 4 the lock was not had within `DORKOS_HEAVY_ORDER_LOCK_WAIT` (30 s). Every write is a line in `heavy-order.log`, and a hand edit is named out loud on the next write. On 2026-11-22 two hand rewrites dropped other chats' labels.

- **Take a turn:** `bash scripts/heavy-run-lock.sh --label <label> <command>`. While the file has a line, only the top label may start, plus the second while the machine is healthy (DOR-5073); anyone else exits 75 at once, told who is next. The second may start only while swap used is under 12 GB and grew at most 512 MB since a reading 10 to 30 minutes old, free memory is at least 40%, the 5-minute load is under 16, and at least 50 GB of disk is free (the `local.heavy_second_*` numbers in `ci/config.yaml`). A reading it can't get counts as unhealthy, and so does a first try with no swap sample from 10 to 30 minutes ago to compare with. A label that starts then waits in the gate like any job.
- **Leave:** a run leaves the line when it ends (a run refused for the load keeps its place). A job that ran outside the script leaves with `bash scripts/heavy-run-lock.sh --done <label>`; one that runs outside it for a while keeps its place with `--label <label> --hold <pid>` until that process ends.
- **See it:** `bash scripts/heavy-run-lock.sh --status` lists the line and marks every label that is running.
- **A top line that never starts moves down.** When the top label has had no live run for 15 minutes (`DORKOS_HEAVY_ORDER_STALE_SECONDS`), the next call through the script moves it down one place, writes a dated line to `heavy-order-notes.md`, prints it, and runs `$DORKOS_HEAVY_NOTIFY <label> <note>` when the caller set that variable (a coordinator's launcher does; a file in the order folder is never run). The owner is also told the next time it asks. A line is never deleted, a running top is never moved, and a top alone in line stays.

Runs with no label, and agents' own commands, never read the order file. CI never does.

**The disk floor is 25 GB free** on a shared Mac. Under it, start no heavy run and no new worktree install, and free space first: remove merged worktrees (`scripts/worktree-janitor.sh`), then `pnpm store prune` (removing a worktree alone frees little, because pnpm hard-links its packages). A second heavy run beside the first needs twice the floor, 50 GB (`local.heavy_second_disk_min_gb` in `ci/config.yaml`), because two jobs fill the disk twice as fast. Briefs, heartbeats and skills cite this number and never set their own.

**What still uses the older host-wide lock.** Three things do not join the gate, and take one of `local.heavy_run_slots` (3) slots in `/tmp/dorkos-heavy-locks-<uid>` instead: the commit gate's `lint`, a bare `turbo build`, `typecheck`, `test` or `lint` (each depends on `@dorkos/heavy-slot#slot`, which holds a slot for the turbo process's life through `scripts/heavy-turbo-slot.mjs`; a workspace task so that a root `package.json` edit does not change every build hash, DOR-4190), and any job whose gate turn could not start: no `tsx` (a fresh worktree before `pnpm install`), an unusable gate folder, or a helper that died or did not reach the line within `DORKOS_LOAD_GATE_START_SECONDS` (60). A slot is an exclusive `flock` held by a sidecar for the run's life, so a holder that dies in any way frees it at once. The directory is used only if it is a real directory you own (DOR-3509). A waiter prints each holder's pid, age, command and directory. Waiting is bounded (`local.heavy_lock_wait_seconds` for the commit gate, `local.heavy_job_wait_seconds` for a job); a wait that runs out runs the command anyway with a `lock_timeout` note. A job on this lock also reads the one-minute load first: over `local.heavy_max_load` (24; 16 for `--tests`) it waits up to 10 minutes, then exits 75. The commit gate is never load-checked and never refuses, because a gate that refuses gets skipped. A nested call and CI never wait. Fixtures: `scripts/test-heavy-run-lock.sh` and `scripts/test-load-gate-turn.sh`. Why any of this exists: several agents each running a full sweep panicked this box on 2026-10-24 (DOR-3274), and the load reached 93 on 2026-11-11.

**Split by what each is good at.** GitHub Actions splits by cost (2026-08-23/24, the CI-saturation fix):

- On PRs, `test` runs **the suites the change can reach**: those whose turbo task hash it moved (`scripts/pr-test-plan.sh`, DOR-3518, ledger `261031-164008`), or every suite when it touches how tests are chosen or run (`turbo.json`, any `package.json`, the lockfile, `.github/`, `scripts/`, `ci/`). Ledger entries, workflows other than `test.yml`, `security-gate.yml` and `build-cache.yml`, the scripts' own suites (`scripts/__tests__/`, `scripts/test-*.sh`) and Markdown under those folders are planned by hash instead, so they run only the suites that read them (DOR-5130, ledger `261124-015041`). Not `--affected`, which ignores declared `inputs`, so a test that reads a file outside its package must name it in `turbo.json`. It uses two shards, or six when the change touches `apps/server/**` or `packages/shared/**` or its plan runs every suite or reaches them (ledger `261031-150702`). `community-pg` does not run (the `test` fan-in accepts its skip on `pull_request` only), and `browser-test` requires four PR shards of Playwright specs tagged `@smoke`. The smoke shards omit the marketing-site leg, use the existing projects and one CI retry, and fail on empty execution; a 25-minute Playwright deadline leaves reports before the step and job backstops. Every failure blocks, with no quarantine absorption on PRs. PR pushes were starving queue builds of runners (ledger `261030-233825`).
- The **full monorepo `test` sweep runs only on `merge_group`**, as a required merge-queue check. The queue's combined-tree build decides every merge. In the queue, `browser-test` runs the same `@smoke` shards as a PR, scoped to the entry's own change (`HEAD^1..HEAD`, `scripts/browser-smoke-scope.sh`).
- The **full Playwright suite runs on `main` after every merge** (DOR-5130, #4231), not in the queue: six shards plus the one-minute first run (`browser-test.yml`'s `first-run` job, `pnpm --filter @dorkos/e2e e2e:first-run`, which boots two never-onboarded servers), as a rolling `push` run (the ref-keyed concurrency group keeps one in flight and only the newest waiting). The canary and pull requests into `release/*` run it too; the `browser-test` fan-in fails unless the shards and `first-run` passed. On `main` a red run blocks no merge: `after-merge-alert.yml` names every merge in the failed run's range, `auto-revert.yml` acts only when the parent commit's own run was green, and the daily release ships only a commit whose run is green. Ledger `261124-014413`.
- The PR legs exist because GitHub requires a required check to succeed **on the PR** before the PR may enter the queue at all. A `merge_group`-only required check deadlocks every PR out of the queue (measured on PR #1246).
- Push-to-main no longer re-runs the `test` suites: the queue already tested the exact tree content (squash rewrites the SHA, not the content).

**Sharding.** The queue and canary `test` leg is **split ten ways** (`test-shard (N/10)`, DOR-5113) and the PR leg **two ways** (`test-shard (N/2)`), or six ways when it touches `apps/server/**` or `packages/shared/**`; a pull request into `release/*` runs the full sweep on six (the `test-shard-count` job picks; DOR-1731 for why the PR leg is split at all). The shard jobs are where the suites run; `test` itself is only their fan-in, so read a red on a PR off the shard, not off `test`. Only `test` is a required context. Never make a shard one.

**Real-CLI suites run beside the shards.** Both shard legs exclude every `*.binary.test.ts` (they spawn a real `claude`, `opencode` or Codex and are the slowest files). `codex-sandbox` runs the Codex ones; `test-binary` runs the rest, on the queue, the canary, and every PR whose test plan reaches their package. Each fails unless every file it owns ran with no skipped test (`scripts/assert-binary-suites-ran.mjs` for `test-binary`), `test` requires both green, and its union check requires every `*.binary.test.ts` in the tree by name (`assert-shard-union.sh --require-files`). A new binary suite needs no workflow edit (DOR-4190).

**`assert-tests-executed.sh`.** Turbo caches `test` and replays a full cache hit in about 280 ms while printing "29 successful". So the merge-group `test` run asserts the suites actually executed (`scripts/assert-tests-executed.sh`, pinned by `scripts/test-assert-tests-executed.sh`). Never weaken that step without reading its header. `scripts/assert-shard-union.sh` is the other half: it restores the zero-collected-files net that `--passWithNoTests` removes from the sharded sweep.

**`lint`.** Full monorepo `turbo lint` (DOR-627), full rather than affected-only for the same cross-PR interaction reason `typecheck` gives. It became a required merge-queue check on 2026-09-02 and dropped its push-to-main leg the same day, because the queue already tested the exact tree. It runs a second ESLint pass beside `turbo lint`: `pnpm lint:root` (`eslint .` from the repo root, DOR-1696), because turbo only reaches workspace packages. `scripts/`, `.claude/`, `.agents/` and `templates/` belong to none, and the hooks and automation there (the guards, the ADR and docs scripts) sat behind zero lint coverage with 164 standing errors until then. The root config declares the Node and browser globals those files need, so `no-undef` still means something there. Its first step is `pnpm format:check`, so a red `lint` is often prettier, not ESLint.

**`site-build`** compiles the marketing site (`turbo build --filter=@dorkos/site`, DOR-913), because nothing else ever did: `typecheck` type-checks the site without bundling it, and `browser-test` builds only the site's **dependencies** (`--filter=@dorkos/site^...`) and then serves the dev server. A page declaring `runtime = 'edge'` beside a node-only import was green everywhere and failed only at the Vercel deploy, blocking production for hours (PR #743, hotfixed by #755).

- It builds unconditionally on `merge_group`. On `pull_request` it builds only when the change reaches the site: turbo `--affected` intersected with the site's dependency closure, plus a `docs/` and `blog/` check. Both are prerendered content roots that `apps/site/source.config.ts` points at from outside any package, where turbo's file-to-package mapping cannot see them (a blog-only commit, which every release ships, otherwise scores as zero affected packages). A collection added there with a `dir` outside `apps/site` needs a matching entry in the workflow.
- The scope decision lives **inside the job**, and a `paths:` filter on `pull_request` sits in front of it so a PR that can't reach the site doesn't hold a runner (ledger `261030-193801`). That filter is safe only because this check is advisory: a path-filtered workflow reports nothing, and a required check that reports nothing keeps a PR out of the queue and then stalls the queue for an hour. `harness-windows` has the same shape.
- **It is not a required check yet.** Making it one is a ruleset change, the operator's to make, and it needs the `paths:` filter deleted first (and, under the steward, a ledger entry).

**Other Actions checks.** `fragment-present` and `no-fragment-under-skip-label` (changelog), `scripts-test` (its `fixtures` job is required and runs on every PR and merge group; its `harness` job is advisory, PR and push only, and scoped by `scripts/scripts-test-scope.sh`; the `scripts/` suites that read the whole repo also run in the required `typecheck` job, listed in `scripts/vitest.repo.config.ts`, so a PR outside that scope that breaks one is ejected from the queue instead of turning `main` red), and CLI smoke tests (Node 22/24) plus integration tests, which run on push to `main` and on PRs that touch what they package. Locally: `pnpm smoke:docker` and `pnpm smoke:integration`. Advisory checks such as `site-build`, `harness-windows` and the Claude `review` do not block the queue; auto-merge waits only for the required checks.

**Capacity.** The org is on the GitHub **Team** plan: 60 concurrent jobs, not the Free plan's 20. One push to a PR starts about 14 jobs (docs-only) to 20 (code), down from 19 to 25 before the PR leg went to two shards and dropped `community-pg`, plus four `@smoke` browser shards of about 15 to 20 minutes each since PRs started running them; a queue entry costs about 19 to 20, plus three browser shards more since that suite went to six (a queue build's full check-run count, the number the CI Steward ledger uses, went from about 31 to 34). Since DOR-5130 a queue entry runs the four `@smoke` shards, or none when its change reaches no browser leg, instead of the six full shards and `first-run`, which run once per push to `main`. Twenty agents each pushing once is 400 to 500 jobs, 7 to 8 full refills of the pool, and the queue's own builds wait behind them. That arithmetic is why no remedy anywhere here is "push an empty commit".

## The merge queue

`main` merges through a merge queue (ADR `260728-112203`). You never update a branch to satisfy a gate: GitHub builds your PR on top of `main` plus everything ahead of it in the queue, runs the required checks against that combined tree, and merges only if they pass. "Require branches to be up to date" is off, and being behind `main` blocks nothing. Consequences:

- **Every required check must report on `merge_group`.** A required check that fires only on `pull_request` blocks the queue forever. Any new required check needs `merge_group:` in its `on:` list, and the census enforces it (the deadlock invariant below).
- **Some checks stay PR-only on purpose.** Fragment _coverage_ needs the PR's labels and number, which the `merge_group` payload does not carry, so it is answered before queueing and not re-asked. Fragment _validity_ does re-run in the queue. This is sound only because a PR cannot enter the queue until its required checks pass on the PR, and neither its labels nor its diff can change afterwards.
- **A skipped job satisfies a required context.** A job-level `if:` that skips posts a _skipped_ check run, and GitHub counts skipped as passing. Never "fix" a required check by making it skip.
- **An ejection is usually not your fault.** 22% of PRs are ejected at least once; 85% of failed-checks ejections (209 of 247 over 30 days) re-pass with no change. The first response to one is to read the failing job without pushing or rerunning, and to re-queue once (`gh pr merge --auto <n>`) when it is plainly not yours. Green PR checks are not evidence that it is not yours: the queue tests your change on top of everything ahead of it, which the PR never ran. **If the same check fails again on the same head commit, stop re-queueing:** it is a regression that only the queue can see, so read the log and push a fix. PR #1964 was re-armed unchanged four times after one browser assertion broke, and cost 17 queue builds, its own and every PR stacked behind it. `queue-repeat-guard.yml` (`scripts/queue-repeat-guard.sh`) now takes such a head back out of the queue on entry, whoever queued it; the `requeue-ok` label lets it through when the failures were `main`'s. The one exception is the same check red on `main` too, a break that landed there: wait for the fix on `main`, then re-queue (`gh pr merge --auto <n>`).
- **A jump is not free.** Enqueueing with `jump: true` (GraphQL `enqueuePullRequest`, the path `ci-fix` PRs use) puts a PR ahead of every waiting PR, and GitHub documents that it also tears down and rebuilds every entry already testing ([managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue#jumping-to-the-top-of-the-queue)), so each jump costs those builds again.
- **Dependent PRs stack; everything else branches from `origin/main`.** One topic, one PR. Before starting, check for an open PR on the same files or one that must land first; if there is one, stack on it with `gh stack` (gh 2.90+). A stack merges only with `gh stack merge` run on its top PR, which sends every layer through the queue together. **Never turn on auto-merge for a layer whose base is not `main`:** it would merge into the branch below and skip the queue (`open-pr.sh` only opens against `main`). Opening a stacked PR: the `creating-pull-requests` skill.

## Release branches

Releases ship from short-lived `release/v<X.Y.Z>` branches cut from the main commit QA pinned (decision DOR-4636, project "Release branches"). Hotfix branches cut from a release tag are planned, but publishing one is off in DOR-4638 until tags are locked by a ruleset (DOR-4789); a PR into one would be judged by the same rule below, with nothing special for a tag base. Main keeps merging meanwhile. A change reaches a release branch only by pull request, and only as one of two things: the release commit, or a cherry-pick of a commit already on main. **Fix on main first, then cherry-pick** (Security, DOR-3100). There is no merge queue on `release/*`, so the pull request itself runs the full gate (DOR-4639).

**What each required check does on a PR into `release/*`:**

| Check                                       | On a release PR                                                                                                                                                                                                |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test`                                      | Full sweep, as on `merge_group` but on six shards (not ten), every suite, `community-pg`, retry budget, quarantine lane, union proof. No shard plan, no no-code skip.                                          |
| `browser-test`                              | Full `browser-shard` matrix and `first-run`, as on a push to `main`; the `browser-smoke` leg is skipped.                                                                                                       |
| `openapi-fresh`                             | Regenerates unconditionally, as in the queue.                                                                                                                                                                  |
| `fragment-present`                          | Validity as always. Coverage is replaced by provenance: the job runs main's `release-branch-contents` rule, then skips coverage (each pick passed coverage on its own main PR, and its fragment rides along).  |
| `no-fragment-under-skip-label`              | Skips: the label decides nothing on a release branch.                                                                                                                                                          |
| `release-branch-contents`                   | New. Refuses any commit that is neither a cherry-pick of main nor the release commit (below).                                                                                                                  |
| `typecheck`, `lint`, `db-check`, `fixtures` | Unscoped already; unchanged.                                                                                                                                                                                   |
| `credential-free-build`                     | Affected-only against the PR's base SHA, the same way it runs in the queue; unchanged.                                                                                                                         |
| `version-outranks-base`                     | Compares the skill-pack version with the release branch's tip; a pick of a main pack bump passes, unchanged.                                                                                                   |
| `security-gate`                             | Judges Security labels at the head itself; `security-review-initialize` stays main-only (its verdict script writes `failure` for any other base), so a release PR has no `security-review` status to wait for. |

In workflow conditions, "a release PR" is a `pull_request` whose `github.base_ref` starts with `release/`: wider than `release/v*` on purpose, so any doubt gets the full sweep. Step bodies see it as `EVENT=release_pull_request`. Only `merge_group` may use the queue runner, so a release PR stays on GitHub's hosted runner.

**The rule is one rule, DOR-4638's** `packages/cli/scripts/release-branch/check-picks.ts` (over `rules.ts`), the same function the release publish runs, so the check and the publish cannot disagree. The `release-branch-contents` workflow extracts **main's** copy of that folder into a temp directory (it imports only itself and node builtins, so nothing is installed) and runs it through **main's** `scripts/ci/release-branch-contents.sh`, so a PR cannot edit the rule that grades it. The invocation is `node --experimental-strip-types check-picks.ts <repo> <version> <base> <head> <main-sha>` on node 24. **Until DOR-4638 is on main there is no `check-picks.ts` there, and the check fails closed (exit 2), as does `fragment-present` on a release base.** Every commit in `base..head` must be:

- **A cherry-pick of main.** Made with `git cherry-pick -x`, so it carries exactly one `(cherry picked from commit <sha>)` line, naming a commit on `origin/main` that the branch does not already hold (`source-before-cut`) and that main has not since reverted (`source-reverted-on-main`), and the pick's patch fingerprint must equal its source's. The fingerprint is byte-exact, unlike `git patch-id --stable`, which ignores whitespace: a "pick" that changes the spacing inside a string literal or a YAML indent is refused.
- **Or the release commit.** Not a cherry-pick, touching only release metadata: `VERSION` (saying X.Y.Z), `CHANGELOG.md`, `docs/changelog.mdx`, `docs/changelog-archive.mdx`, the five `package.json` files (top-level `"version"` only), fragment deletions under `changelog/unreleased/`, the rolling `changelog/archive/CHANGELOG-v0.1.0-to-v*.md`, `blog/dorkos-X-Y-Z.mdx` and new files under `apps/site/public/product/archive/vX.Y.Z/`. Workflow, tool and lockfile paths are refused by name. The release commit is metadata only (Security): runnable code, including a config migration (`config-migrations/`, `merged-migration-hashes.ts`) and the `agent-release-notes.ts` version stamps, lands on main by a normal pull request before the cut, and so does any code or test fix found later. Its subject must be exactly `chore(release): v<X.Y.Z>` for the branch's own version and it must set `VERSION` (`release-commit-subject`, `release-commit-no-version`). Its pull request comes from the head branch `release-commit/vX.Y.Z`.

Merge and root commits, new commits, empty commits and a trailer naming a commit off main are refused by the rule. The shell script adds the rest, and prints the rule's finding codes as the rule names them: a misnamed branch, a base that is not on the branch, a branch with no history in common with main, and an empty range are refused; a shallow clone, a missing rule, a rule that prints no verdict or contradicts its exit code, and any git error fail the check rather than pass it. Fixtures: `scripts/test-release-branch-contents.sh` runs the real `check-picks.ts` end to end; the rule's own cases are DOR-4638's `packages/cli/src/__tests__/release-branch-*.test.ts`.

**A conflict-resolved cherry-pick is refused, with no waiver in the check.** Its patch differs from anything main reviewed and tested. Make it apply cleanly instead: land a preparatory commit on main and pick it first, or land the backport itself on main if it is safe there. When neither works, it is a Security decision (a ruleset bypass by Security, recorded on the PR), never an edit to the rule.

**The `release/*` ruleset** (DOR-4637, Security) should require the same contexts as main plus `release-branch-contents`. `ci/required-checks.json` describes main's ruleset only. Pull requests into `release/*` merge **rebase-only**, so the `-x` picks and the release commit reach the branch exactly as checked, and there is **no merge queue** on `release/*` until `release-branch-contents` has a `merge_group` leg (without one it would deadlock the queue).

## The main canary: who watches `main`

Until DOR-5130, `test` and `browser-test` ran their real suites on `merge_group` only, and the push-to-main legs were retired on 2026-09-19 because the queue already tested the byte-identical tree. Both were right, and together they left a hole: once a commit is on `main`, nothing looked at it again. On 2026-09-17 a fixture pinned the browser clock past Today's 04:00 boundary (#1916). It was green in every queue build outside 00:00–02:00 UTC, hid for three days, then ejected #1930, #1932 and #1933 about nine times in one evening before a person diagnosed it (#1934).

The canary closes it. `test.yml`, `browser-test.yml`, `typecheck.yml` and `lint.yml` each carry `schedule:` (one slot a day at 00 UTC, staggered by minute; four until DOR-5114) and `workflow_dispatch:`, and run their own suites against `main` HEAD. Main's build caches no longer depend on it: `build-cache.yml` saves them after every merge (DOR-4627). Since DOR-5130 (Nov 24) the full browser suite runs on every push to `main` again, so for `browser-test` the canary adds only drift with no code change; `test` still runs its full sweep only in the queue, the canary and release PRs.

- **There is no canary workflow.** It is the same workflows: the steps that read `github.event_name == 'merge_group'` now read `!= 'pull_request'`, so the full sweep runs everywhere but a PR (for `browser-test`, everywhere but a PR or a queue entry, since DOR-5130). A second copy of the suite could drift from what the queue runs, and a canary that disagrees with the gate is worse than none.
- **It can never touch a pull request or the queue.** A required context is required on the `pull_request` and `merge_group` events; a `schedule` run reports on neither, belongs to no PR and to no queue build, and arms nothing. It is not a required check and must not become one.
- **Run one now:** `gh workflow run test.yml --ref main` (or the Actions tab). This is **not** plan §4.9's targeted canary: that wants a `job` input so one failing job re-runs in 5–25 minutes, and this dispatch runs the whole workflow (~150 job minutes, ~30 minutes wall). The input and the matrix gating it needs are a separate change; until they land the targeted canary does not exist. The dispatch has its own concurrency group, so an incident run never queues behind a scheduled round.
- **What one cron a day actually buys.** The evidence is `evals.yml`, not merge-tail: merge-tail's `*/10` cron delivers about 7 runs a day, and the "162-minute median" from it is the gap between delivered runs — how many requests GitHub drops, not how late one is. For a low-frequency cron the comparable is `evals.yml`'s `0 8 * * *`: 57 runs, **100% delivered**, lateness p50 2.60 h, p90 5.61 h, max 11.88 h. With four slots (`0,5,10,21` UTC) GitHub delivered two rounds a day (02:xx and 14:xx UTC on 2026-11-18..22). One slot (DOR-5114, ledger `261123-195020`) still covers what the canary is for once the caches are saved per merge: drift with no code change (runner images, the registry, date- and time-dependent tests), flake data and shard durations, found within about a day. The `00:3x` slot lands in or just after the 00:00–02:00 UTC window as the queue's busy stretch tails off; a time-of-day bug in that window is caught by repetition over weeks, not by an appointment. `canary_silent_hours` is 40 for the same reason: a daily round plus up to about 12 hours of lateness.
- **A daily slot the release flow needs does not ride its cron alone.** `daily-release.yml` (15:07 UTC) and `daily-sweep.yml` (17:13 UTC) sit off minute 0, GitHub's busiest (the first `0 15` slot never fired), and also run as a backstop whenever `CLI Smoke Test` finishes on `main`. Both go through a `due` job, `scripts/timed-slot.sh`: it goes on only after today's slot time, while no cron or backstop run has uploaded the day's `timed-slot-<workflow>-<date>` artifact, and until three runs have failed that day; the workflow's single concurrency group stops the cron and the backstop acting at once. A dispatch skips `due` and runs at once (ledger `261124-161126`).
- **`credential-free-build` and `copy-spec-drift` are not in it.** Both read a base SHA to diff against, which a scheduled run does not carry. Neither do the PR-diff checks (`fragment-present`, `no-fragment-under-skip-label`, `version-outranks-base`, `db-check`): they measure a diff, and `main` has none. Every one of those is named in `canary.exempt` with its reason.
- **It runs against `main` or it fails.** `workflow_dispatch` is ref-free, so `--ref <a PR's branch>` would post a required context's check run on that pull request's head. A three-line guard is the **first** step of every canary job and **fails** such a run — never skips it, because a skipped job satisfies a required context. It is inline in the `run:` block rather than a script, because it runs before `actions/checkout` and a `bash scripts/…` there exits 127 on every event; `packages/ci-steward/src/__tests__/canary-ref-guard.test.ts` extracts the shipped block, runs it, and pins that it stays step 1 and reads no file.
- **The list is a registry, not a convention, and it binds both ways.** `ci/config.yaml`'s `canary.workflows` is what the collector reads a run against. The census fails when a workflow named there is missing, has no `schedule` or `workflow_dispatch` trigger, declares a `schedule:` with no cron, or has no job that can run on one — and it fails when a workflow owning a required context is in neither `canary.workflows` nor `canary.exempt`. Without the second direction, deleting a name would leave the census green while collection and the silence arm both stopped, and a canary that stopped running reads exactly like a healthy `main`.
- **What it does to the data.** Canary runs carry the same gate ids as the PR and queue legs, so every reader that aggregates a gate across events skips them for a gate that also runs on the merge path — decided once **across the window** (`mergePathGates`), never per day, because per-day membership flipped with a single zero-run key. A gate that runs on nothing but a schedule keeps its own samples, so `headroom` still watches merge-tail, the evals, CodeQL and the collector. `main-green` counts `push` runs only and is untouched. The canary's runner minutes are kept out of `job_minutes` and carried as `tracked.canary-minutes`, because its cost is fixed while everything else's is proportional to what was merged. Its own results are `snapshot.canary`, and `tracked.time-to-detect` reads from the previous run's **start** to this one's finish — a run only tests the tree it checked out.
- **It rides the quarantine lane.** The lane's shard steps and fan-in proofs run on the canary exactly as in the queue, because it is the same job: a canary that failed on a flake the queue excuses would report a break that is not there. With no `quarantine.json` on the data branch, `quarantine-list` writes an empty list and exits 0, and an empty lane behaves exactly as no lane at all.
- **What it costs.** About 150 job minutes a round when it was measured (about 320 on 2026-11-16..22, when two delivered rounds cost about 640 a day); one round a day since DOR-5114. The canary's cost is fixed, so it weighs most on a quiet day. The repository is public, so those are unbilled; the price is contention on the pool the queue shares.

## Merging: auto-merge at open, the PR-side gates, and the door

**Nobody arms a PR any more (DOR-5124, Nov 24).** `scripts/open-pr.sh` turns on auto-merge when a PR opens, because main requires `not-held`, `release-window` and `pr-gates`. GitHub queues the PR as soon as every required check is green, and the merge queue runs the full unit-test sweep and the browser smoke (the full browser suite runs on `main` after merge). `arm.sh`, `arm-door.yml`, `merge-tail.yml`'s arming and the local arm sweep are retired. `gh pr merge --auto <n>` (the merge guard allows it) has three uses: re-queueing once after an ejection, a PR opened before Nov 24, and a draft marked ready or a PR whose `hold` was lifted, by whoever readied it or lifted the hold. Outside contributors cannot turn on auto-merge; a maintainer does it after the Security sign-off below.

**The PR-side gates.** Each runs on `pull_request` and `merge_group` with no path filter or job-level `if:`, and checks out main's copy of its script, never the PR's:

| Check            | Fails while                                                                                                                                                                                                                                                          | Decision                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `not-held`       | the PR carries `hold` (DOR-5103)                                                                                                                                                                                                                                     | `scripts/not-held-check.sh`                        |
| `pr-gates`       | Security has not signed off at the head. Security's sign-off is a signed review marker or the cloud verdict: a PR comment whose signature verifies against main's `ci/security/allowed_signers` for this PR's head, or a passing cloud `security-verdict` (DOR-5119) | `scripts/pr-gates-check.sh`, reusing `arm-door.sh` |
| `release-window` | the `MERGE_FREEZE` repository variable names another PR, a release PR is not alone, or main's `VERSION` is not on npm yet (DOR-5102)                                                                                                                                 | `scripts/release-window-check.sh`                  |

`pr-gates` prints QA's `qa-real-data` and the designer's `design-ok` as notes only: no local agent reviews an open PR, and QA and the designer sweep each day's merges instead. The cloud Security lens runs inside the Claude review on every push; `security-verdict.yml` posts its verdict as a status and re-runs `pr-gates` after a pass. Nothing re-runs a check when a freeze lifts or a publish lands, so `release-window-refresh.yml` re-runs failed `release-window` checks once the window is open again. It runs after every push to `main`, after Release Publish (waiting up to five minutes for npm to show the version), after a PR's first `release-window` attempt fails, and on a 15-minute cron that GitHub mostly drops, so the events do the work (ledger `261124-161126`).

**Only Security's `label-pr.sh` adds or removes `security-*` labels and posts its signed review marker; no agent touches them by hand.** A `security-reviewed` label by itself is not a sign-off; `pr-gates` notes it and keeps waiting for the signed marker or the cloud verdict. If you think a PR needs a review, ask Security. Fork PRs get no automatic review (no secrets), so they wait for Security's signed review.

**The door.** `queue-repeat-guard.yml` reads every merge-queue entry and takes out a head that already failed the same required check in two queue builds (see the queue section above). It fails open.

**Lost reviews are re-requested.** `review-redispatch.yml` (merge-tail's second duty, kept when merge-tail retired; ledger `260920-175925`) runs when a `claude-code-review` run fails (a `wait` job first sleeps until the ladder's next rung for that head has passed, `scripts/review-redispatch-wait.sh`), with its `*/10` cron as a backstop, and re-requests the automated Claude review on any open PR whose `review` check is red, by applying the `re-review` label with the `dorkos-merge-tail` app. The decision is `scripts/should-redispatch-review.sh`, pinned by `scripts/test-should-redispatch-review.sh`. This matters more now that `pr-gates` waits on the review's verdict. **What actually bounds it is a ceiling of three retries per head SHA**, not the 10/20/40-minute backoff in the script: every rung was shorter than one cron tick (scheduled workflows are throttled to a median gap of about 162 minutes), and the event trigger now times each scan to the rung, so the backoff is real for a scan that follows a failure. It counts attempts, not runs: a `skipped` or `cancelled` run never reviewed anything, and it counts `run_attempt` rather than rows, because GitHub reuses a run id when a run is re-run by hand. It holds off while the subscription window the last attempt died against is plausibly still shut (300 minutes for a session limit, 360 for a weekly one), then tries again. It refuses when the PR carries `skip-review`, and when the PR edits `claude-code-review.yml`, because the action refuses to review a PR that changes its own workflow. It also **removes** a `re-review` label stranded on a conflicting PR: GitHub creates no run for a conflicting PR, so nothing inside a run can clear it. `gh workflow run claude-code-review.yml -f pr=N` is keyed by PR number, not head SHA, so it runs **beside** an automatic review instead of cancelling it: dispatch when there is no run, not when one is slow.

The mechanism is a label rather than a workflow dispatch because dispatching needs `actions: write`, which the app does not hold, and GITHUB_TOKEN cannot substitute: GitHub creates no workflow run for an event its own token triggered. Reading the review's runs needs `actions: read`; without it the workflow fails red rather than quietly retrying nothing.

- Open a PR with `scripts/open-pr.sh` (fixtures: `scripts/test-open-pr.sh`), never a bare `gh pr create`: it runs the open-PR cap, computes `review:light`/`review:deep`, `skip-changelog` and `needs-design` from the diff, adds the provenance line and applies every label at creation. `.claude/hooks/pr-create-guard.mjs` refuses `gh pr create` and REST or GraphQL PR creates in Claude Code (fixtures: `scripts/test-pr-create-guard.sh`).
- The provenance line traces a PR to the session that opened it, for example `<!-- agent:provenance {"v":1,"harness":"claude-code","sessionId":"bb423f8f","account":"claude2","surface":"github"} -->`. `sessionId` is the first 8 characters of the Claude Code session id (`CLAUDE_CODE_SESSION_ID`), which names the session's transcript, `~/.claude*/projects/<cwd-slug>/<session-id>.jsonl`. `account` is which Claude config dir (`~/.claude2` is `claude2`). Nothing else goes in: no paths, hostnames or tokens.
- A `hold` always carries a reason: a comment starting `hold:` saying why and who lifts it (`scripts/open-pr.sh --hold "<reason>"` posts it). The advisory `hold-reason` workflow (`scripts/hold-reason-check.sh`) flags a held PR without one, for every harness. On 2026-11-20 holds with no owner left 19 PRs stuck for 9 hours.
- Apply `hold` to keep a green PR from merging: `not-held` is required, so the label stops auto-merge and fails the queue entry by itself.
- Only the required checks and the door bind. The Claude review's findings and open threads do not, except its Security lens through `pr-gates`, so a PR can merge with non-Security findings open. Fix forward.

## Admin merges and credentials

**No admin merges.** Every agent on this machine runs as the operator's GitHub account, which holds the admin role. `gh pr merge --admin`, a REST `PUT repos/{owner}/{repo}/pulls/<n>/merge`, and the GraphQL `mergePullRequest` mutation all land a change without the queue's checks. `.claude/hooks/merge-guard.mjs` refuses all three in Claude Code sessions (fixtures: `scripts/test-merge-guard.sh`). Admin merges are reserved for the CI Steward break-glass path, `/ci-break-glass`, which arrives in phase 1b and does not exist yet. Until then no agent has a sanctioned admin merge.

The guard is the paved road, not the fence. It reads command text only, so a script on disk, `curl` with `gh auth token`, or a harness that does not run the hook walks past it (Codex reads a generated, trust-gated `.codex/hooks.json`; whether this guard fires there is unverified). The fence arrives in phase 1b: a detector for any commit on `main` with no merge-queue provenance, and an automatic revert.

**Invariant: no admin credential exists in GitHub Actions.** Nothing automated may be able to edit the ruleset, so no automated change can un-require a check. **Status: true once the phase-0 PR merges and the old `MERGE_TAIL_TOKEN` secret is deleted, which happens right after that merge.** `review-redispatch.yml`, `dependabot-lockfile-repair.yml` and `auto-revert.yml` (only while `AUTO_REVERT` is on) mint a short-lived token for the `dorkos-merge-tail` GitHub App (`actions/create-github-app-token`), which has `contents` and `pull_requests` write, `checks`, `statuses` and `metadata` read, and **no** Administration or actions permission (client id in the secret `MERGE_TAIL_APP_CLIENT_ID`, key in `MERGE_TAIL_APP_PRIVATE_KEY`), in place of the admin-account PAT. Phase 0's exit gate proves two things about it: a REST merge of a blocked PR with the app token is refused, and a merge group the app token enqueues receives check runs (groups created by `GITHUB_TOKEN` get none and jam the queue).

## CI Steward: how the pipeline itself changes

The pipeline changed about 13 times a week, each change well documented, and none checked afterwards: 0 of about 94 changes had a planned post-rollout check, and 3 results found by accident contradicted their change. CI Steward closes that loop (plan: `plans/ci-steward-plan.md`; method: the `stewarding-ci-pipeline` skill).

### Intent on `main`, observations on the data branch

| Where                                  | What                                                                                                                                         | Written by                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `main`: `ci/` hand files, `ci/ledger/` | What we want: gates and their purpose, required checks, SLOs, metrics, ratchets, the ledger                                                  | People and agents, through PRs                |
| `ci-steward-data` (orphan branch)      | What happened: daily snapshots, computed verdicts, floors, high-water marks, the open triggers, the daily report and the Monday deep summary | The daily collector only, with `GITHUB_TOKEN` |

Nothing the system generates ever needs a PR. Ruleset 23704437 makes `ci-steward-data` append-only (no deletion, no force-push, no bypass), and ruleset 23705388 makes its weekly backup tags `ci-steward-data/YYYY-Www` permanent. Read it with `/ci-status`, or by hand: `git fetch origin ci-steward-data`, then `git show origin/ci-steward-data:latest.json` (or `:triggers.json`, `:verdicts/<ledger-id>.json`, `:reports/<YYYY-MM-DD>.html`, `:reports/<YYYY-Www>.md`, `:snapshots/<YYYY-MM-DD>.json`). `pnpm ci:report --open` builds the day's page locally and opens it. The collector's first run creates the branch; until then `/ci-status` says so and `/ci-pulse` collects into a temporary directory instead.

### The ledger

One file per pipeline change, `ci/ledger/<YYMMDD-HHMMSS>-<slug>.md` (ids from `.claude/scripts/id.ts`, so fragments never conflict):

```yaml
---
id: 260919-143012
title: Quarantine flaky browser specs out of the blocking lane
kind: experiment # experiment | incident-fix | hygiene
status: active # hand states only: proposed | active | withdrawn | reverted
actor: agent # agent | ci-improve-tick
gates: [wf.browser-test.browser-shard]
prs: [1931]
hypothesis: # required unless kind: hygiene
  metric: gate.wf.browser-test.browser-shard.failure_rate # a catalogue id (ci/metrics.yaml), the narrowest that can move
  baseline: 0.17
  baseline_source: research/20260919_ci-pipeline-02-timings.md # phase 0: hand-copied, say where from
  target: 0.05
  after_days: 14 # the after-window, anchored on the merge time

floor-release: [] # [{slo, stat, value, reason}]: the only way an SLO floor loosens

```

- `node packages/ci-steward/src/cli.ts ledger-new --slug <kebab-slug> [--kind experiment|incident-fix|hygiene]` scaffolds an entry with a fresh id and prints its path (`--help` lists every command and flag); `ledger-check` validates every entry. Root aliases: `pnpm ci:census`, `pnpm ci:ledger-check`, `pnpm ci:ledger-new`. The engine's schema is the authority; the example above is the plan's shape.
- `verified`, `partial`, `failed` and `inconclusive` are **verdicts**, computed by code into `verdicts/<id>.json` on the data branch once the after-window closes (the rules are under "Observing" below). They never appear on `main`; the validity check rejects them.
- **Coverage:** a PR that touches any gate source, any script a gate invokes, `turbo.json`, `lefthook.yml`, `.claude/settings.json`, a `ci/` hand file, `packages/ci-steward/src/**` or the `creating-pull-requests` skill must add or edit a ledger entry. The PR-only `typecheck` step "CI Steward ledger coverage" checks it. Only a new entry counts, or an existing entry whose `prs:` gains this PR's number (how an implemented proposal records its PR); a typo fix in an old entry does not. A missing entry fails the PR. Dependabot PRs are exempt (the step's `if:` skips them): Dependabot cannot write an entry, and its version-bump PRs would otherwise stay red forever. On a `ci-improve/*` branch, touching a fenced path fails it too.
- **Ratchet releases block by default.** A `ratchet-release` lowers a quality floor on its own say-so, so the review treats it as blocking unless the reason is specific. `field-changes` is required when a required gate's retry, shards, timeout or required status changes.

### Observing: the collector, verdicts, floors and the report

**The daily run.** `.github/workflows/ci-steward.yml` runs at 05:00 UTC (and on `workflow_dispatch`): `data-prepare` checks out `ci-steward-data`, `daily` runs `collect`, then `verdicts`, then `triage`, then the day's HTML report, then on Mondays `report` (the weekly deep summary), and `data-publish` pushes, fetching, rebasing and retrying if the local export pushed first, then tags the head `ci-steward-data/YYYY-Www` whenever this ISO week has no backup tag yet (so a failed Monday is covered by the next good run). The checkout keeps no credentials (`persist-credentials: false`), so no token sits in `.git/config` during `pnpm install`; only the publish step gets `CI_STEWARD_PUSH_TOKEN`, which the engine hands to git as an HTTP header through `GIT_CONFIG_*` variables. It is never a required check and never will be: it runs on no PR or merge-group event. Any command runs locally too; pass `--data <dir>` (a working tree of the branch) and `--now <iso>` to pin the clock.

**What `collect` reads, per UTC day, all through `gh`:** every Actions run created that day, fetched in created-time windows split until each is under the API's 1,000-result cap and asserted against its `total_count`; the jobs of every head SHA (one `commits/{sha}/check-runs` call each), mapped back to gate ids and kept per event (`<gate-id>@pull_request`, `@merge_group`, ...), so a shard's PR leg and queue leg stay apart; the timelines of every PR merged that day (queue entries, removals and their reasons, new commits), paged to the end, because a timeline comes oldest first and a cut-off one loses exactly the merge and the last queue events; a sample of queue builds' test reports (`collect.artifact_builds_per_day`) for flaky-test-runs; the releases, the Actions cache, and the three rulesets. It writes `snapshots/YYYY-MM-DD.json` and `latest.json`. `latest.json` is the one file here that is **not** strict about unknown keys, because a checkout days behind the collector must still read it; a field added to it is additive. It never moves back: it points at the newest complete day on disk, so a run that only backfilled August still reads as today, and it carries this run's failures even when the day it points at was healthy.

**Three readings are only as honest as what they can see**, and each says so rather than reading a number it cannot back. `main-green` closes a red spell only when the push workflow that failed goes green on `main` again, because the push workflows are path-filtered differently and the next all-green commit often never ran it; the snapshot keeps each commit's per-workflow result for that. `headroom` reads a gate against the deadline that actually fires, which for a browser shard is Playwright's `globalTimeout` (25 minutes at six shards, derived in `apps/e2e/playwright.config.ts`), not the 45-minute job backstop. That deadline's clock starts after the job's setup steps, so its `deadlines:` entry also records `lead_minutes` (2.5, the shortest setup measured) and the job is read against the two together. `flaky-test-runs` reads `unmeasured` ("coverage unknown") when a red queue build in the window failed a test job whose report it cannot read (`collect.blind_test_gates`), since a share over the suites it did see says nothing about the others. The collector also computes `tracked.repeat-ejections` per day, and records each day's merge commits and what each release shipped (one compare per release), from which `tracked.merged-to-released` is read: hours from a PR's merge to the first release that holds it, p50 and p90, the first panel of the daily report (DOR-5127). A day collected before any of these existed is brought up to date by `refreshOlderDays` on whatever budget is left after collecting, about three requests a day, never by collecting it again.

**Late, never truncated.** `GITHUB_TOKEN` allows 1,000 REST requests an hour for the repository; the collector stops at `collect.api_budget` (700). A day it cannot finish is written with `complete: false` and resumed by the next run, SHA by SHA, without double counting. Days are planned yesterday first, then missing or late days in the last `collect.lookback_days`, then backfill back to `collect.backfill_from`, oldest first, because Actions keeps run data for 90 days. Measured on 2026-09-19: a quiet day costs about 35 requests, a 1,666-run day about 180.

**The health block, and what turns the run red.** Every snapshot records pages fetched against `total_count`, head SHAs done, each SLO's n against its `min_n`, API requests, gaps in the series, the age of each clone's local export, the merge-queue ruleset reconciled against `ci/required-checks.json`, and whether rulesets 23704437 and 23705388 still exist, are active, still carry their rules and have no bypass actor (an admin token sees the list; any token sees whether it could bypass). A shortfall against `total_count` or against the merged-PR search's count (which also keeps that day `complete: false` and marks it `truncated`, so the next run collects it again from scratch; only a day that stopped for budget is resumed, because a truncated day's counted SHAs were filtered through a short run list), a drifted ruleset, a missing or changed safeguard, an API error, or a local export more than 3 days old (measured from the clone's `exported.json` heartbeat, which every export run writes, so an idle clone is not a stale one; a clone silent for 14 days counts as retired, reported but not red) fails the run and marks the snapshot unhealthy; the snapshot is still published so `/ci-status` shows why. A late day, a thin sample and an unmeasured SLO are warnings, never red.

**Verdicts** (`verdicts/<ledger-id>.json`, for every entry with a hypothesis and a merged PR):

1. The anchor is the merge time of the entry's last merged PR. The before-window is the `verdicts.before_days` × 24 hours before it (7), the after-window the `after_days` × 24 hours after it, both cut at that instant. Samples that carry a time (durations, waits) are cut exactly; metrics kept as daily counts (failure and retry rates, catches, SLO shares) read only the whole days inside each window.
2. `pending` until the day holding the after-window's end has been collected, and while any of the window's days still lacks a complete snapshot the collector can fetch (its backfill); `inconclusive` if such a day is past Actions' 90-day retention.
3. `inconclusive` first, naming why: another ledger entry touching one of the same gates merged inside the after-window (a confounder), or the after-window's sample is below the minimum (`verdicts.min_n`, or the SLO's own `min_n`).
4. `verified` when the after-window's value reached `target`.
5. `partial` when it missed the target but moved at least halfway from the baseline toward it. The baseline is the before-window's own reading when it has enough data, otherwise the ledger's `baseline` (for a gate that did not exist before the change).
6. `failed` otherwise.

The entry's `slo` is read over the same windows and reported beside the verdict as better, worse or flat, so a gate that got faster while its SLO got worse is visible. A final verdict is kept as it is unless the hypothesis changes, because Actions data older than 90 days cannot be read again. There is no automatic revert on `failed`: the verdict leads the report, and the next change decides with the numbers in front of it. The three backfilled entries are the recorded fixtures (`packages/ci-steward/src/__tests__/verdicts.test.ts`): each of #1135, #1246 and #1391 comes out `partial` on its own, and against the whole ledger #1135 and #1246 are `inconclusive`, each confounded by the next change to the same gate.

**Floors** (`floors.json`, moved by `report` each Monday): when an SLO is `met` or `ok` for 4 consecutive non-overlapping weekly windows, each floor value tightens halfway to the objective, and the streak starts again. A floor never loosens except through a ledger entry's `floor-release`, applied once and recorded.

**The constraint** is exactly one, by fixed precedence: (1) a tripwire, meaning a collector health failure or a `headroom` breach (ratchet violations join in phase 2); (2) a quality SLO in breach, in `ci/slos.yaml` order; (3) the SLO with the most excess wait-hours against its **objective**: the sum over the population of each item's time beyond the tail objective, plus killed pushes at the tool ceiling for `local-push` and wasted builds at (median ejected wait − median clean queue build) for `wasted-queue-builds`.

**The triggers**, `triggers.json`, are the ranked list of things worth doing something about, computed by `triage` from the data alone, with no model in the loop. Twelve rules, each with its threshold in `ci/config.yaml`'s `triage:` block (which the fence covers, so an unattended change cannot widen a threshold until its own trigger stops firing):

| #   | Fires when                                                                                                                                                                                                                                                                                                                                                   | Severity                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| 1   | an SLO is under its floor for the current window                                                                                                                                                                                                                                                                                                             | red for a quality or tripwire SLO, amber for speed |

The text names which fired, because "CPU or RAM" is the question | red for memory or swap, amber for CPU alone        |

Rule 12 is the one trigger nothing in the pipeline can fix: it is a fact about somebody's laptop, and the action is to run fewer suites at once. It sits above the SLO floors it usually causes, because `local-commit` and `local-push` read mostly as a measurement of the box. Memory and swap make it red and CPU alone amber, because a busy machine still finishes and one out of memory has the kernel killing processes — which is the shape that turned a two-minute suite into a twenty-two-minute one and then killed it.

A spell on `main` that already recovered is amber, not red: the `main-green` SLO counts it, and a 22-minute blip must not drive the page's light for a week after it healed. A trigger names a `proposed` ledger entry only when the entry names that gate **and** its hypothesis measures it, so an entry listing six gates is not offered as the answer to every trigger on any of them.

Each trigger carries what fired with its numbers, the gate or SLO it belongs to, a suggested next step, whether a matching `proposed` ledger entry already exists (matched on metric id and gate), and the day it first fired, so it stays open until its condition clears rather than firing again every morning; the report says so once one has been open `open_days_warning` (14) days. **Triggers open no pull request and change nothing on `main`.** They are data plus a surfaced list: phase 3's `ci-improve` will consume them, and until then a person or an orchestrating agent reads them in `/ci-status`, in the daily report, or in the SessionStart line when one is red.

**The daily report**, `reports/YYYY-MM-DD.html` with `reports/index.html` listing the days newest first, is the human surface: a traffic-light headline, the constraint and the number behind it, the SLO table with a 7-day trend arrow and an inline-SVG sparkline, the open triggers, yesterday's merges and ejections and red spells and job minutes, the experiments in flight, and whether the data can be trusted. It renders from `packages/ci-steward/templates/report.html`, whose CSS is inline, so the page can be restyled without touching engine code; it loads nothing from the network and opens from a `file://` URL. Everything interpolated is escaped, because pull request titles and API error text reach the page. `pnpm ci:report [--open]` builds it from the data branch into a temp path and never pushes; with `--data <dir>` it writes into that working tree, like the daily job, and still never commits or pushes. `--day` for an older day serves the page already on the branch rather than rebuilding it: `latest.json` and `triggers.json` hold one day's readings, so a rebuild would stamp today's numbers with yesterday's date.

**Report copy is terse by rule.** These strings are deterministic code, not model output, so the rule binds whoever edits them: shortest words and sentences that keep the meaning, no filler, no hedging, no repeating the column header, lead with the number. Never trade away a number, a unit, a name or a caveat to save words — short, not vague; a sentence that will not fit ends with an ellipsis rather than losing its last clause. Cells stay under 40 characters and the headline under 120; `daily-report.test.ts` measures both and bans the usual filler. The same rule sits at the top of `packages/ci-steward/templates/report.html`, beside the copy helpers in `daily-report.ts`, and in the `stewarding-ci-pipeline` skill.

**The page never scrolls sideways**, at any width. Prose sits in a 960px column; the SLO table and the trigger list break out to `min(1440px, 100vw - 2rem)`; a table too wide to fit scrolls inside its own panel, never on the page. Under 720px the table becomes cards, CSS only. Consecutive dates in any cell collapse into a run while a gap stays a gap, `day(s)` is never printed, and a sentence still over 120 characters is cut at a word and ends with an ellipsis. **A trailing clause is never dropped:** it is usually the caveat ("this is NOT attributable to the change, because…"), and cutting it and then writing a full stop would turn a hedged sentence into a confident claim of the opposite. Measured in Chromium at 1440x900, 1024x768 and 390x844: `documentElement.scrollWidth - window.innerWidth` is at most 0 at all three.

**The weekly deep summary**, `reports/YYYY-Www.md`, is written each Monday and stays deterministic Markdown (the same inputs render the same bytes): the SLO trend over four weekly windows first, then the constraint, the verdicts issued, real catches per gate (an ejection for failed checks followed by a new commit before re-queue; the rest are wasted builds), the tracked metrics, and the collector's own health. Agents read this and the JSON; the HTML is for people.

**Daily is the reporting cadence, not a smaller window.** The statistics do not change: SLO windows are still non-overlapping 7 days, floors still tighten only after 4 consecutive met-or-ok windows, and a verdict still waits for its whole after-window. GitHub throttles scheduled workflows by hours (measured: p50 2.7 h late), which is fine for a daily report, and nothing in the job depends on the hour it actually runs.

**Local hook timings.** Every `lefthook.yml` command opens with `[ -r packages/ci-steward/bin/time-wrap.sh ] && . packages/ci-steward/bin/time-wrap.sh && ci_steward_time_wrap <hook> <command>` (the guard means a checkout without the script runs the hook untimed, never broken). It is sourced, not a wrapper process, so the command runs in the same shell with the same stdin and exit status; it appends START and END lines to `$(git rev-parse --git-common-dir)/ci-steward/local-timings.jsonl`, shared by every worktree of the clone, and swallows its own errors (`CI_STEWARD_TIMINGS=0` switches it off). INT, TERM and HUP are trapped: the END gets 128+n and the hook exits with it (without the trap, macOS `/bin/sh` recorded a SIGTERM'd hook as a pass and dash wrote no END). A killed run is an END with such a status, or a START with no END older than `local.killed_after_seconds` (7500; SIGKILL runs no trap, so this age is the only evidence it leaves). That number was derived from the pre-push watchdog's 7200-second ceiling plus margin; the watchdog went with the test gate in DOR-2160 and the number stayed, deliberately generous — nothing local is bounded any more, so the only wrong answer here is calling a hook that is still running killed, and the slowest hook run ever measured on this machine is 734 s. Gate metrics may name one leg: `gate.<id>.<metric>@merge_group` or `@pull_request` (`ci/metrics.yaml` `event_qualifiers`). The `ci-local-export` scheduled skill runs `pnpm ci:local-export` daily at 04:30 UTC: it pushes one aggregate per finished day to `local/<clone>/` and a heartbeat `local/<clone>/exported.json`, then trims the file to 30 days and 5 MB (keeping any line appended while it rewrites, so an END is never lost into a phantom kill). It waits on the Schedules page as "Waiting for approval" until the operator approves it with **Approve at Full autonomy**; it runs Bash and `git push`, which a schedule that arrives in a file is held back from (DOR-2100). Runs under `--no-verify` are invisible to it.

**What each event line also carries** (DOR-2160). Every START, END and note records the machine at that instant: `l` the 1-minute load average, `n` online cores, `m` available memory in MiB, `s` swap in use in MiB, any of them `null` where the platform will not say. On Linux the load and memory probes are shell reads of `/proc`; on macOS one `sysctl -n` returns all four, measured at 20 ms per line while the box was at load 561. `m` is MemAvailable on Linux and free pages on macOS, which compresses memory and has no equivalent figure, so read it beside swap rather than alone. Those readings become `tracked.machine-load` and feed trigger 12.

A third event type, `O`, is a **note**: something the exit status cannot carry. `lock_timeout` is a heavy command that gave up waiting for a machine-wide slot and ran uncapped; `lock_wait` is one that waited and got a slot. `tracked.gate-cut-short` reads those beside the OS kills, because both are invisible in every other number — a killed hook leaves no verdict to count, and a command that ran uncapped looks exactly like one that had a slot to itself, which is how a concurrency cap stops existing without anybody noticing.

**The dead-man's switch.** `.claude/hooks/session-maintenance.sh` runs `packages/ci-steward/bin/session-line.mjs` (plain JavaScript, no type stripping) at SessionStart, only when `origin/ci-steward-data` exists locally and behind a hard 0.4-second timeout, so a slow start under load is silence rather than a slow session. It reads `latest.json` with `git cat-file` (no network) and prints one `[Harness]` line when the newest snapshot is over 2 days old (saying the collector stopped only when this checkout has fetched since; otherwise that the local copy is not fetched), its health failed, a safeguard is reported missing, a red trigger is open (from the summary `triage` writes into `latest.json`, so it still reads exactly one file), a local SLO is in breach, or this clone's last hook run in the last 6 hours was killed.

**If the data branch is missing.** The collector never recreates it once a backup tag exists; `data-prepare` fails and the job summary prints the restore command, which pushes the newest tag's commit back to the branch: `git fetch origin tag ci-steward-data/<YYYY-Www> && git push origin 'ci-steward-data/<YYYY-Www>^{commit}:refs/heads/ci-steward-data'`. It creates the branch only on the very first run, when neither the branch nor any tag exists. Worktree sweeps (`scripts/worktree-janitor.sh`) treat the branch as protected.

### The census and the deadlock invariant

`node packages/ci-steward/src/cli.ts census` generates the facts that live in YAML (triggers, events reported on, required, timeout, retries, shards, invoked scripts) and fails when:

- a gate exists in YAML but not in `ci/gates.yaml`, or the reverse (ids: `wf.<workflow-stem>.<job-id>`, `lefthook.<hook>.<command>`, `claude.<HookEvent>.<script-basename>`, `ruleset.<rule>`);
- a job has no `timeout-minutes`;
- **deadlock invariant:** a context in `ci/required-checks.json` has no job of that exact name, or its workflow lacks `pull_request` or `merge_group`, or has a `paths:` filter, or its `pull_request.types` (if present) omits `synchronize`, or a job-level `if:` cannot be satisfied on both events;
- a required job, or any job it needs (directly or through other jobs), contains `continue-on-error`, or a step-level `if:` that is not true on both events on a green run (`!cancelled()` is), or the required job's own job-level `if:` can skip it, and no `ci/census-allowlist.yaml` entry excuses it. Every entry carries a reason; a `no-timeout` entry also carries `expires:`, and any other entry does when the exception is temporary;
- a required fan-in runs with `always()` (or `!cancelled()`) but no step reads `needs.<job>.result` for each job it needs (or `needs.*.result`), so a red dependency would report green;
- an allowlist entry has expired, or excuses nothing any more;
- a generated block (the required-checks list here and in the `creating-pull-requests` skill) differs byte for byte from `ci/required-checks.json`. `census --fix` rewrites the blocks.

It runs as a step of the required `typecheck` job on every PR and every merge group, so it adds no new required context and no deadlock exposure of its own.

**An expiry is a deadline for a person, never a switch.** When an allowlist entry expires, the census fails on every PR, whatever the PR touches, until a PR removes the entry. That is correct for an exception that has genuinely gone stale (a `no-timeout` job that now has data, a `continue-on-error` that was meant to be temporary), and it is an outage if the date was used to schedule a behaviour change. So never schedule a behaviour change with an expiry: if a change must happen on a date, put the date in `ci/config.yaml` and have the tool read it. An entry gets an `expires:` only when a person should act before then. Event-branching `step-if` and `job-if` entries, and harmless `continue-on-error` artifact uploads, are permanent design and carry no expiry.

### Ledger release first, ruleset edit second

The ruleset is edited by hand, with the operator's admin session, and nothing in Actions can edit it. So changes to the required set go in this order:

1. **PR:** the ledger entry (with `field-changes`), the `ci/required-checks.json` change, the regenerated blocks, and, when adding a check, the job itself reporting on both `pull_request` and `merge_group`. It merges through the queue.
2. **Ruleset edit**, after that PR is on `main`.
3. **When removing a check,** a later PR may delete the job, once the ruleset no longer requires it.

The other order leaves a window where live protection differs from declared intent with no record of why, and when adding a check it can require a context no job on `main` reports yet, which deadlocks the queue.

### The fence

The steward may change gates, never the steward or the judge. When the unattended `ci-improve-tick` exists (phase 3), the coverage step fails a `ci-improve/*` PR that touches any path in `ci/steward-owned-paths.json`: `packages/ci-steward/src/**`, `ci/slos.yaml`, `ci/metrics.yaml`, `ci/ratchets.yaml`, `ci/required-checks.json`, `ci/steward-owned-paths.json`, `ci/config.yaml`, `.claude/rules/ci-pipeline.md`, this guide, `claude-code-review.yml`, `REVIEW.md`, `scripts/should-arm-automerge.sh`, `scripts/should-arm-automerge-input.sh`, `scripts/should-redispatch-review.sh` and `review-redispatch.yml`. `typecheck.yml` and `lefthook.yml` are fenced by content instead (the census steps and the time-wrap must stay present), checked by a different runner, because the census cannot guard its own removal.

### The quarantine lane

A test the data has classified flaky can be taken out of the blocking path without a PR, while somebody fixes it. It keeps running, keeps retrying and is still reported; it only loses the power to fail the queue. The list lives on the data branch as `quarantine.json`, so it takes effect on the next queue build.

```bash
pnpm ci:flaky                     # which tests failed and then passed on the same tree
pnpm ci:flaky --fetch             # the same, read live from Actions (artifacts expire after 7 days)
pnpm ci:quarantine list
pnpm ci:quarantine add --runner playwright --file '<spec>' --title '<test>' --reason '<why>'
pnpm ci:quarantine remove --runner playwright --file '<spec>' --title '<test>' --publish
pnpm ci:quarantine reset --publish   # empty the list when no reader will honour it
```

The full walkthrough is the `ci-quarantine` skill. The rules worth knowing here:

- **Evidence, never assertion.** An occurrence is one merge-group SHA on which the test failed and then passed. Two distinct SHAs in 14 days qualify; a test quiet for longer than its own average gap between flakes is `cooling` and is refused, because that is what a fixed test looks like. **A test that fails deterministically is a real bug and may not be quarantined.**
- **Nothing is skipped.** Quarantine is per test, decided by a gate that reads the shard reports — not `grepInvert`, not vitest `exclude`. Every file is still collected and the shard union is unchanged.
- **A failure the list does not name fails as before.** That is the whole gate.
- **An exit code with nothing behind it is not excused.** The gate reads three numbers out of the same reports: the runner's own failed-test tally, its own per-test walk, and the failures it attributes to no test at all (`numFailedTestSuites`, Playwright's top-level `errors[]` — a file that throws on import fails to _collect_, so it never appears as a failed test). It refuses the first two when they disagree, refuses the third outright, and excuses a non-zero exit only when the tally is exactly the set the lane absorbed.
- **One hole is open and named.** A package whose process dies before writing any report — an OOM kill, a segfault in the worker — appears in none of those three numbers, so in a run where a quarantined test also failed it is excused, and **nothing downstream catches it**: `assert-tests-executed.sh` counts turbo tasks and a failed task still ran, and the union check unions the files the other shards collected. Closing it means reading the turbo summary's per-task exit codes in the gate and requiring a named failure from every task that failed. It is not built.
- **The whole lane is printed** in the job summary of every queue build that read it, with its evidence and expiry.
- **The union checks take the list.** `assert-browser-tests-executed.sh` fails when a quarantined browser test did not run — missing, or collected and then skipped. `assert-shard-union.sh` fails when a quarantined vitest test's FILE contributed nothing to any shard. The vitest side is file-level, not per-test: the fan-in has no install and reads no per-test reports, so a quarantined vitest test that stopped running while its file still collects something is not caught there.
- **The ratchets are phase 2, and the exclusion is a requirement on them, not a fact about today.** When `ratchet-assert` is built, the pass-count ratchets must exclude quarantined tests on both sides of every comparison, or quarantining one lowers a high-water mark with no release and no record. `ci/ratchets.yaml` says so in each ratchet's description and `packages/ci-steward/src/__tests__/quarantine.test.ts` fails if that sentence is ever removed. The same file holds the second requirement: tests deleted from source lower the mark by the number deleted, with no release, so the floors catch tests that silently stopped running and never charge for deleting one on purpose.
- **It expires.** 7 days by default, 10 entries at most, and adding one writes a `proposed` "fix or delete this test" ledger entry. `pnpm ci:status` and the weekly report flag a full lane or an entry near expiry. Every threshold is in `ci/config.yaml` under `quarantine:`, with `quarantine-size` and `quarantine-days` in `ci/ratchets.yaml` behind them.
- **It fails safe.** A list that is missing, unreadable, invalid, over the cap, expired, dated in the future, or outliving `max_expiry_days` measured against the reader's own clock is ignored entirely, and then every test blocks as normal. The step that reads it always exits 0: "we could not read the list" must never be a red queue build.
- **You are never locked out of it.** A refused list still parses, so `remove` edits it to repair it, and `reset --publish` replaces it with an empty one. Hand-editing the data branch is never the answer.

## Anti-Patterns

```bash
# ❌ Re-roll CI with an empty commit: 19-25 jobs, a disarm, and a flake scored as a real catch
git commit --allow-empty -m "retrigger" && git push
# ✅ Not yours: re-run the one failed job, once
gh run rerun <run-id> --failed

# ❌ Update a branch to "keep it current" (pre-queue habit; nothing requires it)
gh pr update-branch <n>
# ✅ Nothing. The queue builds on main for you.

# ❌ Merge around the queue
gh pr merge <n> --admin
# ✅ Open with scripts/open-pr.sh, which turns on auto-merge; the required checks gate it
gh pr merge --auto <n>   # only to re-queue after an ejection, or for a PR opened before Nov 24

# ❌ Ask classic protection which checks are required (retired; returned 6 of 9)
gh api repos/{owner}/{repo}/branches/main/protection
# ✅ Ask the ruleset
gh api repos/{owner}/{repo}/rules/branches/main
```

- ❌ A required check whose workflow has a `paths:` filter, or lacks `merge_group:`. ✅ Decide scope inside the job and always report.
- ❌ A job-level `if:` that skips a required check. ✅ Run and pass explicitly; a skipped run satisfies the requirement.
- ❌ Editing the ruleset, then writing the ledger. ✅ Ledger and `ci/required-checks.json` first.
- ❌ A pipeline change with "should be faster" as its reason. ✅ One catalogue metric, a baseline, a target, a date.
- ❌ Pushing or rerunning on the first failed-checks ejection. ✅ Read the failing job, then re-queue once with `gh pr merge --auto <n>` when it is plainly not yours.
- ❌ Re-queueing again after the same check failed twice on the same head. ✅ Stop: it is a real regression only the queue can see. Read the log, fix, push.
- ❌ Cancelling a queued run and re-running it. ✅ Leave it: queued means waiting for a runner, and a re-run goes to the back of the line.

## Troubleshooting

### A required check sits "Expected: waiting for status to be reported"

**Cause:** the workflow did not run for this event: a `paths:` filter, a missing `merge_group:` trigger, or a conflicting PR (GitHub runs no workflows when it cannot build the test-merge commit). **Fix:** rebase if conflicting; otherwise the workflow is wrong, and the census should have caught it. Fix the workflow with a ledger entry.

### "CI Steward census" is red in `typecheck`

**Cause:** YAML and the `ci/` hand files disagree (a new job with no `ci/gates.yaml` entry, a missing `timeout-minutes`, a generated block out of date, a required check that can deadlock). **Fix:** read the step log, which names the gate. `node packages/ci-steward/src/cli.ts census --fix` regenerates the blocks; gates and timeouts are hand edits.

### "File-size ratchet (DOR-2822)" is red in `typecheck`

**Cause:** a file over 500 lines (ESLint's `max-lines` count) grew, a new file passed 500, a file shrank and its entry in `scripts/max-lines/baseline.json` was not lowered, or the baseline was raised against the base. **Fix:** the step names each file and what to do. Move code out of a file that grew or is new; run `pnpm check:max-lines -- --update` to lower entries after a shrink, or to carry an entry to a file's new path after a `git mv`. Never raise an entry: that is the one fix the check refuses.

### "API lint gate (DOR-4996)" is red in `typecheck`

**Cause:** a change added an API lint finding in a route group (an operation with no `operationId`, a command-word path, an undocumented route, an unpaged list and so on), two operations share an `operationId`, a finding was fixed and `scripts/api-lint/baseline.json` was not lowered (on a PR only), or the baseline was raised against the base. **Fix:** the step names the rule, the group and what it found. Fix the new finding; run `pnpm check:api-lint -- --update` after a fix. Rules and fixes: [api-reference.md](api-reference.md#the-api-lint-gate).

**In the merge queue a lowered count only prints.** The step passes `--queue` there, so an entry above its measured count is a note, not a failure. Two queued PRs that each fix one finding in a group each lower that entry by one; git merges the two identical edits cleanly, so the combined tree holds one finding fewer than its baseline says, and failing on that would eject the second PR for a fix. Growth, a new group, a shared id and a raised baseline still fail in the queue. The next `--update` on any PR locks the drop in. So a PR can go red with a lowered count in a group it never touched: that is a queue leftover, not your change. Run `pnpm check:api-lint -- --update` and commit the lowered baseline with your change. The file-size ratchet has the same race and does not yet make this exception: a stale entry there fails in the queue too.

### "the repo › keeps every package within its test budget" is red in `typecheck`

**Cause:** a package added tests faster than source: it now holds more lines of test than its recorded count and more per line of source than its recorded ratio, both in `scripts/test-ratio/baseline.json` (`scripts/test-ratio/check-test-ratio.ts`; pre-push runs the same check as `test-ratio`). **Fix:** delete weaker tests in that package until it is back under, using `.claude/rules/testing.md`, "Is this test worth keeping?", then run `pnpm check:test-ratio -- --update --package <package>` to lower that one budget. Never raise or remove a budget: pre-push refuses that with `--base`, and review is the guard for an edit pushed past the hook. Two PRs that each pass alone can sum past a budget once both land; the second then goes red on its next run, and the fix is the same.

### "CI Steward ledger coverage" is red

**Cause:** the PR touches a pipeline path and adds no `ci/ledger/` entry. **Fix:** `node packages/ci-steward/src/cli.ts ledger-new --slug <what-changed>`, fill in the hypothesis, amend it into the commit.

### `fragment-present` red on a `skip-changelog` PR

**Cause:** the label raced the `opened` event, whose payload is what the step reads. A re-run replays the same payload and fails again. **Fix:** reword a genuinely non-user-facing commit to `chore(`/`ci(` and force-push, or drop the label and add a fragment. See the `creating-pull-requests` skill.

### The ci-steward workflow is red

**Cause:** the collector's own health failed; it is never a PR's problem. **Fix:** read the job summary or `/ci-status`, where each failure names its fix: a truncated fetch (re-run the workflow), a drifted ruleset (put the ruleset back, or land a ledgered PR that matches it), a missing safeguard ruleset (restore it; `plans/ci-steward-status.md` §3 records how each was made), or a stale local export (approve or re-run `ci-local-export`).

### "The ci-steward-data branch is missing"

**Cause:** the branch was deleted despite ruleset 23704437, or the ruleset was removed first. **Fix:** run the restore command the job summary prints (the newest `ci-steward-data/*` tag's commit, pushed to the branch), then re-run the workflow. Never create an empty branch by hand: it would bury the history the tags still hold.

### The queue holds many PRs and nothing merges

**Cause:** usually a flaky required job ejecting groups, runner starvation, or a GitHub Actions outage (githubstatus.com; one on 2026-08-26 held the queue for about 4 hours). **Fix:** do not push, rerun or re-queue. Name the failing job and the evidence where the operator will see it. Automated freeze and recovery are phase 1b.
