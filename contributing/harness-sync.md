# Harness Sync

The cross-agent file-projection engine (`@dorkos/harness`) — how DorkOS projects skills, instructions, hooks, and commands from one canonical source into every agent harness (Claude Code, Codex CLI, Cursor, GitHub Copilot, Gemini CLI, OpenCode, ...), and how to keep its translation tables current.

Pair this guide with:

- [`packages/harness/src/vendor/rulesync-maps.ts`](../packages/harness/src/vendor/rulesync-maps.ts) — the vendored, MIT-licensed snapshot of rulesync's cross-agent hook-event maps and per-tool path constants.
- [`packages/harness/src/vendor/gemini-maps.ts`](../packages/harness/src/vendor/gemini-maps.ts) — the in-repo Gemini CLI maps (rulesync ships none).

## 1. Overview

Every coding agent stores the same five kinds of project config under a different name in a different place: instructions (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `copilot-instructions.md`), skills, hooks, and commands. Harness Sync keeps a single canonical source and **projects** it into each harness's on-disk layout, so one edit reaches every agent.

Two pieces of static data make that possible:

1. **Hook-event maps** — each tool names the same lifecycle event differently (`PreToolUse` vs `BeforeTool` vs `preToolUse`). We translate through a canonical camelCase vocabulary (`HookEvent`): `CANONICAL_TO_<TOOL>_EVENT_NAMES` projects out, the derived reverse map reads back in.
2. **Path constants** — where each tool reads its skills / rules / hooks / commands (`claudecodePaths`, `codexcliPaths`, `copilotPaths`, `cursorPaths`, `geminiPaths`).

## 3. Re-vendor checklist

Run this when bumping the pinned rulesync snapshot (new tool, renamed event, changed path layout). Keep the diff surgical — only the four vendored tables (Claude / Codex / Cursor / Copilot), the attribution header, and any marked DorkOS addition inside those tables.

1. **Fetch the new upstream.** Check out the target rulesync commit locally and note its full SHA and the npm version it corresponds to.
2. **Bump the pinned SHA.** Update the `Pinned: commit <sha>` line in the header of `vendor/rulesync-maps.ts` to the new short SHA (and the `rulesync@<x.y.z>` version). The attribution test asserts this header still contains `dyoshikawa`, the pinned SHA, and `MIT`.
3. **Keep the DorkOS additions.** They sit inside the vendored tables, marked and dated. Re-check each against its vendor page: if upstream has since adopted it, drop the marker; if the vendor renamed or removed the event, fix or remove the entry. Never let a re-vendor silently overwrite them.
4. **Diff the four target tables** against the new upstream — for each of Claude, Codex, Cursor, and Copilot, compare:
   - the `*_HOOK_EVENTS` array (`src/types/hooks.ts`),
   - the `CANONICAL_TO_*_EVENT_NAMES` map (`src/types/hooks.ts`),
   - the path constants (`src/constants/{claudecode,codexcli,copilot,cursor}-paths.ts`).
     Apply only the deltas. Do not re-vendor tools we do not project.
5. **Leave Gemini alone.** `vendor/gemini-maps.ts` is hand-authored and is NOT part of the rulesync snapshot — never overwrite it from upstream. If Gemini's own docs change, update it independently and clear the relevant `TODO(B9/DOR-143)`.
6. **Re-derive reverse maps for free.** Every `*_TO_CANONICAL_EVENT_NAMES` map is `Object.fromEntries(Object.entries(forward).map(([k, v]) => [v, k]))` — never hand-edit a reverse map. If a forward map gains two canonical keys with the same tool spelling, the reverse collapses and the round-trip test will fail; that is the signal to reconcile.
7. **Run the tests.** From the repo root: `pnpm vitest run packages/harness/src/vendor` (round-trip, non-empty, attribution) and `pnpm --filter @dorkos/harness typecheck`.
8. **Run the engine self-check.** `dorkos harness sync --check` — confirms the projected layout still matches every harness on disk before you commit.
9. **Confirm TSDoc.** Every exported const/type needs a `/** ... */` block; the repo's ESLint fails the build on a missing-TSDoc export.

## 4. Installed-plugin projection

A marketplace plugin installed at **project scope** (`<repo>/.dork/plugins/<pkg>/`) is delivered to every harness, including Claude Code, as harness-native files rather than through a runtime SDK plugin array ([ADR 260706-192819](../decisions/260706-192819-harness-native-plugin-delivery.md), amending ADR-0239). The point of parity: the external `claude` CLI run in the repo and a DorkOS-managed session both read the same projected files, so a plugin never works in one and silently not the other.

`scanInstalledPlugins` (`sources/installed.ts`) discovers each project-scoped plugin and enumerates its portable assets (skills, top-level `commands/*.md`, `hooks/hooks.json`). The projector (`plan/installed-projector.ts`) then emits, per plugin:

| Asset         | Claude Code                                          | Codex                                   | OpenCode                                                      | Cursor / Gemini / Copilot           |
| ------------- | ---------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------- | ----------------------------------- |
| **skills**    | symlink `.claude/skills/<pkg>__<name>`               | symlink `.agents/skills/<pkg>__<name>`  | `native` (reads the `.agents/skills` link)                    | `native` (all three read that link) |
| **commands**  | generated wrapper `.claude/commands/<pkg>/<name>.md` | drop (Codex really has no format)       | generated wrapper `.opencode/commands/<pkg>-<name>.md` (flat) | drop, naming each harness's format  |
| **hooks**     | merge into `.claude/settings.local.json`             | fold into generated `.codex/hooks.json` | drop (no declarative hooks — only a code-based TS plugin API) | drop / merge per harness            |
| **AGENTS.md** | scaffold `.claude/CLAUDE.md`                         | native                                  | native                                                        | native (cursor) / scaffold          |

**The `.agents/skills` link is planned whatever harnesses are enabled** (DOR-1518, DOR-1847). It is not a per-harness projection: it is the one directory five of the six harnesses read AND the only project skills root the DorkOS scheduler watches, so `planCanonicalSkillLinks` plans it once per plan and stands down only when an enabled harness already targets it (Codex does). That is what makes the four `native` cells above true rather than aspirational — before it, an OpenCode-only project was told its packages' skills were read from a directory nothing had ever linked into.

**OpenCode specifics** (verified against docs + `sst/opencode` source, 2026-07-06; see [research/20260706_agent_cli_command_skill_naming.md](../research/20260706_agent_cli_command_skill_naming.md)):

- Commands live in a **flat** `.opencode/commands/` dir with **no namespacing**, so a plugin command projects hyphen-joined: `/flow:capture` (Claude) becomes the file `flow-capture.md`, invoked `/flow-capture`. That invocation-name difference is expected, not a bug.
- The generated wrapper's frontmatter is **reduced to only `description`** — OpenCode documents `description`/`agent`/`model`/`subtask`/`template` and its tolerance of unknown keys is undocumented, so Claude-only keys (`allowed-tools`, `argument-hint`, `category`) are stripped rather than passed through.
- Skills are `native`: OpenCode reads `.agents/skills` (and `.claude/skills`) directly, so it reads the namespaced symlink already on disk rather than projecting its own. The reason on the action names that link, and the link is planned unconditionally (see above) — so this is a claim about a path that exists, not about one another harness might have made.
- Hooks **drop honestly**: OpenCode has no declarative hook config, only a code-based TypeScript plugin API, so there is no on-disk hook file to project into.

Key invariants:

- **No artifact, no line — for every harness, not just Claude Code.** A `drop` says something exists that could not travel, so a repo with no hooks and no `.claude/commands` gets neither a `native` nor a `drop` from any of the six. It used to get five command drops and two hook drops about artifacts it did not have, with Claude Code the only one kept quiet — which made the silence read as a bug in the other five rather than the right answer for all of them. **Instructions are the one exception, deliberately**: `AGENTS.md` missing is a real loss every harness should hear about, so all six drop with one reason.
- **`native` means the source is there.** The word says a harness reads a file where it already sits and nothing is written, so a plan may only use it once the engine has confirmed the file exists: `AGENTS.md` for the instruction natives, hooks in `.claude/settings.json` for Claude Code's, a `.md` anywhere under `.claude/commands` for its commands, and — for an installed skill — the `.agents/skills` link above. `buildPlan` stays filesystem-free, so `engine.ts` reads the three FILE questions off disk (`agentsMdExists`, `claudeCommandsExist`, `loadClaudeHooks`) and passes them in; the fourth is not a read at all — the link is something the plan itself contains. Two properties pin it, and they fail on different things: **P9a** (`native-source-exists.property.test.ts`) reds when a `native` names a file that is not on disk, which is three of the four; **P9b** (`native-reachable.property.test.ts`) reds when the source exists and no harness reads it, which is the fourth — revert the unconditional link and P9a stays green, because the plugin's own directory was there the whole time.
- **A `claudeOnlySkills` entry is read where the entry says it is.** The manifest names skills deliberately kept out of the canonical layer, so the `.agents/skills` walk cannot see them and the entry is the only evidence they exist — which is why they produced no line at all for a long time, and why the entry's own `path` is the claim under test rather than the `.claude/skills/<name>` convention. `engine.ts`'s `scanClaudeOnlySkills` resolves each one into a {@link ClaudeOnlySkillLocation} (`path`, `kind` — `directory` / `symlink` / `missing` — and `atProjectionTarget`), and `buildPlan` reads the answer. **Five states, five answers:**
  1. a real directory at `.claude/skills/<name>` → `native` for Claude Code, an honest drop for every other enabled harness. The only state that produces actions.
  2. a real directory somewhere else → a warning naming the path: the skill is real and no harness reads it there. Calling this "stale" was a wrong statement about a skill that is exactly where the manifest said.
  3. also in `.agents/skills`, in any shape → a warning that the entry is redundant, on the FIRST pass and every one after. **Only sub-case 1 of this — a real directory at the projection target — withholds the claude-code symlink**, because only that one is a conflict; a symlink there is the engine's own projection and IS planned, since withholding it would make the orphan sweep prune a working link.
  4. a symlink, with no canonical skill of that name → a warning: it is either a projection or a link to a skill kept elsewhere, and neither is a skill kept in `.claude/skills`.
  5. nothing at the path → a warning that the entry is stale.
     The lookup is a filesystem one, not a string compare, so its case behaviour is the filesystem's: an entry whose case does not match its directory resolves on macOS and reads stale on Linux.
- **Namespacing is mandatory, and `__` alone does not mean managed.** Installed skills are always `<pkg>__<name>` so they can never overwrite an authored skill. The predicate for "this is an engine-managed projection" is the PAIR: the name carries `__` **and** the entry is a symlink, because a projection is the only thing the engine writes into these dirs and it only ever writes one as a link. `scanSkillDirs` (`scan/scanner.ts`) and the orphan sweep (`sweepInstalledOrphans`) both ask for both halves, so a real directory a person named `my__helper` is authored content and is scanned, projected, and KEPT like any other skill (DOR-1844, DOR-1842). Two costs remain for an authored `__` skill, both reproduced 2026-09-07, and neither loses the authored SOURCE. (1) The `EPHEMERAL_GITIGNORE_PATTERNS` globs (`.agents/skills/*__*`, `.claude/skills/*__*`) cannot ask git what a symlink is, so such a skill's source directory is gitignored and never reaches a teammate's clone. (2) An authored `.agents/skills/my__helper` SYMLINK is indistinguishable from a managed projection by construction, so the scan skips it and the sweep deletes the link itself (`swept: ['.agents/skills/my__helper']`); the real directory behind it survives, and `--check` calls that clean because nothing was ever planned for it. That one is older than either ticket — the old name-only rule skipped such an entry too. **`__` is still an awkward name for an authored skill** — but the engine no longer pretends such a skill does not exist, and no longer deletes the link it just made for one.
- **A skill whose source is a symlink is a skill.** `.agents/skills/x -> ../../elsewhere/x` is how a person links in a skill kept outside the repo, and Codex follows it natively, so the scanner follows it too: an entry counts when it is a directory or a symlink resolving to one, and directly contains `SKILL.md`. A dangling link is skipped, never thrown on. `scanSkillDirs` takes `{ includeManagedProjections }` to separate the two kinds of caller: PLANNERS (`scanSkills`, `collectPortableSkills`) leave it off, so the projector never re-derives its own output; READERS that mirror what a harness reads off disk — the Codex slash palette (`services/runtimes/codex/scan-skill-commands.ts`) and the `dorkos://skills` MCP resource — turn it on, because a bare `codex` in the same repo lists those projections and parity is the promise.
- **Skill identity differs per harness.** Claude Code keys a skill by its **directory** name, so the `<pkg>__<name>` directory namespacing fully protects it. OpenCode and Codex key a skill by its **`SKILL.md` frontmatter `name`** (source-verified: `sst/opencode` `skill/index.ts` keys its map on `md.data.name`; Codex likewise treats the frontmatter name as identity), which the directory namespacing does NOT change — so two skills sharing a frontmatter name collide there. The projector cannot rename inside a plugin's `SKILL.md`, so it emits a `ProjectionWarning` (`planSkillNameCollisions`) naming the colliding skills and the frontmatter-keyed harness. Fix collisions by renaming the frontmatter `name` at the source.
- **`${CLAUDE_PLUGIN_ROOT}` is rewritten to the absolute install dir** in every command wrapper (Claude and OpenCode), every merged Claude hook command, AND every installed-plugin hook folded into a generated hook file (`.codex/hooks.json`, `.cursor/hooks.json`, `.github/hooks/copilot-hooks.json`) — the install root is known at plan time (`rewritePluginRootInHooks`). So a folded plugin hook actually works in the target harness, and the Claude-only-token `ProjectionWarning` now fires ONLY for **authored** hooks (unknown install root) or other unresolved `${CLAUDE_*}` tokens. A projected skill whose `SKILL.md` still carries the token cannot be rewritten (it is read as-is), so the projector emits a `ProjectionWarning` instead.
- **Command wrappers carry a marker line** (`dorkos:generated-command ...`) right after the YAML frontmatter. That marker is the sole ownership predicate for the uninstall sweep, so a hand-authored command is never deleted, even one sharing a wrapper directory. Claude Code owns a whole per-plugin dir (`.claude/commands/<pkg>/`): if that dir already holds authored (marker-less) content, the plugin's command projection surfaces as a conflict and nothing is written into it. The OpenCode dir (`.opencode/commands/`) is instead **shared and flat**, so the block is per-**file**: only a wrapper whose exact path is already occupied by an authored (marker-less) file is a conflict; the plugin's other wrappers still project alongside authored commands.
- **Plugin hooks merge, never overwrite.** `.claude/settings.local.json` is user-owned, so the engine touches only its own managed matcher groups and leaves every user hook and other settings key intact. Ownership is explicit: each managed group carries the `_dorkosHarness: "<pkg>"` sentinel key (Claude Code tolerates the unknown key and the tagged hook still fires, validated on CLI 2.1.197). Ownership is never inferred from the command string, so a plugin hook that does not mention its install path still re-syncs idempotently and sweeps on uninstall, and a user hook that mentions `.dork/plugins/` is never misclassified. A settings file that exists but cannot be parsed (corrupt, mid-write) aborts the merge as a conflict rather than being rewritten. See `apply/settings-hooks.ts`.
- **Plugin hooks need a person's yes before they project (DOR-522).** A hook is a shell command a harness runs unattended, and installing a marketplace package asks nobody (`marketplace.install` is tier `act`). So DorkOS's install-triggered projection passes a per-package gate (`project(root, { allowPluginHooks })`, applied at PLAN time so it covers the generated `.codex/hooks.json` and friends as well as the Claude settings merge) and raises an approval card naming the package and the literal commands. A yes is recorded in `harness.approvedHooks` as `<packageName>@<digest>` over the resolved project path and every hook (command, event and matcher), so a package that moves an allowed command from `Stop` to `PreToolUse` asks again rather than inheriting consent. A no is remembered for the life of the process only, so a refused package stops raising a card on every later install without becoming a decision nobody can undo. The engine itself has no opinion: `dorkos harness sync`, run by a person in their own terminal, passes no gate and projects everything. The decision lives at the server seam, `apps/server/src/services/harness/hook-approval.ts`, whose module docs state the guarantee and its limits (notably: the digest binds the command text, not the content of a script it invokes).
- **A generated hooks file is owned by a sidecar, not by its path.** `.codex/hooks.json`, `.cursor/hooks.json` and `.github/hooks/copilot-hooks.json` are all paths their own vendors tell people to hand-write, so the engine claims one only when `<target>.dorkos-generated` sits beside it holding the sha256 of the exact bytes on disk (`apply/generated-ownership.ts`). Owned → rewritten when the content changes, untouched when it does not, swept with its sidecar when the plan stops generating it. Not owned — no sidecar, or a sidecar that no longer matches because somebody edited the file — → never written, never swept. A marker inside the file could not draw that line: it cannot tell a generated file from a generated file a person has since edited. The Codex file additionally carries the `description` key Codex documents, which reads as a comment and says a program wrote it.
- **A file the engine does not own is reported two different ways, and only one of them is a fault.** At a target the plan WANTS to generate it is a **conflict**: a projection was blocked, `applyPlan` returns it in `conflicts`, `checkPlan` in `blocked`, and both the CLI's `--fix` and `--check` exit 1 with the way out (move the hooks into `.claude/settings.json`, or delete the file). At a target the plan writes nothing to — the first auto-projection pass, which has no hook contributors by design, or a harness the manifest never enabled — it is **left alone**: `applyPlan` and `checkPlan` both return the path in `leftAlone`, the CLI names it under its own heading, and neither command exits non-zero. Nothing was blocked, so a person who keeps their own `.codex/hooks.json` never gets a standing failing command for it.
- **Ownership is the whole sweep guard; the manifest is not consulted.** A harness leaving `harnesses` means DorkOS stops projecting into it, so its generated file is swept rather than left behind still firing. The sidecar is what makes that safe: those bytes are provably the engine's, and nothing a person wrote is reachable either way. Nothing on the plan carries the enabled set any more — it had no reader once the guard went, and a field written and never read is a claim nobody checks.
- **Migration, for files written before sidecars existed** (in order): (1) the bytes on disk are already exactly what would be written now → adopt silently, writing only the sidecar; (2) `.codex/hooks.json` holding the engine's own pre-DOR-1842 bare event map — a top-level object whose every key is one of the ten Codex spellings the old generator could actually emit, each mapping to an array — with no sidecar ever written → rewrite it into the documented shape; (3) anything else → conflict. **Those ten are a frozen literal, never derived from `CANONICAL_TO_CODEXCLI_EVENT_NAMES`** (DOR-1847): rule 2 is a claim about what a PAST build wrote, so it must not track a map the present one extends. `SessionEnd` joined that map and a bare `SessionEnd` map is a file no DorkOS build has ever produced — deriving would have handed rule 2 a licence over somebody's file, and every later map addition would widen it the same way, silently. Cursor's and Copilot's legacy files cannot be told from hand-written ones (they were always in the vendor's own wrapper shape), so they take rule 3 and the conflict message says what to do.
- **Projections are gitignored machine-local ephemera.** Skill symlinks, the settings file, the three generated hooks files and their sidecars are covered by `EPHEMERAL_GITIGNORE_PATTERNS` (`sources/resolve-roots.ts`) mirrored in the repo `.gitignore`; the Claude wrapper directories are covered by a self-ignoring `.gitignore` the engine writes inside each `.claude/commands/<pkg>/` (a static rule would swallow authored `.claude/commands/<ns>/` dirs). The shared flat `.opencode/commands/` dir gets one engine-owned `.gitignore` that names **each generated wrapper filename explicitly** plus itself — never a `*` wildcard, which would hide authored commands. An authored `.opencode/commands/.gitignore` (marker-less) is treated as a conflict, never overwritten.
- **A projection whose source is gone is pruned — and only that.** `applyPlan(..., { sweepOrphans: true })` sweeps orphaned skill symlinks, Claude command wrappers (and their emptied dirs), OpenCode command wrappers and their aggregated `.gitignore` (marker-scoped, so authored files in the shared dir are never touched), managed settings hooks, and generated hooks files whose sidecar proves the engine wrote them (file and sidecar always together). Every one of those has an ownership predicate; nothing is swept by path alone. The skill sweep's keep-set is every `symlink` target in the plan whatever its provenance, not just the installed ones — an authored skill NAMED with a `__` projects as an authored symlink at a path that looks managed, and keeping only installed targets made one apply create that link and delete it again (DOR-1844). What the sweep may touch stays the narrow `__`-plus-symlink test; only what it keeps is wide. Auto-projection reruns project+apply after every install/uninstall (`apps/server/src/services/harness/auto-project.ts`).

  **An uninstalled plugin is not the only way a source disappears.** Remove or rename `.agents/skills/<x>` and `.claude/skills/<x>` is left pointing at nothing — no plan action names it, so for a long time nothing noticed and Claude Code was left with a link it cannot follow (SK-10). A second sweep takes those (`apply/authored-orphans.ts`), behind its own ownership predicate: a **symlink** (never a real directory), **dead**, whose link text resolves **into `.agents/skills/`** (a person's link to a vendored skill elsewhere is theirs), carrying **no `__`** (that shape is `sweepInstalledOrphans`' territory, and one path may only have one owner), and **not named by the current plan** (a link the plan still wants is drift for `applySymlink` to repair). One scanner answers for both `--check` and `--fix`, so the report and the sweep cannot disagree about what an orphan **is**; **when** each runs is the CLI's business, and `--check --harness <id>` withholds the list because the matching `--fix` does not sweep (`sweepOrphans` is passed only for a full plan) — naming a link the recommended command would not remove is a non-zero exit nobody can clear.

  **This is the first sweep that can delete a git-TRACKED file, and that is deliberate.** `EPHEMERAL_GITIGNORE_PATTERNS` covers the namespaced installed links (`.claude/skills/*__*`), not the authored ones: in this repo `.claude/skills/<name>` links are committed (`git ls-files -s .claude/skills` shows mode `120000` for 18 of its 32 tracked entries; the other 14 are files inside the Claude-only skill dirs), so a teammate's clone gets them. When you delete the skill's source, the link is exactly as broken in the commit as it is on disk, and the sweep removes it — which shows up as a deletion in `git status`, to be committed alongside the source you removed. Nothing is lost that git does not still hold. The server runs the same sweep unattended after every marketplace install/uninstall (`services/harness/auto-project.ts`), so the deletion can appear without anybody typing a sync command; that is why the predicate refuses everything but a dead link into `.agents/skills/`.

- **A dead link is drift, never a crash.** `dorkos harness sync --check` is the command a person runs to be _told_ what is wrong with their tree, so it never throws for anything it finds there. A broken symlink is the shape that used to break that promise: `checkPlan` read straight through one at a `generate` target and died with ENOENT (AP-05), while `applyScaffold` counted one as a pointer already present and never repaired it (IN-05). A dead link is now an answer — drift at a `generate` or `scaffold` target, an orphan under `.claude/skills` — and `--fix` **removes the link before writing**, because `writeFileSync` follows a symlink and would otherwise put the file wherever the link pointed. What a path IS gets asked once, in `apply/link-state.ts`, and every caller says which answer it means.

- **Two shapes at a `generate` target are blocked, not drift** (`apply/generate-occupants.ts`). A **directory** there is somebody's content and `writeFileSync` cannot land on it anyway; before this rule `--check` called it drift and told the person to run a `--fix` that then died with EISDIR partway through the loop. A **live symlink** is the subtler one: reading and writing both succeed, somewhere that is not this path — a `.codex/hooks.json` linked to a file outside the repository had the pre-sidecar migration rewrite that outside file. Neither is ever written over, whoever owns what is at the far end, and both carry a reason naming the way out. Only a DEAD link is cleared and replaced, because nothing is there.

Global installs (`~/.dork/plugins`) are still SDK-injected by the claude-code runtime as a transitional exception until global-scope projection lands (DOR-174).

## 5. The vendor-facts table and the coverage walk

`packages/harness/src/vendor-facts/` answers a question the rest of the engine's tests do not: **would the harness actually load what we wrote?** Everything above this section is about writing files. A test that asserts a symlink exists at `.claude/skills/x` proves the engine did its job; it says nothing about whether Claude Code reads that path, keys the skill by its directory, or follows the link at all. Those are facts about someone else's product, and they change without telling us.

Two pieces:

- **`index.ts` — the facts.** One typed, dated, quoted record per harness: where it reads skills at project and user scope, how it walks for those paths (`ascend-to-repo-root`, `ascend-to-worktree`, `descend-recursive`, `fixed`), what it treats as a skill's identity, its name rules, what it does with duplicates and symlinks, and whether a new skill appears without a restart. It is §1.1 of [`meta/harness-sync-capabilities.md`](../meta/harness-sync-capabilities.md) as data — that document is the source, and it is where a new cell's reasoning belongs.
- **`coverage.ts` — the walk.** `harnessCoverage(harness, root, { cwd })` walks a real directory the way that harness's facts say it walks, and returns `{ discovered, uncertain }`. It imports the facts, `HarnessId` and the skills frontmatter parser, and nothing from `plan/` or `apply/` — it is the oracle those get measured against, so it must not be able to agree with them by construction.

**Every skill lands in exactly one of the two lists.** `discovered` is a confident claim: this harness's own documentation is enough to say the skill loads, and under this key. `uncertain` is the refusal to make one. So a consumer may read `discovered` alone and trust it — which is what the projection audits will do. A skill becomes uncertain when it was reached through a symlink and the harness does not document following them; when its identity rule is unknown and the directory and frontmatter names disagree; when the harness keys on the frontmatter name and there is none; when a documented name rule is broken and the consequence is unstated; or when the name must (or might have to) match the directory and cannot be checked. The one case that looks like an exception is not: where a skill is reachable twice under an unknown dedupe rule, the first copy reached is still a confident discovery and each _later_ copy is the uncertain entry.

**Every cell is documentation-derived.** `verified` is `'docs'` on all six rows: nothing here has been checked against a running `claude`, `codex`, `opencode`, `cursor-agent`, `gemini` or `copilot`. `plans/harness-sync-test-plan.md` calls that the H tier, and it does not exist yet. A test asserts the all-`'docs'` state on purpose, so the first real binary run has to change an assertion rather than quietly widen a claim.

**`unknown` is an answer, and the most valuable one in the file.** Where a vendor page said nothing — whether OpenCode follows symlinks, whether Gemini keys a skill by its directory or its frontmatter name, what Cursor does with a name that breaks its own charset rule — the cell says `unknown`, and `harnessCoverage()` reports the skill in `uncertain` instead of counting it or dropping it. That is what stops the table becoming a confident, wrong CI gate. An assertion reads "`discovered` has what we projected **and** `uncertain` is empty", so a gap fails loudly. **On a tree DorkOS has already projected into, expect `uncertain` NOT to be empty** — the projection is a symlink into `.claude/skills`, and Cursor, OpenCode and Copilot do not document whether they follow one, so this worktree reports 31 discovered and 18 uncertain for each of the three, every one of the 18 a symlink reason for a skill they also reach as a real directory under `.agents/skills`. The assertion for a projected tree is the weaker, still-honest one: `uncertain` is empty **or** holds only symlink-reason entries whose skill also appears in `discovered` by another path. Anything else is a real finding, and DOR-1847's false-native work leans on that shape. Filling an `unknown` in with a plausible guess is the single most damaging edit anyone can make here.

**To update a cell when a vendor changes:**

1. Fetch the vendor page again and read the sentence that states the behaviour.
2. Edit the cell, put that sentence in `source.quote`, and bump `source.fetchedAt` to the day you fetched it. **A per-row date is expected, not forbidden**: the rows start out sharing `VENDOR_FACTS_FETCHED_AT` because they were compiled in one pass, and a row carrying its own later literal is the signal that it alone was re-checked. Write the literal; do not move the shared constant to cover one row.
3. If the change is behavioural rather than editorial, update §1.1 of the capabilities contract in the same commit — the table and the contract are one claim in two places.
4. Run `pnpm vitest run packages/harness/src/vendor-facts`. Several facts are pinned by name (that Claude Code alone does not read `.agents/skills`; that every `onInvalidName` is still `unknown`), and a census pins every cell the walk branches on, so a real change reds a test and the red is the prompt to bring a fixture with it. Three values in the vocabulary have no row today — `dedupe: 'by-name'`, `onInvalidName: 'skip'` and `'warn-and-load'` — and the census is what keeps that visible instead of leaving an unexercised branch nobody notices.
5. A cell you verified by **running the harness** flips `verified` to `'binary'` — and then say so in the quote: which binary, which version, what you observed.

**What it is for.** `harnessCoverage()` is the measuring stick for the projection fixes it precedes. DOR-1847's is landed: `__tests__/properties/native-reachable.property.test.ts` (P9b) asserts that every `native` skill action names a source the harness's own read paths reach, in two tiers, because the vendors are two different amounts of clear. **Authored** skills take the strict shape above — in `discovered`, with any `uncertain` entry about them a symlink reason for a skill also discovered by its real path. **Installed** skills take reachability: a `<pkg>__<name>` directory breaks OpenCode's and Cursor's documented name rules twice over, so `uncertain` is the honest answer there (SK-09, SK-12) — what the tier forbids is the walk not reaching the skill at all, and every reason it is uncertain has to be one of the vendor's own documented unknowns. That second tier is what the unconditional `.agents/skills` link is measured by: revert the link and it reds with the harness and skill named, while a file-existence check (P9a) stays green, because the plugin's own directory existed the whole time. And eventually the H tier, which will replace `'docs'` cells with observed ones and is expected to contradict some of them. When it does, the disagreement is a finding about the engine, not a bug in the table — as long as the table said honestly where it got each number.
