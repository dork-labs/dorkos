# Harness Sync

The cross-agent file-projection engine (`@dorkos/harness`) — how DorkOS projects skills, instructions, hooks, and commands from one canonical source into every agent harness (Claude Code, Codex CLI, Cursor, GitHub Copilot, Gemini CLI, OpenCode, ...), and how to keep its translation tables current.

Pair this guide with:

- [`packages/harness/src/vendor/rulesync-maps.ts`](../packages/harness/src/vendor/rulesync-maps.ts) — the vendored, MIT-licensed snapshot of rulesync's cross-agent hook-event maps and per-tool path constants.
- [`packages/harness/src/vendor/gemini-maps.ts`](../packages/harness/src/vendor/gemini-maps.ts) — the in-repo Gemini CLI maps (rulesync ships none).

## 1. Overview

Every coding agent stores the same five kinds of project config under a different name in a different place: instructions (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` / `copilot-instructions.md`), skills, hooks, and commands. Harness Sync keeps a single canonical source and **projects** it into each harness's on-disk layout, so one edit reaches every agent.

Two pieces of static data make that possible:

1. **Hook-event maps** — each tool names the same lifecycle event differently (`PreToolUse` vs `BeforeTool` vs `preToolUse`). We translate through a canonical camelCase vocabulary (`HookEvent`): `CANONICAL_TO_<TOOL>_EVENT_NAMES` projects out, the derived reverse map reads back in.
2. **Path constants** — where each tool reads its skills / rules / hooks / commands (`claudecodePaths`, `codexcliPaths`, `copilotPaths`, `cursorPaths`, `geminiPaths`).

The one hand-authored input is `.agents/harness.manifest.json` — see §11 for every key it has.

## 3. Re-vendor checklist

Run this when bumping the pinned rulesync snapshot (new tool, renamed event, changed path layout). Keep the diff surgical — only the four vendored tables (Claude / Codex / Cursor / Copilot), the attribution header, and any marked DorkOS addition inside those tables.

1. **Fetch the new upstream.** Check out the target rulesync commit locally and note its full SHA and the npm version it corresponds to.
2. **Bump the pinned SHA.** Update the `Pinned: commit <sha>` line in the header of `vendor/rulesync-maps.ts` to the new short SHA (and the `rulesync@<x.y.z>` version). The attribution test asserts this header still contains `dyoshikawa`, the pinned SHA, and `MIT`.
3. **Keep the DorkOS additions.** They sit inside the vendored tables, marked and dated. Re-check each against its vendor page: if upstream has since adopted it, drop the marker; if the vendor renamed or removed the event, fix or remove the entry. Never let a re-vendor silently overwrite them.
4. **Diff the four target tables** against the new upstream — for each of Claude, Codex, Cursor, and Copilot, compare:
   - the `*_HOOK_EVENTS` array (`src/types/hooks.ts`),
   - the `CANONICAL_TO_*_EVENT_NAMES` map (`src/types/hooks.ts`),
   - the path constants (`src/constants/{claudecode,codexcli,copilot,cursor}-paths.ts`).
     Apply only the deltas. Do not re-vendor tools we do not project.
5. **Leave Gemini alone.** `vendor/gemini-maps.ts` is hand-authored and is NOT part of the rulesync snapshot — never overwrite it from upstream. If Gemini's own docs change, update it independently and clear the relevant `TODO(B9/DOR-143)`.
6. **Re-derive reverse maps for free.** Every `*_TO_CANONICAL_EVENT_NAMES` map is `Object.fromEntries(Object.entries(forward).map(([k, v]) => [v, k]))` — never hand-edit a reverse map. If a forward map gains two canonical keys with the same tool spelling, the reverse collapses and the round-trip test will fail; that is the signal to reconcile.
7. **Run the tests.** From the repo root: `pnpm vitest run packages/harness/src/vendor` (round-trip, non-empty, attribution) and `pnpm --filter @dorkos/harness typecheck`.
8. **Run the engine self-check.** `dorkos harness sync --check` — confirms the projected layout still matches every harness on disk before you commit.
9. **Confirm TSDoc.** Every exported const/type needs a `/** ... */` block; the repo's ESLint fails the build on a missing-TSDoc export.

## 4. Installed-plugin projection

A marketplace plugin installed at **project scope** (`<repo>/.dork/plugins/<pkg>/`) is delivered to every harness, including Claude Code, as harness-native files rather than through a runtime SDK plugin array ([ADR 260706-192819](../decisions/260706-192819-harness-native-plugin-delivery.md), amending ADR-0239). The point of parity: the external `claude` CLI run in the repo and a DorkOS-managed session both read the same projected files, so a plugin never works in one and silently not the other.

`scanInstalledPlugins` (`sources/installed.ts`) discovers each project-scoped plugin and enumerates its portable assets (skills, top-level `commands/*.md`, `hooks/hooks.json`). The projector (`plan/installed-projector.ts`) then emits, per plugin:

| Asset         | Claude Code                                          | Codex                                   | OpenCode                                                      | Cursor / Gemini / Copilot           |
| ------------- | ---------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------- | ----------------------------------- |
| **skills**    | symlink `.claude/skills/<pkg>__<name>`               | symlink `.agents/skills/<pkg>__<name>`  | `native` (reads the `.agents/skills` link)                    | `native` (all three read that link) |
| **commands**  | generated wrapper `.claude/commands/<pkg>/<name>.md` | drop (Codex really has no format)       | generated wrapper `.opencode/commands/<pkg>-<name>.md` (flat) | drop, naming each harness's format  |
| **hooks**     | merge into `.claude/settings.local.json`             | fold into generated `.codex/hooks.json` | drop (no declarative hooks — only a code-based TS plugin API) | drop / merge per harness            |
| **AGENTS.md** | scaffold `.claude/CLAUDE.md`                         | native                                  | native                                                        | native (cursor) / scaffold          |

**The `.agents/skills` link is planned whatever harnesses are enabled** (DOR-1518, DOR-1847). It is not a per-harness projection: it is the one directory five of the six harnesses read AND the only project skills root the DorkOS scheduler watches, so `planCanonicalSkillLinks` plans it once per plan and stands down only when an enabled harness already targets it (Codex does). That is what makes the four `native` cells above true rather than aspirational — before it, an OpenCode-only project was told its packages' skills were read from a directory nothing had ever linked into.

**OpenCode specifics** (verified against docs + `sst/opencode` source, 2026-07-06; see [research/20260706_agent_cli_command_skill_naming.md](../research/20260706_agent_cli_command_skill_naming.md)):

- Commands live in a **flat** `.opencode/commands/` dir with **no namespacing**, so a plugin command projects hyphen-joined: `/flow:capture` (Claude) becomes the file `flow-capture.md`, invoked `/flow-capture`. That invocation-name difference is expected, not a bug.
- The generated wrapper's frontmatter is **reduced to only `description`** — OpenCode documents `description`/`agent`/`model`/`subtask`/`template` and its tolerance of unknown keys is undocumented, so Claude-only keys (`allowed-tools`, `argument-hint`, `category`) are stripped rather than passed through.
- Skills are `native`: OpenCode reads `.agents/skills` (and `.claude/skills`) directly, so it reads the namespaced symlink already on disk rather than projecting its own. The reason on the action names that link, and the link is planned unconditionally (see above) — so this is a claim about a path that exists, not about one another harness might have made.
- Hooks **drop honestly**: OpenCode has no declarative hook config, only a code-based TypeScript plugin API, so there is no on-disk hook file to project into.

Key invariants:

- **No artifact, no line — for every harness, not just Claude Code.** A `drop` says something exists that could not travel, so a repo with no hooks and no `.claude/commands` gets neither a `native` nor a `drop` from any of the six. It used to get five command drops and two hook drops about artifacts it did not have, with Claude Code the only one kept quiet — which made the silence read as a bug in the other five rather than the right answer for all of them. **Instructions are the one exception, deliberately**: `AGENTS.md` missing is a real loss every harness should hear about, so all six drop with one reason.
- **`native` means the source is there.** The word says a harness reads a file where it already sits and nothing is written, so a plan may only use it once the engine has confirmed the file exists: `AGENTS.md` for the instruction natives, hooks in `.claude/settings.json` for Claude Code's, a `.md` anywhere under `.claude/commands` for its commands, and — for an installed skill — the `.agents/skills` link above. `buildPlan` stays filesystem-free, so `engine.ts` reads the three FILE questions off disk (`agentsMdExists`, `claudeCommandsExist`, `loadClaudeHooks`) and passes them in; the fourth is not a read at all — the link is something the plan itself contains. Two properties pin it, and they fail on different things: **P9a** (`native-source-exists.property.test.ts`) reds when a `native` names a file that is not on disk, which is three of the four; **P9b** (`native-reachable.property.test.ts`) reds when the source exists and no harness reads it, which is the fourth — revert the unconditional link and P9a stays green, because the plugin's own directory was there the whole time.
- **A `claudeOnlySkills` entry is read where the entry says it is.** The manifest names skills deliberately kept out of the canonical layer, so the `.agents/skills` walk cannot see them and the entry is the only evidence they exist — which is why they produced no line at all for a long time, and why the entry's own `path` is the claim under test rather than the `.claude/skills/<name>` convention. `engine.ts`'s `scanClaudeOnlySkills` resolves each one into a {@link ClaudeOnlySkillLocation} (`path`, `kind` — `directory` / `symlink` / `missing` — and `atProjectionTarget`), and `buildPlan` reads the answer. **Five states, five answers:**
  1. a real directory at `.claude/skills/<name>` → `native` for Claude Code, an honest drop for every other enabled harness. The only state that produces actions.
  2. a real directory somewhere else → a warning naming the path: the skill is real and no harness reads it there. Calling this "stale" was a wrong statement about a skill that is exactly where the manifest said.
  3. also in `.agents/skills`, in any shape → a warning that the entry is redundant, on the FIRST pass and every one after. **Only sub-case 1 of this — a real directory at the projection target — withholds the claude-code symlink**, because only that one is a conflict; a symlink there is the engine's own projection and IS planned, since withholding it would make the orphan sweep prune a working link.
  4. a symlink, with no canonical skill of that name → a warning: it is either a projection or a link to a skill kept elsewhere, and neither is a skill kept in `.claude/skills`.
  5. nothing at the path → a warning that the entry is stale.
     The lookup is a filesystem one, not a string compare, so its case behaviour is the filesystem's: an entry whose case does not match its directory resolves on macOS and reads stale on Linux.
- **Namespacing is mandatory, and `__` alone does not mean managed.** Installed skills are always `<pkg>__<name>` so they can never overwrite an authored skill. The predicate for "this is an engine-managed projection" is the PAIR: the name carries `__` **and** the entry is a symlink, because a projection is the only thing the engine writes into these dirs and it only ever writes one as a link. `scanSkillDirs` (`scan/scanner.ts`) and the orphan sweep (`sweepInstalledOrphans`) both ask for both halves, so a real directory a person named `my__helper` is authored content and is scanned, projected, and KEPT like any other skill (DOR-1844, DOR-1842). Two costs remain for an authored `__` skill, both reproduced 2026-09-07, and neither loses the authored SOURCE. (1) The `EPHEMERAL_GITIGNORE_PATTERNS` globs (`.agents/skills/*__*`, `.claude/skills/*__*`) cannot ask git what a symlink is, so such a skill's source directory is gitignored and never reaches a teammate's clone. (2) An authored `.agents/skills/my__helper` SYMLINK is indistinguishable from a managed projection by construction, so the scan skips it and the sweep deletes the link itself (`swept: ['.agents/skills/my__helper']`); the real directory behind it survives, and `--check` calls that clean because nothing was ever planned for it. That one is older than either ticket — the old name-only rule skipped such an entry too. **`__` is still an awkward name for an authored skill** — but the engine no longer pretends such a skill does not exist, and no longer deletes the link it just made for one.
- **A skill whose source is a symlink is a skill.** `.agents/skills/x -> ../../elsewhere/x` is how a person links in a skill kept outside the repo, and Codex follows it natively, so the scanner follows it too: an entry counts when it is a directory or a symlink resolving to one, and directly contains `SKILL.md`. A dangling link is skipped, never thrown on. `scanSkillDirs` takes `{ includeManagedProjections }` to separate the two kinds of caller: PLANNERS (`scanSkills`, `collectPortableSkills`) leave it off, so the projector never re-derives its own output; READERS that mirror what a harness reads off disk — the Codex slash palette (`services/runtimes/codex/scan-skill-commands.ts`) and the `dorkos://skills` MCP resource — turn it on, because a bare `codex` in the same repo lists those projections and parity is the promise.
- **Skill identity differs per harness.** Claude Code keys a skill by its **directory** name, so the `<pkg>__<name>` directory namespacing fully protects it. OpenCode and Codex key a skill by its **`SKILL.md` frontmatter `name`** (source-verified: `sst/opencode` `skill/index.ts` keys its map on `md.data.name`; Codex likewise treats the frontmatter name as identity), which the directory namespacing does NOT change — so two skills sharing a frontmatter name collide there. The projector cannot rename inside a plugin's `SKILL.md`, so it emits a `ProjectionWarning` (`planSkillNameCollisions`) naming the colliding skills and the frontmatter-keyed harness. Fix collisions by renaming the frontmatter `name` at the source.
- **`${CLAUDE_PLUGIN_ROOT}` is rewritten to the absolute install dir** in every command wrapper (Claude and OpenCode), every merged Claude hook command, AND every installed-plugin hook folded into a generated hook file (`.codex/hooks.json`, `.cursor/hooks.json`, `.github/hooks/copilot-hooks.json`) — the install root is known at plan time (`rewritePluginRootInHooks`). So a folded plugin hook actually works in the target harness, and the Claude-only-token `ProjectionWarning` now fires ONLY for **authored** hooks (unknown install root) or other unresolved `${CLAUDE_*}` tokens. A projected skill whose `SKILL.md` still carries the token cannot be rewritten (it is read as-is), so the projector emits a `ProjectionWarning` instead.
- **Command wrappers carry a marker line** (`dorkos:generated-command ...`) right after the YAML frontmatter. That marker is the sole ownership predicate for the uninstall sweep, so a hand-authored command is never deleted, even one sharing a wrapper directory. Claude Code owns a whole per-plugin dir (`.claude/commands/<pkg>/`): if that dir already holds authored (marker-less) content, the plugin's command projection surfaces as a conflict and nothing is written into it. The OpenCode dir (`.opencode/commands/`) is instead **shared and flat**, so the block is per-**file**: only a wrapper whose exact path is already occupied by an authored (marker-less) file is a conflict; the plugin's other wrappers still project alongside authored commands.
- **Plugin hooks merge, never overwrite.** `.claude/settings.local.json` is user-owned, so the engine touches only its own managed matcher groups and leaves every user hook and other settings key intact. Ownership is explicit: each managed group carries the `_dorkosHarness: "<pkg>"` sentinel key (Claude Code tolerates the unknown key and the tagged hook still fires, validated on CLI 2.1.197). Ownership is never inferred from the command string, so a plugin hook that does not mention its install path still re-syncs idempotently and sweeps on uninstall, and a user hook that mentions `.dork/plugins/` is never misclassified. A settings file that exists but cannot be parsed (corrupt, mid-write) aborts the merge as a conflict rather than being rewritten. See `apply/settings-hooks.ts`.
- **Plugin hooks need a person's yes before they project (DOR-522, DOR-1849).** A hook is a shell command a harness runs unattended, and installing a marketplace package asks nobody (`marketplace.install` is tier `act`). So the engine takes a per-package gate (`project(root, { allowPluginHooks })`, applied at PLAN time so it covers the generated `.codex/hooks.json` and friends as well as the Claude settings merge) and has no opinion of its own about who passes it. **Every trigger applies that gate through one seam**, `apps/server/src/services/harness/project-with-consent.ts`: it partitions each hook-declaring package into refused / approved / unasked — in that order, so a hand-edited config saying both withholds rather than installs — builds the plan with only the approved ones' hooks, applies it, and returns what it withheld and why. `apps/server/src/services/harness/__tests__/project-seam-guard.test.ts` keeps the engine's `project` out of every other module in `apps/server/src` and `packages/cli/src`, in every import form this repo writes (named, aliased, re-exported, `* as`, and the destructured `await import(...)` the CLI is written in) — held at all, it projects every hook on disk, and that is exactly how the CLI shipped a hole. It lives in the server package rather than `scripts/` so `turbo test` reaches it; the merge queue's full sweep is what makes it decisive, since a CLI-only PR does not affect `@dorkos/server` on the affected-only PR leg. Two triggers sit on the seam today: `runAutoProjection` raises the approval card and re-projects on a yes, and `dorkos harness sync --fix` prints a block per withheld package naming each command and the exact `--allow-hooks` re-run, exits 0 (`--strict` for a stop), and records an allow through the same function the card uses. The one exemption is `project-agent-workspace.ts`, which denies every package's hooks outright (HK-08) — stricter than consent, so the seam would loosen it.
- **Both answers are durable, and keyed the same way.** `harness.approvedHooks` and `harness.refusedHooks` hold `<packageName>@<digest>` over the resolved project path and every hook (command, event and matcher), so a package that moves an allowed command from `Stop` to `PreToolUse` asks again rather than inheriting consent — and a refusal expires the same way. Recording either side clears the other, so an entry is never in both — and because both leaves are `operator-only` precisely so a person can hand-edit them, the seam tests REFUSAL FIRST, so a file that somehow says two things withholds rather than installs. A `config.json` the CLI cannot read at all is a third state, kept distinct from "nothing decided": every package is withheld with the parse error named, and `--allow-hooks` refuses rather than opening the store, whose corrupt-recovery would replace every setting with defaults. `apps/server/src/services/harness/hook-consent.ts` owns the store and states the limits (notably: the digest binds the command text, not the content of a script it invokes). A refusal was in-memory only until `dorkos harness hooks --list` / `--revoke <package>` gave it a way back out; that is the whole reason it can now be written down. The store has two readers on purpose: the server's live config manager, and a direct `config.json` parse for `dorkos harness sync --check`, because opening a `conf` store creates the file and the directory around it and `--check` must never write (DOR-678).
- **A generated hooks file is owned by a sidecar, not by its path.** `.codex/hooks.json`, `.cursor/hooks.json` and `.github/hooks/copilot-hooks.json` are all paths their own vendors tell people to hand-write, so the engine claims one only when `<target>.dorkos-generated` sits beside it holding the sha256 of the exact bytes on disk (`apply/generated-ownership.ts`). Owned → rewritten when the content changes, untouched when it does not, swept with its sidecar when the plan stops generating it. Not owned — no sidecar, or a sidecar that no longer matches because somebody edited the file — → never written, never swept. A marker inside the file could not draw that line: it cannot tell a generated file from a generated file a person has since edited. The Codex file additionally carries the `description` key Codex documents, which reads as a comment and says a program wrote it.
- **A file the engine does not own is reported two different ways, and only one of them is a fault.** At a target the plan WANTS to generate it is a **conflict**: a projection was blocked, `applyPlan` returns it in `conflicts`, `checkPlan` in `blocked`, and both the CLI's `--fix` and `--check` exit 1 with the way out (move the hooks into `.claude/settings.json`, or delete the file). At a target the plan writes nothing to — the first auto-projection pass, which has no hook contributors by design, or a harness the manifest never enabled — it is **left alone**: `applyPlan` and `checkPlan` both return the path in `leftAlone`, the CLI names it under its own heading, and neither command exits non-zero. Nothing was blocked, so a person who keeps their own `.codex/hooks.json` never gets a standing failing command for it.
- **Ownership is the whole sweep guard; the manifest is not consulted.** A harness leaving `harnesses` means DorkOS stops projecting into it, so its generated file is swept rather than left behind still firing. The sidecar is what makes that safe: those bytes are provably the engine's, and nothing a person wrote is reachable either way. Nothing on the plan carries the enabled set any more — it had no reader once the guard went, and a field written and never read is a claim nobody checks.
- **Migration, for files written before sidecars existed** (in order): (1) the bytes on disk are already exactly what would be written now → adopt silently, writing only the sidecar; (2) `.codex/hooks.json` holding the engine's own pre-DOR-1842 bare event map — a top-level object whose every key is one of the ten Codex spellings the old generator could actually emit, each mapping to an array — with no sidecar ever written → rewrite it into the documented shape; (3) anything else → conflict. **Those ten are a frozen literal, never derived from `CANONICAL_TO_CODEXCLI_EVENT_NAMES`** (DOR-1847): rule 2 is a claim about what a PAST build wrote, so it must not track a map the present one extends. `SessionEnd` joined that map and a bare `SessionEnd` map is a file no DorkOS build has ever produced — deriving would have handed rule 2 a licence over somebody's file, and every later map addition would widen it the same way, silently. Cursor's and Copilot's legacy files cannot be told from hand-written ones (they were always in the vendor's own wrapper shape), so they take rule 3 and the conflict message says what to do.
- **Projections are gitignored machine-local ephemera.** Skill symlinks, the settings file, the three generated hooks files and their sidecars are covered by `EPHEMERAL_GITIGNORE_PATTERNS` (`sources/resolve-roots.ts`) mirrored in the repo `.gitignore`; the Claude wrapper directories are covered by a self-ignoring `.gitignore` the engine writes inside each `.claude/commands/<pkg>/` (a static rule would swallow authored `.claude/commands/<ns>/` dirs). The shared flat `.opencode/commands/` dir gets one engine-owned `.gitignore` that names **each generated wrapper filename explicitly** plus itself — never a `*` wildcard, which would hide authored commands. An authored `.opencode/commands/.gitignore` (marker-less) is treated as a conflict, never overwritten.

  **And the contract is checked, in the person's repo rather than in this one** (DOR-1851). For a year the pattern list had no consumer: it was declared, mirrored in this repo's `.gitignore` by hand, and nothing ever looked at anybody else's — so a fresh project came out of `--fix` with `.claude/skills/<pkg>__<skill>` untracked and nothing said. `apply/gitignore.ts` reads the finished plan and answers three questions. `missingGitignoreLines(repoRoot, plan)` returns the lines the ROOT `.gitignore` is missing for the paths this plan makes ephemeral: every installed/adopted target, the install directory they read, and the generated hooks files with their sidecars — whose provenance is `authored`, because the hooks come from `.claude/settings.json`, so a provenance-only rule would have missed all six. A path already covered by any line in the file contributes nothing (a repo that ignores `.claude/` is not told to add a narrower rule), and neither does one covered by a self-ignoring `.gitignore` the plan writes beside it. `appendGitignoreLines` adds them behind `--fix --write-gitignore`, under a single DorkOS heading it EXTENDS on a later run rather than stamping again (a narrowed sync followed by a full one is the ordinary case); without the flag both modes only NAME them, because `.gitignore` is a file people are particular about. `canonicalLayerIgnoredBy` answers AP-15 and returns the FILE — a gitignored `.agents/` is a real choice, but it means the links in `.claude/skills` still commit while the files they point at do not, and "stop ignoring it" is advice nobody can act on until they know whether the root file or `.agents/.gitignore` is doing it. **Every one of them is silent outside a git checkout.** The matcher walks the path the way git does — per component, last match wins, `!` un-ignores, nothing under an excluded directory can be re-included, and a `dir/` rule decides a component only when that component really is a DIRECTORY (git calls a symlink a file, and both `*__*` projection families are symlinks, so a repo whose rule is a `*__*` directory one has git tracking them) — because the alternatives got two common shapes backwards in the dangerous direction: with `.claude/*` and `!.claude/skills/` in a repo's file, git TRACKS `.claude/skills/pkg__skill` and a negation-blind matcher called it covered, so the one repo that needed the warning never got it. What stays small is the glob vocabulary (`*`, `**`, `?`, a trailing `/`, anchoring, the bare-name rule); `apply/__tests__/gitignore.test.ts` checks the whole thing against **real `git check-ignore`** on a real repo wherever git is on PATH — 22 shapes, each leaf staged as the file, directory or symlink it claims to be — and asserts that every declared pattern is a shape it understands. Property P7 (`__tests__/properties/p7-gitignore.property.test.ts`) is the standing claim: over generated repos with a random root `.gitignore`, every ephemeral target is covered by a declared pattern or a self-ignore, and the missing list is empty only when the repo already covers them.

- **Detection re-runs on every plan, and `--enable` is the one write path** (DOR-1851, ADR-0302 amendment). `scaffoldManifest` is write-if-absent, so the harness set was decided once and never revisited: a repo that grew a `.cursor/` after its manifest was written never enabled Cursor and nobody was told (TR-11). `engine.ts` now calls `detectHarnessFootprints` on every plan and `buildPlan` puts what it found that the manifest does not enable into `plan.notEnabled`; the CLI prints one line per harness and **changes no exit code**, because a harness somebody runs elsewhere is not drift. `AGENTS.md` is excluded from those signals on purpose — every DorkOS repo has one, so reading it as a Codex footprint would print an unclearable line on every sync of every repo; it stays a signal for the SCAFFOLD, where the question is asked once and a repo with an `AGENTS.md` and nothing else is a reasonable place to start Codex. `dorkos harness sync --fix --enable <id>` then adds the harness by **inserting one array element into the manifest text** (`scaffold/enable-harness.ts`) — never `JSON.parse` + `JSON.stringify`, which would reflow a hand-authored file's every line — verifies the result reparses to the same document plus that one harness, and re-plans in the same run, so one command both turns the harness on and projects to it. Two guards sit in front of that write. The file is validated with `parseHarnessManifest`, the SAME strict schema the engine loads with, so a manifest carrying a stale `sharedSkills` key is refused rather than edited and then rejected by the run that edited it. And a manifest with no `harnesses` key at all is valid — the schema defaults it to `['claude-code']`, and the notice fires for such a file — so the edit adds the whole key carrying the defaulted set PLUS the new harness; writing `["cursor"]` there would have turned Claude Code off on the way past. It refuses `--harness`, because a narrowed run would write the manifest and project nothing for what it had just enabled.
- **A projection whose source is gone is pruned — and only that.** `applyPlan(..., { sweepOrphans: true })` sweeps orphaned skill symlinks, Claude command wrappers (and their emptied dirs), OpenCode command wrappers and their aggregated `.gitignore` (marker-scoped, so authored files in the shared dir are never touched), managed settings hooks, and generated hooks files whose sidecar proves the engine wrote them (file and sidecar always together). Every one of those has an ownership predicate; nothing is swept by path alone. The skill sweep's keep-set is every `symlink` target in the plan whatever its provenance, not just the installed ones — an authored skill NAMED with a `__` projects as an authored symlink at a path that looks managed, and keeping only installed targets made one apply create that link and delete it again (DOR-1844). What the sweep may touch stays the narrow `__`-plus-symlink test; only what it keeps is wide. Auto-projection reruns project+apply after every install/uninstall (`apps/server/src/services/harness/auto-project.ts`).

  **Every one of the six sweeps has a `find*` half, and `--check` names exactly what a `--fix` removes** (DOR-1889). Each sweep is now a pure enumerator (`findInstalledOrphans`, `findOrphanedAuthoredLinks`, `findGeneratedOrphans`, `findGeneratedCommandOrphans`, `findOpencodeCommandOrphans`, `findSettingsHooksOrphan`) plus a deleter that calls it, and `checkPlan().orphans` is their union — sorted, de-duplicated, and **equal** to the `swept` list the next `applyPlan(..., { sweepOrphans: true })` returns. Equality, not containment: before this, `orphans` was the authored sweep alone, so a person who deleted a skill and uninstalled a plugin was warned about 1 path and watched 10 go, and a person who only uninstalled the plugin was told the tree was clean while a sync deleted 9 files. The six predicates are disjoint by construction — one path has one owner — so the de-duplication is a guarantee about the answer rather than a patch over overlap. One path in that list names a file that survives: `.claude/settings.local.json` keeps every user-owned key and loses only its managed hook groups, and it is listed because a sync CHANGES it without being asked. A stranded atomic-write temp in either command directory is listed too, because a `--fix` really does take it; a live one never is. **Every walk a `find*` makes is throw-safe** (`listDir`/`listDirEntries` in `apply/link-state.ts`): the two command directories are now scanned by `--check` as well as `--fix`, and `existsSync` says yes to a stray FILE at `.opencode/commands` and to a `.claude/commands` nobody may read — both of which threw `ENOTDIR`/`EACCES` straight out of the report the first time the finders were split out. A directory that cannot be listed is nothing to list, which is the same answer the skill dirs have always given.

  **An uninstalled plugin is not the only way a source disappears.** Remove or rename `.agents/skills/<x>` and `.claude/skills/<x>` is left pointing at nothing — no plan action names it, so for a long time nothing noticed and Claude Code was left with a link it cannot follow (SK-10). A second sweep takes those (`apply/authored-orphans.ts`), behind its own ownership predicate: a **symlink** (never a real directory), **dead**, whose link text resolves **into `.agents/skills/`** (a person's link to a vendored skill elsewhere is theirs), carrying **no `__`** (that shape is `sweepInstalledOrphans`' territory, and one path may only have one owner), and **not named by the current plan** (a link the plan still wants is drift for `applySymlink` to repair). One scanner answers for both `--check` and `--fix`, so the report and the sweep cannot disagree about what an orphan **is**. **A plan narrowed to one harness reports no orphans at all**, and the engine is what decides that: `--harness <id>` stamps `plan.narrowedTo`, every finder reads the plan as its keep-set, and a narrowed plan has never seen the other harnesses' live projections — so it would call them orphans and recommend a `--fix --harness` that `projectWithConsent` refuses to sweep. Naming a path the recommended command would not remove is a non-zero exit nobody can clear, so `checkPlan` answers with an empty list and every reader of `DriftResult` gets the rule for free (DOR-1889 moved it out of the CLI, where it had guarded one sweep of six). `applyPlan` refuses the writing half of the same pair outright — `sweepOrphans` on a narrowed plan throws, because that sweep deletes every OTHER harness's live projections — and `projectWithConsent` refuses it one layer up. Note the asymmetry `clean` inherits: for a narrowed plan a `true` means "nothing drifted or blocked for this harness" and says nothing about orphans.

  **This is the first sweep that can delete a git-TRACKED file, and that is deliberate.** `EPHEMERAL_GITIGNORE_PATTERNS` covers the namespaced installed links (`.claude/skills/*__*`), not the authored ones: in this repo `.claude/skills/<name>` links are committed (`git ls-files -s .claude/skills` shows mode `120000` for 18 of its 32 tracked entries; the other 14 are files inside the Claude-only skill dirs), so a teammate's clone gets them. When you delete the skill's source, the link is exactly as broken in the commit as it is on disk, and the sweep removes it — which shows up as a deletion in `git status`, to be committed alongside the source you removed. Nothing is lost that git does not still hold. The server runs the same sweep unattended after every marketplace install/uninstall (`services/harness/auto-project.ts`), so the deletion can appear without anybody typing a sync command; that is why the predicate refuses everything but a dead link into `.agents/skills/`.

- **A dead link is drift, never a crash.** `dorkos harness sync --check` is the command a person runs to be _told_ what is wrong with their tree, so it never throws for anything it finds there. A broken symlink is the shape that used to break that promise: `checkPlan` read straight through one at a `generate` target and died with ENOENT (AP-05), while `applyScaffold` counted one as a pointer already present and never repaired it (IN-05). A dead link is now an answer — drift at a `generate` or `scaffold` target, an orphan under `.claude/skills` — and `--fix` **replaces the link rather than following it**: a plain write follows a symlink and would put the file wherever the link pointed, so the atomic write renames over the directory entry instead (§8). What a path IS gets asked once, in `apply/link-state.ts`, and every caller says which answer it means.

- **Two shapes at a `generate` target are blocked, not drift** (`apply/generate-occupants.ts`). A **directory** there is somebody's content and no write can land on it anyway; before this rule `--check` called it drift and told the person to run a `--fix` that then died with EISDIR partway through the loop. A **live symlink** is the subtler one: reading and writing both succeed, somewhere that is not this path — a `.codex/hooks.json` linked to a file outside the repository had the pre-sidecar migration rewrite that outside file. Neither is ever written over, whoever owns what is at the far end, and both carry a reason naming the way out. Only a DEAD link is cleared and replaced, because nothing is there.

Global installs (`~/.dork/plugins`) are still SDK-injected by the claude-code runtime as a transitional exception until global-scope projection lands (DOR-174).

## 5. The vendor-facts table and the coverage walk

`packages/harness/src/vendor-facts/` answers a question the rest of the engine's tests do not: **would the harness actually load what we wrote?** Everything above this section is about writing files. A test that asserts a symlink exists at `.claude/skills/x` proves the engine did its job; it says nothing about whether Claude Code reads that path, keys the skill by its directory, or follows the link at all. Those are facts about someone else's product, and they change without telling us.

Two pieces:

- **`index.ts` — the facts.** One typed, dated, quoted record per harness: where it reads skills at project and user scope, how it walks for those paths (`ascend-to-repo-root`, `ascend-to-worktree`, `descend-recursive`, `fixed`), what it treats as a skill's identity, its name rules, what it does with duplicates and symlinks, and whether a new skill appears without a restart. It is §1.1 of [`meta/harness-sync-capabilities.md`](../meta/harness-sync-capabilities.md) as data — that document is the source, and it is where a new cell's reasoning belongs.
- **`coverage.ts` — the walk.** `harnessCoverage(harness, root, { cwd })` walks a real directory the way that harness's facts say it walks, and returns `{ discovered, uncertain }`. It imports the facts, `HarnessId` and the skills frontmatter parser, and nothing from `plan/` or `apply/` — it is the oracle those get measured against, so it must not be able to agree with them by construction.

**Every skill lands in exactly one of the two lists.** `discovered` is a confident claim: this harness's own documentation is enough to say the skill loads, and under this key. `uncertain` is the refusal to make one. So a consumer may read `discovered` alone and trust it — which is what the projection audits will do. A skill becomes uncertain when it was reached through a symlink and the harness does not document following them; when its identity rule is unknown and the directory and frontmatter names disagree; when the harness keys on the frontmatter name and there is none; when a documented name rule is broken and the consequence is unstated; or when the name must (or might have to) match the directory and cannot be checked. The one case that looks like an exception is not: where a skill is reachable twice under an unknown dedupe rule, the first copy reached is still a confident discovery and each _later_ copy is the uncertain entry.

**Every cell is documentation-derived.** `verified` is `'docs'` on all six rows: nothing here has been checked against a running `claude`, `codex`, `opencode`, `cursor-agent`, `gemini` or `copilot`. `plans/harness-sync-test-plan.md` calls that the H tier, and it does not exist yet. A test asserts the all-`'docs'` state on purpose, so the first real binary run has to change an assertion rather than quietly widen a claim.

**`unknown` is an answer, and the most valuable one in the file.** Where a vendor page said nothing — whether OpenCode follows symlinks, whether Gemini keys a skill by its directory or its frontmatter name, what Cursor does with a name that breaks its own charset rule — the cell says `unknown`, and `harnessCoverage()` reports the skill in `uncertain` instead of counting it or dropping it. That is what stops the table becoming a confident, wrong CI gate. An assertion reads "`discovered` has what we projected **and** `uncertain` is empty", so a gap fails loudly. **On a tree DorkOS has already projected into, expect `uncertain` NOT to be empty** — the projection is a symlink into `.claude/skills`, and Cursor, OpenCode and Copilot do not document whether they follow one, so this worktree reports 31 discovered and 18 uncertain for each of the three, every one of the 18 a symlink reason for a skill they also reach as a real directory under `.agents/skills`. The assertion for a projected tree is the weaker, still-honest one: `uncertain` is empty **or** holds only symlink-reason entries whose skill also appears in `discovered` by another path. Anything else is a real finding, and DOR-1847's false-native work leans on that shape. Filling an `unknown` in with a plausible guess is the single most damaging edit anyone can make here.

**To update a cell when a vendor changes:**

1. Fetch the vendor page again and read the sentence that states the behaviour.
2. Edit the cell, put that sentence in `source.quote`, and bump `source.fetchedAt` to the day you fetched it. **A per-row date is expected, not forbidden**: the rows start out sharing `VENDOR_FACTS_FETCHED_AT` because they were compiled in one pass, and a row carrying its own later literal is the signal that it alone was re-checked. Write the literal; do not move the shared constant to cover one row.
3. If the change is behavioural rather than editorial, update §1.1 of the capabilities contract in the same commit — the table and the contract are one claim in two places.
4. Run `pnpm vitest run packages/harness/src/vendor-facts`. Several facts are pinned by name (that Claude Code alone does not read `.agents/skills`; that every `onInvalidName` is still `unknown`), and a census pins every cell the walk branches on, so a real change reds a test and the red is the prompt to bring a fixture with it. Three values in the vocabulary have no row today — `dedupe: 'by-name'`, `onInvalidName: 'skip'` and `'warn-and-load'` — and the census is what keeps that visible instead of leaving an unexercised branch nobody notices.
5. A cell you verified by **running the harness** flips `verified` to `'binary'` — and then say so in the quote: which binary, which version, what you observed.

**What it is for.** `harnessCoverage()` is the measuring stick for the projection fixes it precedes. DOR-1847's is landed: `__tests__/properties/native-reachable.property.test.ts` (P9b) asserts that every `native` skill action names a source the harness's own read paths reach, in two tiers, because the vendors are two different amounts of clear. **Authored** skills take the strict shape above — in `discovered`, with any `uncertain` entry about them a symlink reason for a skill also discovered by its real path. **Installed** skills take reachability: a `<pkg>__<name>` directory breaks OpenCode's and Cursor's documented name rules twice over, so `uncertain` is the honest answer there (SK-09, SK-12) — what the tier forbids is the walk not reaching the skill at all, and every reason it is uncertain has to be one of the vendor's own documented unknowns. That second tier is what the unconditional `.agents/skills` link is measured by: revert the link and it reds with the harness and skill named, while a file-existence check (P9a) stays green, because the plugin's own directory existed the whole time. And eventually the H tier, which will replace `'docs'` cells with observed ones and is expected to contradict some of them. When it does, the disagreement is a finding about the engine, not a bug in the table — as long as the table said honestly where it got each number.

## 6. The source inventory and the honest-drop tables

§5 answers "would the harness find what we wrote?". This answers the question underneath it: **what is in this repository at all?**

`packages/harness/src/inventory/` walks a source tree once and records every artifact a person authored, by kind — skills in both authored roots, slash commands, hooks from BOTH Claude settings files and from skill frontmatter, subagent definitions, path-scoped rules, and the servers named in `.mcp.json`. It knows nothing about harnesses and decides nothing. `plan/source-artifacts.ts` is the half that decides: for each inventoried artifact and each enabled harness it emits a `native` (the harness reads that source where it sits) or a `drop` naming where that harness keeps the same kind.

Three rules govern edits here:

1. **Sources only, never the engine's own output.** A managed `<pkg>__<name>` symlink, a symlink under `.claude/skills`, a marker-bearing command wrapper and a `_dorkosHarness` hook group are all things DorkOS wrote. Inventorying one would make the completeness check demand that the plan account for a path the plan produced.
2. **Project scope only.** Nothing here reads a home directory. `~/.claude/settings.json` IS read now, and deliberately not from this package — see "Claude Code's own plugins" at the end of this section.
3. **Never a value from `.mcp.json`.** Server NAMES are recorded and nothing else. A real `env` block holds live API keys, and this list is printed by `dorkos harness sync`, passed around, and eventually served over an API.

**The reason tables are a second dated facts table**, and they follow §5's discipline without sharing its constant: `SOURCE_ARTIFACT_FACTS_FETCHED_AT` dates the subagent / rules / MCP cells, `VENDOR_FACTS_FETCHED_AT` dates the skills rows, and a partial re-fetch of one kind must not silently re-date the other. Each table is `satisfies Record<HarnessId, Placement>`, so a new harness id fails the typecheck in three places. Changing a reason means re-opening the vendor page, and a cell nobody can verify says so rather than naming a plausible path.

**Where §5 already has the answer, ask it — never restate it.** A skill kept in `.claude/skills` gets its placement from `skillsFactsFor(harness)`, not from a sentence here: Claude Code is not the only harness that reads that directory (OpenCode, Cursor and Copilot list it too), and a hand-written "only Claude Code reads it" would have been a fresh SK-05, contradicted by this repo's own table two directories away. The link case is the honest middle — a skill LINKED into `.claude/skills` is a confident `native` only for a harness that documents following symlinks, and for the rest a drop that names that silence, rather than a false yes or a false no.

**Nothing here is written.** Every line is a `native` or a `drop`, and `applyPlan` treats both as no-ops. When a projection is built for one of these kinds, its cell moves from `drop` to a real mechanism and the drop reason goes with it.

**The completeness check is what keeps this honest.** `__tests__/properties/plan-completeness.property.test.ts` (P6) asserts that for every inventoried artifact and every enabled harness, the plan says something about it. Note what it does NOT assert: that exactly one list names it. One source file can hold several artifacts with different fates — `.claude/settings.json` declaring both an event Codex maps and one it does not appears in `actions` and in `drops` for the same harness, and both lines are true. The real contradiction, a `native` and a `drop` for one source, is asserted directly instead. A drop that carries no `source` cannot be matched to the declaration it is about, so **every drop about an authored file names that file**, or it is silent to this check while looking reported.

**Adding a kind** means three edits and a red test in between: grow `ArtifactType` (`plan/types.ts`), teach `inventory/` to find it, and add its `satisfies Record<HarnessId, Placement>` table. P6 reds until the third lands.

**Three traps the first review of this code found, all of them one trap.** Each was a place where what a harness reads and what the walk looked at had quietly diverged, and each was invisible to P6 because the generator did not stage the shape:

1. **Recursion.** `.claude/rules` is discovered recursively, like `.claude/agents` and `.claude/commands`. A nested rule got zero lines under every harness, and `arbRepo()` seeded only flat names.
2. **Symlinked directories.** `Dirent.isDirectory()` is false for a link, so a linked-in folder of rules or subagents was neither a directory to descend into nor an `.md` file. The walk now `stat`s and descends, and keeps a visited-realpath set — before, a loop terminated only because nothing ever descended through one.
3. **Identity.** A subagent is keyed by its frontmatter `name`, never its path. Reporting a nested definition as `react/tanstack` named it something nobody can invoke.

The generator now stages a nested rule, a linked-in directory, a dead `.md` link and a person's own link into `.claude/skills`. When you add a kind, add its awkward shape to `arbRepo()` in the same commit — a property with no subject is a green that means nothing.

**P6 cannot catch a scanner gap, and adding shapes to the generator does not change that.** Its subject IS the inventory, so an artifact the walk never sees is not a subject and the property stays green: measured, with a deliberately non-recursive rules walk, P6 passes and only the unit test reds. The missing half is the property beside it — the inventory measured against what the generator knows it wrote, which is an oracle the walk cannot agree with by construction. That one reds on every gap above. Keep both: one asks "did the plan account for everything found?", the other "was everything written actually found?", and only the pair covers a walk.

**Sharing the rule ladder moves one class of bug and creates another.** P9c compares the plan against the walk, so it catches a DIVERGENCE — and it cannot, by construction, catch an OMISSION: a rule missing from `vendor-facts/skill-rules.ts` is missing from both answers at once, and they agree perfectly on the wrong thing. That is not hypothetical. Until `nameRequired` was added, a `SKILL.md` with no frontmatter `name` was "loads" for Copilot, whose own page says the key is required, and the walk said so too. The guard is `vendor-facts/__tests__/skill-rules.test.ts`, which drives the ladder with SYNTHETIC `SkillsFacts` — one case per rule — so it answers to the vendor pages rather than to the other half of the engine. It is also the only thing that reaches a cell value no vendor row uses (`onInvalidName: 'skip'`, `'warn-and-load'`); before it, deleting those branches red nothing at all.

A third, **P9c** in `native-reachable.property.test.ts`, closes the loop from the reader's side: for every `.claude/skills` skill and every enabled harness, the plan's native / drop / warning and `harnessCoverage`'s discovered / uncertain / neither must map onto each other three for three, and the test asserts all three outcomes actually occur so it cannot narrow to one branch. Its one carve-out is stated in the test rather than left silent: a skill present in both roots, where the plan answers about a blocked projection and the walk answers a dedupe question — two different subjects.

### Claude Code's own plugins, and why the read lives outside this package

A person who runs `/plugin install` in Claude Code gets a plugin only Claude Code can see. `dorkos harness sync` now says so, in a block headed **Installed in Claude Code only** (SRC-08, J-07, and the user half of HK-14).

**None of it is in `@dorkos/harness`, and that is the design rather than an accident.** Three module docs in `inventory/` forbid this package from reading a home directory by name, for the reason `inventory/hooks.ts` states: a source inventory of a repository that reached into somebody's home would report one machine's private hooks as if they were the project's. So the read is a server module, `apps/server/src/services/harness/claude-enabled-plugins.ts`, and the block is assembled in `packages/cli/src/harness-sync-command.ts` **beside** `formatDropList`'s output, never inside it.

Four things about that read are load-bearing:

- **Which root.** `$CLAUDE_CONFIG_DIR`, else `~/.claude` — `inheritedClaudeRoot()`, exported from the Hard Rule 3 carve-out `services/runtimes/claude-code/claude-config-dir.ts` rather than re-derived, because that carve-out is by filename. Never `resolveActiveClaudeRoot()`: its first rung answers which Claude account DorkOS runs and bills on, and this question is which Claude Code the person typed into. The root is printed on every run, because `$CLAUDE_CONFIG_DIR` is inherited and a run started inside an agent session can read a different root than the person's own terminal.
- **What is read.** Three documented keys — `enabledPlugins`, `extraKnownMarketplaces`, `hooks` — from `<claudeRoot>/settings.json` and the project's two settings files, merged per key under Claude Code's own precedence (local over project over user). Never `<claudeRoot>/plugins/`, which is a private versioned cache that has already changed format once (contract position D4). The hooks schema never names `command`, so no shell text a person wrote is bound to a value; the entries are counted and nothing else.
- **How it fails.** Into a record, never a throw, on the model of `inventory/read.ts`: absent is silent, unreadable is one two-line block, and the rest of the report is untouched. The reason names the key path and never the value, because Zod's own message quotes what it rejected and this is somebody's private file.
- **How a plugin is matched to a DorkOS package.** On the REPOSITORY, through `services/marketplace/lib/marketplace-repo-key.ts`, never on the marketplace's local name: Claude Code's `dorkos` and DorkOS's `dorkos-community` are one repository under two local names, and a name match misses it. The offer is a printed command into the install flow that already exists, at project scope, and it never installs anything by itself.

## 7. Windows, and clones that cannot make symlinks

A skill projection is a symlink, and a symlink is the one thing this engine writes that is not the same object on every machine. Two consequences, both now covered.

**On Windows a directory link is a junction, and a junction's target is absolute.** `symlinkType()` asks for `'junction'` for a directory source because that is the only directory link Windows creates without Developer Mode or admin rights. Node resolves the relative text against the link's parent before handing it to Windows, so `readlink` answers `C:\repo\.agents\skills\x` where the plan said `..\..\.agents\skills\x`. Comparing link TEXT there would call every junction drifted forever — `--check` could never go clean, and `--fix` would delete and recreate every link on every run. So Windows compares where the link **resolves** instead (`apply/symlink-occupants.ts`, `linkCheckFor`), asking `realpathSync.native` on both sides so the two answers agree about the drive letter's case, an 8.3 short name in a temp path, and the `\\?\` prefix. POSIX is unchanged: it compares the text, which is the property that makes a checkout portable (AP-06).

**A clone whose `core.symlinks` is off has a plain file at every link.** Git stores a symlink as a blob holding its target path; a checkout that cannot create links writes that blob out as a regular file. That is the Git for Windows default, and it is what a teammate's first clone looks like. Nothing is wrong with the repository, so `--check` and `--fix` both say so in one line — the file holds the link's own text, symlinks are off, here are the two ways out — instead of reporting drift the person can never clear (J-10). The same predicate answers for a real file or directory at a link target, and it names a difference of case when the volume does not tell `Foo` and `foo` apart (AP-16).

**Two more things a Windows runner turned up, and one of them is still open.** A projection on Windows is a junction, and **git sees a junction as a directory** — `git add` walks into it and commits the skill's files a second time, storing no symlink at all. So a link committed FROM a Windows checkout is not a link, and "committed authored symlinks resolve" holds only for links committed from macOS or Linux. That one is recorded in the contract and tracked as DOR-1883, not fixed. The other is fixed: a rewritten `${CLAUDE_PLUGIN_ROOT}` used to produce half of each spelling — `C:\Users\me\.dork\plugins\flow/hooks/x.mjs` — inside a shell command and inside a JSON string, because the install root came from `join()` and the text after the token came from the plugin. `pluginRootText` in `plan/installed-projector.ts` now spells the whole path with forward slashes on Windows, which node, PowerShell and bash all read the same way. POSIX output is byte-identical.

**Two things a person on Windows should expect.** If your account cannot create symlinks — Windows without Developer Mode, and not running as an administrator — the engine's own test suites do not degrade gracefully: they build their own links, so they fail. That is a missing privilege, not a broken engine, and the CI job's probe step is what tells the two apart. Separately, the forward-slash change above alters the exact command text DorkOS writes into a plugin's hooks, and the hook consent card is keyed on a digest of that text — so **the first sync after upgrading will ask once more about hooks you have already approved**. Approve them again and it settles.

**Both are exercised on a real runner.** `.github/workflows/harness-windows.yml` runs `packages/harness` and the CLI's `harness sync` suite on `windows-latest`, on pull requests (when the change can reach either package) and unconditionally in the merge queue. It is **advisory**: promoting it is a branch-protection change and needs no edit to the workflow, because `merge_group:` has been in its `on:` list since the day it landed. Its probe step prints what the runner's filesystem could actually do — file symlink, directory symlink, junction, the junction's readlink text, and what git did with one of this repo's own committed links — so a green run is never mistaken for coverage of a capability the runner did not have. Read that step before drawing a conclusion from a green check.

## 8. Concurrency — two syncs into one repo

Projections overlap in real use, and not rarely: the desktop app and a `pnpm dev` server can be pointed at one repo, `dorkos harness sync --fix` runs in a terminal beside a running app, and a marketplace install fires auto-projection while somebody's sync is halfway through. Three things hold, and one deliberately does not (contract AP-10, journey J-12, DOR-1854).

**1. No file is ever read half-written.** Every file the engine writes — scaffolded pointers, generated hooks files, their `.dorkos-generated` sidecars, command wrappers, the harness manifest, and the managed-hook merge into `.claude/settings.local.json` — goes through `writeFileAtomic` (`apply/atomic-write.ts`): a sibling temp file, then a rename over the target. A harness reading one of those paths mid-sync gets the whole old file or the whole new one, never an empty or spliced one. `apply/__tests__/atomic-write-guard.test.ts` holds the line: outside its own tests, no module under `packages/harness/src` may call `writeFileSync`, `writeFile`, `appendFileSync` or `createWriteStream` — only the helper does. The guard exists because a new write site added later is invisible until somebody happens to be reading that exact path at that exact millisecond.

**The temp file is untouchable while somebody is writing it.** That is a rule the engine has to keep against itself: a temp holds the whole content of the file it is about to become, marker included, and the two command directories (`.claude/commands/<pkg>/` and `.opencode/commands/`) are the only ones the engine enumerates by wildcard — so every ownership predicate in `apply.ts` used to look at another process's half-finished write and say "mine". The sweep deleted it and that writer's `rename` died with ENOENT out of the middle of `applyPlan` (6/6 rounds, two writers, a 60-command plugin). A vanished entry did the mirror-image damage: `readdirSync` lists it, the read a moment later finds nothing, and "unreadable" was being read as "somebody else's" — so the engine reported its OWN wrapper directory, all of it, as blocked. Both are closed: every scan asks `isAtomicTempName` first, and an entry that has gone is not foreign.

Leftovers are decided by **age**, not ownership, because ownership cannot tell a stranded temp from one created a microsecond ago. A temp younger than a minute is somebody's write and is never removed; an older one is debris the orphan sweep takes, but only in the two command directories. Everywhere else (`.codex/`, `.cursor/`, `.github/hooks/`, `.claude/`, the repo root) those paths are read by name and never scanned, so debris there is inert and left alone rather than swept — sweeping it would mean walking directories the engine has no other reason to walk. The minute is a **margin, not a guarantee**: a suspended writer, a stalled network mount, or a share whose server clock runs more than a minute behind can make a live temp look old, and then the sweep takes it and that writer's rename fails with ENOENT, leaving its plan half applied until the next sync finishes the job.

**Rename has one cost, and it lands on watchers.** Replacing the directory entry means a watcher holding the old inode stops hearing about the path: measured on macOS, `fs.watch(<file>)` saw 0 events across three atomic replaces while `fs.watch(<dir>)` saw every one. A missed notification is recoverable on the next read and half a config file is not, so the trade stands — but anything DorkOS builds that watches these paths must watch **directories, not files**, or it goes deaf the first time the engine rewrites what it is watching. That is a hard requirement for the `.agents/skills` watcher (DOR-1850).

The one exception is a **repaired symlink**, which is still removed and recreated. It happens only when the link text is already wrong (a skill whose source moved), so a reader in that window would otherwise have followed a link to the wrong place, and the next lookup finds the repaired link. Making it atomic means renaming a junction on Windows, and there is no evidence for that trade yet.

That same code path used to take a concurrent apply DOWN, which is worth knowing rather than only fixing: `applySymlink` checked that the target was free and then created the link, so the second writer's `symlinkSync` threw EEXIST out of the middle of `applyPlan` — a `--fix` that exited 1 for a reason nobody could act on. There is no atomic create-or-adopt for a link, so it now looks again instead: an EEXIST means somebody put something there, and what they put decides the outcome exactly as it would have a moment earlier. Both writers then report the link applied, which is true.

**2. Two projections into one repo in ONE process take turns.** `withProjectLock(projectPath, fn)` (`apps/server/src/services/harness/project-with-consent.ts`) is a promise chain per repository, keyed by realpath. `runAutoProjection` runs its whole body under it — first pass, the wait for a person to answer a hooks card, second pass — so a second install cannot project into a tree the first has half-approved. Different repositories never wait on each other, a turn that throws releases like one that succeeds, and an idle repository holds no entry. It is **not re-entrant**: asking for a repository the current async context already holds rejects with the path in the message rather than waiting for itself for ever. And a turn can be **long** — it is held across an approval card, which a person has up to two hours to answer — so everything else projecting into that one repository waits that long. Accepted for v1: releasing between the two passes would reopen the interleaving the lock exists to close. Any new trigger (the `.agents/skills` watcher, DOR-1850) should take the same lock, and should coalesce its own events rather than queueing one turn per file event.

**3. Across processes the end state still converges.** The engine's output is deterministic: two applies of the same plan write identical bytes, and where a plan lands does not depend on the order its actions land in (`__tests__/properties/apply-order.property.test.ts`). So whichever writer renames last leaves the tree one sequential sync would have left. `__tests__/journeys/j12-two-writers.test.ts` measures it with two real child processes.

**What is NOT guaranteed: a lock across processes.** Nothing takes a lock file, and that is a decision rather than an omission — a lock file needs a stale-lock story (which pid, on which host, after which crash) and the CLI half runs offline with nobody to ask. The residual, stated plainly: two processes applying **different** plans to one repo in the same instant can interleave a generated hooks file's two writes — the file, then its sidecar — so the sidecar ends up describing the other process's bytes. The ownership rule then reads that pair as a file somebody edited by hand and reports a conflict naming the way out (DOR-1842), which is the safe answer and a wrong one. It needs both processes to write different bytes within microseconds of each other; the way out is the same as for a real hand edit — delete the file and re-run.

A read-modify-write target behaves the way read-modify-write always does: `.claude/settings.local.json` keeps whichever writer merged last, complete and parseable either way.

## 9. Journeys and the census

Two test shapes exist only for this engine, and both are easy to weaken by accident.

**A journey stages a whole repository, runs one real projection, and asserts the EXACT diff.** Not a superset — the whole `{ added, changed, removed }`, so a file that appears one step too early or a sweep that reaches one path too far is a red rather than a side effect nobody looked at. That exactness is the point: HK-11 was a sweep deleting a person's `.codex/hooks.json`, and every test in the suite was green because none of them looked at what ELSE the run touched.

Stage with `stageRepo` from `@dorkos/harness/journeys` (`packages/harness/src/__tests__/journeys/stage-repo.ts`), one object per harness plus the canonical layer:

```ts
const repo = stageRepo({
  claude: { skills: ['review'], commands: ['deploy'], settingsHooks: { Stop: [/* … */] } },
  plugins: [{ name: 'flow', scope: 'project', skills: ['capture'], hooks: {/* … */} }],
  manifest: { harnesses: ['claude-code', 'codex'] },
  git: true, // only when the journey asks git a question — `.gitignore`, a clone
});
const before = snapshotTree(repo.root);
// …run the journey's steps…
expect(diffSnapshots(before, snapshotTree(repo.root))).toEqual({
  added: [/* … */],
  changed: [],
  removed: [],
});
```

Rules a journey keeps:

- **One file per journey**, named `jNN-<slug>.test.ts`, with `describe('J-NN — <title>')` and every `it` titled with the contract rows it pins (`it('J-03, IN-03: …')`).
- **Engine-only journeys** live in `packages/harness/src/__tests__/journeys/`; ones that need the seam — the consent card, the install trigger, the unattended boot pass — live in `apps/server/src/services/harness/__tests__/journeys/` and go through `runAutoProjection`, `projectWithConsent` or `projectAgentWorkspace`. No journey may APPLY through a bare `project()` — that is the door with no consent gate, and a journey that walks through it is testing a path no trigger takes. PLANNING with it is fine and several journeys do: `project()` is how you read the plan a seam is about to consent to, and `j04` uses it that way beside `runAutoProjection`. `project-seam-guard.test.ts` enforces the same line for production code, where it is absolute; test files are exempt there precisely because a suite pinning the ENGINE has to reach the engine.
- **Assert what the tree holds before the run**, not just after. A diff against an empty fixture is a statement about nothing.
- **Where the engine is wrong, pin what it does today** and say in the test why, naming the row. A suite that ships red records nothing; a pinned silence goes red the day somebody fixes it, which is exactly when its replacement should be written.

**The census keeps `meta/harness-sync-capabilities.md` honest.** `packages/harness/src/__tests__/capabilities-census.test.ts` parses that document's tables and every test title under the four roots that test this engine, and fails when they disagree. When it goes red:

- _"no test title carries its id"_ — put the row's ID at the front of the title of the test that really covers it, or correct the Coverage cell. The cell is a claim; the census is what makes it one.
- _"names an ID the document does not define"_ — a row was renamed or removed, or the title has a typo.
- _"is marked broken and has a test"_ — somebody fixed a row and left the document saying it does not work. Flip the State cell and cite the test; if the test PINS the gap instead of closing it, add the row to `PINNED_GAPS` with the reason.
- _"is `built` with no coverage"_ — something shipped without a test.

Three things do NOT count as coverage, so none of them can silence a row: an id inside a comment (the census blanks comments with the repo's shared `codeOnly` stripper before it reads a title), a case the runner never runs (`it.skip`, `it.todo`, `it.only`, an `it.each([])`), and an id mentioned anywhere but the front of the title. Write it as a prefix — `it('SK-04: …')`, or `it('J-09, AP-05: …')` for a case that pins two rows.

**Editing the document alone runs nothing.** `pnpm verify` is affected-only and `meta/` belongs to no package, so after a contract edit run `pnpm vitest run packages/harness/src/__tests__/capabilities-census.test.ts` by hand. What catches it otherwise is the merge queue's full monorepo sweep — and only because `turbo.json` carries a `"@dorkos/harness#test"` override whose `inputs` name the contract and the foreign test paths. Without it the task hash does not move when the document changes, and the queue replays a cached green. `turbo-census-inputs.test.ts` guards the override, including the `$TURBO_DEFAULT$` entry and the restated `dependsOn`/`cache` — a package-scoped override REPLACES the base task rather than merging with it.

## 10. Triggers — what starts a projection

Five things call the engine, and the differences between them are the whole design. Each one answers three questions differently: does it **sweep**, does it **ask** about a package's hooks, and does it **scaffold** a harness manifest for a project that has none.

| Trigger                              | When                                                                         | Sweeps? | Asks? | Scaffolds? | Where                                         |
| ------------------------------------ | ---------------------------------------------------------------------------- | ------- | ----- | ---------- | --------------------------------------------- |
| **Marketplace install/uninstall**    | a package is installed or removed at project scope                           | yes     | yes   | yes        | `services/harness/auto-project.ts`            |
| **Boot**                             | server start, for every agent workspace DorkOS owns                          | no      | no    | yes        | `services/harness/project-agent-workspace.ts` |
| **`.agents/skills` watcher + sweep** | a skill appears, changes or goes away; re-armed every 1s; compared every 10s | no      | no    | **no**     | `services/harness/skills-watcher.ts`          |
| **Turn end**                         | a turn finishes and the project's skills look different                      | no      | no    | **no**     | `services/harness/skills-watcher.ts`          |
| **`dorkos harness sync --fix`**      | a person runs it                                                             | yes     | no\*  | yes        | `packages/cli/src/harness-sync-command.ts`    |

\* The CLI cannot raise a card, so it **withholds** an unapproved package's hooks and prints each command it did not install; `--allow-hooks <pkg>` records the same decision a card would.

Every one of them goes through `projectWithConsent` (§8 and `project-with-consent.ts`), which is the only module allowed to hold the engine's `project()` — with one exemption, and it is granted because it is STRICTER than consent rather than looser: the boot pass denies every installed package's hooks outright (`project-agent-workspace.ts`, contract HK-08), which the seam cannot express because its whole job is to honour an approval. `__tests__/project-seam-guard.test.ts` reads the source of both trees, fails on any other module that imports `project()` under any of six spellings, and pins that exemption to the reason it was given.

### Why the watcher does not sweep, ask or scaffold

- **No sweep.** `sweepOrphans` runs five sweeps that delete files, on a tree an agent may be halfway through writing. At file-event frequency that inherits HK-11's blast radius. The visible cost: deleting a skill leaves a dead link in `.claude/skills/`. `dorkos harness sync --check` names it as an orphan and the next `--fix` prunes it.
- **No asking.** A hooks approval card raised by a file change is a card at the wrong moment, and people learn to dismiss those. Unapproved hooks stay unapproved and are counted in the log line; the install path asks, and `--check` reports.
- **No scaffolding.** `project()` reads `.agents/harness.manifest.json` and throws without one, so a project that has never synced is skipped with a debug line rather than having a manifest written into it because a file changed. That is the property worth remembering: **the unattended triggers only ever write into a project that is already set up for Harness Sync.**
- **And nothing outside the boundary.** A projection writes real files, and the directories these two triggers are handed are not checked inputs: `DEFAULT_CWD` is an environment variable, and a session's working directory comes from a runtime binding that `routes/tasks.ts` can set with no boundary call at all. Every root is therefore judged twice — once before it is watched, and once in `projectRoot`, the single point every trigger's write passes through. `validateBoundaryOrDorkHome`, not `validateBoundary`, so the agent homes under `<dorkHome>/agents/*` stay reachable in a `DORKOS_BOUNDARY`-scoped deployment.

### The watcher is not reliable on its own, and here is exactly why

Three holes, measured rather than assumed, and none of them is a steady-state loss rate:

1. **A deaf root — 100%, and permanent.** chokidar cannot watch a path that does not exist. Pointed at an absent `.agents/skills` it silently watches the nearest existing ancestor instead, emits a single raw `rename` when the directory is created, and never watches the directory itself — `getWatched()` still holds no entry for it ten seconds later. A project that has never had a skill would therefore never notice its first one, for the life of the process.
2. **The moments after a watch opens — 13-40%.** A file written immediately after chokidar reports `ready` is dropped that often. The same watcher given 100 ms to settle first missed **0 of 40**, and a long-lived one missed **0 of 40** over the same writes. So this is a startup artefact, not an ongoing loss: a server's watchers live for hours and are past the window before anything happens.
3. **A watch that has died — 100%, silently.** Kernel watch descriptors are shared and finite, and this repo is routinely several agents plus the operator's own two servers on one machine. Measured here: a twenty-run test loop exhausted them and `fs.watch` began throwing `EMFILE`, after which the watch reports nothing at all. Nothing in the engine can prevent that. It is also why no test in this suite asserts an outcome with the comparison switched off — that would be asserting a guarantee the system explicitly does not make.

An earlier version of this guide read the second measurement as a ~22% steady-state loss. That was wrong, and the correction matters: it changes the fix from "poll everything" to "settle at startup, and come back for the deaf root".

So there are three parts. The watch is the fast path. A **1-second re-arm** opens a real watch on any root whose `.agents/skills` has appeared since the last look — one `existsSync` per unwatched root, and the whole latency of a project's first skill. Measured against the built CLI on a project whose `.agents/skills` did not exist at boot: **432 ms** from the file landing to the link existing, against the ~9.8 s the comparison alone would have cost; the second skill, with the watch now armed, took 350 ms. And a **10-second comparison** covers everything else: it `readdir`s each root's `.agents/skills` and compares the entries' modification times against the shape the last projection planned from. Entries rather than the directory itself, because a `SKILL.md` written into a directory that already existed does not move the parent's mtime.

Cost: one `readdir` plus one `lstat` per skill per root per tick — measured at 201 syscalls and 0.49 ms for a root holding 200 skills, about 0.005% of one core. `usePolling` would cover both holes too (0/20 missed) and was refused because it pays a comparable cost against every watched _file_ on a much shorter timer, for ever.

Two rules about that recorded shape, both of which were bugs first:

- **It is committed only when a projection succeeds.** Written down at the moment a change is _noticed_, a projection that then throws has already retired the change, and nothing ever retries it.
- **It is the shape the projection PLANNED from**, snapshotted before the engine runs. Snapshotted afterwards, a skill an agent writes _during_ the projection is recorded as seen while no plan ever included it.

The engine's own `<pkg>__<name>` links are excluded from the shape by the same predicate the event filter uses — they are this trigger's output, not its input.

All three holes sat under `services/tasks/task-file-watcher.ts` too, and DOR-1908 reproduced every one of them there: the absent root was never discovered (no events at all, `getWatched()` empty ten seconds after the `mkdir`), a schedule written straight after `ready` was lost 3 times in 40 against 0 in 40 with the settle, and 80 of 80 trial watches on this machine raised `EMFILE` and then reported nothing. The scheduler now answers them in the same three shapes, with one difference worth knowing about: its watch arms with `ignoreInitial: true` and a **catch-up scan** after the settle, because it has to build a whole row set rather than react to a change, and a scan reads a root the same way its reconciler does. `TaskFileWatcher` reports which roots have no live watch, and `TaskReconciler` covers exactly those every ten seconds instead of every five minutes.

### Two more things the watcher has to get right

- **Directories, never files.** A rename-replace swaps the directory entry, so a watcher holding a file's inode goes deaf (§8). Everything here watches directories.
- **Its own output must not re-trigger it.** The engine writes an installed package's skills into `.agents/skills/<pkg>__<name>`, inside the watched directory. The exclusion is the engine's own predicate for a managed projection (`scan/scanner.ts`): the `__` marker **and** a symlink on disk. A real directory somebody named `my__helper` is authored content and still triggers (DOR-1844).

### The Claude Code restart caveat

Claude Code watches its skill directories, so a skill linked into an existing `.claude/skills/` shows up in a running session. A directory that **did not exist when the session started** is not being watched, and the vendor says to restart: _"If you create a top-level skills directory that didn't exist when the session started, restart Claude Code so it can watch the new directory"_ ([Skills — Live change detection](https://code.claude.com/docs/en/skills#live-change-detection), read 2026-09-08). So both `dorkos harness sync --fix` and the watcher say so — and only in the case the vendor documents, once per project, because a line printed on every sync is a line people stop reading. The claim is read out of `vendor-facts/index.ts` rather than written at the call site, so it carries its page and its date.

### Switching it off

`harness.autoSync` gates the install trigger, the watcher, the sweep and the turn-end re-projection alike. Off means no watcher is opened at all and nothing projects unprompted; `dorkos harness sync` still works.

## 11. The manifest, key by key

`.agents/harness.manifest.json` is the engine's only hand-authored input. It is scaffolded when a repo has none and never rewritten afterwards (ADR-302, and see [ADR-0302's DOR-1851 amendment](../decisions/0302-instructions-scaffolded-not-generated.md) for the one exception, `--enable`). Three keys, and every one of them is read:

| Key                | What it decides                                                                                                                               |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `harnesses`        | The enabled projection targets. Defaults to `["claude-code"]`. `dorkos harness sync --fix --enable <id>` is the only thing that ever adds one |
| `claudeOnlySkills` | Skills deliberately kept out of `.agents/skills`, each with the path it really lives at and why. The manifest is the only evidence they exist |
| `hookPolicies`     | One entry per harness: `{ tool, projection: 'native' \| 'generate' \| 'none', configPath?, status?, notes? }`                                 |

Everything else the engine needs it derives — the scanner reconstructs the skills from `.agents/skills/*`, so the schema is `.strict()` and a stale, derivable `sharedSkills` array is rejected rather than silently accepted.

**`hookPolicies`, and the rule it rests on.** A policy governs what the ENGINE writes, never what a vendor reads. Each harness has exactly one hooks mechanism: Claude Code reads `.claude/settings.json` itself (`native`), Codex, Cursor and Copilot get a file the engine writes (`generate`), OpenCode and Gemini have nowhere to write at all (`none`). So:

- **No entry for a harness is the default**, and it is what every existing manifest gets: nothing changes.
- **An entry naming that harness's own mechanism** changes nothing either.
- **`none` or `native` on a `generate` harness** stops the file being written, and each contributing hook source becomes a drop naming the manifest. `native` additionally says what that harness really reads, cited from `vendor-facts` when there is a dated cell for it.
- **`none` on Claude Code** stops the one thing the engine writes there — the installed-plugin merge into `.claude/settings.local.json` — and drops each package by name. The `native` line for `.claude/settings.json` stays, because Claude Code reads that file whatever a manifest says, and printing "hooks are not projected to Claude Code" over a file Claude Code is reading would be false.
- **A policy asking for a mechanism the harness does not have** cannot be granted, so it earns a plan warning naming the key rather than a silent no-op.

Two surfaces read the policy back rather than restating it, and both have to. `dorkos harness sync --fix --allow-hooks <pkg>` **refuses** when every harness that could receive that package's hooks is suppressed, and records nothing: consent is stored per package and outlives the manifest, so a yes taken here would install itself unprompted the day the `hookPolicies` line went (`pluginHookReach`). When only some are suppressed it records, and names the ones that will not get them. And the "Left alone" advice — put these hooks in `.claude/settings.json` and DorkOS will carry them — is withheld for a harness under a `none` or `native` policy, where moving them would change nothing.

Honouring a `none` that used to be ignored turns a previously generated hooks file into an orphan. `--fix` sweeps it, and only it — the `.dorkos-generated` sidecar is the whole guard, so a file somebody hand-wrote at the same path is left alone (the ownership rules in `apply/generated-targets.ts`). **`--check` says so first** (DOR-1889): generated-file orphans are not in the plan, so `checkPlan` finds them the way it finds a dead skill link, and a `--check` between flipping the policy and running `--fix` names `.cursor/hooks.json` and its `.dorkos-generated` sidecar under "Orphaned projections", says a `--fix` removes them, and exits non-zero — instead of reporting a clean tree over a live hooks file.

**The four retired keys.** `skillWrappers`, `commandMappings`, `instructionProjections` and `skillBundles` are **accepted and ignored** (DOR-1858). Nothing ever read them, and the engine has its own source for everything they described: plugin command wrappers, `plan/command-formats.ts`, the scaffolded instruction pointers of ADR-302, and the scanner instead of a bundle list. They stay in the schema so an existing manifest still parses — `.strict()` would otherwise reject the file, and `--enable` validates with the same schema before it writes a byte.

**There is no config migration**, and there is not meant to be: the manifest is a per-repo file the engine does not rewrite, not `~/.dork/config.json`. `dorkos harness sync` names each retired key it finds — one line, `--check` and `--fix` alike — and that line IS the migration notice. It sits beside the other thing the report says about the manifest rather than about a projection: a `hookPolicies` entry naming a harness the manifest does not enable, or a `tool` that is not a harness at all. Both are notices; neither ever changes an exit code (`manifest/notices.ts`).

## 12. The status model

The engine answers per harness, and every surface that draws a screen needs the same answer arranged the other way round: per FILE, with one column for each agent tool. That arrangement is [`apps/server/src/services/harness/status.ts`](../apps/server/src/services/harness/status.ts) — `buildHarnessStatus()`, a plain read-only function over an options bag, so the CLI can pass the consent copy it reads off disk instead of opening the config store.

It lives in the server rather than in `@dorkos/harness` because two of its states need the hook-consent record, and the engine has no approval primitive and no config store — dragging both in for one call site would be an architectural regression. It builds its plan through `planWithConsent`, never through the engine's bare `project()`, which is the seam the consent guard holds.

Each **row** is one agent file, keyed by `(artifact, source, name)`. All three components are load-bearing: two settings files both contribute a hook group named `hooks`, two MCP servers share one `.mcp.json`, and a skill and a hook declared in that skill's own frontmatter share a source. Each **cell** is that file paired with one enabled harness.

The derivation runs top to bottom and **the first match wins**:

1. after a write, the action is in `applyPlan().conflicts` → `conflict`
2. on a read, the action is in `checkPlan().blocked` → `conflict`
3. the cell is a hook from a package whose commands nobody has allowed → `pending-approval`
4. the action is in `checkPlan().drifted` → `drifted`
5. the action is in `plan.drops` → `dropped`
6. the action is in `plan.actions` with `kind: 'native'` → `native`
7. the action is in `plan.actions` with any other kind → `projected`
8. nothing above names the cell and a `ProjectionWarning` does → `warned`

`conflict` outranks `drifted` because "re-run and it fixes itself" and "re-running will never fix this" mean opposite things to a person. A warning that lands on a cell some other row already decided rides it as `warnings[]` instead of replacing it.

Three rules sit beside the ladder. **A warning attaches, it does not fork a row**: it joins the row sharing its `(artifact, source)`, choosing by `name` when more than one does, and becomes its own row only when it matches none — which is why a warning that names no source is an engine bug, not a second row about one file. **An entry that is not about a harness this project runs is project-level** — never a cell, never dropped. `projectLevel[]` therefore holds four kinds. Three come from the plan: `harnessAgnostic`, the declared one (`drop`); a warning naming a harness the manifest does not enable, which reaches no column and so has nowhere else honest to go (`warning`); and an action for such a harness whose kind WRITES a file (`write`). `source` absence is not the discriminator for any of them, because the unreadable-hook warning carries one. The fourth, `notice`, comes from no plan at all: it is `manifestNotices(manifest)` — a retired manifest key, or a hook policy naming a tool this manifest does not enable (DOR-1906) — read the moment the manifest parses, and carried verbatim, so `dorkos harness sync` and the page say one thing about one file. Its `artifact` is `manifest`, the one artifact kind with no counterpart in the engine's `ArtifactType`, and its `name` is the manifest path rather than the key or tool the line is about: `manifestNotices` returns sentences, and recovering the subject from one would be a second derivation of something the engine already decided. **`adoptable` is row-level**, read straight off the inventory: a real `.claude/skills` directory that is not also in `.agents/skills` and is not named in `manifest.claudeOnlySkills`.

**Placeholder harnesses are the trap under all of this.** Several emitters must name a harness for an answer that is about none — `HarnessId` has no "DorkOS" member — and each documents its choice as arbitrary. Unflagged, a placeholder is read as an answer: a project running OpenCode alone was told its unparseable `.mcp.json` was a Claude Code problem, and `dorkos harness sync --harness opencode` hid the loss entirely. `harnessAgnostic` (DOR-1849) is the flag that says "this id is a placeholder"; set it whenever you hard-code one, and give the entry a `source` so it can still be matched to the artifact it concerns — a sourceless warning matches no row and is reported twice about one file.

The report has **two** agnostic headings, because one was a lie about half of them (`report/drop-list.ts`). `plugin layers:` is for an installed package — an entry whose source is under `.dork/plugins/`, or a sourceless `plugin` artifact. `this project:` is for the person's own tree, which is where the read-time losses live. Neither is ever hidden by `--harness <id>`.

**The trap has an action half too, and it is not closed in the engine.** The unconditional `.agents/skills` link exists for the directory rather than for one reader, so it is attributed to Codex whether or not Codex is enabled — and a Claude-Code-only project therefore has a file a sync WILL write that belongs to no column. The status model files those under `projectLevel[]` as `kind: 'write'`, carrying the target, so the preview names every path a click touches in both directions. A sweep preview that omits a file the click creates is the same hole as one that omits a file the click deletes.

**A wrong chip is a plan bug.** Every sentence the model shows is the plan's own `reason` string, unchanged, so the fix goes into the projector and both the terminal and the screen get it at once. For the same reason `harnessCoverage()` is not called here: it is the oracle a projection is measured against, and running it in the read path would put a second, independent model of six vendors' behaviour on a screen where it could disagree with the first.

`sweepPreview` is `checkPlan().orphans` — every path a sync would delete, equal to the next `swept` and never a subset of it — and `clean` is false whenever anything drifted, anything is blocked, **or** anything would be swept. A tree whose only fault is orphans is not clean, and reading `clean` without the orphans is what once let a "nothing to do" screen sit over a click that removed nine files.

**The client reads it through one slice, [`apps/client/src/layers/entities/harness/`](../apps/client/src/layers/entities/harness/index.ts)** — the chip vocabulary, the skill rows, the "Not shared with `<harness>`" and "Project-level notices" panels, and the two read hooks, all reached through that one barrel. `useHarnessStatus` fills the cache; `useHarnessStatusCached` only reads it, so the profile row's number never costs three filesystem walks on a page that did not ask for it.

**The one surface that draws it is the agent profile's Skills page** ([`apps/client/src/layers/features/profile/ui/pages/SkillsPage.tsx`](../apps/client/src/layers/features/profile/ui/pages/SkillsPage.tsx), `?profilePage=skills`): the not-enabled notice, the skill rows, the per-tool panels, the project-level panel, and the marketplace link at the foot, in that order. It replaced a list of installed marketplace skill-packs that told a person with thirty-one skills they had none, and the profile's Skills row now reads `counts.skills` off the same cache entry rather than counting packages. Every state the page can draw is in the Dev Playground under `/dev/features` ("Skill rows", "Agent file panels", "Skills page states"), built from the same fixtures the tests use.

**The route is `GET /api/harness/status?projectPath=…` ([`apps/server/src/routes/harness.ts`](../apps/server/src/routes/harness.ts)), and it never writes** — no scaffold, no manifest edit, no settings store opened (DOR-678, contract AP-03), pinned by a whole-tree snapshot taken before and after the call. It uses `validateBoundaryOrDorkHome`, because every DorkOS-managed agent lives at `{dorkHome}/agents/<slug>` and the narrow validator would 403 the surface this is built for; the response carries names, paths and reasons and never file bytes, which is the listing side of `boundary.ts`'s own line. Three of the four states reach an HTTP caller — `ready`, `not-set-up` (a `200`, because a project with no manifest is a state the page draws) and `unreadable`; `unavailable` belongs to a build with no harness service and is the in-process transport's answer. The one thing the model cannot decide, it hands to the route: a `projectPath` that leads nowhere reads `ENOENT` exactly as an empty project does, and the boundary validator does not settle it either — it canonicalizes a not-yet-existing path through its deepest existing ancestor and RETURNS it. One `stat` separates them, `404` for absent and `400` for something that is not a directory, the same two answers `GET /api/directory` already gives.
