# Claude account UI: see which account a session spends, and move work off a spent one

**Status:** Specified. The visual design is the operator's (visual companion, 2026-09-26; `04-design-decisions.md`), with the banner placement, its states and the runtime rules decided by the orchestrator on the operator's behalf. Technical choices are made under the autonomy grant and logged in §15. The questions the decided designs left open are in §14; the operator resolved Q0-Q21 on 2026-09-27, and the orchestrator resolved Q22-Q23 the same day.

**Scope:** the DorkOS client (core UI), two small server additions the UI needs (§7), and the Flow extension that ships inside the flow plugin in `dork-labs/marketplace` (§8). Everything the server decides about limits, waiting, moving work and the advisor is S4's (D9, X3); this spec renders it.

## 1. Overview

S4 teaches the server about accounts: a color per account, usage per account for every runtime, a `limit` on a session that hit a hard limit with a server-computed `state` and `plan`, continue and wait endpoints, an account advisor the Flow extension registers, and the tracker item a flow run serves. This spec shows all of it:

- **Where you work** (decision 1, option C): a status-bar account chip with a color dot, the name and two tiny usage bars; a popover with each window, reset times, the tracker item and "Continue on another account →"; a color dot on each sidebar session row; a name badge in the session header. **Only when the session's runtime supports several accounts (`supportsAccounts`, Claude Code today) and that runtime has 2 or more registered accounts.**
- **Settings** (decision 2, option A): Settings → Runtimes shows usage bars for any runtime with usage data, even with one account; with 2+ Claude accounts each row also shows its color, and a one-line pointer leads to a **Flow** tab. The Flow tab (added by the Flow extension) sets each account's role, the main account's reserve, repo scopes, the handoff mode and cross-runtime fallback.
- **When usage runs out** (decision 3, option A): a banner above the message box, for any runtime, that walks through the states S4 emits and collapses into a one-line transcript marker when resolved; and the "Continue on another account" picker.

## 3. Goals and non-goals

**Goals**

- A person with 2+ Claude accounts can tell, without opening anything, which account every Claude Code session spends and how close each is to a limit.
- Near a limit and out of usage are said in words, never by color alone.
- When any runtime runs out, the person sees why, what they can do, and what happened afterwards, in the same place.
- One click moves the work to another account in the same folder.
- The operator sets how flow spends each account in Settings → Flow, and the flow CLI reads the same file.
- One account: no account identity UI (chip, dots, badge, color, picker).
- The status bar's usage and context numbers are there from the moment a session opens, for every runtime, and never older than they say.

**Non-goals**

- Any server behavior S4 specifies (limits, plans, timers, carry-over, the default summary, ranking, the advisor contract).
- Automatic handoff logic, ranking or checkpoints (flow and S4). This UI renders their results.
- A probe button, an Accounts/Fleet page, or a usage history view.
- Multi-account registries for Codex or OpenCode (out of scope in S4; filed separately).
- Moving a live chat between accounts (impossible by design; "continue" starts a new session).

## 4. Invariants (each needs its evidence in tests)

1. **Account identity UI is gated** (the status bar's usage and context items are not account identity and are never gated; §6.8). The chip, sidebar dots, header badge, the Settings color and Flow note, and the popover's continue action render only when the session's runtime has `supportsAccounts` **and** that runtime has 2+ registered accounts (the continue action also needs a limit state that allows moving, §6.1). Codex and OpenCode sessions never show them today. _Evidence:_ each surface's test renders it with 0, 1 and 2 Claude accounts and with a Codex session, and asserts absence (RTL `queryBy*` is null) in every case but 2 Claude accounts on a Claude session.
2. **Color is never the only signal.** Every dot has the account name as its accessible name and tooltip; the chip and header badge always print the name; amber and red states print what happened. _Evidence:_ RTL queries by role and name, never by class; the axe spec of §12.
3. **Unknown is never zero** (S4 invariant 4). A window with no reading renders as unknown (§6.0), is announced as "unknown", and is never drawn as an empty 0% bar. _Evidence:_ bar tests with `usedPct: null` and with the window absent.
4. **Core never reads `fleet.json`.** Policy reaches core only through S4's advisor. _Evidence:_ a guard test (`apps/server/src/services/core/usage/__tests__/no-fleet-policy-read.test.ts`) fails if a non-test `.ts`/`.tsx` file under `apps/server/src`, `apps/client/src` or `packages/shared/src` contains the string literal `'fleet.json'` or `"fleet.json"` (comments and vendored conformance fixtures are skipped).
5. **The banner follows the limit, not the account count.** It shows for any runtime and any number of accounts whenever the session has a `limit` (S4), and renders exactly the actions its `state` allows. _Evidence:_ banner tests for a Codex session (`wait-only`, named "Codex") and a one-account Claude session.
6. **The UI never decides what the server decides.** State, countdown targets, eligibility and the recommended account come from S4's `limit` and `continue-options`; the client computes only display text. _Evidence:_ banner and picker tests drive every case from mocked server data, and a grep test fails if `features/continue-on-account` imports anything that ranks accounts.

## 5. Account identity: palette and helpers

**The palette** (replaces S4's provisional `DEFAULT_ACCOUNT_COLORS` values; 8 entries, order is the default-by-position order):

| #   | Name   | Hex       | Min contrast on any app surface |
| --- | ------ | --------- | ------------------------------- |
| 1   | blue   | `#2f7be0` | 3.41                            |
| 2   | green  | `#1d8a4a` | 3.45                            |
| 3   | amber  | `#c2680a` | 3.25                            |
| 4   | purple | `#9b51e0` | 3.35                            |
| 5   | pink   | `#d6336c` | 3.28                            |
| 6   | teal   | `#0d9488` | 3.06                            |
| 7   | indigo | `#6366f1` | 3.39                            |
| 8   | stone  | `#78716c` | 3.15                            |

"Min contrast" is the WCAG ratio against the worst of the six surfaces a dot sits on: light `#ffffff`, `#fafafa` (background), `#e8e8e8` (sidebar); dark `#0a0a0a`, `#1a1a1a` (sidebar), `#262626` (hover/muted). All pass the 3:1 non-text rule in both themes, so one hex per account works in both (the contract stores one value). The first four follow the order of the decided mockups (blue, green, amber, purple). No red: red means "out" in this UI.

- Dots and badges only, never a large fill (design decision 1). The one literal-color use is the dot's `background-color` from the account's hex, set through a CSS variable (`--account-color`) the way `identity-avatar.tsx` does, with a comment naming this exception.
- A color stored by hand that is not in the palette still renders (the contract accepts any `#rrggbb`).
- A test in `packages/shared` recomputes the table's ratios from the hex values and fails if any drops below 3.0.

**Client helpers** (`apps/client/src/layers/shared/lib/claude-accounts.ts`, pure, tested):

- `accountWindow(usage, key)`: the `AccountUsage.windows` entry for `key`, or `null`.
- `barTone(window)`: `'unknown'` when `window` is null, or `usedPct` is null and `status` is not `rejected`; `'error'` when `status === 'rejected'` or `usedPct >= 100`; `'warning'` when `usedPct >= 70`; else `'success'`. (70 is where both decided mockups turn a bar amber: 72% amber, 40% green. The chip's amber rule is separate.)
- `chipState(accountState, limit)`: `'model-out'` when the session has a limit with `scope === 'model'` whose `state` is not `moved` (the account still runs another model; keyed on scope, so it stays right after the person chooses to wait and the state becomes `waiting-reset` or `reset-ready`); `'out'` when the session has any other `limit` whose `state` is not `moved`, or `accountState` is `limited`; `'near'` when `accountState` is `near-limit` (S4's `sessionAccountState`: the account reads `warning`, i.e. any window at 90% or more or `allowed_warning`); `'unknown'` when there is no usage; else `'ok'`.
- `nearestWindow(usage)`: for the `near` text, the readable window with the highest `usedPct` (ties: `five_hour` first).
- `formatResetTime(iso, now)`: local time. Same day → `2:10pm`; within the next 6 days → `Tue 3pm`; later → `Oct 3`. Minutes dropped when `:00`. `null` → `null`.
- `formatResetDay(iso, now)`: the weekday (`Sun`), or the time (`3pm`) when it is today.
- `formatBackIn(ms)`: under 60 min → `47 min`; under 24 h → `1h 12m` (`2h` when minutes are 0). Never used for 24 h or more.
- `limitText(window, resetsAt, now)`: **the wording rule** (orchestrator): the `five_hour` window with a reset under 24 h away → `back in <formatBackIn>`; any other window → `out until <formatResetTime>`; no reset → `out`.
- `windowShortName(key)`: `five_hour` → `5h`, `seven_day` → `week`, `seven_day_opus` → `week (Opus)`, `seven_day_sonnet` → `week (Sonnet)`, `model:<slug>` → `week (<Slug>)`, anything else → the server's `label`.
- `planName(plan)`: `'max'` → `Max plan`, `'pro'` → `Pro plan`, other non-null → capitalised + ` plan`, `null` → omitted.
- `limitSubject(session, accounts)`: **who ran out**, for the banner and marker: the account's label when the session's runtime has `supportsAccounts` and 2+ registered accounts; otherwise the runtime's display name from the existing `runtimeDisplayName` helper ("Claude", "Codex", "OpenCode"), because with one implicit account the runtime is what the person knows.

## 6. The client (`apps/client/src`)

FSD placement follows today's split: session rows (`entities/session`) already read accounts through `shared/model/server-config/use-claude-accounts.ts`, because an entity may not import `entities/config`. Account data therefore lives in `shared/`.

### 6.0 Shared building blocks

**Data** (`layers/shared/model/server-config/`):

- `useClaudeAccounts()` gains `color` and `colorIsDefault` on each `accounts[]` entry (S4 D1) and `colorFor(pathOrId)`.
- New `useAccountIdentityGate(runtime)` in `entities/runtime/model/use-account-identity-gate.ts` (it reads `useRuntimeCapabilities` from the same slice; `entities/session` already imports `entities/runtime`, and a `shared/` hook may not import an entity): `true` when `runtimeCapabilities[runtime].supportsAccounts` (S4 R) and that runtime's registered account count is 2+ (Claude Code: `useClaudeAccounts().accounts.length`; no other runtime has a registry today). This is **the one gate** for every account-identity surface (invariant 1). It replaces the scattered `isMultiAccount` checks for these surfaces; `isMultiAccount` stays for the existing pre-launch and team-roster uses.
- New `useAccountUsage(runtime)`: `{ byId, byPath, isLoading }`, query key `accountKeys.usage(runtime)`, `staleTime` 60 s. It is **seeded from the session list envelope's `accountUsage`** (S4 D7, which covers every account on the page, the implicit `default` included), so an open session has its account's usage with no extra request; `transport.getAccountUsage(runtime)` (§7.3 N2) runs only when the seed lacks the account or Settings → Runtimes is open. A merge never replaces a newer record (`updatedAt`).
- New `useAccountUsageSync()`, mounted once in `AppShell.tsx` beside `use-config-sync`: `useEventSubscription('account_usage', upsert by (runtime, accountId))` into any cached `accountKeys.usage(runtime)`; a no-op when nothing is cached.
- `Transport` (`packages/shared/src/transport.ts`) gains `getAccountUsage(runtime)`, `getContinueOptions(sessionId)`, `continueSession(sessionId, { account?, model?, runtime? })`, `waitForReset(sessionId, { autoResume? })`, `cancelAutoContinue(sessionId)` and `getLimitHistory(sessionId)`. `HttpTransport` implements them through a new `apps/client/src/layers/shared/lib/transport/account-methods.ts` beside `session-methods.ts`; `createMockTransport` and `createPlaygroundTransport` get defaults.

**UI atoms** (`layers/shared/ui/`, each with `data-slot`, TSDoc, sizes per `components.md`):

- `AccountDot({ color, name, size = 'sm', className })`: an 8px (`sm`) or 10px (`md`) circle, `role="img"`, `aria-label={name}`, wrapped in the house `Tooltip` showing `name` on hover. **Not a tab stop** (no `tabIndex`): screen readers read its label in place, and the row or chip around it is the focus target and carries the account name (orchestrator, 04 §9). Background from `--account-color`.
- `UsageMiniBars({ fiveHour, week, className })`: two vertical 4×10px bars, 2px apart, bottom-filled to `usedPct`, fill by `barTone` through `bg-status-<tone>` tokens (`success`, `warning-dot`, `error`); track `bg-muted`. `role="img"` with `aria-label` "5-hour window 40% used, weekly 72% used" (unknown → "5-hour window usage unknown").
- `UsageBar({ window, label, showReset })`: the horizontal 6px bar of the popover and settings rows, with the label on the left and "40% · resets 2:10pm" on the right (`text-2xs`, `text-muted-foreground`). Same tones and accessible text. Used for every runtime (R7).
- **Unknown** (a window with no reading): no fill and a dashed outline instead of a solid track, and the text says "unknown". (Q6, operator.) It lives behind the one `barTone === 'unknown'` branch.

### 6.8 Cached usage and context in the status bar (operator ask, 2026-09-26)

The status bar's usage and context numbers show **from the moment a session opens**, not only after a turn, for **every runtime and any number of accounts** (not gated like the chip).

- **Shown whenever there is a reading.** The operator asked for the numbers to be there from the moment a session opens, so `UsageStatusItem` and `ContextItem` are promoted whenever they have a readable value, not only near a limit (a change to today's quiet-by-default rule for these two items; their severity still rises near a limit).
- **Usage is account-wide.** `UsageStatusItem` (`features/status/ui/UsageStatusItem.tsx`) reads the session's account's `AccountUsage` from `useAccountUsage` (seeded from the session list, updated by `account_usage`), instead of only the per-turn `UsageStatus`. Every session on the same account shows the same numbers and they change together. A turn's own `UsageStatus` wins only when it arrived as a **live** frame after the session's snapshot (the client stamps live frames on arrival); the usage in a snapshot (`status.usage` on reopen) has no time and always ranks below the account reading, so hours-old data is never labelled "just now". The chip shows the most-used readable window (`nearestWindow`) with its existing gauge and percent; `UsageRevealPopover` lists every readable window with `UsageBar`.
- **One usage display, never two.** When the account chip (§6.1) is showing, it absorbs the usage display: `UsageStatusItem` is not promoted **and is suppressed even when pinned** (a pin bypasses `promote`, so the rule also sits where pinned items render, `buildStatusItemNodes`). Otherwise `UsageStatusItem` shows it. The rule lives next to both entries in `status-bar-registry.ts`, with one test for the promoted case and one for the pinned case.
- **Context is per session.** `ContextItem` falls back to the session status's cached `contextUsage` (with `observedAt`; S4 5.4, §7.3 N8) when no live value exists, so a reopened session shows its last known context at once.
- **Freshness.** The usage popover (the account chip's popover when the chip carries usage, else `UsageRevealPopover`) and the context breakdown tooltip end with a muted line "as of 12 min ago" (from the reading's `observedAt`; "just now" under a minute). The line sits at the end of the popover. When a usage reading is older than 60 minutes, its number in the chip is dimmed and the line says how old it is: a healthy number goes a step lighter (`text-muted-foreground/70`, since the status bar is already muted), and an amber or red number turns muted. Only usage dims; a context reading does not change between turns, so it is never dimmed (04 §13). When a window's `resetsAt` has passed, S4 reads it as expired (`expired: true`, 0%): the popover row shows the empty bar with "reset" instead of a percent, and the chip does not count that window. Dimming is a new treatment inside the existing chip (Q17).
- **Unknown stays unknown:** with no reading, the item is not promoted, as today; it never shows 0%.
- Same for Codex and OpenCode: their usage comes from the same store (S4 R), resolved as the runtime's implicit `(runtime, 'default')` account, which S4 D7 now links (N9). OpenCode's spend-only usage keeps today's pay-as-you-go form in the status bar (the Q15 spend line is for Settings only).

### 7.4 Find account folders on this computer (for §6.9)

A read-only discovery the Settings section calls, plus one small write for Dismiss. Built here (S5 task 2.5) with the S4 lead's review. It follows flow's `flow accounts setup` detection (marketplace `plugins/flow/scripts/fleet/detect-accounts.ts`) with the differences listed at the end.

- **Routes** (`routes/runtimes.ts`, next to the usage route; OpenAPI added and `docs/api/openapi.json` regenerated):
  - `GET /api/runtimes/claude-code/accounts/found` → `200 { folders: Array<{ path: string; name: string; lastUsedAt: string | null; orgManaged: boolean; orgMarker: string | null }> }`.
  - `POST /api/runtimes/claude-code/accounts/found/dismiss { path }` → `204`. The server canonicalizes the path and appends it to `runtimes.claudeCode.dismissedFolders` in one read-modify-write (no duplicates), so two dismissals in a row both stick. A path that is already registered or already dismissed answers `204` (a harmless race with another tab); any other path that is not a current candidate answers `400`. (A plain `PATCH /api/config` cannot do this: the client never sees the list, and a PATCH replaces arrays.)
- **Detection** (`findUnregisteredClaudeFolders(config, deps)` in `services/runtimes/claude-code/`; `deps.home` defaults to the OS home resolved in `claude-config-dir.ts`, the file allowed to read it, and tests pass a temp home; every path below is resolved against `deps.home`, never the real home):
  - candidates: `<home>/.claude` and every `<home>/.claude*` entry that is a folder (following a symlink) holding a `projects/` folder;
  - excluded: the machine default folder (`defaultAccountFolder('claude-code', config, deps.home)` from `services/core/usage/runtime-accounts.ts`; a `default` that aliases a registered row counts as registered), every registered row's path (including rows the reader skips but that carry a path), and every path in `dismissedFolders`, all compared canonically (realpath, via `canonicalAccountPath` with `deps.home`);
  - `orgManaged` is true when the folder holds `remote-settings.json` or `policy-limits.json` as a file (flow's `ORG_MARKER_FILES`); `orgMarker` names the file;
  - `lastUsedAt`: the newest modification time among `projects/`, its direct children and the files directly inside each child (a resumed session appends to an existing file, which a folder's time misses); at most 2,000 entries are statted per folder, newest found wins; `null` when none can be read;
  - **stat and readdir only.** It never opens a file, so it never reads settings or credentials.
- **Differences from flow's detection, on purpose:**
  - DorkOS requires `projects/`, where flow also accepts `sessions/` alone. DorkOS's own check for a usable account folder looks at `projects/`, so a `sessions/`-only folder would show as "not ready" right after Add.
  - `CLAUDE_CONFIG_DIR` is not read: the server resolves accounts from config, never from its own environment.
  - `lastUsedAt` and the dismissed list exist only here; flow does not need them.
- **Config:** `runtimes.claudeCode.dismissedFolders: z.array(z.string()).max(200).default([])` (a closed array), stored canonical. Written only by the dismiss route. It needs a semver-keyed migration at `0.88.0` (the next free key after `0.87.0`; renumber if another branch lands first), pinned in `merged-migration-hashes.ts`, with the DOR-1733 key-count assertion in `config-manager.test.ts` bumped. It is `expose` in `config-disclosure.ts` (folder paths are exposed on purpose; `withhold` is only for secrets and linked-account identity) and operator-only in `config-write-policy.ts`, and it is listed in `safe-defaults/default-verdicts.ts`. An accounts save (`planClaudeAccountWrite`) never drops it.

### 8.2 Server routes (mounted by the host at `/api/ext/flow/`)

- `GET /fleet` → `{ handoff, crossRuntimeFallback, anyRoleStored, groups: Array<{ runtime, label, supportsAccounts, accounts: Array<{ key, id, label, color, implicit, role, reservePct, spendDownWindowHours, repos, effectiveReservePct }> }>, warnings }`. `supportsAccounts` is the runtime's capability (from the host when it exposes one; else true when the runtime has a registered, non-implicit account); the Flow tab's nothing-in-rotation rule counts only those runtimes.
  - Claude Code identities from `ctx.accounts.list()` (registry order, resolved colors), mapped to flow's `{ id, routable }` with `routable = ACCOUNT_ID_PATTERN.test(id)`; with an empty registry, the implicit `default`. Other runtimes' implicit accounts come from the same `ctx.accounts.list()` (`implicit: true`).
  - Policy from `loadFleetPolicy(ctx.dorkHome, identities)`; `effectiveReservePct` from the account's raw ledger read with flow's `usage-ledger.ts`.
  - `anyRoleStored`: true when any account has a stored `role` in `fleet.json` (drives the first-visit notice, §8.3).
  - Group labels: "Claude Code", "Codex", "OpenCode". Claude Code's standalone default takes the host's label, "Main (this computer's sign-in)" (S4 contract 6d: this computer's own sign-in is the operator's Main); a Codex or OpenCode implicit account reads "<Runtime> (this computer's sign-in)".
- `PUT /fleet/accounts/:key` body `{ role?, reservePct?, spendDownWindowHours?, repos? }` (flow's `AccountPolicyPatch`; `null` resets a field). One `updateFleetPolicy` call under the contract's lock. **Choosing `main`** while another account of the same runtime is `main` demotes that one to `rotation` in the same locked write (one `main` per the contract). `repos` entries must match `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`, else `400` naming the entry. - A lock error (gave up after 2 s, or a newer file version) → `409` with flow's own message.

### 8.4 The advisor (S4 X3; DOR-2388)

`server.ts` registers `ctx.accounts.registerAdvisor(advisor)`. A session is a **flow run** when the main checkout's `.dork/flow/flow-state.json` (contract §1.3, found from `cwd` as S4 D8 does) has a run whose `sessionId` equals it.

- `rank(candidates, ctx)`:
  - **Agents and relay** (`ctx.caller` is `agent` or `relay`, S4 D5 and D6): flow's opt-in policy applies in full: an account with no `fleet.json` entry reads as kept-out, and a kept-out account outside its repos is omitted or `eligible: false`, so an agent can never spend an account the operator did not opt in. The lenient rule below is for a person only.
  - **Hidden (omitted), for a person** (`caller` `person` or `advisor`): for a flow run, every account flow could not move the run to (`!mayServe(policy, repo)` with `repo = parseOriginRepo(origin)`, or `rankAccounts` calls it ineligible for a reason other than usage); for any other session, only accounts the operator explicitly set to Kept out whose repos do not include this one. An account with no `fleet.json` entry reads as kept-out to flow (the contract's opt-in default), but hiding it from a person's own picks would hide every account on a fresh install, so it stays listed there.
  - **Order and `recommendedId`:** `rankAccounts` over the listed candidates (the limited account excluded by S4); `badge: 'recommended'` on the top one.
  - **Reserved:** Main outside its spend-down window, while another listed account is eligible: `eligible: false`, `badge: 'reserved'`, `reason: "kept in reserve (<effectiveReservePct>%)"` (the contract's §1.1b main-account rule; the room checks are `rankAccounts`', including the 5-hour window).
  - **Reasons** in plain words for every row ("58% of the week left", "Out until Tue 3pm").
  - **Cross-runtime:** when `crossRuntimeFallback` is `on` and N3 exists, the advisor includes other runtimes' accounts after the same-runtime ones; else it never does.
- `onLimited(info)`: `{ mode: 'ask' }` unless `info` is a flow run. For a flow run: `handoff: 'auto'` and `rankAccounts` has an eligible account → `{ mode: 'auto', target, delaySeconds: 10 }` (the mockup's "in 10s"); a reset under an hour away → `{ mode: 'wait' }` (S4 then sets `autoResume`); else `{ mode: 'ask' }`.
- `claims(info)`: true when `info.sessionId` is a flow run (above). S4 asks it once per limit and stores the answer.
- `move(info, target)`: accepts at once (resolves within 2 s) after checking the run exists and the target is one flow may move it to (else throws with flow's reason, which S4 shows as the 503). It then runs `flow handoff <identifier> --to <target.accountId> --project <main checkout> --json` in the background through `execFile('node', ['--experimental-strip-types', <flowRoot>/scripts/flow.ts, …])` (no shell; `node` from `PATH`, because `process.execPath` is Electron inside the desktop app; 120 s timeout; `flowRoot` three levels above `ctx.extensionDir`). On exit 0 it re-reads the run and calls `ctx.accounts.markContinued(info.sessionId, { sessionId: <new>, runtime, accountId })`. On failure it logs flow's message and reports nothing; S4 returns the plan to `ask` after 10 minutes, so the person can try again (a faster failure report would need a new S4 call; not needed now).
- `cancelAuto(info)`: holds flow's automatic handoff for this run until the person acts again (the same run-store write `wait` uses, with no resume), so flow's supervisor does not move it while the person is in the picker.
- `wait(info, resumeAt, autoResume)`: records the person's choice on the run (flow's `limit.state = 'waiting-reset'`, `resumeOnReset = autoResume`) through flow's run store, so flow's supervisor neither moves nor resumes it early; flow resumes it at the reset only when `autoResume` is true (Q1, operator). Until flow ships a hold (S3), the extension writes the fields S3's reducer reads and says so in its PR.
- When flow's supervisor moves a claimed run on its own, the extension calls `ctx.accounts.markContinued(oldSessionId, { sessionId, runtime, accountId })`, so the banner shows `moved`.
- `modelFallback(info)`: not implemented; S4's default ("sonnet" when Opus or another non-Sonnet model bucket is out) applies.
- `carryOver(info, target)`: for a flow run, the seed is flow's checkpoint: the run's worktree `.dork/flow/HANDOFF.md` (bounded to `SEED_CONTEXT_MAX_LENGTH`) plus the item's identifier and title, and `prompt` = flow's `resume-from-handoff` text (S3 §1); a missing checkpoint throws, so S4 uses its default summary. For any other session it throws, and S4 uses its default summary (S4 logs the fallback; the advisor's error message says "not a flow run" so the log is plain).

## 10. Accessibility

- Color is never the only signal (invariant 2). The chip, badge, banner, marker and picker rows print the name; state is in words.
- `AccountDot`, `UsageMiniBars` and `UsageBar` are `role="img"` with full sentences as names; the popover and dialog use the house primitives (focus trap, `Escape`, focus returns to the chip or button). None of them is a tab stop; their tooltips show on hover (04 §9).
- The chip is a button with `aria-haspopup="dialog"` and `aria-expanded`; its accessible name includes the state text.
- The banner is `role="status"` (§6.7). Countdown digits sit in an `aria-hidden` span beside a visually hidden sentence ("Moving this task to Acct 2 in 10 seconds.") that is set once per state, so a screen reader is not read a number every second. The checkbox is a labelled native checkbox. The picker's inline error is `role="alert"`. The marker is plain text in reading order.
- The Flow tab's segmented controls are real radio groups (arrow keys, `aria-checked`), the slider is a native range with `aria-valuetext`, and every chip remove button is labelled.
- Everything works at 360px: the chip truncates the name first (state words never truncate); the dialog is a bottom sheet on mobile (`ResponsiveDialog`); the banner's buttons wrap.

## 15. Decisions and assumptions (autonomy grant; reversible)

- **Palette** chosen by contrast (§5) and owned here; one hex per account in both themes, because the contract stores one value.
- **Bar amber at 70%**, read off both decided mockups; the chip's amber rule stays S4's 90%.
- **The UI renders S4's decisions and computes only text** (invariant 6): states, targets, eligibility and countdown instants are the server's.
- **Limit history is a table owned here** (§7.1), written by S4's `session_limits` module, because S4 deletes the episode at the next turn and the marker must outlive it.
- **The facts in §7.3 are asked of S4** rather than invented here; the tasks feature-detect them so the UI ships without waiting.
- **Plugin-carried extensions are discovered** (§7.2), approved per source (S4 task 6.1). ADR seeded.
- **The account-identity gate is capability-based** (`supportsAccounts` + 2+ registered accounts of that runtime), one hook for every surface.
- **Usage rides the session list** (S4 D7's envelope) and the `account_usage` event; a fetch happens only for Settings or when the seed lacks the account, so an open session costs no extra request.
- **Banner name rule:** the account's label with 2+ Claude accounts, else the runtime's name.
- **`reset-ready` Continue is a normal send,** not a new endpoint: S4 clears the limit on a person's message.
- **Kept-out hiding for a person's own session** applies only to accounts explicitly set to Kept out; unconfigured accounts stay offered, or a fresh flow install would hide every account.
- **The Flow tab UI is hand-built on host CSS variables** because extensions cannot import host components today.
- **Main moves demote the previous Main of the same runtime** in one locked write.
- **Spend-down choices 6/12/24/48/72 h;** a stored custom value is kept.
- **The status-bar pre-launch picker moves out of `RuntimeItem`** (one place for one choice).
- **`TurnFailedNotice` is replaced by the banner** for a limited turn (one notice, not two).
- **Usage and context always show when there is a reading** (§6.8), a deliberate change to the status bar's quiet-by-default rule for these two items, from the operator's ask (04 §4c).
- **Flow's automatic countdown is 10 seconds** (the mockup), set by the advisor's `delaySeconds`.
