# Claude account UI: see which account a session spends, and move work off a spent one

**Status:** Specified. The visual design is the operator's (visual companion, 2026-09-26; `04-design-decisions.md`), with the banner placement, its states and the runtime rules decided by the orchestrator on the operator's behalf. Technical choices are made under the autonomy grant and logged in §15. Visual questions the decided designs do not answer are in §14 and are **not** decided here.

**Scope:** the DorkOS client (core UI), two small server additions the UI needs (§7), and the Flow extension that ships inside the flow plugin in `dork-labs/marketplace` (§8). Everything the server decides about limits, waiting, moving work and the advisor is S4's (D9, X3); this spec renders it.

## 1. Overview

S4 teaches the server about accounts: a color per account, usage per account for every runtime, a `limit` on a session that hit a hard limit with a server-computed `state` and `plan`, continue and wait endpoints, an account advisor the Flow extension registers, and the tracker item a flow run serves. This spec shows all of it:

- **Where you work** (decision 1, option C): a status-bar account chip with a color dot, the name and two tiny usage bars; a popover with each window, reset times, the tracker item and "Continue on another account →"; a color dot on each sidebar session row; a name badge in the session header. **Only when the session's runtime supports several accounts (`supportsAccounts`, Claude Code today) and that runtime has 2 or more registered accounts.**
- **Settings** (decision 2, option A): Settings → Runtimes shows usage bars for any runtime with usage data, even with one account; with 2+ Claude accounts each row also shows its color, and a one-line pointer leads to a **Flow** tab. The Flow tab (added by the Flow extension) sets each account's role, the main account's reserve, repo scopes, the handoff mode and cross-runtime fallback.
- **When usage runs out** (decision 3, option A): a banner above the message box, for any runtime, that walks through the states S4 emits and collapses into a one-line transcript marker when resolved; and the "Continue on another account" picker.

## 3. Goals and non-goals

**Goals**

- A person with 2+ Claude accounts can tell, without opening anything, which account every Claude Code session spends and how close each is to a limit.
- Near a limit and out of usage are said in words, never by color alone.
- When any runtime runs out, the person sees why, what they can do, and what happened afterwards, in the same place.
- One click moves the work to another account in the same folder.
- The operator sets how flow spends each account in Settings → Flow, and the flow CLI reads the same file.
- One account: no account identity UI (chip, dots, badge, color, picker).
- The status bar's usage and context numbers are there from the moment a session opens, for every runtime, and never older than they say.

**Non-goals**

- Any server behavior S4 specifies (limits, plans, timers, carry-over, the default summary, ranking, the advisor contract).
- Automatic handoff logic, ranking or checkpoints (flow and S4). This UI renders their results.
- A probe button, an Accounts/Fleet page, or a usage history view.
- Multi-account registries for Codex or OpenCode (out of scope in S4; filed separately).
- Moving a live chat between accounts (impossible by design; "continue" starts a new session).

## 4. Invariants (each needs its evidence in tests)

1. **Account identity UI is gated** (the status bar's usage and context items are not account identity and are never gated; §6.8). The chip, sidebar dots, header badge, the Settings color and Flow note, and the popover's continue action render only when the session's runtime has `supportsAccounts` **and** that runtime has 2+ registered accounts (the continue action also needs a limit state that allows moving, §6.1). Codex and OpenCode sessions never show them today. _Evidence:_ each surface's test renders it with 0, 1 and 2 Claude accounts and with a Codex session, and asserts absence (RTL `queryBy*` is null) in every case but 2 Claude accounts on a Claude session.
2. **Color is never the only signal.** Every dot has the account name as its accessible name and tooltip; the chip and header badge always print the name; amber and red states print what happened. _Evidence:_ RTL queries by role and name, never by class; the axe spec of §12.
3. **Unknown is never zero** (S4 invariant 4). A window with no reading renders as unknown (§6.0), is announced as "unknown", and is never drawn as an empty 0% bar. _Evidence:_ bar tests with `usedPct: null` and with the window absent.
4. **Core never reads `fleet.json`.** Policy reaches core only through S4's advisor. _Evidence:_ a guard test (`apps/server/src/services/core/usage/__tests__/no-fleet-policy-read.test.ts`) fails if a non-test `.ts`/`.tsx` file under `apps/server/src`, `apps/client/src` or `packages/shared/src` contains the string literal `'fleet.json'` or `"fleet.json"` (comments and vendored conformance fixtures are skipped).
5. **The banner follows the limit, not the account count.** It shows for any runtime and any number of accounts whenever the session has a `limit` (S4), and renders exactly the actions its `state` allows. _Evidence:_ banner tests for a Codex session (`wait-only`, named "Codex") and a one-account Claude session.
6. **The UI never decides what the server decides.** State, countdown targets, eligibility and the recommended account come from S4's `limit` and `continue-options`; the client computes only display text. _Evidence:_ banner and picker tests drive every case from mocked server data, and a grep test fails if `features/continue-on-account` imports anything that ranks accounts.

## 5. Account identity: palette and helpers

**The palette** (replaces S4's provisional `DEFAULT_ACCOUNT_COLORS` values; 8 entries, order is the default-by-position order):

| #   | Name   | Hex       | Min contrast on any app surface |
| --- | ------ | --------- | ------------------------------- |
| 1   | blue   | `#2f7be0` | 3.41                            |
| 2   | green  | `#1d8a4a` | 3.45                            |
| 3   | amber  | `#c2680a` | 3.25                            |
| 4   | purple | `#9b51e0` | 3.35                            |
| 5   | pink   | `#d6336c` | 3.28                            |
| 6   | teal   | `#0d9488` | 3.06                            |
| 7   | indigo | `#6366f1` | 3.39                            |
| 8   | stone  | `#78716c` | 3.15                            |

"Min contrast" is the WCAG ratio against the worst of the six surfaces a dot sits on: light `#ffffff`, `#fafafa` (background), `#e8e8e8` (sidebar); dark `#0a0a0a`, `#1a1a1a` (sidebar), `#262626` (hover/muted). All pass the 3:1 non-text rule in both themes, so one hex per account works in both (the contract stores one value). The first four follow the order of the decided mockups (blue, green, amber, purple). No red: red means "out" in this UI.

- Dots and badges only, never a large fill (design decision 1). The one literal-color use is the dot's `background-color` from the account's hex, set through a CSS variable (`--account-color`) the way `identity-avatar.tsx` does, with a comment naming this exception.
- A color stored by hand that is not in the palette still renders (the contract accepts any `#rrggbb`).
- A test in `packages/shared` recomputes the table's ratios from the hex values and fails if any drops below 3.0.

**Client helpers** (`apps/client/src/layers/shared/lib/claude-accounts.ts`, pure, tested):

- `accountWindow(usage, key)`: the `AccountUsage.windows` entry for `key`, or `null`.
- `barTone(window)`: `'unknown'` when `window` is null, or `usedPct` is null and `status` is not `rejected`; `'error'` when `status === 'rejected'` or `usedPct >= 100`; `'warning'` when `usedPct >= 70`; else `'success'`. (70 is where both decided mockups turn a bar amber: 72% amber, 40% green. The chip's amber rule is separate.)
- `chipState(accountState, limit)`: `'model-out'` when the limit's `state` is `model-limited` (the account still runs another model); `'out'` when the session has any other `limit` whose `state` is not `moved`, or `accountState` is `limited`; `'near'` when `accountState` is `near-limit` (S4's `sessionAccountState`: the account reads `warning`, i.e. any window at 90% or more or `allowed_warning`); `'unknown'` when there is no usage; else `'ok'`.
- `nearestWindow(usage)`: for the `near` text, the readable window with the highest `usedPct` (ties: `five_hour` first).
- `formatResetTime(iso, now)`: local time. Same day → `2:10pm`; within the next 6 days → `Tue 3pm`; later → `Oct 3`. Minutes dropped when `:00`. `null` → `null`.
- `formatResetDay(iso, now)`: the weekday (`Sun`), or the time (`3pm`) when it is today.
- `formatBackIn(ms)`: under 60 min → `47 min`; under 24 h → `1h 12m` (`2h` when minutes are 0). Never used for 24 h or more.
- `limitText(window, resetsAt, now)`: **the wording rule** (orchestrator): the `five_hour` window with a reset under 24 h away → `back in <formatBackIn>`; any other window → `out until <formatResetTime>`; no reset → `out`.
- `windowShortName(key)`: `five_hour` → `5h`, `seven_day` → `week`, `seven_day_opus` → `week (Opus)`, `seven_day_sonnet` → `week (Sonnet)`, `model:<slug>` → `week (<Slug>)`, anything else → the server's `label`.
- `planName(plan)`: `'max'` → `Max plan`, `'pro'` → `Pro plan`, other non-null → capitalised + ` plan`, `null` → omitted.
- `limitSubject(session, accounts)`: **who ran out**, for the banner and marker: the account's label when the session's runtime has `supportsAccounts` and 2+ registered accounts; otherwise the runtime's display name from the existing `runtimeDisplayName` helper ("Claude", "Codex", "OpenCode"), because with one implicit account the runtime is what the person knows.

### 6.0 Shared building blocks

**Data** (`layers/shared/model/server-config/`):

- `useClaudeAccounts()` gains `color` and `colorIsDefault` on each `accounts[]` entry (S4 D1) and `colorFor(pathOrId)`.
- New `useAccountIdentityGate(runtime)` in `entities/runtime/model/use-account-identity-gate.ts` (it reads `useRuntimeCapabilities` from the same slice; `entities/session` already imports `entities/runtime`, and a `shared/` hook may not import an entity): `true` when `runtimeCapabilities[runtime].supportsAccounts` (S4 R) and that runtime's registered account count is 2+ (Claude Code: `useClaudeAccounts().accounts.length`; no other runtime has a registry today). This is **the one gate** for every account-identity surface (invariant 1). It replaces the scattered `isMultiAccount` checks for these surfaces; `isMultiAccount` stays for the existing pre-launch and team-roster uses.
- New `useAccountUsage(runtime)`: `{ byId, byPath, isLoading }`, query key `accountKeys.usage(runtime)`, `staleTime` 60 s. It is **seeded from the session list envelope's `accountUsage`** (S4 D7, which covers every account on the page, the implicit `default` included), so an open session has its account's usage with no extra request; `transport.getAccountUsage(runtime)` (§7.3 N2) runs only when the seed lacks the account or Settings → Runtimes is open. A merge never replaces a newer record (`updatedAt`).
- New `useAccountUsageSync()`, mounted once in `AppShell.tsx` beside `use-config-sync`: `useEventSubscription('account_usage', upsert by (runtime, accountId))` into any cached `accountKeys.usage(runtime)`; a no-op when nothing is cached.
- `Transport` (`packages/shared/src/transport.ts`) gains `getAccountUsage(runtime)`, `getContinueOptions(sessionId)`, `continueSession(sessionId, { account?, model?, runtime? })`, `waitForReset(sessionId, { autoResume? })`, `cancelAutoContinue(sessionId)` and `getLimitHistory(sessionId)`. `HttpTransport` implements them through a new `apps/client/src/layers/shared/lib/transport/account-methods.ts` beside `session-methods.ts`; `createMockTransport` and `createPlaygroundTransport` get defaults.

**UI atoms** (`layers/shared/ui/`, each with `data-slot`, TSDoc, sizes per `components.md`):

- `AccountDot({ color, name, size = 'sm', className })`: an 8px (`sm`) or 10px (`md`) circle, `role="img"`, `aria-label={name}`, wrapped in the house `Tooltip` showing `name`. Background from `--account-color`.
- `UsageMiniBars({ fiveHour, week, className })`: two vertical 4×10px bars, 2px apart, bottom-filled to `usedPct`, fill by `barTone` through `bg-status-<tone>` tokens (`success`, `warning-dot`, `error`); track `bg-muted`. `role="img"` with `aria-label` "5-hour window 40% used, weekly 72% used" (unknown → "5-hour window usage unknown").
- `UsageBar({ window, label, showReset })`: the horizontal 6px bar of the popover and settings rows, with the label on the left and "40% · resets 2:10pm" on the right (`text-2xs`, `text-muted-foreground`). Same tones and accessible text. Used for every runtime (R7).
- **Unknown** (a window with no reading): no fill and a dashed outline instead of a solid track, and the text says "unknown". Whether that is the right treatment is Q6; it lives behind the one `barTone === 'unknown'` branch so a change is one place.

### 6.6 "Continue on another account" picker (decision 3, DOR-2388)

**Core UI; works without flow.** Everything flow changes arrives as data in S4's ranking; there is no flow-contributed UI slot.

`features/continue-on-account/` (new slice): `ui/ContinueOnAccountDialog.tsx`, `model/use-continue-options.ts`, `model/use-continue-session.ts`.

- **Opened from:** the popover action (§6.1) and the banner's "Continue on another account…" / "Choose account…" (§6.7). Only when the identity gate is on, or when the ranking offers another runtime's accounts (N3). From `handing-off`, "Choose account…" first calls `POST …/continue/cancel`, so S4's timer cannot move the work to its own target while the person is choosing (S4 makes carry-over idempotent per episode, so a timer firing first would win silently).
- **Data:** `GET /api/sessions/:id/continue-options` → `{ plan, ranking }`, `ranking = { accounts: { id, label, color, usage, eligible, reason, badge?, runtime? }[], recommendedId }`, plus `advised` (§7.3 N1). The ranking already excludes the session's own account.
- **Content** (house `ResponsiveDialog`, max width 380px as the mockup):
  - Title "Continue on another account".
  - One radio row per listed account, in the server's order: dot, name, a `recommended` pill (success tone) when `badge === 'recommended'`, and on the right the account's state: eligible → "28% left · resets Sun" (100 − the weekly `usedPct`; the day by `formatResetDay`), weekly unknown → "usage unknown"; not eligible → the ranking's `reason` in plain words (for example "kept in reserve (50%)" from flow, or S4's "Out until Tue 3pm").
  - A row that is not eligible is dimmed. An account that is out (`usage.state === 'limited'`) is also disabled, since nothing can run there. Any other ineligible row (flow's reserved Main) stays selectable, because S4 never refuses a person's pick; whether that is right is Q2.
  - **Hidden accounts:** registered accounts of the session's runtime that the ranking omits (flow hides kept-out accounts) are named in one muted line under the list: "Client is kept out, so it isn't listed." (two or more: "Client and Acct 5 are kept out, so they aren't listed.").
  - **Other runtimes** (R7): when the ranking carries rows whose `runtime` differs from the session's (only when flow's cross-runtime fallback is on; §7.3 N3), they form a second group under the heading "Other runtimes", each named by `limitSubject` rules (an implicit account reads "Codex (this computer's sign-in)").
  - The row matching `recommendedId` is selected on open (S4's default ranking recommends the first eligible even without flow, but only an advisor adds the `recommended` pill), else the first selectable row.
  - Subtitle and carry-over list (mockup v2):
    - a flow run (`advised` and `Session.trackerItem` set): "Picks up in the same folder and branch from flow's checkpoint." / "Carries over: files, branch, checkpoint, task" / "Doesn't: the chat itself";
    - otherwise: "Starts a new chat in the same folder, with a summary of this one. Sorted by most usage left." / "Carries over: the folder and a summary of this chat" / "Doesn't: the chat itself". ("Sorted by most usage left" is dropped when `advised`, since flow's order is different.)
  - "No other account can take this work right now." replaces the list when no row is selectable; the primary button is disabled.
  - Footer: `Cancel` and a primary "Continue on <name>".
- **Continue:** `POST /api/sessions/:id/continue { account }` (plus `runtime` for an other-runtime row). On `202 { sessionId }` the dialog closes and the app navigates to the new session. ### 6.8 Cached usage and context in the status bar (operator ask, 2026-09-26)

The status bar's usage and context numbers show **from the moment a session opens**, not only after a turn, for **every runtime and any number of accounts** (not gated like the chip).

- **Usage is account-wide.** `UsageStatusItem` (`features/status/ui/UsageStatusItem.tsx`) reads the session's account's `AccountUsage` from `useAccountUsage` (seeded from the session list, updated by `account_usage`), instead of only the per-turn `UsageStatus`. Every session on the same account shows the same numbers and they change together. A turn's own `UsageStatus` wins while it is newer than the account reading; it carries no timestamp, so the client stamps it when it arrives. The chip shows the most-used readable window (`nearestWindow`) with its existing gauge and percent; `UsageRevealPopover` lists every readable window with `UsageBar`.
- **One usage display, never two.** When the account chip (§6.1) is showing, it absorbs the usage display and `UsageStatusItem` is not promoted (its `promote` returns false while `account` is promoted). Otherwise `UsageStatusItem` shows it. Rule lives in `status-bar-registry.ts` next to both entries.
- **Context is per session.** `ContextItem` falls back to the session status's cached context (§7.3 N8) when no live value exists, so a reopened session shows its last known context at once.
- **Freshness.** The usage popover (the account chip's popover when the chip carries usage, else `UsageRevealPopover`) and the context breakdown tooltip end with a muted line "as of 12 min ago" (from the reading's `observedAt`; "just now" under a minute). When a reading is older than 60 minutes, the numbers in the chip are dimmed (`text-muted-foreground`) and the line says so. When a window's `resetsAt` has passed, S4 reads it as expired (`expired: true`, 0%): the popover row shows the empty bar with "reset" instead of a percent, and the chip does not count that window. Dimming is a new treatment inside the existing chip (Q17).
- **Unknown stays unknown:** with no reading, the item is not promoted, as today; it never shows 0%.
- Same for Codex and OpenCode: their usage comes from the same store (S4 R). OpenCode's spend-only usage keeps today's pay-as-you-go form only if Q15 says so; until then nothing new shows for it.

## 7. Server additions (`apps/server`)

### 7.1 Limit history for the transcript marker

S4 keeps an episode in `session_limits` until the session's next `turn_start` and then deletes it. The marker needs what happened after that, so this spec keeps a short history.

- **Table** (`packages/db/src/schema/session-limit-history.ts` + a Drizzle migration): `session_limit_history` with `id` (text uuid), `session_id`, `since`, `runtime`, `account_id` (nullable), `window`, `scope`, `resets_at` (nullable), `resolution` (`moved` | `resumed-reset` | `resumed-model` | `resumed-early`), `resolved_at`, `to_session_id`, `to_account_id`, `model_from`, `model_to` (nullable). Unique on (`session_id`, `since`). Rows older than 30 days are swept at boot.
- **Written by the S4 module that owns `session_limits`** (D4; the same code path, so the two cannot disagree):
  - when a plan becomes `continued`: a `moved` row with the new session, account and time;
  - when the row is deleted at `turn_start` without a `moved` row: `resumed-model` when the session's model changed since `since`, `resumed-reset` when `plan.resetConfirmedAt` is set or now ≥ `resets_at`, else `resumed-early`.
- **Read:** `GET /api/sessions/:id/limit-history` → `200 { entries: [...] }`, the last 20, oldest first; `404` unknown session. OpenAPI regenerated (`pnpm docs:export-api`).
- **Event:** the existing session stream `status_change` already tells an open client the limit cleared; the client refetches history then. No new event.

### 7.2 Run extensions that ship inside an installed plugin

- `ExtensionDiscovery.discover` scans two more roots: `<dorkHome>/plugins/*/.dork/extensions/*` with origin `global`, and `<cwd>/.dork/plugins/*/.dork/extensions/*` with origin `local`. Precedence and approval are exactly those of the existing roots: a local record never takes over an id that is core or already approved (the DOR-511 rule in the same file), and a plugin-carried extension needs the person's one-time "Allow it to run" (DOR-516) like any other non-core extension. Two plugins carrying the same id: the first by sorted plugin directory name wins, with a warning.
- The record remembers its plugin directory, so uninstalling the plugin (`flows/uninstall.ts`, which already walks the package's `.dork/extensions`) disables it and clears its approval, and the compile cache is keyed by the real path.
- Tests: an installed fixture plugin with an extension is discovered, enabled by `install-plugin.ts`, refused until approved, and gone after uninstall; a project plugin cannot inherit an approved global id.

### 8.4 The advisor (S4 X3; DOR-2388)

`server.ts` registers `ctx.claudeAccounts.registerAdvisor(advisor)`. A session is a **flow run** when the main checkout's `.dork/flow/flow-state.json` (contract §1.3, found from `cwd` as S4 D8 does) has a run whose `sessionId` equals it.

- `rank(candidates, ctx)`:
  - **Agents and relay** (`ctx.caller` is `agent` or `relay`, S4 D5 and D6): flow's opt-in policy applies in full: an account with no `fleet.json` entry reads as kept-out, and a kept-out account outside its repos is omitted or `eligible: false`, so an agent can never spend an account the operator did not opt in. ## 10. Accessibility

## 14. Open design questions (the operator decides these in the visual companion)

- ~~**Q0. Notice placement.**~~ (RESOLVED, orchestrator for the operator) A: a banner that collapses into a transcript marker, with the states of §6.7.
- **Q1. Holding flow when the person says wait.** With a flow run in `auto`, "Wait for reset" cancels S4's countdown, but flow's own supervisor (S3) may still move or resume the run on its next pass; an unchecked "Continue automatically" cannot stop it either. (a) accept it (the banner then shows `moved` or clears when flow acts); (b) hide "Wait for reset" for a flow run in `auto`; (c) add a hold to flow (a contract change). Default: (a).
- **Q2. Can a person pick an account shown as "kept in reserve"?** The mockup dims Main. S4 never refuses a person's pick. Default: dimmed but selectable.
- ~~**Q3.**~~ (RESOLVED by the orchestrator and mockup v2) the no-flow wording.
- **Q4. The sidebar dot's place** among the row's existing marks, and whether the row keeps printing the name. Default: the dot leads the title; the name moves into the tooltip.
- **Q5. "· started on this account"** in the popover is always true for a DorkOS session; "continued from Acct 4" needs data S4 does not serve. Default: omit.
- **Q6. How a window with no reading looks.** Proposed: a dashed empty track and "unknown".
- **Q7. The pre-launch chip, "restyled to match".** Proposed: the same chip (dot, name, bars) with a chevron; menu rows are dot + name + bars, the default first, with today's "not ready" note.
- **Q8. Choosing an account's color.** Proposed: clicking the row's dot opens a popover of the 8 swatches (a radio group) plus "Default".
- **Q9. "+ add" in "Only for these repos".** Proposed: the chip becomes a small text field (placeholder "owner/name"); Enter adds, Escape cancels, a bad value shows "Use owner/name, like acme/app."
- **Q10. The marker's look.** Proposed: one muted `text-2xs` line with a small icon (a clock for resumed, an arrow for moved), keeping the moved line's account dot.
- **Q11. "Continue here anyway"** re-enables the composer for this window only. Proposed as that.
- **Q12. `reset-ready` wording** ("Acct 4 has reset." / "should have reset by now." + Continue). Proposed as written.
- **Q13. The banner's tone in calm states** (`waiting-reset`, `reset-ready`, `moved`). Proposed: keep the decided red unless the operator wants the neutral banner there.
- **Q14. A moved session in the sidebar.** Proposed: no tint and no text (the work lives in the new session).
- **Q15. Spend-only usage in Settings** (OpenCode reports dollars, no windows). Proposed: nothing until a spend limit exists; the alternative is a line like "$4.20 this month".
- **Q16. Cross-runtime fallback per runtime pair** (R4 mentions it). Proposed: one fleet-wide Off/On row now; per-pair choices need more than the approved row pattern.
- **Q17. Dimming stale numbers.** The chip's numbers turn muted when a reading is over 60 minutes old. Proposed: `text-muted-foreground` on the number only, the "as of" line in the popover saying how old.
- **Q18. "Continue on another account →" on a healthy session.** The decided popover shows it always; S4 cannot move a session that has no limit (N7). Proposed: show it only while the session is out, until S4 allows it.
- **Q19. The chip when only a model is out** ("Acct 3 · Opus out until Tue 3pm"). Proposed: the amber near-limit look, since the account still runs other models.
- **Q20. Where one-account and Codex usage bars sit in Settings** (under "Billing account" for Claude; a new "Usage" row on the Codex and OpenCode cards). Proposed as written.
- **Q21. The implicit account's color** in the Flow tab (stone). Proposed as written.

## 15. Decisions and assumptions (autonomy grant; reversible)

- **Palette** chosen by contrast (§5) and owned here; one hex per account in both themes, because the contract stores one value.
- **Bar amber at 70%**, read off both decided mockups; the chip's amber rule stays S4's 90%.
- **The UI renders S4's decisions and computes only text** (invariant 6): states, targets, eligibility and countdown instants are the server's.
- **Limit history is a table owned here** (§7.1), written by S4's `session_limits` module, because S4 deletes the episode at the next turn and the marker must outlive it. If #2147 adds its own history, this section is dropped in favor of it.
- **The facts in §7.3 are asked of S4** rather than invented here; the tasks feature-detect them so the UI ships without waiting.
- **Plugin-carried extensions are discovered** (§7.2) with today's approval rules. ADR seeded.
- **The account-identity gate is capability-based** (`supportsAccounts` + 2+ registered accounts of that runtime), one hook for every surface.
- **Usage rides the session list** (S4 D7's envelope) and the `account_usage` event; a fetch happens only for Settings or when the seed lacks the account, so an open session costs no extra request.
- **Banner name rule:** the account's label with 2+ Claude accounts, else the runtime's name.
- **`reset-ready` Continue is a normal send,** not a new endpoint: S4 clears the limit on a person's message.
- **Kept-out hiding for a person's own session** applies only to accounts explicitly set to Kept out; unconfigured accounts stay offered, or a fresh flow install would hide every account.
- **The Flow tab UI is hand-built on host CSS variables** because extensions cannot import host components today.
- **Main moves demote the previous Main of the same runtime** in one locked write.
- **Spend-down choices 6/12/24/48/72 h;** a stored custom value is kept.
- **The status-bar pre-launch picker moves out of `RuntimeItem`** (one place for one choice).
- **`TurnFailedNotice` is replaced by the banner** for a limited turn (one notice, not two).
- **Flow's automatic countdown is 10 seconds** (the mockup), set by the advisor's `delaySeconds`.
