# Check a saved model at its first executable launch

**Status:** Specification review candidate — implementation not delivered

**Author:** Codex, directed by the project coordinator

**Issue:** DOR-1692

**Source anchor:** cab229a3fdbe06373ea2bebf29b59f9dac47eb37

## Overview

Give confidently new conversations explicit server-owned birth provenance and evaluate a saved model before their first owned outbound inference attempt. Refuse only when a fresh complete list applies to that exact runtime/session/account/payer and positively excludes the choice. Preserve unknown choices, old/ambiguous conversations and already initialized conversations. Existing approved runtime-specific substitution, including DOR-3168, remains its own route with durable notice.

This document specifies intended behavior and exact ownership. Implementation remains outstanding. All implementation, schema migration, affected tests, checks and actual request/no-request proof remain owed. The selected behavior is complete. Implementation and verification obligations below must pass before delivery.

## Background / Problem Statement

DOR-4411 delivered the original permission half of DOR-1692 through explicit bound/hint authority and SQL strictest-mode reconciliation at binding. Stored models remain a separate issue. `RuntimeRegistry.persistSessionRuntime:261` fills missing model/effort but preserves an earlier explicit model without a catalog check. A nullable-runtime settings row is not a new-chat certificate.

Normal browser drafts mint client UUIDs (`resolve-session-for-cwd:172`, New chat hook:32). `create:true` permits creation but also feeds an existing native chat. Registry discovery deliberately tolerates some failures during creation, and nullable findSession APIs do not establish a complete negative. Existing `POST /session-locations` allocates a _folder reference_ deduplicated by owner+cwd. Chat allocation is a separate operation. Native thread creation, turn_start, context records, user-only or error-only history can precede model work. Shared model_request events are not eagerly durable across an open-turn crash.

## Goals

- Stamp genuine new server allocations without binding a runtime, selecting an account, resolving a key, starting a provider or sampling a model.
- Evaluate every newly covered adapter inference path, including a new chat whose metadata already has a runtime owner.
- Preserve compatibility while handoff/acknowledgement is uncertain and for legacy/imported rows without trustworthy provenance.
- Preserve exact concurrent owner/model winners, abort, rekey, account/payer and current permission-origin semantics.
- Return actionable model-selection feedback without wiping a saved choice or creating an orphan dispatch/claim/projector.

## Non-Goals

No cross-runtime default model, ranking, credential probe, change of payer, provider/account feature expansion, catalog refresh programme, native account scanner, model sampling, new authority map, retrospective validation of established chats, or rewrite of DOR-4411. DOR-4488 PR3989 remains the separate picker session-context fix. DOR-3168 is separately ongoing and requires composition at its actual reviewed source. This pin does not include that composition.

## Detailed Design

### 1. Distinct fresh-chat allocation under the existing location route

Add **POST `/api/session-locations/:id/chats`**, a distinct operation in `createSessionLocationsRoutes`. Keep existing POST `/session-locations` and GET `/:id` semantics and owner+cwd dedup byte-for-byte in behavior. The existing wildcard middleware applies to this new subroute. Cross-site refusal and `assessPerson` precede all work. The location-token branch accepts a strict empty request body. It rejects client session id, lifecycle state, runtime, model, account, payer and authorization selectors. The separate registered-agent branch below accepts only a discriminated agent id, never a path or grant.

Resolve `:id` with the same UUID validation and caller-owner lookup as GET. Revalidate its stored canonical cwd with `validateBoundaryOrDorkHome` on every call. Missing/foreign location is 404. Denied boundary is 403. Only then mint the actual conversation UUID on the server and insert a thin durable owner/location-scoped allocation row. Do NOT insert session_metadata or read configured defaults here. The existing first metadata INSERT consumes the allocation atomically and stamps pending-v1 without changing its original INSERT/CLAIM behavior. On a generated-id collision, fail that attempt and retain the existing row without returning a certificate for it. The response is `201 { sessionId, launchRef }`, where launchRef remains the existing folder reference. No filesystem path enters the navigation identity.

Allocation proves birth. Existing launch checks govern inference in the folder and execution as an agent. It does not persist runtime/agent/account/mode/model grants. Normal PATCH, HTTP origin/person/owner checks, credits-choice check, registered-agent validation, place/boundary/room checks, account eligibility and first-write runtime binding still run as before. The allocation or metadata marker is never accepted from JSON. Location-scoped owner checks are not replaced by possession of a session UUID.

Every intentional allocation yields a new id. **No automatic retry** of a non-idempotent allocation. Keep one in-flight promise for the navigation action and retain its acknowledged id across first-send failures. A lost response can leave an inert allocation. It must not start work or count as dispatch/inference. A deliberate later New chat action may allocate another. Do not add a global cleanup sweep or inference-side retry to hide this normal uncertainty. If product requires network-level idempotence, a receipt key/storage design requires a separate scope decision. This operation retains its selected non-idempotent behavior. Valid unconsumed allocations survive restart/reopen indefinitely. Their lifetime has no silent TTL, per-owner chat cap, eviction or automatic retry. There is no concrete draft-delete/owner-delete route in the inspected session routes to attach cleanup to, so this revision accepts inert orphan storage explicitly and does not invent cleanup. A future actual deletion owner may remove its exact allocation in its normal transaction after separate review.

The existing router supplies the required person bar, per-owner location lookup and boundary validation. The new subroute reuses those exact checks. Agent-id-only starts use the distinct registered-agent allocation branch below. Do not force them through an arbitrary-folder boundary or require a new public location token. First-send current agent/place checks remain authoritative.

### 3. Birth storage, atomic first insertion and internal mint owners

Allocation schema: sessionId primary key, version, createdAt and exactly one source discriminator: person-location (ownerId/locationId), person-agent (ownerId/registeredAgentId/recordedRegisteredPath), or internal typed durable source. No model/runtime/permission/account/payer/dispatch fields or second inference lifecycle. The ordinary allocation router creates this row only. Owner+cwd location dedup is unchanged. No generic use of session_started_by: it creates origin/limit/history effects. No single pending-chat column on shared locations: concurrent tabs need distinct allocations.

At an actual first metadata INSERT, consume the exact allocation and stamp pending-v1 in the SAME synchronous SQLite transaction. Keep all existing settings/permission/launch column expressions and INSERT versus conflict-UPDATE branches unchanged. Agent/default and authenticated request reads stay before the transaction. Re-read and validate the exact persisted allocation, durable source identity/generation and all available durable ownership fences INSIDE that same transaction before INSERT and consumption. An earlier read alone cannot authorize transfer. PATCH still inserts only explicit picker fields plus birth and still updates only its explicit patch on conflict. A bind without prior PATCH still takes its seeded INSERT. A bind after PATCH still takes the existing claim. No allocation means legacy/null. No new INSERT merely to stamp birth. An arbitrary existing row on collision is not promoted based on UUID equality: preserve unknown/refuse inconsistent allocation, retain evidence. Consume only after the successful new-row insert, never on a no-op/conflicting existing-row update. Ordinary repeat after completed consumption observes already stamped metadata. Crash before commit retains allocation/no metadata. Crash after commit leaves pending metadata/no allocation. No state where committed metadata lost its birth due to a separate consume. Allocation failure creates no dispatch or model settings.

All twelve direct production metadata INSERT statements and actual internal mint branches are classified in the accompanying census. Shared helpers that may create metadata before binding (permission-person markers and continuation holds) also need first-insert allocation transfer. Restricting transfer to PATCH/bind is insufficient. They must retain their current write/result/error semantics. This requires a cohesive synchronous transaction helper taking a transaction. Discovery stays outside SQL and the existing authority stores remain unchanged.

Internal server births use the same allocation storage's discriminated internal variant for genuine pre-metadata asynchronous gaps. The variant contains the exact server-minted session id plus a typed durable source identity. No fake person/location or catalog/settings/runtime/permission fields. Only actual mint owners create it, atomically with their existing durable owner insertion when present. Immediately atomic true births may stamp their existing metadata INSERT directly. No added lifecycle flags on chat-message, room-seat, task or heartbeat tables. The internal source and restart rules are specified below. Existing legacy durable rows without the allocation are never backfilled from apparent emptiness. This closes the architectural storage choice. Exact code integration and real crash/race tests remain owed.

Recovery/carry-over/rekey are not automatically ordinary blank births. Their existing required identity/retirement/native aliases remain authoritative and preserve source conversation compatibility. A new successor can carry pending only where its real mint owner proves the new conversation. Copied imported settings or alias rows never prove unused. Established old conversation does not become new merely because a runtime canonical id changes. The exact insert/mint tables below classify these branches.

### 4. One versioned lifecycle on existing session metadata

Proposed nullable `model_launch_state` has only `pending-v1`, `attempted-v1`, `established-v1`. Null is legacy/unknown. No catalog, account token, model snapshot or parallel map is persisted here. Migration defaults every existing row to null. It does not infer initialized=false from absent events.

- **pending-v1:** actual server birth is proven and no evaluated outbound attempt was recorded. Binding, model PATCH and native ensureSession leave it pending.
- **attempted-v1:** the gate evaluated a specific current-owner attempt before its outbound edge. Handoff/acknowledgement may be uncertain. This is NOT “request made,” “model ran,” “turn accepted,” or billable usage. A crash before send can leave this state. Preserve compatibility rather than fabricate a response or retry.
- **established-v1:** meaningful owned response/usage was positively observed. Never reward a thread id, context record, user/error-only assistant row, fake start frame or zero collected request as established.
- **null:** retain legacy/import compatibility. Positive actual owned response can establish it, but absence cannot turn it into pending. The ordinary new-app allocation prevents newly created app drafts from falling into this class forever.

A confidently excluded pending attempt refuses without changing model or state. Unknown evidence permits normal execution after recording that evaluation as attempted. It does not pretend confirmation succeeded. If the attempted write fails, refuse before outbound handoff. Existing single-flight/lifetime ownership still serializes actual work. The field is not a second launch lock.

Use current durable rekey machinery to move lifecycle with its verified identity. Existing positive/unknown destination evidence cannot be overwritten as pending. Preserve required recovery/runtime/agent conflict refusal. New carry-over gets new pending birth, never source established state. No restore/destination merge chooses a state simply by enum ordering.

Pure refusal writes no model. Compare exact canonical owner and current model value at use. If changed since discovery, produce a bounded stale-input refusal and leave the winner untouched. ## Resolved Design Decisions

- Metadata binding performs no new catalog/native discovery. The actual executable owner evaluates fresh applicable complete evidence, or treats it as unknown.
- Server birth uses three disjoint sources in one durable allocation table: person-location, person-agent, internal typed source. Allocation creates no metadata or settings. Original INSERT/CLAIM seeding remains unchanged.
- Normal agent-id-only birth uses the current person-gated registered-agent branch. Its existing folder admission remains unchanged and its allocation retains the real registered-agent source. Existing direct-seat identity and explicit hub relay remain intact.
- One intentional/in-flight non-idempotent allocation. No automatic retry, chat cap, TTL or silent eviction. Inert abandoned allocations are the accepted tradeoff. No network-level dedup or generic cleanup programme is in scope.
- Pending records evaluation before outbound. Attempted preserves uncertainty. Only attributable observed response establishes. If a runtime cannot safely attribute an observed response, it stays attempted/uncertain with compatibility and no new refusal. This is the selected safe outcome.
- No source/model/profile probing or generated request to resolve uncertainty. DOR3168 approved same-account substitution and DOR4488 context consumers remain separately owned contracts. Integrate exact landed versions before final implementation proof.
- Original DOR4411 explicit permission authority and claimed-mode normalization remain acceptance requirements and retain their existing strength.

## Collision, first-write and crash rules

Allocation primary key prevents duplicate birth ownership. Source discriminator+exact source key must match idempotent continuation of the SAME owner. Collision with different source or existing ambiguous metadata refuses birth, never adopts it. Public UUID cannot consume internal allocation. Internal callers cannot manufacture public owner/location. Check congruence in the already authorized owner flow. Possession of a key supplies no authorization. No account/runtime choice is changed by failure.

All twelve existing metadata INSERT sites in the table below remain classified. Perform exact-source allocation check, original INSERT and consume inside one synchronous database transaction. External agent/config reads remain before SQL. A helper that may catch storage failure cannot separately commit consumption. Actual inserted row receives pending-v1. Conflict UPDATE preserves existing lifecycle and all existing original permission/settings expressions. Crash before commit retains allocation/no new metadata. After commit metadata pending/allocation absent. Concurrent different winner never inherits pending based solely on UUID equality. An existing birth-stamped row plus absent allocation records a completed transfer. Its original birth remains unchanged.

Rekey with no destination moves lifecycle and any still-unconsumed allocation/source linkage atomically with authenticated actual owner metadata/ledger changes. Existing destination unknown/established wins conservatively. Do not enum-order merge pending into it, reset attempted to pending, or mark recovery old-id alias independently fresh. No async SQLite transaction or extra model/network/catalog step.
