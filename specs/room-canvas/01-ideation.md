# Canvas and Browser in rooms

**Slug:** room-canvas
**Author:** Claude (Fable, orchestrating; directed by Dorian)
**Date:** 2026-09-11
**Tracker:** DOR-1995 (umbrella) · project "Canvas and Browser in Rooms"
**Research:** [`research/20260911_canvas-browser-in-rooms.md`](../../research/20260911_canvas-browser-in-rooms.md) — the inventory, the three findings, and the Q1–Q5 answers this ideation turns into decisions. Read it first; this document does not repeat it.

## 1) Intent & Assumptions

- **Task brief (operator, 2026-09-11).** An agent session's right panel has a Canvas (documents, widgets, diffs) with an embedded Browser inside it, which the agent can drive and read back. Rooms have neither. Add a **Canvas tab and a Browser tab to rooms, the same way sessions have them**, so any agent in the room can push documents and open pages, and the other agents and people in the room know the state changed. Then carry the research recommendations end to end: fix the drift already present, make the state server-owned, teach agents to read the table, and add what only a room canvas can do.
- **Assumptions (logged, per the calibration ladder):**
  - A1. The operator's 2026-09-11 direction ("execute everything we've discussed … fully autonomously") stands in for the project-creation gate and for the review gate's human approval on each PR; the adversarial review per `REVIEW.md` is the gate that blocks.
  - A2. "A tab for Canvas and a tab for Browser … the same way we have them in Agent Sessions": sessions today have **no** Browser tab (the browser is a document type inside the Canvas tab). To make the two surfaces the same, the Browser becomes its own tab on **both** routes. Session behaviour changes accordingly and the workbench guide, the changelog and the e2e specs move with it.
  - A3. Room canvas state is **server-owned** (D1). Session canvas state stays in `localStorage` in this programme; migrating it to the same server store is the first item of the follow-on spec (D17), not a precondition.
  - A4. A canvas change **never** triggers a turn (D2).
  - A5. The operator's direction overrides the flow WIP cap for this programme; machine load, not the cap, bounds concurrency (two implementers and one reviewer at a time).
- **Out of scope (this spec):** browser driving tools (click/type/read page), recording, screenshots posted as attachments, codex/opencode parity for `get_ui_state` and `browser_*`, session canvas migration to the server store, follow mode, document-anchored threads, merge-preview accept-to-merge, CRDT or multi-cursor editing, canvas over the `CommunityAdapter` port, structured canvas content across chat bridges. All of these are the follow-on spec `canvas-agent-seat` (D17).

## 5) Research

Carried in full in `research/20260911_canvas-browser-in-rooms.md`. The options considered and rejected, in brief:

1. **Register the Canvas tab on room routes and reuse the session store.** Rejected: each viewer would see their own private `localStorage` canvas and call it shared (research §1.6).
2. **New `room_canvas_*` verbs in the room capability domain.** Rejected: forks the vocabulary every skill and template already emits (`open_canvas`, `browser_navigate`); D3 routes the same verbs by turn context instead.
3. **Canvas change as a room trigger reason with its own dials.** Rejected: charges every agent for listening (E7); the merge precedent (ADR `260829-115625`) shows a shared-state change that wakes nobody works.
4. **Canvas state on `signal` frames.** Rejected: signals are lossy and never replayed by design; state needs `seq` and the snapshot.
5. **Blintz for room file documents.** Rejected already by `specs/project-rooms` (provenance); source editor for file-backed documents, Blintz for generated ones.

**Recommendation:** server-owned, room-scoped canvas documents on the room stream; same `control_ui` verbs routed by turn context; awareness through context, a coalesced notice and mentions; a dedicated Browser tab on both routes; the drifts fixed first.

## 8) Open questions for SPECIFY

- Q1. Frame kind versus body: is `canvas` a new `RoomEvent` kind (recommended: it is state, not conversation) or a `RoomEntryBody.canvas` structure on a notice entry? SPECIFY resolves; the notice entry (D2b) exists either way.
- Q2. `editingBy` heartbeat interval and TTL for server-side edit protection (D6). Recommended: 15 s heartbeat, 45 s TTL, cleared on save or close.
- Q3. Whether the Browser tab on `/session` keeps a "Canvas" affordance for `mcp_app` documents that are pages (they stay in Canvas: they are apps, not pages).
