# The canvas agent seat

**Slug:** canvas-agent-seat
**Author:** Claude (Fable, orchestrating; directed by Dorian)
**Date:** 2026-09-12
**Tracker:** DOR-2004 (umbrella) · project "Canvas and Browser in Rooms" · follows DOR-1995 (`specs/room-canvas/`)
**Research:** [`research/20260911_canvas-browser-in-rooms.md`](../../research/20260911_canvas-browser-in-rooms.md) §2 (Q1, the session-side extensions), §4 (what only a room canvas can do), §5 (the 10x list), §6 (what was not asked). ## 1) Intent & Assumptions

- **Task brief (operator, 2026-09-11).** "Execute everything we've discussed, as well as any additional recommendations you have, fully autonomously." The room canvas programme (DOR-1995) delivered the table; this one delivers the seat: an agent that can act in the embedded browser and prove what it saw, the same canvas on every device and readable by the agent, and the room features that make the table collaborative (follow, discuss, merge from the diff).
- **Assumptions:**
  - A1. Everything `specs/room-canvas/02-specification.md` shipped is the base: `canvas_documents` (scope-keyed, `room:<id>` today), `RoomCanvasService.apply` as the single writer with two callers, the `applied` stamp through the normalizer, the `canvas` room frame, `read_canvas` as a room capability, `treeKind`/`aheadOfMain` on rows, the two-view client store with `heldUpdate`, and the Canvas/Browser tabs on session and room routes (P2b) with pins and tab presence (P3).
  - A2. The operator's direction stands in for the project gate and the per-PR human approval; the adversarial review per `REVIEW.md` is the gate that blocks.
  - A3. Nothing here widens what an agent may do on the machine: browser driving acts inside a sandboxed preview frame DorkOS already serves; attachments an agent posts are files it could already write; merge-to-main stays server-mediated and operator-initiated.
  - A4. Money: no path here spends against a model or an external provider in tests; the browser tools are exercised through the test-mode runtime and served fixtures.
- **Out of scope:** CRDT or multi-cursor editing; canvas over the `CommunityAdapter` port; structured canvas content across chat bridges (a link line is the bridge's shape); WebM/video recording (the GIF path is the first step; see `research/20260611_agent_browser_video_recording.md`); driving external sites (never instrumented); an agent following another member (people only).

## 2) Pre-reading Log

- `specs/room-canvas/02-specification.md` §1–§9 and the four ADRs `260911-200301..4`: the base this extends; §5.7 (id story), §8.1 (reader rule), §9.1 (two views).
- `apps/client/src/layers/features/canvas/model/use-devtools-bridge.ts` and `apps/server/src/services/workbench-serve/devtools-shim.ts`: the shim talks only to `window.parent`; the parent forwards `devtools_capture_request` into the frame and ingests `capture-result` keyed by `requestId`; first ingest wins across several previews (v1 limitation). Driving tools ride the same channel.
- `apps/server/src/services/runtimes/claude-code/mcp-tools/devtools-tools.ts`, `services/session/devtools-capture-store.ts`: the request/await pattern (`awaitScreenshot(requestId, 8_000)`), byte budgets, the raster-only screenshot gate.
- `apps/server/src/services/runtimes/shared/dorkos-mcp-injection.ts`, `services/core/external-mcp/register-from-definitions.ts:35-39`, `services/core/capabilities/`: codex and opencode reach DorkOS through the loopback `dorkos` server, which exposes capability-registry `in-session` capabilities; `control_ui`, `get_ui_state` and `browser_*` are hand-registered claude-code tools with no definition entry, which is why they are missing there. Parity means registering them as capabilities whose handlers key the capture store by the calling session.
- `specs/room-attachments/02-specification.md` Open Question 4 ("agents uploading files") and ADRs `260807-233815/233816`: attachments are rows referenced by an entry, hardlinked into each agent's cwd.
- `specs/project-rooms/02-specification.md` §3.4–3.6 and ADR `260829-115625`: worktrees per (room, agent), server-mediated merge that wakes nobody; P4 ("PR-style review gates") left as follow-up — the merge preview is that follow-up.
- `apps/client/src/layers/features/diff-review/`: per-hunk accept/reject writes to disk through the files route with optimistic concurrency.
- `specs/room-presence/02-specification.md`: `signal` frames, published only as a consequence of real state — follow mode rides them.
- `research/20260611_agent_browser_video_recording.md`: per-action keyframes are the cheap honest recording; GIF size scales with action count.

## 5) Research

Carried in the research report. The options that were considered and set aside:

1. **Driving the browser through Playwright or Chrome DevTools Protocol on the server.** Rejected: the preview renders in the person's browser, not on the server; the shim already lives in the page and already round-trips captures; a server-side browser would be a second, unshared rendering.
2. **Video (WebM) recording first.** Deferred: needs `MediaRecorder` in the parent over a cross-origin frame or a server-side browser; per-action GIF keyframes reuse the screenshot path and bound size by action count (research 20260611).
3. **Keeping the session canvas in `localStorage` and only syncing "open" state.** Rejected: it keeps two truths; the room canvas already proved the server-owned shape and the migration retires a whole persistence path.
4. **A dedicated `attach_to_room` tool.** Rejected in favour of an `attachments` field on `post_to_room`: the spec for attachments made "the post names them by id" the contract, and an agent's file is a path in its own cwd.
5. **Agents following members (follow mode for agents).** Rejected: an agent that "follows" has nothing to follow with; `read_canvas` already tells it where people are (P3 presence rides context).

**Recommendation:** six phases (§7), each one PR, in the dependency order given.

## 6) Decisions

| #   | Decision                           | Choice                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Rationale                                                                                                      |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| B1  | Session canvas moves to the server | `canvas_documents` gains the `session:<sessionId>` scope. A `CanvasService` generalises `RoomCanvasService.apply` over scope (one writer, the same ledger/cap machinery with the session cap unlimited or high, the same stamp). The session stream's snapshot carries the session's documents; the per-session `canvas` events ride the durable session stream (they can carry `seq` there — the session stream is seq'd by design). The client store keeps its shape (two views, `heldUpdate`, LRU) but hydrates from the snapshot and writes through to `POST/PATCH/DELETE /api/sessions/:id/canvas/...`; the `localStorage` slice is retired with a one-time import (first load of a session with a local entry and an empty server table posts the documents, then deletes the entry). `get_ui_state` becomes a live read; `read_canvas` works on a session (owner-only; sessions are reachable by no agent but their own). DirectTransport implements the new methods against its in-process store.                                                                                                                                                                                                     | One truth, every device, and the agent can read what you see. The room canvas proved the shape.                |
| B2  | Browser driving tools              | `browser_click` (by accessible role+name, by visible text, or by CSS selector), `browser_type` (into a focused or selected field), `browser_press` (a key or chord), `browser_scroll` (to an element or by amount), `browser_wait_for` (text, selector, or network idle, bounded ≤ 10 s), `browser_read_page` (the accessibility tree as text, byte-capped like console reads). Each is a `devtools_capture_request`-shaped round trip: the server mints a `requestId`, the client forwards the command into the frame, the shim performs it and posts a result the client ingests; timeouts resolve to a plain failure, never a hang. Instrumented previews only (served files, preview-listener origins); external sites and directly framed dev servers return `NO_PREVIEW_NOTE`. Every tool returns what it did and a one-line page summary (title, URL, focused element). Tier `act`, reach `client-only`, auto-allowed with a justification sentence in the table (acts inside a sandboxed, opaque-origin frame DorkOS serves; cannot reach `/api/*`). Multi-preview: requests target the ACTIVE browser document; the client answers from that frame only (closes the "first ingest wins" limitation). | The seat: an agent asked "check the checkout flow" can act, read, and screenshot in one turn.                  |
| B3  | Recording                          | `browser_record_start` / `browser_record_stop`: while recording, every driving tool captures a keyframe after it acts (the screenshot path), plus one on start and one on stop; the server assembles an animated GIF (a small pure-JS encoder, no native deps) into the session cwd under `.dork/.temp/recordings/<id>.gif`, bounded by frame count and bytes, and returns the path and an image block. In a room turn the GIF may be posted as an attachment (B4).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Per-action keyframes reuse the screenshot path and bound size by action count (research 20260611).             |
| B4  | Agents post attachments            | `post_to_room` gains `attachments?: string[]` (paths inside the agent's cwd, boundary-checked). The server copies each into the room's attachment store through the existing upload path and binds the rows to the entry in the same transaction; members get the same inline previews and chips; every other agent gets them hardlinked as today. Byte caps follow the human upload route. This resolves room-attachments Open Question 4.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | "Agents show their work": a screenshot or a recording lands in the log where the second agent can read it.     |
| B5  | Runtime parity                     | `get_ui_state`, `browser_read_console`, `browser_read_network`, `browser_screenshot` and the B2/B3 tools are registered as capabilities in a `ui` domain (`in-session` + `external`), handlers keyed by the calling session (the loopback `dorkos` server knows it), so codex and opencode get the same tools with the same names. The claude-code in-process registrations become thin wrappers over the same handlers (one implementation). `control_ui` stays as is (codex already has it via `dorkos_ui`; opencode gains it through the same domain). Censuses, tiers, the auto-allow table, `GUARDED_READ_ONLY_TOOL_NAMES` and the capability conformance suite are updated in the same PR.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | One place for every agent means every agent gets the same seat.                                                |
| B6  | Follow mode                        | A person can follow another member's browser view in a room: a toggle on the Browser tab ("Follow Ana"); the followed member's client publishes navigation and scroll position of its active browser document as `signal` frames (debounced, only while a follower exists, only from a real client state); followers' frames navigate and scroll accordingly. Off by default, people only, never persisted, cleared on blur/close. Agents are never followers or followed (an agent's browser is a document, not a view).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | "One member drives, others follow" without streaming pixels; the signal channel exists for exactly this shape. |
| B7  | Document-anchored threads          | "Discuss" on a canvas tab opens the document's thread: the first time, a system root entry naming the document is posted (merge-shaped, wakes nobody) and its id stored on the row (`threadRootEntryId`); thread replies are ordinary thread entries; a thread turn's context includes the document's metadata (and content for a `read_canvas`-eligible reader, under the reader rule).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Commenting on a document is replying in its thread; threads exist.                                             |
| B8  | Merge preview and accept-to-merge  | In a room with a repo, `open_diff` for a worktree document renders worktree-vs-main (the row's `treeKind`/`aheadOfMain` decide). The operator (never an agent) gets "Merge into the room" on the diff header: it calls the server-mediated merge for that agent's worktree (`room-merge-service`), which posts its usual merge line and wakes nobody; per-hunk reject on such a diff writes to the worktree copy through the existing files path, so "reject two hunks, then merge" is one flow. Refused when the worktree is behind main (the merge service's own rule; the sentence tells the operator to ask the agent to catch up).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | The P4 review gate of project rooms, with parts that exist.                                                    |
| B9  | Explicit `control_ui.target`       | `control_ui` gains `target?: { room: string }`. From any turn, an agent may put a document on a room it is a member of; the room's cap for a synthetic `turnId` derived from the calling turn applies; refused for non-members with a sentence; the coalesced line is posted by `finishTurn` of that synthetic turn when the calling turn ends (the runner knows). Room turns without `target` behave exactly as today.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | An agent in a DM can put a chart on `#team`.                                                                   |
| B10 | Bounds, honesty, etiquette         | Driving tools count as work, not speech; recording is bounded by frames and bytes; attachments by the upload caps; follow mode publishes only while somebody follows. No new trigger anywhere. Every tool result says what happened; a timeout is a plain failure.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | "Bounds are mechanisms, never prompts."                                                                        |

## 8) Open questions for SPECIFY

- Q1. Does the session `canvas` event ride the existing `ui_command` shape (with `applied`) or a new session event kind? Recommended: a new `canvas` session event kind mirroring the room frame, so the client hydrates both scopes with one reducer; `ui_command` keeps its role as the reveal trigger.
- Q2. GIF encoder: pick a pure-JS, dependency-free encoder already in the tree or the smallest MIT one; name it and its size budget.
- Q3. `browser_read_page` shape: a11y tree flattened to lines (`role "name" [state]`) with a byte cap; confirm the shim can walk `aria` without a library.
