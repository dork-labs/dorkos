**Words.** A **cloud computer** is a cloud agent computer: the computer side of DorkOS, in a box the hosted service starts and stops. Its **home** is the person's DorkOS in the cloud (the server that code and the hosted contract call a "hub"), which holds its agents' records, rules, memory, schedules and chat lists (OneHome rule 2). **The starter** is the piece of the home that asks the hosted service for a start (§4). **Busy** is the computer's report of itself under `PUT /v1/agent-computers/self/activity` (§5.1).

## The short version

- **One contract.** A cloud computer speaks step 8's contract to its home and nothing else. This spec adds no operation to it. It adds, as §14.2 lists in full: the refusal `computer_stopping` and the status field `stopping: true` under the feature `computer.stopping`, required of a cloud computer; the `linkedVia` value `home`, with its one way in through the home's own `https` link route; and the cases of the wait `computer_away` for a cloud computer that is stopping or that its owner stopped. The calls that are specific to the cloud are the ones `packages/cloud-api` defines (start, stop, the link code, the assignment, the busy report), the one route Z1 adds (the home's own busy report), and item 13's wake asked for with a computer's key, which Z1 widens to cloud computers.
- **A computer starts for work, never for looking.** A run for an agent on a stopped cloud computer is accepted, waits as step 8 says (`computer_away`), and the home asks for one start however many runs wait. A list, a sidebar or an opened chat never starts one.
- **The hosted service stops an idle computer** from the computer's own busy report. The home stops one only when its owner presses Stop, and asks first when that would end live work.
- **Each stop reason is said plainly** on the computer, its agents and their waiting messages (§5.4).
- **No person types a code.** The home makes its owner's computer, mints the link code, and records the link as made for the owner by the home. That widens rows Security signed for step 8, which §9 asks Security to sign again.
- **The computer boots step 6's computer entry**, runs OpenCode as a second operating system user, and reaches models only through a short-lived token it mints with its own key.
- **Every older step has a verdict** (§10).

## Goals

- A person can make an agent that works on the cloud, message it any time, and have it run while their Mac is off.
- A person with no computer of their own gets DorkBot on a cloud computer, after the card step the hosted service asks for.
- No work is lost or refused because a computer was stopped; every wait says why.
- A cloud computer costs hours only while it works: it stops when idle, and only for work does it start.
- Each step ships alone and leaves the app working, and every proof runs against a test version of the hosted service in this repo.

## Non-goals (out of scope)

- The contract between a home and a computer: step 8. This spec uses it and changes none of its invariants; the few additions it needs are listed in full in §14.2, and the signed rows it widens are named in §9.
- Team spaces (item 15). Every cloud computer here is its owner's, linked through the owner's own home.
- A second computer for one person. The contract allows more (`cloudComputers`, `packages/cloud-api/src/billing.ts:130-138`); the app makes one and uses one.
- Moving an agent between homes, and changing an agent's "Works on" after it is made (OneHome rule 4).
- A copy of a computer's chat history on the home (§15, question 1).
- The image's build and hosting. The hosted side builds the image from what this repo publishes.
- Prices and plans. This spec names only what `packages/cloud-api` exposes and what `meta/ROADMAP.md` says in public words.
- Claude Code and Codex on a cloud computer.

**Why this spec is short.** Step 8 already specifies the channel, the computer record, placement, the run on another computer, the waits, lost contact and the computer entry over the wire, and Security signed its trust rows. A cloud computer is one more computer on that contract. What is left is the part that only a computer the hosted service runs has: who starts it, when it may stop, how it links with nobody at the keyboard, what it boots, and how the first one is made. This spec points at step 8 for everything else and restates none of it.

## 4. Starting

### 4.1 When the home asks for a start

The home asks for a start in three cases only (H1):

1. **A run waits for a stopped cloud computer.** Admission puts a run for an agent placed on a computer that is not present in the wait `computer_away` (SCC §6.4). When that computer's record has `kind: cloud`, the starter (`services/space-computers/cloud/starter.ts`, new) asks the hosted service to start it, with the reason `beat` when the run's origin is a schedule or a beat, and `turn` otherwise. The reason is for metering only (`hubs.ts:382-394`).
2. **The owner presses Start** on the computer's line or on a chat whose history is on the computer (§6.2). The reason is `viewer` when pressed from a chat, else none.
3. **Once, right after the home makes the computer** and hands over its link code (§6.1), so the computer can boot and link. No reason is sent.

A schedule or a beat that comes due is a run like any other: it is accepted, waits and causes the start. **There is no other trigger.** A read that reaches a stopped computer throws `REMOTE_COMPUTER_AWAY` (SCC §6.2) and the app shows the asleep state; it never calls the starter. An agent cannot press Start; it can cause a start only by making work for a cloud agent (a task, a send), which is case 1 (§9).

### 4.2 The sequence

1. A run is accepted, by whatever door (a message, `agent.send`, a schedule, a beat, a room). Its words wait where step 5 and SCC §6.4 put them; nothing is refused.
2. Admission finds the computer not present and sets `computer_away`.
3. The starter checks whether it already has a start outstanding for that computer. **If it has, it does nothing: one start, however many runs wait** (CC2).
4. It checks the computer's last stop (§4.4). For a stop by the owner, it asks only for a run accepted after that Stop. For a stop for credits, a hold or a suspension, it asks once for each new run, never on a timer (§4.3).
5. It calls `POST /v1/computers/{cloudComputerId}/start` with the home's key, records "start outstanding" in memory with the time, and shows the computer as starting.
6. **It reads the answer's state and assumes nothing.** `starting` or `running`: it waits for the computer's status. `stopping`: it waits until a read of the list shows `stopped`, then asks again (a start of a stopping computer may not be honoured; what it answers is a question for the hosted side in Z1). `stopped` with a stop reason: §4.3. `failed`: §4.3.
7. The computer boots (§7), dials its home (W4) and sends its first `computer.status`. That status releases `computer_away`, as SCC §6.4 says, and every waiting run moves on through admission in the order of step 8's queue; no batch of due work is made at start (§15, question 2). The starter clears "start outstanding".

**While it starts**, each waiting message and the chat show one line, "Starting the cloud computer…", with the wait. The older note's `503` with `Retry-After` is dropped (§10, §14).

### 4.3 When a start does not work

| What happens                                                                                                              | What the starter does                                                                                                                  | What the person sees                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| The answer is a problem `entitlement_required` (a card or a larger allowance is needed)                                   | Asks once more for each new run and for the owner's Start; no timed retries                                                            | "Needs a card to start." with the service's own words below and the card step (§6.3)                        |
| The answer is a problem `balance_exhausted`, or the computer reads `stopped` with `out_of_credits`, `held` or `suspended` | The same: one ask for each new run, one for the owner's Start, none on a timer. So adding credits and then sending a message starts it | The line for that reason (§5.4)                                                                             |
| The answer is `stopping`                                                                                                  | Waits for `stopped` on the list (read at most once every 10 seconds), then asks once                                                   | "Stopping. Starts again when this is done."                                                                 |
| The answer is `failed`, or no first status arrives within 5 minutes of the start call                                     | Records an event on the computer record; asks again after 30 seconds, doubling to at most 15 minutes, while any run waits              | "The cloud computer did not start. Trying again." The person may remove waiting messages, as from any queue |
| The home restarts with runs waiting                                                                                       | The boot scan of §4.4                                                                                                                  | Nothing new: the waiting lines stay                                                                         |

Five minutes covers a cold boot of the image with room to spare; a start that takes longer is shown as not working rather than left silent. No run is ever cancelled by the starter.

### 4.4 What the starter keeps, and the boot scan

- **In memory:** "start outstanding, since when" for each cloud computer. **A start counts as outstanding for at most 5 minutes after each start call**; the gaps of the retry backoff (§4.3) do not count. A computer that the list reads as running but that never dials stops counting as outstanding after those 5 minutes, so it does not keep the home awake (§8.4).
- **On the computer's record** (SCC §8, in its `events` list, newest first): each stop the home learns of, with its time and reason, and whether it was the owner's own Stop. The home writes it when the owner presses Stop (§5.3), and when a read of the list shows the computer `stopped` with a reason it has not recorded. The starter reads the list after each start answer, when the computer's presence ends, and when a person opens the computer's line, at most once a minute.
- **The waiting runs** are step 5's run records and step 8's queue rows, already saved, so a restart of the home loses none.

**The boot scan.** At boot, the starter first reads the hosted service's list of computers and records any stop it had not recorded. Then, for each `cloud` computer with runs waiting `computer_away`, it asks for one start **only if its last stop allows it**: `idle`, `time_limit`, `failed`, or never started. **Any `requested` stop counts as the owner's Stop**, at the time the contract gives for it (`stateChangedAt`, `hubs.ts:308`), also when the home did not record it itself. The starter does not start a computer its owner stopped, or one stopped for credits, a hold or a suspension. Runs that were waiting at the owner's Stop stay waiting until the owner presses Start or a run is accepted after the Stop; such a run starts it at boot like any other. A computer that reads `stopping` is handled as in §4.3.

## 5. Stopping

### 5.1 What busy means, and when the computer says it

The computer is **busy** while any of these holds:

- it holds a live run (its status's `held`, SCC §5.9), except a run that has only been waiting on a person's answer for longer than the bound below;
- a run has registered background work whose copy is still renewed (SCC §5.6, the background phase);
- a fact or record is still in its outbox (`owed`, SCC §7.2).

The computer entry's activity reporter (`services/cloud-computer/activity.ts`, new, computer side) sends `PUT /v1/agent-computers/self/activity` with `busy: true` the moment it becomes busy and every 5 minutes while it stays busy (half the 600-second hold, `hubs.ts:596`), and `busy: false` the moment it stops being busy. A failed report is sent again with the same backoff as the dial (SCC §4.3). The home is not asked: the computer knows its own runs.

**Busy is said before new work starts.** When its last report was `busy: false`, when it has sent none since it booted, or when its last `busy: true` has expired, the computer answers a `turn.start` only after a `busy: true` report has been answered `204`. Z1 makes this safe with a rule of the contract (§8.4): after the hosted service answers `204` to `busy: true`, it does not begin an idle stop until that report expires; once a stop has begun, it answers `busy: true` with a problem, never `204`. So a computer that got `204` takes the turn, and one that got a problem, or the stop signal first, refuses it as §5.2 says. If the hosted service cannot be reached for 10 seconds, it answers the start anyway: a stop needs the hosted service too. **The cost:** a computer that was idle adds one round trip to the hosted service before its first reply, and up to 10 seconds when the service cannot be reached.

**A run waiting on a person keeps the computer busy for 30 minutes.** The bound counts from the run's `waiting_on_person` fact, on the computer's steady clock, and is cleared by `resumed_from_person`. Thirty minutes is long enough to answer a card the person was told about, and short enough that a question nobody answers does not keep a paid computer on for hours. Past it, that run alone no longer makes the computer busy, and the hosted service may stop it after its idle window.

**Such a run is not answered later; the person continues it.** An answer cannot reach a process that is gone. When the computer stops, the run ends with step 5's `shutdown` ending (§5.2), its card is withdrawn, and the chat shows the "slept while this waited on you" line of §5.4, with step 5's way to continue (its §7.4, "Send a message to continue"). An earlier draft of this spec said such a run was "recovered when the answer comes"; that is replaced, because no process is left to take the answer.

### 5.2 The stop sequence, and work that meets it

The hosted service stops a computer with SIGINT, and the computer exits within five seconds (`hubs.ts:51-53`). **On SIGINT the computer entry does four things, in order:**

1. **It takes no new turn.** Every `turn.start` from then on, and any it was holding for the busy report (§5.1), is answered with the refusal `computer_stopping` (new, §14.2). The home puts the run back to `queued` (step 5's transition 8), as it does for `chat_busy`, and it waits `computer_away`. It is not a fault and the run is never cancelled. **It is not lost contact:** the computer said no before it took the turn, so it wrote no `started` fact and handed nothing to a runtime; the home has an answer, so step 8's rules for a start with no answer (SCC §5.2, steps 5 and 7) do not apply.
2. **It ends each live run** with the ending `shutdown` (step 5 §4.4) and delivers those `ended` facts over the channel; whatever it cannot deliver stays in its outbox on disk for its next boot.
3. **It says goodbye:** a last `computer.status` with `stopping: true` (new, §14.2). The home ends the computer's presence at once, not after the 90-second presence window, so a run that arrives next waits `computer_away` without being sent.
4. **It exits.**

On the home:

- **A `shutdown` ending** for a run of a cloud computer is decided at once by step 8's decide step (SCC §6.5, amended in §14.2), by step 5 §7.3's rules: a run that was waiting on a person continues nothing (§5.1); a run whose runtime cannot continue a turn (OpenCode declares `continuesInterruptedTurn: false`, `services/runtimes/opencode/runtime-constants.ts:71`) continues nothing; a runtime that can gets one continuation run, which waits `computer_away` and starts the computer like any other run. An open card for the run is withdrawn. **The home cannot know the hosted stop reason when the ending arrives**, so the chat shows one fixed line for any `shutdown` ending on a cloud computer, with two variants only (§5.4): "slept while this waited on you", when the run was waiting on a person, and the time limit, which **the home** picks once the hosted list reads `time_limit` for that computer (§4.4's read when its presence ends); until then the general line shows, and the home then replaces it. These replace step 5's restart lines for a cloud computer (§14.2).
- **The goodbye status** decides any run left `starting` by SCC §5.2 step 6's rule for the same boot: not held and nothing owed, so its start is reopened, finds the computer not present, and the run waits.
- **If the facts could not be delivered** (the channel was down), step 8's lost-contact rule applies unchanged (SCC §5.2 item 7), with its own line.

**No run that reaches the home during a routine idle stop is lost.** An idle stop happens only when the computer reported not busy (§5.1), so it holds no live run and owes no fact. A run that arrives then meets one of four moments, each with one answer:

1. Before the stop has begun: the computer reports `busy: true`, gets `204`, and takes the turn; the contract rule of §5.1 keeps the hosted service from stopping it until that report expires, and the computer keeps renewing it while it works.
2. The stop had already begun when `busy: true` arrived: the hosted service answers with a problem, the computer does not take the turn and refuses it `computer_stopping`.
3. Between SIGINT and the goodbye: refused `computer_stopping`.
4. After the goodbye: never sent.

In cases 2 to 4 the run goes back to `queued` or never leaves it, and waits `computer_away`; the starter asks again once the computer reads `stopped` (§4.3). None of those runs was handed to a runtime, so none can end as lost contact (which needs a run the home sent and heard nothing back about) or as a dead process (which needs a run the runtime held).

So a run waiting on a person for two hours: busy for 30 minutes; then not busy; the hosted service stops the computer after its idle window; the run ends `shutdown`, its card is withdrawn and the chat shows the "slept while this waited on you" line; the person's next message starts the computer.

### 5.3 The owner's Stop

One control on the computer's line, for the home's owner only (§9).

- **No live run:** the home records the Stop on the computer's record (§4.4), calls `POST /v1/computers/{id}/stop`, and the line shows "Stopped by you. Starts again when messaged."
- **Live runs:** a dialog says "Stop the cloud computer? 2 replies in progress will end." with Stop and Cancel. On Stop, the home records the Stop, stops each live run through the turn port's `stop` (SCC §5.2, `turn.stop`), waits for each receipt or 10 seconds, whichever is first, and only then calls the hosted stop. Cancel does nothing.
- **From the moment the Stop is recorded, the home sends that computer nothing new.** No `turn.start` goes to it, even while it is still present: a new run waits `computer_away` (§14.2 amends step 8's wait for this). Once the hosted list reads `stopped`, the starter asks again only when a new message arrives or the owner presses Start; while it reads `stopping`, it waits as §4.3 says.
- **Waiting messages** at the moment of Stop stay queued and are not a reason to start again, also after the home restarts (§4.4). The dialog says "3 waiting messages will wait until it starts." A run accepted after the Stop starts it as usual, once the list reads `stopped`. To keep agents from working, the owner pauses them (step 5 §4.7), which is a different control.

The owner's Start is the same line's other control: it asks the hosted service for one start (§4.1), and the waiting runs then move on.

## 6. Linking, the first computer, and what a person sees

### 6.1 Linking, with nobody typing a code

The home links the computer when it makes it, through `packages/cloud-api`, on its owner's behalf:

1. **The owner asks** for a cloud agent (§6.3) or finishes onboarding's card step (§6.4). This is the owner's own action on the home, from their signed-in session.
2. **The home makes the computer**, if it has none: `POST /v1/computers` with an `idempotencyKey` the home saves before it sends, so a retry never makes two (`hubs.ts:332-338`). After a refusal that the card step lifts (`entitlement_required`), the home uses a new key: the contract does not say whether a refused key may be reused, and Z1 asks.
3. **The home mints a link code** in its existing store (`services/core/hub-relay/link-codes.ts`, which records who minted each code), bound when minted to the role `agent-computer`, the kind `cloud` and that `cloudComputerId` (W2's role-bound code, SCC §4.2). The minter recorded is the owner for whom the home minted it, and the code is bound to `linkedVia: 'home'` (a new value of step 8's `linkedVia`, §14.2): the home made this link for its owner.
4. **The home hands the code to the hosted service**: `POST /v1/computers/{id}/link-code` with its own key (`hubs.ts:459-533`). It then asks for one start with no reason (§4.1, case 3).
5. **The computer boots** (§7), reads its assignment with its own key (`GET /v1/agent-computers/self/assignment`), checks that `ownerAccountId` and `issuer` are the ones it was first given (on its first read, it records them), and redeems the code at `hubOrigin`'s link route, sending the public half of a signing key it made itself. **A code the home minted for itself has one way in:** the home's own `https` front door, its link route (`routes/hub-link.ts`); a redemption through any other pipe is refused and spends no code (§14.2 amends step 8's rule that binds a code to its pipe).
6. **The home checks the code, pins the key and mints the record** (SCC §8): `kind: cloud`, `cloudComputerId`, `linkedBy` = the owner for whom the home minted the code, `linkedAt`; the `LinkedComputer` row (and so the computer's pin) carries `linkedVia: 'home'`, set from the code, never from what the computer sends (SCC §4.7). The signed link answer names the role. The computer dials (W4) and sends its first status.

So step 8's rules for "a computer its owner linked" apply to it (SCC §5.3, read from `linkedBy`). Step 8's signed rows assumed a person who minted a code; this widens them to a link the home made for its owner, and §9 asks Security to sign them again. The person never sees or types a code.

**Codes that do not arrive.** Link codes live in memory and a restart of the home voids them (`link-codes.ts`). A computer record that is made but not yet linked keeps a "link pending" row on the home; at boot, and when a start for it gets no dial within 5 minutes, the home mints a fresh code and hands it over again (the hosted side keeps one live code per computer). **A second redeem** for a computer already linked is the security event the contract names (`hubs.ts:556-561`): as the contract says, the home unlinks the computer, records it on the record's events, tells the owner ("Your cloud computer was linked twice, so it was relinked with a new code."), and mints a new code and hands it over. **The computer learns of it** when the home refuses its pin: its next dial is refused, so it drops its pin, reads its assignment again at once, and redeems the new code.

### 6.3 The first computer, and "Works on"

- **"Works on" is chosen when an agent is made**, on the cloud home: "Cloud" is the default on the web (`meta/ROADMAP.md` item 14). Changing it later is a move between homes, which is later work (OneHome rule 4). On a cloud home, every agent the person makes works on the cloud computer; an agent that lives on a Mac is made on the Mac (OneHome rule 4; Y13s §11.2, X10).
- **The first computer is made** when the person first makes an agent that works on the cloud, and at onboarding for a person with no computer of their own (§6.4). Each later cloud agent is placed on the same computer (one for each person, H7). The placement is written by the person's own create request on the home (SCC §9: a person writes placement).
- **When the hosted service answers `entitlement_required`**, the app shows the card step and says why: "Cloud agents need a cloud computer. It needs a card." with the service's own words below and the hosted card page the app already opens for DorkOS's own AI (`POST /v1/checkout`, `packages/cloud-api/src/billing.ts:544-560`). No agent is made until the computer exists; after the card, the create is sent again with a new `idempotencyKey` (§6.1). No prices and no plan names appear.
- **Every agent on a cloud home works on a cloud computer.** A cloud home runs no agents itself (ADR `261015-042933` rule 3), so no agent is made there without a placement: a cloud agent is made only once its computer exists, and DorkBot only once its computer is linked (§6.4).

### 6.4 DorkBot and onboarding for a person with no computer

- **Which cloud home makes DorkBot.** Only a cloud home recorded as the home of the private space (Y13s §5.2, `privateSpaceHome`). A cloud home that is a way in makes none: the person's DorkBot lives on their Mac.
- **When.** On such a home, `ensureDorkBot()` makes nothing until the first cloud computer is linked; then, on the event that its first computer linked, the home makes DorkBot and places it on that computer. Both are writes by the home, not by a person; §9 lists them for Security.
- **Onboarding** for a person with no computer is plain app onboarding that never depends on DorkBot (L1a step 11, which stands on this point). It says once, before the card step: "DorkBot works on a cloud computer. It needs a card." With no card, the person still has their DorkOS in the cloud, its rooms, docs and settings, and onboarding shows "DorkBot needs a cloud computer." with the card step, in place of DorkBot.
- **DorkBot has no special grant.** Under step 8, an agent on an agent computer that asks to make an agent is always held for a card on the home (`create_agent`, bucket 2, SCC §5.3). That holds for DorkBot. Onboarding's first agents are made by the person's own action on the home, never by DorkBot. The older "setup grant" and pair allowances are dropped (§10).

## 7. What it boots

**The entry.** The hosted service starts the image with `DORKOS_SERVER_ROLE=agent-computer`, the key file's path and the API origin, and nothing else that grants anything (`hubs.ts:30-42`). The role selects step 6's computer entry, not the full server (step 6 §7.2, C23). Composed over the wire (SCC §7.1, W20), it serves only health and its loopback `/mcp` and `/agent-mcp`, binds loopback only (`env.ts:545-548`), and runs no schedules: only its home starts turns.

**What the entry checks at boot** (`services/cloud-computer/boot-checks.ts`, new, computer side). It refuses to start, with one log line naming the check that failed, when any of these fails:

1. `DORKOS_AGENT_COMPUTER_INSTANCE_KEY` is not set at all (`hubs.ts:39-41`).
2. `DORKOS_AGENT_COMPUTER_INSTANCE_KEY_FILE` names a file owned by the user the server runs as, readable and writable by that user only, holding a key of sixteen characters or more.
3. `DORKOS_CLOUD_API_URL` is an `https` origin with no path.
4. The server does not run as root, and the agent user the entry's own recipe names (§8.1) exists, is a different user, and can read neither the key file, nor the data folder's `session-relay/` (the pin and signing key), nor the outbox (SCC §7.3).

**Then it links or dials.** With a pin, it dials its home at boot and after any drop (W4). With no pin, it reads its assignment at boot and then every `pollAfterSeconds` (300 when absent) until it is linked, and redeems the code (§6.1). Once linked, it reads the assignment again only after its dial has failed for 5 minutes, since `hubOrigin` may change (`hubs.ts:540-542`); a read that names a different owner or issuer stops it working, as the contract says. The computer entry opens no command stream in this spec, so `agent_computer_assignment_changed` is not read; polling is the contract's other path (`hubs.ts:563-564`).

**What it holds** (H5): its key file, its pin and signing key, its outbox, the rules copies step 8 allows, the synced agent copies, the model token (§8.2), and the agents' workspaces and runtime transcripts. No credential of the person, no connection's secret (connections stay on the home and are reached through `tools.call`, SCC §5), and nothing of a Mac.

**What is removed** (Z4). The old shape that the computer entry never runs, once C23 has deleted the `startup/` and `http/` branches: `services/core/agent-computer/agent-gate.ts`, `agent-writes.ts` and `sealed.ts` with their tests; the `agent-computer` branches at `services/core/auth/registration-policy.ts:74`, `services/core/operator/config-patch.ts:449` and `lib/request-classifier.ts:114-116` (and the request kind `agent-computer` with them); and the `agent_computer_assignment_changed` arm of `services/core/remote/command-dispatcher.ts:276-283`, which a full server never receives. **Kept:** `services/core/agent-computer/hub-owned.ts` (step 8 §5.3 reads its list on the home), the loopback rule in `env.ts`, and the OpenCode-only rule (§8.1), which moves into the role policy (step 6's C22). A branch that DOR-4927 has already moved is removed where it now lives.

## 8. The runtime, model access and packages

### 8.1 The runtime

- **OpenCode first.** It is the only runtime the computer entry registers in the `agent-computer` role (today `startup/runtimes.ts:317-336`; the rule moves into the role policy).
- **Doe when its spike says yes.** No ticket or result for that spike exists. §12 asks for one, "Spike: Doe on a cloud agent computer"; the operator decides on its result (ADR `261015-042933` rule 7). Until then Doe does not register there.
- **Claude Code and Codex later**, each with its own spec.
- **What a runtime needs to run there,** by what the contract shows: it runs headless as the agent user, with no sign-in of its own and no account secret; it reaches models only through the token of §8.2, handed to it under the two-user rule (`hubs.ts:44-49`); it reaches only what the computer may reach (`hubs.ts:55-62`); it exits cleanly on SIGINT within the five seconds; and it passes the shared runtime conformance suite through its forwarding runtime (SCC §6.2, W8).
- **The agents of one person share the agent user (H7)**, each in its own folder (`homePath`, chosen by the computer, SCC §5.5). §15, question 5, names the other option.
- **Agent processes as a separate user** (DOR-3067, L1a step 3 item 7, which stands, with the user's name below): the runtime and every tool process are spawned through a launcher that runs them as the agent user. **That user's name is part of the computer entry's own recipe in this repo** (one fixed name, `dorkos-agent`, which the image must create), not a value the hosted service passes at start: the contract's three boot values (`hubs.ts:30-42`) stay three. L1a's `DORKOS_AGENT_RUN_AS` is read only outside the `agent-computer` role, for tests and added machines; and the server's secrets are files mode `0600` owned by the server user. This is the separate-user Must of SCC §13 for a cloud computer.
- **What the agents' user may write.** Everything the home syncs for an agent (its manifest, identity files, skills, commands, agents, packages and the rules copies) is written by the entry and owned by the entry's own user, with no write access for the agents' user. The agents' user can write only to workspaces and to the runtime's transcripts. The entry checks these owners and modes at boot and after each sync.

### 8.2 Model access

- **Who mints.** The computer, with its own instance key, through `POST /v1/inference/tokens` (`inference.ts:11-28`), reusing the mint-and-renew loop in `services/core/cloud/credits-inference.ts`. `agentRef` is the agent's id on its home, for attribution only.
- **The cap.** Tokens are short-lived, and the limits apply for each computer and each account at once; they are the hosted service's. The app shows a refusal when one is hit and sets no cap of its own.
- **Who holds it.** The server user. The runtime gets it the way the contract requires (`hubs.ts:47-48`): the agent user cannot read the server's copy or its process.
- **"Runs on" is fixed** to DorkOS's own AI on a cloud computer. No other model, sign-in or key is used.
- **With no token** (the account is out of credits, or a mint is refused), the runtime refuses the turn before the agent sees it: the run ends `refused` (step 5 §4.4) and the chat says "Out of AI credits." and "Add credits, then send a message or press Start." The hosted service then stops the computer for `out_of_credits` as it decides (§5.4).

### 8.3 Packages

A package an owner installs for a cloud agent reaches the computer in `agents.sync` (SCC §5.5, W11). These kinds do not work on a cloud agent, and the older note's list stands: an agent package for another runtime, a plugin or hook only Claude Code runs, a package that adds a Relay chat connection, and a local MCP server whose program is not in the image. The app refuses the install for a cloud agent and says "This doesn't work on cloud agents yet." on the package's card and in the refusal.

### 8.4 The contract change, contract first (Z1)

One pull request to `packages/cloud-api`, from an issue labelled `cloud-contract`, agreed with the hosted side before it merges. `hubs.ts` is over the size limit (668 lines): the change moves the computer part into a new file first. It adds one route, one stop reason and one rule, states one value, answers three questions, and widens one case item 13 already adds.

1. **A stop reason for the six-hour cap.** `CloudComputerStopReasonSchema` gains `time_limit` ("it ran six hours without a break"), so the app can say why. The enum is read tolerantly (`hubs.ts:298`), so an older app reads it as unrecognised and shows "Asleep".
2. **Busy before an idle stop** (a rule): after the hosted service answers `204` to `busy: true`, it does not begin an idle stop until that report expires; once a stop has begun, it answers `busy: true` with a problem, never `204` (§5.1).
3. **The home's own busy report** (the one new route). With the home's key, shaped as the computer's is (`{ busy }`, held 600 seconds unless sent again, answered `204`). **A cloud home is not idle while a start it asked for is outstanding or one of its cloud computers is connected**, and it says so by this report: `busy: true` when either begins and every 5 minutes while either holds, `busy: false` when neither does. A start counts as outstanding for at most 5 minutes after each start call (§4.4). The hosted service does not put a home to sleep while its report says busy.
4. **A computer that needs its sleeping home** asks the hosted service to wake it with item 13's wake asked for with a computer's instance key (Y13s §8, K2 case 4: answered `202`, at most one a minute and 30 an hour for each computer, `429` past that, never unsigned), which this spec widens rather than adding a route of its own: K2's case covers a cloud agent computer that owes its home facts or holds a live run, as well as a person's computer delivering a notice (§14.2). The hosted side checks only that the key's account owns the home; the home then checks the dial against its pin as for any computer. The computer asks when its dial has failed for 1 minute while it owes facts or holds a live run.
5. **The idle window's length** is stated, so the 30-minute bound (§5.1) can be checked against it. The value is the hosted side's to give.
6. **Three questions, answered in the contract's prose:** what a start of a `stopping` computer answers (§4.2); whether a computer stopped for credits, a hold or a suspension may be started to read its history or export an agent (§6.2); whether a create key refused with `entitlement_required` may be reused (§6.1). Until each is answered, the app does what the section named says.

**With an older hosted service** that knows neither the home's busy report nor the widened wake: the report is answered `404` and the home keeps today's behaviour, so the hosted service may put the home to sleep while its computer runs a turn. Then step 8's rules apply: the computer cannot reach its home, the home hears nothing within the run's rules copy's life, and the run ends `lost_contact`, with a person's words restored as a draft (or, for a reply already under way, step 8's line that its outcome is unknown; SCC §5.2 item 7). The computer keeps dialling with step 8's backoff and delivers what it owes once the home wakes by item 13's other paths (its next wake, its owner, a message for one of its agents). Without the busy-before-stop rule, an older hosted service can also stop a computer that just took a turn, which ends that run `shutdown` by §5.2.

## 13. Risks

- **A computer kept on by work it cannot finish.** A home that cannot be reached leaves facts in the outbox, which keeps the computer busy. The hosted six-hour cap bounds it, and the next message starts it again.
- **Cold starts are slow.** A message to an asleep agent waits for a boot. The line says so at once, and the 5-minute bound turns a silent start into a visible retry.
- **The idle window is the hosted side's.** If it is long, a computer stays on after work; if it is short, a person who answers a card after 30 minutes finds the computer asleep. Z1 asks for its length so both can be checked.
- **Shared files between one person's agents.** Said plainly (H7) and a row for Security; §15 names the stricter option.
- **Old tickets read as live work.** DOR-2939 to DOR-2943 hold the older text. §14's banners and the issue splits in §12 must land before anyone picks them up.
- **The hosted side's pace.** Z1, live starts and the card page wait for it. Z0 lets every step merge and prove itself first.
- **An older hosted service** that knows neither Z1's busy report nor the widened wake may put a home to sleep while its computer runs a turn. That run then ends as lost contact, with a person's words restored as a draft, by step 8's rules (§8.4).
- **Signed rows widened.** H6 makes a link the home made count as the owner's. Until Security signs the rows of §9 again, Z3 and Z12 do not merge.

## 15. Open questions, each with a pick

1. **A copy of a cloud agent's chat history on the home**, so it reads while the computer is stopped. Pick: not now; the chat shows what the home holds and a Start control (§6.2). Other option: keep a copy on the home, which is a second transcript store against ADR-0310.
2. **Batching due work at start**, so one start also runs beats due soon. Pick: not now; measure how often starts cluster first. Other option: on each start, run every beat due within ten minutes.
3. **How long a run waiting on a person keeps the computer on.** Pick: 30 minutes (§5.1). Other option: 10 minutes, the hold cap of a held tool call (`CAPABILITY_APPROVAL_HOLD_CAP_MS`, `services/core/capabilities/capability-approval-hold.ts:105`), which saves hours but stops computers while people are still reading.
4. **Doe on the cloud computer.** Pick: after its spike, the operator decides (§8.1). Other option: ship Doe there with OpenCode now, before any result.
5. **Whether a person's cloud agents may read each other's folders on the shared computer.** Pick: yes, said plainly (H7). They run as one system user, so an agent's level does not wall its folder from another agent of the same person there; each can read and change the others' workspaces. Other option: one operating system user for each agent, which walls each folder at the cost of a user, a launcher setting and a folder owner for each agent.

Decided and no longer open: one contract (H4); starts for work only (H1); waits, never refusals (H2); the hosted service stops idle computers (H3); the home links for its owner (H6); one computer for each person (H7); "Works on" chosen at creation (§6.3); no special grant for DorkBot (§6.4).
