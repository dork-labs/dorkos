# Credentialed launcher acceptance gate

Refs DOR-2169, task 4.3. Status: implemented, locally tested, and proved against a published release (below). Task 4.3 is done.

`pnpm --filter dorkos test:community-live` installs an exact published version, refuses a release without the launcher, and runs that installed CLI against explicitly designated disposable Fly, Neon and Tigris resources. It interrupts and resumes owner setup, checks the applied bootstrap-secret rotation, signs in through the public HTTP contract, posts and downloads a private attachment, and verifies anonymous denial. Secrets stay in private temporary files or memory; the clipboard handoff uses a private local socket.

The gate requires every `DORKOS_COMMUNITY_LIVE_*` arm, an exact published version (or an unreleased tarball, below), provider organization and region, charge acknowledgement, and operator-designated budget before it may start. The budget is recorded, not a provider-enforced billing cap. Ordinary verification and CI do not receive these variables. No production origin is accepted by the HTTP proof.

Cleanup verifies recorded provider identities before deleting the disposable resources. If failure leaves resources behind, it preserves the deployment journal and prints a recovery command using the exact published `npx` package, with an explicitly quoted `DORK_HOME`, which remains usable after the temporary install is removed. Successful nonsecret receipts are written outside both cleanup directories. An execution regression runs that command through an executable package-manager stand-in after removing a disposable installation and verifies its exact arguments and ability to read a retained fixture journal. This proves command durability; it is not a full provider-failure cleanup rehearsal.

## Unreleased tarball mode

A launcher fix used to need a release before the gate could try it against the real services. The gate can instead install an unreleased package tarball. Set `DORKOS_COMMUNITY_LIVE_PACKAGE_TARBALL` to the tarball's absolute path **instead of** `DORKOS_COMMUNITY_LIVE_VERSION`. Setting both, or neither, is refused. Every arm, the charge acknowledgement and the budget are still required, and nothing about the run changes except where the launcher comes from.

The tarball replaces only the launcher. It still deploys the published Community image and signed release manifest for the package's own version, so the launcher has to accept that release. A launcher is built with a fingerprint of `apps/community/migrations` (`scripts/build.ts`) and with the release-manifest contract in `packages/shared/src/community-release-manifest.ts` (its `COMMUNITY_CONFIG_SCHEMA_VERSION` and strict schema). It refuses any release manifest that does not match them (`COMMUNITY_RELEASE_INVALID`). It refuses before it writes a launch record, so nothing is created and nothing is spent. Once `main` gains a Community migration after its last release, a tarball packed from `main` can never deploy that release. So a checkout after its release commit is not enough on its own: its Community migrations and that contract must also be the release's.

If they are, pack from a clean checkout at the commit you want to test:

```sh
git worktree add /tmp/dorkos-pack <commit>
cd /tmp/dorkos-pack
pnpm install --frozen-lockfile
pnpm --filter dorkos pack:community-live -- --out /absolute/output/directory
```

If `main` has moved past the release's migrations, pack from the release tag plus only the launcher commits under test:

```sh
git fetch --tags
git worktree add -b live-gate/<name> /tmp/dorkos-pack v<version>
cd /tmp/dorkos-pack
git cherry-pick <launcher commit>...
pnpm install --frozen-lockfile
pnpm --filter dorkos pack:community-live -- --out /absolute/output/directory
```

The recipe checks this before it builds, by comparing git blob ids between `v<version>` and `HEAD`. It refuses when a `.sql` file directly in `apps/community/migrations` (what the fingerprint covers) was added, removed, renamed or edited, or when `community-release-manifest.ts` changed, and it names each file. A mode-only change (a `chmod`) does not count, because the build reads names and contents, never modes. Any content change to the contract counts, including a comment-only edit. That can refuse a pack that would have worked, but never lets through one that cannot deploy. It also refuses when the tag is not in the checkout, and says to run `git fetch --tags`.

`scripts/pack-community-live-tarball.ts` refuses a checkout with uncommitted changes, both before packing and after the build, and refuses if `HEAD` moved during the build. It writes into a fresh `<out>/<commit>/` directory and refuses one that already exists, so a second pack can never overwrite a tarball an earlier run's recovery command still names. Builds are not byte-reproducible, so an overwrite would swap in different code. It builds the CLI with `pnpm --filter dorkos build` and packs it with `pnpm pack`, which rewrites workspace dependency ranges the way publishing does and `npm pack` would not. Beside the tarball it writes `<tarball>.provenance.json`, which records the commit, the package version and the tarball's sha256.

Before any npm, profile or service call, the gate copies the tarball into the run's retained directory (`<DORK_HOME>/live-gate/<app>/package-under-test/`) and checks the copy. The only process involved is a local `tar` read. The original must be a regular file, not a link, and its sidecar must be complete and say the checkout was clean. The copy's sha256 must match the sidecar's. The copy's `package/package.json` must be `dorkos` at the sidecar's version. From then on only the copy is used: the gate skips the npm "is it published" check and runs `npm install` on the copy into its private prefix, and the recovery command installs from the copy with `npx --package`. Replacing or repacking the original after the check changes nothing. The copy survives a failed run with the rest of the retained directory and is removed with it on success.

The receipt's `source` block reads `{ kind: 'tarball', released: false, file, sha256, commit, packageVersion }`; a published run records `{ kind: 'release', released: true, version }`. The top-level `version` is always the Community image and signed-manifest version the launcher deployed. For a tarball run that is the package's own version, not a claim that this code was released. `commit` comes from the local sidecar the pack recipe wrote. The gate checks that the sidecar matches the tarball, but it does not check the commit against a remote, so whoever cites the receipt must confirm the commit is where they say it is.

A tarball run is evidence about unreleased launcher code, never about a release.

When the launcher exits with a failure and its journal holds no saved error, the gate reports the launcher's own last error code. That happens when the launcher refuses its release before writing a journal, or when a resumed launcher stops while its journal holds no error, which is the normal state. Only the code is shown, from the last `Community setup failed:` line, and only when this checkout knows it. The gate adds `before writing a launch record` only when there is no journal and no recovery command, for example `Community live gate failed (published-launcher): launcher exited with COMMUNITY_RELEASE_INVALID before writing a launch record`. When a journal exists, resources may exist too. The gate then says only `launcher exited with <CODE>`, and prints the recovery command beside it. A journal's saved error, which also names the service, is reported in preference to either.

What a tarball receipt can prove is set per decision. For DOR-2238's provenance gate flip, it is acceptable evidence: the marker round trip is how Fly and Neon behave, not something a release changes. That holds provided the cited receipt records `source.kind: 'tarball'` with its `sha256` and `commit`, and that commit is on `main` or on the pull request being proven (see `specs/launcher-uncertain-create-cleanup/02-specification.md`, Implementation phases).

A tarball packed from a release tag plus cherry-picks names a commit that is on neither: cherry-picking gives new commit ids. To cite such a receipt, push the pack branch and link it in the flip PR, so reviewers can reach the commit. The flip PR shows that `git log v<version>..<commit>` holds only cherry-picks of commits on `main` or on the pull request being proven. `git cherry <that branch> <commit>` must mark every one of them `-`, meaning the same change is already there. It must also show that those changes are not reverted on `main`: `git cherry` compares patch ids, so it cannot see a later revert, and it marks a whitespace-only difference `-` as well. The flip PR also names the tag the tarball was packed from.

## Second member and the hold (DOR-2591)

After the owner proof, every run also proves a second person, whether or not a hold is set. As the owner, the gate makes a one-seat invitation to the proven channel. A fresh session opens it and signs up a new account. That signed-in account must be refused the owner's private file while it has not joined. It then binds and redeems the invitation. As that member, it reads the channel and finds the owner's post, replies to it and checks the reply landed in the owner's thread, and downloads the owner's private file with the same sha256. An anonymous download of that file must still be refused. A failure names only its step (`non-member-download`, `member-join`, `member-read`, `member-reply`, `member-file-integrity`, `member-anonymous-download` and so on). The receipt gains `secondMemberId`, `secondMemberReplyEntryId` and `secondMemberProof: true`.

`DORKOS_COMMUNITY_LIVE_HOLD_MINUTES` is optional. Unset means no hold. When set, it must be a whole number from 1 to 45. Anything else (`0`, `46`, `1.5`, text, an empty value) is refused with the other arms, before any npm, profile or service call, and the refusal names the range. A hold keeps one small Machine and one Neon endpoint running, which is why the ceiling is fixed in code. A hold is also refused before anything starts when the retained directory (`$DORK_HOME/live-gate`) is inside this checkout, since the handoff file must never be where it could be committed.

During a hold the gate:

1. Writes `handoff.json` as a `0600` file in a fresh `0700` directory under the retained run directory. It holds the origin, community id, channel id, the owner's and the member's email and password, and the invitation link: the contract the two-Desktop driver reads through `DORKOS_TWO_DESKTOP_COMMUNITY_HANDOFF` (`apps/e2e/community-two-desktop/config.ts`). A unit test writes one and reads it back with the driver's own reader.
2. Prints only the file's path and the `touch <dir>/done` command that ends the hold early.
3. Checks every 5 seconds until the time runs out, the `done` file appears, or Control-C, SIGTERM or SIGHUP (the terminal closing) arrives. Any of these ends the hold at once.
4. Deletes the handoff directory, then runs the same identity-checked cleanup as every other run.

Cleanup runs however the held phase ends: the `done` file, the timeout, Control-C, SIGTERM, the terminal closing (SIGHUP), a failed second-member proof, an error thrown inside the hold, or a stray uncaught error anywhere in the process. A second signal while cleanup is running is ignored, with one note on stderr, because stopping cleanup part way would leave paid resources running. Output errors once the terminal has gone (EPIPE, EIO) are ignored too, so they cannot stop cleanup. A held-phase failure is reported only after cleanup has finished, as `Community live gate failed (<step>): cleanup finished; the community was removed`, with no recovery command. A cleanup that fails still prints one.

Under `pnpm --filter dorkos test:community-live`, Control-C also stops `pnpm` itself, so the shell prompt comes back at once while the gate keeps running in that terminal. It finishes cleanup and then prints its result line (checked by hand on 2026-09-30 by sending SIGINT to the whole `pnpm exec tsx` process group). **Keep the terminal open until the result line appears.** The gate survives the terminal closing, but you would lose the result, and the recovery command if cleanup fails.

Nothing can catch SIGKILL: a force quit, a signal 9, or the machine losing power. If the gate dies that way during the held phase, the community keeps running and billing, and the handoff folder (two passwords) stays on disk. Then, by hand: delete the `handoff-*` folder under `$DORK_HOME/live-gate/<app>/`; delete the resources the launch journal in `$DORK_HOME/live-gate/<app>/launches/community/` names (the Fly app `<app>`, its Tigris bucket, and the Neon project), checking each id against the journal before deleting it; and compare the Fly and Neon inventories with the before inventory, as in `specs/community-launch-acceptance/05-live-checklist.md`.

Control-C before the held phase, during the launch itself, behaves as before.

The receipt gains `held: { minutes, endedBy }`, where `endedBy` is `done`, `timeout` or `interrupt`, and is absent when no hold was set. No password, email, session or invitation reaches the receipt, stdout or stderr. `src/__tests__/community-deploy-live-hold.test.ts` proves each ending with a fake clock and a fake cleanup, and in a real process under tsx: a real SIGINT, and a real SIGHUP sent to the whole process group after its output pipes were closed. `community-deploy-live-member-proof.test.ts` proves the second-member proof against a fake Community.

## Provenance receipt (DOR-2238, phase 2)

The receipt also carries a `provenance` block for `specs/launcher-uncertain-create-cleanup/`. It needs no new arm and adds no create: the probes run after the launch finishes and before cleanup. They only read, apart from the SSH no-op below, and they never fail the gate or hold up cleanup. A probe that cannot read records a stable code instead of provider text. `scripts/community-deploy-live-provenance.ts` holds them.

The block starts with `schema: 3`. Version 1 also had a leftover-network probe, since removed (see below); version 3 added the `removal` block (see "The removal's own reads" below). Each failure code names its source: `proc:` for a `fly` or `neonctl` process, `gql:` for the launcher's Fly GraphQL client, `http:` for the gate's own raw Fly read, `session:` for the Fly session and secret reads, `probe:` for a check in the probe module, `journal:` for a journal identity that is missing, and `guard:` for the wrapper around the whole run.

Cleanup never depends on the probes. The whole run sits inside a guard that resolves on every path. If a probe throws, every field reads `guard:PROBE_THREW`; if the run takes longer than eight minutes, every field reads `guard:PROBE_DEADLINE`. Either way cleanup goes ahead. On a running app, the worst case with every bounded read timing out is about six and a half minutes: 30 seconds for each Fly and Neon read, and two minutes for SSH.

- **`fly`**: the app's network, read through the launcher's own `DorkosReadAppProvenance`, against the journal's `provenance.flyNetwork`. It records whether the two match and whether the network has the `dorkos-<32 hex>` shape, plus the app's `createdAt` and whether `internalNumericId` came back.
- **`neon`**: whether the journaled role has the `community_<32 hex>` shape and is on the project's default branch, plus the project's `created_at`.
- **`tigrisBinding`** and **`tigrisSecrets`**: whether the add-on is still bound to the journaled app, and whether `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` both exist on the app. Fly's servers do not set them; the launcher stages them from the create answer (DOR-2559), so both being there confirms that step.
- **`sshOnCustomNetwork`**: whether `fly ssh console --app <app> --command true` exits cleanly. It is the one probe that runs anything, a no-op inside the gate's own Machine. It uses, and may start, the operator's local `fly agent` daemon, and it may issue an SSH certificate. It may also create a WireGuard peer for the organization. Fly reuses that peer across runs, it is not made per run, and the gate does not remove it, which is acceptable for a throwaway gate organization. An SSH failure and a WireGuard or agent failure both surface as `proc:EXIT` or `proc:TIMEOUT`. So `sshOnCustomNetwork` failing is not, on its own, proof that the custom network breaks SSH; check the agent and WireGuard state before citing it.
- **`unknownApp`**: what the launcher's parser returns for a name no app has (`null` or an error code), and the raw envelope's shape: whether `data` and `data.app` are `null`, the error count, and each error's `extensions.code` and `path`. Error messages are never kept. This settles whether an unknown app answers `app: null` or `data: null`, and what a real not-found looks like next to a server error.
  There is no leftover-network probe. Whether a custom network outlives its app cannot be read through Fly's GraphQL API. There is no `node(id:)` root field, no network list on `Organization` or at the root, and a `Network` is reachable only through a live app's `IPAddress.network`, so the handle is gone as soon as the app is. (The saved introspection capture of 2026-09-29 confirms this.) After a run, check the organization's networks in the Fly dashboard by hand if that matters.

### The removal's own reads (DOR-2606)

The marker probes above do not send what `dorkos community deploy --remove-uncertain` itself sends, and they do not time a real create. `provenance.removal` records both. It needs no new arm and makes no new create, and every call in it only reads. `scripts/community-deploy-live-create-watch.ts` and `scripts/community-deploy-live-removal-reads.ts` hold it.

- **`journalWatch`** and **`createWindows`**: the launcher clears a create's `requestedAt` from the journal as soon as the create completes, so the finished journal no longer has it. From just before the first launcher starts until the resumed launcher exits, the gate reads the local journal every 200 ms. It keeps the first `requestedAt` it sees for each create, and the journal's `updatedAt` on the first revision that records the created id (`idRecordedAt`). `journalWatch` counts the reads and the unreadable ones. For each of `fly`, `neon` and `tigris`, `createWindows` puts `requestedAt` beside the service's `createdAt`: the Fly app's from the `fly` probe, the Neon project's from the `neon` probe, and the bucket's from `DorkosListAppTigris`. Each entry records `createdMinusRequestedMs` (negative means the service's clock is behind this machine's), `idRecordedMinusRequestedMs`, the `windowDeadlineMs` and `windowMarginMs` the removal uses, and `withinWindow` from the removal's own `isCreatedWithinWindow`. A create that finishes between two reads records `requestedAt: null`; the gate never guesses one.
- **`beforeCleanup`**: read after the marker probes, and before cleanup deletes anything. That includes the cleanup that follows a Control-C during the hold. `listAppTigris` sends `DorkosListAppTigris` through the removal's own Tigris probe, so it is exactly the removal's query, parser and mapping. It records `appFound`, `appNameMatchesJournal`, the app's `network` and `networkMatchesJournal`, `organizationMatchesJournal`, `totalCount`, `listedCount`, `complete`, and the journaled bucket, found by its exact id: `nameMatchesJournal`, `organizationMatchesJournal` and `createdAt`. `verdict` is what the removal's `evaluateUncertainResource` decides for that bucket, given its real `requestedAt`; a healthy run reads `proved`. `appNameWhileLive` sends `DorkosAppNameAvailable` for the gate's own app, which should answer `available: false`. The journal values these reads need are picked one by one, so a journal whose schema drifted still gets every read; only `verdict`, which needs the whole journal, then reads `journal:SCHEMA_MISMATCH`. Both reads sit inside a two-minute guard, like the marker probes, so cleanup goes ahead whatever they do.
- **`afterCleanup`**: read only once cleanup has finished and the after-inventory is taken. The gate prints one line saying it is waiting up to 3 minutes for Fly to release the names. It then reads `DorkosAppNameAvailable` for the app and `DorkosFindTigrisByName` for the bucket (free only on Fly's exact `NOT_FOUND`, since Fly renames a deleted bucket `<name>_deleted_<suffix>`) every 15 seconds. It stops reading a name once it is free, after three failed reads in a row, or when the 3 minutes run out. Each read is cancelled when the time left runs out. Each name records `reads`, `first`, `last`, `releasedAfterMs` and `endedBy` (`released`, `deadline`, `failures` or `interrupt`). Control-C, SIGTERM or the terminal closing during this wait only stops the wait: the in-flight read is cancelled, the receipt is still written, and the run folders are still removed. A five-minute backstop cancels the reads if they have not stopped by then, and records `guard:PROBE_DEADLINE` if they still have not stopped five seconds later.

Worst case, with every bounded read timing out, the probes before cleanup now take about eight and a half minutes: about six and a half for the marker probes and two for the removal's reads. After cleanup, the wait is 3 minutes when a name is still held, and at most about 5 minutes. A clean run adds about 3 minutes only when Fly holds a name that long; when Fly frees both names at once, the wait ends after one round of reads.

The PR that flips `PROVENANCE_ROUND_TRIP_PROVED` cites this block. It needs a run on a version that writes markers. On an older version, the journal has no network to compare, and the block says so. Both flags were flipped on receipt `dorkos-gate-376b14cf0957` (2026-09-30), a tarball run packed from `v0.93.0` plus cherry-picks (commit `f0e98fef` on `live/dor-2238-marker-pack`).

The implementation received independent REVIEW.md reviews, including the recovery and rotation fixes. The final local evidence is recorded in the PR. A successful local unit run does not establish a successful provider deployment, but the published-release run below does.
