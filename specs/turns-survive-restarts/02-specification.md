## Overview

Three things land behind the existing turn path, one pull request at a time:

1. **One turn port.** Every space-side caller starts, watches, stops and answers a turn through one typed door whose payloads are plain data. It is a thin layer over `dispatchSessionMessage` and `dispatchMessage`; callers move to it one at a time, held by a lint ratchet.
2. **A run record and an outbox.** One small DorkOS-owned row per turn (`turn_runs`), and the work that must follow a state change written in the same transaction (`turn_effects`), carried out by one leased worker.
3. **Recovery with caps.** A boot sequence that marks what died with the ending DorkOS observed, drops what cannot be known, continues only what its runtime has proven it can resume, at most three times per turn, and says so in one line.

## Goals

- A restart loses no accepted work: every accepted turn and every follow-up is either carried out, or dropped with a record and a line a person can read.
- Every device reads a turn's status from one record, readable when the computer that ran the turn is off.
- No effect whose outcome is unknown runs twice. A timeout never counts as proof that work finished.
- Each step ships alone and leaves the app working.

## Non-goals (out of scope)

- A unified transcript store. ADR-0310 stands; the run record holds no words.
- The computer side as its own long-lived process (DOR-5162). The spike follows this spec and changes nothing in it.
- The wire itself (roadmap item 8). The port is shaped for it, §3.6 lists what the wire must gain, and nothing here opens a socket.
- Playbook rules (DOR-5156). The run record names a playbook; nothing reads it yet.
- The memory budget's numbers (DOR-5192). Admission has the slot; today's caps fill it.
- Changing what a person sees when they press Stop, or the pause rules of spec `audit-trail` PR5.

```

   (rooms, tasks,              │ one transaction: turn_runs row + turn_effects row(s)
```

## 3. The turn port

### 3.1 Operations

The port has two faces. Space-side callers use the **space face** (`apps/server/src/services/runs/index.ts`). Only the space face uses the **computer face** (`apps/server/src/services/session/turn-port/index.ts`).

| Space face                                                 | Computer face                                                                | Wire form                                                                          | Notes                                                                                                                   |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `start(StartTurnInput) → { runId, status, queuePosition }` | `start(TurnStartRequest) → { accepted: true } \| { refused: RefusalReason }` | `turn.start` (`session-relay-agent-computer.ts:263-280`), extra fields as features | The space face answers at acceptance, never at turn start. Waiting is decided before the computer face is called (§3.5) |
| `stop(runId, by)`                                          | `stop(runId) → InterruptReceipt`                                             | `session.interrupt` today; needs a per-run stop (§3.6)                             | Stops one run; never touches the queue. Receipt vocabulary of ADR `260823-021312`                                       |
| `answer(runId, interactionId, response)`                   | `answer(...)`                                                                | `interaction.respond` (`session-relay.ts:382`)                                     |                                                                                                                         |
| `watch(runId \| sessionId, cursor)`                        | facts sink (§4.6)                                                            | `session.stream`                                                                   | Yields `RunFact` values                                                                                                 |
| `get(runId)`, `list(sessionId)`                            | none                                                                         | none                                                                               | Reads the run record only                                                                                               |
| `isLive(runId) → boolean`                                  | `isLive(runId)`                                                              | `computer.status`, once it names runs (§3.6)                                       | Asks the live owner (§4.5); never reads the record                                                                      |

The computer face reports facts through one sink registered at startup: `accepted`, `started`, `delivered`, `waiting_on_person`, `resumed_from_person`, `background_work`, `ended`. The turn code never imports `services/runs`; it calls the sink. This keeps the import direction space → computer only.

**What the computer face may refuse.** `RefusalReason` is a closed list, and each reason says what happens to the run:

| Reason         | Meaning                                                                                                                                             | What happens to the run                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `already_held` | The computer side already holds this run id: the request is a repeat (§6.2)                                                                         | Nothing changes. No second turn starts, the run keeps its status, and the `start_turn` handler keeps waiting (§6.2) |
| `agent_paused` | The agent is paused and a person typed the message (§3.5). A chat message that has a queue row is not refused: the dispatcher keeps it and holds it | It is cancelled, and the caller sees today's `AGENT_PAUSED` error                                                   |

A refusal at the door, other than `already_held` and `chat_busy`, cancels the run from where it is: `queued` on a Mac (transition 5), where the dispatcher writes `starting` only when a launch begins (§4.7), and `starting` for a remote computer (transition 9).

A chat that turned busy between admission and the hand-over needs one more reason, added in T5 with its first caller: `chat_busy`. Words that belong in a composer become a queue row and are never refused for a busy chat. A run whose words stay at their source (`source_ref`) is refused as `chat_busy` only when a live run of the chat is the cause. The run stays `queued`: on a Mac it never left `queued`; for a remote computer the `start_turn` handler writes transition 8. The handler then tries again with backoff (the retry steps of §6.1), without counting attempts, bounded by the run's `notAfter` when it has one. A chat that is busy with no run behind it is never `chat_busy`, because no `ended` fact would ever release the wait; §4.7 says what happens then. More reasons come with the wire work (DOR-5163, DOR-5166), each with its row here.

The other refusals `launch-session.ts` gives today (`INVALID_AGENT_PATH`, `UNKNOWN_RUNTIME`, `ROOM_SESSION_MOVED`, `DESK_NOT_OWN`, `ACCOUNT_NOT_ALLOWED`, and the thrown `COMPUTER_RUNTIME_MISMATCH`, which T5 answers as `runtime_mismatch` rather than retrying it, since asking again cannot change it) are refusals at the door too: it answers them before the chat is bound to a runtime or anything is queued. Each joins this list, with its row, in the step whose caller can first hit it (T5 for the first ones), and each cancels the run with the reason kept in `ending_detail`. They are not sent as an `ended` fact with `refused`: that ending stays the runtime's own refusal (§4.4). Where the space face can make the check itself before it saves a run (a bad agent path, an unknown runtime), it refuses at `start()`, so the caller still hears at once.

`TurnStartRequest` carries: `runId`, `attempt`, `continuesRunId?`, `sessionId`, `agentId?`, `cwd`, `content` (the words, **inline**, as `turn.start` carries them, at most `SESSION_RELAY_MAX_MESSAGE_LENGTH` = 200,000 characters, `packages/shared/src/session-relay.ts:138`, inside one frame of `AGENT_COMPUTER_MAX_BODY_BYTES`, `session-relay-agent-computer.ts:142`), `origin` (the `TurnOrigin` union), `wireOrigin` (`chat | room | task | beat`, from `wireOriginOf(origin)`), `originRef?` (a `dork:` reference), `tier`, `permissionCeiling?`, `systemPromptAppend?`, `additionalDirectories?`, `prepare?`, `accountRef?` (§3.5), `playbookId?` (§3.5), `settings?`. The `start_turn` handler reads the words from where the space side keeps them (the queue row, a room entry, a source row) when it builds the request. **A queue row id, `source_ref` or effect id is a space-side detail and never crosses the port.** A start whose words exceed the cap is refused at `start()` on the space face, with the cap named, before anything is saved.

`agentId` is optional on `StartTurnInput` and `TurnStartRequest`, as `agent_id` is on the record (§4.1): a person can chat in a folder that has no agent. The wire's `turn.start` requires an agent, so a request without one is served only by this Mac's own computer face.

`StartTurnInput` grows with its callers, so no field ships before something sets it. T1 defines it without `askedByRef`, `startKey` and `sourceRef`. Each is added as an optional field by the step whose caller first sets it: `sourceRef` in T5 (a mini app keeps its words in its own row until the dispatcher has them: `extension-send:<id>`, and startWork's prompt in its `session_started_by` row), `askedByRef` in T6 (no T5 caller can name its asker: an extension id is a name, and a `dork:` kind names an opaque id, ADR `261122-124821`; a mini app is named by its run's source row), `startKey` in T7 (the first source that mints one), then T8, T10 and T11. Both faces also carry `seedContext`, the one honest line a turn's opener attaches (`SendMessageRequest.seedContext`), and `cwd` is optional: absent, the launch path places the chat as it always has. Which runs wait as queue rows is one rule both faces read, `wordsWaitInComposer(origin)` in `turn-port.ts` (§3.5); only the other runs' `start_turn` effects carry `session_id`, so they alone order behind their chat (§5, item 5).

`TurnOrigin` (`apps/server/src/services/session/origin/turn-origin.ts:48`, 16 members then; 17 since T2 added `resume`, DorkOS carrying on in a chat already bound: an approval's verdict, a finished sign-in, work a restart cut short. It seeds nothing, is read by its participants, and travels as `chat`) moves to `packages/shared/src/turn-port.ts` and is re-exported from its old path, so no caller changes in that step. `permissionSeedForOrigin` stays where it is.

**Where a run waits.** On a Mac today, words that belong in a composer (a person's message, a `chat_send`, a mini app's `ctx.agent.send`) wait in the dispatcher's queue as rows a person can see, edit and reorder. Admission hands such a run to the computer face at once, without the chat-busy check, and the dispatcher queues it as a row. A run whose words stay at their source (a `source_ref`: a room trigger, a task, a wake, a heartbeat) waits here, on the space side, until the checks above let it go. **Handing a run to the computer face does not start it.** Who writes each transition on a Mac, and when, is §4.7. Over the wire this changes: the space side keeps the queue and admits a run only when the chat has no live run, so a computer never queues space-side words.

A waiting run keeps its place (§4.6) and shows its reason. **Refusals this replaces** (each becomes a wait when its caller moves to the port):

- `LAUNCH_CAP_FULL` in `session/launch/launch-session.ts:343`, as met by `heartbeats/beat-cycle.ts:476` ("Too many chats were running to start its beat turn."), `runtimes/claude-code/mcp-tools/session-tools.ts:326`, `extensions/start-work.ts:266`, and `session/chat-messages/chat-message-service.ts:354` (for a chat that does not exist yet). These already hold instead: `extensions/agent-send/agent-send.ts:570`, `work-queue/work-queue-wiring.ts:123`, and a chat message to a chat that exists (`capHold`).
- The scheduler's skip at its cap (`tasks/task-scheduler-service.ts:952-959`, `atCapSkipReason`).
- `RELAY_TOO_MANY_NEW_CHATS` (`core/session-relay/relay-errors.ts:58`).
- `whenBusy: 'refuse'` at `routes/session-ui-action-handler.ts:121`, `mesh/mcp-signin-resume.ts:204` and `session/runtime-turns/wake-cut-short-work.ts:120`, and `'refuse-foreign'` at `rooms/room-turn-runner.ts:978`: each becomes a run with `notAfter`.

The Claude Code warm-slot wait (`SESSIONS.WARM_SLOT_WAIT_MS`, 45 minutes, `config/constants.ts:366`) stays inside the runtime in this spec; DOR-5192 folds it into the budget.

### 3.6 What the wire must gain (feeds DOR-5163)

The port is in-process here, but each operation must have a wire form. Against today's contract:

1. **`turn.start` carries the words inline** (`session-relay-agent-computer.ts:263-280`). The port does the same (§3.2). The extra fields (`runId`, `attempt`, `continuesRunId`, `prepare`, `permissionCeiling`, `systemPromptAppend`, `additionalDirectories`, `accountRef`, `playbookId`, `settings`) are added as named features; the protocol stays at version 1. `runId` must be echoed in every later frame about that turn; the computer's own `turnId` stays a reference only.
2. **Stop, answer and watch are missing for agent computers.** `session.interrupt`, `interaction.respond` and `session.stream` exist on the session relay (`SESSION_RELAY_FEATURES`, `session-relay.ts:176-186`), but `AGENT_COMPUTER_RELAY_FEATURES` (`session-relay-agent-computer.ts:150-156`) lists only `agents.sync`, `turn.start`, `tools.list`, `tools.call` and `computer.status`. The contract must add all three as agent-computer operations.
3. **A per-run stop.** `session.interrupt` stops the chat's running turn and empties its queue, as the Stop button does (`session-relay.ts:321-325`). `stop(runId)` stops one run and leaves the queue alone. The wire needs `turn.stop { runId }`. Until it has one, the port sends `session.interrupt` only when the run is the chat's live run; because admission never sends a computer more than the live run (§3.5), the queue that `session.interrupt` empties on the computer is empty.
4. **`computer.status` must name runs.** Its `turns` list carries `agentId` and `sessionId` only (`session-relay-agent-computer.ts:349-353`). `isLive(runId)` and recovery need `runId` in each entry: a contract change.
5. **Facts back to the space side.** `accepted`, `started`, `delivered`, `waiting_on_person`, `resumed_from_person`, `background_work` and `ended` need a frame, keyed by `runId`, on the stream or as a `run.fact` call.
6. **No waiting answer.** Waiting is decided on the space side before a request is sent (§3.5); the wire's `turn.start` answers `accepted` or a refusal only.

### 4.2 Who owns it

The run record is space-side data: every device reads it, and it must be readable when the computer that ran the turn is off. On a Mac both sides share one process and `dork.db`, so the table lives in the machine store now (`packages/db/src/schema/runs/`). Rules that keep the move cheap:

- Only `services/runs/run-store.ts` reads or writes `turn_runs`. Nothing in `services/runtimes/**` or `services/session/**` touches it; they report facts through the sink (§3.1). A test greps for the table's Drizzle name outside `services/runs` and fails on a hit.
- The store's methods take and return the `packages/shared/src/turn-port.ts` types, never Drizzle rows.
- Every write the outbox makes into another table carries a unique key (§6.4), so no claim in this spec depends on two tables sharing one transaction once they live in two stores.
- The move is child issue Q (§10).

Fifteen legal transitions; every other pair is illegal. `run-store.ts` checks each write against the table in `turn-port.ts` and throws on an illegal one; a unit test walks every pair. Every non-terminal status has a way out: `starting` and `started` by a fact or by recovery when the lease runs out; `running` by a fact or recovery; `ended` by its follow-up effects' `not_after`; `queued` by removal, by a caller's `notAfter` when it set one, or by admission once the run ahead of it ends. **A person's queued message never expires by the clock** (ADR `260811-184735` stands): it waits as long as the run ahead of it, and that run always reaches `ended` without a person, except in one case, the run ahead waiting on a person, which is today's behavior and is shown to the person as the open ask.

**The run that is launching heads its turn.** `starting` to `superseded` is illegal on purpose: a launching run is never folded into another run's turn. §4.7 says why the code keeps this true.

**A turn the runtime opened by itself** (transition 2). Its `started` fact says the runtime opened it and carries the run id the computer side minted, the chat, and the agent when the chat has one. The space side inserts the run if that id is absent, treats a repeat of the fact as the same row, and refuses an id that already exists for another chat. It never overwrites a run. When the fact is sent, and what happens to a run of the chat that is `starting` then, is §4.7.

**Where the words are, step by step.** At `started` the dispatcher no longer deletes the queue row (today it does, `message-dispatcher.ts:73-82`); it marks it `in_turn`, which hides it from `queue_update`, from adoption (`message-dispatcher/adopt.ts`) and from the store's `list`, `clear`, `move` and edits (§4.7). The row is deleted with the `delivered` fact, in one transaction, or at settle for a run that ended from `started` (§4.7). A source row (room entry, heartbeat raise, doc batch) is never deleted by the run. A pause cut (transitions 14 and 15) puts the row back in line, §4.7.

### 4.4 Endings, as observed

`completed`, `failed`, `stopped` (with the `InterruptReceipt` kind and who stopped it), `limited` (a usage limit), `refused` (the runtime refused before the agent saw it), `shutdown` (DorkOS ended it while shutting down gracefully, written while SQLite is open, `startup/stop-agent-messages.ts`), `process_died` (the process ended with no `turn_end`: a crash, a kill, or an owner found dead at boot). DorkOS never writes an ending it did not observe (ADR `260823-021312`). An owner whose lease has run out is an observation: the process that ran the turn is gone. **Stops.** Every stop request, confirmed or not, is written to the run's `ending_detail` when it is made, with who made it, in its own transaction, before the runtime is asked (§4.7 says who writes it on a Mac). The receipt kind is added when the receipt comes. A run ends as `stopped` only with a receipt whose outcome is `acked` or `closed`, or when the runtime's own `turn_end` reports an interrupt. A `not-running` receipt is not enough, though `turnEnded` in `packages/shared/src/schemas.ts` counts it: the turn had already finished, and relabelling it `stopped` would be wrong. An `unconfirmed` or `failed` receipt leaves the run where it was; if that run's `turn_end` then arrives, the run ends with the ending the `turn_end` reports, and `ending_detail` keeps the request. This keeps ADR `260823-021312`: the receipt decides whether DorkOS may say "stopped". The `ended` fact for `stopped` carries the receipt when there is one and an optional `stoppedBy` (a `dork:` reference). Because the request is on the run before any answer, recovery's rule "a stop by a person or agent: nothing continues" (§7.3) sees it after a crash. A run that ends from `started` also records `delivery: unknown` in `ending_detail`. An ending is recorded the moment it is observed, even when the status moves later (on a Mac, at settle, §4.7), so a kill between the two never turns a finished turn into `process_died`.

### 4.5 One record, not a second truth

- **Live-turn ownership** stays where ADR `261116-065134` puts it: the dispatcher's `inFlight` entry (`session/message-dispatcher/state.ts`) and the `ConnectorTurnOwnership` registered when a runtime turn opens (`services/connectors/runtime-principal-port.ts:90`), backed by `connector_runtime_bindings` with its `boot_epoch`. Those answer "is this turn live" and "may this tool call run". The run record is **fed by** them (facts) and **points at** them (`turn_binding_id`, `owner_epoch`). No permission or tool decision reads `turn_runs.status`. `isLive(runId)` asks the computer face, which asks the owner. The one launch decision that reads the record is the launch gate (§7.5), and it reads only "does this chat have a live run, an undecided run or a continuation not yet started".
- **The chat's birth and runtime binding** stay in `session_birth_allocations` and `session_metadata` / `session_native_bindings` (ADR `261119-055020`, ADR-0255). The run record references the chat by `session_id`; `runtime` is an immutable snapshot (§12, choice 2).
- **The queue** stays the place words wait (`session_message_queue`, ADR `260811-184735`). A run waiting there references its row; its place in line is read from the row's `position`, never stored twice.
- **The durable stream** stays the one delivery path (ADR-0264). The run record reaches clients as a `run_update` event on it (§4.6).

### 4.6 What every device sees

- A new `run_update` member of the durable session stream carries the chat's live run and its waiting runs (whole list, like `queue_update`), and `SessionSnapshot` gains `runs`. The member joins the client's allowlist of session events in the same PR.
- `queuePosition` is derived at read time: from the queue row's order for a run with `queue_message_id`, else from the order of the chat's waiting `start_turn` effects.
- `GET /api/sessions/:id/runs` returns the same list for integrations, with OpenAPI.
- A status a device shows after a restart comes from the record, so a dead turn never reads "working".
- A **restored draft** (§7.3 step 4) appears in the composer with its line; sending it starts a new turn, discarding it deletes the row.

### 4.7 How the dispatcher feeds the record on a Mac

On a Mac the computer face sits over today's dispatcher, and one hook, landed in T2, turns the dispatcher's own moments into writes on the run. This section is the one place that says who writes each transition on a Mac, and when; other sections point here. Functions are named; line numbers are approximate.

**The rule and the map.** Four invariants are the rule: (i) no write ever needs a pair outside the fifteen of §4.3; (ii) the one-live-run index (§5, item 3) never fires on a normal path; (iii) nothing deadlocks, and no run or effect stays leased forever; (iv) no words are lost or doubled. Everything after this paragraph is a map of today's code that meets them. Where the dispatcher's code and this map disagree, the invariants win: the build step that finds the gap amends this section in its own PR, with a proof case in §8.

**A pause cut.** Both paths are in `launchDispatchInner`:

- The pause lands between the launch and `turn_start` (`heldByPause`). The run is `started`, written before the pause check. While `heldByPause` is set, `delivered` does not delete the row. If the turn then fails, because the pause refuses it, `holdForPause` keeps the row: transition 14, or 15 if the runtime's first event had come, and the row goes from `in_turn` back to waiting. If the pause was lifted and the turn ran, the run goes on as usual and its row is deleted at settle.
- The pause lands after `turn_start`, before the agent did anything (`holdStartedForPause` in `pause-hold.ts`, when the settle reports `agentActed === false`). The row goes back to its old place: transition 14 while the row is still `in_turn`, 15 when `delivered` had already deleted it and the dispatcher re-inserts it from the copy it keeps (`startedRow`).

Transitions 14 and 15 clear `started_at`, `delivered_at`, `runtime_turn_ref`, `turn_binding_id`, `owner_epoch`, `lease_until`, `waiting_on_person`, a recorded `ending` and the stop request in `ending_detail` (the pause's own), and set `wait_reason: 'paused'`. They keep `id`, `chat_seq`, `chain_id`, `attempt` and `queue_message_id`: the row keeps its id. The run's `start_turn` settled at `started`, so nothing hands it over again; a resume re-arms the row and its launch writes transition 4 as usual. **This re-run is the one deliberate exception to "words are never replayed"** (§6.2): the runtime may already hold the words, so the re-run goes out under a fresh runtime message id (`rerunIds` in `pause-hold.ts`), as it does today.

**A turn the runtime opened by itself** (transition 2). It claims `inFlight` when its window opens only if no dispatcher launch holds it (`noteRuntimeTurnOpen`, `pump.ts`), and it waits for the write-lock before it projects anything (`projectRuntimeTurn`, `runtime-turns/runtime-turn.ts`). Its `started` fact is sent at its own `turn_start`, which it reaches only holding the write-lock. At that moment no run of the chat is `started` or `running`: such a run would hold the lock, and it settles in the same step that lets go. The one exception is a lock that expired under a quiet turn. The re-park rule above closes it for every dispatcher launch: none takes the lock while a run of the chat is `started` or `running`. What is left goes to the transport-independent session lock (DOR-2346): the runtime-opened turn's own wait (`acquireWhenFree`) can still take such a lock, and so can a task's or relay's turn until T12 and T13 bring them through the dispatcher. The record stays legal in that case: while a run of the chat is `started` or `running`, no second row is inserted, and the runtime's activity is recorded against that run. A run that is `starting` has begun a launch that has not got the lock, and cannot get it until the runtime's turn ends. That run goes back to `queued` (transition 8) in the same transaction that inserts the runtime-opened run. Its launch then either meets the lock's refusal, and the dispatcher's own transition 8 finds it already `queued` and writes nothing, or it reaches its own `turn_start` later and writes 4 and 7 together. The runtime-opened run's `ended` is written when its turn ends, before it lets go of the lock (`releaseOnce` in `projectRuntimeTurn`). A known gap beside it, accepted for T2: the dispatcher's in-memory slot can be keyed under the new SDK id between a rebind and the turn's next event; the wake goes to the old key, so that launch waits out its bound.

**A run whose words stay at their source** (a `source_ref`). The computer face hands it to the dispatcher with no queue row, as a refusing caller's trigger is handed today. If a live run holds the chat, the computer face refuses it as `chat_busy` (§3.1) and the run never leaves `queued`. If the chat is busy with no run behind it, it is not refused: a summary or `/compact` holding the slot (`launchDueCompaction`, `dispatchCommandIntent`), an ask still open after its turn, a delivery the runtime owes (`isSegmentPending`), a message held for background work, or a task's or relay's turn holding the write-lock outside the dispatcher (until T12 and T13). The dispatcher parks it without a row (`parkDispatch`). The pump starts it at the wake that busy state already has (the summary's end, `interaction_resolved`, `onDispatchGateChange`, a turn boundary); where none comes, its wait bound calls the pump again, never forcing a launch (above). The worker cancels it at the run's `notAfter`. If the write-lock refuses its launch, transition 8 returns its `start_turn` to `pending` (§6.2). It stays `queued` until its launch begins, so a restart in between loses nothing: its `start_turn` is still leased, and recovery returns it to `pending` (§7.3 step 3).

**What T5 adds at the computer face** (proof cases F18 to F23 in §8):

- **The `gone` verdict.** The launch-begin check answers `gone` when the run was cancelled or superseded before its launch began (its app stopped, its deadline passed). The launch is dropped: nothing starts, the launch slot its hand-over claimed is let go (`onSettled('failed')`), and the pump is called for the messages behind it.
- **The hand-back.** When the chat refuses a launch whose words stay at their source (`returnToQueue`), the run goes back to the space side in one step: from `starting` back to `queued` (transition 8, whose move sends its `start_turn` back), or, still `queued`, its `start_turn` reopened. The launch slot that hand-over claimed is let go in the same step; the next hand-over claims its own. Such a plan is never forced at its wait bound: the bound wakes the pump and waits again, and the run's own deadline is the space side's.
- **`checkHeld`.** A `queued` run whose `start_turn` is leased while nothing in this process holds the run (its plan was lost: a reset, a bug) is not left to wait out the lease: its effect is reopened at once and handed over again. A run whose words are a queue row that still exists is the queue's to start (the pump, adoption, a re-arm), so its effect ends `done` with `{ inQueue: true }` rather than awaiting forever.
- **`startAgain`.** A pause cut (14 or 15) of a run without a row would leave nothing for a resume to re-arm, so the same transaction saves the run a fresh `start_turn`, which waits out the pause in admission. **No Mac path reaches it today:** both pause cuts need a queue row (`putBackForPause` runs only under `heldByPause`, and `holdStartedForPause` only with a `startedRow`, and both come from `pausedAgentOfPlan`, which needs a row), so a run without a row never takes 14 or 15. The code stays for the space side's later callers; its test (F22, and `start-work.test.ts`) drives `pauseCut` by hand and proves only the store's reaction.
- **A pause after acceptance.** A mini app's send or start to an agent already paused is refused at `start()` (§3.5). One a pause reaches later meets it at one of four moments, and this is the one place that says what each does:
  1. **Before the space side admits it** (its `start_turn` runs admission): the run waits `paused` (3) and is not handed over; `agentPause()?.onResumed` wakes it.
  2. **After admission, before the launch path's own pause check** (`launch-session.ts`, before any queue row is written): refused at the door, `AGENT_PAUSED`, which the computer face answers as `agent_paused`; the run is cancelled (5). A mini app's start's owner is told once; a mini app's message fails `undeliverable` to the app.
  3. **After that check, before `turn_start`.** A run with a queue row is held by the dispatcher (`pausedAgentOfPlan`, 3) and re-armed when the pause lifts (the resume sweep adopts a mini app's rows too, `orFromApps`). A run without a row is not held there (`pausedAgentOfPlan` needs a row): the backstop in `mesh/pause/hold-paused-turns.ts` throws `AgentPausedError` on the turn's first `next()`, `guardTurnErrors` turns it into an error event, and the turn settles `failed` before `turn_start`. That is not a refused end: `clearIfOurs` writes transition 8 (`backInLine`, `starting` back to `queued`), the move reopens its `start_turn`, and admission then waits `paused` as in moment 1.
  4. **After `turn_start`, before the agent acts.** A run with a row takes 14 or 15 (the pause cut above). A run without a row has no pause cut on a Mac (see `startAgain`): the pause stops its turn as it stops any running turn.
- **Taken back mid hand-over.** `withdraw` (a mini app stopped) takes back any `queued` run: a row run by removing its row (5); a run without a row by cancelling it, even while the launch path still has it, since its launch then meets `gone`. A composer run whose row is written after that cancel is not kept: `queueRowTaken` answers false and the row is removed in the transaction that wrote it. A run whose launch has begun is left to end as it ends.
- **Runtime message ids.** A row the port wrote is named by its run, a ULID. A runtime types its message id as a UUID (Claude Code's `uuid` on the user message, kept in its transcript), so such a row goes to the runtime under a version-8 UUID derived from its id, the same one every time (`runtimeMessageIdFor`, `pause-hold.ts`). The row, its run and the app keep the ULID; history shows the runtime's id, as it already does after a pause cut's fresh id.
- **Lock identity.** A mini app's run holds the write-lock as `extension:<run id>`, one identity per message, where it was `extension:<extension id>`. The lock is never re-entrant, so this changes only `isLocked(key, clientId)`: a steer or a stage asked under one message's identity into another message's turn is refused. No mini app steers or stages (it has no such seam), a chat's own steer asks as the lock's holder (`steerChatTurn`), and a person's steer was refused under either identity, so nothing reachable changes. The `extension:` prefix still marks the turn an outsider's.

## 5. One writer per chat

**Today:** `withDispatchMutex(sessionKey)` chains every dispatcher decision for one chat in process (`session/message-dispatcher/state.ts:315-335`); `SessionTurnQueue` orders turns from one client (`session/trigger-turn.ts:261`); the session write-lock is the mutex one turn window holds (`session/session-lock.ts`); the dispatcher's `inFlight` map keeps one open turn per chat. All of it is in memory.

**This spec adds:**

1. Every write to `turn_runs` and `turn_effects` for one chat is one `better-sqlite3` transaction with `behavior: 'immediate'`. The space face and the effects worker make theirs inside `withDispatchMutex` for that chat's canonical key. The dispatcher's hook writes in the same synchronous step as the dispatcher decision it records, inside the mutex or not (§4.7).
2. `chat_seq` gives each chat's runs a total order, allocated inside that transaction.
3. The partial unique index on `(session_id) WHERE status IN ('starting','started','running')` makes a second live run in one chat a constraint error, not a race. A hit can only be at transition 4 (§4.7); the run stays `queued`.
4. The launch gate (§7.5) holds every launch path while the chat has a live run, an undecided run or a continuation not yet started. It does not order waiting runs against each other: rows start in the queue's `position` order, and a row and a run without a row never wait for each other.
5. The effects worker hands a chat's `start_turn` effects over in `chat_seq` order, except that a continuation goes before every waiting run of its chat; so runs without a row start in `chat_seq` order among themselves. A run's follow-up effects run in the order they were written. Effects of different chats never wait on each other.

The transport-independent session lock (DOR-2346) builds on these; it is not a prerequisite.

**Writing.** An effect is inserted in the same transaction as the state change that causes it: `start()` writes the run and its `start_turn`; the `ended` fact writes the run's `ended` status and its follow-ups. No effect is created from a timer or a listener after the commit.

**The worker** (`services/runs/effects/worker.ts`), one per process. It wakes on any insert (an in-process signal) and, while anything is open, when the next effect falls due, a lease lapses or a deadline passes, no sooner than 1 second and no later than 30 (T4). It leases one effect with a conditional update (`state='pending' AND available_at<=now`) inside an immediate transaction, setting a 60-second lease it renews every 20 seconds while the handler runs or awaits. A handler answers `done`, `wait(retryAt)`, `await(fact)` or `drop(reason)`. `await` keeps the effect leased, renewed by the owner's heartbeat, until the named fact arrives (only `start_turn` uses it, §6.2). A throw on a `repeatable` effect retries after 1 s, 5 s, 30 s, 2 min, then every 10 min, up to 8 attempts, then `dropped` with a notice; a throw on a `once` effect is `unknown`. A handler whose work is a write to `dork.db` does that write and marks the effect `done` in one transaction (§6.4 says what keeps that safe across two stores).

**Dead boots' runs.** Each pass first ends the live runs a dead boot left, as T2's launch check does for one chat (§4.7, "A dead owner's live run retired"), and it runs once more when every lease of the boot before has run out. So a run whose `turn_end` was seen before a kill ends with that ending without waiting for its chat to be used again. What follows a dead run beyond its ending stays recovery's (§7.3, T15).

**Expiry.** The worker settles any non-terminal effect past a `not_after` it has as `expired`, with a reason naming the kind and the deadline. That lets the run reach `settled`. Whoever asked is told once: a `notify_person` effect for a person, the existing report path (`chat-report-back.ts`, `room_report_outbox`) for an asking chat, the task run's ending for a schedule. A `notify_person` that itself expires is recorded and tells nobody.

**The boot epoch** is one ULID minted at startup in `startup/steps/core-stores.ts` and given to the run store and the worker (landed with T2). The per-module epochs that exist (`connectors/event-inbox-store.ts:87`, `connectors/principal/runtime-principal-service.ts:138`) are untouched.

**How a `start_turn` ends (T5).** It is `done` when its run reaches `started`, `superseded` or `cancelled`; it answers `await` while the computer face holds the run (its lease renewed by the worker's heartbeat, its waits and its throws counted apart); and it is `done` with `{ inQueue: true }` once its words are a queue row the queue will start. A run without a row that comes back to `queued` (8) reopens it; one a pause cut (14, 15) gets a fresh one (§4.7).

**The two rules carried from superseded ADR `260929-140932`:**

1. **A timeout is not proof that work drained.** An expired lease, a lapsed stall timer, a passed `not_after` or a missing ack never moves an effect to `done` or a run to `ended` with `completed`. An expired lease on a `once` effect is `unknown`; on a live run it is `process_died`; a passed `not_after` is `expired`.
2. **An effect whose outcome is unknown is never retried or replayed.** `unknown` is terminal, and so is a run that ended between `started` and `delivered`. The one deliberate exception is a turn a pause cut before the agent did anything, which runs again under a fresh id (§4.7). What is recorded: the effect row, its last lease owner and attempt count, and on the run `ending_detail`. Who is told: the person, through the chat's one-line notice (§7.4), or the asker through the report path, or the existing Inbox notice for reports and hand-offs.

## 7. Recovery

### 7.1 Definitions

- **Dead run:** a run in `starting`, `started` or `running` whose `owner_epoch` is not this boot's and whose `lease_until` has passed. A run owned by a live process (another server on the same data folder, when the instance lock is skipped) is never touched, which keeps the ownership rule of `tasks/crash-recovery.ts`.
- **Undecided run:** a run with ending `process_died` or `shutdown` and an empty `recovery_decided_at`.
- **Chain:** one original turn plus every run that continues it (`continues_run_id`), all sharing `chain_id`. A new turn started by a person, an agent, a schedule or any other caller starts a new chain; only recovery adds to one.
- **In a row** means **in one chain**. A chain gets at most `RUNS.RESTART_CONTINUE_MAX` = 3 continuations in total. No time window resets the count: an agent whose own work restarts the server (it runs `pnpm dev`, an update, a reboot) would reset a time-based count every time and loop forever.
- **Safe** for one chat, when all hold: no undecided run in the chat; the chat's runtime is registered and its readiness probe passes; no run of the chat has `waiting_on_person`; the agent is not paused; and the chat's continuation run, if any, has started or ended. Safe for the server: the server is listening (`after-listen.ts`), so no work starts before activation.

### 7.2 The runtime capability

- **`wakesForLostBackgroundWork`** (shipped behavior, declared from T14): after a restart, a chat whose turn had **already ended** but whose process still held background work is woken with a new turn that says what died. Claude Code does this today (`runtimes/claude-code/messaging/background-work-ledger.ts`, `session/runtime-turns/wake-cut-short-work.ts`; measured on CLI 2.1.289: the relaunched CLI writes its own "didn't finish" notice and runs no model turn by itself, so DorkOS starts one). - **`continuesInterruptedTurn`** (new): a turn killed **in the middle** can be continued by a new turn in the same chat, which sees what the dead turn already did. `false` for every real runtime until its measured run is recorded (§7.6).

### 7.3 The boot sequence

Recovery runs once per boot, in `services/runs/recovery/run-recovery.ts`, called from `startup/steps/after-listen.ts` before the effects worker starts and before `resumeChatQueues()` (`after-listen.ts:186-200`). **Each run is handled in one transaction**: mark its ending, decide what follows, write the continuation and notice effects, stamp `recovery_decided_at`. A boot that dies partway leaves every run either fully decided or untouched, so recovery is safe to run twice.

1. **Read.** All `turn_runs` in `queued`, `starting`, `started` or `running` whose owner is not this boot; all undecided runs (§7.1), which includes every `shutdown` the graceful path wrote; all `turn_effects` in `leased` whose owner is not this boot.
2. **Gather facts.** The warm-process reap result (`startup/steps/data-directory.ts:102`), the background-work records the boot found (`after-listen.ts:167`), and the open asks `expireOrphanedAsks` closed (`startup/steps/core-stores.ts:148`).
3. **Effects.** Each `leased` effect with an expired lease: `repeatable` back to `pending` (a `start_turn` whose run has no `started` fact is `repeatable`); `once` to `unknown`. One transaction per effect.
4. **Each dead or undecided run, in one transaction:**
   - `starting` with no `started` fact: back to `queued` (the runtime never saw its words), except a private message whose receipt the boot quarantined as `outcome_unknown`, which is cancelled (§4.7). Done.
   - `started` or `running` with an ending other than `shutdown` already recorded: its turn ended before the kill (§4.7). It ends with that ending, as its settle would have: a run ended from `started` deletes its `in_turn` row and records `delivery: unknown`. Nothing continues. Stamp.
   - `started` (no `delivered`): ending `process_died`, `delivery: unknown`. The words are not replayed. Only a queue row that holds a person's own words goes from `in_turn` to `restored`: the pump never runs it, and the app shows it as a restored draft (§4.6, §7.4). A row whose words came from an agent, a mini app or any other sender is deleted in the same transaction, and its sender is told through its own path: the report for an agent or a schedule (§6.2), `turn.failed` with `interrupted` for a mini app, as agent-send does today. The queue's views stay tolerant of a flagged row that is not a person's (listed, never put in a composer), but nothing makes one. Nothing continues. Stamp.
   - `running`: ending `process_died` (unless `shutdown` is already written), `lost_background_json` from step 2. Decide, first rule that applies:
     - a stop by a person or agent, or a `stopped` ending: nothing continues;
     - it had `waiting_on_person`: nothing continues; the "waited on you" line;
     - `opened_by: 'runtime'` (a turn nobody asked for): nothing continues; if its background work died, `lost_work_wake` covers it as today;
     - the runtime declares `continuesInterruptedTurn: false`: nothing continues;
     - its chain already has 3 continuations: nothing continues; the cap line;
     - a task's or room's run whose task run or room claim already settled: nothing continues;
     - otherwise: a `continue_after_restart` effect (key `continue:<runId>`).
   - In the same transaction: the `notify_person` effect for its line, and `recovery_decided_at` = now.
   - **Lost background work, unchanged.** For each background-work record the boot found, in the runtime that declares `wakesForLostBackgroundWork`: a `lost_work_wake` effect, with today's rules and message (§6.2). When the same chat also gets a `continue_after_restart`, the wake folds into the continuation's message instead of running twice.
5. **Stuck `queued` runs.** A `queued` run with neither a queue row nor a `pending` or `leased` `start_turn` is `cancelled`, ending detail `start_lost` ("its start was not saved"), and whoever asked is told once (a `notify_person` for a person, the report path for a chat, the task run's ending for a schedule). One transaction per run.
6. **Fold the old recoveries.** The room hand-off and report rows that `recoverQueued` and the report store settle today are settled by the same rule (expired lease on a claimed row → `interrupted` with its notice). Task runs whose run record is dead end with that run's ending rather than by `endInterruptedRuns`, once tasks are on the port.
7. **Hold the queue.** Nothing to write: the launch gate (§7.5) reads the record, so a chat with an undecided run or a continuation not yet started holds every launch path until it is safe.
8. **Start the worker.** `continue_after_restart` creates the new run (`attempt` + 1, `attempt_reason: 'restart'`, `continues_run_id`, same `chain_id`, `opened_by: 'recovery'`, origin copied) and its `start_turn`; the continuation runs before the chat's queue.

`session/runtime-turns/wake-cut-short-work.ts` keeps its message, its skips and its one-day bound; the PR that lands this sequence replaces only its direct `dispatchMessage` call with the `lost_work_wake` effect, so the wake gets a run record and a person sees exactly what they see today.

### 7.4 What the agent is told, what the person sees

**The agent.** The continuation's words are fixed DorkOS copy, never the dead turn's content:

> DorkOS restarted while you were working, so that turn was stopped. Check what you were doing and carry on. Background work that stopped: {list, or "none"}.

The list comes from `lost_background_json`: each entry is a kind and a label (a background shell's command label, a helper agent's description, a Monitor), from the background-work ledger and the `background_work` facts.

**The person.** One line in the chat, rendered from `run_update` (copy follows `writing-app-copy`, under 15 words):

| Case                                 | Line                                                                           |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| Continued                            | DorkOS restarted during this reply. The agent is picking it back up.           |
| Not continued: runtime cannot resume | DorkOS restarted during this reply, so it stopped. Send a message to continue. |
| Not continued: waited on you         | DorkOS restarted while this waited on you. Send a message to continue.         |
| Not continued: chain cap             | DorkOS restarted during this reply again. It stopped; send a message to retry. |

| Effect or run expired                | Named by its kind, for example: This message waited too long and was not sent. |

### 7.5 The launch gate

From T15, every path that can launch a turn asks one question first: **does this chat have a live run (`starting`, `started` or `running`), an undecided run, or a continuation not yet started?** If so, it waits. That is all the gate asks.

**Among waiting runs.** Rows start in the queue's own `position` order, which a person can change (§4.5), never in `chat_seq` order. Runs without a row start in `chat_seq` order among themselves (§5, item 5). A row never waits behind a waiting run without a row, and a run without a row never waits behind a waiting row. A continuation not yet started goes before every waiting run of its chat, so it never waits behind a run the gate holds for it.

**What "waits" means.** The pump simply does not launch. A launch already taken out of the waiting set (an entry's `launch` in `park.ts` deletes it from `pending` before it calls `launchDispatch`; the direct launch never entered it) is re-parked with what is left of its bound (`parkDispatch`; `returnToQueue`, DOR-1242) and woken by `schedulePump` when the gate clears.

**No deadlock.** Each thing the gate waits for ends without waiting on a waiting run: a live run ends by a fact or by recovery; recovery decides an undecided run in its boot pass, before the queue is re-armed (§7.3); a continuation passes the gate and goes first. The pump, as it is, tries only the head row; the gate holds that row only for those three things, so moving a row can never make two runs wait on each other. When one of them clears without a turn ending (a continuation cancelled or expired before it starts), the run store wakes the dispatcher through the gate's registration, which calls `schedulePump` for the chat.

**What T15 changes in the pump.** Today `orderedWaiting` (`pump.ts`) sorts entries without a row after every row, and `pumpLocked` tries only the head. So a run without a row parked in the pending set (§4.7) waits behind a head row the pump cannot launch (held for background work, or refused by the write-lock). T15 changes `pumpLocked`: when the head row cannot launch, it tries the oldest entry without a row. When both could launch, the head row goes first, as today. The order among rows does not change.

The check lives in the dispatcher's launch path, so it holds whether or not the caller has moved to the port:

- `session/message-dispatcher/launch.ts` (`launchDispatch`), the one place a dispatch becomes a turn;
- `session/message-dispatcher/adopt.ts` (`adoptQueuedMessages`, `adoptAcceptedPrivateMessages`), which re-arms rows at boot;
- `session/message-dispatcher/queue-upkeep.ts` (`rearmChatQueues`), which the health tick's `resumeChatQueues` runs (`startup/steps/after-listen.ts:186-213`);
- `session/message-dispatcher/pump.ts`, which launches the next row at a turn boundary.

The dispatcher cannot import `services/runs` (§3.4), so `services/runs/launch-gate.ts` registers the check through `session/turn-port/launch-gate.ts` at startup. A dispatch for the continuation itself passes. A test calls each of the four paths with an undecided run in the chat and asserts none launches.

### 7.6 Evidence for a runtime's flip

A runtime's flip PR adds one entry here: the runtime and its version, the tool it was in when the process was killed, what its transcript held after the restart (the tool call, its result or none, any notice the runtime wrote), and what the agent did in the continuation turn. No entry yet.

## 11. Risks

- **Two paths while callers move.** Until T17, some turns are fed to the record by the dispatcher hook and some by the port. The record is the same; only the writer differs. The ratchet shows what is left.
- **No mid-turn continuation until a runtime is measured.** Between T15 and T18 a Claude Code turn killed mid-turn is ended, not continued; the line says so. Today's background-work wake keeps working throughout.
- **A dead turn's half work.** A continued turn is a new attempt; whatever the runtime was doing at the kill is lost unless its transcript kept it.
- **T2 changes how the dispatcher waits.** From T2 every launch (the pump, the direct launch, the wait-bound launch) re-parks while its chat has a `started` or `running` run, where today a launch can take a lock that expired under a quiet turn, and the wait bound forces one in once the lock's 5-minute timeout passes. A message behind a quiet turn can now wait up to the stall guard's 10 minutes. That is right: it keeps one writer per chat (§5), and the forced launch was taking the lock from a turn that was still running.
- **The partial unique index finds a real double writer.** A bug the in-memory rules hid. The fallback (the second run returns to `queued`) keeps the app working while it is fixed.
- **Lease timing on a sleeping laptop.** A lid closed for an hour expires every lease. On wake, the same process still holds its epoch, so it renews and nothing is recovered: recovery only touches runs whose `owner_epoch` is not this boot's.
- **Cap and deadline values** (three continuations, the follow-up `not_after` defaults) are judgment calls to tune from real use.

## 12. Choices made, with the other option

The architect accepted all eight picks below on 2026-11-24. Each stays here with the option not taken, so a builder who finds the pick wrong in practice knows what to raise.

1. **The outbox's store.** Picked: one new generic table, `turn_effects`, plus the two room outboxes driven by the same worker and lease. Other option: no new table; each follow-up lives in its domain's outbox. Picked because in-memory follow-ups (room outcome lines, wakes, notices) have no domain outbox to go to.
2. **`runtime` on the run.** Picked: an immutable snapshot, so the space side can read it with the computer off. Other option: always join `session_metadata`. ADR-0255's first-write-wins makes the copy safe.
3. **The reference kind.** Picked: `dork:turn:<id>`, leaving `dork:run:` to task runs. Other option: rename task runs.
4. **`whenBusy: 'refuse'` callers.** Picked: they become runs with `notAfter`, so "too late" is a recorded ending. Other option: keep refusing them as a named exception.
5. **A runtime-opened turn that dies mid-turn.** Picked: never continued; if its background work died, today's `lost_work_wake` covers it. Other option: continue it under `continuesInterruptedTurn` like a caller's turn.
6. **The scope of the ratchet.** Picked: 14 named domains, `routes/` and `core/` later with DOR-4921. Other option: every non-turn file now.
7. **Paused agents for a person's chat.** Picked: leave today's refusal (spec `audit-trail` PR5). Other option: queue it as `wait: 'paused'`.
8. **`delivered` as "the runtime's first event".** Picked: any event the runtime emits for the turn after `turn_start`. Other option: a runtime-declared acknowledgement, which is stronger but not available on every runtime.

Decided by the architect's rulings and no longer open: the chain cap with no time window (an agent whose own work restarts the server would reset a time-based streak every time, §7.1); where a start waits (the launch gate, §7.5); graceful shutdown writes `shutdown`; a person's queued message never expires by the clock (§4.3).
