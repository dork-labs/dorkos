### Task 1.1: Add host API keys: scoped, revocable credentials for host routes

**Migration 0012 (whole file, including the limit tables task 1.2 uses):** `host_api_keys` (id, label, prefix, secret_hash UNIQUE, scopes text[] with a subset check, issued_via, issued_by_user_id NULL, created_at, expires_at, last_used_at, revoked_at, revoked_by_user_id NULL); `host_audit_events` gains `actor_kind text NOT NULL DEFAULT 'person' CHECK (actor_kind IN ('person','api_key','offline'))`, nullable `actor_user_id`, `actor_api_key_id uuid NULL REFERENCES host_api_keys(id)` and `CHECK ((actor_kind='person') = (actor_user_id IS NOT NULL) AND (actor_kind='api_key') = (actor_api_key_id IS NOT NULL))`; `community_creation_receipts.operator_user_id` nullable beside `operator_api_key_id` with an exactly-one check; `bootstrap_grants.revoked_by_api_key_id` with the revocation check widened to "revoked_at set iff exactly one revoker set"; `community_limits(community_id PK FK, max_active_members, max_storage_bytes, limits_version, updated_at)`; `member_limit_overrides(community_id, member_id, agents_per_member CHECK BETWEEN 1 AND 1000, updated_at, PRIMARY KEY (community_id, member_id))` with a composite tenant FK to `members(community_id, id)`; `managed_blobs_community_usage_idx ON managed_blobs(community_id, state, purpose) INCLUDE (byte_size)`; `entries_community_created_idx ON entries(community_id, created_at DESC)`. The deletion worker deletes `community_limits` and `member_limit_overrides` rows with the tenant.

**Scopes:** `communities:read` (list, single read `GET /host/communities/:id` — new, same projection as the list — usage reads, import reads), `communities:write` (create pending_owner with short name and limits, reissue/revoke owner claims, abandon, set limits and member overrides, set/release short names), `communities:lifecycle` (suspend, resume, hold, release, request/cancel host deletion), `communities:import`. No scope manages keys or operators or reaches inside a community.

**Token:** `dkh_` + 43 base64url chars (32 bytes from `randomToken()`); display `prefix` = first 10 chars, never used for lookup; only `hashSecret(secret)` stored. Keys are host-owned: revoking an operator does not revoke keys they issued; the key list shows the issuer.

**Issuance:** `POST /api/v1/host/api-keys` (operator session only, never a key, plus `password` reauth via `auth.api.verifyPassword`; body label, scopes, `expiresInDays` 1–365 or null; browser default 90); response is the projection plus secret once, `Cache-Control: no-store`. `POST /host/api-keys/:id/rotate` (session + reauth; successor with same label/scopes; old key's `expires_at = now() + overlapMinutes`, 0–1,440). `POST /host/api-keys/:id/revoke` (session, no reauth, sets `revoked_at`, no un-revoke). `GET /host/api-keys` (session only, projections only). Offline CLI `node dist/host-keys.js issue --label <text> --scope <scope>… [--expires-in-days <n>]`, plus `list` and `revoke <id>`, against `COMMUNITY_DATABASE_URL`, prints the secret once, writes an audit row with `actor_kind='offline'`.

**Pipeline:** `requireHostOperator` → `requireHostAuthority(c, auth, pool, scope)` returning `HostActor = {kind:'person', userId, name} | {kind:'api_key', keyId, scopes}`. With an `Authorization` header only the key is considered (a cookie on the same request is ignored); a non-`dkh_` bearer is `401 UNAUTHENTICATED`. Lookup by hash where `revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())`; a miss is `401` and counts against the socket peer via `limitAttempts` (new `COMMUNITY_HOST_KEY_ATTEMPTS_PER_MINUTE`, default 20, ceiling 100). Missing scope: `403 FORBIDDEN` "This key does not allow that action." No header: today's session + `host_operators` check; a person holds every scope. `assertHostOperator` → `assertHostActor(client, actor)` re-reads the key row `FOR SHARE` inside every write transaction so a revocation that commits first wins. `last_used_at` updated at most once a minute per key, outside the request transaction, never failing the request. `bearer(c)` answers `401` for any `dkh_` token before a member-credential lookup. (Create's `limits` field lands in 1.2 and `shortName` in 3.1, each entering the idempotency payload hash.) Audit actions `api_key.issue|rotate|revoke`; changed-field names only, never values; reads not audited.

**Wire:** add to `community-admin-wire.ts` `CommunityAdminHostApiKeyScopeSchema`, `CommunityAdminHostApiKeySchema`, `…ListSchema`, `…IssueRequestSchema`, `…RotateRequestSchema`, `…SecretResponseSchema`, `…RevokeRequestSchema` exactly as the spec's Wire schemas section writes them.

**Host page:** an API keys section (list, issue with one-time reveal and copy, rotate, revoke with a confirmation naming the key).

**Acceptance (release gate):** the full 16-row adversarial matrix in the spec's "Adversarial matrix for P1" passes against real Postgres, each refused row asserting no row changed in `members`, `connection_grants`, `agent_credentials`, `bootstrap_grants`, `entries`, `channels`: K_all on every content route (channels, entries, members, invites, agents, exports, attachment download, SSE) and the singleton alias is `401`; K_all cannot reissue claims for an active community (`409 STATE_CONFLICT`); a claim token without a session is `401`; K_all on key management is `403`; K_read on every mutating host route is `403` with no audit row; revoked and expired keys `401`; a revocation committing while a request waits on the community lock makes it fail `401`; cookie + invalid key is `401`; a member grant bearer on host routes is `401`; no response or log contains a `dkh_` secret, hash, or claim token beyond the one-time response; audit rows name `actor_kind='api_key'` and the key. Also: `communities:read` key cannot suspend (403) but a person can; the key row stores `hashSecret(secret)` and no column contains the secret; a rotated key works for `overlapMinutes` and fails one minute later (injected clock); the offline command's key works on the next request and writes an `offline` audit row.

### Task 1.2: Add host-set community limits, typed cap errors, and a host usage read

**Size:** large · **Priority:** high · **Depends on:** 1.1

**Files:** `apps/community/src/limits.ts (new)`, `apps/community/src/routes/host.ts`, `apps/community/src/routes/invites.ts`, `apps/community/src/routes/agents.ts`, `apps/community/src/routes/attachments.ts`, `apps/community/src/routes/administration.ts`, `apps/community/src/storage/managed-blobs.ts`, `apps/community/src/browser/CommunityApp.tsx (host page limits/usage; invitation preview)`, `packages/shared/src/community-admin-wire.ts`, `packages/shared/src/community-wire.ts`, `apps/community/API.md`

**Limits:** `community_limits.max_active_members` (default none) enforced at admission and reactivation in `routes/invites.ts` (not owner claim or first install); `community_limits.max_storage_bytes` (default none) at attachment and icon commit; `COMMUNITY_AGENTS_PER_OWNER` — **default stays 20, configured maximum stays 100** (operator, 2026-09-23; do not change `config.ts`'s default); `member_limit_overrides.agents_per_member` (1–1,000) per person. Effective agent limit = `override ?? config`. No community-wide agent cap, no history limit. Lowering a limit below use removes nothing; it only refuses the next growing action.

**Errors (add to `CommunityWireErrorCodeSchema`):** `409 MEMBER_LIMIT_REACHED` "This community is full. Ask its owner to make room."; `409 STORAGE_LIMIT_REACHED` "This community is out of file space."; `409 AGENT_LIMIT_REACHED` "You have reached your agent limit in this community." (replaces today's `429 RATE_LIMITED` on the agent cap). Upload and post rate windows stay `429`.

**Enforcement:** members — inside the admission transaction after the invite row lock, lock `community_limits` `FOR UPDATE` (row created lazily; no row = no limit, no lock), count active members, refuse before any insert/reactivation; re-admitting an active person does not count twice. Storage — counted bytes are `SUM(byte_size)` of `managed_blobs` with `purpose IN ('attachment','icon') AND state IN ('stored','committed')`; exports exempt; `pending_delete` not counted. Fast pre-check on declared `byteSize` (icons ≤ 2 MiB) before upload; authoritative check in the commit transaction after `prepareManagedBlobCommit`'s lifecycle lock under `pg_advisory_xact_lock(hashtext('dorkos:storage:' || community_id))` only when a storage limit exists; refusal discards via `discardManagedBlob`. Agents — the existing count query reads the override and throws `AGENT_LIMIT_REACHED`; `/agents/recover` unchanged.

**Routes:** `PUT /api/v1/host/communities/:id/limits` (`communities:write`, `limitsVersion` optimistic concurrency, first write uses 1; stale → `409 STATE_CONFLICT`; allowed in every lifecycle except `deletion_pending`; audit `community.limits`). `PUT /host/communities/:id/members/:memberId/limits` (`communities:write`; set or clear one override; `404` unless the member belongs to that community; response only `communityId, memberId, agentsPerMember, effectiveAgentsPerMember`; audit `member.limits`). `GET /host/communities/:id/usage` (`communities:read`) returns exactly `activeMembers`, `activeAgents`, storage by purpose (attachment, icon, export, import staging, pending delete, counted total), limits + `limitsVersion`, `lastPostDate` (UTC date of newest entry via `max(created_at)::date` on `entries_community_created_idx`, or null), `measuredAt`. `GET /host/usage?after=<id>&limit=1..100` pages the same in UUID order with `next`. No names, handles, emails, channel/message counts, file names, or per-person numbers. Create accepts `limits` in the same transaction and idempotency hash. Wire: `CommunityAdminLimitsSchema`, `…LimitsUpdateRequestSchema`, `…MemberLimitsRequestSchema`, `…MemberLimitsSchema`, `CommunityAdminUsageSchema`, `…UsagePageSchema` as the spec writes them.

**UX:** host page Limits section per community (two number fields, empty = no limit, current use beside each); the invitation preview says "This community is full. Ask its owner to make room." before sign-up; the DorkOS app enrollment flow shows the agent-limit message. No copy mentions a host, plan, or price.

**Acceptance:** with `maxActiveMembers=3` and 3 active, a 4th admission is `409 MEMBER_LIMIT_REACHED` inserting no member, handle, or invite use; after one leaves the same invitation succeeds. Two admissions racing for the last seat (test-hook barrier) produce exactly one success. With `maxStorageBytes=10 MiB`, two concurrent 6 MiB uploads produce one committed attachment and one `409 STORAGE_LIMIT_REACHED` whose reservation is queued for deletion. An owner export succeeds when counted bytes equal the limit. Deleting a file frees space at once. With default config the 21st agent enrollment is `409 AGENT_LIMIT_REACHED` (not 429); with `COMMUNITY_AGENTS_PER_OWNER=100` the 101st is refused, a member override of 150 lets the 101st succeed for that member only, and another member still stops at 100; `COMMUNITY_AGENTS_PER_OWNER=101` fails config parsing. Usage for a seeded community equals independently computed sums and a JSON key scan finds no name, handle, email, file name, or channel data. Lowering any limit changes no row outside `community_limits`. `GET /host/usage` over 250 seeded communities returns three pages whose union is every community once; `lastPostDate` is a date, null with no entries, never a time. Create with `shortName`/`limits` replayed with different limits is `409 IDEMPOTENCY_CONFLICT`. Adversarial rows 6–8 and 16 (limits below use, override response carries no identity, override for another community's member is 404, audit rows) pass.

### Task 2.1: Add a read-only host hold and notice-gated host-started deletion

Both halves ship: the operator approved host-started deletion on 2026-09-23 (spec Open Question 1). ADR `260923-121712` (accepted) amends `260920-201101`.

**Migration 0013:** `communities_lifecycle` check gains `held`; columns `held_from_state`, `held_at`, `deletion_notice_at`, `deletion_from_state`, `delete_requested_by_host_actor`; `delete_requested_by` nullable; `community_deletion_jobs.requested_by_member_id` nullable beside `requested_by_host_actor` (key or user id) with an exactly-one check; the suspension check allows `suspended_from_state='held'`; the deletion check requires exactly one requester; `enforce_community_owner_lifecycle()` counts `held` among states needing exactly one active owner.

**Hold:** `PATCH /host/communities/:id/lifecycle` (`communities:lifecycle`, current `lifecycleVersion`) with `action` in `suspend | resume | hold | release | set_notice` (`CommunityAdminHostLifecycleRequestSchema`, replacing the two-action request). `hold` from `active` or `archived`, recording `held_from_state`; `release` returns to it; suspension may start from `held` and resume returns to `held`. While held, people can do exactly what they can in `archived` (history, threads, roster, authorized files, the `{read}`-only `history_only` pairing flow); every growing action (post, upload, invitation, join, write-scope pairing, agent enrollment, settings edit) is `423 COMMUNITY_HELD` (new error code). The owner keeps reauthenticated owner export and their own deletion request; cannot archive, restore, transfer, or release. Entering a hold runs `revokeTenantAccess`; release revives nothing. `deletionNoticeAt` optional on `hold`, and settable by `set_notice`: at least `COMMUNITY_HOST_DELETION_NOTICE_DAYS` ahead (default 14, minimum 7, maximum 365); may be moved later or cleared; moving earlier than 7 days from now is refused.

**Host-started deletion:** `POST /host/communities/:id/deletion` (`communities:lifecycle`, body `lifecycleVersion`, `confirmIdSuffix` = last 8 chars of the UUID) only when `held`, a `deletionNoticeAt` is set, and it has passed; otherwise `409 STATE_CONFLICT`. Enters the existing `deletion_pending` with the same seven-day `delete_after`, worker, blob inventory, progress, and tombstone. `DELETE /host/communities/:id/deletion` cancels a host-started deletion back to `held`. The host cannot cancel or speed an owner-requested deletion; the owner cannot cancel a host-started one. An owner deletion started from `held` cancels back to `held` (`deletion_from_state`). A `suspended` community cannot be host-deleted directly.

**Projection:** `CommunityAdminLifecycleSchema` gains `held`; the host projection gains `deletionNoticeAt` and `deletionRequestedBy: 'owner' | 'host' | null`.

**UX:** banner on every channel of a held community: "This community is on hold by its host. You can read it but not post." plus, with a notice date, "The host plans to delete it after <date>. The owner can export it until then." Owner Settings keep Export reachable and explain Archive, Restore, and Transfer are unavailable during a hold. Host page shows the hold, notice date, and after it passes a Delete action asking for the last eight UUID characters.

**Acceptance:** a held community refuses post, upload, invitation, join, write-scope pairing, agent enrollment, and settings edit with `423 COMMUNITY_HELD`, and still serves history reads, the `{read}` archived pairing flow, and the owner's reauthenticated export (fails if the hold reuses suspension or archive). Holding revokes grants and agent credentials; release returns to the recorded prior state and revives none. Host deletion is `409` for active, archived, suspended, held-without-notice, and before the notice date (injected clock); after it, `deletion_pending` with `delete_after` +7 days and a host requester. The owner cannot cancel a host-started deletion; the host can, back to `held`; an owner deletion from `held` cancels back to `held`. A notice under 7 days ahead is refused. Community B is untouched by every hold, release, and host deletion of A (two-community isolation fixture). Backout note (document in the PR): release every hold and cancel every host deletion before reverting code; 0013 stays.

## Phase 3 — Short names

### Task 3.1: Add short names: host-set /<name> addresses beside /c/<uuid>

**Size:** large · **Priority:** high · **Depends on:** 2.1

**Files:** `apps/community/migrations/0014_short_names.sql`, `apps/community/src/migrate.ts`, `apps/community/src/schema.ts`, `apps/community/src/routes/short-names.ts (new)`, `apps/community/src/routes/host.ts`, `apps/community/src/deletion-worker.ts`, `apps/community/src/config.ts`, `apps/community/src/main.ts`, `apps/community/src/browser/BrowserRoot.tsx`, `apps/community/src/browser/api.ts`, `apps/community/src/browser/CommunityApp.tsx`, `packages/shared/src/community-admin-wire.ts`, `packages/shared/src/community-wire.ts`, `apps/community/API.md`

Build P6 on the Community server and its browser. ADR `260923-121152` (accepted): a short name is a mutable, host-unique alias, never identity. Credentials, invitation/pairing/claim links, stored connections, SSE, and API routes keep the UUID.

**Grammar:** 3–32 chars, lowercase ASCII letters, digits, single hyphens, starts with a letter, no trailing hyphen: `^[a-z](?:[a-z0-9]|-(?=[a-z0-9])){2,31}$`; input lowercased and trimmed first. `COMMUNITY_RESERVED_SHORT_NAMES` shared constant: `api, assets, c, claim, host, join, pairing, health, auth, login, logout, signin, signup, settings, admin, static, public, www, help, docs, status, well-known, favicon, robots, sitemap, new, import, invite, deletion`; hosts add more with the `COMMUNITY_RESERVED_SHORT_NAMES` env var (comma-separated, same grammar).

**Migration 0014:** `community_short_names(short_name text PRIMARY KEY, community_id uuid NOT NULL REFERENCES communities(id), state text NOT NULL CHECK (state IN ('current','retired')), created_at, retired_at)` with a partial unique index for one `current` per community; `released_short_names(name_hmac text PRIMARY KEY, available_at timestamptz)`. Deletion worker deletes a community's name rows and writes their hold rows.

**Behaviour:** host sets on create (`shortName` in the create request, part of the idempotency hash) or later `PUT /host/communities/:id/short-name` (`communities:write`, body `{shortName | null}`); rename retires the current row and inserts the new one in one transaction under the community lock; null retires. Retired names stay bound for the community's lifetime. `DELETE /host/communities/:id/short-names/:name` releases a retired name (audited `community.short_name.release`). Released or deletion-freed names are held for `COMMUNITY_SHORT_NAME_COOLOFF_DAYS` (default 90, 0–365) as an HMAC-SHA-256 under an HKDF key from `COMMUNITY_AUTH_SECRET` (info `community-short-name-hold`); no name kept in clear text after deletion. `DELETE /host/short-name-holds/:name` lifts one hold (audited). Errors `409 SHORT_NAME_TAKEN` (bound current/retired or in cool-off), `409 SHORT_NAME_RESERVED`. Host projection gains `shortName`.

**Public lookup:** `GET /api/v1/community-names/:name`, unauthenticated, `200 {communityId, shortName}` (current name) only for `active`, `archived`, or `held`; every other case (unknown, reserved, malformed, pending_owner, suspended) returns the identical `404 NOT_FOUND`; rate limited per socket peer by `COMMUNITY_NAME_LOOKUPS_PER_MINUTE` (default 60, ceiling 600). No listing or prefix search. Wire `CommunityWireShortNameLookupSchema`, `CommunityShortNameSchema`, `CommunityAdminShortNameUpdateRequestSchema`.

**Browser:** `main.ts` serves `index.html` for `GET /:name` and `/:name/*` when the name matches the grammar and is not reserved; other paths keep `404`. `BrowserRoot` resolves a short-name path via the lookup, renders with the UUID, `history.replaceState` to the current name if a retired one was used, and on 404 shows the chooser with "No community at this address." `tenantApiPath` and `parseCommunitySettingsPath` take `{communityId, basePath}`; `/<name>/settings[/<section>]` works; `CommunityApp.tsx` keeps the short-name base when arrived by one. Server-minted links stay `/c/<uuid>`; "Copy link" offers the short-name address when one exists. Host page Web address section (current name, retired names with Release).

**Acceptance:** lookup of `acme` returns the UUID; after renaming to `acme-labs`, `acme` returns the same UUID with `shortName: 'acme-labs'` and another community cannot take `acme`. After release (or deletion), re-creating `acme` is `409 SHORT_NAME_TAKEN` until the cool-off ends (injected clock) then succeeds, and no database row contains `acme` after deletion. Identical `404` bodies for unknown, reserved, malformed, pending_owner, suspended. A test pins that every literal top-level path in `main.ts` and `BrowserRoot.tsx` is reserved. - `DEPLOYMENT.md` and `README.md`: every new configuration key (`COMMUNITY_HOST_KEY_ATTEMPTS_PER_MINUTE`, `COMMUNITY_HOST_DELETION_NOTICE_DAYS`, `COMMUNITY_RESERVED_SHORT_NAMES`, `COMMUNITY_SHORT_NAME_COOLOFF_DAYS`, `COMMUNITY_NAME_LOOKUPS_PER_MINUTE`, the OIDC set, the three link URLs), the OIDC callback URL, and the agents-per-person setting: **default 20, maximum 100**, plus the per-member override up to 1,000.
- `RECOVERY.md`: import is not a backup; host backups remain the recovery path.
- `API.md`: a final pass that every new route and error code (`MEMBER_LIMIT_REACHED`, `STORAGE_LIMIT_REACHED`, `AGENT_LIMIT_REACHED`, `SHORT_NAME_TAKEN`, `SHORT_NAME_RESERVED`, `IMPORT_ARCHIVE_INVALID`, `COMMUNITY_HELD`) is documented.
- `docs/` user guide: web addresses (short names, renames, old addresses still work).

**Acceptance:** every configuration key parsed in `apps/community/src/config.ts` appears in `DEPLOYMENT.md`; no guide claims a hosted service, price, or plan; `docs:coverage` passes for any new MDX page; the banned-words and vocab gates pass.
