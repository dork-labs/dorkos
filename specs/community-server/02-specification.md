# A self-hosted community for people and their agents

**Status:** Implemented

**Author:** Codex (directed by Dorian)  
**Date:** 2026-09-16

## Overview

A separately deployed DorkOS community lets an owner invite people into channels, exchange threaded messages, and welcome agents that run on each member's own DorkOS install. The community owns its roster and conversation history in Postgres. A local install remains permanently single-owner and mirrors only the remote rooms its owner may see. A complete v1 runs on a self-hosted deployment without contacting DorkOS Cloud or executing agents on the community host.

## Background / Problem Statement

The July ideation proposed `apps/community` but predated the shipped `CommunityAdapter`, real Buzz backend, mature local room dispatch, and current Cloud boundary. Today the adapter can list remote rooms, but a person cannot configure a community, open a remote room, post, or dispatch an addressed local agent from it. The remote-trigger ideation also assumed a much smaller dispatcher: `RoomTriggerDispatcher` is now roughly 3,000 lines and holds Stop, held turns, tool-only speech, response gating, and the one persisted `RoomTurnBudget` instance. A second dispatcher or budget would produce different behavior and could bypass an install-wide turn limit.

The desired acceptance demonstration is concrete: two people in separate browser sessions join a newly deployed community; one invites the other; they exchange messages and threaded replies; one enrolls a real local agent; an addressed message reaches that owner's install, runs through the deterministic test runtime, and a confirmed agent reply appears in both browsers. No paid inference, Cloud account, SMTP service, or Cloud host is involved.

## Goals

- A licensed, independently deployable community with owner bootstrap, member authentication, signed invites, channel administration, history, threads, bounded message attachments, unread state, live updates, export, and leave.
- Three human roles (`owner`, `admin`, `member`), one owner, and row-backed permission checks on every operation. Agents have distinct identities and credentials, vouched for by one human owner, with no human administration rights.
- A browser experience that works on mobile, tablet, and desktop, including joining and recovery states.
- A native local `CommunityAdapter` backend and a configured connection flow that lets the local app open and post to remote rooms.
- Actual locally executed agent turns reusing the current room dispatcher, shared budget, Stop semantics, and per-agent working directory.
- Correct history under concurrent writes, reconnects, retries, admission races, and revocation.

## Non-Goals

- Additional accounts or member roles on `apps/server`; its second-signup prohibition stays.
- Running an agent, holding an agent workspace, or paying for inference on `apps/community` (ADR `260727-184933`).
- Mandatory Cloud sign-in, Cloud keypair portability, edits to the closed-source Cloud repo, federation, serverless-first deployment, or Buzz posting.
- Extracting `apps/site` or local authentication into a new shared package while their coupling remains unresolved. The new app may follow proven patterns without importing their private auth implementations.
- Mandatory email verification or SMTP. Email addresses identify accounts; no email is sent in the default configuration. A forgotten password needs an owner-mediated recovery procedure until a mail service is configured.
- Offline agent work queues. Old history imported after a local process restart never initiates turns. A bounded same-process reconnect may process fresh entries as described below.
- Mirroring remote room workspaces, repositories, or arbitrary remote filesystem paths in v1. Reactions are deferred. Message attachments are in scope through the bounded blob path below.

## Technical Dependencies

- `packages/shared/src/community-adapter.ts`, its Zod contracts, and `communityConformance` in `@dorkos/test-utils` are the existing port and test gate. Extend them narrowly for an explicit acting identity and idempotent posting.
- `apps/server/src/services/rooms/room-trigger.ts`, `limits/turn-budget.ts`, `room-service.ts`, `author-registry.ts`, and the room store are the local execution path. Reuse their existing instances rather than constructing a remote copy.
- Better Auth for human sessions and Drizzle with Postgres for the community database. Use pinned workspace-compatible releases, checked against official migration/runtime docs at implementation time. Separate migrations and schema under `apps/community`; `packages/db` remains SQLite-local.
- Hono on a persistent Node process, Postgres, and a built React/Vite/Tailwind browser bundle following the existing design system. Docker Compose with a Postgres service and persistent file volume is the self-hosted reference. A paid Render web service plus managed Postgres in the same region is an optional first managed deployment recipe; hosted file storage uses an S3-compatible store. The app remains vendor-neutral. Runtime settings use a dedicated `COMMUNITY_*` namespace (`COMMUNITY_DATABASE_URL`, `COMMUNITY_AUTH_SECRET`, `COMMUNITY_INVITE_SECRET`, `COMMUNITY_BOOTSTRAP_SECRET`, `COMMUNITY_PUBLIC_URL`, storage/OAuth settings). Missing required runtime settings fail startup clearly; build, typecheck, and unit imports never require secrets.
- MIT license for the community app, with dependency license checks and the deployment source published in this repository.

## Detailed Design

### Boundary and addressing

One `apps/community` deployment is one authoritative community. It has a stable server-minted community identifier stored in its database, separate from its changeable public base URL. A local `CommunityRef` remains a locally minted connection handle; it is never a Cloud address or the remote identifier. Every room operation is addressed by `(communityRef, remoteRoomId)` locally. The remote server owns only remote IDs and never accepts a client-supplied local path or working directory.

The app owns a `BlobStore` for message attachments and generated export archives: a persistent filesystem volume in Docker Compose and S3-compatible object storage for hosted deployment. This is a used v1 path, not an unused extensibility seam. It supports put/get/delete by server-generated opaque key; Postgres holds metadata and authorization, never a local path or object-store URL. Upload streams are bounded before storage, use random keys rather than filenames, verify allowed type against bytes, reject executable/active content where inline rendering would be unsafe, and always serve downloads with safe content-disposition and no sniffing. The two implementations run the same store contract tests. No storage vendor name appears in domain IDs or wire DTOs, and remote storage never uses the local `dork-home` layout.

`apps/community` serves a same-origin browser app and versioned `/api/v1` JSON/SSE endpoints. The deployment works when outbound traffic to DorkOS Cloud domains is blocked. It does not import `apps/site` or its Cloud account database. Better Auth sessions belong to this one deployment, are issued as secure HTTP-only cookies behind HTTPS, and are checked against a live member row on every protected request. Optional Google/GitHub buttons render only when their secrets and callback URLs are configured; email/password is always available. Public signup is closed after bootstrap: a valid invite is required.

The local server stores the community URL, local `CommunityRef`, connected human member ID, and secrets in its own protected connection store. The browser gets connection status and non-secret descriptors through `Transport`; no remote bearer credential, agent token, invite signing secret, or Cloud secret enters a DTO. The community browser uses same-origin session requests. The local server contacts the remote community server directly using the connected human's credential. The owner can connect more than one community, each with independent local ref, identity, and cache.

**Local connection authorization is a browser approval grant.** The local owner enters the community HTTPS URL (HTTP only for localhost development). The local server creates a random verifier/challenge and a 10-minute single-use pairing request, then opens the community's same-origin approval URL. The member signs in there, sees the requesting local install and access description, and approves. The community binds approval to its authenticated active member row and returns a one-time code to the polling local server; code plus verifier exchanges for a high-entropy revocable personal connection token. The community stores only token hash, member ID, scopes, and creation/last-used/revocation times. The local server stores plaintext only in its protected credential store, never a browser redirect, query string, DTO, or adapter argument. Pairing completion locks its row so two polls cannot redeem it. Timeout or cancel issues no credential. Each local install gets a separate grant, listed and revocable from the community account page. Member removal makes all grants invalid through the live member-row check. No Cloud device flow participates.

### Bootstrap, invites, and membership

A fresh database has no owner. The owner enters a deployment secret supplied out of band at a rate-limited bootstrap preflight endpoint. Only while no owner exists, successful preflight creates a ten-minute, one-use, server-row-backed bootstrap creation grant and sets its opaque signed HTTP-only cookie. The Better Auth creation hook allows account creation without an invite only when that grant is live. The following owner-claim endpoint requires the authenticated user, the same grant, and the deployment secret again. Its Postgres transaction locks/consumes the grant and inserts the singleton owner row under a unique constraint. Better Auth's account write need not join that transaction: a losing parallel claimant may retain an **unadmitted** account, but every protected route checks for a live member row, so it gains no access. No new bootstrap grant can be issued after the owner row exists. Deployment docs explain rotating/removing the bootstrap secret after success. Privileged server access, never a public role escalation route, handles recovery.

An owner or admin creates a signed, row-backed invite scoped to this community and optionally one channel. The URL carries its token in a fragment, so it is not sent in the initial request or Referer; the browser sends it only in a same-origin POST body and clears the fragment after loading it. The token contains a version, key ID, opaque invite ID, expiry, nonce, and HMAC-SHA-256 signature over a canonical length-delimited payload including the immutable community ID and purpose `community-invite-v1`. Derive its HMAC key from `COMMUNITY_INVITE_SECRET` with HKDF for that purpose; compare signatures in constant time and retain previous key IDs only for a documented rotation window. The server stores an invite ID/hash, issuer, scope, seat limit, use count, expiry, and revocation timestamp; a valid signature alone never grants admission. Default lifetime is seven days (maximum 30), default seats one (maximum 100). It reveals a safe preview (community name, inviter display name, channel name if scoped) before authentication. Preview does not consume a seat or expose roster/history. The join page sends the token to a preflight endpoint that validates it and sets a short-lived, signed, HTTP-only SameSite=Lax pending-admission cookie. The Better Auth creation hook reads this same-origin cookie for password signup or the OAuth callback, validates its current signature/row state, and otherwise rejects new account creation; it **does not consume a seat**. The cookie carries an opaque pending ID, not the invite token; its server row binds the invite and expires in ten minutes. After Better Auth account creation/sign-in, the admission transaction locks the invite row, validates it again, rechecks seats and issuer authorization, creates or reactivates the human member, joins the scoped channel, inserts a unique `(invite_id, user_id)` use row, increments use count, and commits. Duplicate admission by the same account consumes at most one seat. If signup succeeds but admission loses a race, the account is unadmitted and sees only a join-recovery screen; a later valid invite can admit it. A Better Auth session alone grants no community access. Invalid, expired, exhausted, and revoked links give useful messages without identifying existing accounts. A concurrent last-seat race admits exactly one new member.

One active owner is required. Owner cannot leave or be removed until ownership is deliberately transferred by a separate authenticated owner operation with reauthentication, all within a transaction; this is required for an actual exit path. Admins may manage invites, channels, and members except the owner or another admin's role. Owner alone grants or removes admin and transfers ownership. Members may join channels they can see, post, enroll their own agents, export their own data, and leave. A removed human immediately loses sessions, SSE, channel reads, writes, and all agent authority derived from that human. Leaving revokes their agents and connection access in the same transaction while preserving previously posted shared history with the author's display identity at posting time. A personal export includes that member's membership, posts, and agent identities/owned posts, excluding other members' private account data. Community owner export produces a documented versioned whole-community archive and requires reauthentication.

| Action                                                           | Owner | Admin | Member | Agent                          |
| ---------------------------------------------------------------- | ----- | ----- | ------ | ------------------------------ |
| Read/post in joined active channel                               | yes   | yes   | yes    | yes, if explicitly joined      |
| Join a visible channel, mark own read cursor, download its files | yes   | yes   | yes    | read/download only when joined |
| Invite, create/archive channel, remove ordinary member/agent     | yes   | yes   | no     | no                             |
| Grant/remove admin, transfer ownership, whole-community export   | yes   | no    | no     | no                             |
| Enroll/eject own agent, personal export, leave                   | yes   | yes   | yes    | no                             |

All cells still require live row-backed membership and the relevant channel authorization. Admin removal of an agent owned by another member is moderation; it does not grant access to that agent's private credential. An admin cannot make themselves owner or remove the current owner. Public channel discovery does not imply reading a channel until joined; invite-scoped admission joins its named channel atomically.

### Agents and quotas

An enrolled agent is a separate community member with `kind=agent`, its own opaque member ID, display data, `ownerMemberId`, active/revoked state, and credential record. Enrollment is initiated from the owner's local install while its human connection is valid. The server issues a high-entropy token once; the local connection store keeps it encrypted/protected, and the server stores only its hash. The agent can read and post only in channels to which it was explicitly added by its owner or an admin. It cannot create invites, administer members/channels, claim ownership, or enroll agents. Admins can eject an agent or remove it from a channel without removing its owner. Revocation of the owner is immediate for every owned agent: every authenticated agent request joins the agent and owner rows and requires both active, rather than relying on asynchronous token cleanup. Rotating or revoking the token has the same immediate effect. Neither token nor hash is sent in room/member DTOs or logs.

Posting and enrollment limits are charged to the owning human across that human's own posts and all owned agents. Defaults: 120 posts per rolling ten minutes, 20 active agents, 16 KiB UTF-8 text per post, four attachments per post, 10 MiB per attachment, and 200 MiB uploaded per owner per day. Config may adjust these within documented hard ceilings; over-limit requests return `429` or `413`. Unbound uploads still consume daily bytes. Quota mutation is atomic in Postgres, so parallel identities cannot multiply allowance. The owner's local `RoomTurnBudget` separately limits model turns and remains the same instance used for all local rooms.

Hard configuration ceilings are 1,000 posts per ten minutes, 100 active agents, 64 KiB text, eight attachments per post, 25 MiB per attachment, and 1 GiB uploaded per owner per day; all limits must stay positive. Default history page is 50, maximum 100. Each SSE subscriber gets at most 256 queued events and a 15-second heartbeat; an overflow closes the stream and the client resumes from its last committed cursor. Default invite preview limit is 20/minute/IP, pairing creation five/minute/IP, and signup attempts ten/minute/IP. Unbound attachments expire after one hour, then are swept with bounded batches. These limits are set in app config, validated once at startup, and documented with their env names.

### Rooms, entries, ordering, and SSE

Channels are membership-scoped durable streams. Owners/admins create, rename, and archive channels. An admin can remove an agent from a channel; humans may leave or join visible channels; archived channels remain readable by authorized members and refuse posting. Channel and membership checks apply on every list, detail, history, cursor, post, moderation, export, and SSE request. A parent entry must exist in the same channel and be visible to the writer. v1 threads are one-level: a reply may point only to a top-level root; replying to an in-thread entry is rejected with `NESTED_THREAD` (HTTP 409), matching `CommunityAdapter.threadDepth: 1` and the local room writer. Cross-channel parents are rejected. History and thread pages use a scoped opaque cursor carrying channel, thread selector, position, and epoch; a cursor from another scope is rejected. The server returns explicit `nextCursor: null` at exhaustion. Per-member read cursors are monotonic and cannot be advanced past an entry the member could not see.

The database has `communities`, Better Auth tables, `members`, `agents`/`agent_credentials`, `bootstrap_grants`, `invites`/`invite_uses`/`pending_admissions`, `connection_pairings`/`connection_grants`, `channels`, `channel_members`, `entries`, `attachments`, `read_cursors`, `owner_quota_windows`, and `audit_events`, with foreign keys, useful indexes, and migrations checked into the app. `entries` carries server-generated ID, channel ID, `seq`, author member ID, body, parent/root IDs, creation time, and a client idempotency key. Unique `(channel_id, seq)` and unique `(author_member_id, channel_id, idempotency_key)` constraints guard ordering and retries. An attachment row records opaque blob key, channel/uploader, sanitized display name, detected content type, byte size, checksum, upload time, and nullable bound entry; only its uploader may bind it, once, to a post in the same channel. Deleted members retain a tombstoned display snapshot for attributable shared history. No filesystem path, local agent session ID, or raw secret is persisted as shared entry content.

A post transaction authenticates and locks the relevant membership and channel state, validates scope/quota/parent, claims the idempotency key, serializes the channel's sequence allocation by locking/updating its counter row, inserts the entry, and commits. Sequence assignment must follow commit order; a plain Postgres sequence/`nextval` is insufficient because two transactions can commit out of order. An idempotent repeat with the same payload returns the original receipt; the same key with a different payload is a conflict. Publish to SSE only after commit. If publish fails, clients resume from database history. The stream opens with a snapshot/cursor and replays entries after the caller's cursor before live delivery without a gap. `Last-Event-ID` is scoped and checked like a history cursor; heartbeats carry no content. Role/channel revocation closes active streams promptly and every resumed request reauthorizes. A channel membership change that races a post is serialized or rechecked at commit so removed members cannot commit after revocation.

Upload is a two-step operation matching local room behavior: an authorized room member streams at most the configured byte/attachment limits into `BlobStore` and receives an unbound attachment ID; the post names only IDs the same writer uploaded to that channel. The post transaction binds all named IDs atomically with the entry. Reads and downloads recheck current channel membership for the requester. Metadata appears in history/SSE and the browser may fetch bytes only through an authorized endpoint. A bounded sweep reclaims expired unbound rows and blobs; a failed blob delete is retried without making a bound entry disappear. Export includes metadata and bytes for entries the requester may export. Upload idempotency protects retry after a timeout, and orphan cleanup is observable. Agent upload goes through its own token and the same role/channel/owner/quota checks, with limits charged to the human owner.

### Wire API and shared contract

Use Zod request/response schemas in `packages/shared` for the community HTTP wire; do not expose Drizzle rows. Public conversation/account schemas and private credential-delivery schemas are separate modules. The server-only `community-private-wire` subpath defines the pairing exchange response (one-time personal token plus non-secret grant receipt) and agent enrollment/rotation response (one-time agent token plus identity receipt). These private responses are consumed only by the local server credential store; they are never CommunityAdapter or Transport DTOs, browser state, ordinary member responses, logs, or errors. Pairing exchange requires the pending grant code and matching verifier. Agent credential issuance requires a live personal connection bearer grant with owner/enrollment scope, not a browser cookie alone. Browser approval, pairing status, and agent management return only public receipts; credential responses use no-store caching and no browser CORS access. The private response is schema-validated before protected local storage, and only a redacted public receipt is returned to the app. Tests cross the real exchange/enrollment routes and local Transport to prove the intended server receives and stores the secret once and the browser/poll/log/error surfaces never do. Stable operations include public metadata and invite preview; Better Auth sign-in/session; atomic first-host bootstrap preflight/completion; invite creation/list/revoke/redeem; channels list/create/update/archive/join/leave; channel members and administration; entry history/post; bounded attachment upload/authorized download; read cursor; channel SSE; agent enroll/list/eject/token rotation; account export/leave; and owner community export/transfer. Explicit status errors are `401` unauthenticated, `403` unauthorized or invalid/revoked/expired invite, `404` hidden/not found, `409` idempotency or seat/state conflict, `410` stale cursor, `413` attachment too large, `415` unsupported attachment type, `429` quota, and `503` unavailable. Avoid disclosing private room existence to unauthorized callers. API documentation includes example requests, capability behavior, and resume/idempotency semantics. Contract tests compare the real HTTP surface to the schemas.

The primary route shape is `/api/v1/community`, `/api/v1/bootstrap/{preflight,complete}`, `/api/v1/invites` and POST `/api/v1/invites/{preview,redeem}` with token in the body, `/api/v1/pairings/{start,approve,poll,exchange}`, `/api/v1/channels` and `/api/v1/channels/:id/{members,entries,attachments,read-cursor,events}`, `/api/v1/attachments/:id`, `/api/v1/agents`, `/api/v1/me/{export,leave,grants}`, and `/api/v1/owner/{transfer,export}`; Better Auth remains under its own `/api/auth/*` mount. First-host bootstrap completion atomically creates the account, operator, owner membership, community, and first channel; the browser then establishes its session through ordinary Better Auth sign-in. Route handlers call domain services after one common authentication/membership guard; they never trust a role, owner ID, or channel membership supplied in a request body. Posting and attachment upload require a stable client idempotency key. The same schemas cover browser and native adapter use; the browser authenticates by cookie and the native adapter by scoped bearer token.

Extend `CommunityAdapter.post` input with an optional `actingMemberId`, required idempotency key for remote writes, and bounded attachment IDs. Add attachment upload/download methods and a capability flag that makes unsupported backends refuse explicitly. An explicit capability declares whether a backend accepts acting as an enrolled owned agent. Add credential capability `browser-approved`: the human approves a local install in the community browser, and that install privately retains a revocable bearer token. Update its TSDoc, capability consumers, and conformance cases; neither existing `user-account` (sign-in without a key) nor `machine-managed` (no user-facing sign-in) describes this flow. The remote adapter resolves the private credential by `(communityRef, actingMemberId)` and refuses unknown, revoked, or non-owned identities; omission means the connected human. The server independently authorizes the selected credential, owner bond, channel membership, and quota. No credential crosses the port or DTO. The local and Buzz backends explicitly refuse unsupported acting identities or attachment operations according to declared capabilities, and all implementations pass updated capability-aware conformance tests. `admitAgent` returns an agent identity/receipt while storing its secret in the adapter's private credential store; never return the token on a shared response.

### Local mirror and dispatch

The remote server is authoritative for roster, channel state, messages, and read cursors. The local SQLite store is a cache with an explicit remote mapping `(communityRef, remoteRoomId, remoteEntryId)` and origin metadata; local IDs never impersonate remote IDs. Import is idempotent by remote entry ID. Remote members resolve to local opaque authors with a community-scoped natural key. **A remote human's origin must be external**, including when the remote human owns this install, because the trust question is whether this message arrived from outside the local server. An unknown author also remains external. No remote field may select a local agent path or working directory; the enrolled local agent manifest resolves that locally.

A connected local owner subscribes only to channels they joined and enrolled agents they own. The bridge writes remote snapshots and entries into local cache before any dispatch, maps remote mentions only to locally enrolled agents, and delegates live eligible entries to the existing `RoomTriggerDispatcher` with its existing `RoomTurnBudget`, runner, response gate, Stop, held-turn, and tool-only paths. Local human/agent posts and remote agent posts do not wake agents by default. Snapshot import, process restart replay, old cursor recovery, and pagination **never** dispatch old mentions. A same-process reconnect may dispatch entries at most 30 seconds old only when that room had an active subscription immediately before disconnect, and only once per remote entry ID. Server entry time is a conservative freshness bound, never an ordering key. It still rechecks local enrollment, remote authorization, Stop state, and budget. Every remote-reachable dispatch and held/resumed turn retains `externalAuthor=true` for a triggering remote human; remote requests cannot select local-only aside/control paths. Read-only backends never dispatch turns that cannot be delivered. Declines/notices and imported human mirrors remain local; they are never forwarded to the remote community.

`RoomTriggerWriter.post` and tool posting are synchronous and must remain so. Agent output and a bounded remote-outbox row are written in the same local SQLite transaction. At the shared `RoomService.post`/`RoomEntryWriter` seam, a remote-mirror write policy suppresses automatic post-commit dispatch for local agent narration and `post_to_room`/tool output in remote mirrors while preserving that synchronous atomic write. The policy derives remote-mirror status from trusted persisted room mapping or service configuration, never a client-supplied `skipDispatch` flag; remote callers cannot choose a local dispatch/control bypass. Agent output in a mirror enqueues once, while imported remote history writes no outbox. The bridge alone explicitly dispatches an eligible imported live human entry once; local-room posting behavior is unchanged. The outbox records the remote address, acting member, original local entry, remote parent mapping, idempotency key, attachment references, creation/expiry, and delivery state. It holds at most 100 pending rows per community and 1,000 across the install; when full, local posting fails visibly before claiming remote delivery. A worker uploads bounded attachment bytes first, then posts with the returned remote attachment IDs, rechecking current agent ownership, membership/connection state, and Stop/halt before each delivery step. Unsent rows expire after five minutes. Retry uses capped exponential backoff (1, 2, 4, 8, 16, then 30 seconds with bounded jitter until expiry). Local agent attachment files are read only from the existing bounded room-attachment store/projection, never from a remote-supplied path. It never retries a permanently unauthorized or stopped delivery. Network retries reuse upload and post idempotency keys. Only the remote server's receipt or matching SSE echo confirms the entry as shared history; until then the local UI labels it pending, and on permanent error it labels failure with a retry/recover action where safe. Echo reconciliation links the local output to the authoritative remote entry by idempotency key/remote ID and cannot create a second visible entry. A tool post uses this same path; an agent cannot bypass the outbox by calling a remote endpoint directly through the room tool. If a remote reply arrives after the local Stop mark or owner revocation, it is still part of authoritative history, but no new local delivery is attempted.

When a person loses membership, the remote adapter reports `not-admitted`, closes subscriptions, suppresses remote room content from normal views, stops dispatch, and invalidates the affected cache per port contract. The local owner can remove a connection and purge its cached rooms and private credentials. Temporary network failure preserves a read-only cache with an explicit stale state; it never claims a failed post reached the community.

### Local app surfaces

Add a connection/enrollment flow in the existing Connections area and channel UI. A person enters a community URL, sees identity and admission status, authenticates or redeems an invite in a browser flow, and returns to the local app connected as one human. The app shows remote channels alongside local rooms with a community label and per-community failure state; opening a remote room resolves `(communityRef, roomId)` to history, roster, thread, read cursor, live stream, and composer. All client access goes through `Transport`, with no raw fetch from feature code. The app permits agent enrollment from an agent the owner already has locally, shows the community identity and channels it may access, and lets the owner disconnect or eject it. Remote room controls reflect backend capability and role, and a read-only/stale state explains why posting is unavailable. Remote views render only server-confirmed shared entries plus the owner's clearly labeled pending local posts. A cached remote room never grants access through `seesEveryRoom` or the local operator bypass: every remote read checks membership or a clearly marked offline cache policy scoped to that owner's last authorized room; removal invalidates it.

The standalone community browser is a complete way for a person without a local install to read, post with attachments, download authorized attachments, manage allowed members/channels, export, and leave. It does not require installing the DorkOS app. This allows two humans to use the service before either enrolls an agent.

## User Experience

An owner deploys with Postgres and one bootstrap secret, opens the same-origin site, claims ownership, names the community, and creates a channel. Invite produces a copyable link. The recipient sees the name, inviter, and channel before creating an account or signing in; only configured OAuth options appear. Password fields support password managers. On redemption the recipient lands in the channel with history and an accessible composer. A thread opens in context, unread indicators are based on that person's cursor, and new posts appear live. The owner can add a local agent from the DorkOS app; addressing it shows pending work locally, then one confirmed reply appears to both people. The agent's card shows its human owner.

Empty, loading, unauthorized, expired invite, removed membership, offline, pending post, failed post, and archived channel states are explicit. The UI uses semantic controls, keyboard focus styles, dark-mode theme tokens, and responsive navigation; it does not expose token strings or implementation nouns in ordinary copy. A member can export data and leave from account settings. An owner must transfer ownership before leaving.

## Testing Strategy

- Unit and contract: shared schema round trips; capability-aware `communityConformance` against the new adapter; exact role/action matrix; cursor scope and parent validation; idempotency payload mismatch; deterministic quota accounting.
- Real Postgres integration through HTTP with isolated migrated databases: parallel owner claims, last-seat invite redemption, parallel writes and sequence/commit ordering, duplicate post retries, ownership removal racing an agent post, channel removal racing SSE/post, revocation of all owned agent tokens, attachment bind races/ownership, upload retry and orphan reclamation, and unauthorized access to every route including history, download, and stream resume. Assert exact rows and subjects, not merely nonzero counts.
- Local integration: real `RoomService` and `RoomTriggerDispatcher` with the **same** persisted `RoomTurnBudget` instance; remote human `externalAuthor` cannot inherit operator power, including held/resumed paths; remote cache cannot use `seesEveryRoom` to expose nonmember channels; snapshots/restarts never dispatch; fresh reconnect dispatches at most once within 30 seconds; the remote-mirror write policy at `RoomService.post`/`RoomEntryWriter` suppresses recursive/second agent turns for both narration and `post_to_room`/tool output while local rooms still dispatch normally; Stop suppresses narration and tool-only posts; held turns and refusal notices stay local; outbox transactional rollback/retry/receipt/echo dedupe; agent cwd comes from manifest. Mutate guards to show these tests fail at the relevant boundary.
- Browser: two isolated contexts perform owner bootstrap, invite preview/redeem, channel and thread exchange, attachment upload and authorized download, unread update, member/agent administration, export/leave, and one deterministic locally dispatched agent reply. Run mobile/tablet/desktop viewport checks, inspect accessibility names and keyboard path, and visually review screenshots of joining, channel, thread, loading/error, and mobile navigation states.
- Deployment: build a clean Docker image, apply migrations to a fresh Postgres volume, restart both app and local client, prove history, blobs, and token invalidation persist, then repeat the core demo with Cloud hosts blocked. Check the built bundle and runtime paths rather than relying on dev-only imports. No paid model credentials are set. Real Postgres integration is an explicit required command/CI job whose missing database fails setup instead of silently skipping assertions. ## Performance Considerations

Index channel/sequence and thread/root history paths. Bound pages, SSE buffers, message and attachment size/count, invite attempts, owner quotas, outbox rows, retry window, and local mirror retention. Stream uploads/downloads rather than buffering whole blobs in Node memory. The stream uses replay from Postgres after disconnect and heartbeats to clear dead connections; it does not depend on an in-memory event queue for durability. Publish after commit and monitor replay lag. Local cache import is batched, preserves remote order, and cannot block the user's local room writes on remote network latency. The first deployment targets one persistent Node process; multi-process fan-out requires a Postgres-backed notification or polling wakeup before horizontal scaling is claimed.

## Security Considerations

- Authorize by live member/agent/owner rows on **every** HTTP and SSE path. Session validity alone never grants membership. On SSE, close streams after revocation and recheck on resume.
- Passwords and OAuth use Better Auth's supported flows. Set trusted origins/callbacks explicitly; secure cookie, CSRF/origin checks, session rotation, and proxy HTTPS configuration are deployment requirements. No automatic account linking on unverified email.
- Invite signatures are authenticated with a deployment secret and a row backs seats, scope, expiry, and revocation. Redemption is atomic. Preview is limited and rate-limited; tokens are redacted from logs and referrers.
- Store only hashes of agent tokens in Postgres; keep plaintext tokens in the local private credential store. Agents cannot obtain owner rights by supplying `actingMemberId`; the adapter and server both verify ownership and role.
- No Cloud address is a community ID. Validate URLs and redirects during connection to prevent SSRF and secret forwarding; pin an accepted origin and reject redirects to a different host. Deployment documents TLS and secret rotation.
- Attachment authorization is row-backed on upload, binding, metadata, download, and export. Server-generated blob keys and sanitized names prevent traversal; content-type and size enforcement prevent an untrusted file from becoming executable or active browser content. Failed/unbound uploads are reclaimed.
- Treat all remote message text as untrusted in UI and agent prompts; existing room prompt-fencing rules apply. Imported authors remain external for local runtime power levels. Remote data cannot set local paths or command settings.
- Stop and revocation checks precede outbox delivery. A network timeout is uncertain, so retry only with the original idempotency key; never infer success from local persistence.

## Open Questions

- ~~Should v1 require DorkOS Cloud identity or a portable keypair?~~ **RESOLVED:** No. Each community is independent; its own account and opaque member IDs suffice. Portability may be designed later without making Cloud mandatory.
- ~~Should the community execute agents or queue work while owners are offline?~~ **RESOLVED:** No. Agents execute on their owner's install. Restart imports history without triggering; only bounded same-process reconnect freshness is allowed.
- ~~Should the remote trigger create a parallel dispatcher/budget?~~ **RESOLVED:** No. Mirror eligible entries into local rows and delegate to the existing dispatcher and budget. Parallel logic would diverge on Stop, held turns, tool posting, and spend limits.
- ~~Can synchronous `RoomTriggerWriter.post` call the remote API?~~ **RESOLVED:** No. Keep synchronous local writes and use a transactional bounded outbox with remote idempotency and receipt reconciliation.
- ~~Which framework and hosting shape should v1 use?~~ **RESOLVED 2026-09-16:** Hono on persistent Node with React/Vite; Docker Compose is the portable reference and Render paid web service plus managed Postgres is an optional deployment recipe. The app remains vendor-neutral. Vercel Functions are not a v1 promise because stream lifetimes are bounded there. The framework choice does not change the service/data contract.

### Implementation clarification: invitation refusal status

Independent review confirmed that invitation signature, expiry, revocation and issuer-authority failures deliberately share `403 FORBIDDEN` with the same public message. Expired signed tokens are rejected before database lookup; route tests pin this uniform refusal. Preserve it instead of exposing distinct invitation-state responses. `410` remains the scoped-cursor recovery signal. This narrows the HTTP-status paragraph without changing admission, revocation or expiry enforcement.
