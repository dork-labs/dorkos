## The short version

- **One question, one place.** "May this member do this in this space?" is answered by one pure predicate, `mayMember`, in `packages/shared`. The capability registry calls it once, inside `registry.invoke`, before a capability runs. A handler no longer asks "is this the owner?" about space data.
- **A move, not a change.** On a Mac the answers do not change for anyone. The only person is the owner, every agent is the owner's, and the predicate's Owner row allows everything. This spec changes where the question lives, not who may do what.
- **Every call knows its space.** `registry.invoke` sets `context.space` itself, from the one builder that also sets item 10's `context.caller`. No caller supplies it. On a Mac it is the private space; the gate reads only that it is private.
- **The member comes from a directory built from today's caller resolution.** A small space-side port, `MemberDirectory`, turns the server-set caller into a member, or "not a member". On a Mac it answers the doors that use today's two room caller resolvers exactly as they do, with those resolvers moved into one function; every other moved site keeps its own caller rule beside the member check.
- **Five classes.** Each of today's owner checks is a member check, the front door, a place fact, this computer's own things, or a check of who is calling. Only the first moves to the predicate. The front door keeps its own bar, place stays a fact about the request, this computer's own things get a named computer-owner check on the computer side, and the checks of who is calling (a person, an agent, the owner in person) stay where they are.
- **A count that only falls, and does not reach zero.** A checker counts every owner test by its resolved binding and allows only a named list, each entry with a class and a reason. It lands first, so the move can go a few sites at a time: the work queue, search, Direct chats and two small reads first, rooms after, and beside them this computer's own things. The sites to move reach zero; the allowed ones (the front door, place, and the checks of who is calling) stay until equal accounts (§11.5).
- **The space store waits.** It shares the level type and the member view only after the Community Space has opened, when the freeze on the space code ends.

## Goals

- One predicate answers whether a member may take an action on space data, called once by the registry, and the same definition can serve a private space, a person's DorkOS in the cloud and a team space.
- Every capability call knows its space from a value the server sets.
- Every owner check that exists today is in one of five classes, and each class has one home.
- Nothing a person or an agent can do on a Mac changes, proved for every moved site with a table test over every caller kind.
- Each step ships alone and leaves the app working.

## Non-goals (out of scope)

- **Equal accounts**: the Admin, Member and Guest rows' values, editable switches, different editable defaults for people and agents, more than one person on a Mac, agents as admins (the successor of DOR-2743). The level type has four values so nothing changes shape later; no step here creates a level below Owner or a second person, and no path on a Mac reaches one.
- **Approvals opened to anyone but a person.** ADR `261006-225605` item 8 stays: "Until roles exist the decider stays a person." The approval bars are class (e) and do not change.
- **The manager's yes** on the always-a-yes list (`meta/PRINCIPLES.md`). An agent's `reportsTo` is not read by the predicate.
- **Moving the private space onto the space store** (item 16).
- **Changing any rule in the frozen space code** (`services/spaces`, `apps/space`, `packages/shared/src/community-wire*`, `services/spaces/migrate.ts`). Its sharing of the level type is step G13, which waits for the Community Space to open.
- **Redesigning "at this computer" for a hub** (item 13).
- **Moving folders into kernels** (DOR-4925). New server code goes where item 6's side map puts it.
- **Who is calling.** The checks that decide whether a caller is a person, an agent, a program or the owner in person stay as they are (class (e), §8.1). This spec reads them; it does not change them.

## 1. Today

### 1.1 Who the owner is

- **The owner is the first account ever made.** `findOwnerAccount(db)` returns the earliest `user` row by creation (`services/core/auth/accounts.ts:45`); the `role` column is not read, so "no write to `user.role` can move ownership" (`accounts.ts:9-17`). Registration opens only while the `user` table is empty and refuses every later attempt (`accounts.ts:4-7`).
- `readOwnerAccount()` (`services/core/auth/index.ts:547-550`) answers that account, or null before `initAuth` or with no account. `readOwnerEmail` is beside it.
- `isInstallOwner(user)` (`services/core/auth/install-owner.ts:21-24`): the signed-in user is that account.
- `ownerAccountExists()` (`services/core/auth/gate-policy.ts:176-182`): an owner exists; a failed lookup reads as yes, so a bar fails closed. Many routes take it as an injected `ownerExists: () => boolean`.
- **Rooms.** `isOwnerRecord(record, ownerUserId)` (`services/rooms/author-registry.ts:287-290`): a human author whose natural key is the owner's account, or the local sentinel when there is no account. `AuthorRegistry.isOwner` (`:1316-1319`), wired as `isOwnerAuthor`; `RoomAuthority.requireOperator` (`services/rooms/service/room-authority.ts:81`) throws unless the viewer is the owner; `RoomVisibility.seesEveryRoom` (`services/rooms/service/room-visibility.ts:134`) lets the owner see every room. Agents are authors of kind `agent` and never pass `isOwnerRecord`.

### 1.4 The member and role model that exists

**In the space store** (Postgres, `services/spaces`, frozen):

- `members` (`services/spaces/schema.ts:423-480`) holds each member of a space with a `role` and a `kind` (`person` or `agent`, `:456`) and, for an agent, `owner_member_id`. An agent row always has role `member` (the shape check at `:459`). The type is `role: 'owner' | 'admin' | 'member'` (`services/spaces/data.ts:20`). There is no guest and no per-action switch.
- **The space's one predicate**, `requireLiveRole(client, member, allowed, options)` (`services/spaces/data.ts:571`): it locks the space, refuses a cleared account, reads the member's live role and answers 403 `FORBIDDEN`, "Your current role cannot perform this action.", unless the role is in `allowed`. Who is asking is decided apart from it (`requireMember`, `data.ts:425`; `requireAdministrator`, `services/spaces/moderation/administrator.ts:37`).
- What each role may do is written route by route. Owner only: change a member's role, set reserved names, transfer ownership. Owner or admin: channels, invites, bans, mutes, rules, reports, removing a member. Any member: join and leave, direct messages with agents, enrolling and removing their own agents. The removal rule for agents keeps today's shape: the owner may remove any agent, an admin only an ordinary member's, a member only their own (`specs/server-merge/03-agents-as-members.md`, finding 9).
- Host operators (`host_operators`) belong to the whole host, not to a space.

**On this computer** (SQLite, `services/rooms`, `packages/db`):

- There is no member level. `room_members` (`packages/db/src/schema/rooms.ts:520`) records who is in a room, with no role. The only "role" is the owner, through §1.1's rooms checks.
- The local `user.role` column exists and is not read (`services/core/auth/accounts.ts:9-17`).
- An agent's manager is its `reportsTo` in `.dork/agent.json` (`packages/shared/src/mesh-schemas.ts:547-552`). An agent's turn level (`asks`, `reach`) and the permission areas (`packages/shared/src/permissions/permission-areas.ts:29`: `rooms`, `tasks`, `agents`, `messages`, `connections`, `packages`, `extensions`, `own_chat`, `todos`, `settings`, `safety`, `permissions`, `reach`, `files`) belong to the agent's turn gate, not to a member level.

### 1.6 Where a space is known at a call

- **HTTP to this computer:** no space header, parameter or session field. Local rooms live under `LOCAL_COMMUNITY = 'local'` (`packages/shared/src/community-adapter.ts:91`); remote spaces are addressed as `/api/communities/:ref/...`. Requests are classed by place, not space: `this-computer`, `other-device`, `relayed`, `hub`, `agent-computer` (`lib/request-classifier.ts:69-81`).
- **MCP and in-session calls:** an agent identity and, in a session, `sessionId` and `cwd`; no space.
- **The private space's id:** `localSpaceId()` (`lib/identity/space-id.ts:171`), a ULID minted once at first boot in the data folder. It answers `undefined` before boot and when the file cannot be used. Only provenance reads it (`services/runtimes/shared/references/turn-reference-env.ts`). `dork:space:` is a reference kind (`packages/shared/src/dork-ref.ts`); nothing in the server resolves one to a store.
- **The space server:** `resolveCommunityContext` (`services/spaces/tenant-context.ts:85`) reads a `:communityId` from the route.

## 2. The shape

```

   │
   ▼
 registry.invoke
   sets context.space from the one builder on every call (never from the caller)
   1 lookup  2 hub-owned  3 caller proofs (person_only)  4 server principal  5 parse
   6 ── member gate ──►  MemberDirectory.memberOf(caller, space) ──► member | not a member
   │                     mayMember(member, { capabilityId, tier, area }, space)  (packages/shared)
   │                     refuse: 403 forbidden
   7 preGate  8 preflight  9 spend  10 cancel window  11 permission, tier, card  12 confirm  13 invoke
                         │
 every reader of the catalog and every tool list ─┘ (the same predicate, at the declared tier and area)

 (b) front door: refuseFrontDoorChange, unchanged (M3)     (c) place: request facts, unchanged (M4)
 (d) this computer's own things: the computer-owner check, an identity test, computer side (M5)
 (e) who is calling: the person bars and person proofs, unchanged
 the space store: shares the level type and the member view, after the Community Space opens (G13)
```

On a Mac the directory's private-space implementation answers as today's caller resolution does, and in a private space the member gate refuses no one, so every later step runs as now. On an agent computer the member gate does not run (M7, §5.3).

## 3. Normative invariants

These ten invariants are the rule. Everything else in this spec (today's map in §1, the tables in §4 to §12, the inventory in §8, the steps in §17) describes today's code and how it meets them. **Where the code and the per-step map disagree, the invariants win: the build step that finds the gap amends the section it contradicts in its own pull request, with a proof case in §16.**

|         | Invariant                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | How it is checked                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 4. The predicate (P-1)

### 4.1 Its types

One new file, `packages/shared/src/permissions/member-check.ts`, pure, with no import from the server, the community wire or a store.

```ts
/**
 * A member's access level in one space. Four values so nothing changes shape later.
 * Only 'owner' is reached by any path in this spec. 'admin', 'member' and 'guest' are
 * placeholders for equal accounts (ADR 261006-235239): no path on a Mac reaches them,
 * and no step or proof here depends on what they allow.
 */
export type MemberLevel = 'owner' | 'admin' | 'member' | 'guest';

/** Who is asking, as a member of one space. Never a place, a credential or a header. */
export type Member =
  | {
      kind: 'person';
      level: MemberLevel;
      /** Present when a program acts as this person's member: the key's id and the most it may hold. */
      program?: { keyId: string; ceiling: MemberLevel };
    }
  | {
      kind: 'agent';
      level: MemberLevel;
      /** The level of the member who owns the agent, in the same space (M6). */
      ownerLevel: MemberLevel;
    };

/** What the member wants to do: the capability's own id, its fixed tier, and the area this call touches. */
export interface MemberAction {
  capabilityId: string;
  tier: 'observe' | 'act' | 'destructive';
  area: PermissionAreaId | null;
}

export type MemberVerdict =
  | { allowed: true; level: MemberLevel | 'outside' }
  | {
      allowed: false;
      reason: MemberRefusalReason;
      level?: MemberLevel;
      boundedBy?: 'owner' | 'key';
    };

export type MemberRefusalReason = 'not-a-member' | 'level-refuses';

export function mayMember(
  member: Member | 'not-a-member',
  action: MemberAction,
  space: SpaceInCall
): MemberVerdict;
```

`SpaceInCall` is §5's server-set value; `registry.invoke` always passes one. The predicate reads only `space.private` from it. The input has no place, no session and no turn field: place stays a fact about the request (M4), and the turn's own level stays the agent's turn gate (M6).

### 4.2 The effective level

- A person: `level`. A program acting as a person's member: the lower of `level` and `program.ceiling`.
- An agent: the lower of `level` and `ownerLevel` (M6).
- The order, high to low: `owner`, `admin`, `member`, `guest`.

### 4.3 The rows

**Decided here: two rows.**

| Member                                                                 | Every area, every tier |
| ---------------------------------------------------------------------- | ---------------------- |
| A person at Owner (including a program whose effective level is Owner) | Allowed                |
| An agent whose effective level is Owner, that is, an agent of an Owner | Allowed                |

**Placeholders: the Admin, Member and Guest rows.** They exist in the code as one constant beside the predicate so the shape does not change later, and they refuse every action until equal accounts give them values. The code comment and this text both say so. No path on a Mac reaches them (§4.4), no step depends on their values, and no proof tests a value in them; V2 tests only that the placeholder rows exist and that no directory in this spec answers a level below Owner. Equal accounts decide their values, with people's and agents' own defaults and switches to edit them (ADR `261006-235239`, which says each level is "a set of fine-grained switches at full power by default"; §15.6 records that this spec decides none of that).

**The difference between people and agents today** lives in two places that stay: the capabilities only a person may call (`audience: 'person'`, refused at step 3 of §1.5, before the member check) and the agent's own turn gate (step 10 of §1.5).

**Record rules stay in their domain.** Rules about one record, such as "a member removes only their own agent" or "an admin may not remove the owner", are not levels. They stay with the code that owns the record, as the space store keeps its removal rule today.

### 4.4 The answers, and today's answers on a Mac

| Input                                         | Answer                                                                                                                                                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'not-a-member'` in a private space           | `{ allowed: true, level: 'outside' }`: the gate refuses no one in a private space. The caller passes to its door and to today's checks of who is calling, which answer as now. The audit line records `outside` |
| `'not-a-member'` in any other space           | `{ allowed: false, reason: 'not-a-member' }`                                                                                                                                                                    |
| A member whose effective level is Owner       | `{ allowed: true, level: 'owner' }`                                                                                                                                                                             |
| A member whose effective level is below Owner | The placeholder rows answer `{ allowed: false, reason: 'level-refuses', level, boundedBy? }`; equal accounts replace them. No path in this spec produces this input                                             |

**In a private space the gate refuses no one.** Every caller the directory answers (§6.3) is either the Owner member, an agent member at Owner, or not a member; the first two are allowed by the Owner row and the third passes to its door. A second person account, which cannot exist on a Mac because registration closes after the first account (`services/core/auth/accounts.ts:4-7`), would be "not a member", pass the gate, and meet the class (e) checks of who is calling, exactly as it would today. Everything after the gate (preflight, spend, cards, the turn gate, confirm-first, the handler) runs as now. V3 proves this over the live registry.

**The directory answers what today's caller resolution answers, where it answers today.** For the doors that go through today's two room caller resolvers, the private-space directory is those resolvers moved into one function (§6.3); every other moved site keeps its own caller rule (§8.5). The rule they carry is decided: **while login is off, this computer is trusted, so a call from this computer with no session acts as its owner** (ADR `261015-125850`). So where the resolvers make a caller the operator today (a call with no agent token and no session while login is off, on the capability door; a read with no session, or any call while no owner exists, on the route door), the directory answers the Owner member. Where they resolve an agent, it answers that agent. Where they refuse (an agent token that cannot be verified, a chat with no agent of its own, a change with a per-user key or with no session once an owner exists, a call naming nobody while login is on), it answers "not a member" with that refusal's code, and the code that refused today refuses with the same code and words. So a room tool called on the outside MCP server (on by default) from this computer with no session acts as the owner while login is off, as `callerAuthor` makes it the operator today; with login on it names nobody and is refused by the room code as today.

**An agent in the private space holds its owner's level.** The private space has one person, and agents run at the level their owner set (the trust model in `AGENTS.md`). That level reaches nothing of any other person's and nothing at the front door, which keeps its own bar (M3). It is not the admin role of equal accounts. Where a moved check today is true only for the owner as a person, its named action says so and an agent is still refused (§7.2).

## 6. Who the member is (P-3)

### 6.1 The port

A small port on the space side, in `services/core/member-checks/member-directory.ts`:

```ts
/** Who the member gate asks. The caller is always the server-set one (§6.2); never an id from input. */
export interface MemberDirectory {
  /** The caller as a member of this space, or not a member, with today's refusal code where today's resolution refuses (§6.3). */
  memberOf(
    caller: MemberCaller,
    space: SpaceInCall,
    access: 'read' | 'write'
  ): Member | { notAMember: true; refusal?: string };
  /** The space's Owner member's account, for code that reads who the owner is as data (the member gate's own reads). */
  ownerAccountOf(space: SpaceInCall): { accountId: string } | null;
  /** Whether the space has an Owner with an account yet. On a Mac: whether an owner account exists. */
  hasOwnerAccount(space: SpaceInCall): boolean;
}
```

It is synchronous, as every owner check it replaces is today. It holds no cache of its own: each answer reads the store behind it, so a change (a key revoked, an agent removed) holds on the next call.

### 6.2 The caller it is given

`MemberCaller` is derived once, by the gate, from server-set fields only, in this order. The first that is present wins:

1. `context.caller` (item 10's server-set union: `person`, `program`, `agent`, `peer`), where item 10's builder set it.
2. A verified agent: `context.identity` or the server principal's agent (`serverPrincipal`), for in-session calls and the loopback listener.
3. `context.trusted`: the person at the app, in process.
4. Before item 10's D7 lands, for HTTP calls: the same order item 10 §6.2 states (an agent's token; a per-user key, a program; a peer credential; the person by `isPersonTurn`), read from the request facts by the one builder. G3 builds this reading if D7 has not landed; D7 then fills `context.caller` from the same code.
5. Otherwise: `none`.

`MemberCaller` also carries the server-set facts today's ladder reads (§6.3): whether a session is a browser session, the calling chat's session id, whether an agent token was presented, and whether login is on. Once item 10's D7 lands, a caller that presents an agent token that does not resolve, or two credentials of one kind, is refused before the gate as item 10 §6.2 says; until then the directory carries today's refusal for it (§6.3).

### 6.3 The private-space implementation: today's caller resolution, in one function

Today two functions decide who a room caller is. `resolveCaller` (`routes/room-caller.ts:121`) serves the routes, and `callerAuthor` (`services/rooms/service/room-caller-author.ts:93`) serves the capabilities, including the room tools on the outside MCP server; `routes/search.ts` uses the first. The two room functions then call it, and so does `memberOf`. It reads `readOwnerAccount` and `ownerAccountExists` itself; `services/core/member-checks/` is exempt from the ratchet by name (§11.3). When the private space becomes a tenant on the space store (item 16), only this implementation changes.

**Where this table applies.** It applies to the doors that go through `resolveCaller` and `callerAuthor` today, and nowhere else: the rooms, `routes/search.ts` and Direct chats. Every other moved site keeps its own caller rule beside the member check, inside `memberMay` (§8.5): the work queue keeps "a signed-in account must be the owner's, no account passes"; the delivery receipts keep "login off, all; login on, a verified account, and the owner sees every sender's"; and who may see a promise's source chat (`services/todos/todo-http-capabilities.ts:275`) keeps today's in-person test, the request's `accountOwner` fact (`lib/caller-authority.ts:286`), so a program with a key does not see the source chat under login, as today. | 11, confirm-first; 12, the handler | Nothing runs                                                                          |

The gate reads, for this call, the capability's fixed tier (`capability-definition.ts:129`) and its areas (`area`, plus every area `areasForInput` names). It calls `mayMember` once for each area, and allows only if every call allows. It reads `context.space`, which `registry.invoke` has already set (§5.2). On an agent computer it returns at once without asking (§5.3).

### 7.2 What it records

Every refusal writes one audit line: the caller (as the audit actor it already is), the space reference, the capability id, the tier, the areas and the reason. An allowed call adds nothing new to the audit trail; an `outside` caller's allowed call keeps today's audit line, with `outside` added.

**What it hands on, and how a moved check asks.** When the gate allows, it sets one more server-made value on the handler context, `member`: the directory's answer for this call, or `outside`. No caller can supply it, and **no handler reads its level**. A moved (a) check asks one function in `services/core/member-checks/`, `memberMay(context, actionName)` (or, for a rooms service method, the `RoomViewer` that `member-checks/` made for the call, §8.4), about a **named action**. §8.5 is the one table of every named action: for each of the 54 sites, its area and tier, whether it needs a person member, the caller rule it keeps, and today's refusal code and words.

`memberMay` applies the site's caller rule, then asks `mayMember` for the area and tier, then, where the action needs a person, checks that the member is a person. **`mayMember` never reads a member's kind**: no "who is calling" test enters the predicate. The handler gets yes or no and answers exactly as today. The ratchet counts any read of `member.level` outside `services/core/member-checks/` as an owner test (§11.1). A pending hand route asks the same function through the helper (§7.5).

### 7.3 What a refusal answers, on each surface

The gate throws `CapabilityToolError({ error, code: 'NOT_ALLOWED_IN_SPACE' })`. The map from refusal codes to problems is `routes/capability-refusals.ts` (where `NOT_YOURS` already answers `forbidden`, `:123`); G5 adds `NOT_ALLOWED_IN_SPACE` there, as `403 forbidden` (`packages/shared/src/problem.ts:63`) with one detail sentence that says what to do next: **"Your level in this space doesn't allow that. Ask an owner of this space."** (writing-app-copy: 14 words, no "we"). On a Mac no caller reaches it (§4.4).

**The test for (a).** Only a check that asks "may this caller act on this space data" becomes the member check. **A check with a person-or-agent half keeps that half.** Most of the rooms' (a) sites ask "is the viewer the owner, as a person". Each becomes a named action that needs a person member (§7.2), so an agent of the owner is refused where it is today. **A rule about a room's roster is not a caller check.** Some room methods ask whether some _other_ author is the owner: a system room keeps its owner, a private room may hold only its owner and their agents, an agent's roster keeps the owner as witness, the owner's read cursor marks the owner's notices read. ### 8.4 A rooms service method is told who is viewing

## 9. The computer-owner check (M5)

### 9.1 What it is, and which side it lives on

This computer's own things (workspaces, terminals, the local browser, the runtimes' sign-ins, running processes) are execution state, not space data (ADR `261122-173853`). They belong to the person who owns this computer, whatever spaces its agents work in. Their check is named for that, and it is **only an identity test**:

```ts
// services/core/computer-owner/computer-owner.ts  (computer side)
export interface ComputerOwner {
  /** Whether this signed-in account is the owner of this computer. No place, no session, no agent test. */
  is(user: { userId: string } | undefined): boolean;
  /** The owner of this computer's account id, or null while there is none. */
  accountId(): string | null;
}
```

- **Its answer is today's identity answer**: the account that owns this install, the first account ever made (§1.1). On a Mac the computer's owner and the private space's Owner are the same person; on a computer linked into someone's DorkOS in the cloud they are the same person too.
- **It is on the computer side.** `sides.json` places `core/computer-owner` as `computer`. It imports nothing from `core/auth` (front door) or the space side, so the wall's columns do not grow: the owner's account reaches it through an injected reader, composed in one named file, `startup/steps/computer-owner.ts`, from `core/auth`, or from item 6's `services/core/person-gate/` interface where C6 has landed (item 6 §7.5).
- **It never answers a member question**, and the member gate never answers a computer question (M7). An agent computer serves no person, so there `is` answers false for every account.
- **Its calls are not owner tests of space data.** The ratchet lists it among the names it does not count, with the reason "this computer's own things (M5)" (§11.1).

## 10. An agent's call, and what a refused caller learns

### 10.1 An agent's call (P-7)

- **The member tested is the agent.** A call from an agent's turn (in a session, through the loopback listener, through item 6's tools port, or over item 8's wire as `tools.call`) is a call by an agent that is a member of the space. The directory answers it as `{ kind: 'agent', level, ownerLevel }`, and the predicate uses the lower of the two (M6). In the private space both are Owner.
- **The turn gate stays as it is**, after the member gate: the agent's level for the turn, its areas (Blocked, Ask, Allowed), its outside-words marks, the held actions of a marked turn, spend and cancel windows, all unchanged (steps 6 to 11 of §1.5). The member gate can only refuse more; it never lets past what the turn gate holds.
- **The turn's `tier: owner | teammate`** (`AgentComputerTurnTierSchema`, `packages/shared/src/session-relay-agent-computer.ts:256`) says whose turn it is: the agent's owner's, or a teammate's. The gate note keeps it as the only trust fact `turn.start` carries, and the space side decides it from its own record (gate note §4). It is not a member level and the predicate does not read it. Gate note §8 names "the person whose turn it is as the one it acts for": this spec records that person on the audit line beside the agent, and leaves to item 15 whether the predicate should also bound the agent by that person's level (§19, question 7). On a Mac every turn is the owner's.
- **Nothing about member checks runs on a computer** (M7). A computer's `tools.list` is filtered on the space side (§7.4), and the rules copy carries no member data (gate note §8).

### 10.2 What a refused caller learns (P-8)

- **One refusal**: `403 forbidden`, "Your level in this space doesn't allow that. Ask an owner of this space.", on every surface (§7.3), and a tool refusal with the same code and sentence on MCP.
- **Where another record already requires "not found"**, the handler answers as a missing thing does, as today (§7.3); this spec adds no field for it.
- **A refused caller never sees the capability in a list** (§7.4), so it learns of a refusal only by naming a capability it was not shown.
- **The refusal never names** another member, another member's level, or the level rows.
- **`person_only` keeps its meaning.** A caller that is not a person, refused at step 3, gets `403 person_only` exactly as today.

- The directory's owner reads, `MemberDirectory.ownerAccountOf` and `MemberDirectory.hasOwnerAccount`, and **any read of `member.level`**, outside `services/core/member-checks/`.

**How it counts**, as requirements:

1. **By resolved binding, not by spelling.** A renamed import (`import { readOwnerAccount as owner }`), a destructured name (`const { isOwner } = deps`), a re-export, or a local alias of a counted function is still counted, and a different function that happens to share a name is not.
2. **Calls and values.** A call, or a reference passed as a value (an argument, an object property's value, the right side of an assignment, a default parameter), is one count. Imports, type positions, declarations, comments and literal fields are not.
3. **Per file, per name.** The baseline holds a number for each file and each counted name.
4. **No handler compares a level, and a rename does not lower the count.** A moved check asks `memberMay` about a named action (§7.2); a read of `member.level` anywhere outside `services/core/member-checks/` is counted as an owner test. Because the count follows bindings and counts the directory's owner reads, moving an owner test behind another name, a wrapper or the directory leaves the count where it was. Only removing the test, or moving it into a named action, lowers it.

**Not counted, with reasons the rule file states:** `isAtThisComputer` (a place, M4); `personSessionRequired`, `requireOperatorCookieUnderLogin`, `clearsTheAgentBar`, `resolveDecisionAuthority`, `isPersonTurn` and `isPersonAtTheApp` (who is calling, class (e), which stays); the computer-owner check (this computer's own things, M5); `memberMay` and the member gate.

### 11.2 The rule, the checker, the baseline and what they cost

- **The lint rule reads syntax only**, as the computer wall's does: `apps/server/eslint-rules/owner-checks.js` matches the counted names as written, per file, so an editor shows a new owner test at once, and it costs what any lint rule costs.
- **The checker resolves bindings.** `scripts/owner-checks/check-owner-checks.ts` (`pnpm check:owner-checks`) builds one TypeScript program over `apps/server/src` (the server's `tsconfig`, with no type emit) and resolves every identifier and member access to its declaration, so it catches the renamed import, the destructured name, the re-export and the alias that the lint rule cannot see, and it is the one that writes and enforces the baseline. Building the program takes about as long as one type check of the server package, so the checker runs in pre-push and in CI as `check:computer-wall` does (`lefthook.yml` pre-push, `ci/gates.yaml`), and its pre-push run goes through the load gate like any type check. The pipeline change carries a ledger entry in `ci/ledger/`. Tests: `apps/server/src/__tests__/owner-checks-lint.test.ts` (the rule) and `scripts/__tests__/check-owner-checks.test.ts` (the checker, with fixtures for each binding form).
- **The baseline.** `apps/server/eslint-rules/owner-checks.baseline.json`, with two sections:
  - `counted`: per file, per name, a number: the sites still to move. It may only fall, and it is empty after G12.
  - `allowed`: per file, per name, a number, each with a class (`b`, `c`, `e`, `definition`) and a one-line reason. It may only fall.
- **The checker's mechanics** are the wall checker's: `--update` lowers or removes entries and never raises; `--base <sha>` refuses an entry that grew, a new entry and a stale one, **in either section**.
- **Adding an allowed entry.** Pre-push refuses any added entry, as `--base` does in CI. The baseline file sits in Security's path patterns (G1 adds it), so a pull request that changes it needs Security's read through the gate that already exists (`pr-gates`). No checker reads labels.

## 13. The order (P-6)

1. **First, the ratchet (G1).** It needs nothing and costs one pull request. From the day it merges, no new owner test lands outside the allowed list.
2. **Then the pieces, in order:** the predicate (G2), the space in a call (G3), the directory (G4), the gate step (G5), and what a member sees (G6). G2 and G3 can run side by side.
3. **Then the (a) sites, smallest first** (G7 to G9b):
   - **G7 first: the work queue, the search scope, the delivery receipts, Direct chats and who may see a promise's source chat.** Nine sites. The work queue's owner-only actions and the to-do read are already capabilities with the check in the handler; search, receipts and Direct chats are routes, some of them pending hand routes, and search and Direct chats resolve their caller through today's room ladder. So G7 proves the gate, the directory built from that ladder, the named actions, the helper and the table test on every kind of site.
   - **Rooms last, in four steps** (G8a, G8b, G9a, G9b): the 45 of the totals. G8a threads the `RoomViewer` through the rooms service and every caller of §8.4, with visibility, the room list and search; G8b moves authority, projection, the whole-room export and the error details; G9a membership, lifecycle and updates; G9b bridges and repo rooms.
   - The other areas (schedules, agents, mini apps, packages, approvals, settings, and the rest of to-dos and chats) have no (a) site: their checks are of who is calling, or front door, or place, and they stay.
4. **This computer's own things (G10, G11):** the computer-owner check and its (d) sites. They can run beside the steps above.
5. **Then the end check (G12).** The `counted` section is empty; the tests of the sites that stay run whole.
6. **Last, and waiting for the opening (G13).** The space store shares the level type and the member view. It waits for the Community Space to open and its opening checks to be green (item 11; `AGENTS.md` "Where the system is going" rule 4).

## 18. Risks

- **The levels below Owner have no values yet.** They are placeholders that refuse everything, and no path on a Mac reaches them. Equal accounts give them values with Security before item 15 opens a team space to anyone below Owner.
- **Actions with no area.** About 120 capabilities declare `area: null` today. The decided rows allow every area, so nothing changes here; equal accounts choose an area for each on purpose before a level below Owner is used.
- **Many moved sites sit in hand routes.** Until item 1 converts them, a step calls the member gate from the route through one helper. The census keeps that list to routes item 1 still has to convert, and the helper goes when the list is empty.
- **The checks of who is calling still read "is there an owner".** They are class (e) and stay. Equal accounts change the registration policy and those checks together; until then registration closes after the first account, and the directory answers any other account "not a member".
- **Most room checks need a person member.** Their named actions say so, and V12 and V13 run an agent of the owner through every one.
- **The count does not reach zero.** After G12 the allowed sites stay, by class, until equal accounts (§11.5); the checker's binding pass costs about one type check of the server.
- **Counts drift.** The numbers here were read at `410069799f`. G1 records the baseline at its own head, and each step records its own drop.
- **Rooms is the largest area.** The 45 sites, and the `RoomViewer` threaded through every caller of §8.4, in four steps of at most 5 points, each with a table test over every site, every listed caller and every caller kind.

## 19. Open questions, each with a pick

1. **The predicate's home in the server.** Pick: `services/core/member-checks/` (the gate, the directory port and its private-space implementation), a new space-side folder DOR-4925 moves whole into the trust kernel. Other option: inside `services/core/permissions/`, a folder whose other half is the agent's turn gate.
2. **A refused HTTP call.** Pick: `403 forbidden` with one sentence that says what to do next; a handler that must answer "not found" keeps doing so (§7.3). Other option: `404` always.
3. **The catalog.** Pick: every reader hides what a member may not use (§7.4). Other option: it lists it, marked refused.
4. **A program.** Pick: its owner's member, bounded by the key's ceiling, which is the owner's level in this spec (§6.3). Other option: a member of its own, with a level its owner sets.
5. **The order of the (a) sites.** Pick: the work queue and two small reads first, then rooms in two steps (§13): a capability-backed check and a pending hand route first, the largest area last. Other option: rooms first, as the largest share.
6. **An outsider in a private space.** Decided: it passes to its door's own gate and is recorded as `outside` (§4.4), which keeps today's answers for the outside MCP server and A2A.
7. **An agent in a teammate's turn.** Pick: the predicate tests the agent, bounded by its owner, and the turn's `tier` and level hold the rest, as the gate note says (§10.1); item 15 confirms. Other option: also bound the agent by the level of the person whose turn it is.
8. **Hand routes before item 1.** Decided: call the one member gate from the route through one helper, held by a census (§7.5).

Decided and no longer open: one predicate in `packages/shared` (§4); four levels in the type, two rows decided (§4.3); the space is set by `registry.invoke` (§5); the directory is a space-side port whose private-space implementation answers from today's store (§6); five classes, with the front door, place, this computer's own things and the checks of who is calling keeping their own checks (§8.1, §9); the directory is today's caller resolution (§6.3); the space id is never rewritten (§5.4); the ratchet lands first and counts by binding (§11); the space store shares the level type only after the opening (G13).
