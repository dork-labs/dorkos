# Stop owned OpenCode work when its test run ends

**Status:** Specified. Implementation and acceptance evidence pending.  
**Author:** Codex  
**Date:** 2026-11-18  
**Base:** `1b9e910b937219e9676101193bdba6d0e4d23870`  
**Input:** [Accepted ideation](01-ideation.md) at `faf34f9f5d6f52855214166e6dbe906ce649dceb`, with source evidence for the Vitest, Docker and Windows contracts.

## Overview

Add explicit run/scope custody for native OpenCode work started by tests, evals and harness smoke. Cooperative cleanup remains; an owner outside the run's lifetime must also observe run-main loss and stop only its owned native resources. A worker-local finally, a signal sent, a closed port or waiting for a leader PID is not this guarantee.

The design covers normal return, failure, timeout, parent SIGINT/SIGTERM and hard parent death. Acceptance requires an outer observer to prove termination of the actual native resource and its owned descendants after the run main exits. Production background sidecar and guest service lifetimes retain their existing owners.

## Background / Problem Statement

Live [DOR-4500](https://linear.app/dorkspace/issue/DOR-4500) reports an old OpenCode sidecar alive17hours at roughly7%CPU after a test run ended. That is the issue's historical report; no new reproduction, account read or process probe was performed here.

Current manager directly spawns native `serve` (`server-manager.ts:484`), waits readiness and cleans startup/recycle/shutdown paths; TERM escalates after3000ms (`:683–695`). Conformance owns a file-level manager and `afterAll` shuts it down (`conformance.test.ts:398–419`). Those paths cannot run in a SIGKILLed owner. Eval child launcher uses a detached server group but returns early from kill after leader exit (`child-process-launcher.ts:304–316`), so group descendants are a distinct ownership boundary. Docker work persists in the daemon independently of the host CLI. Smoke uses blocking `spawnSync`, timeout and closed input; stdin is not an available parent-lifeline channel.

Installed Vitest4.1.11 worker-source analysis in accepted preflight found a fork worker can remain silent/alive after coordinator death. Therefore watching only worker IPC is insufficient. A run-main descriptor passed by Vitest provide() is structured-cloned metadata, not a transferable ChildProcess or exclusive live handle.

## Goals

- Every covered acquisition registers verifiable ownership before native work can escape startup cancellation or be published as ready.
- Run-main loss, worker/scope loss and normal scope end all initiate bounded owned cleanup; a live but stalled worker is handled by its existing operation deadline, not called dead.
- Preserve actual native PID/executable identity, stdout/stderr/stdin behavior, exit versus close, spawn errors and existing binary-integrity observations.
- Cover direct manager/helper tests, server/eval descendants, actual smoke CLI-run shape and eligible Docker/Windows entry points with explicit platform results.
- An independent observer proves a genuinely started owned child is gone after the actual run-main exits; removal/restoration control discriminates the main-loss backstop.
- Preserve all money gates, runtime permission/profile/model/account choices and production default lifetime.

## Non-Goals

Arbitrary escaped descendants, malicious same-user compromise, an OS sandbox, killing by process name/path/stale PID, a generic production process controller, changing guest systemd services, solving machine/daemon loss, model correctness or new paid execution. Custodian failure guarantees must be limited to the selected platform mechanism and evidence; no universal supervisor immortality claim.

## Technical Dependencies

Existing Node child_process/streams, Vitest globalSetup/run metadata, manager shutdown (15000ms stdout readiness;3000ms TERM grace), pinned native guards, eval launcher/disposer interfaces and smoke gates. `@dorkos/test-utils` is already an eval dependency; use a dedicated Node-only subpath, never its broad barrel. No SDK server-helper upgrade is selected.

Introduce an inert Node-only `@dorkos/test-utils/run-custody` subpath. Its runtime client and executable guardian/anchor are explicit `.mjs` files with adjacent declarations. Resolve executables by module-relative URL to an absolute path, independent of cwd. Server tests and evals use the subpath. The repository smoke entry may use its module-relative workspace path because the root smoke script does not own a runtime dependency on the test-utils barrel. Emitted eval JS must import the same executable-compatible subpath from its existing workspace dependency and prove the emitted entry can acquire custody. This package is private. Enabling custody in an installed DorkOS CLI or Electron bundle is outside this design.

## Detailed Design

### 1. Lifetime and authority model

Three owners are distinct:

1. **Run main:** actual Vitest coordinator, eval CLI/runSuite owner, or smoke run entrypoint. Its exclusive lifeline disappearing means the whole owned run is over, even if workers remain alive.
2. **Scope/worker client:** the file/eval/probe that acquired this resource. Its authenticated channel closing or explicit disposal ends that scope. It cannot keep the run alive after main loss.
3. **Custodian/backend:** remains outside the two monitored lifetimes and holds authority only over resources it actually creates and records. It cannot accept an imported PID/PGID/container as a cleanup target.

Use one lazy guardian per gated scope, outside the dedicated POSIX target group. It owns the main lifeline and an independent authenticated worker transport. A separate group anchor creates and stays in the target cohort. The guardian remains available for terminal observation after group escalation. Section 5 defines group signaling and confirmation.

No target, group anchor or wrapper inherits the exclusive run-main lifeline. Closing only a worker socket must not be the sole run-death signal. A main process that remains alive while blocked does not produce EOF. Operation deadlines remain separate.

### 2. Gates, lazy acquisition and main/worker handshake

Imports/globalSetup may provide inert run IDs and descriptor paths only. Every existing paid flag AND matching key decision must succeed before helper/anchor spawn, port/listener acquisition, native spawn or network check. Free local native custody proof is separate from paid model conformance; no fake key may be used to bypass a real paid gate.

**Vitest integration based on the installed 4.1.11 source:** append a small OpenCode custody globalSetup to the **server project** setup list, preserving the existing contract globalSetup and root load-wait setup. The current server configuration is `apps/server/vitest.config.ts:453`; its contract setup already records main `process.pid`, provides metadata and returns teardown (`src/http/__tests__/contract/global-setup.ts:111–136`). This limits new metadata work to server test runs and also covers direct package-config invocations that do not load root globalSetup.

The installed `cli-api.CnMVyzaz.js:13808–13813` initializes project/root global setups. `:10809–10826` executes setup in main and retains teardown. `:10723–10742` requires structured-cloneable provide values and merges root context into project context. The forks pool creates real child workers with advanced serialization (`:3124–3160`). `coverage.DM_a_rWm.js:180` defaults the pool to forks when no pool is selected. Current root/server configs do not override that pool. `init-forks.H5ZuobOQ.js` handles message/error and exits on EPIPE/ERR_IPC_CHANNEL_CLOSED when an error occurs, but installs no disconnect-exit handler. Acceptance must exercise a silent or blocked worker that survives run-main loss. The installed Vitest source shows why worker EOF alone cannot establish run-main custody.

**Narrow broker:** globalSetup creates only owner-private run metadata and a bounded metadata-inbox service in main. It provides a fresh run ID, inbox path/protocol descriptor and scope capability through documented provide/inject. No custodian, native child, listening socket or provider lookup starts at setup. After the existing gate succeeds, a worker writes an atomic metadata-only acquisition request. The main broker validates scope/request/generation and services it while workers run. It creates the custodian with an exclusive main-lifeline descriptor and returns only authenticated connection metadata. The worker then sends actual argv/env through the private in-memory connection. A ChildProcess or live descriptor is never structured-cloned through provide.

The broker polls the owner-private inbox with an unrefed asynchronous timer. A 25ms interval is an implementation default. Keep one sweep in flight, bound work per sweep and carry a fair cursor into later sweeps. Allow one outstanding request per scope. Defer eligible work to the next sweep when the current sweep reaches its work limit, subject to each request’s original startup deadline. The worker writes a versioned request by exclusive create and atomic rename. Validate strict size ≤4 KiB, one-time per-run request ID, scope capability and expiry. Correlate the response to the exact request, run and generation. Close admission synchronously before teardown, cancel in-flight work and close each main lifeline before awaiting cleanup. Claim each request once and never process it on a later watch generation. Setup may write metadata and start the poll, while only an eligible admitted request can cause a listener or process. Worker installs its cancellation and disconnect handling before sending spawn options. An unread/late reply does not keep the scope alive. Remove inbox metadata after confirmed teardown and retain bounded nonsecret evidence on uncertainty.

Where a caller already has a startup deadline, inbox acquisition, guardian authorization and authenticated transport establishment use its remaining time. Check that deadline before starting work and after each await. A guardian whose authorization has not arrived by that deadline closes without starting the target. Pass the remaining time into any readiness or useful-work phase already governed by that deadline. Where acquisition has no existing clock, its cancellation is tied to explicit close, main loss or scope loss. A late outcome is reconciled under the owned cleanup policy. Preserve independent clocks for later phases. Main retains the exclusive writer/IPC endpoint for its guardian. Worker EOF has its own channel. Neither pipe is target stdin, serialized by provide, duplicated into workers, inherited by a wrapper/anchor/target, or substitutable by a sampled PID.

**Precise proof still needed:** an owned fake-worker fixture and a small real Vitest integration must show this setup belongs to run main under root and direct server configs, the broker services an authenticated gated request after setup returns, and killing that main closes the exclusive guardian lifeline even when a worker remains silent or blocks its JS loop. Also prove no inherited descriptor, duplicate acquisition, late response or watch rerun can keep or recreate custody. Test gate refusal with zero helper/listener/native acquisition. The current source establishes the viable hook and cloning limits, not broker correctness or run-death cleanup. No Vitest patch/plugin or dependency upgrade is currently needed or approved.
For evals/smoke, the actual run-main directly owns the exclusive peer. Embedded library callers must provide an explicit scope or select a documented bounded single-owner mode; do not infer long-lived custody from ambient PID/env. A scope object is not inheritable global permission to register arbitrary children.

Requests/receipts in a filesystem inbox contain only protocol version, fresh run/scope/request IDs, capability/connection metadata and cancellation/terminal status. Never argv, env, provider keys, headers, stdout/stderr or errors containing spawn options. Capability is sensitive: owner-only directory/ACL, nonlogged, short-lived. Actual spawn specification and target environment travel only over the authenticated in-memory worker→custodian connection after gate/handshake. Main metadata broker need not receive provider env. No file fallback for large input.

### 3. Startup state machine and exact native identity

`inert → gated → acquiring → authorized → starting → running → closing → terminal | cleanup-uncertain`.

- Create custody/backend and authenticated streams before target spawn. Register native spawn observation at the actual spawn site, not merely the Node wrapper request.
- Recheck closing state after every awaited resolution/handshake and before resuming/publishing a native target. Main/scope loss while binary resolution/startup is pending latches closing; no late start may survive it.
- Native spawn success requires actual positive native PID, executable identity/hash when the existing pinned test requires it, and the actual spawn event. Error/no-PID is a failed attempt, not a native subject.
- Keep child handles/backend authority through native exit and stream close; a numeric PID that has exited is historical identity, not fresh authority to signal a recycled PID.
- `exit(code,signal)`, stream EOF/close, transport failure and cleanup completion are separate observations. A disconnected relay never fabricates native exit0 or hash verification.
- Existing guard's PRE/POST check must observe actual official native bytes and actual native process. If spawning moves across a helper, move its authoritative observation too; do not count a guardian PID as OpenCode.
- Do not publish a ready client until ownership is established. Manager's existing15000ms startup wait/diagnostics and3000ms TERM grace remain; do not extend deadlines to make custody pass.

### 4. Narrow spawn/lifecycle port and data streams

Use an internal `RunSpawnPort.start(request, signal): Promise<RunChild>` seam. The request carries the already resolved executable, argv, cwd, explicit env, current spawn stdio policy and applicable binary observer. `RunChild` exposes actual pid and executable identity, optional stdin, stdout and stderr streams, latched spawn/exit/close and integrity outcomes, and idempotent `stopAndJoin(reason, deadline)`. A readiness consumer can subscribe without missing early output or an immediate exit. Spawn failure may lack a native PID. Exit result, stream completion, transport failure and cohort cleanup remain distinct. Adapt the existing default directly around the production spawn without changing production lifetime or importing test-utils into production startup. Inject the custody implementation at the explicit test/eval composition seams. Never fabricate a ChildProcess or expose an arbitrary kill-by-PID port.

Create both lifelines and stdio before native creation. Separate bounded binary stdout/stderr/stdin lanes (64 KiB frames, 256 KiB outstanding per lane) from control and lifeline handling. Preserve per-lane byte order, EOF/error and write/end/drain backpressure. Pause a slow producer and keep control/EOF independent of data consumption. Retain fast-exit output until delivery or cleanup, then classify stream loss honestly. Honor the caller's current retention and redaction. Native hooks must not log spawn-request env or helper argv containing credentials. The authoritative pinned-binary observer binds to the exact executable at native creation and rechecks after actual close. A transport EOF does not mint a POST check, exit code or native-clean receipt.

Smoke keeps the existing `spawnSync` 1 MiB-per-stream output ceiling, streaming decode only after successful collection, and ENOENT versus ETIMEDOUT distinction. A limit violation enters bounded cleanup, preserves the result shape and never silently truncates a report into a successful result.

### 5. POSIX descendants and exited leader

The guardian launches its own detached POSIX group anchor before authorizing the actual target. The anchor launches target with no detach or new process group. An authenticated per-anchor pipe carries spawn and stop requests from the guardian. It is never inherited by target, and its EOF requests anchor cleanup if the guardian dies. The anchor catches/ignores the group TERM on its own process while targets retain normal signal disposition. Confirm actual group inheritance for the audited entry points before claiming native coverage.

Group signaling originates inside that verified anchor with group zero. It can only address its own current group. The guardian never signals a remembered negative numeric PGID. On normal close or either lifeline loss, the anchor sends group TERM, remains alive while the group drains, then issues at most one group KILL at the fixed grace deadline if needed. The anchor may die in that KILL. The guardian survives to observe terminal state. A KILL request, anchor EOF or leader exit alone is not proof. If the anchor disappears before its planned signal and the cohort might remain, report uncertainty. No stale-PGID retry or unrelated sweep.

Record the anchor birth identity, actual target and any observed ordinary descendants. Confirm direct native wait/stdio where possible, the anchor exit and group absence via a nonsignaling kernel observation (group existence check); if the group remains, is recycled, observation is denied, or required exit/integrity is unobservable, do not mark clean. A reused PGID may therefore cause bounded uncertainty without signaling anyone. The outer proof separately observes exact owned identities, including leader-exits-first and a resistant member. Escaped processes are outside this cohort contract. A killed anchor cannot report a missing native wait result, so hard escalation may yield confirmed cohort cleanup with native exit/integrity separately unknown rather than an invented normal-close result.

### 10. Terminal outcomes and cleanup

Use distinct terminal observations: never-acquired, spawn-failed, native-closed(code/signal plus stream close/integrity), cleaned-owned-cohort/container, unsupported, and cleanup-uncertain. These are internal receipt concepts, not a public schema proposal. No helper EOF or outer timeout translates to success.

Normal disposal, operation failure, timeout, SIGINT/SIGTERM and main/scope loss converge on idempotent closing. Latch primary error separately from cleanup errors (including a thrown undefined), independently attempt all known owned cleanup, then preserve sole/aggregate diagnostics with bounded secret-safe fields. Do not swallow uncertainty to report a clean run. Profiles/evidence are removed only after owned lifecycle is confirmed; retain them on uncertain ownership. Do not signal unknown/unowned identities.

Use monotonic absolute deadlines, checked before every queued operation and await. Start the 15,000ms manager readiness clock before custody acquisition at the actual boot attempt; preserve the earlier binary/profile resolution boundaries and stop a late result on cancellation. The eval health clock still starts after `launcher.launch()` resolves (default 60,000ms or caller override), as in `harness-server.ts:391–402`. Acquisition uses any separate enclosing deadline and owner-loss cancellation. It does not consume the later health window. Preserve eval turn and suite budgets. Smoke's existing 45,000ms free and 300,000ms armed operation limits include custody acquisition and useful process execution, with no new operation attempt or retry. For cleanup, share the existing eval 5,000ms termination/reap ceiling as the host join ceiling, with existing manager 3,000ms TERM grace inside, leaving up to 2,000ms for confirmation. For the eval child path whose current kill is immediate KILL, retain immediate escalation and use its existing 5,000ms confirmation window. A timeout-triggered smoke terminates useful execution at its original deadline, then joins using the same bounded host cleanup rule without reporting that cleanup as continued probe time. If an enclosing hook/test has less remaining cleanup budget, clip to it and report uncertainty. Section 8 records the separate Docker probe and cleanup limits. Expiry changes the result to failure/cleanup-uncertain, never a successful join. Guardian lifecycle is independent and continues its already armed bounded cleanup if the caller's wait ends. No slow-host timeout ratchet or retry.

## User Experience

Internal verification behavior only: ending or killing a run stops the OpenCode work it owns instead of leaving abandoned CPU/processes. Existing gates, reports, output and signal exit behavior remain recognizable. Unsupported custody or uncertain cleanup produces explicit infrastructure failure with preserved evidence, never mocked fallback or native pass. No user-facing feature, model or security-isolation claim is added.

## Testing Strategy

The tests below define implementation acceptance. Native, daemon and fixture outcomes remain to be proven.

1. Independent outer observer starts an owned offline main/worker fixture. Positively observe live actual target/native identity and any claimed descendant/container **before** terminating parent. Require nonzero actual subjects; registration intent alone cannot pass.
2. Normal return, thrown failure, operation timeout, parent SIGINT, SIGTERM and SIGKILL; exact run-main exit is observed separately from worker/target. Include silent and blocked-but-live worker after main death, and live-main worker loss. Stalled main is not EOF.
3. Startup death before authorization, after spawn before ready, and late resolver/acquisition completion. No target publishes after closing; known late resource cleanup must be observed.
4. TERM-resistant child requiring escalation; wrapper versus actual native PID; leader exits first with live owned descendant; unrelated owned positive remains alive. Never signal system/unowned processes or infer absence from elapsed sleep/closed port/PID lookup alone.
5. Streams: fast spawn error/no-PID, immediate exit before listeners, exit-before-close, early ready output, stdout/stderr ordering, stdin end, bounded backpressure, consumer loss and unread output. Transport error cannot satisfy native exit/hash verification.
6. Actual pinned OpenCode serve over fresh synthetic profiles/offline-local settings, no provider/model request/credential spend. Preserve PRE/POST actual executable verification at the true spawn and actual positive PID/close. Runtime pipeline readiness proof is separate from this process-only proof.
7. Green→remove **only run-main-loss backstop**→intended owned-child-not-gone assertion fails with live native subject, independent positive survives→outer observer cleans only recorded identities→restore fresh green. Worker EOF alone must not rescue a deliberately silent-worker mutation. Setup/timeouts/zero native count are not intended kills.
8. Docker exact-container running positive then main loss, confirmed stop/remove or retained-stopped artifact; lower-level path and CLI's existing refusal each get their own case. Missing daemon explicitly unverified. Container membership is not host group membership.
9. Windows kernel-backed fixture with retained exact process handles, leader-exits-first descendant, creation-time Job assignment versus controlled missing-assignment failure, owner death before resume, handle-leak/breakaway negative controls, nested-job failure and Job close/kill confirmation. No Windows success from taskkill/POSIX/macOS. Native real-caller integration follows actual backend proof; no paid model needed.
10. Gate ordering and secret canaries: unarmed paid paths create zero helper/listener/container/native resources. Inbox, argv/env logs and error receipts must not contain sentinel provider secrets; actual spawn env remains exact existing projection over authenticated memory channel.

Mocks only at external platform/transport boundaries for unit protocol/error tests; real owned-process fixtures prove lifetime, no fake success receipts. Report exact selected/eligible/executed counts and platform skips, raw parent/native/backend exits, and before/after binary/source bindings. Source analysis is not a pass.

## Performance Considerations

Lazy per-gated-scope custody; no default production process or eager global service. Streams remain bounded/backpressured; main-loss observation remains independent of output. Reclaim helper/anchor/channels on confirmed terminal; do not replace orphan sidecars with immortal guardians. Measure actual helper counts and cleanup rather than imposing an unrelated total-process floor.

## Security Considerations

Authority is creation-bound, not discover-and-kill. Private owner-only metadata/ACL plus authenticated capability; exact run/scope/generation ownership; no arbitrary PID import, stale group retry or broad sweep. Existing credentials/paid decision/profile/permission controls precede acquisition and stay unchanged. No spawn env/args/secret fallback to files. Same-user compromise, escaped descendants, machine/daemon loss and unproved platform behavior are not hidden by the design.

## Open Questions

- ~~(RESOLVED) Where does run lifetime authority live?~~ **Answer:** Use separate run-main and scope lifelines and a guardian outside the POSIX target group. **Rationale:** A worker and its native descendants can outlive run-main death, and group escalation must leave a reporter available.
- ~~(RESOLVED) How does Vitest authorize a gated worker?~~ **Answer:** Use server-project globalSetup, a metadata-only inbox with fair bounded processing per sweep, and one outstanding request per scope. **Rationale:** This reaches root and direct server invocations while keeping credentials in memory and existing caller deadlines in force.
- ~~(RESOLVED) How do Windows callers obtain custody?~~ **Answer:** Build the Job guardian from checked-in source for the eligible Node architecture and load it through the private workspace dependency. **Rationale:** Creation-time Job membership closes the suspended-create assignment gap. The explicit source build keeps test tools outside product distributions.
- ~~(RESOLVED) Which Docker transport will implementation prove first?~~ **Answer:** Use the existing absolute Docker CLI's `system dial-stdio` channel with selected-daemon authentication and exact resource identity. **Rationale:** This gives the guardian one connection to prove and leaves bounded alternatives available for eligible selectors the raw stream cannot serve. Compatibility is an acceptance result.
