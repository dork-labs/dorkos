# Design note: the permission gate across the wire

**For:** the architect, Security, Dorian · **Status:** ideation; Security's questions answered by an independent security read, 2026-11-24, and read again by Security, 2026-11-24; the operator's four questions answered, 2026-11-25 · **Builds on:** ADR `261124-150516` (two sides, one contract), `specs/everything-is-a-space/design-agent-computers.md` §2 and §3 · **Tickets:** DOR-5165 (this note), DOR-5166 (the build), epic DOR-5152

Every claim about today's code names a file in this repository at the commit this note was written on. Line numbers are approximate and move with the code.

## 0. The short version

- An agent's **rules live in its space**. A computer that runs the agent gets a **read-only copy** of those rules for each turn, signed by the space side, and checks its own runtime against it.
- The line is drawn by **authority, not by effect**. Anything that uses something the space holds (a connection, a person's attention, another agent, a setting, a post in a room, a credential) is decided on the space side, on every call. Anything that uses only the computer's own files, processes and network is decided on the computer, from the copy.
- A shell command or a file edit is checked **beside the runtime**, with no round trip. A DorkOS tool call already crosses the wire as `tools.call` and is decided where it runs, on the space side.
- **The turn's level and its marks come from the space side's record of the turn.** The computer may make a turn stricter (it saw the agent read a web page); it can never make one looser. A turn on a computer the space's owner linked makes standing changes, such as changing an agent or adding an MCP server, the same way a turn on the Mac does: it runs and is recorded, with the computer named. A hold applies only when the turn carries an outsider mark, or the computer is not one the owner linked (§4).
- A question that needs a person becomes a **card on the space side**. Only someone the space allows may answer it, never the agent that asked. A card raised on a computer is shown as that computer's report.
- **Lowering an agent's level, pausing it or ending a grant** reaches a running turn within one frame while the channel is up, and by the lease's end when it is down (§3): the next DorkOS tool call sees it at once, the next local check sees it as soon as the new copy lands. A runtime that cannot tighten its mode in place is stopped, if its mode lets through, unasked, what the new level would ask about or refuse.
- **The plain limit:** a computer someone has taken over can ignore every local check. The copy keeps honest computers honest. What stops a compromised one is that it holds no space credentials and every action with authority outside it is decided off it.
- On a Mac both sides run in one process. The **same payloads** pass by function call, so there is one design, not two.
- An independent security read, 2026-11-24, answered the eight Security questions. Its answers are decisions in the body, and every requirement a builder must meet is one table in §10.

## 2. The split, as a rule

**The rule.** A decision stays on the space side when the action uses authority the space holds. A decision may be made on the computer when the action uses only the computer's own resources. The copy carries what the computer needs to make its decisions the way the space side would.

Why authority and not effect: a file edit changes state, but only on the computer, and it must be decided beside the runtime. A web fetch changes nothing, yet it is the moment outside words enter a turn. "Decide anything that changes state on the space side" would put every file edit on a round trip and still miss the read that matters. The architect's leaning is right in substance; this is the sharper wording.

**The threat model behind it.** The computer runs agent code, packages and pages the agent read, so it is untrusted (ADR `261124-150516`). The space side is trusted by the agent's owner (ADR `261122-173853`: "the permission gate reads the agent's identity on a server its owner trusts"). Outsiders seed no power and third-party code needs a yes (ADR `261006-225605` items 4 and 5). So a fact that grants power must be read where the agent cannot write, and a check that only protects the computer from its own runtime can live on the computer.

| Decision                                                                        | Where it is made                           | Why                                                                                                                                                                              |
| ------------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Whether a turn starts at all (pause, agent removed, computer not this agent's)  | Space side, always                         | It spends the space's trust in the agent; the computer runs only what it is told (`turn.start`)                                                                                  |
| The turn's level, tier and starting marks                                       | Space side, always                         | Power flows from who started the turn; the computer cannot know the starter                                                                                                      |
| Every DorkOS tool call: permission, tier, card, spend, cancel window, hub-owned | Space side, always                         | The tool runs there and uses space authority; `tools.call` already crosses                                                                                                       |
| Which DorkOS tools the agent sees                                               | Space side (`tools.list`), cached per turn | Blocked areas stay hidden; visibility is a member check (§8)                                                                                                                     |
| A connection's use, including writes to an outside account                      | Space side, always                         | The computer holds no connection credentials (design-agent-computers §0)                                                                                                         |
| Who may answer a card, and recording the answer                                 | Space side, always                         | Separation of duties (ADR `261006-225605` item 8)                                                                                                                                |
| Standing rules ("Always allow", repo hook consent, the person-set floor)        | Space side, always                         | A rule the agent could write is a rule the agent grants itself                                                                                                                   |
| The audit record                                                                | Space side, from what it saw               | The computer's report is a claim, stored and shown as that computer's report, never merged into the space side's decision records; DorkOS tool calls are recorded where they run |

**The hard middle, said exactly.** A runtime's own prompt for a shell command or a file edit is decided on the computer, by the same pure functions that decide it today (`runtimes/shared/policy/approvals.ts`, `core/protected-paths/protected-path-check.ts`, the Claude Code hooks), reading the copy instead of the in-process maps. If that decision is "ask", the ask crosses as a card (§5) and only the answer comes back. A DorkOS tool call is never decided on the computer: the computer forwards it and waits for `call.result`. The computer's own `/mcp` maps the run's agent token to an agent and forwards; it holds no gate of its own for DorkOS tools beyond the hub-owned refusal, which it may apply early to save a trip. The space side always applies the hub-owned refusal itself as well and never relies on the computer's.

## 3. The rules copy

**What is in it.** One object per running turn, small enough to fit one sealed frame (`AGENT_COMPUTER_MAX_BODY_BYTES` in `packages/shared/src/session-relay-agent-computer.ts`):

| Field                        | Holds                                                                                                                              | Read by                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `label`, `version`           | A fixed label such as `dorkos-agent-rules/v1`, and a counter that only rises (per run, or per agent with every live run re-signed) | The signature check                           |
| `computerId`, `agentId`      | Which computer and which agent it is for                                                                                           | The check: a copy for another computer fails  |
| `runId`, `sessionId`         | The space side's run record id (ADR `261124-150517`) and the chat                                                                  | Binds the copy to one turn                    |
| `level`                      | The mode the turn runs at, after the agent-level bound and any carried ceiling                                                     | Every native decision                         |
| `tier`, `marks`              | `owner` or `teammate`; the outsider and teammate marks; the outside-words note                                                     | The runtime's hooks and status reads          |
| `chosenFull`                 | Whether a person set this chat to Full (the "asks nobody" case)                                                                    | `canUseTool`'s Full branch                    |
| `areas`                      | Permission area states, for the few native checks that read one (shell reads of protected files)                                   | The shell guard                               |
| `protectedPaths`, `roots`    | The list from `protected-paths.ts` and this turn's roots                                                                           | Every file tool                               |
| `readFolders`, `heldFolders` | Folders a read skips the card in; folders a held turn may not touch                                                                | `canUseTool`, held-folder hooks               |
| `nativeAllow`                | The standing "Always allow" rules for native tools, held on the space side                                                         | The runtime's allow list, rendered per launch |
| `repoConsent`                | Digests of repo hooks and settings a person let run, and those refused                                                             | The launch                                    |
| `toolsVersion`               | The `tools.list` answer's version, so the computer knows when to ask again                                                         | The computer's `/mcp`                         |
| `notAfter`                   | When the copy stops being good (§3, "How long")                                                                                    | Every check                                   |

What it never holds: a credential, a bearer, a connection's identity, the person-set floor itself (only its result), another agent's rules, or anything about people.

**Who signs it, and with which key.** The space side signs with the same long-lived Ed25519 key the computer already pinned at link time: on a cloud home, the hub signing key (`services/core/hub/hub-signing-key.ts`), whose public half the computer stores in its pin (`services/core/session-relay/pin-store.ts`). That key signs only data that starts with the relay's one label line, `dorkos-session-relay/v1` (`signWithHubKey` refuses anything else). The handshake and the link messages (`session-relay/link-signature.ts`) both start with that line and differ by a kind word after it. The rules copy is signed with that same key under a second, separate label, so a copy can never be read as a transcript and a transcript can never be read as a copy. Decided with the security read:

- The one-label check becomes an exact allow list of complete label lines, each ending in a newline, none a prefix of another. The verifier checks the label before it parses anything.
- The signed bytes are a canonical encoding (fixed field order, no duplicate keys), not whatever a JSON printer emits. The signed body carries `computerId`, `agentId`, `runId`, `version` and `notAfter`.
- A person's own computer has no hub key (`hub-signing-key.ts`: "both readers throw there"). A Mac acting as the home for other computers makes one on its first computer link, the same way the hub's is made: a file only its owner can read, written in one atomic step, never in the environment or the config. The endpoint other computers dial on a Mac home sits outside `/api`, checks the relay credential before it reads the request, and never goes around the session gate.
- Every signing key is a secret no agent tool may read, at any level, Full included; a test proves it. Losing the key means a deliberate re-pin of every linked computer, never a silent new key.

Why sign at all, when the channel is already sealed and authenticated (`session-relay/channel.ts`)? Because the copy leaves the channel: it is kept on the computer's disk so a turn keeps its rules across a short drop, and it is handed to a runtime's hooks, a sidecar or a guest that is not the channel's endpoint. A signature lets each of those check it without trusting the path it came by, and lets the computer refuse a cached copy an agent edited on disk.

**How the computer checks it.** Before first use and on every reload: the signature against the pinned key, the label, its own computer id, a known agent, a `runId` it was told to start, a version no lower than the last it accepted (no rollback), and `notAfter` in the future. When one agent has two turns on one computer, the version counts per run, or every live run's copy is signed again on each change, so no running turn is left on an older copy. Any failure means no copy, and no copy means the strictest behaviour: every native call that would not run in the runtime's default asking mode asks, and with nobody reachable to ask, it is refused. The computer keeps the last version it accepted, and the list of turns it was told to start, only in memory, and it accepts a copy only for a `runId` whose process still lives. So a restart never reopens an older copy, and nothing an agent's shell can delete brings a looser copy back. It never reads the identity copy that `agents.sync` gives it (`design-agent-computers.md` §1) for a trust decision: only the signed rules copy.

**Who may touch it on disk.** On every computer that is not the person's own Mac (a cloud agent computer, one added over SSH, the computer-local guest), agent processes run as a different operating system user from the computer side. The computer-side code, its private key, its pin store and its cached copy belong to the computer-side user, and the agent user can neither read nor write them. On a person's own Mac this is recommended, not required for this build. The purpose is narrow: it keeps the signing key, the pin store and the cached copy out of reach of agent tools. It is not a fence around what agents may do.

**How long it is good for.** The life of one turn, with a hard stop when the turn ends, and capped by a lease of at most five minutes that the space side renews while the channel is up (on `computer.status`). The computer counts the lease on its own steady clock from the moment it received the copy, never by comparing wall clocks across machines. A new turn always gets a new copy with `turn.start`. Marks may be raised inside a copy's life (below); nothing else changes without a new version. A renewal is a new signed version with a later `notAfter`.

**How a change reaches a running turn.**

| Change                                                              | The DorkOS tool call in flight                   | The next DorkOS tool call | The next native call                             | The running process                                                                                                                                             |
| ------------------------------------------------------------------- | ------------------------------------------------ | ------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A person lowers the agent's level                                   | Finishes as decided; it was checked at call time | Decided at the new level  | Decided at the new level once the new copy lands | Tightened in place if the runtime can; if not, interrupted when its running mode lets through unasked something the new level would ask about or refuse (below) |
| A person pauses the agent                                           | Finishes                                         | Refused                   | Refused (the new copy says paused)               | Interrupted, as `hold-paused-turns.ts` does today                                                                                                               |
| A person ends an "Always allow" or a grant                          | Finishes                                         | Decided without it        | Asks again once the new copy lands               | The runtime's allow list is re-rendered at its next launch                                                                                                      |
| The space side marks the turn (a DorkOS tool returned outside text) | Its result carries the new mark                  | Held as marked            | Held as marked                                   | Unchanged                                                                                                                                                       |

Today a turn already running keeps its launch mode when the level drops (`agent-level-bound.ts`: "Out of scope: a turn already running when the level changes (DOR-3177)"). The push of a new copy closes that, on a Mac and on a computer alike. When the runtime cannot tighten its mode in place, the turn is interrupted, but only when the running mode lets through, without asking, something the new level would ask about or refuse. Codex at full access is the plain case: `approvalPolicyFor` in `codex/app-server/turn-parts.ts` sets its policy to `never`, so it asks nothing. Otherwise the new level applies in place. The run record notes "stopped: level lowered", and the turn is never continued at the old level. The earlier draft let such a turn finish with every new ask decided at the new level; the security read replaced that.

**The computer must confirm a stricter change.** A pause or a lowered level needs an acknowledgement from the computer. With no acknowledgement within a few seconds while the channel is up, the space side sends `session.interrupt`. With none by the lease's end, the space side counts the computer as unhealthy and starts no new turns there.

**When the computer cannot reach the space side.** DorkOS tool calls fail: there is nothing to forward to, and they report so to the agent. Asks are refused, since nobody can see the card. Native calls the copy already allows keep running until `notAfter`, so a dropped connection does not kill a file edit half way. After `notAfter` the turn ends on that computer. This is the lever working: the lease is how a pause, a lowered level or a revoke takes effect on a computer the space side cannot reach. The space side records the run as "ended: lost contact", and recovery does not continue it unattended. No new turn starts, since only the space side starts turns. All of this assumes a space side that is on. When the home is a Mac that sleeps, a cloud computer's turn ends at the lease's end; whether that is right is part 6 of `01-ideation.md`.

**What an attacker who owns the computer can do.** Ignore every local check; run any native action under the computer's own operating system rights; read the copy (it holds no secret); omit marks it was supposed to raise; replay an old copy to its own runtime. What they cannot do: forge a new copy or raise a level, since they lack the space's private key; act through a connection, post, message, schedule or change a setting except as the agent itself, through `tools.call`, at the level the space side holds for it; reach any hub-setup action (the hub-owned table); answer their own card; or make the space side's audit say anything but what it decided. **So the copy protects honest computers and honest runtimes. The wall is that everything with authority beyond the computer is decided off it.**

## 4. Level and marks come from the space side's record

`design-agent-computers.md` §3 already says the tier for a bridged tool comes "from the hub's own record of the turn, never from the computer". The same holds for runtime-internal checks, because those checks read the copy, and the copy is built from the space side's record:

1. When a turn is accepted, the space side writes its run record (ADR `261124-150517`): run id, status, attempt, the runtime chat. Beside it, in the same write, it stores the level and marks it computed at turn start (rows 2 and 3 of §1). The copy is built from that durable row and carries its `runId`. Since DOR-4148 the outside-words note is saved with the chat and outlives a restart, and step 1 stores every mark on the run row, so the copy for a recovered or continued turn keeps its marks.
2. The computer never sends a level. Of the trust facts, `turn.start` today carries only `tier: owner | teammate` (`session-relay-agent-computer.ts`, `AgentComputerTurnTierSchema`); it gains the signed copy and nothing the computer can choose.
3. Marks move one way. The space side raises a mark when a DorkOS tool or a connection read returns outside text (`capabilities/mark-caller-turn.ts`); it records it on the run and pushes a new copy. The computer raises a mark when its runtime reads outside text natively (the job of `claude-code/tool-gate/outside-text-hook.ts` today): it applies it to its local copy first, so its own next check is already strict, then reports it. The space side ORs it in. No message from the computer can clear a mark; only a new turn, with a new run record, starts clean, which matches `markRunningTurnOutsider` today ("it lasts until the conversation's next turn starts").
4. Ordering: the mark report and a following `tools.call` ride one sealed channel with sequence numbers, so the space side must handle frames in order and apply a mark before it decides the call after it. Each `tools.call` should also carry the computer's current marks, under a new feature id with a strict schema. The space side only ORs them in: no field can clear or lower a mark. This becomes a Must if in-order handling across handlers cannot be proven.
5. Every `tools.call` and `tools.list` is bound to a live run: it names its `runId`, or the space side finds exactly one live run for that agent and chat on the channel's proven computer. Level and marks come from that run's row. A call for a run that has ended, been paused or been stopped is refused.

**Standing changes on a remote computer.** A computer the space's owner linked into the space is the owner's own. Its turns get the same standing-change behaviour as local ones: the change runs at the agent's level and is recorded, with the computer named in the audit. Where a turn runs does not put a person back in the loop (trusted by default, `meta/PRINCIPLES.md`). The hold in `marked-turn-holds.ts` covers changing an agent (`operator.update_agent`), patching config (`operator.config_patch`), creating a binding (`binding_create`), marketplace installs (`marketplace.*`) and MCP server changes (`mcp.*`). It applies in two cases only: the turn carries an outsider mark, whether the computer reported it or the space side set it; or the computer is not one the owner linked. Whether the owner linked a computer is read from the space side's own record of it, never from what the computer sends. Marks live on the run record, and a computer can only add one. Writes through a connected service (`connectors.execute_write`) stay on the mark, as today. The independent security read asked for every remote turn to start held. Security's second read (2026-11-24) replaced that: it would ask a person about their own agent on their own computer, with no outsider involved.

## 5. Approvals across the wire

- **Raising.** A native ask on the computer becomes an approval event on the turn's stream, which `session.stream` already carries, and is answered with `interaction.respond` (`packages/shared/src/session-relay.ts`). The space side records it against the run and shows the card in the person's chat. A native card is a report from an untrusted machine: the space side cleans the tool name, input and command before showing them, labels the card with the computer's name, and never words it in DorkOS's own voice.
- **The direction is the reverse of a linked Mac's.** A linked Mac decides what the web may answer and refuses most of it (`session-relay/relay-approvable.ts`: no standing raises from the web, no `mcp__*` tools), because the Mac is in charge (ADR `261015-042933` rule 5). An agent computer has the space side as its only controller, so every card may be answered there. One idea carries over: an answer never becomes a standing rule on the computer.
- **Who may answer.** The space side's rule (`approvals/decision-authority.ts`): a proven person, never the agent that asked; later any role holder but the asker (ADR `261006-225605` item 8). The answer goes back as `interaction.respond`, bound to the ask's id and a digest of the exact input the card showed. It works once and expires. A native answer never becomes approval for a DorkOS tool, a grant, or anything outside that computer and that run. A computer has no person at it, so it never decides its own card.
- **While it waits.** The runtime holds that one call, with the existing wait and park timing (`runtimes/shared/timing/pending-approval-timing.ts`); the rest of the turn behaves as it does on a Mac. An "Always allow" answer is stored on the space side as a standing rule and reaches the computer in the next copy; it is never written by the computer into the workspace, where the agent could write the same rule itself. The card shows the exact rule the space side will store, built by the space side, not text the computer wrote. Teammate turns get an empty `nativeAllow`, and their cards never offer "Always allow" (ADR `261015-042933` rule 6).
- **What an "Always allow" may be.** The rule moves to a space-side record on a Mac too, so the agent cannot write the same rule into its own folder. It comes from a closed set: one tool, or one exact command pattern. It is never a broad tool by prefix (`git`, `gh`, a language interpreter, a package runner). It is scoped to one agent and one computer, and checked again against the current level on every use. A launch ignores allow rules in settings files the agent can write.
- **Restarts.** If the space side restarts, the computer still holds the ask; on reconnect it lists pending asks and the space side shows the cards again. If the computer restarts, the process that asked is gone, so the ask is gone: the space side withdraws the card and the run record marks the turn as waiting on a person, which the recovery rule never continues (ADR `261124-150517`).
- **DorkOS tool cards** are already space-side: a `destructive` call raises its card where it runs, and the computer only waits on `call.result`.

## 6. The Mac case

On a Mac both sides run in one process, and that stays true until the spike in ADR `261124-150517` says otherwise. What changes: the runtimes stop reaching into the space side for trust facts, and instead read a `TurnRules` object handed to them at launch and updated by a callback, with the same fields as §3. What does not change: what is decided, and by which function. In-process, the copy is passed as a deeply frozen object and not signed, and a change is a new object through the callback, because runtime SDK code runs in the same process; the payload type and the builder are the same ones the wire uses, so a Mac and a cloud computer cannot drift. The object a runtime sees can only tighten: its one setter raises a mark, and it has no setter for a level or an allow rule. A test proves runtime SDK code cannot loosen it.

The shortcuts that have to go behind the split, in the order to move them so nothing breaks:

1. **Build the copy, change no reader.** A space-side builder that assembles the `TurnRules` from today's readers (`agent-level-bound.ts`, `turn-levels.ts`, `full-autonomy.ts`, `protected-path-roots.ts`), attached at the decorate seam (`core/runtime-seam/decorate-runtime.ts`). A test asserts it equals what each runtime reads today.
2. **Doe and OpenCode first.** Their checks already take plain inputs (`runtimes/doe/approvals.ts` takes a mode and roots; `opencode/messaging/approvals.ts` takes the mode). Point them at the copy.
3. **Codex.** `approvalPolicyFor` and the permission profile read the copy's level (`codex/app-server/turn-parts.ts`).
4. **Claude Code's native gate.** `createCanUseTool` and the hooks in `launch-resolver.ts` read the copy instead of the session's ceiling maps and `marksOf`. The outside-text hook raises the mark through the copy's callback instead of calling `markRunningTurnOutsider` directly.
5. **Claude Code's tool server.** `runtimes/claude-code/mcp-tools/index.ts` builds an in-process SDK server that calls `registry.invoke` with an identity resolved from the working folder. It moves out of the runtime and behind `tools.list` and `tools.call` (DOR-4926); on a Mac that call is a function call.
6. **Connection authority.** The per-turn bearer and its process-local permit (ADR `260908-153657`, `connector-turn-context.ts`) stay on the space side. On a remote computer there is no permit to hold: the run record and the channel's proven computer stand in for it, and connection calls are `tools.call`.
7. **Standing rules.** "Always allow" for native tools and repo hook consent move to space-side records that the copy carries (`always-allow-breadth.ts`, `repo-config-consent.ts`), with the limits in §5.

A lint ratchet counts runtime imports of `core/turn-power`, `core/agent-identity`, `core/capabilities`, `core/approvals` and `core/permissions` and may only fall. It reaches zero when the computer entry's wall (DOR-5158) can hold.

## 7. Latency and cost

Per turn, on a remote computer:

| Exchange                          | Round trips                            | Cached                           |
| --------------------------------- | -------------------------------------- | -------------------------------- |
| `turn.start` with the signed copy | 1                                      | The copy, for the turn           |
| `tools.list`                      | 1, then only when `toolsVersion` moves | The list, per turn               |
| Each DorkOS tool call             | 1 each (already true by design)        | Nothing: decided fresh, as today |
| Each native check                 | 0                                      | Decided from the copy            |
| A mark raised on the computer     | 0 (sent on the stream, no reply)       |                                  |
| A new copy after a change         | 0 (pushed)                             |                                  |
| A card                            | 1, plus the person's time              |                                  |
| Lease renewal                     | 0 extra (rides `computer.status`)      |                                  |

So a turn costs two round trips plus one per DorkOS tool call and one per card. The ADR's worry, a round trip per local check, does not arise. The extra work on the space side is building and signing one copy per turn and per change: one Ed25519 signature each, which is small beside a model call. These counts assume a space side that is on (see part 6 of `01-ideation.md` for a Mac home that is off).

## 8. Member checks

DOR-5150 turns "is this the owner" into "may this member do this in this space", run by the registry as each capability's visibility rule before `invoke` (ADR `261123-170830`). A `tools.call` from a computer is a call by an agent that is a member of the space, so the same question is asked on the space side before the call runs, with the agent as the member and the person whose turn it is as the one it acts for. `tools.list` uses the same rule, so a tool the member may not use is never shown. Nothing about member checks runs on the computer, and the copy carries no member data.

## 9. Options considered

| Option                                                                                                                                 | What it costs                                                                                                                                                        | What it risks                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Everything decided on the space side, a round trip per check**                                                                    | Dozens to hundreds of round trips per turn; every file edit waits on the network; a dropped connection stops all work; Claude Code's hooks must block on the network | Little extra security: a compromised computer ignores the answer anyway. Turns slow enough that people turn checks off                                                                                                              |
| **B. A signed copy, plus space-side decisions for anything with authority beyond the computer** (the architect's leaning, recommended) | A new payload, a signing label, a push on change, moving the runtimes' trust reads behind one object                                                                 | A compromised computer runs native actions as it likes, which it can do under any option; the copy must stay in step with the space side, which the version counter and the lease handle                                            |
| **C. Full trust in the computer, with only an audit record**                                                                           | Cheapest to build                                                                                                                                                    | A computer that holds the rules can raise its own level, answer its own cards and act through connections. It breaks ADR `261122-173853` (the gate reads identity on a server its owner trusts) and `261006-225605` item 4 outright |

**Recommendation: B.** It is the only option that keeps the wall where the threat model puts it (authority beyond the computer is decided off it) at a cost that does not grow with the number of native tool calls. A buys almost nothing for its cost, since its checks are the ones a compromised computer skips. The evidence supports the leaning, with one correction: draw the line by authority, not by "changes state" (§2).

## 11. What must be true before DOR-5166 is built

1. **One gate (DOR-5183).** The registry gate and the hand-registered tool gate decide through one path, so `tools.call` reaches all of them the same way.
2. **The turn port (DOR-5157).** Every space-side caller starts and watches a turn through one door, with a run record the copy can bind to.
3. **The tool server out of Claude Code (DOR-4926).** DorkOS tools are `tools.list` and `tools.call` for every runtime, in-process first.
4. **The `TurnRules` object on a Mac** (steps 1 to 4 of §6), so the runtimes read trust from one object before it ever crosses a wire.
5. **The hello (DOR-5164).** A feature name for the signed copy, so an older computer is never sent one. A computer that does not offer the feature gets no turns, or only the strictest level with no native allows.
6. **Every Must in §10 has its test written,** and each Should is built or has a ticket.

## 12. Open questions

**For Security: answered 2026-11-24** by an independent security read at main `7878dda99c`, then read a second time by Security on 2026-11-24, which changed answer 5 and two wordings. Each answer is now a decision in the body and a row in §10.

1. Signing key: the existing hub key under its own label, with an exact label list (§3).
2. A Mac home's key: yes, made on first computer link, and no agent tool may read it (§3).
3. A separate operating system user: required on every computer that is not the person's own Mac, recommended on a Mac. It protects the key and the copy; it does not fence agents in general (§3).
4. The lease: at most five minutes, renewed while the channel is up, plus a hard stop at turn end (§3).
5. Standing changes on a remote computer follow the same rule as local ones. A hold applies only with an outsider mark, or on a computer the owner did not link. The independent read asked for every remote turn to start held; Security's second read replaced that (§4).
6. `tools.call` carries the computer's marks: yes, as a Should, OR-in only (§4).
7. "Always allow" moves to a space-side record on a Mac too: yes (§5).
8. A lowered level interrupts a runtime that cannot tighten in place, when its mode lets through, unasked, what the new level would ask about or refuse. This overturns the draft (§3).

**For the operator: answered 2026-11-25.** He took the pick on all four ("yes to all four"). Each is now a decision.

1. When the connection to a computer drops mid-turn, the turn keeps running what the copy allows until the lease ends, then stops (§3). Not chosen: stop at once. A half-done edit is worse than a few minutes of local work under rules already granted.
2. Lowering an agent's level reaches running turns, on a Mac too (§3). Not chosen: from the next turn, as today. A person who lowers a level means now.
3. Order of work: the `TurnRules` object on a Mac before any wire work (§6, §11). Not chosen: the wire first, for cloud computers. One design, proven where the bugs are cheap.
4. The copy for teammate-tier turns (another agent's turn, ADR `261015-042933` rule 6) has the same shape with `tier: teammate` (§3, §4). Not chosen: no native tools at all until a card says yes. The tier already caps what runs, and one shape is simpler to review.
