# Design note: the permission gate across the wire

**For:** the architect, Security, Dorian · **Status:** ideation, waiting on a Security read and the operator's ruling · **Builds on:** ADR `261124-150516` (two sides, one contract), `specs/everything-is-a-space/design-agent-computers.md` §2 and §3 · **Tickets:** DOR-5165 (this note), DOR-5166 (the build), epic DOR-5152

Every claim about today's code names a file in this repository at the commit this note was written on. Line numbers are approximate and move with the code.

## 0. The short version

- An agent's **rules live in its space**. A computer that runs the agent gets a **read-only copy** of those rules for each turn, signed by the space side, and checks its own runtime against it.
- The line is drawn by **authority, not by effect**. Anything that uses something the space holds (a connection, a person's attention, another agent, a setting, a post in a room, a credential) is decided on the space side, on every call. Anything that uses only the computer's own files, processes and network is decided on the computer, from the copy.
- A shell command or a file edit is checked **beside the runtime**, with no round trip. A DorkOS tool call already crosses the wire as `tools.call` and is decided where it runs, on the space side.
- **The turn's level and its marks come from the space side's record of the turn.** The computer may make a turn stricter (it saw the agent read a web page); it can never make one looser.
- A question that needs a person becomes a **card on the space side**. Only someone the space allows may answer it, never the agent that asked.
- **Lowering an agent's level, pausing it or ending a grant** reaches a running turn within one frame while the channel is up, and by the lease's end when it is down (§3): the next DorkOS tool call sees it at once, the next local check sees it as soon as the new copy lands.
- **The plain limit:** a computer someone has taken over can ignore every local check. The copy keeps honest computers honest. What stops a compromised one is that it holds no space credentials and every action with authority outside it is decided off it.
- On a Mac both sides run in one process. The **same payloads** pass by function call, so there is one design, not two.

## 2. The split, as a rule

**The rule.** A decision stays on the space side when the action uses authority the space holds. A decision may be made on the computer when the action uses only the computer's own resources. The copy carries what the computer needs to make its decisions the way the space side would.

Why authority and not effect: a file edit changes state, but only on the computer, and it must be decided beside the runtime. A web fetch changes nothing, yet it is the moment outside words enter a turn. "Decide anything that changes state on the space side" would put every file edit on a round trip and still miss the read that matters. The architect's leaning is right in substance; this is the sharper wording.

**The threat model behind it.** The computer runs agent code, packages and pages the agent read, so it is untrusted (ADR `261124-150516`). The space side is trusted by the agent's owner (ADR `261122-173853`: "the permission gate reads the agent's identity on a server its owner trusts"). Outsiders seed no power and third-party code needs a yes (ADR `261006-225605` items 4 and 5). So a fact that grants power must be read where the agent cannot write, and a check that only protects the computer from its own runtime can live on the computer.

| Decision                                                                        | Where it is made                           | Why                                                                                             |
| ------------------------------------------------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| Whether a turn starts at all (pause, agent removed, computer not this agent's)  | Space side, always                         | It spends the space's trust in the agent; the computer runs only what it is told (`turn.start`) |
| The turn's level, tier and starting marks                                       | Space side, always                         | Power flows from who started the turn; the computer cannot know the starter                     |
| Every DorkOS tool call: permission, tier, card, spend, cancel window, hub-owned | Space side, always                         | The tool runs there and uses space authority; `tools.call` already crosses                      |
| Which DorkOS tools the agent sees                                               | Space side (`tools.list`), cached per turn | Blocked areas stay hidden; visibility is a member check (§8)                                    |
| A connection's use, including writes to an outside account                      | Space side, always                         | The computer holds no connection credentials (design-agent-computers §0)                        |
| Who may answer a card, and recording the answer                                 | Space side, always                         | Separation of duties (ADR `261006-225605` item 8)                                               |
| Standing rules ("Always allow", repo hook consent, the person-set floor)        | Space side, always                         | A rule the agent could write is a rule the agent grants itself                                  |
| The audit record                                                                | Space side, from what it saw               | The computer's report is a claim; DorkOS tool calls are recorded where they run                 |
| A native tool's allow, ask or refuse by mode                                    | Computer, from the copy                    | Many per second; it cannot wait on a round trip; its only authority is the computer's own       |
| Protected paths, the shell guard, held folders, Never ask                       | Computer, from the copy                    | Same; they protect the computer and the copy from the runtime                                   |
| Raising the outsider mark on a native read (web fetch, browser, another MCP)    | Computer raises, space side records        | Only the computer sees the read; a mark only ever makes the turn stricter                       |
| The load gate, keep-awake, the file boundary                                    | Computer alone                             | No trust content: they manage the machine                                                       |
| The sandbox a runtime runs under (Codex's profile, the guest VM)                | Computer alone, from the copy's level      | Enforced by the operating system, below the runtime                                             |

**The hard middle, said exactly.** A runtime's own prompt for a shell command or a file edit is decided on the computer, by the same pure functions that decide it today (`runtimes/shared/policy/approvals.ts`, `protected-path-check.ts`, the Claude Code hooks), reading the copy instead of the in-process maps. If that decision is "ask", the ask crosses as a card (§5) and only the answer comes back. A DorkOS tool call is never decided on the computer: the computer forwards it and waits for `call.result`. The computer's own `/mcp` maps the run's agent token to an agent and forwards; it holds no gate of its own for DorkOS tools beyond the hub-owned refusal, which it may apply early to save a trip.

## 3. The rules copy

**What is in it.** One object per running turn, small enough to fit one sealed frame (`AGENT_COMPUTER_MAX_BODY_BYTES` in `packages/shared/src/session-relay-agent-computer.ts`):

| Field                        | Holds                                                                                            | Read by                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| `label`, `version`           | A fixed label such as `dorkos-agent-rules/v1`, and a counter that only rises per agent           | The signature check                           |
| `computerId`, `agentId`      | Which computer and which agent it is for                                                         | The check: a copy for another computer fails  |
| `runId`, `sessionId`         | The space side's run record id (ADR `261124-150517`) and the chat                                | Binds the copy to one turn                    |
| `level`                      | The mode the turn runs at, after the agent-level bound and any carried ceiling                   | Every native decision                         |
| `tier`, `marks`              | `owner` or `teammate`; the outsider and teammate marks; the outside-words note                   | The runtime's hooks and status reads          |
| `chosenFull`                 | Whether a person set this chat to Full (the "asks nobody" case)                                  | `canUseTool`'s Full branch                    |
| `areas`                      | Permission area states, for the few native checks that read one (shell reads of protected files) | The shell guard                               |
| `protectedPaths`, `roots`    | The list from `protected-paths.ts` and this turn's roots                                         | Every file tool                               |
| `readFolders`, `heldFolders` | Folders a read skips the card in; folders a held turn may not touch                              | `canUseTool`, held-folder hooks               |
| `nativeAllow`                | The standing "Always allow" rules for native tools, held on the space side                       | The runtime's allow list, rendered per launch |
| `repoConsent`                | Digests of repo hooks and settings a person let run, and those refused                           | The launch                                    |
| `toolsVersion`               | The `tools.list` answer's version, so the computer knows when to ask again                       | The computer's `/mcp`                         |
| `notAfter`                   | When the copy stops being good (§3, "How long")                                                  | Every check                                   |

What it never holds: a credential, a bearer, a connection's identity, the person-set floor itself (only its result), another agent's rules, or anything about people.

**Who signs it, and with which key.** The space side signs with the same long-lived Ed25519 key the computer already pinned at link time: on a cloud home, the hub signing key (`services/core/hub/hub-signing-key.ts`), whose public half the computer stores in its pin (`services/core/session-relay/pin-store.ts`). That key signs only data that starts with the relay's one label line, `dorkos-session-relay/v1` (`signWithHubKey` refuses anything else). The handshake and the link messages (`session-relay/link-signature.ts`) both start with that line and differ by a kind word after it. The rules copy gets a second, separate label, which turns that one prefix check into a short allow list, so a copy can never be read as a transcript and a transcript can never be read as a copy. Two gaps to close: a person's own computer has no hub key (`hub-signing-key.ts`: "both readers throw there"), so a Mac acting as the home for other computers needs one made the same way; and the one-label check becomes a list, which Security should rule on (§11).

Why sign at all, when the channel is already sealed and authenticated (`session-relay/channel.ts`)? Because the copy leaves the channel: it is kept on the computer's disk so a turn keeps its rules across a short drop, and it is handed to a runtime's hooks, a sidecar or a guest that is not the channel's endpoint. A signature lets each of those check it without trusting the path it came by, and lets the computer refuse a cached copy an agent edited on disk.

**How the computer checks it.** Before first use and on every reload: the signature against the pinned key, the label, its own computer id, a known agent, a `runId` it was told to start, a version no lower than the last it accepted for that agent (no rollback), and `notAfter` in the future. Any failure means no copy, and no copy means the strictest behaviour: every native call that would not run in the runtime's default asking mode asks, and with nobody reachable to ask, it is refused. The computer keeps the last version it accepted, and the list of turns it was told to start, only in memory, and it accepts a copy only for a `runId` whose process still lives. So a restart never reopens an older copy, and nothing an agent's shell can delete brings a looser copy back. It never reads the identity copy that `agents.sync` gives it (`design-agent-computers.md` §1) for a trust decision: only the signed rules copy.

**How long it is good for.** The life of one turn, capped by a lease the space side renews while the channel is up (a few minutes, renewed on `computer.status`). A new turn always gets a new copy with `turn.start`. Marks may be raised inside a copy's life (below); nothing else changes without a new version. A renewal is a new signed version with a later `notAfter`.

**How a change reaches a running turn.**

| Change                                                              | The DorkOS tool call in flight                   | The next DorkOS tool call | The next native call                             | The running process                                                                                                                     |
| ------------------------------------------------------------------- | ------------------------------------------------ | ------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| A person lowers the agent's level                                   | Finishes as decided; it was checked at call time | Decided at the new level  | Decided at the new level once the new copy lands | Runtimes that take a mode change mid-turn get it; others keep the old mode until the turn ends, with every ask decided at the new level |
| A person pauses the agent                                           | Finishes                                         | Refused                   | Refused (the new copy says paused)               | Interrupted, as `hold-paused-turns.ts` does today                                                                                       |
| A person ends an "Always allow" or a grant                          | Finishes                                         | Decided without it        | Asks again once the new copy lands               | The runtime's allow list is re-rendered at its next launch                                                                              |
| The space side marks the turn (a DorkOS tool returned outside text) | Its result carries the new mark                  | Held as marked            | Held as marked                                   | Unchanged                                                                                                                               |

Today a turn already running keeps its launch mode when the level drops (`agent-level-bound.ts`: "Out of scope: a turn already running when the level changes (DOR-3177)"). The push of a new copy is the natural place to close that, on a Mac and on a computer alike.

**When the computer cannot reach the space side.** DorkOS tool calls fail: there is nothing to forward to, and they report so to the agent. Asks are refused once the runtime's own wait ends, since nobody can see the card. Native calls the copy already allows keep running until `notAfter`, so a dropped connection does not kill a file edit half way. After `notAfter` the computer stops the turn. No new turn starts, since only the space side starts turns. All of this assumes a space side that is on. When the home is a Mac that sleeps, a cloud computer's turn ends at the lease's end; whether that is right is part 6 of `01-ideation.md`.

**What an attacker who owns the computer can do.** Ignore every local check; run any native action under the computer's own operating system rights; read the copy (it holds no secret); omit marks it was supposed to raise; replay an old copy to its own runtime. What they cannot do: forge a new copy or raise a level, since they lack the space's private key; act through a connection, post, message, schedule or change a setting except as the agent itself, through `tools.call`, at the level the space side holds for it; reach any hub-setup action (the hub-owned table); answer their own card; or make the space side's audit say anything but what it decided. **So the copy protects honest computers and honest runtimes. The wall is that everything with authority beyond the computer is decided off it.**

## 4. Level and marks come from the space side's record

`design-agent-computers.md` §3 already says the tier for a bridged tool comes "from the hub's own record of the turn, never from the computer". The same holds for runtime-internal checks, because those checks read the copy, and the copy is built from the space side's record:

1. When a turn is accepted, the space side writes its run record (ADR `261124-150517`): run id, status, attempt, the runtime chat. Beside it, in the same write, it stores the level and marks it computed at turn start (rows 2 and 3 of §1). The copy is built from that row and carries its `runId`.
2. The computer never sends a level. Of the trust facts, `turn.start` today carries only `tier: owner | teammate` (`session-relay-agent-computer.ts`, `AgentComputerTurnTierSchema`); it gains the signed copy and nothing the computer can choose.
3. Marks move one way. The space side raises a mark when a DorkOS tool or a connection read returns outside text (`capabilities/mark-caller-turn.ts`); it records it on the run and pushes a new copy. The computer raises a mark when its runtime reads outside text natively (the job of `claude-code/tool-gate/outside-text-hook.ts` today): it applies it to its local copy first, so its own next check is already strict, then reports it. The space side ORs it in. No message from the computer can clear a mark; only a new turn, with a new run record, starts clean, which matches `markRunningTurnOutsider` today ("it lasts until the conversation's next turn starts").
4. Ordering: the mark report and a following `tools.call` ride one sealed channel with sequence numbers, so the space side must handle frames in order and apply a mark before it decides the call after it. Each `tools.call` may also carry the computer's current marks, which the space side ORs in.

The residual: a compromised computer can skip step 3's report. Its turn then runs unmarked at the agent's own level, so the actions `marked-turn-holds.ts` holds for a marked turn (standing changes, acts in an outside account) run without their card. That is more than a marked turn may do, though no more than the agent may do in an unmarked one, and every such action is still decided and recorded on the space side. §11 question 5 asks whether to close it by starting such turns marked.

## 5. Approvals across the wire

- **Raising.** A native ask on the computer becomes an approval event on the turn's stream, which `session.stream` already carries, and is answered with `interaction.respond` (`packages/shared/src/session-relay.ts`). The space side records it against the run and shows the card in the person's chat.
- **The direction is the reverse of a linked Mac's.** A linked Mac decides what the web may answer and refuses most of it (`session-relay/relay-approvable.ts`: no standing raises from the web, no `mcp__*` tools), because the Mac is in charge (ADR `261015-042933` rule 5). An agent computer has the space side as its only controller, so every card may be answered there. One idea carries over: an answer never becomes a standing rule on the computer.
- **Who may answer.** The space side's rule (`approvals/decision-authority.ts`): a proven person, never the agent that asked; later any role holder but the asker (ADR `261006-225605` item 8). The answer goes back as `interaction.respond`, bound to the ask's id. A computer has no person at it, so it never decides its own card.
- **While it waits.** The runtime holds that one call, with the existing wait and park timing (`runtimes/shared/timing/pending-approval-timing.ts`); the rest of the turn behaves as it does on a Mac. An "Always allow" answer is stored on the space side as a standing rule and reaches the computer in the next copy; it is never written by the computer into the workspace, where the agent could write the same rule itself. A standing rule is scoped to the computer whose card made it, and the card shows the exact rule the space side will store, built by the space side, not text the computer wrote. Teammate turns get an empty `nativeAllow`, and their cards never offer "Always allow" (ADR `261015-042933` rule 6).
- **Restarts.** If the space side restarts, the computer still holds the ask; on reconnect it lists pending asks and the space side shows the cards again. If the computer restarts, the process that asked is gone, so the ask is gone: the space side withdraws the card and the run record marks the turn as waiting on a person, which the recovery rule never continues (ADR `261124-150517`).
- **DorkOS tool cards** are already space-side: a `destructive` call raises its card where it runs, and the computer only waits on `call.result`.

## 6. The Mac case

On a Mac both sides run in one process, and that stays true until the spike in ADR `261124-150517` says otherwise. What changes: the runtimes stop reaching into the space side for trust facts, and instead read a `TurnRules` object handed to them at launch and updated by a callback, with the same fields as §3. What does not change: what is decided, and by which function. In-process, the copy is passed as a deeply frozen object and not signed, and a change is a new object through the callback, because runtime SDK code runs in the same process; the payload type and the builder are the same ones the wire uses, so a Mac and a cloud computer cannot drift.

The shortcuts that have to go behind the split, in the order to move them so nothing breaks:

1. **Build the copy, change no reader.** A space-side builder that assembles the `TurnRules` from today's readers (`agent-level-bound.ts`, `turn-levels.ts`, `full-autonomy.ts`, `protected-path-roots.ts`), attached at the decorate seam (`core/runtime-seam/decorate-runtime.ts`). A test asserts it equals what each runtime reads today.
2. **Doe and OpenCode first.** Their checks already take plain inputs (`runtimes/doe/approvals.ts` takes a mode and roots; `opencode/messaging/approvals.ts` takes the mode). Point them at the copy.
3. **Codex.** `approvalPolicyFor` and the permission profile read the copy's level (`codex/app-server/turn-parts.ts`).
4. **Claude Code's native gate.** `createCanUseTool` and the hooks in `launch-resolver.ts` read the copy instead of the session's ceiling maps and `marksOf`. The outside-text hook raises the mark through the copy's callback instead of calling `markRunningTurnOutsider` directly.
5. **Claude Code's tool server.** `runtimes/claude-code/mcp-tools/index.ts` builds an in-process SDK server that calls `registry.invoke` with an identity resolved from the working folder. It moves out of the runtime and behind `tools.list` and `tools.call` (DOR-4926); on a Mac that call is a function call.
6. **Connection authority.** The per-turn bearer and its process-local permit (ADR `260908-153657`, `connector-turn-context.ts`) stay on the space side. On a remote computer there is no permit to hold: the run record and the channel's proven computer stand in for it, and connection calls are `tools.call`.
7. **Standing rules.** "Always allow" for native tools and repo hook consent move to space-side records that the copy carries (`always-allow-breadth.ts`, `repo-config-consent.ts`).

A lint ratchet counts runtime imports of `core/turn-power`, `core/agent-identity`, `core/capabilities`, `core/approvals` and `core/permissions` and may only fall. It reaches zero when the computer entry's wall (DOR-5158) can hold.

## 7. Latency and cost

Per turn, on a remote computer:

| Exchange                          | Round trips                            | Cached                           |
| --------------------------------- | -------------------------------------- | -------------------------------- |
| `turn.start` with the signed copy | 1                                      | The copy, for the turn           |
| `tools.list`                      | 1, then only when `toolsVersion` moves | The list, per turn               |
| Each DorkOS tool call             | 1 each (already true by design)        | Nothing: decided fresh, as today |
| Each native check                 | 0                                      | Decided from the copy            |
| A mark raised on the computer     | 0 (sent on the stream, no reply)       |                                  |
| A new copy after a change         | 0 (pushed)                             |                                  |
| A card                            | 1, plus the person's time              |                                  |
| Lease renewal                     | 0 extra (rides `computer.status`)      |                                  |

So a turn costs two round trips plus one per DorkOS tool call and one per card. The ADR's worry, a round trip per local check, does not arise. The extra work on the space side is building and signing one copy per turn and per change: one Ed25519 signature each, which is small beside a model call. These counts assume a space side that is on (see part 6 of `01-ideation.md` for a Mac home that is off).

## 8. Member checks

DOR-5150 turns "is this the owner" into "may this member do this in this space", run by the registry as each capability's visibility rule before `invoke` (ADR `261123-170830`). A `tools.call` from a computer is a call by an agent that is a member of the space, so the same question is asked on the space side before the call runs, with the agent as the member and the person whose turn it is as the one it acts for. `tools.list` uses the same rule, so a tool the member may not use is never shown. Nothing about member checks runs on the computer, and the copy carries no member data.

## 9. Options considered

| Option                                                                                                                                 | What it costs                                                                                                                                                        | What it risks                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Everything decided on the space side, a round trip per check**                                                                    | Dozens to hundreds of round trips per turn; every file edit waits on the network; a dropped connection stops all work; Claude Code's hooks must block on the network | Little extra security: a compromised computer ignores the answer anyway. Turns slow enough that people turn checks off                                                                                                              |
| **B. A signed copy, plus space-side decisions for anything with authority beyond the computer** (the architect's leaning, recommended) | A new payload, a signing label, a push on change, moving the runtimes' trust reads behind one object                                                                 | A compromised computer runs native actions as it likes, which it can do under any option; the copy must stay in step with the space side, which the version counter and the lease handle                                            |
| **C. Full trust in the computer, with only an audit record**                                                                           | Cheapest to build                                                                                                                                                    | A computer that holds the rules can raise its own level, answer its own cards and act through connections. It breaks ADR `261122-173853` (the gate reads identity on a server its owner trusts) and `261006-225605` item 4 outright |

**Recommendation: B.** It is the only option that keeps the wall where the threat model puts it (authority beyond the computer is decided off it) at a cost that does not grow with the number of native tool calls. A buys almost nothing for its cost, since its checks are the ones a compromised computer skips. The evidence supports the leaning, with one correction: draw the line by authority, not by "changes state" (§2).

## 10. What must be true before DOR-5166 is built

1. **One gate (DOR-5183).** The registry gate and the hand-registered tool gate decide through one path, so `tools.call` reaches all of them the same way.
2. **The turn port (DOR-5157).** Every space-side caller starts and watches a turn through one door, with a run record the copy can bind to.
3. **The tool server out of Claude Code (DOR-4926).** DorkOS tools are `tools.list` and `tools.call` for every runtime, in-process first.
4. **The `TurnRules` object on a Mac** (steps 1 to 4 of §6), so the runtimes read trust from one object before it ever crosses a wire.
5. **The hello (DOR-5164).** A feature name for the signed copy, so an older computer is never sent one.

## 11. Open questions

**For Security** (each a yes or no, or a choice):

1. Sign the copy with the existing hub key under a third label (proposed), or with a separate key pinned at link time?
2. A Mac acting as a home for other computers needs a long-lived signing key it has never had. Make it the same way the hub's is made, on first computer link: yes or no?
3. Should a computer run agent processes as a different operating system user from the computer side, so an agent's shell cannot rewrite the computer side or its cached copy: required, or recommended?
4. Is a lease of a few minutes, renewed while the channel is up, the right bound on how long a turn may run without contact: yes, or tie it to the turn only?
5. A turn on a remote computer whose agent can read the web natively: treat it as marked from the start for the held set in `marked-turn-holds.ts` (stricter), or mark only on a reported read (proposed)?
6. Should `tools.call` carry the computer's current marks for the space side to OR in, on top of channel ordering: yes or no?
7. Move "Always allow" for native tools to a space-side record on a Mac too, so the agent cannot write the same rule into its own folder: yes or no?
8. On a lowered level mid-turn, interrupt the running process when its runtime cannot change mode in place, or let the turn finish with every new ask decided at the new level (proposed)?

**For the operator** (two options each, with a pick):

1. When the connection to a computer drops mid-turn: **(a)** keep running what the copy allows until the lease ends, then stop; **(b)** stop at once. Pick **(a)**: a half-done edit is worse than a few minutes of local work under rules already granted.
2. Lowering an agent's level: **(a)** reaches running turns; **(b)** applies from the next turn, as today. Pick **(a)**, on a Mac too: a person who lowers a level means now.
3. Order of work: **(a)** the `TurnRules` object on a Mac before any wire work; **(b)** build the wire first for cloud computers. Pick **(a)**: one design, proven where the bugs are cheap.
4. The copy for teammate-tier turns (another agent's turn, ADR `261015-042933` rule 6): **(a)** the same shape with `tier: teammate`; **(b)** no native tools at all until a card says yes. Pick **(a)**: the tier already caps what runs, and one shape is simpler to review.
