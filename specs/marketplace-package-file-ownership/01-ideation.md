# Keep a package's settings when it is updated or reinstalled

**Slug:** marketplace-package-file-ownership
**Author:** Claude Code (prog-DOR-2245)
**Date:** 2026-09-23
**Baseline:** `origin/main` at `3b36e3876`, pinned once for the whole investigation.

---

## 1) Intent & Assumptions

- **Task brief (DOR-2245).** Updating or reinstalling a marketplace package deletes the settings a person keeps inside it. `MarketplaceInstaller.update` is uninstall then install, and only `<installRoot>/.dork/data/` and `<installRoot>/.dork/secrets.json` are carried across. flow keeps its per-project settings in `config/config.json` and `config/config.local.json` inside its install root, so every flow update resets them. The operator restored them by hand on 2026-08-07 (0.5.0 reinstall) and three times on 2026-09-23 (0.7.2, 0.7.3). The question to settle: **who owns which files inside an installed package, and how does a package say so**, for every package type (plugin, agent, skill-pack, adapter, shape).
- **Assumptions.**
  - Packages are not sandboxed. A plugin's hooks and scripts run as the person. Anything that says "package A's files are hidden from package B" is not a property this system can offer, so no design may be sold on it.
  - The install root path is stable across versions in DorkOS (`<scope>/.dork/plugins/<name>/`, `<scope>/.dork/agents/<name>/`, `<scope>/.dork/shapes/<name>/`, or the same under `dorkHome`). This is unlike Claude Code, whose install directory is versioned (`~/.claude/plugins/cache/<mkt>/<plugin>/<version>/`). It is what makes in-place preservation possible here and not there.
  - DorkOS keeps per-package state by default and deletes it only on `--purge`. That contract (ADR-0233, `dorkos uninstall --purge`) stays.
  - DorkOS does not migrate a package's settings between versions. A package must accept its own older settings. flow failing to (DOR-2246) is flow's defect, fixed separately.
- **Out of scope.**
  - DOR-2246 (flow's validator rejects configs that omit defaulted fields).
  - DOR-2248 (the cache tree can disagree with its commit). This work depends on it and is sequenced after it (§7).
  - Where DorkOS files a schedule a person makes for a marketplace agent (DOR-1791 T3/T4: a second task root and the `isPackageOwned` carve-out). This work makes such a file survive an update. It does not add the task root.
  - Moving flow's own config out of its install root. Section 5 explains why it is not needed for this item, and §8 records it as a flow-side follow-up.

## 3) Codebase map

- **Primary components:** `services/marketplace/transaction.ts` (the one place every install lands files), `flows/uninstall.ts` (what a removal keeps), `marketplace-installer.ts` (`update` / `applyUpdate`), `flows/install-agent.ts` + `services/core/agent-creator.ts` (the agent scaffold), `installed-metadata.ts` (the sidecar), `lib/locate-install.ts` (what counts as installed).
- **Shared dependencies:** `@dorkos/marketplace` (`manifest-schema.ts`, `package-validator.ts`) for the package contract; `@dorkos/shared/marketplace-schemas` for `InstallResult` / `UninstallResult`; `@dorkos/harness` for projection.
- **Data flow:** resolve → fetch into the SHA-keyed cache → `validatePackage` → flow `stage` (copy, compile extensions, `npm install`) → transaction backup → `activate` (atomic move, then type side effects) → sidecar write → harness auto-projection.
- **Blast radius:** every install, reinstall, update and uninstall of every package type; the three surfaces that drive them (HTTP routes, `marketplace_*` MCP tools, CLI); harness projection of commands and hooks.

## 4) Root cause

- **Repro.** Install flow into a project. Run `/flow:init` (writes `config/config.json`, `config/config.local.json`). Run `dorkos update flow --apply`, or reinstall from the app. Both files are gone.
- **Observed vs expected.** Observed: every file a person or agent created inside an install root is deleted by update, reinstall (worse: reinstall does not even keep `.dork/data/`), and uninstall. Expected: a package manager replaces what it installed and leaves what it did not.
- **Root cause (high confidence).** The installer has no record of which files it put in an install root. It cannot tell "the package's `skills/x/SKILL.md`" from "the person's `config/config.json`", so it treats the whole directory as the package's and hard-codes two exceptions. Everything else follows from that: flow's settings, an agent package's identity and persona (`.dork/agent.json` is rewritten with a new id on every update, DOR-1791 F1), a person's schedule under a package agent, and any `${CLAUDE_PLUGIN_DATA}`-style state.

### Options

1. **A package-declared preserve list.** The manifest names user-owned paths (`preserve: ["config/config.json", …]`); the installer keeps them across an update, with a merge step when the shipped default changes. _Pros:_ small, explicit. _Cons:_ protects only what an author thought to list. Every undeclared write is still deleted, including writes by an agent the author never imagined, `/flow:init`'s generated adapter, a person's schedule under an agent. A Claude-Code-native package has no DorkOS manifest to declare anything in. It needs a merge story for a file the package does not ship, which is a contradiction. **Rejected.**
2. **Move user state out of the install root** (a DorkOS per-package data dir, exposed as `${CLAUDE_PLUGIN_DATA}`); the install root is replaced wholesale, as today. _Pros:_ it is Claude Code's model and VS Code's, so the root stays pristine. _Cons:_ it fixes nothing that exists. flow, and every package that writes into its own root, keeps losing data until its author changes it. It cannot work for **agent packages**, whose install root _is_ the agent's working directory: the agent writes `MEMORY.md`, `.dork/agent.json` holds its id, `.dork/SOUL.md` its persona, and the agent's sessions are keyed by that path. A per-plugin-id user-level dir (Claude Code's exact layout) is also wrong for per-project settings: flow in `dorkos` and flow in `blintz` use different Linear teams. **Rejected as the whole answer; its useful half (a conventional data dir named `${CLAUDE_PLUGIN_DATA}`) is kept in option 3.**
3. **Ownership by provenance (dpkg's model).** At install, record every file the install put in the root and its content hash: the **installed-files record**. A file is the package's if and only if it is in the record and unchanged. Update, reinstall and uninstall replace or remove only those. Everything else in the root belongs to the person and is kept; only `--purge` removes it. A shipped file the person changed gets an explicit rule (option 3b below). `${CLAUDE_PLUGIN_DATA}` resolves to `<installRoot>/.dork/data/`, which a package may not ship into, so it is always the person's. _Pros:_ fixes every package type with no author action, flow's four installs included. It is also exact enough that the two hard-coded exceptions are deleted rather than extended, and it gives Claude-Code-format packages the data dir they expect. _Cons:_ the installer hashes the staged tree, a new file is written per install, the legacy installs need their record rebuilt once, and the concept of a "kept file" is new to surface honestly.
   - **3a. Edited shipped files: the person always wins** (rpm `noreplace` for everything). Rejected: a package's own code, prompts and hooks would silently stop updating, so the install would be half one version and half another. It also inverts DOR-1789's refusal model without saying so.
   - **3b. Edited shipped files: the package wins, the person's copy is saved beside it as `<file>.dork-old`, and the result names it, unless the package declares the file `userEditable`. Then the person wins, and a changed default is saved beside it as `<file>.dork-new`** (dpkg conffiles / rpm `%config` vs `%config(noreplace)`). An agent package's persona and identity files are user-editable without being declared. **Chosen.**
4. **Keep everything, three-way merge on update** (git-style merge of the person's tree, the old version and the new version). Rejected: conflict markers in a SKILL.md or hooks.json are worse than a `.dork-old` file, and it needs the old tree on every update.
5. **mtime-based detection** instead of hashes. Rejected: `cp`, `git checkout` and `/flow:init`'s restore all rewrite mtimes, which is exactly how the operator restored flow's config.

### Recommendation

Option 3 with 3b. It answers the ticket's question with one rule that holds for every package type: **DorkOS removes or replaces only files it can prove the install put there, unchanged**. A package says a shipped file is meant to be edited with one manifest field, and says where it keeps its own state by writing to `${CLAUDE_PLUGIN_DATA}`, the name Claude Code already taught plugin authors.

## 6) Decisions

No operator clarification was requested; the brief asked for a first-principles choice. Decisions carried into the spec:

| #   | Decision                              | Choice                                                                                                                                                                                                  | Rationale                                                                                                                        |
| --- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Ownership model                       | Provenance: an installed-files record (path → sha256) written into the staged tree, so it activates atomically with the package                                                                         | The only model that fixes all five types and existing packages without author action; dpkg's 30-year answer to the same question |
| 2   | Edited shipped files                  | Package wins + `<file>.dork-old`; `userEditable` paths: person wins + `<file>.dork-new` when the default changed                                                                                        | dpkg/rpm conffiles; keeps packages coherent; never loses a byte                                                                  |
| 3   | How a package declares editable files | `userEditable: string[]` in `.dork/manifest.json`, exact paths or `dir/**` only                                                                                                                         | The one ambiguous category needs a declaration; a tiny glob subset avoids a matcher dependency and ambiguity                     |
| 4   | Agent packages                        | `.dork/agent.json`, `.dork/SOUL.md`, `.dork/NOPE.md`, `.dork/MEMORY.md` are user-editable for every agent package; the agent flow adopts an existing workspace (keeps its id) instead of re-scaffolding | They are the agent's identity and persona; DOR-1791 F1 showed an update re-keys the agent today                                  |
| 5   | Package data dir                      | `${CLAUDE_PLUGIN_DATA}` → `<installRoot>/.dork/data/`, rewritten by Harness Sync everywhere `${CLAUDE_PLUGIN_ROOT}` is                                                                                  | Claude Code compatibility; per-scope (per-project) where Claude Code's is per-user; reuses the path DorkOS already preserves     |
| 6   | Reserved paths                        | A package may not ship `.dork/data/**`, `.dork/secrets.json`, `.dork/install-metadata.json`, `.dork/installed-files.json`, or any `*.dork-old` / `*.dork-new` file                                      | These belong to the person or the installer; shipping one would make ownership ambiguous                                         |
| 7   | Uninstall without purge               | Keeps every person-owned file (and the record) in place; the root then holds no manifest and counts as **not installed** everywhere                                                                     | Generalizes today's two paths; one predicate for "installed"                                                                     |
| 8   | Update                                | Stays uninstall-then-install; the scratch-dir dance is deleted because the install transaction now carries the person's files itself                                                                    | One code path for update and reinstall                                                                                           |
| 9   | Legacy installs (no record)           | Rebuild the record from the recorded commit's tree (cache, else fetch by SHA); if that fails, a no-loss fallback                                                                                        | The four flow installs rebuild cleanly; nothing is ever deleted on a guess                                                       |
| 10  | Settings migration                    | Not DorkOS's job; a package must read its own older settings                                                                                                                                            | Claude Code's stance too; DOR-2246 is flow's instance                                                                            |
| 11  | flow                                  | No change required for this item; its config is not shipped, so it is the person's under the new rule                                                                                                   | Contract-first is satisfied trivially; a flow-side improvement is a follow-up (§8)                                               |
