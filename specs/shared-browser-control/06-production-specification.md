# One shared browser: production contract

**Status:** Frozen implementation contract after two distinct independent reviews of `17d7c579c0a52211521a2ce50de29b47f8142a1d` against `041afeaaaf3eb8960b77018ffafa42fb51f878db`, each with zero Important findings or Nits (journals44/45). Full-scope delivery is already authorized. Contract freeze establishes design acceptance, not production implementation, identity-mode availability or native acceptance.
**Rollout addendum:** The user-requested default-off experiment below is a new plan amendment pending fresh independent review. Earlier freeze receipts do not accept this addendum or establish implementation readiness.
**Author:** Codex
**Date:** 2026-10-01

## Overview

Give each agent an independent browser that keeps working without an open viewer. People can view and control the same running page, keep a named profile, start a separate clean browser, and share an explicitly authorized browser in a room. Managed browsing must not add Chrome icons to the macOS Dock or app switcher.

This is the reviewed production refinement of [01-ideation](01-ideation.md). [02-specification](02-specification.md) remains the frozen bounded experiment, and its receipts remain scoped evidence. Incremental decomposition preserves the completed prototype tasks. The ADR amendment remains proposed until its implemented pattern satisfies the ADR acceptance gate; the accepted iframe decision still governs existing lightweight previews.

## Background / Problem Statement

The visible Browser currently frames a page in the person's browser and routes driving through the injected shim. The managed Playwright MCP preset starts a separate isolated browser seeded from saved storage state. They differ in cookies, page identity, lifetime and visibility. Full control must operate the actual page people see, not a second rendering of its URL.

The owned Chromium prototype establishes useful mechanics but also exposes sudden-death storage loss, failed injected-RTT latency, native observation gaps and host pressure. These limits constrain delivery and copy; a green script suite does not establish native or production success.

## Goals

| Requirement                   | Production behavior and acceptance                                                                                                                                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Retained state                | Named private profiles survive clean close/reopen and three real process restarts with exact cookie, localStorage, IndexedDB, service worker, Cache Storage and HTTP cache fixture values. Site expiry and session-cookie behavior remain explicit.  |
| Clean mode and return         | A separate unseeded ephemeral browser starts empty. Returning uses the original profile without overwriting it. Clean-mode close removes its data after exact process cleanup.                                                                       |
| Independent unattended agents | Two agents have separate profiles and Pages, each completing 100 exact mutations with no viewers. Reopening a viewer shows the same live Page and counter. Browser restart preserves stored site state, not page-JavaScript variables.               |
| Shared viewing/control        | Authorized people and agents attach to one canonical tab. Multiple viewers receive that Page's pixels; only one controller epoch can dispatch input. Revocation and human takeover reject stale/queued work and clear held input before new control. |
| macOS presence                | The exact supported headless executable adds no Chrome Dock/app-switcher icon and steals no foreground focus through normal input, capture, crash and recovery. Actual inventory with a visible-app positive control is mandatory.                   |

All five are full-delivery requirements. Native input, accessibility and phone/tunnel verification belong to the core quality gate, not optional polish.

## Non-Goals

Personal Chrome tabs/profiles, credential brokerage, universal website compatibility, raw public CDP, security-challenge bypass, fingerprint indistinguishability, lossless forced-crash persistence, or replay of uncertain side effects. Lightweight document previews and Doc Channel are not replaced. No paid model or real account is needed to verify the contract.

## Detailed Design

### Boundaries and identities

`packages/browser/src/` owns Chromium integration, profile reservation, process identity, tabs, actions, captures and bounded telemetry. Its constructor requires an absolute injected `dataDir`, an explicit runtime descriptor, clocks/process observers and narrow policy callbacks. It does not resolve home directories or import app code, users, rooms, authentication or agent runtime SDKs. Its public engine interface does not expose raw Page, CDP sessions or profile files.

`apps/server/src/services/browser/` owns owner-qualified registry metadata, grants, browser/tab bindings, controller arbitration, authenticated streaming, artifact authorization and shutdown orchestration. Thin `routes/browser.ts` validates shared schemas and maps typed errors. Add this cohesive domain to AGENTS.md and the service census test when implemented.

Separate objects: durable `profileId`; running `browserId` plus generation; live `tabId` plus navigation generation; disposable `viewerId`; controller actor/epoch; and server-side scope attachment. IDs are opaque references, never authority. Durable profile ownership survives session changes; live browser/tab IDs become stopped after restart and are never silently rebound. Recovery creates fresh identities and reports the relationship. Closing a viewer or Canvas attachment does not close the browser.

Server registry metadata stores profile owner, label, mode, version, grants and session/room attachments through a schema migration. Chromium storage lives beneath a private engine data root, separate from metadata and artifacts. Database state records intended lifecycle; actual liveness comes from the engine. Startup reconciliation marks stopped/uncertain objects accurately. Clean contexts are never seeded from the retained profile and do not mutate its stores.

### Lifecycle and recovery

Reservation is atomic across independent processes. Its record includes launch phase, manager PID/birth and the launched Chromium root PID/birth. A dead Node owner or absent native lock does not authorize reuse while recorded Chromium remains live. PID reuse, unknown holder, missing process observation and failed launch cleanup fail closed; quarantine uncertain profiles for explicit repair rather than deleting locks optimistically.

Record attributable descendants before parent death and retain PID/birth identities after reparenting. Shutdown operates only on recorded matching identities, never process groups or operator browsers. Bound acquisition, teardown and IPC; install cleanup before fallible runtime/browser acquisition. Check original-tree disappearance before recovery, and check the recovery tree too. Every result distinguishes observed refusal, observed root exit, unsafe acquisition and unavailable observation.

Clean close/reopen is the retained-state baseline. Sudden termination can lose recent writes even after page readback acknowledged them. Chromium profile persistence is not a per-action disk commit. Do not expose a fictitious flush/durable-action flag. Persist DorkOS lifecycle metadata separately, report interrupted actions as uncertain/failed, and never automatically replay clicks, forms or other side effects. Renderer death, Chromium death and manager death are distinct failure events.

### Ownership, grants and control

Trusted authentication/capability context supplies the owner and actor. Request bodies cannot choose that identity. Session ownership and room membership are necessary scope checks, but neither implicitly grants profile access. Explicit grants distinguish viewing, control, diagnostics, download/artifact access and profile management. Attachments hold references, not copied account state. Membership removal, grant expiry/revocation and owner deletion close authorized streams and invalidate pending actions. Unknown and inaccessible IDs give indistinguishable refusals.

Before granting access, disclose that participants may see private page contents and that controllers may act using that browser's signed-in accounts. Viewing permission alone may reveal private information. Agent access to a profile is an explicit owner decision. Read-only diagnostics can contain secrets and require their own grant and redaction policy.

Only the server issues controller epochs bound to authenticated actors and a tab lifetime. Human takeover immediately invalidates queued old work, rechecks the epoch before each composite step and waits for the bounded in-flight barrier before accepting new input. Reset mouse buttons, modifiers, composition and drag state. An already dispatched external action cannot be undone; barrier timeout stops further input and reports failure rather than granting concurrent control. The required barrier is at most two seconds.

### Schemas, Transport and namespaces

Add browser-safe Zod contracts in `packages/shared/src/browser-schemas.ts` with an exported subpath. Include lifecycle descriptors, permissions, typed errors, structured actions, capture identities and bounded diagnostics. Transport methods cover profiles, browser/tab lifecycle, grant changes, controller transitions, actions and viewer attachment. HttpTransport implements them in a dedicated `shared/lib/transport/browser-methods.ts`; mock transports follow the same contract.

Use `/api/browser/profiles`, `/api/browser/instances` and `/api/browser/tabs` for managed resources. Use capability IDs `browser.*` and distinct `managed_browser_*` tool names during migration. The existing `ui` preview verbs and `/sessions/:id/devtools/*` retain iframe semantics until an explicit compatibility change. No managed stream enters the Doc Channel namespace or pretends to be an iframe MessagePort.

Metadata/control events have sequence/generation identities and resynchronization semantics. Pixels are lossy and non-durable: at most one pending frame per viewer, at most 2 MiB, with superseded-frame drops. Viewer tickets are short-lived, actor/tab-bound, scoped and revocable; validate credentials and origin on every stream/upgrade. Do not place durable credentials in query strings or public receipts. A stalled viewer cannot backpressure the canonical Page or other viewers.

Every frame identifies browser/tab lifetime, navigation generation, viewport revision, controller epoch and monotonic sequence. Acknowledgments refer to a genuinely decoded/drawn prior frame; wrong, missing or replayed receipts cannot acknowledge delivery. Lost transport creates a fresh subscription. Fixed canonical viewport is explicit: viewer resize scales presentation and does not silently resize the Page. Input carries viewport and control identities; stale coordinates are refused. The visible pointer is canonical server-observed state, not an invented client-only cursor. Preserve native caret pixels and test blur/blink/focus changes.

### Client FSD and Canvas/Rooms

`layers/entities/browser/` owns shared server state, query keys, identities and subscriptions. `layers/features/browser/` owns viewer presentation, input, navigation, takeover and status. `features/canvas/ui` composes Browser UI through its barrel; model/hooks never import sibling feature internals. Canvas and Rooms consume entity contracts. Widgets compose larger room/session surfaces. No runtime package is bundled into the frontend.

Introduce an explicit managed-browser document reference distinct from the existing URL iframe preview, validated end to end. Session and room scope writers retain their existing author checks, replay and document limits. Attaching a browser never grants its permissions. Two authorized viewers see one tab; local panel history cannot accidentally navigate the shared Page. Navigation and viewport changes are controller operations. Detaching, room removal or closing a document removes presentation bindings, with explicit browser-stop controls separate.

Semantic accessibility is an independent design gate. Provide a versioned semantic tree and keyboard/focus interaction tied to the same canonical Page; an image with an accessible label is insufficient. Prototype page outlines establish no screen-reader parity. Before implementation-ready contract approval, specify the semantic transport, focus/action mapping and revocation on tree, navigation and controller changes. Before production-readiness acceptance, demonstrate focus order, text editing, status announcements, navigation and stale-tree action refusal with assistive technology. Contract approval need not wait for implemented assistive-technology evidence, but cannot leave that transport and revocation design unresolved. Do not copy an untrusted DOM into the authenticated app origin.

The separately reviewed [semantic contract](07-semantic-browser-contract.md) supplies strict transport shapes, exact private DOM bindings, write-only secret input, bounded own-edit focus continuation, revocation and proposed assistive-technology acceptance. Its contract freeze establishes design acceptance only; it does not establish implementation, hostile-page allocation safety or native accessibility readiness.

### Browser identity and UA preference

The operator explicitly prefers a Chrome-compatible default without a DorkOS brand token. Proposed default starts from the actual executable's native reduced User-Agent and changes only its `HeadlessChrome/` product token to `Chrome/`, when present. Preserve native version reduction and platform conventions rather than reconstructing the string from host OS/CPU. It never advertises a different engine/version to gain compatibility. Apply the policy before the first request and to every new Page/popup. Do not patch page JavaScript getters independently from network metadata.

Define one runtime identity descriptor for HTTP User-Agent, `navigator.userAgent`, `navigator.platform`, User-Agent Client Hints, brand lists and high-entropy full-version/platform/architecture values where supported. A Chrome-compatible UA string on Chromium does not imply the executable is branded Google Chrome: Client Hints and status must report actual engine/distribution truth, and accepted GREASE brands are not DorkOS branding. If the pinned engine cannot maintain the specified coherence through supported APIs, mark the Chrome-compatible gate failed and revise implementation before releasing that mode; do not silently ship contradictory spoofing.

The requested Chrome-compatible default remains a delivery objective, not an available mode until its full acceptance matrix passes. Native is an explicit, separately named option preserving engine defaults, including any headless token. Never silently substitute native identity for a requested Chrome-compatible browser. Changes take effect only on a fresh context/browser; do not mutate a live profile's identity mid-session. Show the actual runtime version for either available choice. The engine may use an internal identity descriptor, but this contract does not add a free-form UA editor.

Readiness records bind the exact executable hash, supported platform, policy revision and identity mode. Verified native mode can become available after its own complete identity, network, distribution and native/platform gates pass; a failed Chrome-compatible candidate neither rejects that separately verified mode nor activates Chrome-compatible mode. Unsupported or unobserved configurations remain unavailable. Core engine and fixture-only integration phases can progress while identity research continues. Full delivery retains the user's Chrome compatibility preference as unresolved work; native completion alone cannot close the parent.

The isolated native-metadata candidate has only a scoped Page/popup success: first request, negotiated hints and JavaScript metadata matched, and withholding its actual installation blocked popup requests until acknowledgment. Shared-worker JavaScript still exposed HeadlessChrome; service-worker initial script requests and JavaScript did too. Removing the initialization await produced a stale HeadlessChrome popup request during the hold. The candidate is rejected for full coverage. OOPIF, persistent/restarted contexts, nested/background worker lifetimes and other platforms remain unverified. Its private copied-package patch is research, never an installed dependency or production configuration; its independently reviewed cleanup correction still attempts exact-owned worker close after process-inventory failure, preserves the original error, and reports incomplete inventory as UNVERIFIED with allGone:null rather than inventing complete disappearance proof.

An optional explicitly selected branded Chrome executable may use exclusively DorkOS-owned private profiles with its own tested executable receipt. Never reuse the person's Chrome profile or attach to personal tabs. This is not the default and cannot inherit Chromium-only acceptance results. No option promises indistinguishability, anti-bot success or challenge bypass.

#### Identity acceptance matrix

Chromium deliberately freezes some legacy platform/version fields: macOS uses `Macintosh; Intel Mac OS X 10_15_7` and `navigator.platform` uses `MacIntel`, including machines whose actual architecture differs. Reduced browser versions may be `<major>.0.0.0`. Full version and architecture belong to supported high-entropy hints; coherence means matching the engine's conventions, not making every string equal to host hardware. [Chromium UA reduction](https://www.chromium.org/updates/ua-reduction/)

Before launch acceptance, collect a native baseline for each exact executable hash/OS/runtime choice. Store the native UA, appVersion, platform, low-entropy brand/mobile/platform fields and available high-entropy values. A proposed Chrome-compatible descriptor keeps that metadata, distribution brands and GREASE entries intact while normalizing only the headless product token in HTTP/JS legacy UA and appVersion. Chromium remains Chromium; do not add a `Google Chrome` brand to an unbranded executable. The observed native prototype `HeadlessChrome/153` with Chromium 153, GREASE `Not_A Brand` 8 and macOS is a scoped baseline, not a hard-coded brand order/version for future builds.

Do not assume Playwright's `userAgent` option preserves Client Hints. When overriding identity, the engine must apply a supported protocol configuration carrying both UA and native UA metadata before releasing a newly created target to network execution. Unchanged native mode needs no override, but still requires the full observed target/lifetime matrix. [Chromium Emulation protocol](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/) is a candidate implementation seam, subject to the pinned protocol's actual behavior. A popup that sends its initial request before identity application fails the gate; use a proven browser/context-wide policy or pre-execution target attachment, not a later page-event correction. Any worker request that uses a different identity also fails. No injected JS getter replacements or response-header rewrites substitute for browser evidence.

| Matrix dimension  | Required evidence and comparison                                                                                                                                                                                                                                                                                                                                                       |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime/mode      | Exact default Chromium and any separately selected branded Chrome; Chrome-compatible and native policies; fresh clean and named persistent contexts. No inheritance between runtime builds.                                                                                                                                                                                            |
| Initial request   | Dedicated trustworthy HTTPS fixture logs HTTP UA and low-entropy hints before any Accept-CH negotiation. Page records `navigator.userAgent`, `appVersion`, `platform` and `userAgentData` support. HTTP/JS legacy UA agree.                                                                                                                                                            |
| Negotiated hints  | Fixture sends Accept-CH for full-version-list, platform-version, architecture, bitness/model/wow64 where supported. Subsequent request and `getHighEntropyValues` agree under native conventions; full version matches actual runtime, major matches reduced UA and distribution brands remain native. Initial absence before negotiation is expected, not failure or fabricated data. |
| Lifetimes         | Same-origin navigation, cross-origin HTTPS navigation to second fixture, reload, popup's first request, worker request, clean-mode creation and persistent reopen. Policy applies before each first request; negotiate hints separately per origin.                                                                                                                                    |
| Negative controls | UA-only override that drops/mismatches hints, fake Google Chrome brand, host-arm64 rewrite of MacIntel, invented full version, and popup/worker without policy must fail the intended comparison. Native choice matches its collected native baseline, including headless token when present.                                                                                          |

Record absent API/hints as unavailable fields with cause and origin negotiation state. A runtime lacking required metadata cannot pass the Chrome-compatible identity gate on assumptions; it remains unsupported for that choice until a reviewed native alternative or different executable passes. No result proves indistinguishability or security-challenge bypass.

### Explicit installation and migration

`dorkos browser install` explicitly installs the reviewed full Chromium revision into a private versioned cache using the pinned official Playwright CLI with `install chromium --no-shell --no-remove`. `status` reports actual version/hash/platform and readiness without exposing profile contents. Browser actions never install or update implicitly. No `--with-deps`, system package changes or overwriting other caches. Validate an installation in a fresh process, then atomically publish its verified manifest. Cache reuse, concurrent install, interrupted install and revision mismatch require tests.

CLI build includes the private engine from the same source vintage and resolves runtime assets explicitly. Desktop server uses the same engine and manifest policy; executable assets must be real files through the established single-copy unpack strategy. Do not execute from virtual asar paths or duplicate binaries into unreachable resources. Any bundled runtime also needs installation provenance, updates, license notices and platform-specific acceptance. Website identity, macOS visibility and forced-crash guarantees do not follow from successful packaging.

Existing `browser login/status/forget` and `agent-browser.ts` site summaries are compatibility seams. Import a saved storage-state snapshot only with explicit authorization into a new named profile; it is not a complete profile clone. Do not silently reuse the old login profile or seed clean mode. Initially retain the existing browser path while the Shared browser experiment is off. While it is on, expose an explicit managed-browser selection across all runtimes only after the selected exact mode passes readiness and scoped capabilities explain changed persistence/sharing. Do not silently replace a requested mode, fall back to the legacy browser, replay an uncertain action or migrate a live page into another browser. Remove a legacy path only through a separately reviewed compatibility change; the initial opt-in rollout does not remove it.

### Default-off Shared browser experiment

Propose a persistent `UserConfigSchema` section `browser` with boolean `browser.enabled`, declared as `z.boolean().default(false)` and an enclosing `.default(() => ({ enabled: false }))`. This is instance-wide user configuration, not a session/room grant or temporary environment switch. Register it in the existing server `EXPERIMENTS` list with `graduationIssue: 'DOR-2671'`, no environment override, and consume the existing `describeExperiments` / `GET /api/config` / `ExperimentsTab` nested-patch flow. The user reaches the row under Settings → Advanced → Experiments. Do not create a second experiment registry or a separate settings page.

Proposed row: **Shared browser**. Description: “You and your agents can see and control the same page, even when you close its viewer.” Cost note: “Uses more memory and processing power. People you allow can see private pages and use signed-in accounts.” These describe the intended accepted behavior, not today's implementation status.

Append an idempotent config migration keyed to the actual implementation release, preserve an explicit existing boolean, and persist false for missing values. Validate both fresh defaults and stale config on disk; distinguish any whole-section default pre-write from a migration body's effect. Classify the leaf in both config exposure and write policies: show the nonsecret boolean, but treat activation of server-spawned browsing as operator-only. Mirror the setting in the developer and user configuration references during implementation. No schema, migration, registry or UI changes are made by this plan amendment.

The server is the authority for this global setting and for every browser grant. Use the existing guarded config-write mechanism across Settings, CLI and capability writes; do not trust caller-supplied actor fields. With login enabled, the existing operator-cookie bar and agent refusal govern this setting; do not invent an owner-only check the current generic route does not provide. A permitted global write affects all users' managed browsers, but does not grant the writer access to their private pages or profiles. With login off, retain and disclose the existing local-trust limitation: an unlabelled local process can resemble a Settings caller. A row hidden or disabled in the client is not enforcement.

Off denies new managed instances, actions, grants/control, viewer subscriptions and dynamic managed tools at the server admission boundary for every runtime. Enforce it in direct routes and long-lived streams as well as runtime tool discovery and dispatch; stale cached tool lists cannot bypass it. Keep lightweight Doc/iframe previews and their existing authority available without running Chromium. Private fixture development remains separately confined and cannot bypass public readiness.

Enabling checks the exact selected executable/platform/policy/identity mode's current accepted readiness before publishing on-state or admitting work. Missing installation, failed or unverified gates return a bounded truthful reason and leave the experiment off; never download on toggle or action. Installation alone is not readiness. Recheck readiness at dispatch and subscription, including policy/runtime changes. Native and Chrome-compatible remain separately named choices with their existing complete gates; unavailable Chrome-compatible never selects native implicitly. The Chrome preference and all five full-delivery requirements remain unresolved until their original acceptance passes.

A live disable linearizes at a server-owned admission revision: close admission and persist false before new work can enter, revoke viewer/control/profile-use/semantic grants, detach streams and invalidate queued work. Already admitted actions retain their attributable outcome; never report their effects undone. Advance input generation and drain/reset held input under the existing control barrier (at most two seconds), then stop only exact owned PID/birth identities with the existing bounded lifecycle cleanup. A timeout is not proof of cancellation, reset or process disappearance. Concurrent enable/disable writes and close/recovery must serialize against the same admission revision; late callbacks cannot reopen an old generation. If the config write fails, retain the admission fence, attempt cleanup and expose the persistence failure without off-success. Reconcile the persisted setting, pending shutdown evidence and exact process inventory on restart; uncertain persistence or cleanup refuses acquisition until reconciled. Startup never resumes stale browser metadata, queued work or grants. On restart, persisted false still blocks admission.

Only report completed off-state after reset/drain and exact-owned stop are observed. While cleanup is incomplete, report stopping or stopped/uncertain with a bounded reason; retain false admission and never claim off-success prematurely. If a process remains or observation is unavailable, retain its ownership/reservation evidence and refuse re-enable until safe exclusion/stop is established. Preserve named profile data; clean-mode cleanup follows its existing exact-stop rule. No automatic page/state migration to legacy browsing, uncertain-effect replay or stale action retry on re-enable. Re-enable needs fresh readiness and fresh browser/grant identities.

Task9.4 ([DOR-2672](https://linear.app/dorkspace/issue/DOR-2672/try-shared-browser-from-settings-experiments)) implements and proves this opt-in boundary; task9.2 consumes it for compatibility. [DOR-2671](https://linear.app/dorkspace/issue/DOR-2671/decide-whether-shared-browser-graduates-from-experiments) is a separate later graduation decision, outside initial rollout and full-programme closure dependencies. Graduation removes the registry entry in the same reviewed change that changes the default; eventual flag removal follows the normal lifecycle. This plan neither schedules default-on nor relaxes readiness.

### Doc Channel independence

Keep instrumented iframe previews and their parent/MessagePort authority independent from managed browser viewers. Doc Channel documents need not run through Chromium. A later browser-process transport requires its own reviewed contract and tests for emit/downstream replay with zero viewers, one emission with two viewers and revocation of old-page authority after navigation. It cannot infer SDK authority from possession of browser pixels or a tab ID.

## User Experience

Choose a named profile or start clean. An agent can keep working when the Browser panel closes. Reopening shows the current live page. Explicit stop closes the browser; switching views does not. Shared controls show who has control, who can view, and the scope of the grant. Taking control waits for the real barrier and exposes refusal/timeout.

Proposed messages follow the writing-for-humans standard:

- Installation: “The browser is not installed. Install it before opening a page.”
- Sharing: “These people can see this page. Anyone with control can use its signed-in accounts.”
- Recovery: “The browser stopped unexpectedly. Recent changes may be missing. Check the page before trying again.”
- Uncertain action: “The browser stopped during this action. Check whether it finished before trying again.”
- Clean mode: “This browser starts signed out. Your saved profile stays separate.”

## Security Considerations

### Mandatory destination broker

**Proposed B1/B2 clarification:** the inventory and CONNECT grant clauses below await independent whole-plan review before implementation release. Base `57ea622c06df54a6adeccb1e559c87cee23e089d` contains the reviewed task5.1 primitives, which remain unmerged at this checkpoint; their current conservative refusals are unchanged by this document-only proposal. Existing freeze provenance and all other gates remain intact.

Default managed mode assumes trusted, unmodified, pinned Chromium with its native sandbox enabled, running untrusted page code. Its web-network enforcement boundary is a per-browser authenticated forwarding broker, owned by `services/browser/egress/`. This is a tested destination policy for supported page protocols, not containment of browser RCE or arbitrary process/socket access. The engine receives a verified broker endpoint and lease, not a generic URL callback. Chromium proxy configuration has no DIRECT fallback, no PAC/system/WPAD inheritance, no positive bypass entries, and explicitly subtracts implicit localhost/link-local bypass with `--proxy-bypass-list=<-loopback>`. Chromium documents proxy-side DNS for HTTP proxies and HTTP/HTTPS/WS/WSS support; CONNECT preserves end-to-end TLS. [Chromium proxy documentation](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md)

A browser-wide broker lease binds browser generation, owner, policy revision and expiry. No origin sees its proxy credential; the broker strips proxy credentials from forwarded requests and refuses unbound clients. Independent profiles use independent leases. Grant revocation closes existing broker sockets/tunnels, not only future navigation. Proxy outage or lease failure blocks requests; it never retries directly.

Public mode allows HTTP/HTTPS and WS/WSS counterparts only to global unicast destinations, initially ports 80/443. Owner-authorized explicit public port additions are exact host/port grants. Deny loopback, private, link-local, multicast, unspecified, reserved, metadata endpoints, host interface addresses and IPv4-mapped IPv6 equivalents. Deny DorkOS admin authorities on every configured localhost/LAN/tunnel origin, including known aliases, before any allow grant; no local-dev grant can override that deny. Keep private/LAN/admin-listener address/port denies. For public tunnels on shared CDN infrastructure, deny the canonical hostname/port and configured aliases, not every site using its resolved public edge IP. Supported page requests to DorkOS APIs must be denied even if a page guesses paths or receives an app URL; this is verified at the fake admin listener, not asserted as a browser-compromise guarantee.

The server retains a complete trusted interface and protected-listener inventory, distinct from the permanent destination deny set. Public mode still denies every host interface address. Local-dev initially supports only exact canonical literal `127.0.0.1` or `::1` endpoints selected by the authenticated profile owner for an authorized workspace. Eligibility requires complete protected-listener coverage: no app/admin authority, listener address/port or explicitly permanent address/interface deny may overlap the endpoint. Ordinary eligible loopback is not implicitly placed in the permanent address deny set; an explicitly configured permanent loopback deny still wins over every grant. Non-loopback interfaces, LAN endpoints, DNS names resolving to loopback, other loopback aliases, port ranges and redirects to adjacent local ports remain unavailable as local grants. Public subresources still follow public policy.

The server-owned inventory adapter records actual listener bind address/family/port, known numeric aliases and advertised app/admin authorities. It accounts for wildcard and dual-stack listeners on each supported canonical loopback; incomplete or unknown coverage suspends local-grant admission and closes active local-grant circuits until reconciled. Listener/interface/alias changes advance policy revision and close affected or conservatively all old circuits before updated admission. The adapter derives the protected deny set explicitly rather than accepting caller-supplied lists or silently filtering a complete inventory. A server-owned preview endpoint still requires a separate explicit preview grant whose upstream is already confined. No grant overrides permanent app/admin denial.

For each CONNECT, absolute-form HTTP request and WS upgrade: parse and canonicalize the authority once; reject userinfo, ambiguous/invalid hosts, mismatched Host/absolute-form authority and forbidden port/scheme. Resolve DNS in the broker with bounded lookup/CNAME depth, evaluate every A/AAAA answer and reject mixed allowed/forbidden sets. Select an allowed numeric IP, create the upstream socket using that literal address without a second hostname lookup, verify the connected peer address, and bind the socket to policy revision/authority/IP. Retry evaluates fresh answers and never silently falls back to an unvalidated address. New connections repeat validation; a DNS change cannot retarget an already pinned socket. Local grants use only their pinned literal endpoint.

CONNECT permits an opaque destination tunnel only to its validated authority/IP/port, with byte/time budgets and revocation. Local-dev HTTP and observable WS grants remain exact scheme/host/port grants. Secure local-dev access uses an explicitly distinguished private CONNECT endpoint grant, bound to the exact literal host/port, owner/workspace/browser generation, policy revision and expiry. CONNECT carries no inner scheme: its grant may carry HTTPS or WSS in the supported trusted-browser configuration, and does not certify TLS presence, inner protocol, path or virtual-host authority. Strict HTTPS-only or WSS-only local grant requests are unsupported unless a separately reviewed enforcement seam exists. No silent WSS-to-HTTPS coercion, arbitrary TCP tool or generic protocol capability is introduced. Native protocol and first-target gates remain separate requirements. Revoking a CONNECT endpoint grant closes every associated tunnel or secure WebSocket, including worker traffic. TLS remains browser-to-site with certificate validation enabled; no interception CA or `ignoreHTTPSErrors`. The broker cannot inspect encrypted paths, redirects or HTTP/2 authorities, so it enforces destination endpoints, not HTTPS path rules or proof of virtual-host identity. Private/LAN admin authorities also deny their known address/port aliases. A public shared-CDN address does not establish equivalent virtual-host authority: unrelated allowed hostnames remain eligible even when they resolve to the tunnel's edge IP. Deny the public app's canonical hostname/port and configured hostname aliases before DNS, and close affected tunnels on alias/policy changes. Do not claim detection of unknown virtual-host aliases from IP equality. Every redirect/subresource/worker/WebSocket connection must still reach a permitted endpoint. No existing CONNECT or connection pool may cross to a newly forbidden endpoint; policy changes close affected pools/tunnels. Origin-level UI checks are additional restrictions, not a substitute for this endpoint boundary.

Current Chromium source enables H2 IP-pooling lookup only for direct proxy chains and records cross-domain IP aliases only for direct sessions. This supports the inference that mandatory proxy tunnels remain authority-separated; current-source behavior is not proof for pinned Chromium 153 or future builds. [Chromium socket pool](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/socket/client_socket_pool.cc), [Chromium SPDY pool](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/net/spdy/spdy_session_pool.cc)

Require exact-runtime shared-IP/shared-SAN HTTP/2 acceptance: warm an allowed hostname's tunnel/connection, then attempt a denied app hostname covered by the same certificate on the same IP. The allowed host must still work, and the denied hostname must receive a separately denied CONNECT with no app upstream request. Exercise cross-origin fetch, navigation/redirect, iframe, popup, workers/service workers, WS/WSS and alternative-service advertisements; test tunnel grant revocation too. If the runtime can reuse an allowed tunnel across the denied authority, that configuration fails acceptance until a supported authority-preserving restriction is reviewed and verified. This contract does not introduce default H2 disablement, CDN-wide IP denial or TLS interception.

Managed browsers never receive the app viewer's DorkOS cookies, local token or user keys through headers, engine configuration or profile seeding. Broker authority denial supplements server authentication and origin checks; it cannot replace them or prevent an allowed remote server from relaying requests itself. Verify denied app requests remain unauthenticated and refused at a fake admin service even when attempted through an allowed relay fixture. Profile site state grants do not authorize DorkOS administrative access.

Service workers remain enabled to preserve the retained-state requirement. Playwright routing neither intercepts all service-worker traffic nor preserves HTTP cache when enabled, so `route()` is not the firewall. All supported HTTP(S)/WS(S) connects from Pages, popups, iframes, dedicated/shared/service workers and background requests must use the mandatory broker. [Playwright BrowserContext routing](https://playwright.dev/docs/api/class-browsercontext#browser-context-route)

### Native protocol restrictions and limits

The engine is not an OS sandbox, and proxy flags alone do not prove all-protocol confinement. The supported runtime configuration must disable or policy-route page-accessible non-proxy networking, including WebRTC ICE/STUN/TURN and data channels, WebTransport and QUIC/HTTP3. Keep Chromium's native sandbox enabled. Select only supported restrictions verified on the exact runtime build; do not assume a proxy setting, denied camera permission, JS API shim or guessed command-line switch blocks these protocols. Native restrictions apply before the first Page/worker executes and cannot be changed by an agent action.

Before accepting a runtime configuration, actual native page-API fixtures must attempt these protocols against fake loopback/private/admin endpoints while recording endpoint connects/packets. A passing negative needs an exercised API/attempt and observable endpoint, not an unavailable API mislabeled as a block. Verify permitted HTTP(S)/WS(S) positives concurrently, no DIRECT fallback with a dead broker, and the behavior of all unsupported URL schemes. If a reachable page protocol can bypass destination policy and cannot be disabled or routed through the broker with supported runtime controls, return `NETWORK_POLICY_UNSUPPORTED` and refuse that configuration. Missing observation remains unverified and cannot enable it. Record the exact protocol/restriction gap before selecting a revised runtime or narrower supported protocol set.

This default policy does not promise prevention of browser exploits, compromised Chromium, raw socket access by native processes or all host egress. It does not require new Apple entitlements, privileged firewall changes or a platform-isolation launcher. A hardened OS-isolated mode may be separately proposed later with concrete platform topology, permissions and tests; it is optional future work, not a blocker for the five authorized requirements. No silent privileged host changes or disabled Chromium sandbox.

### Files and artifacts

Reject `file:`, external/custom schemes and arbitrary executable/path inputs. App-owned `about:blank` and same-origin blob/data documents may render without network authority; their fetches still traverse the broker. Local HTML previews use a confined server grant, not browser filesystem access. Engine actions expose only private profile/staging roots and authorized artifact IDs, never arbitrary operator paths or personal profiles. Native file-picker actions require explicit staged-file authorization and cannot become a general filesystem browser. This API/path policy does not constrain a compromised executable or claim OS file isolation.

Uploads require an authenticated actor grant for a server-staged artifact ID, normalized/realpath-confined to an owner/browser-specific staging root, size/type limited and opened without following a changed symlink. Agents cannot supply absolute paths or browse operator files. Downloads default to deny unless explicitly granted; authorized downloads go to exclusive private staging paths with sanitized filenames and byte/time quotas, never website-supplied filesystem paths. Publish only an artifact ID after completion and ownership validation; cancel partial/oversized downloads and remove them on cleanup. A room attachment never grants artifact access. Profile, cookie, cache, executable and reservation files cannot be uploaded/exported through this surface.

### Exact negative fixtures

Use fake sites and isolated endpoints; never operator/admin production services. A policy-equivalent fake admin listener records accepted sockets/requests and must remain untouched. A controlled resolver provides global-to-loopback rebinding, mixed public/private A/AAAA, CNAME-to-private, mapped-IPv6 and reconnect-after-TTL cases; assert zero forbidden upstream connects, not merely a browser error. A positive approved public fixture and one exact owner-granted local dev endpoint must receive their intended requests. Shared-CDN fixtures additionally require the allowed and denied hostnames on one IP/shared SAN certificate: deny the app authority without denying the allowed host, and record CONNECT plus upstream request observations after H2 warmup. Current source comments alone cannot pass this gate.

Repeat blocked fetches from navigation redirect, image/script, iframe, popup, service-worker install/fetch after page detach, dedicated/shared worker and WS/WSS. Include direct localhost and alternate loopback encodings, link-local metadata, adjacent local-dev port, expired/revoked grant and fake admin address/alias with a nominal local grant. TLS CONNECT denial, no DIRECT fallback on broker death and revocation of an already open WebSocket/tunnel must be observed. Actual WebRTC ICE/STUN/TURN/data-channel, WebTransport and QUIC/HTTP3 page attempts must not reach fake denied endpoints under the accepted native restrictions. A controlled removed-restriction or bypass-enabled mutant must exercise the intended failure; raw-socket worker helpers do not substitute for page-API evidence. Artifact tests reject traversal, symlink swap, outsider/room-only access, private-profile upload, oversized/partial download and filename overwrite; positive staged upload/download retains only authorized artifact data. Additional B1/B2 fixtures prove an exact eligible canonical loopback dev endpoint works while an explicit permanent loopback deny and every fake admin listener/alias remain denied before grants. Cover applicable IPv4 wildcard and observed IPv6/dual-stack listener coverage; unknown inventory suspends admission and closes local circuits. Noncanonical loopback and adjacent ports refuse. An explicit CONNECT endpoint grant permits actual HTTPS and WSS on one exact owned secure endpoint, while strict inner-scheme-only requests refuse before grant/dial; HTTP and observable WS grants cannot substitute for CONNECT. Revoke while both secure transports are live and observe closure on both sides. Removed admin-deny or live-circuit-close mutants must expose the named forbidden endpoint or surviving circuit; unrelated setup assertions cannot certify detection. These are future acceptance fixtures, not observations established by this clarification.

Cookies, URLs, page text, screenshots and console/network payloads may contain secrets. Diagnostics require bounded retention, attribution to tab/navigation/request, truncation markers, redaction and explicit sharing. Browser binary provenance and updates are security-sensitive; identity presentation does not reduce that risk. No copied page code receives app-origin credentials or access to `/api/*`.
