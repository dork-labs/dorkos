# Identity runtime options

**Status: Proposed research recommendation.** No runtime candidate is accepted. This note does not amend [06-production-specification](06-production-specification.md), approve production activation or relax the user's Chrome-compatible preference. Normative context is the parent's production-design review at `349` and the frozen 06 contract; this independently owned note is for design review.

## Decision still required

06 requires a proposed Chrome-compatible default, an explicitly selected native option, actual engine/distribution/version metadata, consistent identity before first script/network across Pages, popups, frames and workers, private profiles, and no Chrome Dock/app-switcher presence or stolen focus on macOS. Neither the rejected metadata experiment nor the unchanged-native Phase1 proves that complete contract. Native is not an automatic substitute; changing the Chrome goal requires a direct human scope decision.

This research performed no launches, installation, browser acquisition, profile/account access or source/dependency changes. Source inference below is distinguished from the already retained actual observations. No path promises indistinguishability or security-challenge bypass.

## Pinned source constraints

1. **Headless full Chrome keeps the prefix.** `components/embedder_support/user_agent_utils.cc`, `GetUserAgentInternal`, inserts `"Headless"` into the product when `kHeadless` is present. `GetUserAgentMetadata` returns early on a command-line custom UA, before native full-version/architecture population. The early result is empty or low-entropy-only depending on `kUACHOverrideBlank`; disabling that feature does not restore all high fields. Consequently branded Chrome, unified headless or a launch `--user-agent` string alone is not a solution. [Exact implementation](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/components/embedder_support/user_agent_utils.cc)
2. **No context-wide identity option in this CDP pin.** `third_party/blink/public/devtools_protocol/domains/Target.pdl`, `createBrowserContext`, provides proxy/isolation options, no UA/metadata policy. `Emulation.pdl` exposes target-level `setUserAgentOverride` with optional metadata. This is a source/API finding, not proof that every future API lacks such a seam. [Target](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/public/devtools_protocol/domains/Target.pdl), [Emulation](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/public/devtools_protocol/domains/Emulation.pdl)
3. **Worker Emulation exists, but first-fetch ownership is unresolved.** `third_party/blink/renderer/core/inspector/worker_inspector_controller.cc` installs `InspectorEmulationAgent` for WorkerGlobalScope. `inspector_emulation_agent.cc`, `setUserAgentOverride`/`ApplyUserAgentMetadataOverride`, supports override state without requiring a frame. This makes an owned pre-resume script policy plausible; it does not prove the initial worker script fetch waits for that policy. [Worker inspector](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/renderer/core/inspector/worker_inspector_controller.cc), [Emulation implementation](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/renderer/core/inspector/inspector_emulation_agent.cc)
4. **Playwright currently owns and resumes targets.** `packages/playwright-core/src/server/chromium/crBrowser.ts` handles Pages/service workers and detaches shared workers: “Detach from any targets we are not interested in”. `crPage.ts` resumes dedicated workers without an explicit UA installation. `crServiceWorker.ts` calls updateUserAgent without awaiting it, then resumes; later crash reload resumes again. Native metadata is not a public context option. [Browser](https://raw.githubusercontent.com/microsoft/playwright/v1.63.0/packages/playwright-core/src/server/chromium/crBrowser.ts), [Page](https://raw.githubusercontent.com/microsoft/playwright/v1.63.0/packages/playwright-core/src/server/chromium/crPage.ts), [Service worker](https://raw.githubusercontent.com/microsoft/playwright/v1.63.0/packages/playwright-core/src/server/chromium/crServiceWorker.ts)
5. **Worker hint omission has a native explanation, not accepted coverage.** `third_party/blink/renderer/core/loader/worker_fetch_context.cc` notes that workers lack a permissions policy for deriving proper hints. FrameFetchContext has document/policy hint generation. The actual same-endpoint positive controls support this interpretation, but required missing observations remain UNVERIFIED. [Worker fetch](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/renderer/core/loader/worker_fetch_context.cc), [Frame fetch](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/renderer/core/loader/frame_fetch_context.cc)

## Route A: private non-headless runtime with hidden targets

**Source-supported candidate, not observed.** Native non-headless identity avoids the headless-token override path. The experimental `Target.createTarget(hidden:true)` protocol states “The target will be observable via protocol, but not present in the tab UI strip.” It forbids tab-target/new-window combinations and ties lifetime to the session. Chrome's target handler falls through for hidden targets; content's `HiddenTargetManager` creates WebContents with its own delegate and retains them until closure/session cleanup. [Pinned protocol](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/third_party/blink/public/devtools_protocol/domains/Target.pdl), [Chrome handler](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/chrome/browser/devtools/protocol/target_handler.cc), [Hidden implementation](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/content/browser/devtools/protocol/hidden_target_manager.cc)

Do not equate a hidden tab with an invisible native application. Official Chrome describes headless mode as creating but not displaying platform windows; that statement does not cover non-headless hidden targets. Normal Playwright `newPage` does not request `hidden:true`. Its adapter/target creation path would need explicit reviewed support, without a second autoattach owner. [Official headless modes](https://developer.chrome.com/docs/automation-and-testing/headless), [Pinned Playwright creation](https://raw.githubusercontent.com/microsoft/playwright/v1.63.0/packages/playwright-core/src/server/chromium/crBrowser.ts)

**Smallest early falsifier:** in a parent-reviewed, coordinated correctness slice, observe actual startup, hidden-target creation and a real popup for Dock/app-switcher/focus against a visible-app positive control; prove Playwright can adopt the target and capture/render/input; disconnect its owning session and record exact target lifetime and cleanup. Stop on visible app presence, stolen focus, unsupported adoption/popup behavior or broken rendering. Only if viable, expand to first HTTP/JS/native metadata, actual cross-site frame and all three worker kinds, private persistent clean close/reopen/restart, and reconnect/recovery presence. Persistent stores and live Page-JS state remain separate claims. This separates an early feasibility falsifier from full acceptance work.

Route A still uses native worker fetch behavior. Dropping `--headless` does not itself resolve the presently unaccepted worker HTTP-hint availability interpretation; missing required observations remain UNVERIFIED.

**Cost:** retains an upstream browser binary but adds experimental target-adapter maintenance and platform presence acceptance. Branded Chrome must be an explicit privately installed executable with exact provenance; no personal Chrome profile/tabs. Native sandbox and mandatory egress policy still need exact-runtime proof. This route may conflict with 06's specified headless executable, requiring a reviewed contract amendment rather than an implementation shortcut.

## Route B: one Playwright attachment owner and native fetch policy

**Candidate extension, not supported public option or complete proof.** Prefer a reviewed upstream context-native identity option if one becomes available. For 1.63.0, a narrow maintained Playwright change could retain target ownership in CRBrowser/CRPage/CRServiceWorker, validate native metadata, install it before resume, own shared-worker restart and propagate policy to nested workers/OOPIFs. Do not layer a separate controller that changes autoattach or competes over sessions.

The decisive gap is **first script fetch**, especially service-worker install/update and shared-worker creation/restart. Script execution pause alone is insufficient. Before extending the rejected patch, establish the exact pinned service/shared-worker script-fetch ordering relative to target attachment and identify a native browser/context or pre-fetch policy seam that covers that request; prove the real server receives no stale request while policy acknowledgement is held. If it is already fetched before attachment, reject this route for the current contract. No late override repairs history, and HTTP header substitution does not establish JS/native coherence.

**Minimal decisive proof:** begin with service-worker installation and shared-worker first request, a held policy acknowledgement and actual omission/ordering mutant. Only if these work, expand to initial/popup/OOPIF/dedicated/nested targets, detached worker/background events, SW update/restart and private persistent reopen/restart. Each request must bind target URL/id, lifetime and actual native descriptor; no expected-schema-only negative. API errors and missing metadata fail closed; unavailable observers remain UNVERIFIED with zero invented subjects.

**Cost:** package patch/types/protocol propagation, upstream rebase checks, reproducible builds and source/bundle hashes on every upgrade. If no native pre-fetch seam exists, a narrowly reviewed custom full-Chromium change that removes only the Headless prefix in `GetUserAgentInternal` (pinned lines202–215), leaving native metadata generation intact is a **custom binary maintenance route**, not a launch option. It adds Chromium security-update response, signed/notarized per-platform distribution, license/provenance/SBOM, reproducible patch correspondence and full runtime regression ownership. It is not branded Google Chrome merely because its legacy product token is Chrome.

A separate headless embedder has independent legacy-UA/native-metadata paths, but is not a drop-in shortcut: pinned `headless/lib/browser/headless_browser_impl.cc` regenerates native brands with HeadlessChrome, and `headless_content_browser_client.cc` disables network-service sandboxing. Browser options/context UA do not prove coherent renderer/worker defaults; CLI `--user-agent` still reaches the metadata-suppressing path. Any custom embedder requires separate native policy, sandbox, compatibility and distribution review. [Metadata implementation](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/headless/lib/browser/headless_browser_impl.cc), [Browser client](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/headless/lib/browser/headless_content_browser_client.cc), [Public options](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.12/headless/public/headless_browser.h)

## Route C: explicit native mode

**Separately gated option already contemplated by 06, not a silent fallback.** Native keeps unmodified engine identity, including HeadlessChrome when present. The corrected actual Phase1 supports bounded JS/legacy HTTP coherence, not complete metadata/network/lifetime/platform acceptance. First complete the independently reviewed availability interpretation and remaining native matrix; never promote omitted hints into observations or call the native choice Chrome-compatible.

**Cost:** lowest identity-maintenance burden because it avoids overrides, but still needs exact executable/platform upgrades, sandbox/egress, persistent-profile and presence acceptance. It leaves the Chrome-compatible goal open unless the human explicitly changes scope. A user selecting native knowingly is different from silently changing a proposed default after initialization failure.

## Common proof and cleanup boundaries

Future proof work needs a parent-reviewed scope and measurement coordination within the already authorized research; this note does not itself schedule a launch or widen that scope. Use only fake owned trustworthy HTTPS sites/private profiles, native sandbox enabled, exact executable/package/source hashes and narrowly scoped fixture-only TLS trust. No system trust changes, general TLS bypass, personal accounts, paid inference or live product/demo changes. Runtime installation/distribution is explicit; no silent downloads on action paths.

Register cleanup before acquisition. Record each attributable owned PID and birth identity, bounded graceful close and exact-identity termination only; never process groups/operator processes. Observer failure must still attempt graceful cleanup and preserve the original observation error as UNVERIFIED, with inventory completeness/allGone unavailable rather than fabricated. Retain candidate failure, acquisition failure, missing observations and cleanup outcome separately. Zero subjects cannot certify a pass.

## Recommendation and independent challenge

There is no accepted stock-runtime seam at this pin. Do not broaden the rejected patch until the native first-fetch question has a source-backed answer. Route A is the most distinct alternative using an upstream binary, but its macOS presence/popup contract may decisively reject it. Route B is justified only after a pre-fetch seam is demonstrated; otherwise its honest continuation is a reviewed native-binary maintenance decision. Route C can be developed as the explicit native option while the full Chrome goal stays open, not as an automatic escape from it.

The parent reassigned independent debate to the existing manager reviewer after both control-agent contact attempts hit the collaboration thread limit. The manager's read-only critique agreed there is no accepted stock seam and that native/headless-shell choices cannot stand in for Chrome acceptance. It challenged the original Route A “minimal” proof as too broad, noted that non-headless mode does not settle native worker hint availability, and required exact SW/shared fetch-before-attach analysis before another Route B patch. This revision incorporates those corrections: early presence/adoption/lifetime falsifier first, explicit availability dependency, and stop on an already escaped script fetch. The manager also identified a prefix-only custom full-Chromium change as source-plausible; it is recorded solely as a maintained-binary candidate, with no implemented proof.

This independent debate is design input, not compliance/quality acceptance of this exact document or production approval. The parent still owns document review and route selection. Native availability interpretation remains unaccepted.
