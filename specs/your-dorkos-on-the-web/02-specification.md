**Words.** A **home** is a DorkOS that holds an agent's space side (OneHome, "Decision"): a person's own computer, or their DorkOS in the cloud. **Your DorkOS in the cloud** is the server that code and the hosted contract call a "hub" (`DORKOS_SERVER_ROLE=hub`); this spec says "cloud home" for short. It is the home of the private space for a person with no computer, the home of any agent they run on a cloud agent computer, and otherwise a way in. **The link** is the session relay between a cloud home and a person's own computer (`packages/shared/src/session-relay.ts`). A **relayed caller** is a request that came over the link. "The web" means the app opened in a browser at the person's cloud home.

## The short version

- **The web is a window, not a third home.** It shows what lives in your DorkOS in the cloud directly, and what lives on your Mac by asking the Mac while it is on. Nothing of the Mac is copied to the cloud to make that work, except the list of your homes with whether each is reachable, and a notice the Mac chose to send.
- **Away is said, never faked.** A Mac that is off shows as away, with its agents' names where this browser has seen them, and no history.
- **The link stays the Mac's.** It carries chats (stream, send, approvals, interrupt), as built, plus three reads and one delivery this spec adds: the Mac's list of agents with its presence, a notice the Mac sends, the Mac's answer to a search, and the cloud home's list of its own agents for the Mac. Each is a row for Security, is named in the Mac's consent line, and has its own switch at the Mac, off for a link that existed before. The Mac turns it on, limits it, records it and turns it off.
- **One list, by home.** Wherever the app is opened, it lists your agents grouped by where each lives: this computer, your other computers, the cloud. Each home is asked only for its own.
- **The account holds account things.** Who you are, how you sign in, your homes and devices, and what the hosted service needs to bill. No settings of a space, no chats, no inbox contents. A space's settings stay on its home; working hours stay on the Mac.
- **Everything beyond chats opens the Mac's own page.** Rooms, docs, settings, files and the terminal open the Mac's managed remote address, behind the Mac's own login.
- **A cloud home that holds an agent with a schedule tells the hosted service when to wake it,** through the next-wake operation the contract already has.
- **A person with only a Mac sees no change.** Everything is added beside what exists, and the link is off until they turn it on at the Mac.
- **Every old step has a verdict** (§7). Most stand and many are built. Ten of the parent's steps and decisions change (P4, A6, B2, B6, B7, B8, B9, B10, C11, C12), as does the L1a gate; B8's default posting is dropped, and A7 to A11 move to item 14.

## Goals

- A person who opens the app on the web sees one list of every agent they have, each with where it lives and whether it is there, and can chat with any agent whose home is reachable.
- A person with a Mac reaches their private space from anywhere: chats through the link, everything else on the Mac's own page.
- A person with no computer gets their whole private space in their DorkOS in the cloud, as the parent planned.
- Nothing that lives on a person's computer is kept in the cloud beyond the two named exceptions (W1), and an away home is always shown as away (W2).
- The Mac decides what the web may reach (W3), and every new reach is signed by Security before it ships.
- The account and the hosted service see account things only (W5).
- A person with only a Mac, and a person whose install already has a DorkOS in the cloud, lose nothing on upgrade.
- Each step ships alone and leaves the app working.

## Non-goals (out of scope)

- Cloud agent computers: their start and stop, "Works on", the tool bridge, their DorkBot, credits running out, and export and import (roadmap item 14; parent steps A7 to A11).
- Team spaces, DMs with a teammate's agent, the teammate tier, space page protections, a space waking a computer, and seats (item 15; parent C5 to C10).
- Moving the private space onto the space store (item 16).
- **Two homes working together**: what an agent in the cloud may do on the person's Mac, where a room or a document shared by a Mac agent and a cloud agent lives, and how a message between a Mac agent and a cloud agent is carried and trusted. It is its own later piece of work (§7.5). Until it is decided, an agent on one home has nothing on the other (OneHome rule 9).
- Moving a home, or moving one agent from one home to another.
- A copy of a Mac's chats, or of any part of a Mac's inbox beyond a notice, in the cloud.
- Widening the link beyond what §6 lists: the chats, the two agent lists (the presence of R-Q11), the notice and the search read.
- Publishing (item 19). Its use of the cloud home as an always-on home is item 19's; this spec only makes sure the cloud home can wake for its own work.
- Prices and plans. This spec names only what `packages/cloud-api` exposes and what `meta/ROADMAP.md` already says in public words.
- The frozen space code (`services/spaces`, `apps/space`, the community wire, `spaces/migrate.ts`), until the Community Space opens (W9).

### 1.3 The link today

**Who dials.** The Mac dials only the cloud home and key it pinned, when the hosted service's command stream says a viewer is open (`services/core/session-relay/relay-dialer.ts`; the cloud home asks for it through `services/core/hub/hub-relay-wake.ts:39`, which calls `ViewerOpenResponseSchema`'s route, `packages/cloud-api/src/hubs.ts:430`). A computer that is not connected is woken and answered `503` with `Retry-After` (`routes/hub-computers.ts:31-35`; `services/core/hub-relay/computer-waker.ts:31`).

**What it carries.** Six request kinds, all keyed by chat and all asked by the cloud home of the Mac (`packages/shared/src/session-relay.ts:296-382`): `chats.list` (titles and times only), `session.stream`, `session.send`, `session.interrupt`, `interaction.challenge` and `interaction.respond` (approve, deny or answer). The Mac serves the first four always, and approvals only while an approvals passkey is pinned (`relay-request-server.ts:80-93`). `interaction.respond` approves or denies only with a passkey proof and refuses the `answer` kind (SCC §1.4). There is no request from the Mac to the cloud home, and no request that lists the Mac's agents: the cloud home's linked-computer record holds keys and a name only (`services/core/hub-relay/computer-store.ts:45-65`).

**What the Mac serves.** Only a person's own chats with a registered agent that is not a system agent; never a room turn, a schedule, a beat, a bridged chat or a chat another agent started. A chat it does not serve answers as one that does not exist (`services/core/session-relay/relay-serves.ts:1-16`).

**What the cloud end lets through.** Only the owner's own browser session reaches `/api/hub/computers`: an agent identity or an API key is refused, every request is parsed by the shared relay schemas and an unknown field is a `400` (`routes/hub-computers.ts:1-22`).

**What the code does for a relayed caller.**

| Where                                                               | What it does                                                                                         |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `lib/request-classifier.ts:118`                                     | A request that came in over the link is its own kind, `relayed`                                      |
| `services/core/auth/gate-policy.ts:80-81`                           | `relayed` is `refused` at every HTTP gate: relayed work enters only through the Mac's request server |
| `lib/caller-principal.ts:51`                                        | Its principal is `{ kind: 'relayed' }`, never the operator or a program                              |
| `services/session/asks/ask-entitlement.ts:120-121`                  | It may see an ask; whether its answer counts is the request server's decision                        |
| `services/notifications/notification-entitlement.ts:55-56`          | It gets nothing of the inbox                                                                         |
| `middleware/remote-access-switch.ts:77`                             | The Remote Access switch covers it                                                                   |
| `routes/extensions-rooms-bar.ts:65`; `routes/extensions-forward.ts` | Mini app paths refuse it                                                                             |

**Where it is turned on.** At the Mac only: `sessionRelay.enabled` (default off), the pin's level (`chat` by default, or `full`) and its pause, written only through the pin store (`pin-store.ts:211-232`), never through config (`packages/shared/src/config-schema.ts:690-694`).

```
   │   Mac asks cloud:  home.agents (the cloud home's own agents, for the Mac's list)
   ▼
 Your Mac (home of the private space and of its agents)
     everything else (rooms, docs, settings, files, terminal) ◄── page move to the Mac's own
                                                                  managed remote address, its own login
```

Nothing on the cloud side of the link keeps what a Mac answers, except the notice (W1). The browser may keep, on the person's own device, the names of a home's agents it last saw, to show them as away (§4.6).

### 4.2 Chats with a Mac's agents, and the client that reads them

The cloud end exists (`routes/hub-computers.ts:354-430`). This spec adds the web's client for it (step Y4):

- **Transport.** `hub-methods.ts` gains a method for each route the server already has: list chats, open the stream, send, interrupt, and (with B4) answer. A relayed chat renders in the same chat view as a local one, from a transport that reads the relayed stream. No new server route is needed for chats.
- **What a person can do.** Read the chat as it streams, send a message, stop the agent, and, once B4 lands, approve or deny with a passkey. Answering a question from the web waits for B4 too: today the Mac refuses the `answer` kind (SCC §1.4), and the web says "Answer this on your Mac" with a link to the Mac's own page when full control is on.
- **Starting a chat.** A new chat with a Mac agent from the web is a `session.send` with no chat id, which the Mac already caps (`RELAY_MAX_LIVE_NEW_CHATS`, `relay-request-server.ts:159`).
- **Approvals** are answered as the decided records require: with a passkey proof bound to the exact action (EIAS:61 rule 5; parent B4; L1a step 4). Until B4 lands, the web shows the approval card read-only with "Approve this on your Mac".
- **Creating a Mac agent from the web** is a page move, never an operation on the link (the design note's open question 1, `specs/everything-is-a-space/design-agent-computers.md:110`; OneHome rule 4).

### 4.3 Everything else: the Mac's own page

Rooms, docs, settings, files, connections, previews and the terminal of a Mac open the Mac's own managed remote address, behind the Mac's own login (EIAS:60 rule 4; R-Q5). This is parent step B5, which stands: offered only when the Mac's owner has turned on full control at the Mac (which is also when the directory holds the address the hosted service issued for the Mac's own page, `packages/cloud-api/src/directory.ts:171-173`, unchanged by K1) and the account is entitled (`packages/cloud-api/src/billing.ts:124-129`, `fullControl`, "Absent reads as no"). Without it, the web shows what a person needs to turn it on, in the words `meta/ROADMAP.md:51` already uses. With the Mac away, the page move is not offered.

### 4.4 The inbox view and the notice

One inbox view, two kinds of item (R-Q2). **The web's inbox is the cloud home's items and the notices a Mac sent. There is no live read of a Mac's inbox on the link** (§3.1, R-Q2).

- **The cloud home's own items**, as its notification store holds them today, always shown.
- **Notices from a Mac.** A Mac's own notification service decides which items it delivers, by what leaves the machine today: **only a `blocking` item becomes a notice, and only once the escalation delay that exists, `notifications.escalation.phoneAfterMinutes`, has passed without an answer** (never when it is `'never'`). The escalation service arms that timer when a blocking condition starts standing (`services/notifications/escalation-service.ts:215-221`, `arm`, and `:288-300`, `armIn`) and fires it, reading the delay again (`:315-323`, `fire`; `delayMs`, `:484`); the notice is one more thing that fire sends. No other item makes a notice. It delivers to "your DorkOS on the web": a new delivery channel beside `services/notifications/channels/web-push.ts` and `relay.ts`, behind the Mac's notices switch (§6), off until the person turns it on at the Mac. Each notice carries a kind, the agent's id and name, one line, **a target kind and a chat id, never an address**, a time and an id, sent with `notice.deliver` (§6). The Mac keeps a small outbox and delivers when it can reach the cloud home; the Mac asks the hosted service to wake a sleeping cloud home first (§8, K2). The cloud home keeps a notice until it is read or 7 days pass (§15, question 3), then drops it. It keeps at most 200 notices for each computer, and drops the oldest first. It keeps nothing else of the Mac's inbox.
- **A notice from a turn that read words from outside says so.** A notice made in a turn that carried the outside mark carries that mark, and the web shows it beside the line: "From a turn that read outside text." (7 words) So a line an outside text shaped never reads as DorkOS speaking. It is still plain text with no link of its own.
- **The cloud builds the link.** From the target kind and chat id, the cloud home builds the link itself: `chat` opens that chat through the link (§4.2); `page` opens the Mac's own page at the address the directory holds for that Mac (`DirectoryInstanceSchema.remoteAddress`), which it holds only while the Mac's owner has turned on full control at the Mac (`directory.ts:171-173`); when the directory holds no address for that Mac, the notice shows with no link. It refuses a notice with any other target kind, with a chat id of the wrong shape, or with any field it does not know (the schema is strict). It shows the line and the agent's name as plain text, never as markup or a link.
- **Grouping.** The inbox groups by where an item came from: this home, each Mac. With a Mac away, its group shows the notices already delivered, each with its time, and one line: "Maya's MacBook is away. New items show when it's back."
- **Opening a notice** opens the link the cloud built. Opening it marks it read in the cloud home's copy only; the Mac's own inbox is the Mac's.
- **Account notices** (a new sign-in, C11) go to the cloud home's inbox, as L1b's open question 4 recommended.

### 4.5 Search across homes

Search on the web asks each home (R-Q3; step Y11, Y12):

- The cloud home searches its own index (`services/search/`) and, as today, the spaces the person is in.
- While a Mac is reachable, the cloud home sends it `search.query` (§6) with the words and a limit. The words are at most 200 characters and are matched literally: never as a pattern, and never as a query language the Mac parses. The Mac searches its own index, keeps only matches in chats the link serves (`relay-serves.ts`), and answers each match with the chat's id and title, the agent, the time and **the matching line of a message, never anything from tool output** (§15, question 4). Nothing of the answer is stored in the cloud.
- Results are grouped by home. With a Mac away: "Your MacBook is away, so its chats weren't searched." A Mac that answers late is left out of that search, with "Your MacBook didn't answer in time."
- Opening a Mac result opens the chat through the link.

**Where away names come from.** The cloud keeps no list of a Mac's agents (W1). The browser keeps, in its own storage on the person's device, the names and ids of the agents it last read from each home and when it read them, under these rules:

- They are kept for each account, never shared between two accounts on one browser.
- They are cleared at sign-out on that device, and, after a session ended elsewhere or expired, on the next open, before anything is drawn.
- They are never stored in public-computer mode (`services/core/hub/public-computer.ts`).
- They are shown only as away, never as available, and each shows when it was last read ("Seen 3 days ago"), so an old name is not taken as current.

A browser that never saw a Mac on shows its group as away with no names: "Open this page while Maya's MacBook is on to see its agents." The Mac's own store is cleared on unlink and when the list switch is turned off.

### 5.4 The cloud home's wake

A cloud home that holds an agent with a schedule cannot simply sleep (OneHome:71). R-Q7, step Y13:

- **What it reports.** Before it sleeps, and whenever its due times change, the cloud home works out the earliest next due time among the schedules (`services/tasks/`) and beats (`services/heartbeats/beat-scheduler.ts`) of the agents that live there, and, once step 9's O3 lands, the durable wakes it holds (`services/runs/wakes/wake-store.ts`). It sends that time with `PUT /v1/hubs/self/next-wake` (`HubNextWakeRequestSchema`, `packages/cloud-api/src/hubs.ts:657`; route at `routes.ts:98`), or `at: null` when nothing is due. The contract already sets the rules: at most one wake every 300 seconds, nothing more than 31 days ahead (`hubs.ts:636-656`).
- **What the report carries.** A time and nothing else: no agent, schedule name or content (§9).
- **What else wakes it.** Its owner opening the web, and a message for an agent that lives there (spec `send-to-an-agent`'s `agent.send`), each through the hosted front door as a request for that home. Before a Mac delivers a notice (§4.4), it asks the hosted service to wake its own account's cloud home, with its own instance key; the hosted side does not read the sleeping home's pins. Nothing else a Mac does wakes it: the Mac reads the cloud list only while the cloud home is already awake (§6). The contract names all three (K2). Waking for a published page is item 19's.

  **Since 2026-11-26 (DOR-5465): a message for an agent wakes a sleeping cloud home only when the hosted front door can check who sent it.** Today that is the signed-in owner alone. Every other caller carries a credential only the home itself can check, and the home is asleep, so the request answers `503` with `Retry-After` and wakes nothing. This keeps the rule that, on a home's own address, an unsigned request never wakes it. The way such a caller will wake a home is a wake pass, a later contract step (DOR-5466): the hosted service mints a pass at the home's request for one named caller, the pass only wakes, and the home still checks the caller's own credential. The hosted side checks only what it issued; it never holds or checks a credential a home issued.

- **Until item 14** the cloud home holds no agent with a schedule for a person with a Mac, so it reports `null`; for a person with no computer it reports the due times of what it holds. The step is useful and testable now, on fixtures.

### 5.5 What happens on upgrade

- **A Mac with no link, or with the link off:** nothing changes (W8). No new delivery channel, no new operation is served, no directory report is sent and the directory is not read.
- **No install starts reporting anything new by itself.** At HEAD no Mac reports to the directory: the reporter and its switch (`cloud.directorySync` in L1a step 5) are not built, and no app code calls `/v1/directory`. So the report is one more addition with its own switch at the Mac, **List this Mac in your account**, off for a link that existed before these steps. While it is on, and only while the link is on too, the Mac sends the report and reads the directory. The report names this computer, whether it is reachable, whether it offers its own page, and the spaces its owner joined from it (name and address). It holds nothing else of the computer.
- **A Mac whose link existed before these steps land:** chats work as before. Every addition (the agent lists both ways, search of the Mac's chats, notices, and the report to the account) is **off** until its owner turns it on at the Mac, and a switch that is absent from the pin reads as off. The Mac shows one notice, in two lines: "Your Mac can share more with the web." and "Choose what in Settings." Settings lists the four by name, and so do the consent line and the changelog fragment (E19).
- **A link made after these steps land:** the consent screen lists each addition by name with its own switch, beside the existing consent line, with the picks of §6.
- **Turning the link off:** the Mac, if it can reach the hosted service, removes **its report** from the directory (`DELETE /v1/directory/instances/self`, `packages/cloud-api/src/routes.ts:122`): the report leaves without unlinking the instance (`packages/cloud-api/src/directory.ts:379-381`). The contract then lists that instance with no report as `unknown` (`directory.ts:54-56`), which is never shown as offline. The web and another Mac show such a computer by its name, as "not linked", with no reachable state. The web shows a Mac it cannot reach while its report stands as away (§4.1).
- **An install that already has a DorkOS in the cloud (a hub):** nothing is moved or deleted, and no pairing is closed. Its record of home or way in (§5.2) is made once, on its first read of the assignment after K4, from what the hosted side says. A cloud home recorded as the home sees no change. A cloud home recorded as a way in shows its settings page as §5.3 says; the rooms, docs and files already in it stay there, listed "In the cloud" (E16).
- **An old cloud DorkOS that a Mac already pairs with.** Rooms that Mac agents already sit in stay where they are and keep their members, shown under "In the cloud". No new pairing of a Mac agent into the cloud's private space is offered: creating a Mac agent no longer offers it, and the cloud home's room settings offer only the agents that live in the cloud. The person sees their existing rooms unchanged, under "In the cloud", and new Mac agents on the Mac (E24).
- **An older hosted side:** when K2's wake is not there, a notice waits in the Mac's outbox until the cloud home is awake for another reason (the owner opening the web, its own next-wake), then goes (L1b's fallback, "the outbox holds them", which stands). No setting is copied anywhere: the account never held one.
- **An older cloud home and a newer Mac, or the reverse:** only the computer sends a hello, with its features (`RelayHelloFrameSchema`, `packages/shared/src/session-relay.ts:578-590`); the cloud home's own list reaches a computer only as step 8's `features` frame (step 8's W1). Each side uses only what both named; the missing part shows the "Update DorkOS" line (§4.6).
- **Old plan rows already in the tracker:** DOR-2949 to DOR-2953, DOR-2960 and DOR-2961 get their new text from §7 before they are built.

## 6. The link, exactly

Every operation the link carries after this spec.

**The chat operations, counted at HEAD.** ADR `261015-042933` rule 4 names four things the link carries: a chat's stream, sending a message, approvals and interrupt. The code carries them as **six request kinds** (`RelayRequestSchema`, `packages/shared/src/session-relay.ts:388-395`): `chats.list` (to find a chat), `session.stream`, `session.send`, `session.interrupt`, and an approval as two, `interaction.challenge` then `interaction.respond`. Step 8's spec says "the five chat operations" (SCC:47, §1.4, :181) because it leaves out `interaction.challenge`, the first half of an approval. Six is right at HEAD; §11.6 amends step 8's count.

Rows 1 to 6 are those six, and do not change (SCC:47). Rows 7 to 10 are this spec's additions. Only the computer sends a hello: each addition the Mac serves is a feature it names there (`SESSION_RELAY_FEATURES`, `packages/shared/src/session-relay.ts:178-186`), and the cloud home's own list reaches the Mac only as step 8's `features` frame (step 8's W1), so an older peer never sees an addition. Each lives in a new file beside `session-relay.ts` (931 lines) and is dispatched from a new module beside `relay-request-server.ts` (622 lines), so neither file grows.

**Every addition is named, consented to and switchable at the Mac (W3).** The pin gains four switches, set only at the Mac by its signed-in owner through the pin store, as the level and the pause are today (`pin-store.ts:211-232`), never through config. **A switch that is absent reads as off.** The pin is at format 2 today (`pin-store.ts:54`). If Y16 lands before step 8's W2, it writes format 3 with the four switches, and W2's fields then make format 4; if after, Y16 writes the format after W2's. **Limits on both sides.** Each side keeps its own; neither relies on the other.

### 7.5 Two homes working together: a new, separate piece of work

What an agent in the cloud may do on the person's Mac and how the person allows it, which connections it can use there, how the app on a Mac reaches (chats with) agents in the cloud, where a room or doc shared by a Mac agent and a cloud agent lives and who serves it while the Mac is off, and how a message between a Mac agent and a cloud agent is carried and trusted (OneHome:72, :77-80). ## 14. Risks

- **A wider link.** Four additions cross from a person's computer to the cloud or back. Each is a feature both sides name, named in the Mac's consent line, behind its own switch at the Mac, capped and recorded by the Mac itself, a row for Security, and covered by a census test (Y14) that fails when a new store or operation appears without a row.
- **Switches nobody turns on.** An existing link gets every addition off, so a person who updates sees no new agents on the web until they choose. The one notice on the Mac says so; the web's line names the switch.
- **Away more often than people expect.** A Mac that sleeps makes its agents away on the web, and a fresh browser shows no names. The words say why and what to do; a person who wants agents that keep working uses a cloud agent (item 14).
- **Notices can lag.** A Mac that is on but cannot reach the cloud holds notices in its outbox; the web says the Mac is away. The seven-day limit can drop a notice nobody saw; the Mac's own inbox still has the item.
- **Files that may not grow.** `packages/shared/src/session-relay.ts` (931 lines), `relay-request-server.ts` (622), `packages/cloud-api/src/hubs.ts` (668) and `routes.ts` (527) are over the limit. Each step that touches one moves a part out first.
- **Old tickets read as live work.** DOR-2949 to DOR-2953, DOR-2960 and DOR-2961 hold the old text. §11.1's banners and the issue updates in §13 must land before anyone picks them up.
- **The hosted side's pace.** Y2, Y6, Y9, C11b, B4 and B5 wait for it. Everything else ships first, so the web gains chats, the list, search and the wake without it.
- **Two Macs.** A person with two computers sees each as a home on the web, but neither Mac lists the other's agents until §7.5's work. "Your devices" names both.

## 15. Open questions, each with a pick

1. **A copy of recent Mac chats in the cloud, so they can be read while the Mac is off.** Pick: no (W1, W2). Other option: an opt-in copy the Mac's owner turns on at the Mac, as its own later decision.
2. **The link carrying more than chats (rooms, docs), so the web needs no page move.** Pick: no; the Mac's own page (R-Q5, §4.3). Other option: room and doc operations on the link, each a new row for Security.
3. **How long the cloud keeps a notice.** Pick: until it is read, and at most seven days. A week covers a person away for a weekend or a short trip; past that the line is stale, and the Mac's own inbox still holds the item, so nothing is lost by dropping it. Other option: 30 days, which keeps more of the Mac's activity in the cloud for little use.
4. **What the Mac's search answer carries.** Pick: the chat's title and the one matching line of a message, nothing from tool output (§6 row 8). Other option: titles only, which makes results hard to tell apart.
5. **Away names on the web.** Pick: the browser keeps the names it last saw, on the person's own device, shown only as away (§4.6). Other option: no names at all for an away Mac, only "Maya's MacBook is away", which fails R-Q4.
6. **A Mac's app chatting with a cloud agent itself.** Pick: not in item 13; the Mac lists cloud agents and opens them on the web (§4.1), and the rest is §7.5's. Other option: relay a cloud agent's chat into the Mac's app now, which is the reverse link that work has to design.
7. **The four switches' starting state.** All four are off for a link that existed before these steps. Pick, for a new link: the consent screen offers the agent lists and the report to the account on, and search and notices off (§6). The list and the report are what linking is for: without them the web cannot show this Mac at all. Search and notices send what nobody asked to see on the web, so the person chooses them. Other option: all four off for a new link too, which leaves a new link showing nothing until a second choice.

Decided by the rulings and no longer open: the web is a window, not a home (§2); two lists, two owners (R-Q1); one inbox view with the notice (R-Q2); search asks each home (R-Q3); names and "away", no history (R-Q4); the Mac's own page beyond chats (R-Q5); two homes working together is later work (§7.5); the cloud home reports its next wake (R-Q7); no move of a home or an agent (R-Q8); settings stay on each home (R-Q10); the link stays, default posting is dropped (R-Q11); the list groups by where an agent lives (R-Q13).
