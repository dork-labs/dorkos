**Words.** A **playbook** is how a team of agents works together: a setting of a space, with words, rules and defaults. An **act of working together** is one thing an agent does that involves another place or another agent: start a piece of work, post in a room, message a chat, make a room. A **piece of work** is something an agent was asked to do that runs over one or more turns in one place (§9). A **place** is where a turn runs: a direct chat, a room, a thread, a work channel or a spin-off chat (§4.4). The **gate** is the one permission decision every DorkOS tool call passes (`services/core/capabilities/permission-enforcement.ts:7-11`). The **turn port**, the **run record**, **admission** and the **outbox** are step 5's (`contributing/architecture-target.md:13-17`). A **turn mark** is a mark a turn carries because it read words from outside the owner's circle (`services/core/turn-power/turn-marks.ts:1-16`). **Held** means DorkOS decides it, the same way on every runtime. **Told** means the agent is asked to do it in words and DorkOS does not decide it.

## The short version

- **One question, answered the same way on every runtime.** When an agent starts a piece of work, where does the work happen, and where does it report? A playbook is DorkOS's answer, set by a person.
- **A playbook is data**, in three parts: words for each kind of place (what every agent is told each turn), rules of three closed kinds (**place**, **report**, **route**), and defaults of two closed kinds (**work channel**, **origin updates**). It has an immutable version: a digest of its content.
- **The first three are DorkOS's own.** **Quick answers**: answer fast, do longer work in the agent's own spin-off chat. This is today's behaviour and today's words, and it is the default. **Everything in rooms**: a piece of work asked for in a room becomes a thread of that room. **A channel for each piece of work**: DorkOS makes a channel, adds who asked and who does the work, and the place it came from hears three updates with a link.
- **Levels.** A space sets one. A room may set its own. An agent may be given an exception for its own turns. The nearest level that set one wins, whole. One line says which playbook, set where, by whom.
- **Held at two places.** The gate learns a fourth outcome, **sent elsewhere**: an act goes to the place the playbook names, passes the whole gate again as the same caller, and the agent is told where it went and why. The turn port stamps every run with the one playbook version it started under, so a change never strands work under way.
- **A playbook never grants.** It can leave an act alone, send it elsewhere, or refuse it with one sentence. It never allows what a permission setting blocks, never raises a level and never adds an ask.
- **Only a person sets a playbook.** An agent that thinks another would fit says so in its own words, as a co-worker does; the in-force line tells it which level set the playbook, so it can say where a person changes it.
- **What DorkOS cannot hold, it says.** A runtime's own helpers (Claude Code's subagents, Codex's agents, OpenCode's task tool, DorkOS's own engine's helpers) follow the words only. Every place a playbook is chosen says so.
- **Stage 1** picks, tells, holds and records a playbook. Its thread placement needs item 17's seat work too (MS2 and MS3), because a placed thread runs in a seat of its own, so Everything in rooms waits longest; A channel for each piece of work does not wait for it. **Stage 2**, after more of item 17, lets a piece of work move from a chat into a thread or a channel and keep its context.

## Goals

- A founder picks how their agents work together in one place, understands it from one line, and can change it for one room or one agent.
- Work placed in a thread never keeps the agent from answering in the room, beyond the agent's own limit on turns at once.
- The same rule gives the same result for a Claude Code, Codex, OpenCode and DorkOS-engine agent, on this computer and on another.
- An agent told "not here" learns where its act went and why, in words it can act on, and does not retry.
- A run started before a change finishes under the playbook it started with.
- With nothing chosen, DorkOS behaves exactly as it does today, word for word.
- Each step ships alone, is 5 points or less, and leaves the app working.

**Stage 1 and stage 2.** Stage 1 is a playbook picked, told, held and recorded: the format, the store, the three playbooks, the capabilities to read and set them, the words from one source, the stamp on each run, the gate's new outcome, and the three rule kinds held on every runtime (§19.1). Stage 1 needs item 17 for one thing: the seat a placed thread works in (§10.4). Stage 2 is work that moves: an agent hands a piece of work from a direct chat or a spin-off chat to a thread or a channel, with a summary and a link, and keeps working on it there (§15). Stage 2 needs item 17, which makes every chat a conversation.

## Non-goals (out of scope)

- **A rule kind that asks first or caps.** No playbook can say "ask before posting" or "at most n posts" (`meta/PRINCIPLES.md:11`). The closed lists in §4 cannot express either.
- **Loop limits between agents.** They stay as they are until DOR-2745 decides (`session/chat-messages/chat-message-service.ts:29-34`).
- **Projects.** No project exists in code (§1.7). A project level is a named later step (§16).
- **Playbooks from marketplace packages, and an editor for custom playbooks** (§16).
- **Hosted and community spaces.** The space store's code stays frozen (`AGENTS.md`, rule 4 of "Where the system is going").
- **Holding what a runtime does with its own helpers** (§14).
- **A workspace for each channel** (§16).
- **Onboarding or DorkBot proposing a playbook.**
- **Changing any permission setting.** No area, preset, level or card changes because a playbook is chosen.

### 1.4 What the gate is given, and what it can answer

- **One decision, three callers.** `registry.invoke`, `authorizeCapability` and the hand-registered tool gate each call `resolveCallPermission` and then `enforceCapabilityTier` (`services/core/capabilities/permission-enforcement.ts:7-11`). `authorizeCapability` serves the marketplace routes only (`routes/marketplace/context.ts`) and gates no act of working together. Step 6's C9b removes the hand-registered tool gate, so one entry point remains for agents' calls.
- **Answers.** `allowed`, `approval_required` or `denied` (`tier-enforcement.ts:416-424`). A denial carries a reason (`:350-357`), whether a person can approve past it, and one plain sentence a model can act on.
- **Inputs.** The action's tier and area, the install's permission settings and the agent's own, read fresh from `.dork/agent.json`, the turn's marks and the chat's Full choice. A call's areas are its own area plus any its input reaches, and the strictest wins (`areasForCall`, `permission-enforcement.ts:295-318`). An action can always ask for some inputs (`alwaysAsksForInput`, `capability-definition.ts:164`; used by `permissions.change`, `permission-enforcement.ts:487`).
- **What it does not decide on.** A request's origin, the requesting session and the context's session id and folder are "a delivery address and never an authorization fact" (`services/core/capabilities/tier-enforcement.ts:555-572`; `services/core/capabilities/registry.ts:185-195`). No space id and no room id reach the gate.
- **The early refusal.** `services/core/capabilities/pre-gate-refusals.ts:1-17` is one registration point that both entry points ask before the decision: `registry.invoke` at `registry.ts:808-818`, skipped for a trusted caller (the person at the app), and the hand-registered tool gate at `services/core/mcp-tool-gate.ts:250-258`. A domain registers a check for its own tool by id (`registerPreGateRefusal`, `:49-51`); a check is given `{ sessionId?, cwd?, agentPath? }` (`PreGateCaller`, `:23-31`) and answers a sentence or nothing; the answer becomes a denial nobody can approve past (`preGateRefusal`, `:78-94`).
- **A turn mark refuses with no card** in one place today: spending on an outsider-marked turn (`registry.ts:855`).

No answer sends an act somewhere else.

```
        │                    │

```

Nothing here runs on a computer away from the space side except the rendering of the words, which arrive as data. Every rule is read on the space side, where every DorkOS tool call is already decided.

## 4. A playbook as data (S-1)

### 4.1 The document

The schema lives in `packages/shared/src/playbooks/playbook-schemas.ts` (new), plain data with no imports from the server, so the client, the CLI and the computer side read it. Every object is strict and every union is closed: an unknown field or an unknown kind is refused.

```ts
/** One playbook. Stored whole; its version is a digest of exactly these bytes, canonicalized. */
export interface PlaybookDocument {
  schema: 1;
  /** A stable id, also the slug: /^[a-z][a-z0-9-]{1,39}$/. */
  id: string;
  /** What a person reads on the card: at most 40 characters. */
  title: string;
  /** The one line under the title: at most 120 characters. */
  summary: string;
  /** Who made it. Stage 1 accepts only 'dorkos'. */
  source: 'dorkos';
  /** What every agent is told, by slot and place (§4.2). */
  words: PlaybookWords;
  /** What DorkOS holds (§4.3): at most 16, in order. */
  rules: PlaybookRule[];
  /** What DorkOS does without being asked (§4.5): at most one of each kind. */
  defaults: PlaybookDefault[];
  /** Generated from `rules` and the runtime table (§14); never typed by hand. */
  toldNotHeld: { held: string[]; told: string[] };
}
```

**The version.** A version reference is `<id>@<digest>`, where `<digest>` is the lowercase hex SHA-256 of the document's canonical JSON (keys sorted, no insignificant spaces, UTF-8). For example `quick-answers@3f9c…` (64 hex characters). It is at most 105 characters, well inside the 8,192 bytes step 8 gives a start request's ids and references. A version never changes: a changed document is a new version. The function that computes it, `playbookVersionRef(doc)`, lives beside the schema, and one test pins the digest of each of DorkOS's three.

### 4.2 Words

```ts
export interface PlaybookWords {
  direct_chat: string; // the chat slot, in every turn that is not in a spin-off chat
  spin_off_chat?: string; // the chat slot in a spin-off chat; absent means direct_chat's
  room: string; // the room slot, in a room turn at the top level of a channel
  thread?: string; // the room slot in a thread placed for a piece of work; absent means room's
  work_channel?: string; // the room slot in a work channel; absent means room's
}
```

- **Two slots, where today's texts sit.** The **chat slot** is the part of `<chat_tools>` that `runtimes/claude-code/messaging/context-builder.ts:188-212` holds today, on Claude Code; on Codex, OpenCode and the DorkOS engine it is a short `<working_together>` block in the context each already gets: Codex through its prompt prefix and OpenCode through `body.system` (`runtimes/shared/agent-context.ts:14-18`), and the DorkOS engine through its own system channel, which already carries the shared blocks (`runtimes/doe/context.ts:6`, `:144`). The **room slot** is the part of `<room_tools>` that `runtimes/shared/room-tools-context.ts:190-202` holds today, on every runtime. Every other line of those blocks (tool documentation, etiquette E29 to E32) stays where it is and is the same under every playbook.
- **Which key fills a slot.** The chat slot gets `spin_off_chat` in a spin-off chat, else `direct_chat`, in every turn of an agent whose chat tools are described (on Claude Code, while Messages is not Blocked, as today: `runtimes/claude-code/messaging/tool-doc-gates.ts:30-32`). The room slot gets `thread` in a turn answering in a thread placed for a piece of work, `work_channel` in a work channel, else `room` (an ordinary thread included), in room turns only. An empty string renders nothing.
- **Tool names.** Words name a tool only as `{tool:<name>}`, for example `{tool:session_start}`. Each runtime's builder renders it with its own prefix, as `${T}` and `${t}` do today. **On Codex, OpenCode and the DorkOS engine, a key that names a tool the runtime is not offered on this turn is left out whole**, and the slot falls back along the same chain (`thread` and `work_channel` to `room`, `spin_off_chat` to `direct_chat`), leaving the slot empty when the last key is left out too. So those runtimes are never told to use a tool they do not have (`context-tool-names.test.ts` holds this today and keeps holding it). **Claude Code's chat slot keeps today's own gate instead** (`runtimes/claude-code/messaging/tool-doc-gates.ts:30-32`: written while Messages is not Blocked), and no key is ever dropped from it, so under the default its text is byte for byte today's in every case, including an agent whose `agents` area is Blocked.
- **Lines for one runtime.** A line may start with `[claude-code] ` or `[others] `. The first is rendered only on Claude Code, the second only on Codex, OpenCode and the DorkOS engine, each without its marker. This exists so the default can keep Claude Code's text, which names Claude Code's own helper tool, byte for byte, while the other runtimes get words that name no runtime's own tool (Q9). No other placeholder or marker exists.
- **The budget.** Each key is at most 2,500 characters after rendering with the longest prefix; a turn pays for at most two keys. The whole document is at most 16 KiB. Every turn pays for the words, so the budget is a check in the schema, not a guideline.
- Words may say anything a person would want every agent told. They are DorkOS's own text in stage 1 (Q1).

### 4.3 Rules: the closed list of kinds

A rule reads only these facts, each from the server's own records (§7.3):

| Fact                                                                      | Values                                                                  | Read from                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The act                                                                   | `start_work`, `post_in_room`, `message_chat`, `make_room` (§4.4)        | The capability being called                                                                                                                                                                                                         |
| The kind of place the calling turn runs in                                | `direct_chat`, `room`, `thread`, `work_channel`, `spin_off_chat` (§9.4) | The run's chat: its room seat, its source entry, the work graph, its starter                                                                                                                                                        |
| The kind of turn                                                          | `person`, `agent`, `beat`, `schedule`, `continuation`, `other` (§9.4)   | The run's origin and `continuesRunId`                                                                                                                                                                                               |
| Whether the act's target is the place the current piece of work came from | `origin` or `elsewhere`                                                 | The act's target (a room or chat id in its input) compared with the work-place record's `came_from_ref`, at room level: a thread's origin is its room. With no record, or a record whose `came_from_ref` is null, it is `elsewhere` |

**Kind 1, place.** Where a new piece of work goes when an agent starts one.

```ts
interface PlaceRule {
  kind: 'place';
  /** The places this rule covers; at least one. */
  from: PlaceKind[];
  /** The turns it covers; absent means every kind. */
  turns?: TurnKind[];
  /** Where the work goes. */
  to: 'own_chat' | 'thread' | 'channel';
  /** What the calling turn is told when its start is sent elsewhere: at most 300 characters. It says what happened
   *  and to end the turn ("It has started there. End this turn."), never to do the work in this turn. Never names a
   *  level: the in-force line appended to it does (§7.5). */
  sentence: string;
}
```

`own_chat` is a spin-off chat, which is what `session_start` makes today. `thread` is a thread of the room the turn runs in: from a turn in an ordinary thread, that thread, which becomes placed work; from a turn in a thread already placed for work, a new sibling thread of the same room, with its own seat; otherwise a new thread whose root is the brief. Every placed thread runs in a seat of its own (§10.4). `channel` is a new channel made for the work (§10.2). A place rule whose `to` cannot apply in a place (`thread` from a direct chat, which has no room) is refused by the schema: `from` may name only places where `to` applies (`thread`: `room`, `thread`, `work_channel`; `own_chat` and `channel`: any).

**Kind 2, report.** Where a piece of work reports when one of its runs ends finished, failed, needing a person or paused at a limit.

```ts
interface ReportRule {
  kind: 'report';
  /** Which pieces of work, by where they run; at least one. */
  for: Array<'spin_off_chat' | 'thread' | 'work_channel'>;
  /** `asking_chat`: DorkOS delivers the run's last message to the chat that asked, as spin-off chats report today.
   *  `work_place`: the report stays in the work's own place; nothing is delivered to the chat that asked. */
  to: 'asking_chat' | 'work_place';
}
```

**Kind 3, route.** An act of a named kind, from a turn in a named kind of place, is sent to another place or refused with one sentence the agent can act on.

```ts
interface RouteRule {
  kind: 'route';
  act: 'post_in_room' | 'message_chat' | 'make_room';
  from: PlaceKind[];
  turns?: TurnKind[];
  /** For `post_in_room` and `message_chat`: only when the target is (or is not) the place the work came from. Absent: any target. */
  target?: 'origin' | 'elsewhere';
  answer: { send: 'work_place' } | { refuse: true };
  /** At most 300 characters. */
  sentence: string;
}
```

`send: 'work_place'` is allowed only for `post_in_room` from `thread` or `work_channel`, the places that belong to a piece of work: the post goes to that thread or channel instead, with the same words. **It keeps its origin and its outside mark exactly**: the entry in the work's place has the same author, the same origin and the same turn marks as the post would have had where it was sent, and a run that reads it there takes that mark as if the post had been made there. Every other route answer is `refuse`. `start_work` has no route rule: the place rule is its rule.

**How rules are read.** For one call, the check reads the rules of the kind that matches the act (place for `start_work`, route for the rest) in order, and the first one whose `from`, `turns` and `target` all match decides. No match means the act is left alone. A place rule whose `to` equals the place the called capability makes (`own_chat` for `session_start`) leaves the act alone. Report rules are read by the turn port (§8.3), never by the gate.

**What no rule can say.** There is no field for a count, a time, a size, a level, a permission area, a preset, an ask, a person to wait for, a word list, a model's judgment or code. A rule cannot allow: "leave alone" is the absence of a match (Q2).

### 4.5 Defaults: the closed list of kinds

```ts
/** How DorkOS makes a channel when a place rule sends work to one. */
interface WorkChannelDefault {
  kind: 'work_channel';
  /** The channel's name: the prefix, then the work's title as a slug, at most 40 characters in all. */
  name: { prefix: string /* /^[a-z][a-z0-9-]{0,11}$/ */ };
  /** Who is added: the one who asked, the agent doing the work, or both. The worker is always added. */
  members: Array<'asker' | 'worker'>;
  /** The worker's response mode in the channel, written at join. Held only while every member is the space's own (below). */
  workerResponseMode: ResponseMode;
  /** Whether the worker is the channel's lead. Held only while every member is the space's own (below). */
  lead: 'worker' | 'none';
}

/** Which updates DorkOS itself writes to the place a piece of work came from, each a one-line notice with a link. */
interface OriginUpdatesDefault {
  kind: 'origin_updates';
  for: Array<'thread' | 'work_channel'>;
  updates: Array<'started' | 'waiting_on_person' | 'shipped'>;
}
```

`ResponseMode` is the existing `ResponseModeSchema` (`packages/shared/src/mesh-schemas.ts:105-111`). No default kind can set a permission, a level, a turn budget, a cascade limit or an engaged window: those stay as they are (§13).

**What the work-channel default sets, and why only there.** A channel DorkOS makes for placed work has its worker as lead, answering every message there (`workerResponseMode: 'always'`, `lead: 'worker'` in the one playbook that has the default). `rooms.create` gives an agent neither: an agent's own room has no lead it chose, and an agent may not set its own response mode. These two are set by DorkOS, on a channel it makes because a person chose that playbook, and on such channels only. A room an agent or a person makes with `rooms.create` gets nothing from any playbook.

**Only while every member is the space's own.** The default holds only while the channel's members are the space's own people and agents. If the channel is bridged to an outside window (a Telegram or Slack chat, an outbound webhook), or gains a member from outside the space or a teammate from a shared space, the worker's response mode drops back to the channel's normal one (`engaged`, as a channel member is seeded, `packages/shared/src/room-schemas.ts:714-722`) and it stops being the lead, so a sender from outside can never drive an agent that answers everything. This is checked twice: when the channel's membership or bridge changes (adding a member, binding a connection), in the same write as the change; and again when a turn is triggered in the channel, where the room trigger reads the members and the bridge before it lets the worker answer as lead. Dropping back is recorded in the audit trail and shown in the channel as a notice; nothing restores the default when the member leaves, and a person may set the worker's mode again.

### 4.6 The told-not-held statement

`toldNotHeld` is generated by one function, `describeHolding(doc)`, beside the schema, by one rule, and a test regenerates it for each of DorkOS's three and compares it with the stored lists.

- **`held`**: one line for each rule and each default, in the document's order, from this table; a line equal to one already listed is dropped.

| Rule or default             | Line                                                                                                            |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| place, `to: 'own_chat'`     | New work starts in its own spin-off chat                                                                        |
| place, `to: 'thread'`       | New work in a room starts in a thread there                                                                     |
| place, `to: 'channel'`      | New work starts in a channel of its own                                                                         |
| report, `to: 'asking_chat'` | Work reports to the chat that asked                                                                             |
| report, `to: 'work_place'`  | Placed work reports in its own place                                                                            |
| route, `send: 'work_place'` | Posts about placed work stay in its place                                                                       |
| route, `refuse`             | Some acts are refused, with a reason                                                                            |
| `work_channel`              | A work channel has who asked and who does it                                                                    |
| `origin_updates`            | The place work came from hears: {the updates, as "started", "waits on a person", "shipped", joined with commas} |

- **`told`**: always exactly two lines, "Helpers inside a chat follow these words only." and "How long a piece of work takes is up to the agent."

The app shows `held` as a list and `told`'s first line wherever a playbook is chosen (§12.1, §12.4). Each line is at most 60 characters.

## 6. Levels: which playbook is in force, and why (S-3)

### 6.1 One resolver

`resolvePlaybook({ agentId, place }) → InForce`, in `services/playbooks/resolve.ts` (new), is the only code that answers which playbook is in force. Admission (§8.1), `playbooks.in_force` (§11.2), the room panel, the agent profile and the page of what an agent is told all call it. It reads the choices table and the work-place records (§11.1, §9.1), and nothing else. A choice names a playbook, never a version: the version in force is that playbook's current version (§11.3).

**For a turn in a piece of work that was started under a playbook** (a placed thread, a work channel, or a spin-off chat): **one rule, no levels.** Its runs are stamped from the work-place record (§9.1): the version the work was started under. No level is consulted: not the agent's exception, not a choice set on a made channel, not the room or the space. A placed thread or channel works under the playbook that placed it, whatever anyone chooses later. A spin-off chat with no record (one started before the step that writes spin-off records) is resolved as an ordinary chat of its agent, below.

**For every other turn**, in order:

1. **The agent's exception**, for the agent's own turns in this space, if one is set.
2. **The room's choice**, if the turn runs in a channel (at its top level or in an ordinary thread) that has one. A direct chat is a two-member room underneath (`rooms/direct-chat/direct-chats.ts:1-28`), but it takes no room choice.
3. **The space's choice**, if one is set.
4. **DorkOS's default**: Quick answers.

| Case                                                                                  | Levels read                                           |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| A room turn, top level or ordinary thread                                             | agent, room, space, default                           |
| A direct chat; a scheduled run; a beat; a chat of the agent's own                     | agent, space, default                                 |
| A placed thread, a work channel, a spin-off chat with a record                        | none: the version on its work-place record            |
| A spin-off chat with no record                                                        | agent, space, default                                 |
| A room in no space (none exists on this computer: every room is in its private space) | agent, room, default                                  |
| A continuation, a resumed or retried run                                              | none: it carries its parent's or its own stamp (§8.1) |

The first level that answers wins, whole: its playbook's words, rules and defaults, and nothing from any other level. Nothing is merged rule by rule (Q8).

## 7. The gate: a fourth outcome, "sent elsewhere" (S-4)

### 7.1 Three answers, and only three

For one call, the playbook check answers exactly one of:

| Answer             | What happens                                                                                                                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Leave alone**    | The call goes on to the gate as if no playbook existed. This is the answer for every call no rule matches, every call from outside a DorkOS turn, and every call by a person                        |
| **Refuse**         | The call is refused before the gate, with the rule's sentence. Reason `playbook_refused`, `approvable: false`: nobody can approve past it, and no card is raised                                    |
| **Send elsewhere** | The call does not run. A new call, to the capability the rule names, in the place the rule names, runs in its stead through the whole gate (§7.4), and the agent is told where its act went and why |

There is no "allow" answer: the check can never let through what the gate would stop (Q2).

### 7.2 Where the check sits

At the one registration point both entry points to the gate already ask before the decision, `services/core/capabilities/pre-gate-refusals.ts`: `registry.invoke` (`registry.ts:808-818`) and, until step 6's C9b removes it, the hand-registered tool gate (`services/core/mcp-tool-gate.ts:250-258`). The registration point gains:

- **A list for each id.** Today a second registration replaces the first (`pre-gate-refusals.ts:40-51`). It becomes an ordered list for each capability id or tool name: every refusal check first, as today, then at most one routing check. A refusal check that answers wins over any routing answer, so the protected-file rule still answers first for `session_start`.
- **A routing check.** `registerPreGateRoute(id, check)`, where `check(input, caller)` answers `null`, `{ refuse: string }` or `{ send: { capabilityId, input }, sentence: string, why: PlaybookWhy }`. Like a refusal check it must not throw; one that cannot decide answers `null`.
- **The run.** `PreGateCaller` gains `runId?: string`, filled only from the verified principal's turn binding (§7.3).
- **Refusals only for a runtime's hook.** `preGateMessage` is also read by a Claude Code hook (`runtimes/claude-code/tool-gate/protected-file-hook.ts:14`, `:53`). It reads refusal checks only, never a routing check, so no playbook rule is ever held in a runtime's hook (ADR `261124-152801`).

`services/playbooks/gate-check.ts` registers one routing check for each act of §4.4. The module `pre-gate-refusals.ts` still imports no domain. Neither the check nor the registration point is in the hand-registered tool gate's file, so C9b's removal of that gate changes nothing here: after C9b the one entry point is `registry.invoke`. The third caller of the decision, `authorizeCapability` (`tier-enforcement.ts:1074`), serves the marketplace routes and gates no act of §4.4, so it gains nothing.

### 7.3 Which run a call belongs to

The gate today is given no space or room and treats the session id as a delivery address (§1.4). The playbook check never uses the session id to find a playbook. It uses the run:

- **Where the run comes from: the verified principal's binding.** Step 6's tools port binds every DorkOS tool call from every runtime to exactly one run: a live run, or an ended run with registered background work (step 6 §5.1, "Which run a call is bound to"). On a Mac the loopback listener's bearer is a server principal bound to one turn binding, which the run record keeps (`turn_runs.turn_binding_id`, `packages/db/src/schema/runs/turn-runs.ts:122`), and Claude Code's glue is built per query, so no run is ever inferred. The registry already reads a verified runtime principal's turn (`principalTurnOf`, `services/core/capabilities/marked-turn-holds.ts:76-84`); the playbook check reads the run from that same verified binding, through the tools port's run rule, and from nothing else (§17.3 adds this to step 6's spec if C10 does not already say it). A plain context field never names the run.
- **The outside `/mcp` server.** A call there is a call from outside a DorkOS turn, and so is not under a playbook, until step 6's C18 gives the local `/mcp` a per-run token; from then a per-run token names its run the same way and its calls are under the run's playbook.
- **What the check reads.** The run by that id, through `services/runs` (`getRunRecord`), and from it `playbook_id`, the stamped version (§8.2), and the facts of §9.4. It reads the version from `playbook_versions` (§11.1).
- **A call from outside a DorkOS turn is not under a playbook**: left alone. That is every call by the person, a program (item 10), a mini app, and an outside caller with no per-run token. Rules govern agents' acts in agents' turns (Q7).
- **A run with no stamp** (a run that started before step PB8 landed) is under no playbook: left alone, which is what Quick answers does too (Q9).
- **A helper's DorkOS calls and background work** are bound to the run that holds them (step 6's background-work conditions), so the same playbook applies to them as to the turn.

The check reads a run only where the tools port names it: from C10 for Codex, OpenCode, the DorkOS engine and `computer-local`, and from C11 for Claude Code. The step that adds the check (PB11) needs both.

### 7.4 The second call

When the check answers "send elsewhere", `registry.invoke` does this, in order:

1. Records the first call in the audit trail with the decision `sent_elsewhere` (§7.6).
2. Calls `registry.invoke(target.capabilityId, target.input, context')`, where `context'` is the first call's server-set context unchanged (the same identity, session, verified principal, run, space and caller; never `trusted`) plus `sentFrom`, the second-call mark: a new value naming the first call's capability, its parsed input and its audit record. **The mark is built the way its neighbours are.** It is minted only by the registry, as an instance of a class its module does not export, so no value that arrived as JSON can be one, as the trusted-caller value is built (`services/core/capabilities/trusted-caller.ts:11-17`). The registry checks it on every call the way it checks a server principal (`registry.ts:798-802`): a `sentFrom` on a context that the registry did not mint for this second call is refused, so neither a door that builds a context, nor a mini app, nor in-process code that sets the field itself can supply one. The registry copies it onto the handler's context, and handlers read it only there; it is never read from the context a door builds, nor from input. **The target's input is rebuilt by one pure function** of the first call's parsed input, the rule and the run's facts as recorded at the first call; the agent supplies nothing new, and the same first call always rebuilds the same target input.
3. The second call passes **the whole gate**: parsing, the early refusals, the member check once item 12 builds it, the preflight, the spend check, the permission decision, cards, confirm-first, the in-session hold and the handler, exactly as if the agent had called it.
4. **The stricter of both acts decides.** In the second call the registry also decides the first act on its own input, with everything the gate reads for that id: its areas (`areasForCall`, `permission-enforcement.ts:303-318`), its marked-turn holds, `alwaysAsksForInput`, confirm-first and its spend preflight. It runs no handler and raises no card of its own for the first act. The outcome is the stricter of the two: refused if either is refused; otherwise one card if either asks (bound to the target's id and its rebuilt input, its subject naming both acts and the playbook's line); otherwise confirm-first if either needs it; otherwise allowed. So a start sent to a channel is decided on `agents` (the first act's area) and `rooms` (making a channel): if either is Blocked for this agent, it is refused, and if either is Ask, the one card appears. The playbook adds no ask of its own (Q2).
5. **The limits of the first act travel with it.** A start sent to a thread or a channel keeps every limit `session_start` holds in its handler (§10.3).
6. **Once.** The routing check answers "leave alone" for any call that carries `sentFrom` (Q4). A second sending elsewhere cannot happen.
7. Returns the second call's result wrapped as `SentElsewhere` (§7.5), or throws its refusal with the `sentElsewhere` member on the decision.

**When the second call needs a yes.** The card is bound to the target's id and its rebuilt input. Over HTTP the `202`'s payload names the first act's id as the act to retry, so a caller retries what it called. The in-session hold (`services/core/capabilities/mcp-projection.ts:299-322`, resuming at `:391-413`) and an HTTP retry both call the registry again with the **first** act's id, its input and the token, as they do for any held call. The registry runs the routing check again on the same stamped run, which rebuilds the identical target input, and passes the token to that second call only. The token is never consulted for any other call, and it covers the first act's decision only inside that second call. If the run's facts changed so the rebuilt input differs, the binding does not match and a fresh card is raised, as for any changed input. A resumed or retried call writes no second sent-elsewhere audit record: the first call's record names the decision, and the second call's own record is written once, when it runs.

## 8. The turn port (S-5)

### 8.1 Admission carries the stamp, or resolves one

`admit` (`services/runs/admission.ts`) gains its playbook step, last, after every check that can make a run wait. For a run that goes, it answers `{ go: true, accountRef?, playbookId }`, where `playbookId` is the version reference of §4.1:

- **When the run already has a stamp** (a paused run resumed, a retried start, a continuation, a run in placed work stamped when it was made), admission returns that stamp unchanged. So the request a computer gets always carries what the run record says.
- **Only when the stamp is empty** does it call `resolvePlaybook` (§6.1) with the run's agent and place. Resolution cannot fail: with no choice, the default answers. Because the step is last, a run that waited with no stamp is resolved when it finally goes: a change of playbook made while it waited applies to it.

The `start_turn` handler puts `playbookId` on the computer face's request beside `accountRef` (`services/runs/effects/handlers/start-turn.ts:188-208`) and, when the stamp was empty, stamps the run in the same write that moves it to `starting` (§8.2).

### 8.2 The stamp on the run record

- **What the string is.** `turn_runs.playbook_id` holds the version reference `<id>@<digest>` (§4.1), the same string `TurnStartRequest.playbookId` carries. It names one immutable row of `playbook_versions`, so a run's rules and words can always be read back, however the choice changes later. Neither the run table nor the port's request changes shape: the column and the field exist (`turn-runs.ts:125-126`; `turn-port.ts:619-626`); only their doc comments change, in step PB8.
- **Written once.** One function, `stampPlaybook(runId, version)`, writes it only where `playbook_id` is null. Nothing ever rewrites or clears it. Step 5's pause transitions (14 and 15) clear a list of fields and keep the rest; `playbook_id` is not on that list, so a resumed run keeps its stamp.
- **When.** Before the turn's words are built, always:
  - a run that goes through admission is stamped in the write that moves it to `starting`;
  - a run the dispatcher starts on a Mac before its caller has moved onto the port (chat messages and spin-off chats until T6, wakes until T7, beats until T8, room turns until T10, tasks until T12) is stamped at its launch-begin fact (step 5's transition 4), before the runtime is asked and before any block is built. When each caller moves onto the port, its stamp moves to admission with it;
  - **a continuation** (a run with `continuesRunId`, and a run step 5's recovery starts in its place) is stamped with its parent's version when it is created, never resolved fresh;
  - **a run in a piece of work** (the first run of a placed thread or channel, made by the placement; any later run there; a spin-off chat's runs) is stamped from its work-place record (§9.1), when the run is made, with no level consulted (§6.1). A spin-off chat with no record is stamped as an ordinary chat of its agent.
- **Why it matters.** The gate (§7.3) and the report path (§8.3) read the stamp, never the choices. So a run started before a change finishes under the old playbook, words, rules and all (Q5). A spin-off chat or a piece of work started by that run works under the version on its work-place record (§6.1).

`services/runs/run-store.ts` is the only reader and writer of `turn_runs` and is over 500 lines, so PB8 moves one part of it out before adding the stamp's write (§21).

### 8.3 Where a run's result goes: the report rule and the updates

Both are read by the turn port from the run's stamped version, never from the choices, and carried out as outbox effects written in the same write as the fact they follow (step 5 §6), so a restart loses neither.

- **The report rule.** When a run ends finished, failed, needing a person or paused at a limit, the report path (today `session/chat-messages/chat-report-back.ts` and its durable outbox, which step 5's T9 moves onto the worker) finds the run's piece of work (§9) and the first report rule whose `for` names the work's place kind. `asking_chat` delivers the run's last message to the chat that asked, exactly as a spin-off chat reports today. `work_place` delivers nothing: the report stays in the work's own place. No matching rule: today's behaviour (a spin-off chat reports; a room turn does not).
- **Origin updates.** For a piece of work whose place kind is named in an `origin_updates` default, DorkOS writes a one-line notice with a link into the place the work came from (§9.2), for each update the default lists:
  - `started`: written by the placement capability in the same write that makes the place (§10).
  - `waiting_on_person`: written with the run's `waiting_on_person` fact, once per run (`packages/shared/src/turn-port.ts:784`).
  - `shipped`: written by `work.finish` (§10.5).
    The notice is a room entry of kind `notice` by DorkOS itself, in the room (or thread) the work came from; in a Direct chat it is an entry of that chat's two-member room, as `relay_notify_user` already posts there. It is not a turn of the agent and starts no turn. When the work's record has no room to come from (`came_from_ref` null, §9.1), no notice is written; the same three updates reach the chat that asked as reports, through the report path, when the default lists them.

### 8.4 The words in a start, and what reaches another computer

- **On a Mac.** The builders of the two slots (§4.2) read the words for the turn's place from the run's stamped version, through the turn's prompt facts (step 6's `promptFacts(runId)`, §5.3 of that spec). Until step 6's C18 builds that port, the space side hands the builders the words the way it hands them room conventions today. The builders render `{tool:<name>}` with their own prefix.
- **On another computer.** The start request already carries `playbookId` (step 8 §5.2, inside the 8,192 bytes for ids and references) and the run's prompt facts (inside 49,152 bytes). The prompt facts gain one optional field, `playbookWords: { chat?: { key, text }, room?: { key, text } }`, the unrendered words for this turn's two slots, at most 5,000 characters together. The computer renders them with its runtime's prefix. Nothing else about the contract changes.
- **What never reaches a computer.** The rules, the defaults, the choices and who set them. The rules copy (step 8's gate note §3) gains no field. Every act a rule reads is a DorkOS tool call, and every DorkOS tool call is decided on the space side (`design-permission-gate.md` §2), so nothing about a playbook is decided on a computer away from the space side. The only thing a computer does with a playbook is render its words.

## 9. A piece of work (S-6)

### 9.1 No second object

There is no "work item" object, and this spec makes none. A piece of work is its place, who asked, and one record in the playbooks store:

- **Its place**: the spin-off chat, the thread (its root entry) or the work channel (its room) where its runs happen. A `dork:chat:`, `dork:entry:` or `dork:room:` reference (`packages/shared/src/dork-ref.ts:33-44`).
- **Who asked**: read from the record, which takes it when it is written from the placing run's `askedByRef` (`turn-runs.ts:88-89`, set by step 5's T6); until T6, for a room turn, the author of its source entry, and for a direct chat, the person.
- **Its work-place record**: one row of `playbook_work_places` in the playbooks store (§11.1).

**The work-place record** holds: the place's reference (unique), its kind, where the work came from, who asked, the asking chat, the playbook version the work was started under, the run that placed it, the title, when, and the done state (the run that marked it done, when, and its one-line summary). A run is named by the kind the run record itself uses, `dork:turn:<id>` (`runReference`, `packages/shared/src/turn-port.ts:36-37`, `:372-380`); `dork:run:` names a scheduled task's run and is never used here. The record is written in the same transaction as the place: by the placement capability for a thread or a channel (§10), and, for a spin-off chat, by the start path in the same transaction as the insert that records who started the chat (`session_started_by`, `SessionStartedByStore.insert`, `services/session/origin/session-started-by-store.ts:164-165`; step PB8). **The gate decides from this record only**: the work's kind, where it came from, who asked, its version, whether `work.finish` is offered and "done once" are all read from it, never from the work graph's best-effort edges. A spin-off chat carried to another account keeps its version through this row only.

**Where the work came from** is the asking chat's place, read at room level when the record is written: the room whose seat the asking chat is, or the asking chat's own two-member room for a Direct chat. A thread's origin is its room.

**Work that came from no room.** A spin-off chat started from another spin-off chat, from a scheduled run, from a beat, or from a chat a person started outside any room has no room to come from: its record's `came_from_ref` is null. Then a post's target is always `elsewhere`, and no origin-update notice is sent. Under A channel for each piece of work, a start from such a plain chat, answering a person or an agent, still gets a channel, with the worker and whoever asked; with no room to tell, the chat that asked hears the three updates as reports, through the report path, in place of notices (§8.3).

**The work graph gets a mirror, nothing more.** The work graph (ADR `261124-131941`) records a chat that another chat started as `started` (`services/work-graph/index.ts:20-31`); nothing playbook-specific rides that edge or its write hook, which carries ids only. Work placed in a thread or a channel is a new fact that no relation says, and `started` may not be widened ("New relations are added, never reinterpreted", `packages/db/src/schema/work-graph/work-links.ts:21`). So this spec adds one relation kind:

- **`placed_work`**: from the chat that called the start (`dork:chat:<asking chat>`) to the place the work was put (`dork:entry:<thread root>` or `dork:room:<channel>`). It is written after the placement commits, as a best-effort mirror, by the work graph's own rule that recording an edge never decides the action (`services/work-graph/index.ts:6-8`). Its fixed ends join the store's table of relation kinds (`services/work-graph/work-link-store.ts:58-68`): from a `chat`, to an `entry` or a `room`; the store refuses any other ends.
- `placed_work` edges stay off every agent-facing read of the work graph until a view needs them. Where a reader does return a room or an entry end, room membership decides who may see it.
- The work graph's lineage walks `started` only (`readChatLineage`, `services/work-graph/index.ts:152`), so a thread or channel that work was placed in does not show in the chat tree. "The chat tree follows placed work" is a later step for the chat-tree work (DOR-4971), not built here (§16).

**The place of a run** (§9.4) is read from the work-place record: its `kind` says spin-off chat, thread or work channel. Only for a spin-off chat with no record (one made before step PB8 writes records) does the playbooks service ask the work graph, through the one function it exports beside its lineage read, `placeOf(chatRef)`, whether the chat was started by another chat. It never reads the work graph's table directly. The composition root hands `placeOf` to the playbooks service, so no new pair is added to the domain-pair check.

A work channel is a room with a work-place record of kind `work_channel`; a thread placed for work is a root entry with one of kind `thread`.

**The title** of a piece of work is the `title` its start was given (the brief's first line when it has none; `session_start` already takes a `title` of at most 80 characters, `runtimes/claude-code/mcp-tools/session-start/input.ts:23-32`). A thread root the placement made, and a work channel's first entry, begin with it; an ordinary thread that became placed work keeps its own root. Its state is its runs' states and the record's done state. Nothing here reads a transcript.

### 9.2 Starting one is one act

"Start a piece of work" is one act, carried by one capability every runtime has: `session_start`, as step 6's C9b makes it a capability and C12c shows it to Codex, OpenCode and the DorkOS engine. Under Quick answers it is exactly what `session_start` does today: a spin-off chat. Under the other two, the place rule sends it to one of two placement capabilities (§10), which no agent calls directly. Its existing `title` names the place. The agent never names the place.

A thread's origin is its room. It is `elsewhere` when the run belongs to no piece of work with a record, when `came_from_ref` is null, or when the act goes to no room.

## 10. The places work is sent to, and marking work done (S-7)

The two placement capabilities exist so that an act sent elsewhere is a real capability call that passes the whole gate (§7.4). Neither has an MCP, HTTP or CLI surface. **They answer only the gate's second call.** `POST /api/capabilities/:id/invoke` reaches every capability by id, and the command line's `dorkos call` uses it (`routes/capabilities-invoke.ts:5-10`), so each handler refuses any call whose handler context does not carry the second-call mark (§7.4), with "This is only reached through a playbook." The mark is new: minted only by the registry, checked as a server principal and the trusted-caller value are, copied onto the handler's context, and never read from the context a door builds or from input. Both live in `services/playbooks/placement/` (new) and use the rooms store and the turn port's space face; neither imports a runtime.

**Their inputs carry exactly what a placed start may carry**: `{ prompt, title?, reason? }`, the three fields of `session_start` a thread or channel can take. Where the work goes (the room, the thread, the asker) comes from the calling run's records, never from input. The routing check is what refuses a start that names any other field, by name, before any second call (§10.3).

### 10.1 `work.start_in_thread`

| Field          | Value                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `id`, `title`  | `work.start_in_thread`, "Start a piece of work in a thread"                                        |
| `tier`, `area` | `act`, `agents` (it starts work, as `session_start` does); the first act is decided with it (§7.4) |
| Surfaces       | none; answers only a second call                                                                   |
| Input          | `{ prompt, title?, reason? }`                                                                      |
| Output         | `{ place, placeName, link, runId }`                                                                |

What it does, in this order, with the writes in one transaction:

1. Runs the start checks of §10.3. A refusal there ends the call with its sentence; nothing is written.
2. Finds the room from the calling run's seat. From the top level, or from a thread already placed for work, it writes the brief (`prompt`, headed by `title`) as a new top-level entry in the room, by the calling agent, through the rooms store's own entry write (so the broadcast, search and outside windows run after the commit as for any post); that entry is the thread's root. From an ordinary thread, the thread exists and nothing is posted; its root stays as it was.
3. Writes the work-place record (§9.1) with the calling run's version.
4. Gives the calling agent a seat of its own in that thread: a new session, seated for the thread (§10.4).
5. Starts that seat's first run explicitly, through the turn port's space face, with the brief as its words, origin `room`, the turn kind of the placing run (§9.4), `askedByRef` the first run's asker, and the record's version as its stamp. The run is started by the placement, not from the root entry: item 17's rule that no run starts for an entry the seat's own agent wrote (`specs/one-message-system/02-specification.md` §4.4, item 1) is untouched. The run takes a claim under the agent's ceiling like any room turn (§10.4).

After the commit, the `placed_work` mirror edge is written (§9.1). This needs room turns on the port (step 5's T10) and a seat for each placed thread (§10.4).

### 10.2 `work.start_in_channel`

| Field          | Value                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `id`, `title`  | `work.start_in_channel`, "Start a piece of work in its own channel"                                |
| `tier`, `area` | `act`, `rooms` (it makes a room); the first act, with its `agents` area, is decided with it (§7.4) |
| Surfaces       | none; answers only a second call                                                                   |
| Input          | `{ prompt, title?, reason? }`                                                                      |
| Output         | `{ place, placeName, link, runId }`                                                                |

What it does, with the writes in one transaction:

1. Runs the start checks of §10.3. A refusal there ends the call with its sentence; nothing is written.
2. Makes a channel through the rooms store's create, as `rooms.create` does: its name is the work-channel default's prefix and the title as a slug, cut to 40 characters, with `-2`, `-3` and so on when the name is taken. Its members are the worker (the calling agent, always) and, when the default lists `asker`, whoever asked (from the calling run's `askedByRef`): a person or an agent on this computer. The worker joins with the default's response mode and is the lead when the default says `worker`, which DorkOS sets only on a channel it makes for placed work (§4.5). A place rule with `to: 'channel'` in a playbook with no `work_channel` default is refused by the schema.
3. Writes the brief, headed by its title, as the channel's first entry, by the worker.
4. Writes the work-place record with the calling run's version.
5. Writes the `started` update into the place it came from, when the playbook's `origin_updates` lists it: "Started: {title}, in #{channel}." with a link (an outbox effect, §8.3).
6. Starts the worker's seat run in the new channel explicitly through the space face, with the brief as its words (not from the brief entry, as §10.1 says), the placing run's turn kind, and the record's version as its stamp.

After the commit, the `placed_work` mirror edge is written. Making the channel is decided by the gate on `rooms` and `agents` for this agent (§7.4): a playbook cannot make a channel for an agent whose Rooms area is Blocked. It needs step 5's T10, as §10.1 does.

### 10.3 The limits a start keeps when it is sent elsewhere

`session_start` holds its limits in its handler, not in the gate (`runtimes/claude-code/mcp-tools/session-tools.ts:10-45`). A start sent to a thread or a channel keeps every one of them:

- **The checks run in one shared function.** The step that adds the start checks moves the handler's checks into one function, `startChecks`, in a space-side module, which `session_start` and both placement capabilities call: only as itself (an `agentPath` must be the caller's own home, and a folder inside another agent's home is refused); never above the calling chat's level; no account the owner has not opened to agents (`checkAccountLaunch`); every launch counts against `runtimes.maxAgentChats`; and an extension's start limits, through the chain recorded in `session_started_by`.
- **The level and marks ride along, for the seat's whole session.** The placed seat's session takes the first run's level and marks as its ceiling, as the room hand-off already makes the drafting chat's marks ride the seat's turn (`rooms/handoff/room-handoff.ts:44`), and keeps that ceiling for every later run in it, as a spin-off chat keeps its mode. A marked turn's start is placed as a marked session; what is held for the mark stays held.
- **What a placed thread or channel cannot carry is refused by the routing check, never dropped.** A placed start carries only `prompt`, `title` and `reason`. A start that names any other field of `session_start`'s input (`runtimes/claude-code/mcp-tools/session-start/input.ts:21-114`: `cwd`, `account`, `runtime`, `model`, `effort`, `permissionMode`, `seedContext`, `agentPath`, `reportBack`, `claim`, `startAnyway`) is refused by the routing check before any second call, with one sentence naming the field: "This playbook puts new work in a {thread or channel}, which can't take `{field}`. Start it without `{field}`, or ask a person." It is never placed without it.

### 10.4 A seat for each placed thread

Today one seat for each agent in each room holds, and another chat's post goes to that seat (`rooms/handoff/room-handoff.ts:24-45`). Rules that depend on it: the hand-off itself, who answers when woken, the agent's read cursor in the room, and the claim before a turn (`rooms/room-trigger.ts:19-30`). Thread work must never block the room seat, so stage 1 changes it to **one seat for each agent in each conversation, where a thread placed for a piece of work counts as a conversation of its own for seating** (step PB16, which needs item 17's MS3):

- **Where the seat lives.** The seat table (`room_sessions`, `packages/db/src/schema/rooms.ts:1024`) gains a nullable `thread_root_entry_id`: null is the room seat, as today; a value is a thread seat.
- **Its own read cursor.** Item 17 keeps a seat's cursor on the member row, one for each agent in a room (`room_members.last_read_seq`, its §4.2). A thread seat keeps its own cursor on its seat row (a `last_read_seq` column on the thread seat's row of `room_sessions`), covering only that thread. It starts at the thread's root entry's `seq`, and the thread seat's window never reaches below that root (its floor). The member row's cursor stays the room seat's, and skips entries of a thread that has its own seat.
- **Who answers.** A message in a placed thread is answered by the thread's seat, never the room seat. A post by the agent's room seat into a placed thread goes to the thread seat as a hand-off, by the same rule that sends another chat's post to the seat; a post by the thread seat at the room's top level goes to the room seat.
- **One claim for each seat, one ceiling for the agent.** Today a claim is keyed by room and agent (`agentKey`, `rooms/room-claims.ts:401-403`), and a claim under that key answers "busy here" (`claimBusyWith`, `:656-657`), so thread work under today's key would hold the room seat. The claim key becomes one for each seat: (room, thread root, agent), with no thread root for the room seat. The per-agent ceiling still counts every claim of the agent, whatever its seat (`:649-669`): `rooms.maxConcurrentTurnsPerAgent`, default 3, bounds 1 to 8 (`packages/shared/src/config-schema/rooms.ts:72-82`). So the agent answers in the room when it has a free slot, never "at once" by promise. A thread run that finds no slot waits `agent_busy` (step 5 §3.5).
- **What the room shows.** While the thread's run holds its claim, the room's presence shows the agent as working, in that thread, through the presence the claim already raises (`rooms/room-claims.ts:12`).
- A channel made for work is its own conversation already, so nothing changes there.

Which steps must be in before Everything in rooms can be chosen is §11.4's one statement.

### 11.3 The move, and DorkOS's own versions

- **The move ticket.** Choices and work-place records are space data (ADR `261122-173853`). They live in this computer's store until the private space becomes a tenant on the space store (roadmap item 16). PB4 files the ticket for that move under item 16 (New), naming the three tables; the space level's `target_id` becomes the space's id then. The space store's code is not touched here (Q10).
- **A new DorkOS version of its own playbook.** A choice names a playbook, so when an update ships a changed text of one of the three, the choice follows it: at boot the new version is written, and the next run resolved under that choice is stamped with it. Runs already stamped, and placed work, keep theirs (Q5). When the new version's `rules_digest` differs from the choice's `seen_rules_digest`, the in-force line gains its second line, "Its rules changed in this DorkOS update.", until a person opens the playbook at that level (§6.2), and the release that ships it carries a changelog line saying what the rules now hold. A change of words alone changes no `rules_digest`, so it needs neither.

### 11.4 Who sets a playbook, and which can be chosen

- **A person.** `playbooks.set_choice` and `playbooks.clear_choice` are person-only (`audience: 'person'`): `registry.invoke` refuses any other caller as `PERSON_ONLY`, a `403 person_only` over HTTP, before the gate runs (`contributing/api-reference.md:53`). They have no MCP tool and no command-line verb, so no agent, program or outside caller can set a playbook.
- **An agent that would like another playbook** says so in its own words, as a co-worker does. `playbooks_in_force` tells it which level set the playbook and who set it, so it can say where a person changes it. A suggestion a person accepts in one press is a later step (§16).
- **Which person.** The member check asks item 12's question, "may this member do this in this space", for `settings` and, for a room, `rooms` (what changing that room's settings needs, `rooms.update`), and for an agent's exception, `agents`. On this computer only the Owner level is reached (item 12 §4.4), so today the Owner sets every level. Until item 12's gate step lands, the person-only bar answers the same.
- **Which playbooks can be chosen: one statement, used everywhere.** `set_choice` refuses a playbook whose rules or defaults DorkOS does not hold yet, with the problem `playbook_not_available` ("This playbook is not available yet."), and `playbooks.list` marks it so:
  - **Quick answers**: from PB6. Its rules leave every act alone.
  - **A channel for each piece of work**: once PB13 (the channel, which needs step 5's T10 and step 6's C12c), PB14 (where results go, which needs step 5's T9) and PB15 (the route rule) are in. It does not wait for thread seats: a work channel is a room where the worker has its ordinary seat.
  - **Everything in rooms**: once PB14, PB16 (a seat for each placed thread, which needs item 17's MS2 and MS3) and PB17 (work in a thread) are in. It is the one that waits longest, for MS3.

  So the app never offers a playbook whose rules would be only words (Q3).

### 11.5 What agents may read

An agent reads which playbook it is under, and why, with `playbooks_in_force`: with no input, its own run's stamp and line; with a room or an agent, that place's answer. It reads the playbooks with `playbooks_list` and `playbooks_get`. These are observe-tier with no area, like the room reads. They reveal nothing private: the answer is the name of a playbook, its level and the name of the person who set it, the same line every member of the space sees on the room panel, and the playbooks themselves are DorkOS's own published text.

A choice is one resource for each level and target. `{level}` is an enum path segment (`space`, `room`, `agent`); the space level's `{targetId}` is `space`. `/api/playbooks`, `/api/playbook-in-force` and `/api/playbook-choices` are new groups, so no playbook id can collide with a fixed segment. No path segment is a command word. **Both lists page** as every list does: `cursor` and `limit` in, `nextCursor` out.

**Shapes**, in `packages/shared/src/playbooks/` (new), so the client and the CLI read them:

- `playbooks.list`: input `{ cursor?, limit? }`; answer `{ playbooks: Array<{ id, title, summary, version, toldNotHeld, available }>, nextCursor? }`.
- `playbooks.get`: input `{ playbookId, version? }`; answer the `PlaybookDocument` and its `version`.
- `playbooks.in_force`: over HTTP there is no calling run, so the input needs `roomId`, `agentId` or both; neither is `400 invalid_request`. `roomId` alone answers a room turn's resolution with no agent exception; `agentId` alone answers that agent's turns outside any room; both answer that agent's turns in that room (§6.1). The in-session tool with no input reads the calling run's stamp. Answer `InForce` (§6.1).
- `playbooks.list_choices`: input `{ cursor?, limit? }`; answer `{ choices: Array<{ level, targetId, playbookId, setBy, setAt }>, nextCursor? }`, in the order level, then target id.
- `playbooks.set_choice`: path `{ level, targetId }`, body `{ playbookId }`; answer `{ choice: { level, targetId, playbookId, setBy, setAt }, inForce: InForce }`. Setting the same playbook again changes nothing and answers the same.
- `playbooks.clear_choice`: path `{ level, targetId }`; answer `204`, also when no choice was set.
- **The answer of an act sent elsewhere.** The capabilities a rule can send elsewhere are named in code (`SENT_ELSEWHERE_ACTS`: the capability C9b makes of `session_start`, and `rooms.post`) and pinned by a test, so a new one is a reviewed change. Each declares its `200` in the API document as one of its own output or the `SentElsewhere` shape (§7.5), told apart by the discriminant `outcome: 'sent_elsewhere'`, with `Location` set to the place it went. An asked or refused second call answers today's `202` or `403`; their bodies carry an optional `sentElsewhere` member, which is one optional extension of the shared approval and problem schemas, documented once, not per route. The `202` names the first act's id as the act to retry. Only a call bound to an agent's run can get any of these.

| `invalid_request`        | 400    | Input fails its checks, including `in_force` with neither `roomId` nor `agentId`, or a `{level}` outside the enum |     |
| `person_only`            | 403    | `set_choice` or `clear_choice` from any caller that is not a person                                               |     |
| `forbidden`              | 403    | The member check refuses (an area Blocked for that member)                                                        |     |

## 15. Stage 2: work that moves (S-10)

Stage 2 waits for item 17, which makes every chat a conversation with a log, seats and read cursors (`specs/one-message-system/02-specification.md` §4). It is designed here only as far as its steps need; each step's pull request settles its details within these rules.

### 15.1 The act

`work.move` (MCP `work_move`, in-session; tier `act`; area `agents`, and `rooms` through `areasForInput` when the target is a new channel) moves the piece of work the calling turn is in, from a spin-off chat or a direct chat, to a thread of a room the agent is a member of, or to a new channel made as §10.2 makes one. Input: `{ to: { thread: { roomId } } | { channel: true }, title, summary }`, where `summary` is 1 to 2,000 characters the agent writes. A person may move work from the chat's menu; that is a person's act and no playbook reads it (Q7). `work_move` joins the act list (§4.4) as `work_move`, so a later playbook's route rule may refuse it; none of the first three does.

### 15.2 What a move does

1. **A seat in the target.** The work's session (the chat's own runtime session) becomes the agent's seat in the target: a thread placed for the work (a new root entry, as §10.1 makes one) or a new channel. A work-place record for the target is written in the move's transaction, as for any placed work, and the `placed_work` mirror edge after it. The agent keeps its context because its session is the same; nobody else reads that session (item 17 §4.5 decides who may read the turn behind an entry, unchanged).
2. **A hand-over entry in the target**, by the agent: "Moved here from {source}." then the agent's `summary`, then a link to the source. The link opens the source only for a reader its existing rule allows (`canReadSession`, item 17 §4.5). **No transcript is copied** (Q12): the entry holds the summary and a reference, and no code path in the move reads a transcript. **The summary carries the marks of the turn that wrote it**: the hand-over entry records that turn's marks (`turn_marks`, as any entry an agent writes in a turn), and the target's run takes them on reading it, so a summary written after reading words from outside stays marked in its new place.
3. **A line where it was**: a notice in the source conversation, "Moved to {target}.", with a link.
4. **The run chain continues.** Runs are kept by chat, and the chat is the same session, so the next run of the work is the session's next run, now answering in the target. Its `askedByRef` stays the work's asker. A `moved_to` work-graph edge, from the source chat (`dork:chat:`) to the target place (`dork:entry:` or `dork:room:`), with those fixed ends, records the move (a new relation, as `placed_work` is).
5. **A direct chat stays a direct chat.** Moving work out of a person's Direct chat moves the session; the Direct chat's seat gets a new session the next time it is needed, as it does today on first use (`rooms/direct-chat/direct-chats.ts:15-18`), and item 17's recap rule gives that session a bounded recap from the log (item 17 §4.4, item 9). The person's Direct chat keeps its whole log.
6. **The playbook.** The work's next run is stamped from the target's work-place record, which holds the version of the run that moved it, as for any placed work (§6.1).

### 15.3 The seat

A move uses the seat rule stage 1 already built (§10.4): one seat for each agent in each conversation, a placed thread counting as one. A moved session becomes the agent's seat in a thread placed for the work or in a new channel, never a second seat in a room's top level, so the room seat and its hand-off are unchanged.

### 15.4 A channel tied to a workspace

Named later (§16). What is reserved today: a room may own a repository (`owned`); binding a room to a checkout that already exists (`linked`) is reserved and refused by name (`packages/shared/src/room-repo.ts:36-43`). A work channel made by a place rule takes neither in this spec.

## 21. Risks

- **Steps that wait on other items.** The rules hold only once step 6's C9b, C10, C11 and C12c, step 5's T9, T10 and T15, and item 17's MS2 and MS3 land. Until then the format, the store, the words, the stamp and the reads land, and Quick answers is the only playbook that can be chosen (§11.4), so nothing is claimed early. Everything in rooms waits longest, for MS3, because its threads need seats of their own (§10.4); A channel for each piece of work does not wait for it.
- **Files that may not grow.** The gate's, the run store's, the builders' and the room schema's files are over 500 lines; §19's last table says how each step keeps the ratchet.
- **More seats, one ceiling.** A placed thread has a seat, and so a session, of its own, and each counts against `runtimes.maxAgentChats` while it runs, as a spin-off chat does today (§10.3). All of an agent's seats share its one `rooms.maxConcurrentTurnsPerAgent` ceiling, so an agent at its ceiling answers in the room when a slot frees; the limit is today's.
- **Many channels under A channel for each piece of work.** Each start makes one. The name says it is work (`work-`), and archiving a room is today's act. A cleanup of finished work channels is not part of this spec.
- **Words that drift from rules.** A playbook's words could say what its rules do not hold. The `told` list is fixed and the `held` list is generated from the rules (§4.6), so the app never claims a rule the data lacks; PB2's test reads each of the three's words against its rules.
- **A card a person did not expect.** With an area at Ask, a start sent to a channel raises one card, naming both acts and the playbook's line, so the person sees why (§7.4).
- **A second record of placed work.** The playbooks store's record is the truth; the work graph's `placed_work` edge is a mirror that can miss a write, by the work graph's own rule. Nothing reads the mirror to decide anything (§9.1).

## 22. Open questions, each with a pick

1. **Which level wins between a room's choice and an agent's exception.** Pick: the agent's exception, so an agent kept on Quick answers stays on it in every room (§6.1). Other option: the room, so every agent in a room works the same way.
2. **Whether a person's instruction inside a turn ("spin this off anyway") overrides a rule.** Pick: no. The result's in-force line names the level that set the playbook, and the person changes it there. Other option: a person's words in the turn's source lift the rule for that turn, which would make a rule depend on reading words.
3. **How an agent asks for a different playbook.** Pick: not in this spec. An agent says so in its own words, and the in-force read tells it which level set the playbook so it can say where a person changes it; a suggestion a person accepts in one press is a later step, which waits so it never becomes a way to nag (§16). Other option: a suggestion capability now.
4. **Which playbook is the default.** Pick: Quick answers, because it is today's behaviour and today's words (Q9). Other option: Everything in rooms, so work is visible by default.
5. **A playbook's version when DorkOS ships a new text of its own playbook.** Pick: a choice names the playbook, so it follows the new version; running runs keep theirs; a change of rules is shown on the in-force line until a person has seen it, and the release notes carry a line (§11.3). Other option: a choice stays on its version until a person moves it.
6. **Everything in rooms, in a direct chat.** Pick: a spin-off chat, as Quick answers, because a direct chat has no room and its one-to-one view shows no threads (§5.2). Other option: a thread of the Direct chat's own two-member room.
7. **Where "shipped" comes from.** Pick: `work.finish`, the agent's own act, because DorkOS cannot judge when work ships (§10.5). Other option: no `shipped` update, and the room hears it only if the agent posts it.

Decided by ADR `261124-152801` and no longer open: a playbook has three parts and is space data; it is held at the gate and the turn port, never a runtime's hooks; a run keeps the playbook it started under; what DorkOS cannot hold, it says; the first three are DorkOS's own. Decided in this spec: the closed lists of rule and default kinds (§4); the nearest level wins, whole (§6); a fourth gate outcome at the shared early registration point (§7); the stamp is a version reference (§8.2); no second object for a piece of work (§9); stage 1's playbooks ship in the app (§5).
