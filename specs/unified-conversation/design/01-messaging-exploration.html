1 · One component tree, three surfaces

What I found: DMs are already rooms (same route, same widget, kind:'dm' only changes the name). So it is really two surfaces to unify: session chat and room. Today they share the composer primitives (Composer.*), the row layout tokens (messageItem tailwind-variants, anchor: corner|rail), grouping math and the a11y feed — and duplicate the row, the list, the composer host, hover actions, markdown, scroll-pinning, and the “busy” and “waiting on you” vocabularies. Nine duplicates; the seam is already there.

How I’d sequence it
  1. Row — merge MessageItem + RoomEntryRow into Message.*; one hover-action system driven by capability flags.
  2. Live lane — presence pill + Ask + stalled + queue as one component both surfaces mount (this is where parts 2 and 3 land).
  3. Timeline — one virtualized list; rooms gain virtualization + ScrollThumb, sessions gain thread grouping.
  4. Composer host — one host, a ConversationTarget adapter for submit / queue / attachments / mentions.

2 · Approvals: answer where you are

Today the room shows a dead line: “Meeting Notes is waiting for you to approve something… Open Meeting Notes’s session to answer.” You go hunting. Ten minutes later it auto-denies and the agent guesses.

Two things I found in the code that change the plan: (a) DorkOS already has a global approvals queue — the header pill + ApprovalCard/ApprovalList — but it only carries capability approvals (2-hour window), not the SDK “may I read/write/run” prompts (10-minute window, session-only). Two systems, one meaning. (b) The room notice deliberately hides the file path / command, because a shared room might have people who shouldn’t see one member’s approval decisions. So: the Ask becomes one object; detail shows only to who can answer.

Edge cases to get right, whatever we pick

Two people in the room
First answer wins; others see “Dorian allowed this”. Only an eligible approver sees the card at all — everyone else sees the vague notice (privacy rule already in the code).
Ask arrives while you’re typing
Never steal focus. A/D fire only when the card is focused. Draft untouched.
Burst of asks
Same agent, five reads → one stacked card “wants to read 5 files ▾ · Allow all”. Different agents → separate cards.
Answered elsewhere
Card morphs into a receipt with who/when. Second answer gets “already allowed by Dorian at 2:01”.
Session gone / agent restarted
Ask goes stale → “no longer needed”. Never a button that does nothing.
Mobile
Full-width card, two buttons per row, details in a sheet, long-press for scope.

My pick: B first — it removes the hunting and reuses the queue that exists. C is the follow-on that removes the lunch-break failure.

3c · What the click does — the peek

Hover: tooltip with per-agent times. Click / Enter: the pill grows in place into a small card. Esc closes. Never steals focus from the composer.

MN
Meeting Notes · working · 1m 04s
Reading standup.md — replying to “can you log today’s decisions?”
Open its session →Stop
PM
Mio Clicker PM · working · 12s
Replying to your last message
Open its session →Stop

People want to know who, how long, what are they answering, and can I do anything. So, per agent, exactly:

  • Who + how long — have it.
  • What it’s answering — link scrolls to the triggering message (we carry entryId).
  • What it’s doing now — the verb glimpse, if we add the signal.
  • Two actions — Open its session and Stop. Steering stays in the composer via @mention.

Delight budget, spent carefully: the avatar breathes (soft halo, only while working); the pill grows into the peek instead of popping a menu; the hand-off when the reply arrives. That’s the list.
