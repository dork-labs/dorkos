# Spaces email: forgot-password, email confirmation and sign-in links

**Slug:** spaces-email
**Author:** Claude Code (/flow, DOR-2710)
**Date:** 2026-10-04

---

## 1) Intent & Assumptions

- **Task brief (DOR-2710; Dorian in #dorkos, 2026-10-04: "why doesn't spaces.dorkos.ai have email support yet? ... let's setup email for spaces now"):** Spaces can send mail (`apps/community/src/mail/`, SMTP via `COMMUNITY_SMTP_URL` + `COMMUNITY_MAIL_FROM`), but only for a few notices (owner replacement, and from DOR-2709 the "a sign-in was linked" notice). It has no forgot-password email and no email confirmation, so no Spaces account has a confirmed email and a locked-out person needs an operator to run the offline `recover-password` command with downtime. Build:
  1. **Forgot password.** "Forgot password?" on sign-in sends a single-use, short-lived reset link. Same answer whether or not the email exists. Rate-limited per email and per IP. Using the link ends every other session.
  2. **Confirm email.** A confirmation link on sign-up and on email change; a "resend" button; mark `emailVerified`. Existing unconfirmed accounts get a soft banner to confirm.
  3. **"Email me a sign-in link"** as the no-password fallback for the DOR-2709 link screen.
  4. **Mail off** (self-hosted, no SMTP): all three hide and the screen says to ask the space's host.
  - Lands after DOR-2709 (PR #2555) on `apps/community`. Configuring spaces.dorkos.ai's SMTP is Cloud-side, separate work (sender `spaces@mail.dorkos.ai`).
- **Binding from DOR-2709's agreed design (Linear comment):** pre-account takeover. A never-confirmed account's email proves nothing; a stranger can make a password account with someone's email first. When a trusted, verified sign-in hits a never-confirmed account, it wins: the `recover-password` clean-out (old password removed, every other session ended, every other linked sign-in dropped), then link, mark the email confirmed, audit, and tell the person what was cleared. The DOR-2709 refusal screen says a "send a link to this email" path waits for Spaces mail: this issue is that path.
- **Operator's security requirements (non-negotiable):** every reset, confirmation and sign-in-link path withstands account takeover: pre-account squatting, token replay, email enumeration (same answer and no meaningful timing difference), and races between clearing access and linking or signing in (reuse #2555's `access_cleared_xid`, `withRequestStart`, `writtenBeforeClearing`, `clearAccountAccess`). Rate-limit reset and link mail per email and per IP. Single-use, short-lived tokens; only hashes stored (`hashSecret`). A GET must never consume a token: mail scanners prefetch links.
- **Assumptions:**
  - Proof that a person reads an address's mail is the same strength of proof as DOR-2709's trusted, verified issuer sign-in, so it gets the same rule on a never-confirmed account.
  - A confirmation link is not a sign-in: it only marks an address confirmed, and only for the account it was sent for.
  - Sign-in links never create accounts. Admission (invitations, owner grants, owner replacement), the minimum age and `signInRefusal` (erasure, host closure) are unchanged.
  - Mail is optional per host. spaces.dorkos.ai turns it on separately; everything here must be complete and tested with mail off.
- **Out of scope:**
  - Email change (Spaces has none; see §6 decision 4).
  - A general "email me a sign-in link" on the main sign-in page (the brief asks for it on the DOR-2709 link screen only; "Forgot password?" covers a forgotten password).
  - HTML mail, tracking, or a mail provider API: plain text through the host's own SMTP, as today.
  - Configuring spaces.dorkos.ai (DorkOS Cloud work; handed over after merge).
  - OIDC reauthentication for owner actions.

## 2) Pre-reading Log

- `apps/community/src/auth.ts` (#2555): one Better Auth instance; `emailAndPassword: { enabled: true }` with no `sendResetPassword`; no `emailVerification`; `disabledPaths` already drops `/change-password` because it checks a password outside the shared guess budget. `databaseHooks.account.update.after` says "password changes and resets are off", which this work changes. `auth.handler` is wrapped in `withRequestStart` for every request but `get-session`.
- `apps/community/src/sign-in/account-access.ts` (#2555): `clearAccountAccess(client, userId, memberIds, keep, hostActor)` stamps `"user".access_cleared_xid`, deletes sign-in rows (unless kept), every session, revokes connection grants, agent credentials, pairings, issued host API keys and live invites, deletes `pending_sign_in_links` (guarded with `to_regclass` for recovery run before the migration). Returns removed provider ids.
- `apps/community/src/sign-in/request-start.ts` (#2555): `withRequestStart`, `markAccessCleared(userId)` (exempts this request's own new session and link), `writtenBeforeClearing` (fails closed with no recorded start).
- `apps/community/src/sign-in/link-gate.ts` (#2555): the trusted path calls `markAccessCleared` then `clearAccountAccess({password:false, links:false}, 'system')` on a never-confirmed account; the untrusted path stores a 10-minute `pending_sign_in_links` row (hash only) and a signed `community_pending_link` cookie.
- `apps/community/src/routes/account/sign-in-link.ts` (#2555): the password link route; mints the session through `auth.api.signInEmail` with the entered password. An email sign-in link has no password, so it needs another way to mint a session through Better Auth's own path.
- `apps/community/src/browser/sign-up/LinkWithPassword.tsx` (#2555): `PASSWORD_REQUIRED` copy "This account has no password. Ask the space's owner for help." This is where "Email me a sign-in link" goes.
- `apps/community/src/password-confirmation.ts`: spend-before-verify, refund-on-success guess budget keyed `reauth-account:<userId>`.
- `apps/community/src/app.ts`: `limitAttempts(key, ceiling)` is an in-memory, per-process 60-second window (10,000 keys, oldest evicted); `peer(c)` is the socket address or the configured trusted proxy header. `canSendNotice(kind)` = mail configured and a composer exists. `GET /api/v1/auth-options` feeds the sign-in page.
- `apps/community/src/mail/{outbox,worker,messages,transport}.ts`: a durable outbox queued inside the causing transaction; `notice_outbox.community_id NOT NULL`; no address stored (read at send); worker leases, retries 72 hours, fails `RECIPIENT_UNAVAILABLE` for an erased account; a composer "may write what that attempt needs, such as a single-use link it mints" and returns `null` (`NOTICE_OBSOLETE`) when the notice is no longer true. `plainTextMail` is the only way to build a message.
- `apps/community/src/owner-replacement/object-tokens.ts` + `KeepOwnership.tsx` + `browser/index.html`: the precedent for mailed links: the composer mints a random token per send attempt, stores only its hash, and the link carries it after `#`; an inline script reads the fragment into page memory and erases it from the address bar before any network work; the page POSTs to use it.
- `apps/community/src/host/release-unverified-account.ts`: the offline command for the squatted-email collision; deletes a `"user"` row and fails if any other row still names it, so new tables need `ON DELETE CASCADE`.
- `apps/community/src/owner-replacement/notices.ts`: reads `"user"."emailVerified"` to decide the owner-replacement wait. Confirming addresses makes that wait follow a real confirmation from now on.
- `better-auth@1.7.6` source (`node_modules/.pnpm/better-auth@1.7.6_*/dist`), read for the build-vs-reuse decision:
  - `api/routes/password.mjs` `requestPasswordReset`: stores the token as `verification.identifier = "reset-password:<token>"`, **plaintext** unless `verification.storeIdentifier: 'hashed'` is set. Unknown email runs a dummy lookup, but a known email inserts a row and **awaits `sendResetPassword`** (unless background tasks are configured): a timing difference. Several reset tokens stay valid at once; none is invalidated by a password change. `resetPassword` revokes sessions only with `revokeSessionsOnPasswordReset`, and nothing else: no other linked sign-ins, connection grants, agent credentials, host keys, invites, no `access_cleared_xid` stamp, no confirmation of the email.
  - `api/routes/email-verification.mjs`: tokens are **stateless JWTs** signed with the auth secret: not single-use, not revocable, valid until expiry. `GET /verify-email` **acts on GET** (a scanner prefetch confirms), and `autoSignInAfterVerification` would mint a session on that GET. The signed-out resend has a 500 ms floor against timing; the signed-in path has none.
  - `plugins/magic-link/index.mjs`: `storeToken` defaults to `"plain"`; `GET /magic-link/verify` **consumes the token and creates a session on GET**; it **creates a user** for an unknown email unless `disableSignUp`; `sendMagicLink` is awaited inline (timing). On a never-confirmed user it calls `revokeUnprovenAccountAccess` (`db/revoke-unproven-account-access.mjs`): deletes every account row and session and sets `emailVerified`, under a verification-row lock, outside any transaction, with none of this server's derived credentials or the clearing stamp.
  - `api/rate-limiter/index.mjs`: rate limiting is **per IP only**, on by default only in production, in memory: `/request-password-reset` and `/send-verification-email` get 3 per 60 s. No per-email limit.
  - `api/index.mjs`: `disabledPaths` matches the normalized path exactly and answers `404`.
  - `api/routes/update-user.mjs`: `/update-user` refuses an `email` field; `/change-email` is off unless `user.changeEmail.enabled`.

## 3) Codebase Map

- **Primary components/modules:** `apps/community/src/{auth.ts,app.ts,main.ts,config.ts,security.ts}`; new `src/email-links/` (request routes, resolver, composers, token store, Better Auth plugin for the two session-minting uses); `src/sign-in/account-access.ts` (also deletes email-link tokens); `src/mail/{outbox,worker}.ts` (account-level kinds, resolver tick); migration `0032_email_links.sql`; browser: `components/Admission.tsx` (Forgot password?), `sign-up/LinkWithPassword.tsx` (email me a sign-in link), new pages `ResetPassword`, `EmailSignIn`, `ConfirmEmail`, a `ConfirmEmailBanner` in `CommunityApp.tsx`, the Account section in `components/SignInMethods.tsx`; `browser/index.html` fragment capture.
- **Shared dependencies:** `@dorkos/shared/community-wire` (auth options gain `emailLinks`, new request/response schemas, account sign-in methods gain `emailConfirmed`), `@dork-labs/ui` (`Notice`, `Button`, `Field`).
- **Data flow:**
  - Request: browser → `POST /api/v1/account/password-reset` `{email}` → per-IP limit → one identical `INSERT` into `email_link_requests` for every address (keyed hash for throttling, plaintext email held only until resolved) → `202 {accepted:true}`.
  - Resolve (mail worker tick, seconds later): claim unresolved rows → look the address up → queue an account-level `notice_outbox` row only for an eligible account → null the plaintext email.
  - Send: composer mints the token (hash stored, older live tokens of that kind superseded), returns plain text with `${publicUrl}/reset-password#<token>`.
  - Use: page reads the fragment, `POST` peeks (no consume), then `POST` uses: one transaction locks the account, checks the token, clears or resets, consumes; the session is minted through Better Auth's internal adapter so the session hooks (`signInRefusal`, `writtenBeforeClearing`) run.
- **Feature flags/config:** no new on/off switch: email links exist exactly when mail is on (`COMMUNITY_SMTP_URL` + `COMMUNITY_MAIL_FROM`) and the three composers are registered. New limits with defaults: `COMMUNITY_EMAIL_LINK_REQUESTS_PER_MINUTE` (per IP, 5), `COMMUNITY_EMAIL_LINKS_PER_HOUR` (host-wide, 300).
- **Potential blast radius:** session creation (new path into `internalAdapter.createSession`); `clearAccountAccess` (recovery, trusted link and three new callers); `notice_outbox` schema (nullable `community_id` for account kinds); the meaning of `"user"."emailVerified"` (owner-replacement wait, DOR-2709 trusted link); short-name reserved paths (three new top-level pages); the sign-in page and link panel.

## 5) Research

- **Potential solutions:**
  1. **Better Auth built-ins** (`emailAndPassword.sendResetPassword` + `revokeSessionsOnPasswordReset`, `emailVerification`, the `magicLink` plugin with `storeToken: 'hashed'`, `verification.storeIdentifier: 'hashed'`, `disableSignUp`). Pros: little code. Cons, from the source: confirmation tokens are stateless JWTs (no single use, no revocation) and confirm on GET; magic links consume and sign in on GET (scanner prefetch burns or uses them); reset does not run this server's clean-out, stamp `access_cleared_xid`, or confirm the email, and leaves other reset tokens alive; magic-link's never-confirmed handling skips connection grants, agent credentials, pairings, host keys, invites and the race stamp; the known-email branch awaits the send (timing leak); throttling is per IP only and memory-only; a magic link can create accounts. Each gap needs a wrapper hook, so the result is the custom design plus a dependency on internals that move between versions. Rejected.
  2. **Better Auth built-ins for reset only, custom for the rest.** Pros: reuses the reset endpoint. Cons: still needs the clean-out, stamp, confirmation and token invalidation around it via hooks on `/reset-password`, and two token stores with different rules. Rejected.
  3. **Custom, on this codebase's own primitives**: hash-only token table, mail through the notice outbox (token minted by the composer, as owner replacement does), a request table whose insert is identical for every address and a worker-side resolver (so the request path never reads `"user"`), use only by POST from a fragment page, one transaction per use with `clearAccountAccess` + `markAccessCleared`, sessions minted through Better Auth's internal adapter from a small server plugin, built-in reset/verify/magic routes listed in `disabledPaths`. Pros: every requirement is a property of code this repo already reviews; one token rule for all three kinds. Cons: more code; one more Better Auth seam (plugin endpoint + `setSessionCookie`), pinned by a test.
- **Recommendation:** option 3.
