## Root sequence and handoff

`apps/server/src/index.ts:5789–5897` performs ordered teardown. Workspace disposal is first. Other stops occur only after its await, and most later failures reject the sequence immediately. There is no aggregate budget or structured outcome. Account-usage flush alone has a local catch at this level. Later closers can remain unvisited after an earlier failure/hang.

`index.ts:804,897` retains/acquires the instance lock; `:4862` injects `db.$client.close()` only into admin reset; `:5896` releases the lock at the end of ordinary cleanup. `routes/admin.ts:278–301` acknowledges reset/restart and schedules independent callbacks: reset awaits cleanup, closes DB, awaits recursive data-directory removal, then restarts; restart awaits cleanup then restarts. Both catch cleanup failure and restart regardless. Normal restart and signal cleanup have no equivalent explicit consolidated-DB close in this inspected path. `routes/admin.ts:116–132` production restart spawns a successor before process exit; development exits for the watcher. Thus lock release precedes reset's database closure/deletion, and cleanup rejection does not prohibit successor launch today.

`index.ts:5901–5911` guards only signal entry with a boolean. Admin calls bypass it; repeated signal calls do not join a stable operation result. A signal may compete with a deferred admin action. This is why DOR-2481's later terminal owner must own the complete action, not merely memoize cleanup. DOR-2551 does not resolve this race for already-admitted admin requests.

`index.ts:5942–5970` startup failure attempts workspace disposal, contains its failure, then closes only the offline fixture before existing error reporting/exit. Fixture rejection can still replace that reporting. General acquisition rollback belongs to DOR-2483. Fatal exception handling (`:5918–5931`) flushes a crash report then exits; it does not run ordinary cleanup.

## Outcome vocabulary

- **Fenced**: inspected code prevents the named late mutation; scope matters.
- **Awaited work**: cleanup awaits an enumerated set, with no conclusion about unenumerated producers.
- **Stop/cancel only**: timer/unsubscribe/abort or kill request, without observed completion.
- **Unproven handoff**: no demonstrated all-writer or late-acquisition guarantee. A method resolving `void`, swallowing an error, or racing a deadline is not authorization to release lock/close DB/delete data.

## Design implications, not implementation instructions

A later DOR-2482 contract needs per-owner results distinguishing completion, proven late-write fence, failure and unfinished work. Deadlines may stop waiting but cannot promote unfinished work to safe handoff. Class-local workspace timed-out is uniquely backed here by its tested mutation fence; do not generalize its shape to every timed-out owner.

The permission to close the shared DB, remove data, release the lock or launch a successor needs explicit dependencies on writers, not `Promise<void>` completion. Current swallowed adapter/pump/reporting errors and scheduler deadline exhaustion disappear into that void return. Preserving evidence requires addressing those outcome losses deliberately with owning domains.

Do not adopt a blanket parallel close: adapters may require Relay; Relay may emit trace writes; scheduler may publish stop messages; skills projection callbacks must be stopped before watcher teardown; shared DB consumers outlive no-op store closes. Dependency direction and failure policy must be stated before changing order.

Candidate future proof matrix: hold an actual write just before its async boundary; initiate cleanup; inject success, rejection and nonsettlement; release the held writer after the claimed handoff; assert exact mutation behavior plus positive control. For DB/lock design, use disposable local DB/files and a fake lock/successor port, never real production reset or spawning. Assert denied handoff on unproven/failed owners and no false success after merely closing transport. Include competing admin/signal continuations with the future operation owner. Root AST wiring supplements these behavioral proofs, never replaces them.

No all-server shutdown, safe reset deletion, DB/lock exclusivity or successor readiness guarantee is established by this source inventory.

### What per-instance cleanup actually proves

`extension-server-lifecycle.ts:188,219–255` awaits compilation/shutdown, creates/writes a runnable bundle under `dorkHome/cache/extensions/server/_run`, loads it with `require`, creates context/router, and calls arbitrary extension registration. Its bounded registration wait is not cancellation. On timeout (`:258–278`) it calls context `dispose`, leaves a late-result continuation that may call the eventual cleanup function, and refuses to mount that timed-out instance. Successful registration mounts state and calls inbox `markRunning` (`:289–308`). Root shutdown does not gate later completion of this path.

The context's `dispose` is **not whole-extension drain**. `extension-server-api-factory.ts:306–316` marks disposed, clears the registered scheduling intervals and releases scoped listeners. It blocks future `ctx.schedule` and guarded listener registrations (`:223–224,253–270`), logging an inert-use warning once (`:193–200`). It does not join callbacks already executing, revoke every context method, stop arbitrary code/children, or fence filesystem writes. In particular `storage.saveData:218–219` still atomically writes `dorkHome/extension-data/<id>/data.json`; secrets/settings objects remain exposed (`:204–205,273–286`). No resource-specific fence should be inferred for these methods from the registration-only guard.

Ordinary per-id `shutdown:323–352` marks the inbox stopped, cancels the captured scheduled-cleanup functions (swallows errors), invokes the extension cleanup synchronously (catches errors; does not await a returned promise), releases listeners, deletes the mounted router record, and logs. It does not invoke the timeout `dispose` function or prove active scheduled callbacks settled. Inbox is another dependency: `inbox/extension-inbox.ts:231–263` reads decisions, starts its sweep, rearms standing escalations/deadlines on mount, and disarms standing state on stop; the separate boot `cancelUndiscovered:271–285` updates persistent decision rows. Do not conflate that boot writer with the running/stopped methods. Routes already executing and arbitrary registration/cleanup code remain outside the proven boundary. No claim about managed child exit is justified here.

**Disposition:** unknown/default-deny for affected DB, filesystem and authority handoff. Retain subscription ownership, close new scan/server acquisition, and join active work or prove exact effect fences before permitting those resources to close. Timer cancellation, a fulfilled scan queue and synchronous cleanup invocation are not all-writer proof.
