# Managed remote access: two contract decisions

**Work item:** DOR-2086, with its existing service and contract owners. **Status:** proposal for decision, not an accepted wire contract or implementation authorization. **Public baseline:** `f8df106324d29a2199bb07e2a1102a0b75df9de1`. **Prepared:** 2026-09-28.

The identity prerequisite has landed in [PR #2260](https://github.com/dork-labs/dorkos/pull/2260). The [consumer specification](02-specification.md) remains a draft. This note makes its two blocking questions concrete; it does not create a second programme or reopen forwarding, SSE, command verbs, or local login policy.

## What source already settles

`packages/cloud-api/src/remote.ts` publishes enrollment's response (`enrolmentId`, `consentVersion`, `enrolledAt`), permits creation only by a person's session, and permits withdrawal by the person or the instance. It does not publish the create request, a local-to-person ceremony, or proof provisioning. `routes.ts` already names `/v1/remote/enrolment`. A linked instance bearer must not become a person credential. Published `/v1/remote/open` accepts a person session, person bearer or wake token; that does not broaden enrollment.

The merged consumer draft requires an explicit local human action, immediate offline withdrawal, encrypted secret references, proof validation before local authorization, and refusal of duplicate proof headers. It preserves BYO mode and requires all authorized hostnames. `CloudAuthority` remains exactly `open | close | rotate | revoke`; neither decision below adds enrollment or configuration to it. An edge proof establishes a managed ingress path, never the caller's identity or permission.

These constraints need no new operator decision. Which human ceremony to offer and which side owns proof provisioning remain decisions. Route names and schema identifiers below are concrete proposed deltas for owner review, not declarations that endpoints exist. Publish the accepted package schemas, principal table, fixtures and compatibility behavior before consumer code. Deployed acceptance remains a later gate.

## Decision 1: local action followed by Cloud browser consent

**Recommendation:** a local signed-in human starts a short-lived enrollment intent; a browser signed in to Cloud approves that exact intent; the same linked instance reads the resulting receipt. No Cloud cookie or person bearer passes through the app server. The app keeps a separate local consent record and honors neither a bare browser callback nor a Cloud enrollment created without that current local action.

| Option                                                           | Consequence                                                                                                                                                                                                   |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local intent + Cloud browser approval (recommended)              | Two explicit steps bind the local action to the Cloud person and machine. Works across origins without exporting a person credential; requires a small intent/readback contract.                              |
| Existing Cloud account page, then local selection                | Fewer new endpoints if an authenticated enrollment read is added, but independently initiated Cloud and local consent must still be reconciled and explained. Do not infer local consent from a Cloud record. |
| Give the app a person bearer or let the instance POST enrollment | The former expands credential exposure and the latter contradicts the published principal rule. Neither is an acceptable shortcut under the current contract.                                                 |

### Proposed public deltas

All request schemas are strict; identifiers use the package's opaque ID type. Expiry timestamps use its timestamp type. Never accept an arbitrary callback origin. An enrollment intent is not enrollment and cannot issue a tunnel credential or open anything.

| Proposed operation                                                                    | Principal and request                                                                                                                                                                                                                                                    | Response and required semantics                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/remote/enrolment-intents` (`remoteEnrolmentIntents`)                        | Current instance bearer; `RemoteEnrolmentIntentRequest { requestId: Id, verifierChallenge: string }`. The challenge is base64url SHA-256 of an unpredictable local verifier. Derive instance identity from authentication, never a request-selected target.              | `RemoteEnrolmentIntent { intentId: Id, instanceId: Id, verificationUrl: URL, expiresAt: Timestamp, pollAfterMs: nonnegative integer, consent: { version: string, text: string } }`. Same authenticated instance and request ID replay the same intent; changed challenge under that key is a conflict. The URL stays on the configured trusted Cloud origin and contains no bearer or verifier. |
| `POST /v1/remote/enrolment` (existing route)                                          | Cloud person session, with normal CSRF/origin protection; proposed `RemoteEnrolmentRequest { intentId: Id, consentVersion: string }`. Cloud checks the person's authority over the intent's instance and displays that machine and exact consent text before submission. | Existing `RemoteEnrolmentSchema`; server selects the instance from the intent, not caller identity fields. Repeating an approved intent returns the same receipt; another person, stale consent version, expired/canceled intent or wrong account is refused. Approval alone cannot enable an app lacking matching active local consent.                                                        |
| `POST /v1/remote/enrolment-intents/{intentId}/result` (`remoteEnrolmentIntentResult`) | Original current instance bearer; `{ verifier: string }` in the body, never URL or logs.                                                                                                                                                                                 | `RemoteEnrolmentResult { intentId, instanceId, state: pending                                                                                                                                                                                                                                                                                                                                   | approved | expired | canceled, enrolment?: RemoteEnrolment }`, discriminated so only approved has a receipt. Stable approved replay supports a lost response until the intent expires; withdrawal changes subsequent reads to canceled. An unknown intent is refused. The verifier supplements instance authentication, never replaces it. |
| `DELETE /v1/remote/enrolment` (existing route)                                        | Instance bearer: target only itself, reject a conflicting supplied target. Person session: proposed strict query `{ instanceId: Id }`, with ownership and CSRF checks.                                                                                                   | Existing withdrawn response; document repeat/no-record behavior explicitly. Recommended idempotent already-withdrawn result, with no invented historical timestamp. Local withdrawal is immediate regardless of HTTP outcome. Withdrawal also cancels pending intents for that instance; delayed approvals/results cannot restore them.                                                         |

The local server mints and encrypts the verifier only after its existing local-human/trusted-caller guards pass. Persist the intent ID, context generation, expiry and consent version, not a person credential. The local action explains standing access in plain language; Cloud hosts the authoritative versioned text. Local installation must reject a receipt after unlink/relink, account change, expiry, cancellation or superseding local intent, including equal-token replacement. A lost create response retries the same request ID/challenge; a lost approval/read response retrieves the same receipt. Expired ambiguous setup remains unavailable and asks for a fresh explicit action, never automatic re-enrollment.

**Operator choice:** approve the two-step experience and authoritative Cloud consent text, or choose the account-page alternative. **Service-owner engineering decisions:** precise expiry/replay retention, conflict and refusal Problem codes, cancellation transaction boundaries, and consent-version rollout behavior. Those are reviewable contract values, not reasons to ask the operator to design endpoints. Material consent changes require a fresh explicit agreement; a new version must not silently expand old consent. An authorized change to that product rule would need a separate decision.

### Credential-free acceptance cases

Use fake transport and deterministic clocks: no local human means no intent request; an instance/person bearer cannot approve; wrong-account person cannot approve; target tampering cannot change the instance; stale version/expiry/canceled intent fail; duplicate request ID with changed challenge conflicts; lost responses recover the same receipt; wrong verifier and wrong instance fail; remote approval without matching local consent remains disabled; withdrawal during pending approval prevents later completion; A → unlink → A and origin changes discard old results. The browser leg must prove CSRF refusal and that no bearer/verifier reaches URL, history, referrer, logs or client DTOs. Supplier acceptance later proves the real signed-in browser-to-instance round trip.

## Decision 2: service-provisioned, generation-bound ingress proof

**Recommendation:** the service owns the edge proof and its stripping policy, and supplies the matching verifier secret to the authenticated instance through the public credential exchange. The app owns encrypted storage and strict request validation. Prefer a short, explicitly reported interruption during rotation over an unspecified dual-secret overlap in the first slice. This is a proposal; private service code is not permission to publish a header name or assume its secret is retrievable.

| Option                                                     | Consequence                                                                                                                                                                                                 |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Service provisions proof with the credential (recommended) | One issuer binds credential, host set and proof generation. Requires recoverable issuance and explicit activation/rotation ordering.                                                                        |
| App generates proof and configures the edge                | Avoids delivering an issuer-generated verifier but needs a newly authorized edge configuration operation and ownership/recovery rules. A forwarding token alone does not prove that capability.             |
| Per-request signatures                                     | Can bind method/path/time and reduce bearer-proof replay, but adds canonicalization, body/stream handling and clock/replay rules. A separate design, not a silent replacement for the draft's shared proof. |

### Proposed public deltas

1. Publish a single fixed `REMOTE_INGRESS_PROOF_HEADER` constant. Proposed new public spelling: `X-DorkOS-Remote-Proof`. This is a candidate, not a claim about any deployed header. Never let a response choose an arbitrary header to trust.
2. Extend credential issue's response with a required-for-managed-consumers `ingressProof: { generation: Id, value: SecretValue, hosts: Hostname[] }`. The credential ID, proof generation and complete normalized host set form one bundle. Old responses without it leave managed mode unavailable. Retain compatibility for older clients by publishing the addition and feature requirement explicitly; no BYO change. The service must not mix a credential from one attempt with proof from another.
3. Extend credential confirmation's request with `ingressProofGeneration: Id` and `ingressProofFingerprint: string`, defining the fingerprint algorithm and encoding in the package. Proposed SHA-256 of the exact UTF-8 proof value, lowercase full hexadecimal. Confirmation binds both persisted credential and proof. Neither a fingerprint nor a generation is a usable proof secret.
4. Define the `value` encoding as unpadded base64url from 32 random bytes. Define retry of the same issue key after a lost response: recommended same complete bundle returned to the same still-authorized instance during a bounded recovery window. This needs explicit secret-retention support; it is not established by the current “returned once” prose. After the window, fail with a specific recovery-required Problem and require a new issuance, never falsely ACK an unrecoverable rotation. This is the existing lost-response question, not a new programme.
5. Publish edge/app transition fixtures. Initial access stays closed until the app has stored the bundle and confirmation/edge activation satisfy a defined ordering. Rotation closes old managed listeners, stages and persists the new bundle, applies the corresponding policy on every host, confirms readiness, then reopens only that generation. The service owner must define which operation constitutes edge readiness and how the app observes it; confirmation cannot mean readiness merely because it returned 200. Any partial host application remains closed for that host. A crash at any step recovers by the recorded generation or stays unavailable. Revoke and withdrawal invalidate every retained proof immediately locally; remote convergence is a separate receipt.

The edge must strip **all** client-supplied instances of the fixed proof header before adding exactly one value for the active generation on each authorized host. The app checks the raw header occurrences before framework coalescing: zero, multiple, case-varied duplicates, comma-joined, whitespace-malformed or wrong values fail before local session/API work. Use constant-time comparison on valid fixed-length decoded values. Do not log or echo proof values.

A proof sent to an ordinary direct/local listener must not gain a managed classification. The integrated slice must isolate the managed ingress listener or otherwise prove a trustworthy ingress boundary; `Host`, forwarding headers and client IP alone are not that proof. The shared proof is replayable by anyone who steals it, so secret confidentiality, TLS on its delivery path, and unchanged local login/authorization are required. Do not describe it as a per-request signature or a new person principal.

**Operator choice:** approve service-owned proof provisioning and brief fail-closed interruption during rotation, or require seamless rotation and fund an explicit bounded overlap protocol. **Service-owner engineering decisions:** public constant, bundle publication, retry window, edge-ready signal, host application ordering and failure recovery. The app cannot settle these by inventing a request or copying an unpublished implementation detail. No live supplier configuration is authorized by this note.

### Credential-free acceptance cases

Fixtures must cover missing proof on an old service; no bind before persistent bundle/readiness; same issue key replay after lost response; new generation under stale link refused; storage/confirm failure; wrong credential/proof pairing; duplicate and spoofed headers through a real local HTTP socket; proof on a direct listener; wrong host and removed host; every custom host using the current generation; rotation crash at each recorded step; partial edge application; withdrawal during rotation; and old-proof refusal after reopen. Fake edge assertions prove configuration intent, not actual supplier stripping: live acceptance must separately demonstrate stripping, readiness and every granted host.
