# Managed remote access: local app consumer

**Work item:** DOR-2086

**Evidence baseline:** `5794f638160a68811382347356fd29b31ee2e911`

**Status:** Offline implementation design. Production enrollment and managed ingress are gated on published supplier contracts and deployed acceptance evidence.

## Outcome and boundaries

After a person explicitly selects managed access on the computer running DorkOS, the app stores the one-time tunnel credential privately. An authenticated Cloud `open` command then opens managed forwarding through the existing ngrok manager for every authorized hostname, and the app shows the same truthful remote state in Settings, Control Center, the beacon, and the command palette. The person can close access or withdraw enrollment locally. Cloud commands can reopen, close, rotate, revoke, or report pending work without a browser tab remaining open. BYO ngrok setup, autostart, environment precedence, and use remain available.

No linked account, entitlement, designation, saved URL, or machine boot can enroll a person automatically. No Cloud response can bypass local login/exposure rules. No client DTO, log, config export, or telemetry payload contains a Cloud bearer, issued tunnel value, ingress proof secret, or command lease token. The app does not implement Cloud's closed-address page, plan logic, pricing, or a second tunnel transport.

## Prerequisites and contract gates

1. Adopt DOR-2348's authenticated `/v1/session` instance identity and current credential/origin generation. Require an authenticated instance session with an opaque `instanceId` for instance-scoped calls. An absent route, stale context, 401, or missing ID leaves managed setup unavailable; never use a credential hash or telemetry ID. DOR-2348's local-first unlink and stale-response guards must have landed before this consumer relies on them.
2. Publish an enrollment POST request and local-human-to-Cloud-person ceremony, with request/response/refusal fixtures and exact DELETE authorization. `RemoteEnrolmentSchema` in `packages/cloud-api/src/remote.ts` is only the POST response. The documented POST accepts a person session, while the local app holds an instance key. Do not implement or fake the ceremony route/request until that contract exists; the app must not send a guessed body or let the instance enroll itself.
3. Publish the ingress proof-header contract, including provisioning, rotation, origin trust, stripping of untrusted supplied values, and duplicate-header refusal. The app must reject missing, malformed, or repeated proof before a managed request reaches the local session/API gates. A header value is never a local operator identity or approval bypass. Do not invent a header name or secret from an unpublished service implementation.
4. Confirm deployment availability and authenticated success/refusal fixtures for the routes the slice uses. Package publication, fake tests, and service implementation are separate evidence states. Production controls remain hidden or clearly unavailable until both the enrollment and ingress gates pass.

The accepted handoff uses the existing `ngrok.forward` call with a different credential, domain, and lifecycle. Its transport choice is settled. The public package declares SSE for `GET /v1/remote/commands`; long polling is optional only if a separate public contract is published. The closed-address browser page is deliberately outside the machine wire and belongs in supplier acceptance.

## Server ownership and persistent state

Keep `TunnelManager` the single owner of active tunnel mode (`off | byo | managed`), never running BYO and managed forwarding together. Managed mode must serve every hostname in the complete `RemoteCredential.hosts` set; if the forwarding API needs one listener per host, the manager owns that set and closes removed hosts. A mode switch closes every listener owned by the old mode before using the new credential; a failed switch reports actual listener state and does not leave BYO and managed exposure overlapping. `resolveTunnelSettings` continues to resolve BYO environment and config unchanged. Managed mode has its own selection and status; it never writes `tunnel.authtoken`, `tunnel.domain`, or `tunnel.enabled`. Managed boot recovery requires prior local enrollment and its own explicit persisted preference, not a BYO token or flag. Boot may reconnect the managed command stream, but it cannot infer an `open` command from the enrollment record alone.

**Proposed boot precedence, to validate before implementation:** an explicit `TUNNEL_ENABLED=true` selects BYO for this process; an explicit `TUNNEL_ENABLED=false` suppresses automatic forwarding in either mode; with the variable unset, a persisted managed selection takes precedence over an older saved `tunnel.enabled=true`, which remains available when the person switches back. This extends the existing flag's effect to managed mode and must be checked against operator expectations and pinned by a boot matrix test before adoption. Every path still checks `canExpose()` before opening. The selected mode, actual listener set, and Cloud status may differ during recovery; the report must name that difference instead of guessing that enrollment implies reachability.

Add a semver-keyed config migration for a separate managed-remote section. The migration introduces a default-off mode preference and non-secret enrollment/credential references, preserves existing BYO fields byte-for-byte, and never copies a BYO token into managed storage. Store each issued or rotated tunnel value under a distinct name in `EncryptedFileCredentialStore`; config stores only the `file:` reference, Cloud credential ID, and opaque enrollment metadata needed for recovery. Resolve secrets server-side just before forwarding. Treat a dangling reference as blocked and instruct the person to repair managed setup. Never put an issued value in `~/.dork/config.json` or echo it in `/api/config`.

The local managed coordinator captures the current Cloud credential, normalized origin, instance ID, and link generation for each asynchronous operation. Before retaining any response or changing active listeners, it verifies that capture is still current. A → unlink → A with the same bearer must still invalidate an older result. On unlink, local withdrawal wins synchronously: disable managed opening, stop its command connection, clear the local managed credential reference and pending start, and begin closing all managed listeners before awaiting best-effort Cloud withdrawal/revoke with the captured old credential. A late result or 401 from the old link cannot alter a replacement. If Cloud is unreachable, report that its record may still exist while local access remains closed; retry remote cleanup without restoring local access.

Put a non-exported `CloudAuthority` marker beside `trusted-caller`, with the closed verb union **exactly** `open | close | rotate | revoke`. Mint it only from a validated, current leased Cloud command while the matching local consent remains active; register its mint call in `PROTECTED_EFFECTS` with the narrow allowed call sites and refusal tests. It cannot enroll a person, select a mode, configure ingress proof, or waive `canExpose()`. Local human enrollment, selection, and withdrawal use their separate cookie, `trustedCaller`, and `isLocalCaller` guards; they cannot mint a `CloudAuthority` from a JSON field or header. Add every new route, config write, listener start, and credential-store effect to the existing protected-effect scan with its actual guard. `POST /api/tunnel/start` keeps its BYO bars. Managed commands cannot enroll or restore withdrawn consent. Closing and withdrawing remain available when exposure prerequisites or Cloud are down.

`canExpose()` remains mandatory before either mode opens or reopens a tunnel, including boot and a Cloud `open` command. Managed ingress proof is an additional edge check, not a replacement for local login. A request from the managed host with failed proof is refused before agent/session work. The proof must be validated against exactly one canonical header value after the supplier-defined stripping rule; ambiguous duplicates are refused, not accepted by first/last-value behavior.

## Person-facing lifecycle

The selected mode and source of truth are explicit in one server report returned to all existing remote-access surfaces. Distinguish `off`, `opening`, `open`, `draining`, `blocked`, and the local listener's reconnecting state; include a safe reason, URL only when usable, and `alwaysAvailable` as Cloud reports it. Do not compute a plan promise from a subscription or infer that a closed tunnel means the computer is asleep. When Cloud status is unavailable, show last-known local listener truth with a stale/read-failed indication rather than a fabricated Cloud state.

Settings offers BYO and managed as separate choices, preserving the BYO token/domain controls. Managed setup explains that the person is opening access to this machine and requires an explicit local action. Until contract gate 2 is satisfied, the managed action cannot be offered as a working enrollment path. The Control Center toggle, beacon, flyout, and command palette dispatch through the same selected-mode action model; they must not send `startTunnel()` to BYO merely because a managed token is absent. A mode change, close, or refusal updates every surface through the shared store and server event stream. The UI treats `opening` as pending, `draining` as finishing active requests, and `blocked` with a reason as requiring attention; it does not show a copyable URL while unusable.

Read the Cloud-supplied remote capability (`byo | on_demand | always_available`) and current `RemoteStatusSchema` before offering managed setup. `byo` leaves managed selection unavailable; `on_demand` and `always_available` describe behavior without hardcoded plan names or prices. The server remains the source of `alwaysAvailable`; the client does not derive it from entitlement. A stale or absent entitlement cannot silently enroll, but it also must not disable an existing BYO tunnel.

The closed-address browser page shown when this machine is asleep is served outside the local app. The app can use the public `RemoteStatusSchema` and idempotent `POST /v1/remote/open` response (`wakeId`, `pollAfterMs`) for reachable, authenticated views, but it cannot claim its own UI works on a sleeping machine. The open route accepts a Cloud person session, person bearer or wake token; the linked instance bearer must never substitute for one of those principals. Local controls must use the agreed human ceremony or an explicitly authorized wake credential. Supplier acceptance must demonstrate the closed page, authorized reopen, and honest failure when the instance stays asleep.

## Command connection and effects

Once enrollment, current instance identity, a stored credential, and exposure prerequisites are present, open the instance-authenticated SSE `GET /v1/remote/commands` stream. Parse SSE framing and `RemoteCommandSchema` strictly; honor `retry:`/`keepalive.reconnectAfterMs` with a bounded reconnect delay and cancellation on withdrawal or context change. The ordinary JSON `CloudApiClient` does not parse SSE; the coordinator owns this narrow transport. No undeclared long-poll fallback. A disconnected stream is not proof the existing listener has closed.

For each leased command, persist a local command ID, lease token, and outcome in a bounded durable acknowledgement journal before considering it settled. Mint the matching `CloudAuthority` only after validating the lease, verb, current link context, and enrollment; the protected effect checks it again before acting. Apply `open`, `close`, `rotate`, and `revoke` idempotently against current listener/credential state. `inbox_pending` only signals the existing appropriate seat path; it never grants remote authority. `keepalive` needs no acknowledgement. A duplicate command must not repeat a destructive effect, yet must be acknowledged with its lease token and recorded outcome. A lost acknowledgement retries `POST /v1/remote/commands/ack` with the same item, including after restart, until accepted or the service explicitly rejects the lease. Do not treat the response's count alone as a per-item success decision if it differs from the submitted count; reconcile by redelivery or supplier-confirmed lease semantics. A command whose instance/link context became stale is refused and cannot operate a new link. Keep the journal free of Cloud bearers and issued tunnel values.

An `open` command uses its `wakeId`, optional address/host, and supplied idle/drain windows, then acknowledges applied only after every required managed host is reachable. If the command omits an address or host, resolve the canonical address through the published address route. When the issued credential includes `hosts`, serve its complete case-insensitive set, including custom hosts, and stop serving hosts removed by a later credential. An absent list means keep the previous host behavior. Refuse opening when no valid target is known. Repeating the wake must not create duplicate forwarding for any host. `close` stops accepting new managed requests, lets already accepted work finish until the current drain deadline, then closes all managed listeners; it records the actual outcome if a local failure prevents closure. Use a bounded local deadline when the service supplied none, and report that fact. Local withdrawal can close immediately and outranks a drain. Idle close uses the server-supplied window and post-gate request activity, not passive UI reads. All timers belong to the active managed generation and are canceled on mode change, withdrawal, or shutdown.

For `rotate`, pass the command's `credentialId` as the idempotency key to `/v1/remote/credentials/issue`; store the returned `value` in a new encrypted entry, confirm the returned credential ID, and switch the listener only while the original context is still current. If issue is refused, retain the current credential as the public contract directs. On a switch failure, retain or recover the last locally usable credential when still valid and report failure; never persist an unconfirmed plaintext value. Apply a present `hosts` list as the full case-insensitive set and stop serving removed hosts; an absent list leaves existing hosts unchanged. `acl` remains opaque. `revoke` forgets the named credential, stops using it, and closes managed access if no valid replacement exists. A revoked credential must not be recovered from a stale config reference.

## Activity, retries, and shutdown

Count authenticated requests that cross the managed tunnel after the ingress proof and local session gates. Never count refused ingress attempts as usage or activity. Report running request windows in `activity[]`; on close include a span from `openedAt` to `at`, a reason, `wakeId`, request count, and byte counts as base-10 integer strings when measured. Draining reports only work accepted before the drain gate closed. Do not manufacture bytes or infer them from response headers. `RemoteEventBatchSchema` permits older lower-precision reports, but this app should send the fields it actually measures.

Persist each outbound batch and its chosen `Idempotency-Key` before send. Retry an unchanged batch with the same key after timeout, restart, or lost response; change the key only when contents change. The published response `{ accepted: 0 }` can mean a previously accepted batch or an empty batch, so treat the durable local batch record and the request's nonempty content as the source for retirement. A refused or failed batch retains its key and retries according to the refusal/retry policy. Bound the queue and expose a safe operational error if reporting cannot drain; never block local withdrawal on reporting. Shutdown cancels SSE, stops new managed ingress, drains/ends the listener within the active deadline, and leaves unsent activity/ack records for restart recovery.

## Open contract decisions

- Enrollment request schema, consent-version source, person-session ceremony from the local app, lost-response recovery, and DELETE subject/authorization.
- Ingress proof-header name, provisioning/rotation, validation and edge stripping rules, including duplicate rejection.
- Whether the service offers anything beyond SSE; if so, publish it before implementation. Confirm reconnect/redelivery and lease-expiry semantics for durable acknowledgements.
- The issue route promises idempotent replay while credential `value` is described as returned once. Confirm whether a retry after a lost issue response returns that same value, a new issuance, or a recoverable reference; rotation crash recovery depends on this answer.

No public contract change is assumed by the local `CloudAuthority` type, config migration, or shared client state. Contract proposals belong in an issue labeled `cloud-contract`; the service owner's deployed acceptance is a later gate, not evidence supplied by this specification.
