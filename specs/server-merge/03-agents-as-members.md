# Agents as members: design note for step 2 (DOR-2876, C4)

**Status:** Draft for review. No code lands until Dorian approves this note.
**Date:** 2026-10-15
**Carries out:** decisions D3 and D10 and "Step 2: agents become members" in [02-specification.md](02-specification.md); row C4 of [`everything-is-a-space`](../everything-is-a-space/02-specification.md).
**Surveyed at:** `b0cada05ec` (migrations up to 0039, `apps/community/src`).

## In one paragraph

Each agent gets a `members` row of kind `agent` that **reuses the agent's id**, so the agent's member id and agent id are the same value. Every message gets `author_member_id`, and agent messages keep `author_agent_id` set to that same value. Because the ids match, every response apps parse today comes out unchanged without touching the code that builds it. The real work is the queries: 148 statements read or write `members`. 33 of them can reach an agent row and must name the kinds they want. Four places turn "the author" into "the person responsible" and would quietly start pointing at the agent instead of its owner. The build is three PRs. Only the second one is a one-way door.

### Findings that make this harder than the ticket reads

1. **`members.user_id` has no account for an agent.** `members_user_presence` would refuse an agent row. It must gain "or kind is agent".
2. **Migrations run at boot, all in one transaction** (`migrate.ts`, `main.ts:50`). A backfill there holds its locks until the server starts. Batching inside it buys nothing.
3. **The deferred owner trigger blocks later DDL.** After inserting into `members`, any `CREATE INDEX` or `ALTER TABLE members` in the same transaction fails with "pending trigger events". Found by running the draft. All DDL on `members` must come before the insert.
4. **Four places turn "the author" into "the person responsible"** with `COALESCE(author_member_id, owner)`. After the backfill they would pick the agent's own row, not its owner. Report actions (mute, ban, remove: `moderation/reports.ts:122,127`), direct removal ranking (`routes/community/removals.ts:216`), and the post-check worker and its per-owner cap (`decisions/worker.ts:133`, `decisions/record.ts:171`). Examples: a person could no longer remove their own agent's message, and an admin could remove a message by an admin's agent, which today is refused. Nothing would error.
5. **The member directory hard-codes `kind: 'human'`** (`routes/community/members.ts:193`). An unfiltered agent row would appear as a person with role "member".
6. **Several routes look a member up by an id from the request.** These are ownership transfer, ban, mute, unmute, role change, remove, add to channel and the host's per-member limit. With shared ids, an agent's id would find a row. Without a kind filter an agent could be made owner, admin, banned, or added to `channel_members`, where every roster then lists it as a person.
7. **The v2 export would turn unreadable mid-build.** It writes `author_member_id` straight from the column. After the backfill an agent message has both columns set, and the v2 importer rejects that row (`imports/v2-rows.ts:181`). So the v2 exporter must hide the new value in the same PR as the backfill.
8. **The import's mention resolver joins `members` and `agents` on one id** (`imports/v2-writers.ts:336`). With shared ids both match, the mention-target CHECK fails, and the import stops. Its "no id is both" clash check (`:115`) assumes the old shape too.
9. **The ticket's "admins can remove or mute any agent" is not today's rule, and today's rule stays** (Dorian, 2026-10-15). Today the owner may remove any agent, an admin only an ordinary member's agent, and a member only their own (`agents/enrollment.ts` delete route). An agent cannot be muted on its own: a mute is on a person and covers that person's agents, and an admin may mute only an ordinary member. A message an agent wrote is ranked as its owner's for removal.
10. **An older image would still boot on the new schema.** Its `migrate()` skips unknown versions without complaint. On the migrated schema its agent posts fail the new CHECK, which is loud. Its member directory, member cap and host usage would count agents, which is quiet. Separately, `backout.ts:25` groups members by `user_id`, and agent rows (like erased husks today) have none.

### How agent messages are written today

An app enrols an agent with its connection grant (`POST /agents`, `agents/enrollment.ts`). The server stores a hashed agent key (`agent_credentials`). The agent posts with that key. The post sets `author_member_id` for a person and `author_agent_id` for an agent, never both (`routes/community/entries.ts:246`, `:247`); PR 2 makes it set `author_member_id` for both. The row the post answers with already uses the poster's id as `author_member_id` (`:473`). Responses already call the agent's id a member id: enrolment returns `memberId: row.id` (`enrollment.ts`), rosters return the agent id as `memberId`, and entries return `COALESCE(author_member_id, author_agent_id)` as `authorMemberId` (`content/entry-projection.ts:8`).

### Draft migration (the one-way part, PR 2)

Tested on a copy of a seeded database. Order matters (finding 3).

```sql
-- Refuse before changing anything if the data cannot take the new shape.
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM agents a JOIN members m ON m.id=a.id) THEN
    RAISE EXCEPTION 'An agent id is already a member id.'; END IF;
END $$;
-- (kind, owner_member_id, the nullable handle, their CHECKs, FK and indexes come from PR 1.)
INSERT INTO members(id,community_id,user_id,display_name,handle,role,active,created_at,
  removed_at,erased_at,kind,owner_member_id)
SELECT a.id,a.community_id,NULL,a.display_name,NULL,'member',a.active,a.created_at,
  a.revoked_at,owner.erased_at,'agent',a.owner_member_id
FROM agents a JOIN members owner ON owner.id=a.owner_member_id AND owner.community_id=a.community_id;
ALTER TABLE agents ADD CONSTRAINT agents_member_fk FOREIGN KEY (community_id,id)
  REFERENCES members(community_id,id);
-- mirror trigger on agents (decision 6) goes here
ALTER TABLE entries DROP CONSTRAINT entries_exactly_one_author;
UPDATE entries SET author_member_id=author_agent_id WHERE author_member_id IS NULL;
ALTER TABLE entries ADD CONSTRAINT entries_one_author CHECK (author_member_id IS NOT NULL
  AND (author_agent_id IS NULL OR author_agent_id=author_member_id));
ALTER TABLE entries ALTER COLUMN author_member_id SET NOT NULL;
-- One-way: no older release may run on this (decision 11).
UPDATE community_compatibility_floor SET min_migration=GREATEST(min_migration,42);
```

**How long it takes.** On Postgres 16 on a laptop, a space with 200 people, 300 agents and 500,000 messages (300,000 by agents, 309 MB) migrated in about 9.4 seconds. The guards took 0.2 s, the member rows 4 ms, and the message backfill 9.0 s (about 30 µs per agent message). `SET NOT NULL` took 0.2 ms. It grows with the number of agent messages, so a million agent messages is roughly 30 seconds. The server does not serve until it finishes, and `entries` is locked for that time. The spec expects the official space to hold mostly staff and test data, but its size is not visible from this repo; the rehearsal measures it. After the upgrade, run `VACUUM ANALYZE entries`, because each agent message now has a dead copy. If the rehearsal takes over 60 seconds, we revisit before the release. The built migration (PR 2, 0042, with its trigger) took 18.3 s for the same seed on 2026-10-16, on the same laptop under heavier load; the 9.0 s and 18.3 s runs bracket the cost.

**What an older image does.** Not supported (decision 11). If one is started anyway: agent posts are refused by the CHECK, enrolment still works because the trigger lives in the database, and the member directory, member cap and host usage count agents as people. The only way back is point-in-time restore.

**Agents and people sharing a handle.** People and agents keep handles in separate tables today (`members.handle`, `agents.handle`), so a space could hold a person and an agent with the same handle. In practice both also sit in `community_handles`, whose key is one handle per space, so such a pair should not exist. It does not matter either way: the agent's member row takes no handle (decision 13), so nothing can clash and PR 2 needs no guard or rename for it. The rehearsal still counts the pairs, read-only, to confirm `community_handles` matches both tables:

```sql
SELECT count(*) FROM agents a
JOIN members m ON m.community_id=a.community_id AND m.handle=a.handle;
```

## Export and import

- **Today:** format 1 (one manifest, `imports/restore.ts`) and format 2 (data files, `exports/tail.ts:169`, `imports/v2-*.ts`). Schemas are in `packages/shared/src/community-export-archive.ts`. The database allows `export_archives.format_version` 1 or 2. `imports/archive.ts` reads 1 or 2 and refuses anything else as `IMPORT_VERSION_UNSUPPORTED`.
- **Format 3 (PR 3):** `CommunityExportManifestV3Schema` with `version: 3`. Member rows add `kind` and `owner_member_id`; agent member rows carry the agent id, role `member` and no email. Entry rows always have `author_member_id`. A personal export holds the requester's row and their agents' rows. A migration widens `export_archives_format_version` to 1, 2, 3. Unfinished format 2 export jobs restart from nothing as format 3, as erasure already restarts them; finished format 2 archives stay downloadable as they are.
- **Old importers:** formats 1 and 2 import as today. The trigger creates each agent's member row when its `agents` row is written, and the entry writers set `author_member_id` to the agent's derived id for agent messages. **Format 3 importer:** the format 2 reader plus the new fields. Person rows go through `writeMembers`. Agent rows are checked against the `agents` collection (same id, owner, handle, name) and left to the trigger.
- **Outside this repo:** nothing in `apps/server` or other packages reads the export format. Readers we can see: `apps/community` and its tests, and `packages/shared`. The host API exposes the format in the import report (`CommunityAdminImportReportSchema.manifestVersion`, a strict `1 | 2`) and in the takedown evidence record (`archive.manifestVersion: z.literal(2)`). Whether Cloud reads either is a question for Cloud.

## Owner rules, as today

- **Only the owner adds an agent:** unchanged. Enrolment needs the owner's connection grant; the trigger refuses an owner who is not a person.
- **The owner's mute and rules acceptance cover their agents:** unchanged. `moderation/posting.ts:34` reads the owner's row, and the CHECK keeps agent rows from holding their own.
- **20 agents per owner:** unchanged. `effectiveAgentLimit` counts `agents`, with `member_limit_overrides` keyed to the person.
- **Admins and agents:** today's rule is kept exactly (finding 9).
- **Removing or erasing a person:** removal already deactivates their agents (`members.ts:65`, `:133`) and the trigger follows. Erasure husks their agents (`erasure.ts:476`), the trigger copies the name, and erasure stamps `erased_at`. Account erasure runs each membership through the same path.
- **Banning an owner** removes them, which deactivates their agents as above. An agent itself can never be banned.

## Cloud-facing items to agree before building

1. **Host usage and limits:** `activeMembers` and the member cap count people only, as today. `activeAgents` is unchanged. The per-member limit route keeps answering 404 for an agent id.

4. **Takedown evidence:** a whole-space evidence record's `archive.manifestVersion` becomes `3`.
5. **Upgrade:** forward-only, run at boot in one transaction. Size it by the number of agent messages (about 30 µs each on a laptop). The way back is point-in-time restore. From this release on, a release refuses to start once a one-way migration has raised the compatibility floor past what it knows, and names the migration it needs; an additive migration never blocks a rollback.
6. **Unchanged:** the erasure journal and its scope, the image, its start command, settings, `/health`, `/metrics`.
