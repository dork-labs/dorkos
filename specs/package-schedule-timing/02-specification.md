# Let a person change when a package's schedule runs

**Status:** Approved
**Author:** Claude Code
**Date:** 2026-09-24

## Overview

A schedule that came with an installed package gets a person's own timing, kept by DorkOS on the schedule's row instead of in the package's file. The package's timing stays the default; the person's cron or timezone, when set, wins; "Reset to the package's default" goes back. Every place that reads a schedule's timing reads the one that wins, and the approval a person gave follows it.

## Background / Problem Statement

A package's schedule can be approved and switched on and off from the Schedules page (FB-26), but its timing cannot be changed there. `PATCH /api/tasks/:id` and `tasks_update` answer 409 `schedule_package_owned` to any `cron` or `timezone` change (`lifecycle/update-task-file.ts:181-208`), because the only place the timing lived was the package's own SKILL.md, which DorkOS never writes. The sync then copies the file's cron onto the row on every pass (`task-store.ts:1260, 1338`). The one way to change it — editing the package's file by hand — is shared by every agent that installed the package, is wiped by the next update, and re-parks the schedule for approval. DOR-2300 (flow's tick cadence) needs a person to be able to run `flow-drain` at their own pace without forking the plugin.

## Goals

- A person can change the cron and the timezone of a package's schedule from the Schedules page, and the change survives syncs and package updates.
- They can see that the timing is theirs, what the package's own timing is, and put it back in one click.
- A person's change keeps the schedule approved. An agent's change stops it at once and asks the person.
- Every reader of a schedule's timing — the scheduler, the arm gate, the bypass keep-grant, the approval record, the parked-schedule preview — uses the timing that actually runs.

## Non-Goals

- Changing anything else about a package's schedule (prompt, name, permission level) from DorkOS.
- A timing override for a schedule whose file DorkOS can write. Its timing is still edited in its own file.
- Pointing flow's dials page at the Schedules page (DOR-2300, `dork-labs/marketplace`).
- The `scheduling-tasks` operating skill (a pack version bump collides with every pack PR in flight; the tool's own description carries the new argument).

## Technical Dependencies

- `drizzle-orm` 0.45 / `drizzle-kit` 0.31 (existing) for the column and the generated migration.
- `croner` via `TaskSchedulerService` (existing) — unchanged, reads the mapped Task.
- No new libraries.

## Detailed Design

### Data model (`packages/db/src/schema/tasks.ts`)

Two nullable TEXT columns on `pulse_schedules`, next to the ones they stand in for:

- `cron_override` → `cronOverride` — the person's cron, `''` meaning "on demand". NULL means "the file's cron runs".
- `timezone_override` → `timezoneOverride` — the person's IANA timezone. NULL means "the file's timezone".

`cron` and `timezone` keep their meaning: what the SKILL.md says. The sync keeps writing them and never touches the overrides. Migration generated by `drizzle-kit generate` (lefthook `db-migrations`); existing rows read NULL, so nothing changes on upgrade.

### Effective timing (`apps/server/src/services/tasks/schedule-timing.ts`, new)

One pure module every reader and writer of the four columns goes through:

- `effectiveTiming(row)` → `{ cron, timezone }`: override when non-null, else the column.
- `effectiveContentKey(row)` → `scheduleContentKey({ prompt, cron: effective cron })`.
- `timingColumnWrites(row, request, landsOn)` → the column updates for one update request:
  - `resetTiming: true` → both overrides NULL.
  - `landsOn: 'row'` → `cron`/`timezone` go to the override columns; a value equal to the file's is stored as NULL (choosing the package's own timing is not a custom timing). `cron: null` stores `''`; `timezone: null` stores NULL (the file's).
  - `landsOn: 'file'` → `cron`/`timezone` go to the default columns exactly as today, AND clear the matching override, because a timing written to the file is the new timing and an override left behind would silently beat it.
- `conflictingTimingRequest(request)` → a refusal sentence when `resetTiming` arrives with `cron` or `timezone`, else null.

### Row → Task (`task-row-mappers.ts`)

`mapTaskRow` sets `cron`/`timezone` to the effective values, plus:

- `defaultCron`, `defaultTimezone` — the raw columns (the file's timing).
- `timingOverridden` — `cronOverride !== null || timezoneOverride !== null`.

Because the registrar (`task-registrar.ts:89`), the scheduler (`task-scheduler-service.ts:677`), the parked preview (`routes/tasks.ts:297`), the run's system prompt (`task-append.ts`), relay dispatch and the approval card all read a mapped Task, they read the effective timing with no change of their own.

### Raw-row readers (`task-store.ts`, `file-sync-gates.ts`)

The four places that read the columns directly switch to the helpers:

- `recordApproval` — keys the grant off `effectiveContentKey(row)`.
- `backfillApprovalGrants` — same.
- `rekeyMigratedFile` — compares the row's effective key against the rewritten file's content with the row's cron override applied, and stamps that key.
- `FileSyncGates.resolve` — `approved.cron` is the row's effective cron and `incoming.cron` is the row's override when it has one, else the file's. So `keepsApprovedBypass` (`schedule-permission-clamp.ts:139`) and `resolveFileArmStatus` (249) both compare effective content, and so does `keepsRowEnabled`, which follows the arm verdict. The refusal log keeps keying on the file's own content.
- `upsertFromFile` — the un-pause branch's grant uses the effective incoming key.

Consequence, as designed: a package update that changes only the default cron of an overridden row does not re-park it (the effective content is unchanged); a changed prompt still does.

### The approval key

Unchanged: `[prompt, cron]`, with cron meaning the effective value. Timezone is not in the key, so a timezone-only change needs no re-key and never parks.

### Update request (`packages/shared/src/schemas.ts`)

- `TaskSchema` gains `defaultCron: string | null` (default null), `defaultTimezone: string | null` (default null), `timingOverridden: boolean` (default false). `cron`/`timezone` are documented as the timing that runs.
- `UpdateTaskRequestSchema` gains `resetTiming: z.literal(true).optional()` — "put this schedule back on its package's own timing".
- `task-write-policy.ts`: `resetTiming: 'agent-writable'` (a timing choice, not a power one; an agent's reset that changes what runs still parks it).

### What an edit may write where (`task-file-update.ts`, `lifecycle/update-task-file.ts`)

- `ROW_ONLY_WHEN_PACKAGE_OWNED` becomes `{enabled, cron, timezone}`.
- `applyTaskFileUpdate`'s success carries `timingLandsOn: 'file' | 'row'` — `'row'` only from the package-owned branch.
- The package-owned refusal sentence now says what still works: "You can switch this schedule on or off, or change when it runs, here".

### The two update doors

Both run the same sequence: refuse a conflicting timing request (400 / tool error), validate the merged timing (existing), clamp (existing, now also counting a reset that changes the cron), write the file (existing), `store.updateTask(id, data, { timingLandsOn })`, then — when no file was written — `store.settleTimingChange(id, previousKey, { trusted })`:

- The effective key did not change → nothing.
- **Trusted** (the caller cleared the agent bar) → if the grant covered the previous effective content, it is re-keyed to the new one. The person's edit is itself the approval (the design's "re-approves in the same act"). Keyed on the grant, not on `status`, so a switched-off or paused schedule the person approved stays approved when it comes back.
- **Untrusted** (every MCP call; a PATCH carrying an agent token) → an `active` row is parked at once: `status: pending_approval`, grant withdrawn, `reason` = "An agent changed when this schedule runs, so it is waiting for you again. Check the new timing, then approve it or change it back.", `reasonSource: 'dorkos'`. A row that is not active keeps its status; its grant no longer matches, so nothing can arm it without a person.

Why at once (deviation from the design, which left it to the next sync): no file is written, so no watcher fires; for up to five minutes the row would stay `active` and the registrar would run the agent's timing on a schedule nobody approved at that time; and the sync's own sentence ("this schedule's file changed") would be false.

After the park:

- `PATCH` — the existing "entered `pending_approval`" edge raises `schedule.parked` (the standing condition + escalation clock). That edge records `data.reason` only for an operator's own park (`data.status === 'pending_approval'`), so an agent cannot put its words over DorkOS's.
- `tasks_update` — raises `schedule.parked` the same way, and replies `needsReapproval: true` with a note written for this case: the schedule has already stopped and is waiting on the person.

### `tasks_update` (MCP, both servers)

- New argument `resetTiming: z.literal(true).optional()` with a description; forwarded in the patch.
- The tool description mentions that a package's schedule accepts a new cron or timezone, kept by DorkOS, and that `resetTiming: true` puts it back.

## User Experience

On the Schedules page (`TaskRow`):

- The timing line shows the effective timing in words, as today. When `timingOverridden`, it ends with "· Your timing".
- The expanded row shows one line under the file path: "The package runs this {default timing in words}, {timezone}." and a small "Reset to the package's default" button.
- The row's actions menu gains "Reset to the package's default" when `timingOverridden`.
- Reset sends `{ resetTiming: true }`; success toasts "Back on the package's timing"; failure uses the shared mutation toast.

Changing the timing: Edit → Schedule → change "When it runs" or "Timezone" → Save. The edit form now sends only what the person changed, so a timing change on a package schedule is a timing-only request and lands; changing the prompt of a package schedule still answers the existing refusal, which now also says the timing can be changed here.

Mobile/tablet/desktop: the marker is inline text in the existing timing line (wraps with it); the expanded line and button stack under the file path; the menu item is in the existing menu.

- **Write policy**: the existing drift test fails until `resetTiming` has a verdict.
- **Integration, real package on disk** (`package-schedule-timing.integration.test.ts`, the FB-26 fixture): a timing change lands on the row and never writes the package's file; survives the next sweep; survives a package update that changes the default cron; a package update that changes the prompt still parks; reset restores the default.
- **Route** (`routes/__tests__/tasks-package-timing.test.ts`): trusted PATCH of cron on a package schedule → 200, effective cron, defaults, flag, still active, registrar registered the new cron, the next resync keeps it active; agent PATCH → `pending_approval` with the DorkOS reason; `resetTiming` + `cron` → 400; parked row's `nextRuns` preview uses the override.
- **MCP** (`task-tools-package-timing.test.ts`): `tasks_update` cron on an approved package schedule → parked at once, `needsReapproval` + the timing note, package file untouched; `resetTiming` on an overridden row whose default differs → parked; conflict → tool error.

Every test carries a purpose comment and is mutation-checked against the line it guards.

## Performance Considerations

Two nullable columns and a `??` per mapped row. No extra queries: every writer already reads the row it writes. `settleTimingChange` is one read and at most one write, only on row-only updates.

## Security Considerations

- The arm gate and the bypass keep-grant compare effective content, so an override cannot smuggle new work past either: a changed prompt still parks, and an override can only change WHEN the approved prompt runs.
- An untrusted timing change never runs before a person sees it (immediate park), closing the window the sync-only design left open.
- `resetTiming` is agent-writable and treated exactly like a cron change for approval purposes.
- Nothing is ever written into a package's own files.

## Open Questions

~~1. Should an agent's row-only timing change wait for the sync to park it, as the design says?~~ (RESOLVED)
**Answer:** No — park in the same request. **Rationale:** no watcher fires for a row-only write, so the new timing would run unapproved for up to five minutes, and the sync's reason would say a file changed when none did.

~~2. How is a reset spelled?~~ (RESOLVED)
**Answer:** `resetTiming: true`; combined with `cron`/`timezone` it is refused. **Rationale:** `cron: null` already means "on demand".
