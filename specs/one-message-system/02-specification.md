**Words.** A **conversation** is a log of entries with members (people, agents and outside senders) and threads. Today a conversation is a room: `rooms`, `room_members` and `room_entries`. An **entry** is one message in the log. A **session** is one agent's runtime transcript and state, private to that agent. A **seat** is one agent in one conversation: which session it works in (`room_sessions`) and how far it has read (`room_members.last_read_seq`). A **run** is one attempt of a turn, recorded in step 5's run record (`turn_runs`). A **room-style conversation** is one where a post is an entry at once: a channel, a thread, a Telegram or Slack chat, an object's thread. **Words that wait in a composer** are a message that waits as a `session_message_queue` row until a turn takes it: a person's 1:1 message, an agent's `chat_send`, a mini app's message. An **outside window** is a place outside DorkOS where a conversation is also shown: a Telegram chat, a Slack channel, an outbound webhook. **Relay** means the message bus in `packages/relay` and `services/relay`. It is a different thing from **the session relay** (`services/core/session-relay`, `services/core/hub-relay`), the sealed channel between a person's DorkOS in the cloud and their Mac, which item 13 covers and this spec does not touch; no non-test file in those two folders imports Relay.

## The short version

- **Every word a member reads is an entry in one conversation's log.** One kind of chat at a time, the words move out of the places they live today (a runtime's transcript as the only record, `chat_messages`, a mini app's send rows, Relay's Maildir) into `room_entries`, which stays where it is.
- **A session stays private.** A runtime's transcript is the agent's working context. No member reads another agent's session as the record.
- **Delivery is a record kept with the run.** Each run lists the entries it was given. "Delivered" means a run the runtime accepted listed the entry. "Replied" means such a run wrote an answer, or an entry names it as its parent. "Failed" means the run that held it ended before it started; "may not have arrived" means it ended after it started and before the runtime's first event. The list lives beside step 5's run record, in one place.
- **No double feed.** A turn is given only the entries its seat has not read and its own session did not write.
- **Two ways in, one way to start a turn.** In a room-style conversation (a channel, a thread, a Telegram or Slack chat) a post is an entry at once and the conversation's dispatcher starts runs through the turn port, as rooms do today. Words that wait in a composer (a person's 1:1 message, an agent's `chat_send`, a mini app's message) stay queue rows a person can see and remove; when a turn takes a row, the space side writes the entry from that row's own words and its own records. On a Mac the entry is written before the runtime reads the words; for an agent on another computer, whose queue the home keeps, the home writes it from its own row when the `started` fact arrives. Nothing in Relay starts a turn.
- **Relay keeps one job.** It carries messages to and from outside windows, with their retries, rate limits, failure handling and receipts for what left. It gives up starting turns, its Maildir store, its own map of agent sessions, agent subjects and task subjects.
- **Nothing new in Maildir.** From the first step, a count of the places that can put words into Maildir may only fall. Maildir retires when the count is zero, and its files move to a dated archive folder with one command to read them. Nothing is imported.
- **The order.** First the count and the delivery record (they need the least), then outside chats, agent-to-agent messages, mini app and object threads, then Relay's agent and task paths go, then Maildir retires, and 1:1 chats move last, as a conversation kind of their own.

## Goals

- One answer to "what was said here, by whom, and did the other side get it" for every kind of chat: the log for the words, the delivery record for "did it arrive".
- Every turn for a message starts through the turn port, with a run record, and the run lists exactly the entries it was given.
- Telegram and Slack chats under every binding strategy have a log, and their words stay marked as words from outside.
- Relay stops storing words and stops starting turns; Maildir retires with nothing lost.
- Nothing a person or an agent can do today stops working on upgrade, and no connection that works before a step stops working after it.
- Each step ships alone, is 5 points or less, and leaves the app working.

## Non-goals (out of scope)

- **Moving the log to the space store.** That is roadmap item 16. This spec neither waits for it nor does it (M9).
- **Who may message whom.** This spec does not change it (§4.6). Block and mute are later work.
- **Messages between spaces**, and a person messaging a person.
- **Email.** The draft's email design (its §9) stands as a design; nothing here builds it.
- **Retention.** The log is never trimmed by this spec. It says what grows and how to measure it (§11.6), and names the decision as later work that comes before the 1:1 step.
- **Loop limits for agent-to-agent messages.** They stay as they are until DOR-2745 decides.
- **The A2A rebuild** (item 10's D12) and **the inbound webhook's removal** (item 9's O6). This spec needs both and redoes neither.
- **The session relay** between a person's DorkOS in the cloud and their Mac (item 13). It is not Relay.
- **A backfill of runtime transcripts into the log.** A turn run outside DorkOS (a bare command-line resume) writes no entries, and no transcript is copied into a log (§11.1, §11.5).
- **The frozen space code** (`services/spaces`, `apps/space`, the community wire, `services/spaces/migrate.ts`) (M10).

### 1.4 Who may message whom today

A person messages an agent in a Direct chat, any 1:1 chat, a room, a Telegram or Slack chat bound to it (a binding's `dmPolicy`, default `'allowlist'`, `routes/relay-adapter-grants.ts:78`, and its approver list), A2A (off by default), and `POST /api/relay/messages`. An agent reaches a person with `relay_notify_user`, a room post or a notice. An agent reaches another agent with `chat_send`: an agent id first, else a chat whose origin is in `CHAT_SENDABLE_ORIGINS`, "deny by default" (`session/chat-messages/chat-target.ts:1-25`). Two people message each other only in a room or on a space server. No block or mute exists.

```
 the agent's reply: an entry in the same log, carrying its run id
   │
   ▼
 the chat bridge carries it to the outside window through Relay (retries, limits, receipts)

 Relay: connections to outside windows only. No turn starts, no Maildir, no session maps.
```

## 4. The log and the entry

### 4.1 What an entry is

An entry is a row of `room_entries` (`packages/db/src/schema/rooms.ts:636`). It already has an id, a per-conversation `seq`, one author (`author_id`), a kind (`post` or `notice`), a body, mentions, the session that wrote it (`session_id`), a dispatch id kept off the wire (`dispatch_id`), the marks of the turn that wrote it (`turn_marks`), and a thread relation (`parent_entry_id`, `thread_root_entry_id`). This spec adds two columns, both null for every row written before, in one migration under `packages/db/drizzle/` (MS2):

- **`run_id`**: the run that wrote the entry, for an entry an agent writes in a turn. With the run's `runtime_turn_ref` it is the link from a reply to its turn that ADR `261017-211859` asks for ("a dispatch id plus a runtime anchor"): the run is the runtime-neutral turn id that did not exist when the ADR was written.
- **`origin_json`**: the origin an entry carries when its words came through a composer: `{ kind: 'chat-message', sendingChatId, ceiling }` for an agent's `chat_send` (the sending chat and the sending turn's level, server-written, never typed), `{ kind: 'extension-message', appId }` for a mini app's message, and `{ kind: 'chat', queueMessageId }` for a person's 1:1 message. The fence nonce is not stored; it is made fresh each time the words are given to a turn, as today.

**Kinds kept off the shared enums.** `RoomKindSchema` (`channel`, `dm`) and `AuthorKindSchema` (`human`, `agent`, `system`) in `packages/shared/src/room-schemas.ts:46`, `:51` are reused by the community contract (`packages/shared/src/community-adapter.ts:50`, `:453`, `:491`, `:655`), which is frozen. So the `chat` conversation kind (MS19) and the `app` author kind (MS13) are defined in a local type that widens the shared one, for this computer's store, and the shared enums do not change. Each kind lands with its own migration (MS13, MS19). Every reader that parses a room's or an author's kind with the shared schemas keeps working by one rule: **a `chat` room is never returned through a surface that uses the shared room schema** (it is a 1:1 chat and is shown through the chat surfaces), and **an `app` author never reads as the system's own voice**: on this computer's own surfaces its entry carries the local kind and shows as a mini app; where only the shared kinds exist, it is given as `system` with its name reading "<name> (mini app)". An entry written when a turn takes a row takes everything but its words from the space side's own records: its author and origin from the run's stored origin and who asked (`origin_json`, `asked_by_ref`) and, for an agent's message, the chat-message row; its marks and level from the same; its time from the run's `created_at`, when the message was accepted. Its words are the row's own words (§5.2). Its `seq` is the next in the conversation.

**A row can change after its entry was written.** A pause puts a taken row back in line (step 5's transitions 14 and 15), where its sender may edit or remove it. Two columns, added in MS12's migration, record that: `revised_at` (an edit after the take writes a revision of the entry, with the new words; readers see the new words and "edited") and `withdrawn_at` (a removal marks the entry withdrawn; its words stay, because the log is never trimmed: readers of the conversation see "Maya withdrew this message", and a reader who may read the turn that took it (§4.5) may open the words). The resumed turn is given what the row holds then.

### 4.2 The seat and its read cursor

A seat is one row of `room_sessions` (`rooms.ts:1024`, agent and conversation to session) and the agent's `room_members.last_read_seq` (`rooms.ts:520`, with `joined_seq`). The cursor says what the seat has not read. It moves at hand-over (§5.2), before the runtime is asked, so it cannot prove delivery; the delivery record does (§5). A person's own read state stays in `read_cursors` (`packages/db/src/schema/read-cursors.ts:64`), apart from seats.

### 4.3 The mark for words from outside, and a run's level

An entry from outside is one whose author is an outside sender. **A run's mark and level start as those of the entry or row that starts it**: a run started by an outside entry carries the outside mark, by the rule that exists for room turns (the `room` origin's `externalAuthor`, `packages/shared/src/turn-port.ts:106`), and runs no looser than the binding it came through allows (its `permissionMode` and the binding's own level, as today in default mode). **Marks only add, and the level only tightens.** The window (§4.4) may hold unread entries the seat was not addressed by, kept as context: for example an outside post in a channel that names another agent. When it holds an entry with a mark the run does not have, or a stricter level, the space side adds that mark to the run, and takes the stricter level, at hand-over, before the turn is given the words. Moving a chat from default mode to a conversation must not change the level or the marks of the turn its message starts; MP5 compares them cell for cell.

### 4.4 No double feed, exactly

1. **When a room-style entry starts a run.** A new entry starts a run for a seat that should answer unless the seat's **newest** waiting run (one not yet handed over) has the same mark and level as the entry; then it starts nothing, and that run's window takes it. The dispatcher never starts a seat's run for an entry its own agent wrote, from whichever chat.
2. **The window, in a room-style conversation.** At hand-over (§5.2), a run's entries are the seat's unread entries (`seq` above the larger of `last_read_seq` and `joined_seq`), minus every entry whose `session_id` is this seat's session, minus every entry that is the source of another run of the seat, and ending just before the source entry of the seat's next waiting run. The window always includes the run's own source entry. Today rooms exclude by author (`rooms/room-store.ts:1239`); MS3 changes it to the session, because an agent works from many chats and an entry it wrote from another chat is news to this seat, as context.
3. **Walked through: three posts, the middle one from outside.** Maya posts P1, Priya posts P2 from Telegram (marked), Maya posts P3, while Ana's seat is busy. P1 starts R1 (unmarked). P2 differs from R1, the newest waiting run, so it starts R2 (marked). P3 differs from R2, now the newest, so it starts R3 (unmarked). At hand-over R1 is given {P1} (its window ends before P2, R2's source), R2 is given {P2}, R3 is given {P3}. No run meets an entry whose mark differs from its own, and no window is empty. Had P2 come from Maya, it would have started nothing and R1 would have been given {P1, P2}.
4. **Walked through: a run cancelled before hand-over.** In the example above, R2 expires before it is handed over. P2 reads `failed` with the reason and **Retry**. R1 is still given {P1}, and R3 {P3}: P2 is the source of another run, so no window takes it. No entry is stranded unread without a status.
5. **The cap.** The window keeps the room's cap (`ambientMaxEntries`, `rooms/room-context.ts:481`), always keeping the run's own source entry. Entries past the cap that the window skips are listed in the delivery record as `skipped`, so the record says they were not shown, and the cursor still moves past them, as today.
6. **Words from a composer.** A run's entries are the rows its turn took, written as entries when the turn takes them (§5.2). The queue already gives each row to one turn; nothing else is added. Entries in a conversation whose words wait in a composer (an agent-to-agent conversation, a mini app's, a 1:1 chat) never start a run through the room dispatcher.
7. **Once per seat.** An entry is given to a seat only by the run whose hand-over listed it. A run that ended after `started` and before `delivered` is not replayed (step 5 §7.3): its entries read "may not have arrived", and the sender is told by its own path (a person's words come back as a restored draft, and sending that draft is the Retry for that entry and writes no second entry; an agent's sender through the report path; a room through `post_room_outcome`). A run cancelled before `started` never had its words given to the runtime: its entries read `failed`. In neither case is anything given again by itself; only **Retry** does that (§5.3). The cursor never moves backwards.
8. **A pause.** Step 5's transitions 14 and 15 put a started run back in line, and its words are given again on resume. That second showing is the same run's: it reuses the run's rows and lists none, and the entries read `queued` again until the run's `delivered_at` is set again. For words from a composer, the row is back in line and its sender may change it: an edit writes a revision of the entry, a removal marks it withdrawn (§4.1), and the resumed turn is given what the row holds then.
9. **A new session gets a recap, not a rewind.** When a seat's session changes (a reset, a bridge adopting a chat, a `stateless` binding's next message), the cursor stays. The new session's first run gets a bounded recap from the log, listed as `recap`, which changes no entry's status. A `stateless` binding gets no recap (§11.1).
10. **A backfill never feeds.** A step that writes old messages as entries (MS11, MS20) writes without starting a turn and moves every seat's `last_read_seq` and `joined_seq` past what it wrote.
11. **A joined row and a steered row.** A row that joins another row's turn (a drain join, `session/message-dispatcher/join-chat-rows.ts:39`, which merges the joined rows' words into the head row at `:75`) and a row sent into a running turn (a steer, `finishSteer`, `session/message-dispatcher/pump.ts:79`) have no `started` fact of their own: their runs end `superseded` (step 5's transition 6, written through the facts feed's `supersedeRow`, `session/turn-port/facts.ts:167`). On a Mac the in-process feed passes each row's own words: the `started` report carries the head row's words as they were before the join merged others into it, and the feed call that ends a joined or steered row carries that row's id, the run it went into, and its own words. So each row becomes exactly one entry with its own words, listed on the run that took it (`new` for a join, `steer` for a steer), and no words land twice. On another computer nothing joins or steers: the home keeps the queue (§5.2).

### 4.5 Who may read the turn behind an entry

A member who may read the conversation reads its entries. The turn behind an agent's entry (its run, and the session it ran in) is read only by a reader the existing rule allows: today, for a room's peek, a person who may see the room may ask which session each agent answers in (`GET /api/rooms/:id/sessions`, `routes/rooms.ts:222`, ids only, people only, an agent refused `PEOPLE_ONLY`), and then opens that session only if `canReadSession` lets them (`routes/audit-reader.ts:51`; on a Mac the owner reads every session, an agent only its own). This spec uses that rule for every conversation kind and changes nothing in it. For anyone else, "Show work" is absent, not disabled.

### 4.6 Who may message whom

This spec does not change it. A person and an agent in the same private space message each other as today (§1.4). Who may send to an agent directly is item 10's policy; who may do what in a space is item 12's; people messaging people is the space store's, which is frozen. For outside windows, a binding's `dmPolicy` and its approver list stay exactly as they are. Relay's access rules are removed only where a step shows nothing reads them (§8.1). Block and mute are later work.

## 5. The delivery record

### 5.1 Its fields, and where it lives

One new table beside the run record, `turn_run_entries`, in `packages/db/src/schema/runs/`, with its migration under `packages/db/drizzle/` (MS2). It is written only by the hand-over module (§5.2) and read only through `services/runs/run-store.ts`. One row for each entry a run was given:

| Column            | Type              | Meaning                                                                                                                                                           |
| ----------------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `run_id`          | text, not null    | The run (`turn_runs.id`)                                                                                                                                          |
| `conversation_id` | text, not null    | The conversation the entry is in (today a room id)                                                                                                                |
| `entry_id`        | text, not null    | The entry                                                                                                                                                         |
| `entry_seq`       | integer, not null | The entry's `seq`, so a range reads in order                                                                                                                      |
| `role`            | text, not null    | `new` (unread by the seat), `steer` (joined a running turn), `recap` (context for a new session; changes no status), `skipped` (past the window's cap; not shown) |
| `created_at`      | text, not null    | ISO 8601                                                                                                                                                          |

Primary key `(run_id, entry_id)`; indexes on `entry_id` and on `(conversation_id, entry_seq)`. It holds no words: the words stay in the entry.

The rest of the record is already on the run: **when the runtime accepted the turn** is the run's `delivered_at` (`turn-runs.ts:154`). "Accepted" here is step 5's choice of the delivered moment (its §12, choice 8): the first event the runtime emits for the turn after `turn_start`. A start the runtime refused never sets it. **Why it failed** is the run's `status`, `ending` and `ending_detail`. So the delivery record is the run plus its rows here, in one place, and it moves with `turn_runs` when step 5's child Q moves the run store.

### 5.2 How it joins the run: the hand-over

**One module owns it.** `services/runs/delivery/hand-over.ts` (a working name) is the only code that writes `turn_run_entries`, moves a seat's cursor, and turns a composer's row into an entry. It runs on the space side. It does not write the log table by itself: it calls the rooms store's own entry write in the same transaction, so the broadcast, the search index and the outbound bridge run after the commit as they do for any entry. Session and runtime code write nothing to the log or the run store; they report facts.

**Path 1, a room-style conversation.** The dispatcher starts a run with `source_ref` naming the entry and `conversationRef` (`{ conversationId, seatAgentId }`, a new optional field of `StartTurnInput`) naming the seat (§4.4, item 1). When the `start_turn` handler hands the run over, the hand-over module reads the window (§4.4, items 2 and 5), writes the rows, and moves the cursor, then builds the turn's words from those entries. A repeat of the hand-over for the same attempt (step 5 makes `start_turn` repeatable until `started`) reads the rows already written and never chooses again.

**Path 2, words from a composer.** The message is a queue row, and its run is started as step 5 starts it today; nothing about waiting changes. The entry's words are always **the row's own words**, and everything else comes from the space side's own records (§4.1): the author, origin, marks and level from the run's stored origin, who asked, and the chat-message row where one exists; the time from the run's `created_at`. Where the words come from:

- **On a Mac**, the in-process feed passes them. The `started` report for a row's own run carries the head row's words as they were before a drain join merged others into it; the feed call that ends a joined or steered row (`supersedeRow` today) carries that row's id, the run it went into, and its own words (§4.4, item 11). Each row becomes one entry; no words land twice. The words stay within `SESSION_RELAY_MAX_MESSAGE_LENGTH` (200,000 characters, `packages/shared/src/session-relay.ts:138`), the cap a start's content already has.
- **On another computer**, the home keeps the queue (step 8's `remote_chat_queue`), and nothing on the computer joins or steers. When the `started` fact arrives, the home writes the entry from its own row. A computer over the wire never supplies words for an entry; on that path the entry lands after the runtime may already have the words.

**A reported row must be real.** The hand-over module matches the row id it is given against its own run and chat (the run's `queue_message_id` and `session_id`, or, for a joined or steered row, that row's own superseded run and the run it went into), and refuses a report that does not match. An entry is unique on its row id, so a repeated report writes nothing.

The hand-over module lists the entry on the run that took it (`new`, or `steer` for a steered row) and moves the seat's cursor, in the same write as the run's transition. On a Mac that write happens before the runtime reads the words. A row removed before a turn takes it never becomes an entry: its run is cancelled as step 5 says (transition 5), and no reader but the sender ever saw it.

**Path 3, a report run.** When step 5's report path carries a reply back to the chat that asked (§11.2), the run it starts has the reply entry as its source. Its hand-over lists that entry as `new` and moves the asking agent's read cursor in the conversation past it, so the reply is never given to the sender twice. The effect that delivers the reply to the chat that asked commits in the same transaction as the reply entry, so a restart between them loses neither.

**An entry the agent writes** in a turn carries the run's id in `room_entries.run_id` (§4.1).

**One write today, and when the stores split.** Today the run record, the log and the cursor share `dork.db`, so the module's writes are one transaction. When `turn_runs` moves to the space store (step 5's child Q) and the log moves later (item 16), no claim here rests on one transaction across two stores: each row of `turn_run_entries` is unique on `(run_id, entry_id)` and written insert-or-ignore; an entry written from a row is unique on the row's id (`origin_json.queueMessageId`, or the chat message's id); and the cursor moves only forward (`setReadCursor` already keeps the larger value, `rooms/room-trigger/claim-collected.ts:288`), so a repeated hand-over is safe.

### 5.3 What "delivered", "replied", "failed" and "may not have arrived" mean

For an entry E and one seat S (one agent the entry was for):

| Status                                     | True when                                                                                                                                                                                                                                    | Reason shown                                                                                                        |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `queued`                                   | No run of S that the runtime accepted lists E as `new` or `steer`, and E is neither `failed` nor `unknown` for S. This includes a run a pause put back (§4.4, item 5): its entries read `queued` again until its `delivered_at` is set again | The run's wait reason ("Waiting for @ana to finish", "@ana is paused"), and its place in line                       |
| `delivered`                                | A run R of S lists E as `new` or `steer`, and R's `delivered_at` is set                                                                                                                                                                      | none                                                                                                                |
| `replied`                                  | `delivered`, and R wrote an entry in this conversation (an entry with `run_id` = R), or any entry names E as its parent                                                                                                                      | a link to the reply                                                                                                 |
| `failed`                                   | The run of S that lists E as `new` was cancelled before `started` (refused at the door, expired, removed) or the runtime refused it, and no later run of S lists E; or E was listed only as `skipped`                                        | From the run's ending, in plain words; or "Too many messages arrived at once; @ana saw the latest ones" (`skipped`) |
| `unknown`, shown as "may not have arrived" | The run of S that lists E ended after `started` and before `delivered_at` (step 5's `delivery: unknown`)                                                                                                                                     | "DorkOS restarted while this was being handed to @ana"                                                              |

Words that wait in a composer are not entries yet, so they have no status here: the sender sees the queue row as waiting, as today, and no other reader sees them. Once a turn takes them, the entry is `delivered`, `unknown` or, after a pause, `queued`.

One function, `entryDelivery(conversationId, entryIds, seats)` in `services/runs/`, computes these from `turn_run_entries` and `turn_runs`. No status is stored on an entry or anywhere else; a `chat_messages` row stops carrying one once its kind of message is an entry (MS12, MS21). "Sent" and "delivered" are never shown for something that could still be lost.

**Two statuses at once.** An entry a turn was shown is `delivered`, and stays `delivered` whatever the run does next. If that run then fails, the failure is said beside it: "Delivered. The turn failed." A surface reads one seat's statuses in this order and shows the first that holds: `replied`, `delivered` (with the run's failure beside it, if any), `unknown`, `failed`, `queued`.

**Retry** on a `failed` or `unknown` entry is a person's or the sender's choice, never automatic: it starts a new run for S whose hand-over lists exactly the retried entries as `new`, and writes no new entry. When step 5 restores a person's own row as a draft after its run ended with delivery unknown, sending that draft is the Retry for its entry: it starts the new run for that entry and writes no second entry.

### 5.4 Who may read it, and what each surface shows

- **The status** of an entry (the word and the reason in plain words) is shown to anyone who may read the conversation, on the sender's own entries and on every entry in a two-member conversation. Whether a caller may read a conversation, a private one included, is decided by item 12's viewer check for rooms (the `RoomViewer` its step G8a threads through the rooms service); reading a private conversation and reading an entry's delivery are named actions of that check and join its count.
- **The record** (the run ids, which entries each run was given, `ending_detail`) is read only by whoever may read the run, step 5's and item 10's reader rule: the chat's readers (§4.5).
- **The app** shows the status on the sender's entry (the draft's R4, as changed in §12.3): a quiet dot for queued and delivered, nothing for replied (the reply is the signal), and words with **Retry** for failed and for "may not have arrived". In a room the entry shows one status for each agent it was for: at rest the least advanced, on hover each one.
- **An agent** reads the same words in its tool results: `post_to_room` and, from MS12, `chat_send`.
- **An outside window** shows nothing new. A failed outbound delivery to it shows on the entry in the app (§8.3).
- **The API**: one capability, `conversations.entry_delivery` (statuses for up to 100 entries of one conversation), projected to HTTP by item 1's rules.

### 5.5 Which steps build it, and the ticket for the move

MS2 builds the table, the `run_id` and `origin_json` columns, `entryDelivery`, and the hand-over module with both of its paths (the room-style hand-over, and the composer path with the `started` fact carrying a row's words), for fixture callers; it needs step 5's T2, T4 and T5, which are built. MS3 makes rooms its first real writer, once T10 puts rooms on the port and T15 gives the port its recovery, which the restart cases of §4.4 rest on. MS12 is the composer path's first real writer. MS4 shows it. MS2 also files the ticket that names the move of the log and its seats to the space store (New, under item 16), as `AGENTS.md` requires of a feature built on `services/rooms`; `turn_run_entries` moves with `turn_runs` under step 5's child Q.

## 6. What starts a turn for a message

### 6.1 The two ways in, and the one way to start

**A room-style conversation** (a channel, a thread, a Telegram or Slack chat, an object's thread), as rooms do today:

1. **The words become an entry at once.** The poster (a person, an agent, an outside window through the chat bridge) writes an entry in the log.
2. **The dispatcher decides, in the same transaction.** The conversation's dispatcher (today the room trigger: addressing, the cascade guard, the turn budget) decides which seats should answer, never a seat whose own agent wrote the entry, and starts runs by the rule of §4.4, item 1: a new run unless the seat's newest waiting run has the same mark and level. For each new run it calls the space face's `start()` with `source_ref` naming the entry and `conversationRef` naming the seat. The entry and every run it starts, with their `start_turn` effects, commit in one transaction. This is step 5's own rule for the outbox ("an effect is inserted in the same transaction as the state change that causes it"), applied to the entry, and it holds for room-style conversations only. Today the trigger does not decide inside the entry's write: it keeps its claims and held triggers in memory (`rooms/room-trigger.ts:246`, the `claimed` map, and `:274`, the `held` map) and reads the room's and the agents' config. Step 5's T10 replaces the in-memory hold with queued runs, and its T15 gives them recovery; MS3 then moves the decision into the entry's write, reading the config it reads today (MP10; §17 keeps the risk).
3. **Admission and hand-over.** The run waits on the space side as step 5 §3.5 says. When it goes, the `start_turn` handler calls the hand-over module (§5.2, path 1), which writes the window's rows and moves the cursor, and then asks the computer face.

**Words that wait in a composer** (a person's 1:1 message, an agent's `chat_send` to an agent or a chat, a mini app's message): nothing about waiting changes. The message is a `session_message_queue` row the person can see, edit, reorder and remove (ADR `260811-184735`); steer and interrupt work as today; step 5 starts its run as it does now. Entries in such a conversation never start a run through the room dispatcher.

1. **The turn takes the row.** The dispatcher takes the row at turn start, as today, or joins it to the turn starting, or sends it into the running turn.
2. **The row's own words reach the space side.** On a Mac the in-process feed passes them (the head row's words before any join, and each joined or steered row's own words with its id and the run it went into); for another computer the home already holds the row (§5.2, path 2).
3. **The space side writes the entry from its own records.** The facts handler calls the hand-over module, which checks the row against its own run and chat, then writes the entry, its delivery row and the seat's cursor in the same write as the run's transition. On a Mac that is before the runtime reads the words; for an agent on another computer the home writes the entry from its own row when the `started` fact arrives.

**Either way, the reply is an entry.** The agent's answer is written to the log with its `run_id`, and the chat bridge carries it to any outside window. In a composer conversation the answer goes back to the chat that asked by step 5's report path (§5.2, path 3; §11.2).

### 6.2 The room-style hand-over, step by step

Inside the chat's dispatch mutex (step 5 §5): read the seat's `last_read_seq`, `joined_seq` and session; read the window (§4.4, items 2 and 5), which ends just before the source entry of the seat's next waiting run; add to the run any mark a context entry in the window has and the run lacks, and take the stricter level (§4.3); write the run's `turn_run_entries` rows; move the cursor to the newest entry read; build the turn's words from those entries, fenced, with each entry's author and marks, as `room-context.ts` does today. A run whose rows already exist reuses them. The run's words are inline in the computer face's request (step 5 §3.2); no entry id crosses the port.

### 6.3 Exclusion by session, and who starts runs

The window drops entries whose `session_id` is the seat's session, not entries whose author is the seat's agent: an agent's own post from another chat reaches this seat as context, like anyone else's. But the dispatcher never starts a seat's run for an entry its own agent wrote, from whichever chat. An entry the seat's own session wrote is never given back to it.

## 7. The order, and why

1. **The count and the delivery record first (MS1, MS2).** They need the least: the count needs nothing, and the record needs only step 5's run record, outbox and door, which are built. From MS1 on, nothing new can be stored in Maildir.
2. **Notices and the measure of log growth (MS5, MS6).** Small, need nothing, and they take one path out of Relay's word-carrying.
3. **Rooms write the record, and it shows (MS3, MS4).** Every room-style chat inherits the record. MS3 waits for step 5's T10 and T15.
4. **Outside chats (MS7 to MS10).** Room mode already works for one binding shape, so the step is mostly a default and the shapes it refuses today. It is the biggest gap: in default mode an outside chat has no log at all. The binding router's republish goes at the end of it.
5. **Agent-to-agent messages, old before new (MS11, MS12).** MS11 folds every old agent-to-agent message into its pair's conversation first; MS12 then writes new ones as entries, after folding any written in between. So old messages always come before new ones in a log. MS12 needs step 5's T6 and item 10's seat table (D6).
6. **A mini app's and an object's thread (MS13).** A mini app's old words are not kept (its send rows are pruned), so there is nothing to fold.
7. **Relay's turn paths go (MS14, MS15).** Tasks after step 5's T12; agent subjects after T13 and item 10's D7 and D12, and after MS10, when the binding router no longer uses them.
8. **Relay stops dead-lettering into Maildir, and its sending screens go (MS16, MS17).** Then the count is zero once item 9's O6 has landed. Relay's message and dead-letter views stay, read-only, until MS18.
9. **Maildir retires and is archived (MS18)**, with its read command and the removal of the read-only views in the same step, so old messages are never unreadable.
10. **1:1 chats last (MS19 to MS21)**, as ADR `261017-211859` orders: they are the most-used surface, the only one with live detail to protect, and they need the retention decision first. Old `chat_send` rows to a chat and old reports fold in (MS20) before new ones are written as entries (MS21).

Each kind's step deletes what it replaces in the same series, and leaves every chat readable.

### 8.2 Maildir: what it holds, and when it retires

ADR `261017-211859` says it retires "when the log's delivery records and the session queue cover what it holds today". Each part, and what covers it:

### 8.3 A failed outbound message

Today an outbound message a connection cannot deliver is dead-lettered into a mailbox named for its subject (`adapter-delivery.ts:476-485`). From MS16 the connection's delivery code reports a final failure to a failure sink instead. For a message from a conversation, the chat bridge's outbound row in `room_bridge_messages` (written before the send, today's echo guard) records `failed` with the reason, the entry shows "Not sent to Telegram: why · Retry", and the existing dead-letter notification (`notifications/emitters/dead-letter.ts`) is re-pointed to tell the person once. For a notice copy (§11.4), the notification that exists already tells the person, and the words are in the Direct chat. Retries, rate limits and the breaker run before the failure is final, as today.

### 8.4 The archive

At MS18 Maildir's files, and Relay's files and rows that hold words or maps nobody reads any more, move to one dated folder under the data directory, `{dorkHome}/archive/YYYY-MM-DD-relay/`, written once and never read by the server:

- `mailboxes/` as it is (every endpoint's `tmp/`, `new/`, `cur/` and `failed/`);
- `relay-index.jsonl` (the `relay_index` rows), `relay-delivery-receipts.jsonl` (the `relay_delivery_receipts` rows);
- `sessions.json` and `agent-sessions.json`;
- `README.txt`, one paragraph saying what the folder is and that nothing in it was imported.

One command reads it: `dorkos archive relay` lists what is there (endpoints, message counts, dates), and `dorkos archive relay show <id>` prints one message. The command reads local files only; no HTTP route and no agent tool reads the archive. The tables `relay_index` and `relay_delivery_receipts` are dropped in the same migration. Nothing is imported into the log. A person who never used Relay's screens gets an empty folder with its `README.txt`, or none if Relay never wrote a file.

### 8.5 What a person who used Relay's screens sees

- **The Connections screens stay**: connections, bindings, setup, recent chats, who may answer, the event log and the trace of an outbound message.
- **At MS17 the sending parts go**: the compose dialog, endpoint registration and the console. The activity feed, the dead-letter section and its attention item, an endpoint's inbox, the metrics and the health bar stay as a read-only view of what Maildir holds, so nothing becomes unreadable.
- **At MS18 the read-only view goes, in the same step as the archive and `dorkos archive relay`.** What it showed is now where it belongs: each conversation shows its own messages with their status, a message that could not leave for a window shows on its entry and as a notification, and old messages and dead letters are in the archive.
- **Changelog fragments** in MS17 and MS18 say so in plain words, the second with the command.

## 9. The count: nothing new in Maildir (M6)

ADR `261017-211859` says the rule "has to be held by review until a check holds it". MS1 is that check. ## 11. Each kind of chat, in order

### 11.1 Outside chats: Telegram and Slack (MS7 to MS10)

**What exists.** A binding joins a connection (and optionally one chat) to an agent. With `bridge: 'room'` the chat bridge writes each inbound message as a room entry and the room decides whether to answer (`relay/binding-router.ts:679-690`; `relay/chat-bridge/ingest.ts:1-7`). With `bridge: 'off'`, the default (`packages/shared/src/relay-adapter-schemas.ts:695`), the router picks a session by strategy (`binding-router.ts:1044`: `per-chat`, `per-user`, `stateless`, `relay-adapter-schemas.ts:571`) and republishes to an agent subject (`:777`); the words live only in that session and in Maildir. Room mode requires a chat id: a binding with none (a wildcard) is refused it (`relay-adapter-schemas.ts:577-602`). The claim card offers "Answer privately", which keeps today's default mode (`apps/client/src/layers/features/connections/ui/ClaimCard.tsx:58`, `:167`). A group chat whose platform type is unknown is never bridged (`relay-adapter-schemas.ts:653`). Who may message the bot privately is the connection's `dmPolicy`, default `'allowlist'`, with its approver list.

**What it becomes.** Every claimed outside chat has a log. The picks for the shapes the draft left open (the designer's five answers; §18, question 1, puts them to the operator):

| Shape                             | Becomes                                                                                                                                                                                                                                                                                                                                                                     | Step                               |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| A binding to one chat, `per-chat` | One conversation for the chat, bridged as room mode is today. The binding's default becomes `bridge: 'room'`                                                                                                                                                                                                                                                                | MS7 (new bindings), MS8 (existing) |
| "Answer privately"                | A visibility of the conversation, not a way to store it: the room row gains `private` (a boolean, default false, with its migration in MS7); a private conversation's members are the person who claimed the chat, the agent and the outside senders, it is not listed as a channel, and only its members see it. A person can open it to a channel later, with its history | MS7                                |
| A wildcard binding (no chat id)   | Each new outside chat gets its own conversation on its first message, bridged to that chat. The refusal's reason ("one room cannot honestly be the channel for an unbounded set of chats") still holds: it is one conversation for each chat, never one for all                                                                                                             | MS9                                |
| A group chat of unknown type      | Held as unclaimed until its type is known, then a shared conversation                                                                                                                                                                                                                                                                                                       | MS9                                |
| `per-user`                        | One conversation for each outside user of the binding, bridged to the chat the user wrote from                                                                                                                                                                                                                                                                              | MS10                               |
| `stateless`                       | The log is kept; the seat gets a fresh session for each message, with no recap                                                                                                                                                                                                                                                                                              | MS10                               |

**A bound on new conversations.** Every strategy that makes conversations by itself (a wildcard binding, and `per-user`) makes at most 60 new conversations an hour and 500 a day for each binding. Past either bound a new chat or user waits as unclaimed, where a person can claim it, and nothing is lost. The count is read from `room_bridges` by `binding_id` and `created_at` (`packages/db/src/schema/bridges.ts:63`, `:89`; both columns exist today), with a new index on those two columns in MS9's migration; no new table holds it. The bound applies only to conversations made for chats and users that arrive after a step lands: the chats and users a binding already holds when MS9 or MS10 lands move, whatever the count.

**Who the person member is.** The person member of a binding's conversation is the person who claimed the chat on the claim card, or, for a binding made with no claim card (in Settings or by the API), the person who made the binding.

**A moved chat still answers every message.** In default mode every message started a turn. A moved chat becomes a bridged room of the kind the bridge already picks (a `dm` for a private platform chat, a `channel` for a group, `services/rooms/manage/room-bridge-create.ts:256`), and the agent's membership is seeded with the response mode `always`, not the `mention-only` a new bridged channel gets today (`room-bridge-create.ts:286-287`). So every outside message there addresses the agent and still starts a turn (MP5).

**What must not change.** `dmPolicy`, the approver list and the unclaimed-chat store (which holds no message words) stay exactly as they are. Words from outside stay marked: each entry's author is an outside sender, and a turn given it runs at the binding's level with the outside mark (§4.3). An agent's reply still reaches the chat it came from, through the bridge's outbound path and `room_bridge_messages` (the only echo guard, `relay/chat-bridge/bridge-store.ts`). `canInitiate` (default false) and its consent gate (`relay/initiate-consent.ts`) still decide whether an agent may start a message on a chat. Telegram's and Slack's own message ids still map to entries, so edits and threads keep working.

**What happens on upgrade.**

- **MS7** changes only the default for new bindings and the claim card's two actions. Existing bindings keep their mode.
- **MS8** moves every existing `bridge: 'off'` binding with a chat id and the `per-chat` strategy. A default-mode chat was one a person kept private, so it stays private: the conversation gets the `private` visibility, with the person who claimed it, the agent and the outside senders as its members. MS8 makes the conversation and its bridge row, and seats the agent on the session the binding's map already holds for that chat, so the agent keeps its whole context and nothing is fed twice (the session wrote nothing in the new log). The conversation's first entry is a notice, "Earlier messages in this chat are in @ana's session", linking to that session for whoever may read it (§4.5). No transcript is copied into the log. The binding's level and marks are unchanged (MP5).
- **MS9** turns on wildcard conversations: each chat already in the binding's map becomes a private conversation the same way on its next message, within the bound.
- **MS10** does the same for `per-user` (one private conversation for each user already in the map, seated on that user's session, within the bound) and `stateless`, then deletes the router's republish to agent subjects (`binding-router.ts:777`) and stops reading `sessions.json`. The file stays on disk until MS18 archives it.
- **A connection that works before a step works after it** (M8): each step's upgrade test runs a fixture binding of every shape through an inbound message and an outbound reply, before and after.

### 11.2 Agent-to-agent messages (MS11, MS12)

**What exists.** `chat_send` to an agent id goes to the chat the sending agent keeps with that agent, found through `chat_agent_dms`, keyed by the sender's home and the receiver (`packages/db/src/schema/session/chat-messages.ts:99`; `session/chat-messages/chat-target.ts:1-25`). The words are a `chat_messages` row with the sending chat, the fence nonce, the sending turn's level (`ceiling_json`), the delivery the sender asked for (`queue`, `steer`, `interrupt`) and a stored status (`:49-51`), and a queue row in the receiving chat. The person comes first; agent messages that wait together run as one turn; there is no loop guard or turn cap, and the launch cap applies (ADR `261009-171114`).

**What it becomes, exactly.**

- **The conversation** has two members, the two agents: a `dm` room, one per pair, found by its member key as rooms do today. Its log holds the words.
- **Waiting does not change.** A message is a queue row in the receiving agent's seat session, on the port from step 5's T6; `steer` and `interrupt` work as today.
- **No room runs.** Entries in an agent-to-agent conversation never start a run through the room dispatcher. Runs start only from queue rows (the receiver's) and from the report path (the sender's).
- **The receiving agent's seat starts runs, from the queue row.** When its turn takes the row, the space side writes the entry from the row's own words (§5.2, path 2), authored by the sending agent, with `origin_json` holding the sending chat and level from the chat-message row and the turn's marks in `turn_marks`, and its delivery row and the receiving seat's cursor, in one write. A message joined into a turn already starting, or sent into a running one, is written the same way from its own words and listed on the run that took it.
- **The sender has no seat that starts runs for its own entries.** The sending agent is a member, so its read cursor exists, but nothing starts a run for an entry its own agent wrote (§6.3).
- **The reply is an entry in that conversation, written by the run that produced it,** with that run's `run_id`. So it links to its turn. Its parent is the message it answers; when one turn took two or more messages, its parent is the last entry that run took.
- **The sender gets the reply through step 5's report path** to the chat that asked (the run's `askedByRef`, set from T6). The run the report path starts in the asking chat is the third hand-over path (§5.2, path 3): its delivery record lists the reply's entry as `new`, and the sending agent's read cursor in the conversation moves at that hand-over, so nothing is fed twice.
- **The seat table is an index, not a store.** Item 10's seat table (`agent_send_seats`) gets a `conversation_id`: `chat_send` to an agent id with caller key `agent:<sending agent id>` and a fixed conversation key reads or makes the row, and the row points at the two agents' conversation; its `session_id` is the receiver's seat in it. It stores no words. This is item 10's optional D14, amended (§14.4).
- **Status** is read from the delivery record once the entry exists (§5.3), and from the queue row before; never from a stored column. The tool result says "Queued", "Delivered" or "May not have arrived", the same words a person sees.
- **No turn cap.** The agent-turn ceilings (§8.1) do not apply here; an agent-to-agent message has no loop guard or turn cap until DOR-2745 decides one.
- **People see agent DMs on each agent's page**, never in their DM list or unread counts (DOR-3086's acceptance test). The owner reads them as any conversation (§4.5).

**What must not change.** Every chat-message rule: the server stamps the sender; a fresh nonce fences the words each time they are given; a turn runs no looser than the tightest message it is given (a row whose level is tighter than the turn about to run waits for a run of its own); a person comes first; no loop guard or turn cap until DOR-2745 decides, and room turn budgets do not apply to an agent DM; an agent may stop a chat it may send to. `chat_read_cursors` stays, keyed to the conversation, as a reader's cursor.

**What happens on upgrade, old before new.** MS11 lands first: it makes each pair's conversation and writes every old agent-to-agent `chat_messages` row as an entry, with its original time and author, unique on the row's id, without starting a turn, and moves both agents' cursors past them (§4.4, item 7). Backfilled entries show no delivery status (they predate the record). New messages keep their old path during MS11. MS12 then runs the same fold once more at boot, for rows written since, before it accepts a send, and from then on writes new messages as entries when a turn takes them. So a pair's old messages always come before its new ones. MS12 drops `chat_agent_dms`. `chat_send` to a chat id and spin-off reports stay on `chat_messages` until MS20 and MS21.

### 11.3 A mini app's thread and an object's thread (MS13)

**What exists.** `ctx.agent.send` to an agent id keeps one chat for the mini app and the agent in `extension_agent_chats` (`packages/db/src/schema/extensions/extension-agent-sends.ts:97`); the words wait in `extension_agent_sends` (`:43`) and then a queue row until the turn takes them, and finished rows are pruned. It runs through the turn port as origin `extension-message` (step 5's T5). Doc comments are a separate feature (DOR-2983).

**What it becomes.** A conversation can be anchored to a thing: the room row gains `anchor_ref`, a `dork:` reference (ADR `261122-124821`) to a mini app, a doc, a file or a task, with an index for the lookup, in MS13's migration. A mini app's messages stay composer words: they wait as today, keep their origin `extension-message`, and become entries in the conversation anchored to the mini app when the agent's turn takes them, authored by the mini app (an author of the local kind `app`, §4.1), with `origin_json` `{ kind: 'extension-message', appId }` and the turn's marks. Item 10's D15 is amended the same way as D14: the seat row for caller key `app:<mini app id>` points at that conversation (§14.4). `extension_agent_chats` retires; `extension_agent_sends` keeps its idempotency keys and receipts (and loses its status columns under step 5's T20). Doc comments land on an anchored conversation when DOR-2983 builds them; this spec builds the anchor and the lookup only.

**What must not change.** `ctx.agent.send`'s inputs and answers (`started` or `queued`, with `busy` or `at_capacity` as the reason); how its words wait; "a mini app's own conversation with an agent is not a wake" (item 9 §10.3); the marks; a mini app reads only what it could read before.

**What happens on upgrade.** A mini app's old words are not kept (its send rows are pruned), so nothing is folded. Each `extension_agent_chats` row becomes the seat of a new anchored conversation on the chat it names, with a first notice entry pointing at that chat's earlier messages. Sends already waiting become entries when a turn takes them, like new ones.

### 11.5 1:1 chats, last (MS19 to MS21)

**What exists.** The Direct chat is the agent's seat session in the person-and-agent `dm` room: posts land in the room, the person's typed words and the agent's replies only in the session (`rooms/direct-chat/direct-chats.ts:3-18`). Every other 1:1 chat is only a session. A person's waiting messages are `session_message_queue` rows. `chat_send` to a chat id and a spin-off's report are `chat_messages` rows queued into that chat.

**What it becomes.**

- **A `chat` conversation kind**, defined in the local type that widens `RoomKindSchema` (§4.1), with its migration in MS19; the shared enum and the community contract do not change. One conversation for each 1:1 chat, made at the chat's first turn after MS19. Its members are the person and the agent; the agent's seat is the chat's own session. The Direct chat's conversation is its existing `dm` room.
- **The entries**: the person's message stays a queue row while it waits and becomes an entry when its turn takes it (§5.2, path 2), with the words the turn took and the time the run was accepted; an edit or removal while a pause has put it back writes a revision or marks it withdrawn (§4.1); the agent's reply is written at the turn's end, its visible text blocks in order, with its `run_id`, never tool output, thinking or to-dos. One turn's entries are written together (the log is turn-atomic).
- **The 1:1 view keeps reading the session** for live detail: streaming, tools, thinking, to-dos. The log is the record for every other reader (search, an agent's history tools, another window). Nobody shows both: the second record is invisible to the person (ADR `261017-211859`).
- **A turn run outside DorkOS** (a bare command-line resume) writes no entries. The log shows one quiet line where entries are missing, "2 turns ran outside DorkOS · Open the session", worked out from turns in the session that have no run. No backfill.
- **MS20, old before new**: every old `chat_messages` row sent to a chat id, and every old spin-off report, is written as an entry of the receiving chat's conversation, with its original time and author, unique on the row's id, without starting a turn, seats moved past.
- **MS21**: the same fold once more at boot for rows written since, then `chat_send` to a chat id and spin-off reports become entries when a turn takes them (they stay queue rows while they wait), with status from the record; `chat_messages` is dropped; the message search index is re-pointed at the log for these chats; the Direct chat's special cases (pings drawn into the session stream, its own redirects) retire.

**What must not change.** Everything the person sees in the 1:1 view: history, streaming, steps, the composer, an editable queue, scroll position, no flash and no double. The chat-message rules (§11.2).

**What happens on upgrade.** No transcript is copied. A 1:1 chat's log begins at MS19, with one notice entry, "Earlier messages are in this chat's session"; the 1:1 view still shows the whole history from the session, so the person loses nothing. Search keeps its session sources for words from before.

### 11.6 Log growth

The log is never trimmed. What grows: every entry a step adds, most of all two or more for each 1:1 turn from MS19. MS6 adds a measure: `dorkos doctor` and one read-only capability report the entries and bytes of the log by conversation kind, and their growth over the last 7 and 30 days. Retention is later work: a ticket (New, filed by MS6) decides how long a log is kept, and MS19 waits for that decision.

## 17. Risks

- **Two delivery paths live side by side until MS18.** The count (MS1) holds "nothing new" from the first step; each step's drop is measured at its own head.
- **The entry and its runs in one transaction** (§6.1) applies to room-style conversations only. It moves the room trigger's decision inside the entry's write, where today it runs off the committed entry and keeps its claims and holds in memory (`rooms/room-trigger.ts:246`, `:274`). Step 5's T10 and T15 replace the in-memory hold with queued runs and their recovery; MS3 then makes the decision synchronous, reading the rows and the config it reads today, and proves it with MP10. If a decision ever needs to wait on something outside the database, it becomes an outbox effect written in that transaction instead.
- **Moving outside chats changes where a person reads them.** A Telegram chat that was only a session becomes a conversation in the app. The first notice entry points at the old session, and the changelog says so (MS7, MS8).
- **Bindings that make conversations by themselves make many of them.** The bound of 60 an hour and 500 a day for each wildcard or `per-user` binding, and `dmPolicy`, limit it (§13); a chat or user past the bound waits as unclaimed and is not lost.
- **A composer's entry appears when the turn takes it, not when it is sent.** Another reader sees a waiting message only once a turn has taken it; the entry's time is when the message was accepted, so a reader sorting by time sees it where it was sent, and the log's `seq` says when it was taken. This is the price of leaving the queue exactly as it is.
- **The log grows faster from MS19.** MS6 measures it; retention is decided before MS19.
- **A turn run outside DorkOS leaves the log short.** The line says so; nothing is backfilled.
- **Files that may not grow.** `relay/binding-router.ts`, `rooms/room-store.ts` and `packages/relay/src/relay-publish.ts` are on the file-size baseline, and `rooms/room-context.ts`, `chat-bridge/deliver.ts` and `services/runs/run-store.ts` are long. Each step that touches one moves a part out first.
- **Removing HTTP routes** (MS15, MS17) has no deprecation period (ADR `261123-170832`): each removal fixes every caller in the same change, and the step's search for callers decides the final list.
- **Old tickets read as live work.** DOR-3086 and the draft's steps hold the old text; §14.2's banner and the issue updates must land before anyone picks them up.
- **Steps that wait on other items.** MS3 waits for step 5's T10 and T15 (recovery, not built), and every chat kind waits for MS3. If they are late, MS1, MS2, MS5 and MS6 still land and the count still holds.

## 18. Open questions, each with a pick

1. **The bindings the draft's first step left open, for the operator.** Pick: the designer's five answers (§11.1): "Answer privately" is a visibility, every claimed chat has a log; a wildcard binding gives each new chat its own conversation on its first message; `per-user` is one conversation for each outside user; `stateless` keeps the log with a fresh session for each message; an unknown group chat waits as unclaimed until its type is known. Other option: keep default mode for the shapes room mode refuses today, which leaves those chats with no log and Maildir with words in it.
2. **How long a log is kept.** Pick: decided later, in its own ticket, before MS19. Other option: decide now, before anyone has measured the log (MS6).
3. **Who may read the turn behind an entry, when the reader is a member but not the session's owner.** Pick: what rooms do for the peek today (§4.5): a person who may see the conversation may learn which session an agent answers in, and opens it only if `canReadSession` lets them; an agent never. Other option: any member of the conversation may read the turn, which opens agents' working context to every member of a shared space.
4. **Backfilling default-mode outside chats from their transcripts.** Pick: no; the seat keeps the old session and the log begins with a notice that points at it (§11.1). Other option: copy each past turn's visible text into the log, which reads a runtime's transcript as a source of record, against ADR-0310.

Decided by ADR `261017-211859` and no longer open: old Maildir rows are archived as they are, not imported (§8.4); a 1:1 chat is a `chat` kind (§11.5); delivery is a record, and "delivered" means a turn the runtime accepted showed the entry (§5.3). Decided in this spec, and no longer open: the delivery record lives with the run record (§5.1); the count only falls (§9); who may message whom is unchanged (§4.6); loop limits for agent DMs wait for DOR-2745 (§11.2); a turn run outside DorkOS writes no entries (§11.5); words that wait in a composer stay queue rows and become entries when a turn takes them (§5.2); old rows of a kind fold in before new entries of that kind are written (§7); email is not built here.
