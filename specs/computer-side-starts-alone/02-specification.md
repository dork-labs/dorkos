## Overview

Four things land, one pull request series at a time, inside the one process a Mac already runs:

1. **A wall, first.** One side map names every server folder as computer side, space side, kernel or front door. An ESLint rule counts every import from a computer-side file into a space-side file, against a baseline that may only fall. It lands before any seam, so nothing new crosses while the old crossings are removed.
2. **One tools port.** Every runtime reaches DorkOS tools through `list(ctx)` and `call(ctx, tool, input)`, plain data, decided by one gate on the space side. The 39 hand-registered tools become capabilities, the second gate and its tier table go, and the tool server leaves the Claude Code runtime's folder. This is 182 of the 522 crossings.
3. **The other seams.** Records leave the computer as facts on the turn port's sink; each turn reads one rules object; agent facts arrive in the `agents.sync` shape; pause and holds come through the turn port; asks, turn-start input and the computer's own tools get ports of their own; a short list of files moves. Together they remove the other 340.
4. **Two entries.** Startup steps become shared functions. One role policy is read once. The full server composes both sides; a computer entry composes the computer side alone, serves only health and the loopback `/mcp`, and boots, runs a turn and stops against a test double of the space side.

## Goals

- No computer-side file imports a space-side file, held by a check that only tightens and ends at zero.
- Every runtime gets the same DorkOS tools for the same agent and turn, decided by one gate, recorded once.
- The computer side boots alone and runs a turn with the space side behind ports.
- Nothing a person sees changes, except where a step says so and ships a changelog fragment.
- Each step ships alone and leaves the app working.

## Non-goals (out of scope)

- The wire and the forwarding runtime (roadmap item 8). The ports here are shaped to the wire schema; nothing here opens a socket.
- The own-process test (item 7). The computer entry runs inside tests; nothing here makes it a long-lived process on a Mac.
- An image target for agent computers (item 14).
- Splitting the database. One `dork.db` stays (§6).
- The signed rules copy across a wire and its keys (`design-permission-gate.md` §3, item 8). On a Mac the rules object is unsigned and frozen (its §6).
- Moving trust decisions. What is decided, and by which function, does not change; only where the deciding code reads its facts from.

### 1.2 The census and its counting rule

**The rule** (the wall's baseline, §4). The census counts each statement in a non-test computer-side file that reaches a space-side file. It counts these statement kinds, type-only ones included:

- `import` and `export … from`;
- `import x = require`;
- a dynamic `import()` with a literal path, and an `import('…')` type expression;
- `declare module`.

Only relative paths count. Each is resolved against the importing file, never matched as text: `.js`, `.ts` and `.tsx` are dropped, and a trailing `/index` counts as its folder. Package paths (`@dorkos/*`, `node:*`, npm) are not counted here; §6 covers the one package the wall also checks. Tests (`__tests__/`, `__fixtures__/`, `*.test.ts(x)`, `*.spec.ts(x)`) are not counted. This is the set TypeScript's `preProcessFile` reports, the reader the turn-port checker already uses.

## 3. Normative invariants

These seven invariants are the rule. Everything else in this spec (the per-path map in §1, the seam tables in §5, the step table in §9) describes today's code and how it meets them. **Where the code and the per-path map disagree, the invariants win: the build step that finds the gap amends the section it contradicts in its own pull request, with a proof case in §8.**

|        | Invariant                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | How it is checked                                                                                                                                                                                                                                                                                                                      |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **I1** | No computer-side file imports a space-side file, by value or by type: the wall's `space` column reaches zero in this spec. Computer-side files may also import kernel modules and the plain-data contracts in `packages/shared`. Front-door imports (109 at `ca404cfc4c`: `core/cloud` 46, `core/usage` 41, `core/auth` 16, others 6) may only fall here, except `core/auth`, which must be absent from the computer entry's import graph by C23. `core/cloud` and `core/usage` leave with DOR-4925's kernels or a new issue, "cloud and usage off the computer side" (New issue). | The wall's rule and baseline (§4); the computer entry's import-graph test (§7.4), which forbids the space side, `core/auth` and `routes/`; proofs W1 to W4.                                                                                                                                                                            |

### 5.1 P1: the tools port (182)

**What it is.** One runtime-neutral door for DorkOS tools, on the space side:

- `list(ctx) → RelayToolSummary[]`, the tools this agent may see on this turn (`RelayToolSummarySchema`, `packages/shared/src/session-relay-agent-computer.ts:368`).
- `call(ctx, tool, input, signal) → RelayToolCallOutcome` (`RelayToolCallOutcomeSchema`, `:382`). A failed tool is an `ok: false` outcome, as the wire defines it.
- `ctx` is `{ agentId, sessionId, runId?, backgroundWorkId? }`, plain data (`ToolsPortContextSchema`). `runId` is required whenever `backgroundWorkId` is present. The wire's `tools.list` and `tools.call` carry `agentId` and `sessionId` only today (`RelayCallSchema`, `:332`), so `runId` and `backgroundWorkId` are new fields under a new feature id (`tools.call.run`, below).

**Which run a call is bound to.** A call is always decided at the level and marks of the run it truly belongs to, never at those of a newer turn in the same chat. This is `design-permission-gate.md` §4 item 5 and its amended §10 Must row, which say the same:

- Every call is bound to exactly one run: a live run, or an ended run that still has background work registered to it.
- A call from background work names both its `runId` and its `backgroundWorkId`. Neither is ever inferred for it.
- **A transport that knows which turn a call belongs to always names its `runId`.** The space side infers a run only for a transport that has no turn binding, and then only exactly one live run for that agent and chat; an ended run is never inferred. A call that names no run while an ended run of that chat still has registered background work is refused. Both transports on a Mac know their turn: the loopback listener's bearer is bound to one turn binding (`ServerPrincipalProof`'s `bindingId`, `services/connectors/principal/server-principal.ts:37`; the bearer is revoked when the turn ends, `runtimes/shared/dorkos-mcp-injection.ts:14`), which the run record keeps (`turn_binding_id`, `packages/db/src/schema/runs/turn-runs.ts:121`); Claude Code's glue is built per query by the factory the launch calls (`runtimes/claude-code/messaging/launch-resolver.ts:725-726`). So on a Mac no run is ever inferred.
- A call for a paused or stopped run, for an ended run with no registered background work, or that matches no run or two, is refused. A background call that names its run but no registered item is refused. When the run's agent is not `ctx.agentId`, the call is refused.

**Settled with Security: tool calls from background work.** Security has signed the amended rule (2026-11-25); it is recorded in the gate note in this pull request (its §12, item 9). A call may be bound to one live run, or to one ended run with registered background work, under five conditions. The tools port step (C10) builds the rule. C11 proves it on Claude Code, the one runtime whose background work can call a DorkOS tool after its turn ends today. On Codex, OpenCode, Doe and `computer-local` the per-turn bearer ends with the turn (`runtimes/shared/dorkos-mcp-injection.ts:14`), so such a call has no way in, and that stays so: it is a declared difference below. The five conditions:

1. Background work is registered with its run, by id, when it starts. A call that names no registered item, or one the space side did not see start, is refused.
2. It runs at the run's level and marks as they stood when the turn ended, or stricter. Marks it picks up are added to that run and carried as usual. A ceiling lowered later applies at once. Nothing can widen it.
3. A person's stop, a pause, the agent's level being lowered, or the end of the run's chat ends it at once, and its next call is refused.
4. The space side holds a hard deadline after the turn ends, which the computer's reports cannot extend. Default: four hours, the length of today's ceiling for held background work (`SESSIONS.BACKGROUND_WORK_PARK_CEILING_MS`, `apps/server/src/config/constants.ts:405`).
5. Each call is recorded as background work of that run, and teammate metering counts it against the run's space.

**Registration (condition 1).** Today the run record's `background_work` fact lists the work a run's process holds (`packages/shared/src/turn-port.ts:831-834`), each entry a kind and a label (`BackgroundWorkEntrySchema`, `turn-port.ts:757-760`). The runtime reports its own id for each item when it starts: `BackgroundTaskStartedEventSchema.taskId`, with `subagentSessionId` and `toolUseId` beside it (`packages/shared/src/schemas.ts:2475-2479`). C10 requires that every item is registered with its run when it starts, through a `background_work_registered` record (`{ runId, backgroundWorkId, kind, label, startedAt, subagentSessionId?, toolUseId? }`, in `packages/shared/src/computer-records.ts`, §5.5), with `backgroundWorkId` set to the runtime's `taskId`. Each transport that lets background work call a tool after its turn ends must name the item the call comes from. Claude Code's glue maps a call to its item through the helper's ids: Claude Code already hands its hooks the helper's `agent_id` and the call's `tool_use_id` for tools a helper runs (`runtimes/claude-code/audit-tool-hooks.ts:55-70`), and the glue matches those against the `subagentSessionId` and `toolUseId` the record carries. C11 proves that match on a real helper. A runtime whose transport cannot name the item gets no tool calls from background work, a declared difference (table below).

**Live turn facts.** The space side's record is the authority for level, tier and marks. ### 7.2 One role policy (DOR-4927)

`ServerRolePolicy` is read once, at the start of `start()`, from `currentServerRole()` (`lib/server-role.ts:26`). It says which entries are on (space, computer, or both), which runtimes register, whether schedules run, whether keep-awake runs, which front-door features mount, and how the computer binds. Steps read the policy, not the role. Today's role branches in `startup/`, `http/` and `index.ts` (the calls to `isHub`, `isAgentComputer`, `isPersonalComputer`, `runsSchedules` and `currentServerRole()` there) move onto the policy as each step function is extracted. Branches inside routes and services, and the 22 request-classifier sites, stay as they are; DOR-4927 moves them later.

**How an agent computer is started.** The public contract says so in `packages/cloud-api/src/hubs.ts:30-42`: the agent computer is started with `DORKOS_SERVER_ROLE=agent-computer`, a key file path, and the cloud API origin, and nothing else that grants anything. The computer entry keeps that contract.

**The agent-computer role becomes the computer entry.** When the role is `agent-computer`, the CLI imports the computer entry's bundle instead of the full server (`packages/cli/src/cli.ts:840-849`, where the CLI uses the server bundle's exports as its handle on the running server). The computer bundle exports the same shape, so the CLI's handle works with either. The role is set by whoever starts an agent computer (`packages/cloud-api/src/hubs.ts:30-42`); what changes is that the same role now selects the computer entry instead of the full server in a sealed role. The full server's agent-computer branches in `startup/` and `http/` then never run, and C23 deletes them, with Security reading that pull request. Two things stay:

- **The loopback-only bind.** `env.ts:533-548` refuses `DORKOS_ALLOW_INSECURE_BIND` for any role but `computer` and rewrites `DORKOS_HOST` to loopback for `agent-computer`. Those rules stay in `env.ts` and are read into the role policy for the computer entry; proof E6 shows the computer entry binds loopback only.
- **The rules in `services/core/agent-computer/`.** The hub-owned action refusal is what an agent computer's `tools.call` will meet in item 8, keyed then on the calling computer rather than on this server's role.

**Restarts.** The role rides `DORKOS_SERVER_ROLE`, and the entry is the program `process.argv` names, so a restart that re-spawns `process.argv` with the same environment (as `routes/admin.ts:115` does) comes back as itself. Proof E2.

### 7.3 The computer entry

`apps/server/src/computer-entry.ts` composes `infra` and `computer` and serves only `/api/health` and the loopback listener's `/mcp` and `/agent-mcp`. It takes the space side as ports: P1 tools, P2 rules, P3 agent facts, P4 config, P5 records sink, P6 pause, asks, turn-start input and the space face of the turn port. In the full server those are in-process implementations from `space.ts`; in the proof (E1) they are a test double; over the wire (item 8) they become a client.

- **Build.** A second esbuild entry beside the server's in `packages/cli/scripts/build.ts` (beside `:399`), with the same externals, a type shim in `packages/cli/server/`, and the bundle entries pinned in `server-shims.test.ts`. No image target (item 14) and no new CLI command: the role selects the entry (§7.2).
- **Processes.** It takes the same instance lock, runs the same warm-process reap before any spawn, and runs the computer half of the same teardown. It never shares a `dorkHome` with a full server: the lock refuses the second (E4).
- **Runtimes.** It registers the runtimes the policy allows. Its proof uses the test runtime; OpenCode is what the role registers today (`startup/runtimes.ts:317`).

### 7.4 The import-graph test

`apps/server/src/__tests__/computer-entry-imports.test.ts` walks the computer entry's import graph with the existing esbuild walker (`walkImports`, `services/spaces/__tests__/promises/image-imports.ts:121`), reads the repo paths in `metafile.inputs`, classifies each with the side map, and fails on any space-side path, any `services/core/auth/` path and any `routes/` path. ## 10. Risks

- **Codex, OpenCode and Doe gain 39 tools, one group at a time.** Their lists grow and their prompts name more tools. Each group is its own small change with its fragment, behind the same gate and levels as on Claude Code, and the prompt-name tests hold each runtime to what it is offered.
- **Held calls on the loopback runtimes.** A runtime's client may not wait the hold. D3 runs per runtime; a runtime not shown to wait keeps the poll answer as a declared difference, so nothing breaks while it is unproven.
- **Background work on Claude Code.** C11 requires each helper to be registered with its run and holds its tool calls to the four-hour deadline. Work that outlives the deadline loses its DorkOS tools; C11 says so with a changelog fragment if a person can notice.
- **A one-time relaunch of warm processes.** Each conversion step (C9a, C9b) may change the tool-surface digest once, so a quiet warm Claude Code process relaunches on its next turn. Pure moves change no digest (D5).
- **Two gates while the tools move.** Until C9b ends, some tools pass the hand gate and some the registry. C8 makes the registry gate a superset first, so a tool decides the same either way.
- **Front-door code on the computer.** After C23 the computer entry may still load `core/cloud` and `core/usage` modules. Its graph test's allow list names them and only shrinks; DOR-4925 or the new issue of I1 removes them.
- **Empty space tables on a computer.** The computer entry's file holds every table. Nothing writes them (E5), and item 16 removes them. The `browser_*` foreign keys stay a tie until their own issue (§6).
- **Boot order.** C21 moves boot code into functions. It keeps the order of §1.5, and the boot tests and E3a compare the step lists.
- **Counts drift.** The numbers here were taken at `ca404cfc4c` (and the `tables` column at `ba50ef6a4f`). Each step records its exact drop, and C1's recorded baseline is the one that counts.

## 11. Open questions, each with a pick

1. **Claude Code's transport.** Pick: keep its in-process SDK server, made of glue that calls the port as a function. Other option: switch it to the loopback listener like the other runtimes. The pick keeps warm processes, the digest and the `canUseTool` layer as they are; item 7 can revisit it.
2. **Lists past 256 tools.** The 256 cap stays and DorkOS's own list is pinned under 200. Pick: when a list would pass the cap, leave out mini apps' tools, newest mini app first, and tell the person once. Other option: leave out by a declared priority on each tool.
3. **Room seat tables.** Pick: space tables for the wall, because the rooms service writes them. Other option: computer tables now, as ADR `261122-173853`'s step 5 leans.
4. **For Security, for roadmap item 8 (not this step): the rules copy and background work.** The gate note's §3 ends a remote computer's rules copy with a hard stop when its turn ends. Does the copy outlive the turn while background work is registered to the run, up to the same deadline? Pick: yes, under the same five conditions as §5.1. Security's direction so far (2026-11-25): yes, and a lowered level or a new mark reaches the copy at once, pushed and not polled, and the copy is deleted at a stop or at the deadline. It stays open until the wire work specifies it. Other option: the copy ends with the turn, and background work on a remote computer runs no native tools after it. The gate note's §12 lists this as open.

Settled since the first draft, and no longer open: front-door imports (I1), the exposure field (§5.1), how the computer entry starts (§7.2), audit names (§5.1), the three session folders (§1.1, C7), and tool calls from background work (settled with Security, §5.1).
