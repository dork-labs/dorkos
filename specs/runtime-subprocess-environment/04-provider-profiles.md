# Exact runtime environment profiles

DOR-1904 design checkpoint 4. This is the finite automatic catalog and the compatibility contract for implementing the projection, not a report of live authentication. Source baseline: `03f68928b427e7a533055dbdfa2b3dac457c5714`. Installed Claude SDK `0.3.224`, Codex SDK `0.147.0`; DorkOS provisions OpenCode `1.18.15`.

## Selection and precedence

The baseline includes `DO_NOT_TRACK` for every runtime and helper purpose. Preserve its exact value and let the receiving tool interpret it. DorkOS declares it at `apps/server/src/env.ts:135–140`; the pinned Claude SDK directly reads it in its telemetry policy at character offset 725533. Do not silently turn opt-out off by dropping it; DorkOS-specific telemetry/debug variables remain withheld.

The catalog is runtime-specific. Claude credentials never become automatic Codex or OpenCode credentials merely because they share a server. For Claude, the common row always applies; each enabled, recognized parent mode flag adds its finite row. Use the installed SDK's boolean spelling (`1`/`true`/`yes`/`on`, case-insensitive after trimming); preserve the flag's original value. If several flags are enabled, preserve their finite union and leave the SDK's existing precedence unchanged. Do not choose a different service, validate credentials by network, or infer a mode from a key's presence. Configuration supplied inside the runtime's own settings remains the runtime's responsibility.

A mode selected only inside a Claude settings file cannot be inferred from a parent environment without recreating the SDK's settings precedence. Do not implement that parser. A deployment splitting its mode into a settings file and its cloud credentials into the parent environment must explicitly list those credential names in owner custom inheritance. Credentials already in runtime-owned settings, OS keychains or login files continue to resolve there. This mixed-source case is a documented compatibility change with a regression fixture, not an automatic-preservation claim.

OpenCode has one shared sidecar that can serve several model providers, so its default host-auth profile preserves the three DorkOS-supported ambient model keys together. Narrowing that sidecar to one current session's model would break another session. The selected DorkOS credential fragment still overrides only its own mapped name, as today. This deliberate three-key union is not an arbitrary provider-prefix allow rule.

The lists below mean preserve a name **when present**, not require every credential mechanism at once. Keys, tokens, endpoints and paths are never emitted in diagnostics. Existing authentication precedence is unchanged, including potentially conflicting ambient credentials; this work does not silently unset an alternate credential to force a selected account.

## Explicit custom and unsupported cases

No prefix is automatic, including `AWS_`, `AZURE_`, `GOOGLE_`, `ANTHROPIC_`, `OPENAI_`, `CODEX_` or `OPENCODE_`. Unlisted names are withheld unless the owner lists that exact name; reserved server-only names remain forbidden. A provider installed through the runtime's own supported config is not declared unsupported merely because its ambient key needs opt-in.

The installed Claude source recognizes newer `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD`, `CLAUDE_CODE_USE_MANTLE` and `CLAUDE_CODE_USE_GATEWAY`. They are **custom profiles for this change**, not silently mapped to first-party Claude. If one is enabled in the parent and is not explicitly opted into custom inheritance, refuse that launch with a names-only migration instruction; do not strip it and start against a different backend. For opt-in, preserve the selector and every required exact companion name configured by the operator. Known companion examples from the installed catalog are `ANTHROPIC_AWS_API_KEY`, `ANTHROPIC_AWS_BASE_URL`, `ANTHROPIC_AWS_WORKSPACE_ID`; `ANTHROPIC_GOOGLE_CLOUD_BASE_URL`, `ANTHROPIC_GOOGLE_CLOUD_PROJECT`, `ANTHROPIC_GOOGLE_CLOUD_LOCATION`, `ANTHROPIC_GOOGLE_CLOUD_WORKSPACE_ID`; and `ANTHROPIC_BEDROCK_MANTLE_BASE_URL` with explicitly opted AWS chain names. Gateway-specific host credentials are never guessed. These source-recognized modes are not live-verified by DorkOS. Future selectors unknown to this pinned catalog follow the documented unknown-name policy; there is no claim of automatic forward compatibility.

Codex custom `model_providers` can name arbitrary `env_key` and `env_http_headers` variables. Preserve the existing config file but require those exact parent names in the Codex custom list; reading a config name must not itself grant inheritance. Alternate endpoints stay in existing runtime config/SDK options. `OPENAI_BASE_URL` can be explicitly opted into for a CLI that supports it; the installed TypeScript SDK does **not** consume it itself and its `baseUrl` option uses an `openai_base_url` config argument. Do not fabricate a new DorkOS endpoint setting or move credential-bearing URLs into argv. Other/new CLI auth controls are custom until separately source-reviewed.

OpenCode's model catalog and config can enumerate arbitrary provider env names or substitute `{env:NAME}`. Never use that dynamic catalog or project config to widen DorkOS's inheritance. AWS Bedrock in OpenCode, Azure and other model services continue through their own auth/config files where supported; parent-only credentials need explicit custom names. Anonymous local models require no invented API key. Unknown DorkOS provider IDs keep the current no-injected-fragment behavior. The shared sidecar means custom names intentionally apply to every session it serves; per-agent environment isolation is not promised.

No extra diagnostics list detected credential names, profiles or values from the real environment. A rejected **known selector** may be named; ordinary unknown values are silently withheld and the migration documentation explains opt-in. Tests use only synthetic parent objects and source files.

## Required profile acceptance

Use table-driven synthetic positive and negative controls for every automatic row and every purpose. Standard Claude must withhold all AWS/Google/Azure credentials; each enabled cloud profile retains its documented alternatives and excludes other cloud rows. False/absent flags do not activate rows; multiple enabled flags retain SDK precedence. Settings-only mode plus parent credential demonstrates explicit opt-in migration. Account-pin undefined deletion is preserved. Model/default deployment names, privacy-disable flags including universal `DO_NOT_TRACK`, proxy/mTLS and filesystem login roots survive. Exercise the installed SDK telemetry predicate with only synthetic input to show preserved DO_NOT_TRACK retains opt-out. Capture the real default Ollama child-process seams (including promisified execFile) and prove a locator/hardware/provision child receives no automatic model or server-only credential; high-level mock command functions alone cannot prove this. The configured secret reference overrides the same permitted model variable and missing references preserve the existing fallback.

Codex's real installed SDK receives complete env even with no extraEnv and no Connections. OpenCode's sidecar receives the exact three-key union, selected override, path controls and fresh internal password only; arbitrary models.dev/project env declarations cannot authorize new parent names. Unknown/custom/reserved case-collision tests and wrong-purpose credential negatives must fail if the implementation broadens a catalog or reintroduces ambient inheritance. No live model, auth, cloud metadata service or installation is part of this proof.
