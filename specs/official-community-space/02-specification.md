# The DorkOS Community Space

**Status:** Approved for build (decisions below are final unless Dorian changes one)
**Author:** Claude (SPECIFY for Dorian Collier)
**Date:** 2026-10-07
**Linear:** DOR-2764 (parent DOR-2735)
**Ideation:** [`01-ideation.md`](./01-ideation.md)

## Overview

One official space, run on the shared Community host, where everyone using DorkOS talks. A person with a DorkOS account is a member the first time they show up: no invite, no request. The app shows the space from the first run, even with the spaces experiment off, and offers to connect it during onboarding. Our own agents answer in it. Owners and admins of any space can ban, mute, slow a channel down and work through reports, and members agree to the rules before they post. A message from a stranger in a space can never give anyone's agent power. The server holds thousands of people at once on one machine, and says when it is unwell.

The exception logic never compares against a literal hostname. The connection store records the origin and community id discovery returned at pairing; "official" is worked out on **every read** by comparing those to the current config, so changing the link immediately un-officials an old connection.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| D5  | The exception to DOR-2740               | One server predicate, `spaceReachable(ref)`: `spaces.enabled` OR the connection is official. Every action is audited. Every new table and column joins export, import, erasure, takedown and the deletion worker.                                                                                                                                                                                                                                                                                                                                                                                                                                     |

| D9  | Who can wake your agent in a space      | Per connection, `wakeAgentsFrom: 'me' \| 'members'`, operator-only. Default `'me'` for the official connection, `'members'` for every other (today's behaviour). With `'me'`, only your own @mention of your agent starts its turn.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| D10 | Strangers never give power              | Today only a brand-new session is protected: `externalAuthor` is checked on insert (`room-turn-runner.ts:629-650`), so if the owner's own mention created the mirror room's session first, a later stranger turn inherits the owner's level. **New rule:** every turn whose trigger is external runs at the stranger ceiling (the mode that asks, or `dontAsk` when the agent is set lower) whatever the session row holds, and nothing (the operator's level, the DOR-2739 flip, an unattended mode) raises it. Pinned end to end, including "owner first, stranger second". A space room's context says people outside this computer post there.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| D11 | Our agents host it                      | A staff DorkOS install holds a plain member seat (never admin: people moderate from their own accounts) with a dedicated host agent enrolled. Per connection, `answerIn: string[]` (operator-only) lists channels where a human post wakes the agent without a mention (the official host uses `welcome` and `help`), with a wake budget per author and per channel so a flood cannot buy unlimited turns. The host agent runs `dontAsk` with an exact read-only tool allowlist over the docs, written in the runbook, so a stranger's question can never make it act.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| D12 | Scale target                            | One machine, counted in streams (one per open channel, plus agents' background streams): 20,000 open streams, 50 posts a second for one minute, delivery p95 under 1 second, no errors. Live streams wake on Postgres `LISTEN/NOTIFY` with in-process fan-out, on a direct (unpooled) connection (`COMMUNITY_LISTEN_DATABASE_URL`, defaulting to the main one, with a self-test at boot). Notices carry ids only. Access checks are cached and dropped by a notice from **every** revocation source the 250 ms check covers today (`data.ts:328-390`: sessions, grants, agent credentials, lifecycle, channel archive and epoch, agent deactivation) plus bans and mutes. A 15 s fallback poll covers a lost notice; a listener reconnect re-reads every stream once. Pool size, a per-process stream cap and a per-community stream quota (503 with `Retry-After` past either) are config, so one community's spike cannot shut out the rest of the host.                                                                                                                                                                                    |
| D13 | Monitoring                              | `/health/ready` checks the database and the listener. `/metrics` (Prometheus text, host key required) reports open streams (total and per community), posts and joins per minute, pool waits, listener health and notice lag. The app shows a calm "not reachable right now" state for the official space. A public status page is a supplier choice (NEEDS DORIAN).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| D14 | Soft launch                             | Two weeks with current users before the public date. A runbook lists who is invited, what we watch daily, and the bar to launch: no data loss, no stranger-power regressions, the load target met on the production size, and every reported bug answered within a business day.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| D15 | Spam and rule checks (added 2026-10-07) | The `DecisionModel` design from `research/20261006_decision-models.md` (§5). A port in `packages/shared/src/decision-model.ts` and bridges in a new `packages/decisions`: built-in rules, OpenAI-compatible chat (forced JSON), and Jev through its System One endpoint. The Community server runs the ladder on each new post (rules, then a decision model) for two questions: spam (choice) and rule breaking (choice, labels from the space's rules). **Watch-only through the soft launch:** every decision is recorded as a `decision.*` audit row and shown to owners and admins as a hint in the report queue; nothing is hidden, held or removed by a model. Jev and one OpenAI-format model run side by side on the same posts so we can keep the one that agrees with moderators more often for less. Paid calls need their own switch (`COMMUNITY_DECISIONS_PAID=1`) beside each key; a key alone arms nothing, and a daily call cap per model applies. A decision can only narrow, never widen: no decision result reaches a permission or tool check. Neutral label codes, the post in its own field, failures count as unsure. |

## Work (each item is one PR; order below)

**Phase 1 (in parallel)**

1. **Community: open admission, auto-join channels, ban.** Migration adds `open` to `admissionPolicy`, `channels.auto_join`, a `bans` table (community, user, email hash, reason, actor, time). A join route for `open` spaces reuses the invite redeem path (handle minting, member cap, audit `member.admit` with origin `open`). Ban refuses preflight, redeem, open join, pairing and sign-in to that space; a ban removes the member (existing removal). Admin routes to ban and unban. Wire types and conformance capability flags updated. Space web UI: a join page for open spaces and the ban action.
2. **App: stranger safety, pinned.** End-to-end tests from a mirrored space message through `isEntryAuthorExternal` to the `'none'` seed; no automatic path raises a space room's session; a stranger cannot enroll, eject or spoof an agent; space rooms get the outsider framing in the room context; `wakeAgentsFrom` with tests for both values. Mutation-checked: each test fails when its guard is removed.
3. **Community: live streams that scale.** `LISTEN/NOTIFY` fan-out, cached access checks with invalidation, config for pool size and stream cap, `/health/ready`, `/metrics`.

**Phase 2**

4. **Community: mute, slow mode, reports, rules, display name.** Server routes, wire types, conformance, and the space web UI (moderation queue, rules editor, mute and slow-mode controls). Depends on 1 (same migration chain).
5. **App: the official space.** `spaces.official` config and migration, `official` on the connection record, `spaceReachable` and `useSpaceVisible` replacing the whole-feature checks from DOR-2740, the official row in the switcher, a "Join the DorkOS community" step in onboarding and after linking a DorkOS account. Depends on DOR-2740 merging.
6. **App: members' side of moderation.** Report a message, accept the rules, change your display name, and clear states for muted and slow mode, in the app's space view. Depends on 4.
7. **Load test.** `apps/community/load/`: a script that opens N readers and M writers against a server and prints delivery p50/p95 and errors. A recorded run against a local server, and the command Dorian runs against production size. Depends on 3.

8a. **Decision models: the port and three bridges.** `packages/shared/src/decision-model.ts` (types and Zod schemas only), `packages/decisions` (rules, OpenAI-compatible, Jev bridges; circuit breaker; `decisionModelConformance` in `@dorkos/test-utils`). No network in tests. Usable by the app server and the Community server. Coordinate with DOR-2745, which wants the same port for the loop judge.
8b. **Community spam and rule checks, watch-only.** Depends on 8a and 4. The ladder on new posts, `decision.*` audit rows, the hint in the report queue, the paid switch, daily caps, and a small comparison report (agreement with moderators, cost, latency per model) an operator can read from `/metrics` or the host API.

**Phase 3**

8. **Host agent.** `answerIn`, the host agent's `dontAsk` ceiling and docs access, its persona file, and `contributing/official-community-host.md` (setup runbook).
9. **Docs and story.** `docs/guides/dorkos-community.mdx`, the rules and code of conduct drafts, `CODE_OF_CONDUCT.md`, README and docs pointers. Site pointers land after the site retell (#2621). Never mention any other chat product.
10. **Soft-launch runbook and monitoring guide.** `contributing/official-community-operations.md`: alerts to wire, the daily checks, the launch bar from D14.

## Testing

- Community: Postgres integration tests for every admission path against a ban, mute and slow mode at the post route, report lifecycle, rules acceptance gate, and the fan-out (two streams, one notice, both wake; lost notice recovered by the fallback poll).
- App: the stranger-safety suite (item 2) and route tests for `spaceReachable` with the experiment on and off.
- Conformance: new capability flags run against the local, Buzz and remote adapters.
- Browser: one e2e journey per app item (5, 6) on the test-mode server.
