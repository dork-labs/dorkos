# API Reference

DorkOS runs a local REST and SSE API on your own machine, the same one the app's own interface talks to. Sessions, rooms, agents, the marketplace and more have endpoints here, so you can script them, build your own client against them, or point a tool you already use at your DorkOS instance.

The pages in the sidebar are generated straight from the running server's OpenAPI spec, grouped by resource (sessions, rooms, agents, marketplace, and so on). Each one documents the request shape, the response shape, and lets you try the call.

## What may change

Each operation is marked in the spec (`x-stability`):

- **Stable** operations are meant for your scripts and tools. When one has to change, the change and what replaces it are in the release notes.
- **Preview** operations are new or still being reshaped, and may change in any release. Their pages open with "Preview."
- The app's own plumbing, such as sign-in steps and settings pages, is not listed here. It can change at any time.

The spec's version is the DorkOS version, so you can tell which release a page describes.

## Base URL

By default the server listens on `http://localhost:4242` (or `:6242` in a dev checkout). Every path below is relative to that.

## Authentication

Most operations need nothing when a script runs on the same computer as DorkOS. A few ask for a personal API key even there, such as running a connected app's action from a script. Calls need a sign-in in two cases: you turn on "Ask for a password on this computer too" (or run `dorkos auth enable`), or the call comes from another device. (One exception for now: a browser reaching a Docker container through its published port, while the container runs with `DORKOS_ALLOW_INSECURE_BIND` and has no owner account yet, needs no sign-in.) Then a call needs one of two things. A browser sends the sign-in cookie it got when you signed in. A script sends a personal API key as `Authorization: Bearer <key>`. You create keys in DorkOS under **Settings → Login & security → API keys**, which shows up while you are signed in or the password setting is on.

Each operation's page says what it takes. A few need nothing from anywhere, such as the health check. The API document marks each one the same way, so a generated client knows how to sign in.

The `X-DorkOS-Agent` header names the agent making a call. It only says who is calling, and it never stands in for a sign-in, so it is not listed as a way to sign in. Agents reaching DorkOS from outside the app can also use the [MCP server](/docs/integrations/mcp-server) at `/mcp`, which takes an API key the same way.

## Prefer talking to an agent instead?

Most of what this API exposes, an agent already has as tools through the [MCP server](/docs/integrations/mcp-server). If you are building an integration rather than a script, start there.
