          message joins the session queue and runs when that turn ends. Either
          way the events are delivered solely on the durable `GET
          /api/sessions/{id}/events` stream (the single delivery path), and the
          `202` body says which happened: `outcome` carries the requested and
          applied disposition, `queuePosition` is 1 when nothing was ahead of
          it. A busy session is never a `409` here — read and edit what is
          waiting through `/api/sessions/{id}/queue`. The `202` also carries the
          CANONICAL session id: for a brand-new session this is the real id
          assigned during the turn (it differs from the client-supplied id), so
          the client re-keys its URL and `/events` subscription to it. To avoid
          missing the turn, a client should be subscribed to `/events` before
          (or concurrently with) this POST.'
