      - content: 'A **WebSocket** endpoint, not a plain GET: open it with
          `ws://`/`wss://` at this path (ADR 260804-030000 moved the durable
          streams off SSE, because an SSE stream holds one of a browser''s ~6
          sockets per origin and three cockpit windows spent all six). It is the
          single delivery path for session state (spec chat-stream-reconnection,
          ADR-0264/ADR-0266); NO feature flag or `enableCrossClientSync` gate.
          Every frame is a JSON text frame `{ "event": string, "data": unknown,
          "id"?: string }`. On a COLD connect the first frame is `event:
          "snapshot"` (a SessionSnapshot: completed messages, in-progress turn,
          status, non-expired pending interactions, and the resume `cursor`),
          then it goes live with one SessionEvent per frame, each carrying `id:
          "<sessionId>-<epoch>-<seq>"`. On a RESUME connect —
          `?resume=<sessionId>-<epoch>-<seq>` (the cursor moved from the
          `Last-Event-ID` header into the query because a browser `WebSocket`
          cannot set headers) or `?after=<cursor>` — it SKIPS the snapshot and
          replays only events with `seq` greater than the cursor, then goes
          live. A cursor the server cannot serve gap-free (mismatched epoch
          after a restart, or one trimmed past the replay buffer) falls back to
          the cold snapshot path instead of resuming. A `__heartbeat` frame is
          sent every ~15s so a client can tell a quiet stream from a dead one.
          Refusals (400/401/403/500) arrive as an HTTP status on the handshake,
          before any socket opens.'
