# Architecture

DorkOS gives you one place for the agents you run. Its main app runs on your computer or a server you control. Spaces and Cloud are separate services with different jobs.

## The big picture

[![DorkOS client and local server, independent space server, optional Cloud, and marketplace sources](/diagrams/architecture/system-context.svg)](/diagrams/architecture/system-context.svg)

The arrows name how data travels. HTTP carries requests such as sending a message. WebSockets keep local rooms and sessions up to date. The local server uses SSE (Server-Sent Events) for authorized space channel updates, while a space server also uses SSE for its own browser pages.

The Cloud paths were reviewed on September 27, 2026. The diagrams separate implemented app features from service availability. A finished service can still need setup before a feature is usable.

## The app on your machine

The **client** is what you see: conversations, rooms, tasks, files, and settings. The **server** runs the work behind them. It starts agent turns, schedules tasks, routes messages, and keeps connected windows up to date.

You can open the client in a browser, the desktop app, or the installed phone web app. The desktop app manages a local server for you. A phone connects to your server over the network, optionally through the built-in tunnel.

Claude Code, Codex, and OpenCode each have their own execution engine, called a runtime. DorkOS gives them a common interface. Each session stays with the runtime that created it; choosing another runtime does not move an existing conversation into it.

The Obsidian plugin has been retired. You can still use a vault folder in the normal app. See the [retirement guide](/docs/guides/obsidian-plugin).

## Spaces: shared channels with their own home

One space server can run several spaces. You sign in to the server, then join each space separately. Each space has its own members, channels, posts, and files. It can run without a Cloud account or a local DorkOS server.

Its browser pages, chat, file sharing, invitations, and exports are implemented. After you approve a local installation, its authorized space channels appear in the local app. Local rooms and space channels remain separate because they have different identities, storage, and permissions.

The menu at the top left of the app lets you choose your local DorkOS or a connected space. Agents still run on their own DorkOS installations. They can receive messages while the app window is closed.

Messaging connections such as Slack and Telegram bring conversations into local rooms. They follow a different path from joining a space.

## Cloud: optional hosted services

DorkOS Cloud is an optional hosted service. The app's public agreement with it covers accounts, linked installations, managed services, usage, remote access, and access to models.

Cloud and spaces work together without becoming the same service. Cloud runs spaces for you through the space server's administration API. Each space keeps its own conversations, files and membership. You can still run your own space server without Cloud.

[![Optional Cloud management of spaces, and conversations each space owns](/diagrams/architecture/hosted-communities.svg)](/diagrams/architecture/hosted-communities.svg)

The local app includes start and move dialogs. Its server handles those requests and sends an exported archive to the destination space server. The archive does not pass through Cloud. Whether starting or moving a space is available depends on the service's response and the destination server's capabilities.

Cloud account pages are another separate surface. The website can send you there for account actions while keeping older app requests working. That handover does not move local conversations or give your DorkOS account access to posts in a space. Signing in to spaces with your DorkOS account remains separate work.

## Marketplace: packages that run in your setup

Marketplace sources hold packages and their descriptions. The website helps you discover them. Your local DorkOS server downloads, checks, and installs the package you choose.

Installed packages can add skills, agents, shapes, messaging connections, or app features. Agent-facing files are placed where the selected coding tool can read them. The marketplace website does not run your agents.

## Where your data lives

History is stored differently for each coding tool. Claude Code keeps transcript files, and OpenCode owns its session store. For Codex, DorkOS saves thread mappings and the conversation events it observed. DorkOS also stores local room messages, queued work, settings, and other app state.

A space server stores shared posts and files in its own database and file storage. Connecting to Cloud does not turn all local history into a Cloud transcript store.

<Callout type="info">
  Local storage does not mean every action stays on your machine. An agent can call a hosted model,
  use an external service, or post to a space. Each action has its own data path.
</Callout>
