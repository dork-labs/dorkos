# Turning on the automatic loop

`/flow` can work through your ready queue on its own and stop at your review gate. You get the progress without babysitting every stage.

<Callout type="info">
  **"Automatic" means the loop carries work to a check, then waits for it.** The loop claims a ready
  item, drives it to a pull request with evidence, parks at the review gate, and waits. Who answers
  that gate is a per-project setting in DorkOS: you, or a separate reviewer agent that ships work it
  reviewed clean ([How much it does on its own](#how-much-it-does-on-its-own)). Without DorkOS, it's
  always you. Either way, nothing ships that nobody checked.
</Callout>

There are three ways to run this loop without hand-driving each stage yourself. They differ in one way: how the loop gets scheduled. All three carry one item along the same path (triage, through verify, to review) and stop at the same gate.

## The three setups

Pick based on how much you want running in the background versus in front of you.

| Setup                       | Needs a server running? | Runs...                           | Available now?      |
| --------------------------- | ----------------------- | --------------------------------- | ------------------- |
| **A: `/flow auto`**         | No                      | While your terminal is open       | Yes                 |
| **B: DorkOS Schedules**     | Yes                     | On a schedule, in the background  | Yes, off by default |
| **C: a scheduler of yours** | No                      | On a schedule you set up yourself | Yes, you wire it up |

<Cards>
  <Card title="A: Terminal drain (/flow auto)">
    Run it in your terminal and watch the queue drain to the review gate, item by item. Nothing to
    install. Stops when you close the terminal, so it's a great fit for a focused afternoon, less so
    for overnight.
  </Card>
  <Card title="B: DorkOS Schedules">
    A scheduled background loop that keeps working without you at the keyboard. Off by default, and

  </Card>
  <Card title="C: A scheduler of yours">

  </Card>

## A: `/flow auto` (the attended terminal drain)

`/flow auto` works through your ready queue one item at a time, right from your terminal. It needs no server and no setup beyond having the repo open.

### Setup

<Steps>
  <Step>
    **Be in the repo, with your tracker reachable.** No server, no install required.
  </Step>
  <Step>
    **Run `/flow auto`.** It claims the top-ranked ready item, carries it to its review gate, parks,
    then claims the next one. It keeps going until the queue is empty or nothing is left to claim.
    For a single item instead of the whole queue, run bare `/flow` and choose **Continue the
    queue**.
  </Step>
  <Step>
    **Watch it work.** Each item ends at a pull request with evidence attached, then stops at
    review. If it runs out of ready work, it asks whether to run a triage pass. If it hits a
    question, answer it in the terminal and it keeps going.
  </Step>
  <Step>
    **Answer the review gate.** Approve with `flow review <issue> --approve`. By default that also
    sets the pull request to merge once its checks pass. If you merge by hand instead, run
    `/flow:done <issue>` to close the item, file any follow-up work, and clean up. [Driving it
    manually](/docs/guides/flow/driving-it-manually) shows the review step in full.
  </Step>
</Steps>

**Pros**

- No infrastructure. Runs anywhere you have the repo open.
- You see every claim, every stage, and every question as it happens.

**Cons**

- Only runs while your terminal is open. Close it, and the drain stops.
- You answer the review gate yourself.

## B: DorkOS Schedules (the scheduled background loop)

A scheduled run moves the same drain off your terminal and onto the DorkOS server, so it keeps working while you're away. It runs on a schedule: each time it fires, it picks up exactly one ready item, carries it to the review gate, and stops. That keeps every run isolated and easy to pick back up if something goes wrong.

This is real today, but it ships turned off, and it needs the DorkOS server running.

### Setup

<Steps>
  <Step>**Start the DorkOS server.** The scheduled runs only fire while the server is up.</Step>
  <Step>
    **Register the project's DorkOS agent.** DorkOS watches that project's skills folder, which is
    where it finds the tick. The agent is also the identity the scheduled run works as.
  </Step>
  <Step>
    **Turn on the flow-drain schedule.** It arrives with the plugin and waits for you: open
    **Schedules**, read what it does, and approve it. Nothing runs on a timer until you do, and
    approving is the only step: it arms the schedule and switches it on together. There's no build
    step, and the change takes effect right away. (flow 0.6.0 and later ships its timing in a
    `schedule:` block. An older install lists `cron` and `enabled` flat at the top instead, which
    still works, but update the plugin from the Marketplace to see what this page describes.)
  </Step>
  <Step>
    **Tune how often it runs and how much it takes on.** It runs at the top of every hour. To change
    that, edit `flow-drain`'s time on the **Schedules** page. See [The
    dials](/docs/guides/flow/the-dials) for cadence and work-in-progress limits.
  </Step>
  <Step>
    **Watch and steer it.** `/flow:status` shows every item in flight, every parked question, and
    why each decision was made. `/flow pause` stops every automatic mode from one place; `/flow
    resume` brings it back.
  </Step>
</Steps>

**Pros**

- Makes progress with your terminal closed.
- Reacts to new ready work in the tracker on a regular interval.
- Each run is isolated, so a crash or a stall doesn't take down the next one. A run that stalls
  gets picked back up or restarted clean.

**Cons**

- Needs the DorkOS server running. No server, no scheduled runs.
- Still stops at the review gate until someone checks it: you, or the reviewer agent if you allow it.
- Checks for new work on an interval rather than reacting instantly.

## C: a scheduler of yours (no DorkOS server)

For repos that don't run the DorkOS server, any scheduler you run yourself can start the same loop: an OS `cron` line, a launchd job, or a scheduled CI job. Each time it fires, it starts one agent run of `/flow continue` in the repo. That run claims the top-ranked ready item, carries it to its review gate, and ends.

### Setup

<Steps>
  <Step>
    **Pick a scheduler.** To keep going with your laptop closed, use one that lives somewhere else,
    like CI.
  </Step>
  <Step>
    **Have each fire run `/flow continue` once** in the repo. Your scheduler's own entry sets the
    timing; flow never changes it.
  </Step>
  <Step>
    **Pause it the same way.** `/flow:pause` writes a pause flag into your project, and each run
    checks it first and stops. A scheduler on another machine, like CI, is paused by turning that
    job off.
  </Step>
</Steps>

**Pros**

- No DorkOS server needed. Works with any repo and tracker flow supports.
- Same loop as DorkOS Schedules, so nothing about how work gets carried to review changes.

**Cons**

- You set up the scheduler and keep it running.
- With nobody at a terminal, a question parks on the tracker and waits for your reply there.

## Which should I use?

Good news: you don't have to think hard about this one.

| If you want to...                                                      | Use...                                         |
| ---------------------------------------------------------------------- | ---------------------------------------------- |
| Put the loop to work right now and watch it, no setup                  | **A, `/flow auto`**                            |
| Do a single item, then stop                                            | **A, bare `/flow` then Continue the queue**    |
| Keep making progress while your terminal is closed, and you run DorkOS | **B, DorkOS Schedules** (approve `flow-drain`) |
| Run it on a repo with no DorkOS server                                 | **C, a scheduler of yours**                    |

Short version: attended and no server means A. Unattended and you run DorkOS means B. Unattended with no DorkOS server means C. All three stop at the same review gate; the only difference is who keeps the loop ticking.

## How much it does on its own

In DorkOS, each project has one dial in its Flow settings: **Ask me first**, **Tell me after** or **Just do it**. It decides who answers each kind of question.

- **Ask me first.** Flow asks you before it ships finished work, and an agent's question waits for you.
- **Tell me after.** The reviewer agent ships work it reviewed clean. An agent's question shows its own pick and a deadline; if you haven't answered by then, the agent goes with its pick. You get a note about each one.
- **Just do it.** The same, with quieter notes, and agents go with their own pick without asking, writing down why.

A new project starts at **Tell me after**. A project flow already worked in stays at **Ask me first** until you choose, and so does any project flow runs without DorkOS. A question about secrets or spending always waits for you. By default, flow also waits for a person to add the `security-reviewed` label before it sets a pull request to merge for the reviewer agent. [The dials](/docs/guides/flow/the-dials#how-much-it-does-on-its-own) has the full table.

## Staying in control

Autonomy never means losing the ability to see or stop what's happening, in any setup:

- **`/flow:status`** shows one screen with every item in flight, every parked question, and the
  reasoning behind each decision.
- **`/flow pause`** stops every automatic mode at once. **`/flow resume`** brings it back.
  `/flow pause for 1 hour` or `/flow pause until 9am` ends on its own at that time.
- **Reprioritize or turn off part of the loop** through its config.
- **Reassign an item** to redirect it. The change takes effect at the next stage boundary.

The loop also has a hard floor it never crosses, no matter how confident it is. Anything irreversible, anything that touches money or secrets, anything outward-facing, or anything that changes scope always stops and waits for you. That floor can't be configured away: a settings file that tries to remove it simply fails to load.

## Reference: how the loop works under the hood

Most people never need this section. Here's what's happening if you're curious.

- **One item at a time, unless you ask for more.** The scheduled run and `/flow auto` take one
  item, finish with it, then claim the next, capped at 2 items in flight overall and 1 per project
  by default. To work on several at once, run `flow drain --parallel <n>`: each item gets its own
  copy of the project and its own session, and a reviewer agent checks every push.
- **Ready work fuels it.** The loop only claims items carrying a "ready" label. Triage adds that
  label when it accepts an item; decompose adds it to the tasks it produces. No labeled work means
  nothing to dispatch.
- **It tells you when it runs dry, instead of going quiet.** If the ready queue empties out but
  there's still unshaped work waiting behind it, the loop says so and asks whether to run a triage
  pass, rather than just reporting "done" and leaving you to notice the backlog yourself.
- **Each scheduled run checks for stuck work first.** Before claiming anything new, it recovers any
  run that crashed mid-way and picks up any answer you left to a parked question. New work only
  gets claimed after that.
- **What a scheduled run actually is today:** each time it fires, it's a fresh chat that checks
  for recovery and resumed work, then dispatches, and carries one item to its gate. It gets you
  unattended progress to the gate. Whether it goes past the gate depends on [how much it does on
  its own](#how-much-it-does-on-its-own).
- **What's still ahead:** one always-on process that runs the loop nonstop instead of run by run,
  and a push-based connection to the tracker instead of checking on an interval.
