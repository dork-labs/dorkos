# The dials

`/flow` ships with sane defaults. Out of the box, it already runs the loop the way it's meant to: safe, sequential, and asking before anything risky. You don't need to touch anything on this page to use `/flow`.

Come here when you want to change one specific thing, like turning on the autonomous loop or getting pinged when a question is waiting on you. This page covers the settings most people reach for. The full list, with every block and its default, is the `config.schema.json` file that ships with the plugin.

## Quick win: turn on the autonomous loop

By default, `/flow` only runs when you type a command. Letting it work on its own schedule (a "tick" that claims one ready item and carries it forward) takes one step: approve it.

Open **Schedules** in DorkOS, find `flow-drain`, and approve it. Approving is the only step that matters: it arms the schedule and switches it on together, in one action.

flow-drain ships with its `schedule:` block set to `enabled: false` in `.dork/plugins/flow/skills/flow-drain/SKILL.md`. That flag is just the file's starting point, not something you need to hand-edit: DorkOS never arms a schedule from the file alone, and approving it flips `enabled` to `true` for you regardless of what the file says. (flow 0.6.0 and later ships the `schedule:` block shown below. If your copy lists `cron` and `enabled` flat at the top instead, it is an older install: update the plugin from the Marketplace.)

```yaml
---
schedule:
  enabled: false
  cron: '0 * * * *'
---
```

<Callout type="warn">
  Autonomous mode also needs a **running DorkOS server**. That's what actually fires the schedule.
  Manual `/flow` commands don't need the server running at all. If you want to stop it in a hurry,
  run `/flow:pause`: it stops every scheduled run in this project until you run `/flow:resume`.
</Callout>

Everything past this point is reference material: the full list of dials, grouped by what they control. Skim the headings and stop wherever you've found what you needed.

## Reference

### Where the dials live

Almost every setting lives in `config.json`, with a second file beside it for what belongs to your machine alone. Two things live elsewhere: the schedule, and how much flow does on its own.

| File                                                                | Owns                                                                                                                     | Validated by                                         |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `.agents/flow/config.json`                                          | The engine's rulebook: autonomy, eligibility, involvement, gates, loops, ingestion. Commit it: it is your team's policy. | `config.schema.json` (linked at the top of the file) |
| `.agents/flow/config.local.json`                                    | This machine's tracker account and overrides. Git ignores it, so it never leaves your computer.                          | Checked with `config.json` once the two are combined |
| `.dork/plugins/flow/skills/flow-drain/SKILL.md` (`schedule:` block) | The schedule's starting defaults. You change the real timing on the **Schedules** page, not in this file.                | DorkOS's Schedules page                              |
| DorkOS, per project (the project's Flow settings)                   | [How much it does on its own](#how-much-it-does-on-its-own). Only a person can change it.                                | DorkOS                                               |

That schema file isn't just documentation: it's enforced. If you type a value that isn't on the allowed list, or set a number below the floor `/flow` requires, the file fails to load instead of quietly misbehaving. Most code editors also read the schema reference at the top of `config.json` and give you autocomplete and inline errors as you type, the same way editors validate a `package.json`.

<Callout type="info">
  A per-repo `WORKFLOW.md` override is part of the plan for `config.json`, but nothing reads it yet.
  Adding one today has no effect. That piece is planned for a later, server-backed build.
</Callout>

<Callout type="warn">
  A few dials below describe a schedule (`priority`, `intervalMs`) that a future always-on process
  will run unattended. Today, each scheduled run (see the Cadence section) walks the loops in that
  same priority order once per tick, but nothing fires them independently in the background yet.
  Each such dial is flagged where it appears.
</Callout>

### Cadence: the scheduled run

Autonomous mode runs on DorkOS's **Schedules**. The plugin ships its starting timing in the `schedule:` block of `.dork/plugins/flow/skills/flow-drain/SKILL.md`, not in `config.json`. That block is also what makes the file a scheduled task at all.

To change how often it runs, open `flow-drain` on the **Schedules** page and edit its time. DorkOS keeps your timing on its side, so a plugin update never undoes it. The row then says **Your timing**, and **Reset to the package's default** puts flow's own timing back. Don't edit the file itself: the next plugin update replaces it.

Not using DorkOS? Any scheduler you run yourself (a `cron` line, a scheduled CI job) can start one `/flow continue` run per fire. Its own entry sets the timing.

```yaml
---
name: flow-drain
description: Claim the top-ranked eligible issue and carry it to its review gate.
schedule:
  cron: '0 * * * *'
  timezone: America/Los_Angeles
  enabled: false
  max-runtime: 2h
  permissions: acceptEdits
---
```

| Field                  | What it does                                                        | Default                        | To change it                                              |
| ---------------------- | ------------------------------------------------------------------- | ------------------------------ | --------------------------------------------------------- |
| `schedule.enabled`     | The starting switch. Installing never turns the run on.             | `false`                        | Leave it. Approving on the Schedules page switches it on. |
| `schedule.cron`        | When each tick fires. One tick claims and carries one item forward. | `0 * * * *` (top of each hour) | Edit the time on the Schedules page, not in this file.    |
| `schedule.timezone`    | The timezone the schedule is evaluated in.                          | `America/Los_Angeles`          | Edit it on the Schedules page, not in this file.          |
| `schedule.max-runtime` | Hard ceiling on how long a single tick may run.                     | `2h`                           | The plugin's choice. An edit here is undone by an update. |
| `schedule.permissions` | How much the unattended chat is allowed to do without asking.       | `acceptEdits`                  | The plugin's choice. An edit here is undone by an update. |

<Callout type="warn">
  The schedule ships `schedule.enabled: false`, and that flag is your intent, not your permission. A
  schedule DorkOS finds in a file still waits on the **Schedules** page for you to approve it,
  `true` or not. Autonomous mode also needs a **running DorkOS server** (it hosts the scheduler);
  manual `/flow` doesn't. `/flow:pause` halts every scheduled run in the project from one place.
</Callout>

### Autonomy

How aggressively the engine takes work on its own, under `autonomy` in `config.json`:

| Dial                | What it does                                                        | Default        | Notes                                                                 |
| ------------------- | ------------------------------------------------------------------- | -------------- | --------------------------------------------------------------------- |
| `default`           | Whether `/flow` runs all the way to a gate, or one stage at a time. | `"auto"`       | `"auto"` drains the ready queue; `"manual"` runs one stage and stops. |
| `concurrency`       | Reserved for a later build.                                         | `"sequential"` | Has no effect today. To run several items at once, see Drain below.   |
| `wipCap.global`     | Max items in flight across all projects at once.                    | `2`            | The ceiling on total concurrent work.                                 |
| `wipCap.perProject` | Max items in flight for a single project.                           | `1`            | Keeps one project from hogging the loop.                              |
| `seat`              | Which autonomous runner hosts the loop.                             | `"pulse"`      | `"pulse"` (DorkOS Schedules) is the only value the file accepts.      |

<Callout type="info">
  Setting `concurrency: "parallel"` is accepted, but it does nothing: the scheduled run and `/flow
  auto` always take one item at a time. Running several at once is the `drain` block below.
</Callout>

### Drain: several items at once

`flow drain --parallel 3` works on three ready items at the same time. Each gets its own copy of the project (a worktree) and its own agent chat, spread across the accounts you allow. A separate reviewer agent reads every push, and a pull request opens only after a clean review. These settings live under `drain`:

| Dial                | What it does                                                      | Default       |
| ------------------- | ----------------------------------------------------------------- | ------------- |
| `parallel`          | How many items a drain works on at once. `0` means one at a time. | `0`           |
| `host`              | Where chats run: `cli`, `cmux`, `dorkos`, or `auto` to pick one.  | `"auto"`      |
| `maxLivePerAccount` | The most chats one account runs at once.                          | `2`           |
| `maxLoadPerCpu`     | New chats wait while the computer is busier than this.            | `1.5`         |
| `maxReviewRounds`   | Review rounds before the item stops and waits for you.            | `5`           |
| `stallAfterMinutes` | Minutes without progress before a quiet chat is restarted.        | `60`          |
| `permissionMode`    | How much each chat may do without asking.                         | `acceptEdits` |

Each account flow may use has to join the rotation first; `flow accounts setup` walks you through it. See [Use all your accounts](/docs/guides/flow/use-all-your-accounts).

### Eligibility

Dispatch (the step that hands an item to the engine) only ever picks up work that's genuinely ready. Readiness is marked by the `agent/ready` label, applied at these stages:

<Steps>
  <Step>
    **TRIAGE** applies `agent/ready` (plus a `stage/*` label) when it accepts a piece of work,
    whether it's simple enough to go straight to EXECUTE or complex enough to need IDEATE first.
  </Step>
  <Step>**DECOMPOSE** applies `agent/ready` to each task it breaks work down into.</Step>
  <Step>
    **Dispatch** filters down to ready items, then ranks them. If the queue is empty but there's
    work waiting to be shaped, it says so ("0 ready, N shapeable: run a triage pass?") instead of
    going quiet.
  </Step>
</Steps>

`agent/ready` is a label on an item in your tracker, not a setting in `config.json`: the shaping stages produce it, you don't set it directly. What you _can_ tune is how the ready items get ordered, under `dispatch`:

| Dial                 | What it does                                                 | Default                                                              |
| -------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| `dispatch.rank`      | The order of tiebreakers used to rank ready items.           | `["unblockers", "priority", "projectStatus", "type", "size", "age"]` |
| `dispatch.sizeOrder` | At the size tiebreaker, prefer smaller items or larger ones. | `"small-first"`                                                      |

Dispatch also skips anything not actually dispatchable: items with open blockers, items in a finished or canceled project, items already at the WIP cap, and items your ownership settings don't allow it to touch. `agent/ready` is the dial you feed; everything else is a safety check.

### Involvement

When the engine asks you first versus just proceeds, under `involvement`:

| Dial                              | What it does                                                      | Default                                                                                 |
| --------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `comms`                           | How the engine decides its tone and channel when it talks to you. | `"infer-from-trigger"`                                                                  |
| `calibration.proceedSilentlyWhen` | Conditions under which the engine acts without asking first.      | `["reversible", "confident"]`                                                           |
| `calibration.alwaysAsk`           | The floor: these always require asking, no exceptions.            | `["irreversible-or-destructive", "outward-facing", "secrets-or-spend", "scope-change"]` |
| `calibration.stageBias.intake`    | Default posture during the shaping stages (IDEATE, SPECIFY).      | `"ask"`                                                                                 |
| `calibration.stageBias.execution` | Default posture during EXECUTE.                                   | `"proceed-and-log"`                                                                     |
| `nudge.relay`                     | Send a Relay ping when a question is waiting on you.              | `false`                                                                                 |
| `nudge.telegram`                  | Send a Telegram ping when a question is waiting on you.           | `false`                                                                                 |

The `comms` setting is the one that shapes tone day to day. The engine reads where a request came from (you, live in a `/flow` chat, versus an unattended tick) and checks it against the calibration rules above. That's why IDEATE tends to ask a lot and EXECUTE tends to just proceed: it's one rule reacting to context, not a separate switch per stage.

<Callout type="warn">
  `calibration.alwaysAsk` is a **floor, not a preference**. The file requires at least one entry
  here (an empty list fails to load), so nobody can accidentally configure the engine into asking
  for nothing. You can add more items to the floor. You can't remove the last one.
</Callout>

The `nudge` settings are the only way to get pinged outside your tracker. If you're the only person on the account (the common setup), a parked question otherwise shows up only as a tracker comment and an `agent/needs-input` label, easy to miss. Turning on `nudge.relay` or `nudge.telegram` adds a real notification so a stuck question doesn't sit there unnoticed.

### How much it does on its own

Each project has one more dial, and it isn't in any file in the repo. In DorkOS, open the project's Flow settings and pick **Ask me first**, **Tell me after** or **Just do it**. It decides who answers each kind of question flow runs into.

| Kind of ask            | Ask me first  | Tell me after                                | Just do it                          |
| ---------------------- | ------------- | -------------------------------------------- | ----------------------------------- |
| Ship finished work     | asks you      | the reviewer agent approves, and you're told | the reviewer agent approves         |
| Agent questions        | waits for you | the agent goes with its pick at the deadline | the agent picks and writes down why |
| Retry and fix problems | asks you      | on its own, and you're told                  | on its own                          |

Whatever you pick, someone checks. A question about secrets or spending always waits for you. **Customize** sets one kind apart from the rest. `flow autonomy` shows what's in force.

<Callout type="warn">
  **Where it starts depends on the project.** A new project starts at **Tell me after**, so its
  reviewer agent can ship work it reviewed clean. A project flow already worked in stays at **Ask me
  first** until you choose, and so does any project flow runs without DorkOS. Check a new project's
  setting before you leave it running.
</Callout>

The dial lives in DorkOS, not in the repo, because it decides who checks the agents, and an agent can write any file in the checkout. Only a person can change it. By default, when the reviewer agent approves, flow still won't set the pull request to merge until a person has added the `security-reviewed` label to it.

### Gates

The checkpoints between stages, under `gates`:

| Dial                                 | What it does                                                   | Default   | Notes                                                                               |
| ------------------------------------ | -------------------------------------------------------------- | --------- | ----------------------------------------------------------------------------------- |
| `planApproval`                       | Stop after DECOMPOSE for your sign-off before EXECUTE starts.  | `false`   | Off by default, so DECOMPOSE flows straight into EXECUTE. Turn on for a checkpoint. |
| `review.requireCiGreen`              | Require green CI before the review gate clears.                | `true`    | Part of the review gate, which is **always on**.                                    |
| `review.reapproveOnFunctionalChange` | Ask for a fresh approval if the change shifts after review.    | `true`    | Stops a stale approval from covering a diff that's since changed.                   |
| `review.mergeOnApproval`             | Approving at the review gate also sets the PR to merge.        | `true`    | Turn off if you'd rather press merge yourself.                                      |
| `circuitBreaker.estimateMultiplier`  | Trip a stop if actual work runs N times over the estimate.     | `2`       | Lower to catch runaway items sooner.                                                |
| `circuitBreaker.tokenBudget`         | Hard token ceiling for a single item before the breaker trips. | `2000000` | Raise for large items; lower to cap spend.                                          |

<Callout type="info">
  The **review gate** (after VERIFY) is always on. There's no setting that turns it off. Who answers
  it is [How much it does on its own](#how-much-it-does-on-its-own). The **plan-approval gate**
  (after DECOMPOSE) is the one you toggle, and it's off by default.
</Callout>

### Loops

`/flow` runs on a small set of internal jobs called reconcilers, one per loop. Each takes the same three dials, under `loops.<id>`:

- **`enabled`**: whether this loop runs at all.
- **`priority`**: lower numbers run earlier in a tick and win if two loops want the same item at once.
- **`intervalMs`**: how often the scheduler considers this loop due to run (in milliseconds).

| Loop       | `priority` | `intervalMs`         | What it does                                                  |
| ---------- | ---------- | -------------------- | ------------------------------------------------------------- |
| `recovery` | `10`       | `300000` (5 min)     | Picks back up or restarts work that got orphaned mid-flight.  |
| `inbox`    | `20`       | `60000` (1 min)      | Checks for replies on parked questions and resumes that work. |
| `review`   | `25`       | `300000` (5 min)     | Checks the auto-merge rules at the review gate.               |
| `dispatch` | `30`       | `300000` (5 min)     | Claims the top-ranked ready item and carries it to its gate.  |
| `triage`   | `40`       | `3600000` (1 hour)   | Classifies incoming work so dispatch never runs out of items. |
| `hygiene`  | `50`       | `21600000` (6 hours) | Housekeeping: flags stuck items, cleans up stale records.     |

The order isn't arbitrary: recovery goes first because losing in-flight work is the one mistake nobody forgives. Inbox comes next because a person waiting on a reply is the cheapest thing to unblock. Review and dispatch follow, and triage and hygiene bring up the rear as slow background chores. Want replies to resume faster? Lower `loops.inbox.intervalMs`. Want fewer tracker reads? Raise it.

<Callout type="warn">
  These `priority` and `intervalMs` values describe a schedule for a future always-on process that
  fires each loop independently. Today, each scheduled run (see Cadence above) runs the whole set in
  priority order once per fire, in the same order shown here. The `intervalMs` numbers are already
  set to the cadence that future process will use.
</Callout>

### Ingestion

How updates from your tracker reach the engine, under `ingestion`:

| Dial             | What it does                                            | Default         | Notes                                                           |
| ---------------- | ------------------------------------------------------- | --------------- | --------------------------------------------------------------- |
| `producer`       | Whether `/flow` polls the tracker or waits for a push.  | `"poll"`        | `"webhook"` is reserved for later; it isn't built yet.          |
| `pollIntervalMs` | How often polling checks the tracker (in milliseconds). | `60000` (1 min) | Lower for faster pickup; raise to ease up on the tracker's API. |

<Callout type="warn">
  Setting `producer: "webhook"` is accepted but does nothing today: it needs an inbound endpoint
  that doesn't exist yet. Leave it `"poll"` until that ships.
</Callout>

## Which dial should I touch?

| If you want to...                            | Turn this                                                                          |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| Turn the autonomous loop on                  | Approve `flow-drain` on the Schedules page, which switches it on (server required) |
| Stop it for a while                          | `/flow:pause` (and `/flow:resume` to lift it)                                      |
| Make the autonomous tick fire more often     | Edit `flow-drain`'s time on the Schedules page                                     |
| Run more than one item at a time             | `flow drain --parallel <n>`, or `drain.parallel`                                   |
| Let the reviewer agent ship clean work       | The project's **How much it does on its own** setting in DorkOS                    |
| Merge by hand after you approve              | `gates.review.mergeOnApproval: false`                                              |
| Cap how much work is in flight               | `autonomy.wipCap.global` / `wipCap.perProject`                                     |
| Get pinged when a question is waiting on you | `involvement.nudge.relay` / `nudge.telegram`                                       |
| Require sign-off on the plan before EXECUTE  | `gates.planApproval: true`                                                         |
| Cap spend per item                           | `gates.circuitBreaker.tokenBudget`                                                 |
| Make replies resume faster                   | `loops.inbox.intervalMs` (lower it)                                                |
| Ease up on tracker reads                     | `ingestion.pollIntervalMs` (raise it)                                              |
| Turn a loop off                              | `loops.<id>.enabled: false`                                                        |
| Change which loop wins when two collide      | `loops.<id>.priority`                                                              |
