# Securing Your Instance

By default, DorkOS runs with **no login**: instant start, no accounts, localhost only. That is the right default for a tool running on your own machine. The moment you want to reach DorkOS from another device, you turn on a real login: an owner account backed by a password, not a PIN.

<Callout type="info">
  Login is **optional and off by default**. Turning it on adds an owner account and a sign-in
  screen; nothing else about local use changes.
</Callout>

## Enabling login

<Steps>
<Step>
### Open Settings → Login & security

Open **Settings** (gear icon), then the **Login & security** tab, under **This computer**.

</Step>

<Step>
### Turn on "Ask for a password on this computer too"

Toggle **Ask for a password on this computer too**. DorkOS walks you through creating the **owner account**: an email and a password.

The email is a **local identifier only**: it is never verified and no email is ever sent.

</Step>

<Step>
### You're signed in

Once the owner account exists, this computer asks for your password too, and every other device always does. Your sign-in lasts 7 days and renews each time you use DorkOS, so you stay signed in across reloads and restarts. Sign out anytime from **Settings → Login & security**.

Turning **Ask for a password on this computer too** back off doesn't delete the owner account, it just stops asking for it: the account and any API keys stay put, and this computer opens DorkOS without a password again. Other devices still sign in as the owner.

</Step>
</Steps>

### Creating the owner from another device

If you create the owner account from a phone or another computer, DorkOS asks for a **setup code**. The computer DorkOS runs on saves it in a `setup-code` file in the DorkOS data folder, and prints it in its terminal when you started DorkOS from one. Type it into the setup form.

- A code works once and lasts an hour. Ask again for a new one.
- After too many wrong codes, new tries wait ten minutes. Creating the owner on the computer itself always works.
- Creating the owner on the computer itself never needs a code.
- A Docker container with no owner yet doesn't ask, for one more release. It logs a warning instead.

### "This browser can't keep the sign-in over plain http"

A sign-in cookie in a built DorkOS is marked secure, and browsers throw secure cookies away over plain `http`, except at `localhost`. So signing in at an address like `http://192.168.1.5:4242` used to bring you straight back to the sign-in screen. DorkOS now says so instead. Reach DorkOS over `https` (a [reverse proxy](/docs/self-hosting/reverse-proxy) or [your tunnel](/docs/self-hosting/tunnel-setup)), or use **Let devices on my Wi-Fi in**, which handles plain `http` on your own network.

## Exposing DorkOS beyond localhost

Want to reach DorkOS from your phone or another computer? Create the owner account first. Every other device signs in as it, whatever this computer asks, whether you get there through a tunnel or by binding to another network interface (any address other than your own machine, like your Wi-Fi IP).

<Callout type="warn">
  **Breaking change:** the 6-digit tunnel passcode is gone. Exposing DorkOS requires an owner
  account. Existing passcode settings are removed automatically on upgrade.
</Callout>

- **Starting a tunnel** with no owner account routes you into creating one first, with the copy _"Exposing DorkOS requires a login."_ After the owner exists, the tunnel starts.
- **Binding to a non-loopback host** (setting `DORKOS_HOST` to anything other than `localhost` / `127.0.0.1` / `::1`) with no owner account **refuses to start** with an actionable error. Create the owner account first, then restart.

### On your own Wi-Fi

To open DorkOS on a phone or tablet in the same home or office, you don't need a tunnel. On a Mac, in **Settings → Remote access**, turn on **Let devices on my Wi-Fi in**. On other computers, set `DORKOS_HOST` instead (see above).

- With no owner account yet, DorkOS walks you into creating one first, the same way the tunnel does. Every device on the Wi-Fi then signs in as the owner.
- It takes effect right away, with no restart. Settings then shows this computer's address, like `http://studio.local:4242`, a QR code to scan, and its current IP address as a backup.
- Turning it off closes the door at once.
- The connection between the two devices is **not encrypted yet** (plain `http`). Someone else on the same Wi-Fi could read what passes between them, including your sign-in, and use it to get in. So use it on a network you trust, never on café or hotel Wi-Fi. Encrypted connections are planned.
- Only devices on the same networks as your computer get in, including a VPN it is connected to. A connection from anywhere else is turned away.
- If `DORKOS_HOST` or `DORKOS_ALLOW_INSECURE_BIND` is set, it decides where DorkOS listens, and the switch stays off.
- The first time, your computer may ask whether DorkOS may accept incoming connections. Say yes.

Remote visitors reaching an exposed instance get the **sign-in screen**: static assets load so the login page renders, but every API call requires a valid sign-in.

<Callout type="warn">
  **Docker operators, this is you.** The official Docker image bakes in
  `DORKOS_ALLOW_INSECURE_BIND=true`. That is what lets the container accept connections through
  Docker's port forwarding, and it skips the bind gate that would otherwise stop a login-off server
  from listening beyond localhost. Until an owner account exists, anyone who reaches the port gets
  in, for one more release. So if you expose the container to anyone else, you are exactly who must
  [create the owner account first](/docs/self-hosting/docker#with-a-reverse-proxy).
</Callout>

<Callout type="info">
  DorkOS already slows password guessing: it allows 10 sign-in attempts from one IP address every 15
  minutes, then briefly blocks that address. Set `DORKOS_AUTH_SIGNIN_RATE_LIMIT` to a different
  number if that default gets in your way.
</Callout>

## Which addresses DorkOS answers to

With login off, DorkOS answers to `localhost` and `127.0.0.1` only, plus your tunnel address while a tunnel is running. A request that arrives under any other name gets a `403`.

That closes a browser trick called DNS rebinding. A web page you happen to visit can point its own domain at your own machine, and the browser then treats that page as if it came from DorkOS itself. Checking the address the request arrived under is what stops it, because the page cannot fake that.

Reach DorkOS by another name, such as `dorkos.example.com` through a reverse proxy? List it:

```bash
DORKOS_TRUSTED_HOSTS=dorkos.example.com,dorkos.internal
```

Separate names with commas and leave the port off. DorkOS matches the name only, so the port your proxy or `ssh -L` forward uses never matters.

<Callout type="info">
  Turning on login retires the whole question. A sign-in cookie belongs to one real address, so a
  rebound page never receives one and gets turned away at the door. DorkOS skips the address check
  entirely once login is on, which is why proxies and remote setups with a login need no extra
  configuration.
</Callout>

<Callout type="warn">
  **`DORKOS_ALLOW_INSECURE_BIND=true` also turns this address check off.** That setting says "the
  thing around DorkOS controls who reaches it", so it does more than let DorkOS listen beyond your
  own machine. It also stops DorkOS checking where each request came from, both the address it
  arrived under and whether it came from this computer at all. So if you set it once to get past the
  startup error, you gave up the rebinding protection above as well, even on `localhost`.

That is the right trade inside a container, which owns its own network boundary, and it is why the
official Docker image ships with it. It is the wrong trade on a normal machine. If you set it for
the listening reason alone, [turn on login](#enabling-login) instead and remove it.

</Callout>

## API keys for MCP, scripts, and agents

External agents (Claude Code, Cursor, Windsurf), scripts, and the MCP endpoint authenticate with **per-user API keys** instead of a single global key.

<Steps>
<Step>
### Create a key

**Settings → Login & security → API keys → Create.** Give it a name and an optional expiry.

</Step>

<Step>
### Copy it once

The key value is shown **exactly once** at creation. Copy it immediately: DorkOS never displays it again. Revoke a key anytime from the same screen.

</Step>

<Step>
### Use it as a Bearer token

Send the key as a Bearer token (a kind of key you attach to each request) in an `Authorization: Bearer <key>` header, to `/mcp` or any `/api/*` route.

**Reference:** here's what that looks like in practice.

```bash
curl -H "Authorization: Bearer dork_..." http://localhost:4242/mcp
```

</Step>
</Steps>

<Callout type="warn">
  **`MCP_API_KEY` does not open a side door past login.** Once login is on, the login gate answers
  `/mcp` first, and it only accepts a sign-in or a per-user API key — a client sending nothing but
  `MCP_API_KEY` gets a `401`. Use it for a **headless** setup (a server nobody signs into, like CI
  or a background job) where login stays off: there it is a fixed key you can hand to every client,
  it wins over the local token, and it can only be changed in the environment, never revoked from
  the UI. It does still work on the separate A2A gateway, which the login gate does not cover.
</Callout>

The old global MCP key (and its `POST /api/config/mcp/generate-key` / `DELETE /api/config/mcp/api-key` endpoints) have been removed. If you had a global MCP key configured, it is **migrated automatically** into an owner-owned API key the first time you create the owner account (or on the next server start if an owner already exists), so existing MCP clients keep working without changes.

## Recovering a lost password

There is no "forgot password" email: the local edition sends no email, and a laptop that already trusts you doesn't need one. Because machine access already implies owner-level trust, you recover from the command line:

```bash
# Reset the owner password (prompts, or pipe it in for non-interactive use)
dorkos auth reset-password
```

You can also create the owner and turn on the setting entirely from the CLI (useful before you ever open the UI, or when preparing a server to expose):

```bash
# Create the owner account and ask for a password on this computer too
dorkos auth enable
dorkos auth enable --email you@example.com --password '<secret>'
```

<Callout type="warn">
  If a server is already running, restart it after `dorkos auth enable`. The CLI writes
  `~/.dork/config.json` directly and the running server does not watch the file.
</Callout>

## Who can use an exposed instance

<Callout type="error">
  Anyone who can drive agents on an instance effectively has the server process's filesystem access
  and spends the owner's Claude quota. That is why registration is **owner-only**: the first account
  is the owner, and further sign-ups are closed. There is no second account today: sharing access
  means sharing the owner login itself. A viewer/operator role model that safely admits more people
  is a planned fast-follow; until it exists, only share the owner login with people you trust with
  your machine and your Claude account.
</Callout>
