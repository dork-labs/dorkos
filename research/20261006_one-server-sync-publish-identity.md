# DorkOS as "one software, many sizes": precedents, sync, publishing, agent mobility, identity

**Prior research in the repo, and a conflict with the new vision.** Four reports already cover parts of this:

- `research/20260724_multi-user-communities.md` (Buzz model, no federation, email-first identity)
- `research/20260727_agent-identity-in-communities.md` (owner attestation, "zero user-facing keys")
- `research/20260225_pglite_deep_dive.md`
- `research/20260717_cloud-sandbox-workspace-provider.md`

The new vision directly reverses three decisions in the 2026-07-24 report:

- **Decision 1:** `apps/community` is its own app, "structurally incapable" of spawning agents.
- **Decision 12:** the community deploys serverless on Vercel + Neon.
- **Decision 13:** the community has no filesystem.

Those decisions need to be formally replaced, not quietly drifted from. My suggested replacement is in Section 1.

## 1. Same software, many sizes

I didn't individually verify Nextcloud or the Supabase self-host setup. From memory: Nextcloud supports SQLite for small or test installs, and Supabase self-host is Postgres plus a set of separate services.

**Recommendation.** Use the **Gitea / Bluesky PDS pattern, and skip federation**:

1. **One server package with deployment profiles** ("personal", "community"). Don't build two apps. Replace Decision 1's guarantee ("structurally incapable") with a separate **runner** process that is the only thing allowed to spawn agents or touch the filesystem. A public community can then run with no runner, or with runners that live in sandboxes. The safety property survives; it just moves from "which app" to "which process".
2. **A storage seam with a conformance suite run against both SQLite and Postgres**, as Gitea does. The other option is Postgres everywhere, using PGlite on the laptop (see the existing pglite report). Both client and community already use Drizzle (`packages/db` with better-sqlite3, `apps/community` with pg). Supporting two dialects is a real ongoing cost, so this needs a spike before committing.
3. **Per-person "home" data stored like a Bluesky actor store.** Moving a home from laptop to cloud is then: copy the file, repoint the identity.
4. **Communities stay authoritative per server** (Buzz/Slack model). The client keeps N connections open. No Matrix-style room federation.

**Fit with the requirement** ("the laptop is sometimes offline, a cloud peer is always on, many people and agents edit"):

- **Document CRDTs fit best: Yjs, Automerge, Loro.** A document is just bytes, so the SQLite-vs-Postgres question goes away for documents: store a blob plus updates in either database.
- **Electric, Zero and PowerSync all assume Postgres upstream with logical replication.** That is a poor fit for a laptop whose authoritative store is SQLite. Zero's SQLite "Lite Sync" variant came up only in search snippets. **Unverified.**

**Recommendation.**

- **Documents: Yjs.** The client already uses Lexical, and Lexical has an official Yjs binding (`@lexical/yjs`; I didn't re-verify it in this session). Run a Hocuspocus-style endpoint inside the DorkOS server, so every server, laptop or community, can host documents.
- **Agents edit as ordinary Yjs clients on the server side.** They are members like everyone else, so their edits get cursors and attribution.
- **Keep Automerge or Loro on the watch list** for "agent proposes a branch, human merges", where Automerge's history model and Loro's version control are stronger.
- **Chat, channels and the roster should _not_ use CRDTs.** Keep the server-ordered log with `seq` numbers that DorkOS already has (the Linear/Figma pattern).
- **For comparison, Claude Docs** (beta, 2026-09-16) are "living documents you write with Claude and your team" that colleagues edit at the same time ([Axios](https://www.axios.com/2026/09/16/anthropic-claude-docs-microsoft)). That is the same product shape, hosted only.

## 3. Publishing from local to the web

| Option                                   | Example                                                                                                                                                                                                                                                                                                                                                       | Survives lid close?       | Updates       | Trade-offs                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | ------------- | ----------------------------------------------------------------------------- |
| (a) Laptop serves it through a tunnel    | Tailscale Funnel: ports 443/8443/10000 only, bandwidth caps you can't configure, `ts.net` names ([docs](https://tailscale.com/docs/features/tailscale-funnel)). Cloudflare quick tunnel: random URL that dies on Ctrl-C ([guide](https://flaviocopes.com/cloudflare-quick-tunnels/))                                                                          | **No**                    | Live          | Zero storage cost. Links break. Exposes the laptop's server to the internet   |
| (b) Push a snapshot to an always-on host | Claude Artifacts: public link, no ACL, no expiry, may be indexed, remixable ([Simon Willison](https://simonwillison.net/2024/Jul/9/claude-share-artifacts/), [Stacktree](https://stacktr.ee/blog/claude-artifacts-public-sharing)). Obsidian Publish is a separate paid service from Sync ([help](https://obsidian.md/help/sync)). Vercel/Netlify CLI deploys | Yes                       | On re-publish | Simple, cacheable, easy to reason about. Needs a host                         |
| (c) Sync to an always-on peer            | Anytype backup node; an always-on Yjs peer                                                                                                                                                                                                                                                                                                                    | Yes                       | Live          | The same mechanism as co-editing. Needs a host that can render live documents |
| AT Protocol                              | Standard.site lexicons for publications and documents on your PDS, rendered in Bluesky since 2026-05-27 ([atproto blog](https://atproto.com/blog/standard-site-bluesky-timeline))                                                                                                                                                                             | Yes, the PDS is always on | Live records  | Good for distribution and portability. Only fits documents                    |
| IPFS                                     | n/a                                                                                                                                                                                                                                                                                                                                                           | Only if pinned            | Immutable     | Pinning is just (b) again; no reason to pick it                               |

**Recommendation: (b) by default, with (c) as an optional "keep it live" toggle.**

- **Publishing writes an immutable, versioned snapshot** to the person's **publish host**:
  - by default, their home in DorkOS Cloud for desktop-only users;
  - or any DorkOS server where they have publish rights.
- **"Keep it live"** keeps the Yjs document syncing to that host, so edits show up on the published page.
- **Tunnels are only for "preview to a friend right now"**, and the UI should label them that way.
- **Copy the Artifacts features:** a stable link and remix ("open in your DorkOS"). **Don't copy its weakness** of no access control: offer public, unlisted and members-only.
- **Serve published HTML from a separate, sandboxed origin with a strict CSP.** DorkOS's own records note the canvas serve path still needs a content security policy before publishing reuses it.

I didn't research Replit Agent or Manus.

**What moves easily:**

- the transcript
- agent config and memory files
- the git state, once pushed
- secrets, if the host holds them and passes them through a proxy

**What doesn't move:**

- uncommitted or untracked files
- local apps and MCP servers listening on localhost
- a logged-in browser profile
- keychain items
- running background processes

**Recommendation: the agent's home is a server; a laptop is just one possible runner.**

- **The agent's identity, transcript, memory and inbox live on its always-on home**: a DorkOS Cloud home or a community server.
- **Execution happens on a runner:** the laptop, or a cloud sandbox (see the existing cloud-sandbox and Vercel Sandbox reports).
- **Give each agent a single "active runner" lease**, the same idea as one checkout, one writer. A handoff then works like this:
  1. finish or pause the current turn;
  2. push the branch;
  3. move the lease;
  4. the new runner checks out the branch and keeps going.
- **This makes handoff a true move in both directions.** Claude Code's teleport only makes a copy, one way. DorkOS owns the transcript (ADR-0310), so it can do better.
- **Be upfront about what doesn't travel:** "This agent uses your local browser; it will pause if moved."

## 5. One identity across servers

| Option                                                                                                                                       | Portable?                                                                                                                                                            | Works while the laptop is offline?         | User-facing keys?            | Cost                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ---------------------------- | ----------------------------------------------------------------------- |
| Matrix MXID (`@me:server`) plus OIDC through the Matrix Authentication Service ([MAS](https://matrix.org/blog/2025/04/matrix-auth-service/)) | No, tied to the server                                                                                                                                               | Only if your homeserver is up              | No                           | Identity dies with the server                                           |
| AT Protocol DID plus handle                                                                                                                  | **Yes**: rotation keys let you move hosts, even from a host that won't cooperate ([migration](https://github.com/bluesky-social/pds/blob/main/ACCOUNT_MIGRATION.md)) | Verification yes; logging in needs the PDS | Rotation keys are optional   | The PLC directory is a central dependency                               |
| Central account (Slack / Discord)                                                                                                            | Within one vendor only                                                                                                                                               | Needs the vendor                           | No                           | Every community depends on the vendor (rejected earlier as Decision 11) |
| OIDC with any home server as the identity provider                                                                                           | Partly                                                                                                                                                               | Only if that provider is always on         | No                           | A laptop can't serve as an identity provider when its lid is closed     |
| Keypair plus owner attestation (Buzz)                                                                                                        | Yes                                                                                                                                                                  | Yes                                        | Hidden, but recovery is hard | See the 2026-07-27 report                                               |

**Recommendation: home-server identity, email-first, with a stable DID-like ID underneath.**

1. **Every person and agent gets an opaque, stable ID**, such as `did:web` or a PLC-style ID. Rosters key on that ID, never on an email or a server-local row number (as the earlier report advised).
2. **Your home server is an OIDC provider for you.** DorkOS Cloud is the default home for people whose only install is a laptop, because an identity provider has to stay online. It is still **one optional provider, never the authority** (Decision 11 stands).
3. **When you join a community, it issues its own long-lived session** after the first OIDC handshake, so a laptop home being offline only matters for first join or re-auth.
4. **Moving homes works like the Bluesky PDS:** export the actor store and repoint the ID. Keep the signing keys device-held and invisible. That keeps Decision 3 ("zero user-facing keys") intact.
5. **Agents keep owner-attested identities** issued by their owner's home (as in the earlier report). A community admits an agent because it admits the owner.
