**How to read the levels.** Every row below names the highest level the evidence reaches, and what that level does not prove:

| Level                    | Means                                                                                                                          | Does not mean                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| **Implemented**          | The code is on `main` at the reviewed source, with its registration in startup.                                                | That it runs where a person uses it, or that anyone has used it.            |
| **Configured or tested** | Implemented, and either on by default with tests, or complete behind a default-off switch, a server role, or a test-only path. | That the switch is on anywhere real.                                        |
| **Released**             | The commit is an ancestor of the `v0.139.0` tag, so it is in the published CLI and desktop builds.                             | That it is on by default, or that a hosted service runs it.                 |
| **Deployed**             | A receipt (ticket comment, run log, Cloud confirmation) says it runs on a real host for real people.                           | Anything about load, support or launch readiness.                           |
| **Planned**              | A decision or spec names it. No code, or a contract only.                                                                      | That it is scheduled, or that its shape will survive contact with the code. |

A Done ticket is not deployment proof. Where Linear says Done and this review found no receipt, the row says so.

## The judgment

The October 9 assessment described a system with two separate server programs, a decision ladder nobody called, no beat runner, an audit trail with no read side and trust defaults still gated. **None of those four descriptions is true any more.** The space server's code moved into the DorkOS server package in October (server-merge step 7, DOR-2882, seven PRs merged between October 18 and 20). Heartbeats run on every install by default. The decision ladder has two production callers. The audit trail records every runtime tool call, has a read side that keeps a person's own chats private, and has a per-agent pause. The default permission preset is Trusted. The hub role, the session relay, the request classifier and the devices model from ADRs `261015-042933` and `261015-125850` are built in the app code, though the hub and relay sit behind a server role or a default-off setting and the hub image has booted only in CI.

What has **not** moved is instructive. The three recommendations from October that named unowned risk still name it: `AgentRuntime.acquireLock` still takes a response object (DOR-2346, Backlog); admin reset and restart still spawn a successor after a swallowed cleanup failure (DOR-2482, Backlog); and a failed audit write is still a gap in the record, never a block. The active-runner lease (server-merge step 8) and a Mac that hosts spaces (step 9) stay after launch, as decided. Hand-offs between room seats are still held in process memory (PR #4098 is open for that). The 20,000-stream bar for the official space (DOR-2879) has no run on any image since the per-channel lock fix.

So the right shape of this document changes. October asked "which boundaries should the one program have?" The program exists. November's question is "which of the three roles, and which seams between them, are proven at which level, and what do the gaps cost before early February?"
