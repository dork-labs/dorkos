## 3. The design: one function, two lists

### 3.1 Principles

1. **One function.** `flow next` (the flow plugin, `selectDispatch` extended) is the only code that ranks work. Nothing else sorts a work item: not a brief, not a digest, not a mini app page.
2. **Only Linear fields go in.** Priority, state, labels, estimate, due date, relations, project status, project priority, project target date, project relations, created time. No chat, no decision log, no file in `.temp/`.
3. **Same data in, same order out.** No model in the loop. Input order never matters. A fixture test proves it.
4. **Overrides are visible.** The only way a person moves an item against the fields is a `pin` label with a reason comment, and the output shows it at the top. Everything else a person wants, they change the field for.
5. **Skips are visible.** An item that is not ranked says why (blocked by X, needs a project, needs a size, pinned out), in the output and in Linear. No silent skip.
6. **Projects first, then issues.** Started projects feed the order, in their own rank. An issue's place inside its band comes from its project's place.
7. **Execution order is not priority.** The heavy line and the merge train take the work order as an input, never the other way round.

### 3.2 Projects

**Which projects count** (Linear project status type):

| Status              | Role in the order                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| Started             | Feeds the issue order. Shown first as "now", in project rank                                            |
| Planned             | Queued. Shown as "next", in the same rank. Its issues do not rank, except Urgent ones and release gates |
| Paused, Backlog     | Out. Shown only in `--all`                                                                              |
| Completed, Canceled | Out                                                                                                     |

**Project rank**, ascending, each a Linear field:

1. **Pinned** (project label `pin`, with a reason in the project update or description) first.
2. **Project priority** (Urgent 1, High 2, Medium 3, Low 4). No priority sorts last and is flagged `needs a priority`.
3. **Target date**, earliest first. None sorts last and is flagged `needs a target date`.
4. **Dependencies.** Linear project relations (`Project.relations`, the project graph; the API field exists, nothing uses it yet). A project blocked by an unfinished project is flagged `can't start: waits on <P>` and its issues do not rank. The blocker inherits the better of its own rank and its dependants' ranks, so the thing in the way rises.
5. **Remaining work**: the sum of estimates on its open issues, smaller first (unsized issues count as the largest bucket, so a project nobody has sized does not look small).
6. **Created time**, older first; then the project's slug id.

**The cap.** `projects.startedCap` (proposed 6) lives in `.agents/flow/config.json`, the flow config the PM owns and Code edits by a one-line PR. The function never changes a project's status. It reports `over cap: N Started, cap M; lowest: <P1>, <P2>` and the groom lists it every day until a person pauses or finishes one. A Planned project is "ready to start" only when Started < cap, its target date and priority are set, and nothing blocks it.

**Standing projects.** Maintenance has no end, so "no target date can't be Started" would stop every Maintenance Must. Pick: the PM gives Maintenance a rolling target date (the last day of the month) at the Monday grooming, and the function keeps one rule. Option 2: a project label `standing` that exempts a project from the date rule and the cap. Fewer edits, one more concept. (§6, call 3.)

**Exclusion.** A project the operator's own manual chats run gets the project label `owner/dorian`. Its issues leave the agent order and appear in a separate "Dorian's list". The same label on an issue does the same for one item (the Desk items the PM named).

### 3.3 Issues

**Which issues count**, by Linear state type and fields:

| State                                                            | Role                                                                                                                                         |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Todo (`unstarted`), Backlog (`backlog`)                          | Candidates                                                                                                                                   |
| Triage (`triage`), or no priority, or no project, or no estimate | Not ranked. Listed under **needs triage** with the missing field named. Exception: an Urgent issue or a release gate ranks without a project |
| In Progress (`started`, not In Review)                           | **In flight.** Listed first with its owner; counts toward WIP; never re-ranked                                                               |
| In Review                                                        | Listed as **in review**; not "next"; counts toward WIP                                                                                       |
| Done, Canceled, Duplicate                                        | Out                                                                                                                                          |

An issue in a project that is not Started does not rank unless it is Urgent or a release gate; it is listed under its project as "waits for project". An issue blocked by an open issue does not rank; it is listed under its blocker as "held by DOR-x". An issue labelled `owner/dorian`, or in an `owner/dorian` project, is out of the agent order.

**The band** (the first key):

| Band           | Rule                                                     | Linear fields                                          |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 0 pinned       | A person said so; the very top (Dorian, Nov 22 10:54 CT) | label `pin` plus a comment starting `pin:`             |
| 1 Urgent       | Broken now                                               | priority 1                                             |
| 2 release gate | Needed by the next release                               | label `release-gate`; the due date is the release date |
| 3 Must         | High and PM-confirmed                                    | priority 2 **and** state Todo                          |
| 4 Should       | Medium, or an unconfirmed Must                           | priority 3, or priority 2 still in Backlog             |
| 5 Could        | Nice to have                                             | priority 4                                             |

**Inside a band**, ascending:

1. **Due date**, earliest first; none last.
2. **Unblocks**: how many open team issues this one blocks, more first (counted against every open issue in the team, not only the candidate set).
3. **Its project's rank** (§3.2). Urgent issues skip this key: broken is broken, whatever the project.
4. **Type**: `Bug`, then `Improvement`, then `Feature` (Linear's labels, which the humans use; flow's `type/*` group maps `task` and `idea` onto them). This is the PM's "broken or confusing before new".
5. **Size**, smaller first; unsized last.
6. **Created time**, older first.
7. **Issue number**, lower first (numeric, replacing today's string compare).

**Inheritance.** A blocked issue D does not rank, but its blocker B takes the better of its own key and D's key, through any depth (B blocks C blocks D: B sorts where D would). The output says `inherits DOR-D's place`. This is the PM's "whatever unblocks them takes the highest rank of what it blocks", and it replaces today's unblocker count as the first thing that matters after the band.

**Readiness is an output, not a filter.** Today `agent/ready` hides an item from the order; that is why `/flow` sees nothing. Proposed: the order is the order. Each item carries `ready: true | false` and, when false, the reasons: `needs a size`, `needs a done-when`, `needs a decision (DOR-x)`, `blocked by DOR-y`. The drain's first job when the top item is not ready is to make it ready (the triage stage), or to hand it to a person with `agent/needs-input`, which is a visible skip. The `agent/ready` label stays as the claim gate and the groom's invariant, so an agent never starts building an unready item; it no longer decides what is next. One vocabulary: flow accepts `## Done when` as its validation-criteria section, so an issue filed by the rubric is also ready by flow's rules.

### 3.5 The output: "why this rank"

`flow next --json -n 10` returns, per item: its place, the band, and a `why` list in plain words, one entry per key that decided it: `pinned: "ships with 0.141 (PM, Nov 24)"`, `Must (High, Todo)`, `due Nov 27`, `unblocks DOR-4981`, `project #2 Release branches`, `Bug`, `size 2`, `filed Nov 19`, `inherits DOR-5027's place`.
