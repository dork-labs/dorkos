## Boundary and evidence vocabulary

This audit covers local marketplace install, update and uninstall recovery. It does not change behavior, required gates, shared test infrastructure, authentication, server composition, runtime/transport contracts, Cloud or Community. Existing local reconnect work remains with DOR-1912/DOR-1916. Source citations describe the pinned revision; Linear owns current status.

- **Persistent coverage:** committed executable assertions for a stated boundary.
- **Recorded proof:** a previous run whose result is documented; not a fresh run or necessarily reproducible from a committed harness.
- **Missing proof:** the claimed boundary has not been demonstrated by the evidence inspected.
- **Persistent coverage gap:** a useful demonstrated scenario lacks a retained regression test. This is not itself a defect.
- **Defect:** observed behavior contradicts the intended guarantee. The retained-copy finding below is separately reproduced; the recovery audit found no new recovery defect.

### Current gate and platform limits

[Server package scripts](../apps/server/package.json) run Vitest. The [test workflow](../.github/workflows/test.yml) runs affected PR suites (`test.yml:769`), full sharded merge-queue suites (`:687`) and the required `test` fan-in (`:943`). Its runners are Ubuntu. A docs-only PR can skip execution through path selection; the gate's existence does not mean every suite ran on this PR. Local verification receipts are recorded below.

This is Linux CI coverage plus the explicitly recorded local macOS runs, not a Linux/macOS/Windows recovery matrix. No CI change is part of this delivery. `atomicMove` has EXDEV fallback coverage; that is not proof that a recursive cross-device copy is atomic. Process-crash recovery also does not establish host-power-loss durability: a journal sync alone does not prove every file and parent-directory write is durable.

### Shipped work and prior process proof

The audit credits DOR-2273 (backup recovery, PR #2041), DOR-2245 (file ownership, PR #2084), and DOR-2322 (unproven-file classification). Completed cache retention, batch updates, MCP updates and update UI work are not reopened merely to organize this matrix.

[The ownership implementation record](../specs/marketplace-package-file-ownership/04-implementation.md#42-proof) records real installer/fetcher harnesses with direct Node-process SIGKILL on APFS. The three windows were mid-uninstall side effects, installed tree before commit, and staging. Each restored a byte-identical 870-file snapshot with no sibling left. The temporary harnesses were deleted. The record also distinguishes an unsuccessful first attempt that killed `pnpm` instead of its child.

That is prior proof, not a fresh kill run in this audit. Lack of a retained harness limits reproducibility, but does not erase the deterministic crash tests or justify a generic duplicate suite. **Disposition:** defer a dedicated process harness until record-owner, journal or process-boundary changes require fresh proof. If selected, the marketplace owner should retain one opt-in local fixture with direct PID ownership, deterministic IPC checkpoints, complete-tree hashes and exact settlement assertions. No paid resources or new CI lane are implied.

## Retained-file triage

### DOR-2340: confirmed local defect, implementation deferred

[DOR-2340](https://linear.app/dorkspace/issue/DOR-2340) - Saved copies keep execute bits and stay runnable.

[Retained reproduction](20260926-marketplace-retained-copy-reproduction.md) calls the real carry, program disclosure, skill disclosure and Harness Sync scanner functions. `carry-as` and `save-new-as` preserve `0755`; harmless fixture scripts execute. `carry-dir-as` creates `skills/x.dork-old/SKILL.md`, which both skill discovery and disclosure find. Clearing execute bits alone still leaves the saved program in `readPackagePrograms().executables`. This proves local execution/discovery behavior, not an agent turn or an approval bypass.

Required outcome: recovery copies preserve recoverable content but cannot become independently discovered or activated package capabilities merely because they remain on disk. A chmod-only patch is incomplete. Changing discovery/disclosure changes global approval digests (`global-plugin-consent.ts:204,457`), so an isolated reader change is not automatically compatible with DOR-2306.

The architecture coordination review selected **design first, no behavior change in this slice**. Alternatives to assess are location/metadata-based quarantine and coordinated discovery/disclosure filtering. Neither is approved implementation. The existing issue owns decisions about existing-copy migration, collision naming, restoration, interpreter-readable content, directory-based skills, and compatibility with prior approvals. Revisit when that design can demonstrate both non-activation and recoverability without broadening approval. No implementation-ready label is implied.

### DOR-2341: unresolved product semantics, preservation works as designed

[DOR-2341](https://linear.app/dorkspace/issue/DOR-2341) - A person-only ownership action for unresolved kept files.

The real `sortUnprovenFiles` returns `no-source` without fetching, or `fetch-failed` when historical content is unavailable. Both leave the record and person file byte-identical. Existing `lib/integrity/__tests__/strict-record.test.ts:648–681` pins this safety policy. The persistent reminder is a product limitation, not demonstrated data loss.

Before a “Keep these as mine” action, specify the authority allowed to accept ownership; the exact file set, bytes and package version being accepted; what runnable content is disclosed; how concurrent edits invalidate acceptance; and how a person reverses a mistake. Ownership acceptance must remain distinct from activation approval. Clearing `unproven` changes guards in `global-plugin-consent.ts:341,644`; it cannot be treated as harmless metadata cleanup. UI, CLI and agent approval behavior require separately approved design. Keep the existing issue open without implementation readiness, and revisit once those semantics are settled.
