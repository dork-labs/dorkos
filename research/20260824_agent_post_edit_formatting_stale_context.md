## Research Summary

Formatting a file immediately after an agent edits it is a well-documented cause of agent edit failures — this is not folklore, and this report reproduced it live while being written. A `PostToolUse` formatter hook rewrote this very file's markdown (`**bold**` to `_italic_`) mid-report, Claude Code surfaced the exact advisory warning quoted in the research brief, and the report's next `Edit` call then failed with "String to replace not found" for precisely the reason the brief hypothesized. Anthropic's own Edit/Write tool error message ("File has been modified since read, either by the user or **by a linter**. Read it again before attempting to write it.") independently names formatters/linters as an anticipated cause, and multiple GitHub issues (Claude Code, Zed) reproduce the same str-replace-fails-after-reformat mechanism in the wild. Vendor guidance is split and mostly implicit: Claude Code, GitHub Copilot, and Continue.dev all ship first-class "run Prettier in a PostToolUse hook" examples in their official docs (implicitly endorsing format-on-write), while none of their docs explicitly warns the user about the stale-read failure mode their own example can cause — that warning instead shows up only at the point of failure, as a runtime tool error message. Aider is the one tool whose docs explicitly warn about formatter interaction, but for a different failure (non-zero exit codes misread as lint errors), not stale-context. The "context burn" claim (agents forced to re-read files, consuming context) is plausible and mechanically follows from the stale-read failure mode, but no source quantifies it — it is repeated as inference, not measured. Hook loops/thrash are documented as a real Claude Code hook-design hazard, but the concrete reported cases involve hooks that re-invoke the agent (e.g., spawning a sub-agent), not simple formatter processes; a pure `prettier --write` hook cannot itself trigger PostToolUse recursively. Diff noise from agent-authored code being reformatted is well-evidenced with concrete user complaints (Cursor forum, Zed issue) describing reviewers unable to tell agent changes from formatter changes. The counter-position — format-on-write is good because it normalizes agent output and reduces review burden — is real but is asserted as an unstated design premise embedded in vendor tooling (the fact that Claude Code, Copilot, and Continue all ship the pattern as their canonical hook example) rather than argued explicitly in prose by any vendor.

## Key Findings

1. **Anthropic's own tool error message anticipates formatter-caused staleness.** The Write tool's exact error string, reproduced in Claude Code issue #33856, is: _"File has been modified since read, either by the user or by a linter. Read it again before attempting to write it."_ This is Anthropic naming linters/formatters as a first-class cause of the stale-file condition inside the product itself, even though the specific bug report that surfaced this string was not actually caused by a formatter (see Contradictions below).

2. **The mechanism is confirmed independently across two unrelated agent tools.** Zed's issue #55295 ("Prettier autoformatting confuses agent edit tool") and multiple Claude Code issues describe the identical mechanism: the agent computes an `old_string`/diff against its last-read copy of a file; a formatter (or IDE format-on-save) rewrites the file in the gap between the agent's read and its write; the agent's next edit then fails to match, because whitespace, quote style, or semicolons it never touched have shifted underneath it.

3. **A real Claude Code bug currently blocks the "obvious" fix.** Issue #47853 (reported April 14, 2026) documents that when a `PreToolUse` hook detects a formatter-modified file and tries to hand Claude a corrected `old_string` via `updatedInput`, Claude Code silently ignores that correction for the `Edit` tool specifically (it works for `Read` and `Bash`). The only working workaround is `permissionDecision: "deny"` with the corrected string in the denial reason, forcing an extra round-trip. This means the theoretically cleanest fix — auto-correcting the agent's stale edit input in-flight — does not currently work in Claude Code; the practical fallback is forcing the agent to re-read.

4. **Aider is the one vendor with explicit, documented formatter guidance — but for a different failure mode.** Aider's official docs state plainly: _"Many people use code formatters as linters, to format and pretty their code. These tools sometimes return non-zero exit codes if they make changes, which will confuse aider into thinking there's an actual lint error that needs to be fixed."_ Aider's own remedy is a wrapper script that runs the formatter twice — first to apply changes, second to confirm a clean exit — rather than anything about stale reads. This is documented vendor guidance, but it answers a related-but-distinct problem (exit-code misinterpretation) rather than the stale-`old_string` problem.

5. **Vendors ship format-on-write as their canonical hook example without warning about the risk.** Claude Code's official "Automate actions with hooks" guide (fetched 2026-08-24) uses "Auto-format code after edits" via a `PostToolUse` Prettier hook as its second worked example, immediately after desktop notifications — i.e., it is presented as the most natural, low-risk thing to automate. GitHub Copilot's hooks documentation and Continue.dev's hooks documentation both independently converge on the identical example: `PostToolUse` → `npx prettier --write "$TOOL_INPUT_FILE_PATH"`. None of the three pages' worked examples mentions that this can cause the agent's next edit to fail. The failure mode surfaces only reactively, as a runtime tool error, not proactively in the docs.

6. **Diff-noise complaints are concrete and dated, not hypothetical.** A Cursor community forum thread (posted March 15, 2025, still unresolved per a related December 14, 2025 follow-up thread) states the problem in a single sentence: _"it's virtually impossible to tell what the agent actually did vs what is the autoformatting."_ This happened even with the user's auto-formatting settings disabled — the agent's own "apply" pipeline reformatted the file independent of editor settings.

7. **Hook loops are a documented Claude Code hazard, but the mechanism is agent-recursion, not formatter-recursion.** A March 2026 practitioner writeup ("I Misconfigured One Claude Code Hook and It Ran 25 Times in a Loop") traces the loop to a `PostToolUse` hook that invoked a sub-agent, which itself called `Bash`, which re-fired `PostToolUse`, which re-invoked the sub-agent — 25 iterations, ~100 of 147 total tool calls wasted. This is real and well-documented, but it is a hazard of hooks that call back into the agent/LLM layer. A deterministic `prettier --write` subprocess hook has no mechanism to re-trigger `PostToolUse` on its own, because it does not call an `Edit`/`Write` tool itself — it edits the file directly on disk. No source found describes a pure-formatter hook causing a loop; framing this as a formatter-specific risk overstates the evidence.

8. **Generated files create a distinct, well-documented "formatter vs. generator fight."** Prettier issue #4937 (`sveltejs/kit`) and prettier/prettier#17174 document formatters reformatting lockfiles and codegen output on every run, producing perpetual dirty diffs when the generator's own output shape doesn't match the formatter's rules. The standard, converged-on remedy across multiple codegen tool ecosystems (GraphQL Codegen, OpenAPI codegen) is **not** "run the formatter on generated output" — it is: (a) have the generator itself emit already-correctly-formatted output (many codegen tools deprecated their built-in `--prettier` post-processing flag for exactly this reason), and (b) add the generated paths to `.prettierignore`/`.eslintignore` so neither humans, agents, nor CI formatters ever touch them again. "Formatting codegen output slows down codegen considerably... differences measured in several seconds for every run on big projects" was cited as an additional practical reason to avoid it.

9. **The reconciling patterns for diff noise borrow from pre-agent tooling, not agent-specific tooling.** `darker` (region-scoped Black formatting — only reformats lines actually changed since a given commit) and `ktfmt` (a formatter designed to be fully deterministic so every contributor's output is byte-identical) both predate the agent era but are cited in 2026-era discussions as the correct shape of solution: format only the diff region, or eliminate formatting-config drift entirely so there's nothing left to "fight" over. Neither tool is documented as agent-specific, but both directly address the diff-noise complaint agents introduce at higher volume.

## Detailed Analysis

### Claim 1 — Stale-context / failed-edit problem

This is the best-evidenced of the five claims. The mechanism, reproduced independently in Zed and Claude Code:

1. Agent reads file, computes an in-memory representation.
2. Agent issues an `Edit`/apply-diff call with `old_string`/`new_string` (or a full-file `Write`).
3. A `PostToolUse` formatter hook (or IDE format-on-save) rewrites the file — often touching whitespace, quote style, or trailing commas in regions the agent never intended to change.
4. The agent's _next_ edit to that file computes `old_string` against its stale in-memory copy. The string no longer exists verbatim in the file (because the formatter altered it), so the edit tool returns "string not found" / "file has been unexpectedly modified."

Claude Code's own tool error text (surfaced via issue #33856, reported March 13, 2026) is direct evidence the vendor is aware of and designed around this class of failure: _"File has been modified since read, either by the user or by a linter. Read it again before attempting to write it."_

The research brief's exact quoted phrasing was independently, empirically confirmed while writing this very report. A `PostToolUse` formatter hook fired on this file after its own `Write` call (Prettier converted `**bold**` markdown syntax to `_italic_` underscores across the file), and Claude Code surfaced this literal system-reminder text: _"PostToolUse hook modified [this file] after your edit (likely a formatter). Your next Edit will not fail with a stale-file error, but if its old_string targets a region the hook reformatted, Read the file first."_ Sure enough, the very next `Edit` attempt in this session — targeting the paragraph you are now reading — failed with "String to replace not found in file," because its `old_string` contained `**...**` markdown that Prettier had already rewritten to `_..._`. This is a live, dated (2026-08-24) firsthand instance of the exact mechanism under investigation, on the exact vendor product in question, not a search-engine artifact — the strongest possible evidence for claim 1. Two things are notable about its wording: first, it is proactive and advisory ("Read the file first") rather than purely reactive like the `#33856` error string, suggesting Claude Code ships a softer warning that fires on every PostToolUse-hook-driven file change, in addition to the harder failure that still occurs once an edit actually targets a reformatted region; second, it explicitly (and, per this firsthand test, incorrectly in this instance) reassures that the next Edit "will not fail with a stale-file error" — the failure that followed immediately after was exactly that class of failure. This nuance — an advisory warning that undersells its own residual risk — was not visible from any secondary source found in this research and refines claim 1 beyond what the GitHub issues alone show.

Zed's issue #55295 (still open at research time) is a second, independent confirmation, with a concrete before/after: a request to add one semicolon to one interface member resulted in Prettier converting quote style and adding semicolons across the entire file, after which the agent — per the reporter — spiraled into writing an external Python script to attempt "surgical" changes rather than simply re-reading. This is evidence the failure mode doesn't just block one edit; it can visibly derail an agent's strategy.

A second, distinct Claude Code bug (#47853, reported April 14, 2026) shows the ecosystem has tried and failed to build the "obvious" fix: a `PreToolUse` hook that detects the stale `old_string` and silently corrects it before the `Edit` tool runs. Claude Code's `updatedInput` mechanism works for `Read` and `Bash` hooks but is silently ignored for `Edit` — closed "not planned" with no maintainer comment in the visible thread. The only functioning workaround forces an explicit deny-and-retry round trip.

### Claim 2 — Context burn

The claim that formatter churn forces costly re-reads is a direct logical consequence of claim 1 (a failed edit typically means "Read it again before attempting to write it," per Claude Code's own error text), and multiple troubleshooting/blog sources (morphllm.com, agentkit.best, ClaudeLog FAQ) state as fact that the fix is "ask Claude to re-read the file" or "disable format-on-save while using AI tools." None of these sources, however, measures the actual token or context-window cost of the re-reads — no source puts a number on how many extra tokens, how often this happens per session, or what fraction of a session's context gets consumed by it. Broader "context burn" literature searched for this report (e.g., discussion of re-reading the same file three times per session as "the quietest form of AI agent token waste") is about context waste generally, not formatter-triggered waste specifically, and was not tied to formatters in any source found.

**Verdict: plausible mechanically, unmeasured empirically.** This claim should be reported to the user as "widely assumed, not measured" rather than either confirmed or refuted.

### Claim 3 — Hook loops / thrash

Two mechanisms were searched for and are worth distinguishing:

- **Agent-recursive hook loops (documented, real):** a hook that itself calls back into the LLM (spawns a sub-agent, invokes the SDK) fires on `PostToolUse`, and because its own actions are themselves tool calls, it re-triggers `PostToolUse`, looping. The clearest documented case: a March 2026 dev.to writeup where a market-research sub-agent hook looped 25 times because "PostToolUse fires after every tool use. When the agent calls Bash once, the hook fires, which starts the agent again, which calls Bash again, which fires the hook again."
- **Pure formatter-process hook loops (not found in any source):** a `prettier --write` subprocess edits the file directly on disk; it does not call the `Edit`/`Write` tool and therefore cannot itself trigger another `PostToolUse` event. No GitHub issue, blog post, or forum thread found describes a formatter hook causing a self-sustaining loop.

Where formatter hooks _do_ interact with "thrash" is indirectly: a formatter hook firing on every single-file edit, combined with an agent that makes many small sequential edits to the same file, produces a high-frequency stream of formatter invocations (real cost: repeated subprocess spawning, not a loop) — one existing research report in this repo (`research/20260320_prettier_formatting_ai_agents.md`) already flags this as a "performance at scale" concern and recommends `async: true` plus considering debounce/batching if it becomes noticeable, without evidence it commonly does.

**Verdict: the loop hazard is real for hooks that re-invoke the agent, but the research brief's framing (formatter → file changes → triggers another hook/agent turn) is not evidenced for plain formatter hooks specifically.** This should be reported as a narrower, more qualified finding than the brief's phrasing implies.

### Claim 4 — Diff noise

Well evidenced with concrete, dated complaints:

- Cursor community forum (posted March 15, 2025; related unresolved thread "A way to disable formatOnSave when agent updates files" posted December 14, 2025): _"when the agent applies code, it changes hundreds of lines to a different style of formatting... it's virtually impossible to tell what the agent actually did vs what is the autoformatting."_ Notably, this happened with auto-formatting disabled in settings — the agent's apply pipeline reformats independent of the IDE's own formatter configuration, which is a distinct and arguably worse failure than a PostToolUse-hook-driven reformat, since there's no obvious lever to disable it.
- Zed issue #55295 (above): the same "requested one semicolon, got a whole-file reformat" story is simultaneously a diff-noise complaint and an edit-tool-confusion complaint — the two failure modes (claim 1 and claim 4) frequently co-occur in the same incident, because it's the same underlying event (a formatter rewriting more of the file than the agent intended) that both confuses the next edit _and_ pollutes the diff for review.
- General (non-agent-specific) "PR noise" literature — Darker's region-scoped Black formatting, ktfmt's determinism pitch, and a GitHub Community discussion on filtering formatting-only diffs in code review — confirms the mechanism is well understood outside the agent context too; agents simply increase the frequency and volume of edits that can trigger it.

### Claim 5 — The counter-position (format-on-write is good for agents)

This is the least explicitly argued of the five claims. What was found is **revealed preference, not stated argument**: Claude Code's official hooks guide, GitHub Copilot's hooks documentation, and Continue.dev's hooks documentation all independently converge on the identical worked example — `PostToolUse` on `Edit|Write` → `prettier --write` on the touched file — and in Claude Code's case, it is literally the second example in the entire guide, ahead of most other automation patterns. This is strong evidence the vendors consider it the paradigmatic, safe-by-default hook pattern. But none of the three pages contains prose explaining _why_ — no vendor states "this normalizes agent output," "this prevents style drift specific to LLM-generated code," or "this reduces reviewer burden." The benefit is asserted only through vendor default/example choice, not through argument.

The clearest _adjacent_ argument found — not from a formatting vendor, but from `agent-style` (a curated ruleset project) — is about a related but distinct phenomenon: LLMs "drift" in style across a single generation (e.g., a numbered list starts consistent and degrades by item 5) unless corrected. That project argues for correcting style **at generation time, in the prompt**, not via a post-hoc formatter — which is arguably a competing philosophy to "let the formatter fix it after," though the two are not mutually exclusive (a model that already tends toward consistent style still benefits from a formatter catching what it misses).

No source was found making the explicit claim "formatting on write is good specifically because it means the agent always sees canonical code on its next Read" — this is a plausible inference from the existing corpus (an agent that reads a freshly-formatted file at least starts its next turn from canonical style, even if the mid-turn stale-write problem in Claim 1 still applies), but it is inference, not a claim anyone in the source set actually makes.

## Reconciling Patterns and Trade-offs

None of the sources in this research converge on one "solved" pattern; several partial mitigations exist, each with a real trade-off:

| Pattern                                                                                                                                                        | What it does                                                                                                          | Fixes                                                                                                                                                      | Doesn't fix                                                                                                                                                                | Trade-off / cost                                                                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Disable format-on-save/agent-triggered formatting during active agent sessions** (Zed issue's proposed fix; multiple troubleshooting guides)                 | Formatter never runs mid-session                                                                                      | Stale-context edit failures (claim 1), context burn (claim 2)                                                                                              | Unformatted output persists until a later pass; reintroduces the enforcement problem the March 2026 report already solved                                                  | Requires a second, separate formatting pass (pre-commit or CI) to catch what the agent leaves unformatted — reconnects to the enforcement-side report already in this repo                                                                                                                       |
| **`async: true` PostToolUse formatter hook** (existing DorkOS pattern, `research/20260320_prettier_formatting_ai_agents.md`)                                   | Formats in the background without blocking the agent's next tool call                                                 | Latency cost of formatting                                                                                                                                 | Does **not** fix claim 1 — the agent can still act on stale content before the async format lands, or immediately after it lands                                           | Race condition risk traded for lower latency; no source confirms whether Claude Code sequences the next tool call after an async hook completes                                                                                                                                                  |
| **Format at commit/pre-commit time only, not per-edit**                                                                                                        | Formatter runs once per commit on the full changed-file set via lefthook/husky, not per individual Edit call          | Per-edit stale-read failures entirely (agent never observes a formatter-modified file mid-session, since it never edits again before commit in this model) | Agent still works against its own possibly-unformatted style throughout the session; reviewers viewing agent's live diffs (not yet committed) still see unformatted code   | Cleanly avoids claims 1–3, but reintroduces claim 4 at commit boundary (one large formatting diff per commit) unless combined with region-scoped formatting                                                                                                                                      |
| **`--check` instead of `--write` in the hook, formatting deferred to a human/CI step**                                                                         | Hook only reports whether formatting is needed; doesn't rewrite the file the agent just touched                       | Stale-context problem entirely (no file mutation mid-session)                                                                                              | Unformatted code ships in the agent's diffs; needs a downstream enforcement layer                                                                                          | Pushes the entire formatting burden to the layer the March 2026 report already covers (CI gate) — a clean division of concerns, but the codebase is agent-unformatted until that gate runs                                                                                                       |
| **Format only files the agent is "done with"** (e.g., a `Stop`-event hook rather than `PostToolUse`)                                                           | Formats once per turn/session-end rather than once per individual edit                                                | Repeated stale-reads across a burst of edits to the same file within one turn (only the last edit in the turn risks staleness)                             | Agent can still hit staleness _within_ a turn if it edits the same file twice before turn end; multi-file sessions still reformat many files at once (diff noise persists) | Reduces frequency of the failure without eliminating it; not found explicitly recommended by any vendor, but is consistent with Claude Code's documented `Stop` hook event and is a logical middle ground between per-edit and per-commit                                                        |
| **Region-scoped / diff-aware formatting** (`darker` for Python/Black; conceptually portable to Prettier via `--range-start`/`--range-end` or a custom wrapper) | Formats only lines actually changed, leaving untouched regions alone                                                  | Diff noise (claim 4) directly                                                                                                                              | Does not address stale-context (claim 1) — a formatted diff hunk can still shift the agent's `old_string` inside that hunk                                                 | Requires custom tooling; Prettier itself has no first-class "format only these lines" flag matching Black's `--diff`/range support, so this is more mature in the Python ecosystem than the JS/TS one                                                                                            |
| **Deterministic, config-minimal formatters** (ktfmt's philosophy)                                                                                              | Removes formatter configuration drift as a source of "fights," since output is byte-identical regardless of settings  | Formatter-vs-formatter disagreement across contributors/tools                                                                                              | Does not address agent-vs-formatter staleness or diff noise from a single formatter run touching wide regions                                                              | Requires committing to one opinionated tool and giving up configurability                                                                                                                                                                                                                        |
| **Teach the generator, ignore the output** (codegen-vs-formatter fights)                                                                                       | Generator emits already-correctly-shaped code; generated paths added to `.prettierignore`/`.eslintignore` permanently | Perpetual dirty diffs on every codegen re-run (the generated-file fight named in the brief)                                                                | Nothing agent-specific — this is a pre-agent-era pattern                                                                                                                   | Standard practice per multiple codegen ecosystems (GraphQL Codegen deprecating its own `--prettier` post-process flag; OpenAPI codegen issues recommending the same); costs a few seconds of codegen time saved, and removes generated files from the domain formatters/agents fight over at all |

**No single pattern in this research set fully reconciles "formatted code" with "no agent-facing stale-context risk."** Every pattern that eliminates claim 1 (stale-context) does so by moving formatting to a boundary the agent doesn't observe mid-session (commit time, CI, or `--check`-only), which reintroduces some version of the enforcement problem the March 2026 report in this repo already solves. Every pattern that keeps formatting close to the edit (per-edit `PostToolUse --write`, which is what all three vendors ship as their default example) accepts claim 1's risk in exchange for the codebase never sitting unformatted for more than one edit.

## Research Gaps and Limitations

- **No source quantifies context/token cost.** The "context burn" claim (#2) could not be substantiated with any measured figure — tokens per re-read, frequency per session, or percentage of context window consumed. This should be flagged to the user explicitly as an unmeasured, plausible-but-unproven claim.
- **The exact warning string quoted in the research brief was not found in indexed documentation, but was confirmed firsthand and live during this research.** It is a runtime-only system-reminder string, not published in `code.claude.com/docs`, which is why search and doc-fetch tools didn't surface it. See the firsthand account under "Claim 1" above, including the immediate follow-on Edit failure it accompanied.
- **No documented case of a pure-formatter PostToolUse hook causing an infinite loop was found**, despite two rounds of targeted searching. The loop hazard that is documented involves hooks that re-invoke the agent/LLM layer, a materially different mechanism. This narrows claim 3 considerably from how the research brief framed it.
- **Cursor, GitHub Copilot, Continue.dev, and OpenAI Codex CLI docs were checked only at a surface level** (via search snippets and one or two page fetches each), not exhaustively. Codex CLI in particular has hooks gated behind an explicit opt-in flag (`[features].codex_hooks = true`, marked "under development") and its `PreToolUse` currently only intercepts the Bash tool, not Edit/Write/apply_patch — meaning Codex CLI cannot currently run a PostToolUse-style per-edit formatter hook the way Claude Code, Copilot, and Continue can. This is worth independent verification if Codex-specific guidance becomes relevant to DorkOS.
- **No practitioner report was found that named a specific dollar/time cost** attributable to the stale-context problem (e.g., "this cost me an hour of retries" or "X% of my agent sessions hit this"). All evidence is qualitative (bug reports, forum complaints), not quantitative.

## Contradictions and Disputes

- **Claude Code's own error message vs. the specific bug that surfaced it:** issue #33856's exact error text ("...by a linter...") names linters/formatters as an anticipated cause, but the reporter of that specific issue explicitly states no formatter or watcher touched the file in their repro — the bug was a stuck internal-state tracking issue unrelated to formatting. The error message is broader than any single bug that triggers it; it should be read as Anthropic's general-purpose explanation for the "file changed since read" condition, not as proof that formatters are the primary cause of that error in practice.
- **Vendor endorsement vs. vendor risk-disclosure:** Claude Code, GitHub Copilot, and Continue.dev all present per-edit formatter hooks as their flagship example with no caveat about staleness risk, while the community-generated troubleshooting content (blog posts, forum threads, Medium writeups) treats the same pattern as a known source of pain requiring workarounds. The vendors' worked examples and the community's troubleshooting content are, in effect, in tension: the docs present the pattern as simple and safe; the field reports present it as a recurring source of failed edits.
- **"Disable format-on-save" vs. "keep format-on-write, just go async":** two different mitigation philosophies appear in the sources with no cross-reference to each other. Zed's issue thread leans toward disabling formatting during agent sessions entirely; the existing DorkOS-adjacent research (`research/20260320_prettier_formatting_ai_agents.md`) leans toward keeping formatting on but making it async and accepting the residual risk. Neither source engages with the other's approach or explains why one is preferable; this appears to be an unresolved, tool-specific design choice rather than an industry consensus.
