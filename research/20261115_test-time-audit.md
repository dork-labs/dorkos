## Method

Scope: the six `test-shard (n/6)` jobs of `.github/workflows/test.yml`, measured on merge-group run 43747929385 (green, `main` 2026-11-15), cross-checked against runs 43748344852 and 43750656389. Read-only audit; nothing was changed. The raw data (5,381 per-file rows, 162 per-package vitest summaries, and the stripped job logs) was parsed from those runs' public job logs and is not committed; `gh run view --job … --log` reproduces it.

Every number below is **measured** from those logs unless marked **(est.)**. File-level causes and line numbers were read from `main` as of 2026-11-15. Two single-file local runs were made to measure import floors; no package suite was run.

## 1. Summary

The suite is not slow because it has many tests; it is slow because (a) each shard rebuilds 19 packages from a cold turbo cache (141–223 s per shard, 0 cache hits), (b) ~40% of all vitest worker time is module import/environment setup rather than test execution (import 7,388 s + environment 1,356 s + transform 654 s + setup 281 s of 19,100 s summed worker time), (c) ~30 server files re-bootstrap the world per test (fresh migrated SQLite DB, `vi.resetModules` + re-import of the server graph, a spawned `tsx` server, or a real `claude`/`opencode` child process), and (d) the runner CPU lottery: with the duration-balanced sequencer already giving every shard 20.5–21.5 estimated test-minutes, the same work takes 16 min on an EPYC 9V45, ~20.5 min on a 9V74 and ~27 min on a 7763 (three runs, nine shards each, no exceptions). The sequencer from #3506 is working; the 16-vs-27-minute spread is hardware, not assignment.

**Headline (est.):** code and config fixes alone (sections 3.1–3.9) cut per-shard wall by **30–35%** (a 9V74 shard from ~21 min to ~14 min; a 7763 shard from ~27.5 to ~18.5) and total job-minutes from ~138 to ~90 (−35%), with identical test counts. Reaching **≥50% wall** needs one structural change on top: 10 shards (after build caching, so the extra shards are cheap) gives ~9–10 min on a 9V74 and ~12–13 min on a 7763, at roughly the same total job-minutes (~95) as the code-fixes-alone case. No fix in this report deletes a test.

## 7. What NOT to do

- Do not delete cheap tests for speed: 4,084 files under 1 s are 6.9% of test time (650 s of 9,425); the whole bottom 50% of files is 0.9%. Test deletions are justified on duplication grounds, not time.
- Do not rebalance shards by hand or add a seventh shard before caching builds: each shard pays ~3–4 min of identical rebuild today.
- Do not set `isolate: false`, share one SQLite/PGlite across tests with truncation, or drop migration replay from templates — these tests cover tenant isolation and permission gates; the template must be built through the same `runMigrations`/`provisionManagedTestDatabase`.
- Do not raise `timeout-minutes` or tune `ulimit`/`maxWorkers` on EMFILE evidence (already documented in test.yml; the EMFILEs are fault injections).
- Do not read the 16-vs-27-minute spread as a sequencer bug: estimated test-minutes are equal; it is the CPU draw.
