# Multi-repo organisation for agents

**Date:** 2026-09-13
**Why:** DorkOS just became a multi-repo project (`dork-labs/dorkos` public, a closed-source control-plane repo, plus `marketplace`, `dork-plugins`, `loop`, `homebrew-dorkos`, all cloned side by side under one parent folder). Three questions: how do the harnesses see sibling repos, how do platforms model a project that spans repos, and should DorkOS add such a thing.
**Method:** official docs for Claude Code, Codex, Cursor, VS Code; platform docs and engineering blogs; a repo-internal map of how DorkOS models workspaces, agents, sessions and rooms today.

Only Buzz has a first-class Project that holds several repos. Devin and Ona get there through environments. The worktree-per-agent orchestrators (DorkOS's direct peers) have no cross-repo concept at all.

## 3. How DorkOS models this today (repo-verified)

- **Workspace** (`packages/shared/src/workspace.ts`, `apps/server/src/services/workspace/`): one isolated checkout per unit of work, keyed `(projectKey, key)`, provider `worktree | clone`, file-first sidecar manifest. `projectKey` is a grouping string; `source` is an opaque origin path. No repo entity, no branch entity, no multi-repo notion. The `/workspaces` page renders a read-only filesystem scan of worktrees, not the managed entities.
- **Agent** (`.dork/agent.json`, `packages/shared/src/mesh-schemas.ts`, `packages/mesh/src/discovery/unified-scanner.ts`): identified by the directory the manifest lives in; one manifest = one directory = one agent. The scanner yields one agent per directory. An agent cannot span two repos.
- **Session**: one `cwd` per session (`packages/shared/src/schemas.ts`); `AgentRuntime` takes one `projectDir` per call.
- **Room** (`apps/server/src/services/rooms/repo/`): exactly one repo per room, with a worktree per agent off that repo.
- **/flow**: the tracker config binds one Linear team per repo (`connection.team.{key,id}`); no project routing table and no dispatch filter by project or label. One team cannot serve two repos: a drain running in either checkout would claim the other's issues.
- **No CLAUDE.md or AGENTS.md exists above any repo root**, and nothing in `contributing/` documents Claude Code's parent-directory loading.
- The only prior mention of multi-repo work is an open question in the torq litepaper drafts ("dispatch across multiple repositories, or single-repo?") and a note that MultiDevin does it.

## 4. Patterns that recur

1. The parent folder is the workspace. Every ecosystem answers "several repos, one task" with a directory that contains them. DorkOS already has one: the parent folder that holds the repos.
2. A manifest in its own repo (Google `repo`, Buzz Project) is the durable form; it outlives any single repo.
3. Instructions layer; permissions do not.
4. Cloud platforms solve multi-repo by cloning extras in a setup script.
5. The project entity is a social object (repos + conversations + agent activity under one identity), not a build object.
6. Knowledge is scoped three ways: none, this repo, all repos (Devin).
7. Worktree-per-agent orchestrators have no cross-repo concept, so a repo-spanning Project in DorkOS is a differentiator, not table stakes.

## 5. What works today for this multi-repo setup

1. **A `CLAUDE.md` at the parent folder.** Loaded by every Claude Code session started in any sibling repo, no flag needed. Keep it short (the docs' 200-line target; it costs context in every session): the repo map with each sibling's role, remote and default branch, and the cross-repo rules. Each repo's own `AGENTS.md` keeps its detail. `claudeMdExcludes` is the escape hatch if it becomes noise somewhere.
2. **Codex will not see that file.** Mirror the same block into `~/.codex/AGENTS.md` (machine-local, say so) and put a short "sibling repos" section in each repo's `AGENTS.md`. Do not assume parity between harnesses.
3. **Cross-repo edits:** `claude --add-dir <sibling>` (plus the env var to load its instructions) or `codex --add-dir <sibling>`; persist with `permissions.additionalDirectories` in each repo's `.claude/settings.json`, remembering it loads no rules or skills and does not apply inside a `--worktree` session.
4. **Make the contract a published package, not a shared folder.** the control plane depends on a versioned package from the public repo (`@dorkos/cloud-api` or a subpath of `@dorkos/shared`). A submodule or symlink invites an agent to edit across the boundary; a version number makes the boundary visible in a diff and in CI.
5. **A boundary guard in CI on the public repo**, in the shape of the existing vocab gate: fail if private hostnames, control-plane identifiers or private repo paths appear in public source or prose. Rules in CLAUDE.md are context; hooks and CI are where rules become real.
6. **A VS Code `dork-os.code-workspace`** beside the repos for the human side (folders, recommended extensions). Claude Code does not read it; it is for people and for Cursor.

## 6. If DorkOS adds a Project entity

It should hold: repos with **roles** (public monorepo, control plane, plugin source, distribution) plus local path, remote and default branch; **shared rules** scoped Devin-style (project-wide / one repo / none); a **tracker binding** (Linear team + project) so an issue resolves to a repo set; an **environment** recipe (clone list, install, dev ports); an explicit **secrets boundary** (which repos may see which credentials, the field that makes a public/private split safe); and **rooms bound to the project** (Buzz's insight that the conversation is part of the project, which DorkOS's rooms already make cheap). The workspace layer stays as it is: a Project is the thing above workspaces, rooms and agents, not a replacement for any of them.
