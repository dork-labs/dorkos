# Push to another instance: remotes, leases, identity and publishing with no mandatory home

**Date:** 2026-10-06. **Scope:** design research, web plus repo. **Builds on:** `research/20261006_one-server-sync-publish-identity.md` (same batch), `research/20260724_multi-user-communities.md`, `research/20260727_agent-identity-in-communities.md`, `packages/shared/src/community-adapter.ts`, `packages/cloud-api/src/communities.ts`, and the community ADRs. Nothing under the private cloud repo was read.

**The founder's constraint, restated:** local-only is the default. There is no mandatory always-on home and no required fee. A remote (DorkOS Cloud or a self-hosted DorkOS) is optional and can be removed at any time. A file or agent made locally can be pushed to another instance, and anything on a self-hosted instance should also be visible locally.

## 0. What the "no mandatory home" answer changes in report 03

| Report 03 said                                                                                                                                                        | Why it no longer holds                                              | Replacement                                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| §4: "The agent's home is a server; a laptop is just one possible runner." Identity, transcript, memory and inbox live on an always-on home.                           | That makes a server mandatory for any agent that might ever move.   | **The laptop is the default home. A remote is an optional runner and mirror.** The authority over an agent (its rotation keys and owner attestation) stays with the owner's devices. Only the _runner lease_ moves.                                      |
| §5: "DorkOS Cloud is the default home for people whose only install is a laptop, because an identity provider has to stay online." Home server acts as OIDC provider. | An identity that needs an online provider makes Cloud a dependency. | **Self-certifying identity**: every person, agent and instance gets a keypair at birth, hidden from the user (D3, "zero user-facing keys", survives). Remotes and communities _verify_ it and then issue their own sessions. No OIDC provider is needed. |
| §3: default publish host is "their home in DorkOS Cloud".                                                                                                             | No home by default.                                                 | **Default is no publish host.** Zero-cost option is tunnel preview. First real publish asks the person to add a remote (Cloud or self-hosted).                                                                                                           |
| §1: one server package with profiles.                                                                                                                                 | Unchanged, and now essential.                                       | "Remote" only works if every remote is the same program. Keep it.                                                                                                                                                                                        |
| ADR `260727-184933` "The community server never runs a member's agent".                                                                                               | A pushed agent _must_ run on a remote.                              | **Narrow it, don't drop it:** "An instance runs an agent only if that agent's owner pushed it there, into an isolated box." A community you merely joined still never runs your agent. Supersede via a new ADR.                                          |
| ADR `260916-210002` "remote community is authoritative, local is a dispatch cache".                                                                                   | Still right, but too narrow.                                        | Generalise: **whoever holds the lease is authoritative for that agent; every other instance holds a mirror.**                                                                                                                                            |

The safety property from ADR-0320 ("whoever can drive agents holds the filesystem and spends the quota") still holds. It now has to be enforced per box on the remote rather than by "agents only ever run on your own machine".

### 1.2 Recommendation: git-shaped remotes, three verbs

A local instance has zero or more **named remotes**. Each remote is another DorkOS instance (same program) plus an account on it.

```
dorkos remote add cloud https://cloud.dorkos.ai      # device-code sign-in, like `codex login --device-auth`
dorkos remote add my-vps https://dork.example.com
dorkos remote list                                     # name, url, reachable?, what lives there

dorkos fetch                                           # refresh mirrors of every remote (metadata, lazily content)
dorkos publish ./site --to cloud --access unlisted     # artifact: immutable snapshot, new URL per version
dorkos push doc "Q4 plan" --to my-vps                  # document: adds the remote as a live Yjs peer
dorkos move scout --to cloud                           # agent: hand the runner lease over
dorkos move scout --to here                            # agent: bring it back
dorkos remote remove cloud                             # guided off-boarding (section 7)
```

Three different verbs, deliberately:

- **publish** = snapshot, one way, versioned (Vercel/Obsidian Publish).
- **push/sync** = a document or folder replicated two ways (Obsidian Sync/Syncthing/Yjs).
- **move** = single-writer handoff of something that _runs_ (Bluesky migration plus a lease).

**What "pull back" means, per kind:**

| Kind                 | "Pull"                                                                                    | Notes                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Artifact             | Download a published version into the local workspace                                     | Rarely needed; local source is usually the origin.                                                                                         |
| Document             | Implicit: Yjs syncs both ways. "Clone" fetches a doc that started on the remote.          | A doc made on the VPS appears in the local app's mirror list after `fetch`.                                                                |
| Agent                | `move scout --to here`: the remote finishes its turn, ships a delta, signs the lease back | Not a copy. The remote keeps a stopped standby for a retention window, then deletes it.                                                    |
| Anything on a remote | `fetch` keeps remote-tracking state (like `refs/remotes/cloud/*`)                         | Satisfies "anything on a self-hosted instance should also be available locally": listed always, readable when cached, live when reachable. |

**Naming caveat:** `packages/cloud-api/src/remote.ts` already uses "remote" for _remote access_ (tunnel modes `off | byo | managed`). Internally a second meaning of "remote" will confuse. Suggest the code noun `InstanceLink` / `remotes` config section, and test a user-facing noun ("Where it runs: This Mac · DorkOS Cloud · my-vps"). Open question for the operator.

**The instance link** is a server-to-server session the local server holds (credential stays on the local server, the browser only ever talks to localhost). This is the same rule `RemoteCommunityAdapter` follows today ("Community credentials stay on the local server"). The laptop always dials out; a remote never needs to reach a laptop behind NAT.

## 2. What can be pushed, and what is in each bundle

### 2.1 Bundle format

- **Content-addressed chunks plus a signed manifest.** Each part is a layer with a SHA-256; a push uploads only chunks the remote lacks (git/OCI dedupe). Manifest is signed by the agent's current runner key and the owner's attestation is attached.
- **Declare size and digest before upload**, idempotency key, resumable parts, tolerant state enum: copy `CommunityMoveStartRequestSchema` / `CommunityMoveSchema`.
- **Box base image by reference** (OCI digest pulled from a registry), so it never travels from the laptop. Only the **home volume delta** travels.
- **Home volume as chunked snapshot** (restic/casync-style content-defined chunks), not a single tar, so repeated moves ship only what changed. Not verified which library; a design choice, not a finding.

### 2.2 Agent bundle contents: what moves once, what syncs continuously

### 2.3 Documents

- **Yjs, as report 03 recommended.** "Push" = add the remote as a sync peer for that doc (Hocuspocus-style endpoint in the one server). Offline edits on the laptop merge on reconnect by construction.
- A doc can live on several instances at once; there is no lease, because CRDTs make multi-writer safe. This is the one place multi-writer is fine.

### 2.4 Artifacts

- An **artifact** is an immutable snapshot: a static bundle (HTML/CSS/JS/media) with a version id. Each publish makes a new version and an immutable version URL; the public URL is a pointer moved to the newest version (Vercel preview/production).
- **Optional "keep it live":** the remote re-publishes on a debounce when the source doc changes (doc via Yjs) or when the agent re-publishes. Live is a property of the source sync, not of the artifact.
- **Apps with a backend** are not artifacts. Anything that needs a process is an agent box with a port, so it follows the agent model.

## 3. The single-runner lease

### 3.1 Model

- **Token passing, not a lock service.** There is no always-on lock server, so the lease cannot be "acquire from the coordinator". The current holder _passes_ it: it signs `lease(agent, epoch N+1, holder = target)`. Whoever holds the highest epoch they can verify is the runner.
- **Fencing tokens** ([Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)): every write that goes through a DorkOS-controlled sink carries the epoch, and the sink rejects lower epochs. Sinks: transcript append on mirrors, room posts, Relay sends, Tasks firing, secrets broker, published-artifact updates, community posts.
- **External side effects cannot check epochs** (an email already sent). So the old runner must **self-fence**: on any sign that it lost the lease (a higher epoch seen, or the handoff it started was committed) it stops its box before doing anything else.
- **Codex's own docs already require this shape**: ChatGPT auth on a runner is allowed only if "only one machine or serialized job stream will use a given `auth.json` copy" ([Codex CI/CD auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). Rotating refresh tokens break if two copies refresh.

### 3.2 Handoff, laptop to cloud (two-phase, Bluesky-style)

1. **Preflight.** Target reachable and has box capacity; model access on the target is settled (section 6); list what will not travel: localhost MCP servers, the local browser profile, Keychain items, files outside the workspace. Show it before anything happens.
2. **Quiesce.** Let the current turn finish (or stop at the next turn boundary). Pause the agent's schedules locally. Hold incoming Relay messages in its Maildir inbox.
3. **Snapshot.** Home volume delta, transcript tail, memory, config. Git: the whole working tree is in the home volume, so uncommitted work travels too (better than Claude teleport, which needs a pushed branch). Additionally commit WIP to `dorkos/<agent>/e<epoch>` and push it if a git remote exists, as a belt-and-braces copy.
4. **Transfer.** Upload missing chunks (digest-declared, resumable). Secrets envelope encrypted to the target's instance key.
5. **Stage on target, deactivated.** Target restores the box (base image by digest, home volume), mints a runner key, verifies the manifest signature and owner attestation. Nothing runs yet. **If anything fails up to here, nothing has changed**: the laptop still holds the lease (CommunityMove's "old never touched" rule).
6. **Commit.** Laptop signs epoch N+1 to the target; target acknowledges. Laptop marks its copy **mirror (read-only)** and self-fences.
7. **Announce.** Signed route update (`agent X at instance Y, epoch N+1`) to every instance that cares: the owner's other remotes and every community the agent is in.
8. **Resume.** Target resumes schedules and drains held messages (laptop forwards its held inbox in the same push). Laptop UI subscribes to the remote session stream.

### 3.3 The laptop is offline while the cloud copy works, then comes back

This is the **normal** case and should involve no conflict at all:

- The laptop handed off cleanly before the lid closed, so it knows it is a mirror.
- On wake, the laptop server `fetch`es: transcript events since its last `seq` (durable SSE replay), new memory/config versions, new published versions, route changes.
- The UI shows "Running on DorkOS Cloud · 14 new messages". Opening the session proxies to the remote while online, and shows the cached mirror while offline.

### 3.4 Where conflicts can still happen, and the rule for each

| Situation                                                                                                                        | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Person edits the agent's memory or config on the laptop while it runs remotely                                                   | Mirrors are read-only for agent-owned state. The edit is sent to the runner as a request ("Dorian edited your memory"), applied there, and flows back. Offline: queued, sent on reconnect.                                                                                                                                                                                                                                                                                                      |
| Person edits a document locally while the agent edits it remotely                                                                | Yjs merges. No rule needed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Forced reclaim: remote unreachable (outage, cancelled account, lost VPS) and the owner takes the agent back from the last mirror | Owner signs epoch N+2 from a device holding the rotation key. Every instance that sees N+2 rejects N+1 writes. If the remote comes back, its box sees N+2 and self-fences. Its unsynced work is preserved as a **fork**, never merged silently.                                                                                                                                                                                                                                                 |
| Fork reconciliation                                                                                                              | **Transcript:** append-only per epoch; the fork is shown as a separate "while disconnected on cloud" branch, not interleaved. **Git:** the fork's work is on `dorkos/<agent>/e<N+1>`; merge is a normal PR/merge the agent can do. **Memory:** three-way text merge from the common base; conflicts handed _to the agent_ as a task ("reconcile these two memory versions"). **Published artifacts:** versions are immutable, so both survive; the pointer stays where the higher epoch put it. |
| Laptop wants it back while the cloud is mid-turn                                                                                 | Wait for the turn boundary, or offer "interrupt and bring back now".                                                                                                                                                                                                                                                                                                                                                                                                                            |

### 3.5 Seeing a remote agent from the laptop

- The laptop server is a **proxy, not a client of a client**: for an agent whose lease is elsewhere, its session routes (`/api/sessions/:id/events`, `POST /messages`) forward over the instance link to the runner's same routes. Same durable SSE contract (snapshot, gap-free replay with `Last-Event-ID`, live with monotonic `seq`), so the client needs no new code path.
- Precedent in-repo: `RemoteCommunityAdapter` with lazily cached, owner-qualified instances and qualified routes (`/api/communities/:ref/rooms/:roomId`). Do the same for instances: `/api/instances/:remote/...`, or transparent forwarding keyed on the route table.
- Phones reach the laptop via the tunnel today. When the laptop is closed, the phone should talk to the remote directly. The remote is the same program, so it serves the same web app; the person signs in there with the same identity (section 4).

## 4. Identity across instances with no mandatory home

### 4.1 Options

| Option                                                                                                                                                         | Rotation                                          | Needs an always-on service                                                          | Location-independent | Verdict                                                                                                                                                                |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `did:key` ([spec](https://w3c-ccg.github.io/did-key-spec/))                                                                                                    | **No** (id is the key)                            | No                                                                                  | Yes                  | Fine for per-runner signing keys; wrong for long-lived identity.                                                                                                       |
| `did:web`                                                                                                                                                      | Yes                                               | **Yes**, the hosting domain                                                         | **No**, id is a URL  | Mastodon's problem. Use only as an optional _alias_ for people who own a domain.                                                                                       |
| `did:plc` ([spec](https://web.plc.directory/spec/v0.1/did-plc))                                                                                                | Yes, rotation keys sign ops; 72 h recovery window | **Yes**, the PLC directory                                                          | Yes                  | Right shape, wrong dependency (a central directory).                                                                                                                   |
| Self-certifying id plus key-event log carried with the principal (did:plc's genesis-hash idea without the directory; Syncthing's cert-hash idea plus rotation) | Yes                                               | **No**: the log travels in bundles and is mirrored to every instance that knows you | Yes                  | **Recommended.** Not a standard DID method; could be published later as `did:dork` or mapped onto did:webvh. did:webvh and did:peer were not researched in depth here. |
| Server-issued accounts only (today: Better Auth per instance)                                                                                                  | n/a                                               | Each server                                                                         | No                   | Keep as the _session_ layer, not the identity.                                                                                                                         |

### 4.2 Recommendation

1. **Every principal (person, agent, instance) gets a stable id at birth on the instance that creates it.** For agents, keep the existing ULID as the id everyone keys on, and add a hidden keypair plus a small signed key log (genesis, rotations, revocations). Zero user-facing keys (D3 holds); keys live `0600` under the dork home like `host.key`, or in the OS keychain.
2. **Owner attestation, mutable at the receiver.** The owner's person key signs "agent X belongs to person P". A receiving instance stores it as a **mutable row** and honours later revocations, which keeps the identity report's warning ("a signature the owner cannot revoke is worse than a row"). The signature is what lets a remote with no shared server trust it; the row is what keeps it revocable.
3. **"The remote vouches for it."** When you push an agent to a remote, you are signed in there as P. The remote checks the attestation against P, admits the agent, mints its local credentials (`agentIdentityTokens`, ADR `260725-133220`: attribution, ceiling-only), and signs a **location record** `(agent X, hosted by instance R, epoch N)`. Third parties (communities) trust the chain _owner → agent_ and _instance R → hosting epoch N_.
4. **Addressing.** The identity is `agent:<ulid>`. Human-facing handles are _names that resolve_, not identities: `@scout` within your own space, `scout.dorian@…` only if someone owns a domain (did:web-style alias). **Never** `scout@instance` as identity, or a move becomes a rename.
5. **Person identity across instances.** A person signs in to a remote by proving the key (device-code approval from a device that holds it, RFC 8628 already exists in `apps/site/src/lib/auth.ts`) or by an invite link. After that, the remote issues ordinary sessions. Email is an optional recovery channel per remote, as the communities report proposed.
6. **Recovery is the honest weak point.** With no home, losing the only device that holds the rotation key means losing the identity. Offer, never force: a recovery kit (file or passkey-wrapped key), or escrow of an encrypted rotation key to a remote you trust. Without either, losing the laptop loses local-only work exactly as today. Say so in the UI.

### 4.3 How Relay routes to an agent that moved

- **Route table** per instance: `agentId → { location: local | remote(name) | community(ref) | unknown, epoch, updatedAt }`, fed by signed location records.
- **Local subject unchanged.** `relay.agent.{namespace}.{agentId}` keeps working. If the agent is remote, its local endpoint becomes a **forwarding endpoint** (a Relay adapter) that ships the envelope over the instance link, keeping hop count, TTL and ancestor chain (the envelope budget).
- **Store and forward both ways.** Laptop to remote: if the remote is unreachable, the Maildir inbox holds it (durable today) and retries. Remote to laptop: the remote keeps an outbox; the laptop drains it when it next dials out. This replaces ADR `260727-184933`'s "presence follows the install" with **presence follows the runner**.
- **Fencing on receipt.** The receiving runner checks the envelope was addressed under its current epoch, and senders sign with their runner key so a stale runner cannot impersonate.
- **Stale routes heal lazily**: a forward to an instance that no longer holds the lease returns "moved, epoch M, at R'", like an HTTP 301 the sender caches.

## 6. CRITICAL: can a Claude or ChatGPT subscription drive a 24/7 agent on a server?

### 6.1 What the Anthropic sources say (fetched 2026-10-06)

([consumer terms](https://www.anthropic.com/legal/consumer-terms))
- **Claude Code legal and compliance page** ([link](https://code.claude.com/docs/en/legal-and-compliance)):
  - "Advertised usage limits for Pro and Max plans assume **ordinary, individual usage** of Claude Code and the Agent SDK."
  - OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications."
  - "Developers building products or services ... **including those using the Agent SDK**, should use API key authentication ... Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not **collect, store, or intermediate** Claude.ai credentials or session tokens; sign-in to a Claude account must complete through Anthropic's own flow."
  - Hosting is allowed under conditions: "preinstalling or running Claude Code in your products or services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our **Commercial Terms** and ... The Claude Code binary must not be modified ... Customers **may not pay for, resell, or intermediate Claude usage on their end users' behalf.** Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential."
  - And: the rule does not "prevent an end user from signing in to the **unmodified Claude Code binary** with their own Claude subscription, **including where a platform hosts Claude Code**."
- **Agent SDK overview** ([link](https://code.claude.com/docs/en/agent-sdk/overview)): "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK."
- **`claude setup-token`** ([authentication](https://code.claude.com/docs/en/authentication)): mints a **one-year** OAuth token for "CI pipelines, scripts, or other environments where interactive browser login isn't available"; requires Pro, Max, Team or Enterprise; set as `CLAUDE_CODE_OAUTH_TOKEN`; model requests only (no Remote Control, no claude.ai connectors). Docs also warn unattended background and Remote Control sessions stop when a `/login` credential expires.
- **History** (third-party reporting, not Anthropic primary): OAuth in third-party harnesses was blocked in early 2026 and the terms clarified on 2026-02-19/20 ([The Register](https://www.theregister.com/software/2026/02/20/anthropic-clarifies-ban-on-third-party-tool-access-to-claude/5014546)). A planned "Agent SDK credit" (separate metered pool for SDK, `claude -p` and third-party apps) was announced for 2026-06-15 and **paused**. Anthropic's own support article now says SDK, `claude -p` and third-party app usage "still draw from your subscription's usage limits" and an update will come "before anything takes effect" ([support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). This can change again with notice.

### 6.3 OpenAI Codex with a ChatGPT plan

- Headless sign-in is **documented**: `codex login --device-auth`, or copy `~/.codex/auth.json` from a machine with a browser ([Codex auth](https://learn.chatgpt.com/docs/auth)).
- Automation: "Use **API key** authentication for programmatic Codex CLI workflows, such as CI/CD jobs." ChatGPT-managed auth on a runner is an "advanced" path only for "**trusted private infrastructure**", where "**only one machine or serialized job stream** will use a given `auth.json` copy", refreshed tokens are persisted, and not for public repos ([CI/CD auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). Tokens refresh after roughly 8 days.
- OpenAI Terms of Use forbid sharing credentials or making your account available to others (reported via search; the page returned 403 to fetch).
- **Reading:** a user running Codex with their own ChatGPT login on their own VPS fits the documented "trusted private" path, provided only one machine holds the `auth.json`, which the lease guarantees. **A DorkOS-operated host holding a user's ChatGPT `auth.json` is not addressed by anything I found; unverified.** Recommended path on DorkOS Cloud: device-code sign-in inside the box (the credential is minted there, never shipped), or `CODEX_API_KEY`, or credits (Codex credits path per ADR `261002-221210`).
- OpenCode's ChatGPT-plan sign-in exists in OpenCode itself; whether OpenAI sanctions it officially is only reported by third parties. Unverified.

### 6.4 Design consequence

- **Model access is per runner, never in the bundle.** The move preflight asks: "On DorkOS Cloud, scout will use: your API key · DorkOS credits · sign in to Claude in the box". Default for DorkOS Cloud: API key or credits (subject to 6.2's flag). Default for a self-hosted VPS: whatever the user sets up there, including their own subscription sign-in.
- **Usage limits are a product risk even where it is allowed.** "Ordinary, individual usage" plus Codex's 8-day refresh and Claude's one-year token mean a 24/7 agent on a subscription will hit limits or expiry. Surface a clear "paused: Claude sign-in expired / limit reached" state on the remote, and push a notification.

## 7. User story walkthrough

**Setup.** Maya runs DorkOS on her MacBook. No account, no fee. Her agent `scout` lives at `~/.dork/agents/scout`, runs Claude Code on her Max sign-in, and has a Linux box with her repo checked out.

**1. Publishes a page.**

- She asks scout for a launch page. It lands in the canvas.
- She clicks **Share**. Choices: "Preview link (works while this Mac is awake)" or "Publish to the web (needs a server)".
- She picks preview first: a tunnel URL, labelled "stops when your Mac sleeps".
- She wants it permanent, so **Publish → Add a server → DorkOS Cloud** (or "My own server" with a URL). Device-code sign-in in the browser. A remote named `cloud` appears in Settings.
- She picks **Unlisted**. DorkOS uploads the snapshot. She gets `https://<site>.<user-content-domain>/` plus an immutable version URL. Edits later: **Publish update** makes v2; **Keep it live** republishes on change.

**2. Moves scout to the cloud overnight.**

- On scout's header: **Where it runs: This Mac → Move to DorkOS Cloud**.
- Preflight sheet: "Will travel: memory, history, skills, its computer (1.2 GB changed). Won't travel: the local Postgres MCP server on localhost:5432. Model on Cloud: your API key / DorkOS credits / sign in to Claude in the box." She picks one.
- scout finishes its current turn. Its delta uploads. Cloud restores the box, staged and inactive. Laptop signs the lease over. Status: **Running on DorkOS Cloud**.
- Its nightly schedule now fires on Cloud. A teammate's agent in their shared room @-mentions scout; the community already has the new route.
- She closes the lid.

**3. Laptop wakes in the morning.**

- The app shows "scout · on DorkOS Cloud · 23 new messages". Opening it streams the remote session through her local server. The transcript is already cached for offline reading.
- She edits scout's memory; the edit is sent to Cloud and flows back.

**4. Moves it back.**

- **Where it runs → Move to This Mac.** Cloud finishes its turn, ships its delta (new commits, a node_modules change, transcript), signs the lease back.
- Laptop resumes; Cloud keeps a stopped standby for N days ("Delete now" available).
- Its overnight branch `dorkos/scout/e7` is already in the repo; nothing to merge, because there was only ever one writer.

**5. Cancels cloud.**

- **Settings → Servers → DorkOS Cloud → Remove.** Guided checklist:
  1. Agents running there: none (scout is home). Otherwise: "Bring back" for each, or "Move to my-vps".
  2. Published sites: 1. "Move to my-vps", "Download", or "Unpublish". Warns the URL will stop working unless she used a custom domain.
  3. Documents synced there: kept locally; Cloud copy deleted.
  4. Download a full export (owner export, same shape as the community move export).
  5. Confirm. The instance link is revoked; Cloud applies its retention and deletion rules (ADR `260920-201101`).
- Her identity and scout's identity do not change, because neither ever depended on Cloud.

## 8. Recommended model in 10 bullets

1. **The laptop is home by default.** Remotes (DorkOS Cloud or self-hosted) are optional, named, removable, and run the same server program.
2. **Git-shaped remotes plus three verbs:** `publish` (artifact snapshot), `push/sync` (document, Yjs, multi-writer), `move` (agent, single runner). `fetch` keeps remote-tracking mirrors so anything on a remote is visible locally.
3. **Agents move by lease, never by copy:** a token-passing lease with a monotonic epoch, two-phase Bluesky-style (stage inactive, then commit), fencing tokens at every DorkOS sink, and self-fencing by the old runner.
4. **Bundles are content-addressed, digest-declared and resumable**, reusing the existing CommunityMove contract shape. The box base image travels by OCI digest; only the home-volume delta moves; optional background delta keeps handoffs fast.
5. **Runner-owned state syncs one way to mirrors** (transcript live via durable SSE, memory, config). Mirrors send edits as requests. Documents are the one multi-writer exception, via Yjs.
6. **Self-certifying identity with hidden keys:** stable id (agent ULID) plus a key log carried in bundles; owner keeps rotation keys; each runner gets a fresh signing key per epoch; owner attestation is signed but stored as a revocable row.
7. **Location is a signed record, not part of the name.** Relay keeps `relay.agent.{ns}.{id}`; a route table turns a moved agent's local endpoint into a forwarding endpoint with store-and-forward both ways. Presence follows the runner.
8. **Publishing goes to a remote with a sandboxed origin** (separate PSL domain on Cloud; CSP `sandbox` fallback for one-domain self-hosts), immutable versions plus a moving pointer, public/unlisted/members-only, tunnel preview as the free option.
9. **Model access is per runner and never travels in a bundle.** Secrets re-encrypt to the target instance key; Claude/ChatGPT sign-ins are redone on the target through the vendor's own flow, or replaced by an API key or credits.
10. **Supersede, don't drift:** a new ADR narrows `260727-184933` to "an instance runs only agents their owner pushed there, each in an isolated box", generalises `260916-210002` to leases, and replaces report 03's "server is home" and "Cloud as OIDC provider".

## 9. Top 5 risks

1. **Vendor terms (highest).** Driving Claude Code through the Agent SDK on a subscription is "not allowed unless previously approved" per Anthropic's SDK page; hosted Claude Code forbids paying for usage on users' behalf unless agreed; moving a Claude credential to a DorkOS-run host is forbidden outright. This affects the move feature and may already affect DorkOS's local subscription path and credits. **Get written answers from Anthropic (and OpenAI for hosted ChatGPT-login Codex) before building the Cloud runner.**
2. **Split brain and double side effects.** Schedules, chat pollers, email and webhooks fire twice if any sink ignores the lease, and external effects cannot be fenced after the fact. Every scheduler, adapter and outbound channel must check the lease, and forced reclaim must be rare, explicit and owner-signed.
3. **Handoff weight and "what doesn't travel".** Multi-GB home volumes make "move before I close the lid" slow; localhost MCP servers, browser profiles and Keychain items silently break on the remote. Needs background delta sync (storage cost) and an honest preflight.
4. **Identity recovery with no home.** Self-certifying keys plus "zero user-facing keys" plus no mandatory server means a lost laptop can mean a lost identity. Recovery kit or escrow must exist and be explained without jargon.
5. **New trust domain on remotes.** The ADR that kept agents off servers was protecting against credential custody, tenant isolation and blast radius. A runner remote now holds secrets and runs code with network access; published user content invites XSS and phishing. Box isolation, per-agent secret envelopes, a strict CSP and a separate user-content domain are prerequisites, not polish.

## 10. Unverified or weakly sourced

- Whether DorkOS's existing Agent SDK plus subscription use is "previously approved" by Anthropic, and whether DorkOS credits for hosted Claude Code is covered by an agreement. Not knowable from the public repo.
- OpenAI's stance on a third-party host holding a user's ChatGPT `auth.json`; OpenAI Terms of Use page returned 403 (clauses quoted from search results).
- OpenCode's ChatGPT-plan sign-in being officially sanctioned by OpenAI (third-party sources only).
- Timeline of the 2026 Anthropic OAuth ban, reversal and paused credit: secondary sources for dates; only the pause is confirmed on Anthropic's own support page.
- Telegram rejecting concurrent `getUpdates` pollers (well known, not checked this session).
- Fly Sprites specs (Willison and vendor marketing); E2B persistence semantics (vendor docs via search snippets).
- CSP `sandbox` opaque-origin fallback: behaviour is standard, but which app features break under an opaque origin (service workers, storage) was not tested.
- did:webvh, did:peer and KERI were not researched in depth; the "self-certifying id plus carried key log" is a design proposal, not a vetted standard.
- Chunked home-volume format (restic/casync-style) is a design suggestion; no library was evaluated.
