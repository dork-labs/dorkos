## Research Summary

Checked `research/` first — no existing report covers directory/roster naming (`20260322_agents_page_fleet_management_ux_deep_dive.md`, `20260320_agents_page_ux_patterns.md`, and the community/identity reports cover fleet UX and agent identity but not this naming question) — so this is fresh web research, 9 searches, ~12 sources.

**Headline finding:** among Slack, Discord, MS Teams, Linear, Notion, Zoom, GitHub, and Basecamp, the roster-of-people page is named "Members" or "People" — never "Directory" as the primary nav label for a small/medium team. "Directory" is what Slack calls the _searchable org-wide index_ (with People and User Groups as sub-tabs) once an org is too big to just eyeball — a different job than DorkOS's page. No mainstream collaboration product has shipped a UI that lists humans and AI agents as peers in one roster; "agent roster" is informal industry language (MindStudio, Istoria Collective), not a shipped nav label. Discord is the only reference product that natively mixes humans and bots in a single list — it does so via role-based grouping, not by renaming the feature.

## Recommendation

**#1 — Nav label: "People" · Route: `/people`**

"People" is the plurality choice across every reference product that ships a roster page for a small-to-mid-size team (Slack's People tab, MS Teams' People app, GitHub's People tab, Basecamp's "People & Permissions") — it's the safest, most learnable choice precisely because users already have muscle memory for it. It also does real work for DorkOS's brand thesis: putting agents under the same plain, human-first noun as the one user (rather than a technical/ops word) reinforces "agents as first-class operators" without needing separate UI vocabulary for humans vs. agents. It scales cleanly from today's one-human-plus-agents state to a future multi-user workspace without needing to rename. It avoids both collision risks from question 5: it doesn't read as a filesystem directory (unlike "Directory," which is a real risk in a product that already exposes working directories and file paths constantly via `/workspaces`, `resolve-root.ts`, harness projections), and it doesn't overlap with Mesh, which already owns agent _discovery/topology_ — People is about "who's here," Mesh is about "how they're connected."

**#2 — Nav label: "Team" · Route: `/team`**

"Team" is the more control-panel-voiced, ops-flavored option — it reads naturally today when the page is "you + your agents working together" and avoids the faint irony of a page called "People" being 90% non-human entries in the current single-user state. No reviewed product uses "Team" for exactly this job (Linear and GitHub use "Team"/"Teams" for sub-groupings within an org, Slack pre-2019 used "Team" for the whole workspace), which is both the appeal — a clean word with no baggage in the members-list sense — and the risk: if DorkOS ever wants a distinct concept of sub-teams or pods of agents (a Linear/GitHub-style grouping), "Team" as the page name would collide with that vocabulary the way "Directory" collides with the filesystem sense. Choose this only if that future grouping feature is unlikely, or if you're willing to call groupings something else (e.g., "Pods," "Squads").

**Ruled out:** "Directory" (real filesystem-collision risk in a dev tool that already talks constantly about directories/paths; also the term every reference product reserves for a _searchable index at scale_, not a plain roster — premature for DorkOS's current size). "Members" (functionally identical to "People" but colder/more admin-console-coded — Linear and Notion use it in _settings_, not primary nav, which is a subtly different job than DorkOS's user-facing roster). "Roster" (no shipped precedent in any reviewed product as a nav label — a legitimate on-brand coinage for the ops/mission-control voice, but pure novelty costs a beat of learnability that "People" doesn't; worth keeping in reserve as a section header or empty-state copy rather than the primary nav word).
