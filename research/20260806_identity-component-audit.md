## (b) The current agent-vs-human convention, and its violations

**The documented rule** (`layers/shared/ui/identity-avatar.tsx:31-44`, and restated verbatim in the dev playground at `dev/showcases/DataDisplayShowcases.tsx:264-281`):

> "Square is the agent shape, circle the person shape — a colourblind-safe distinction that does not depend on the badge rendering." Plus: `variant="fill"` for agents (their own colour as a solid disc), `variant="tint"` for everyone else; a `Bot` badge for agents, a `Send`/platform-logo badge for external humans, and **no badge at all for a local human** ("absence is the signal").

**Only two production components fully implement all three axes (shape + variant + badge):**

1. `MessageAuthorAvatar.tsx:70-72` — session chat AND room chat (via `RoomEntryRow` reuse)
2. `identity-hover-card.tsx:120-122` — only wired live in room `@mention` hover cards

**Everything else that draws an agent renders it as a tinted circle — visually identical in shape to a human — because it goes through `AgentAvatar` (`entities/agent/ui/AgentAvatar.tsx:39-55`), which never sets `shape`/`variant` and inherits `IdentityAvatar`'s defaults (`circle`, `tint`).** Since `AgentAvatar` is the base every other agent-rendering component builds on (`AgentIdentity`, `AgentCommandItem`, `AgentPicker`, `agent-columns.tsx`, `AgentNode`, `RecentSessionRow`, `AgentCard`, `AgentHubHero`, `IdentityTab`, `ExecutionExceptionsStrip`, `FirstLight`), the violation is systemic rather than a handful of stragglers:

## (c) Duplication / near-duplicate candidates for a variants-based merge

1. **`AgentAvatar` (entities/agent) vs `IdentityAvatar` (shared) directly.** `AgentAvatar` is a thin, non-parameterized wrapper that hard-codes `shape`/`variant` omission and adds only a health ring + working dot. A `variant="agent"`/`kind` prop on `IdentityAvatar` itself (or a health-ring slot alongside the existing `badge` slot) would collapse this layer entirely and make the shape/fill convention structurally impossible to skip.
2. **Three independent agent-picker comboboxes**, each hand-rolled with its own list/trigger/empty-state code:
   - `features/tasks/ui/AgentPicker.tsx` (Command + Drawer, single-select)
   - `features/room-management/ui/AgentChipPicker.tsx` (custom combobox, multi-select, hand-rolled keyboard handling — deliberately not built on `Command`)
   - `features/command-palette/ui/AgentCommandItem.tsx` (single row inside the global palette's own `Command`)
     All three resolve `resolveAgentVisual`/`AgentPickerCandidate` and draw `AgentAvatar` + name + secondary text. `AgentPicker` and `AgentCommandItem` in particular are structurally identical (single-select, `Command`-based) and are strong merge candidates via a shared "agent row" render-prop/variant, leaving `AgentChipPicker` separate only because of its genuinely different multi-select keyboard model.
3. **Two color/emoji override pickers for the same data** (`agent.color`/`agent.icon`): `agent-hub/ui/AvatarPickerPopover.tsx` (`AvatarPickerPanel`, inline full-width panel with sparkle/ripple celebration) and `agent-settings/ui/IdentityTab.tsx:276-374` (two separate `ResponsivePopover`s, one for color one for icon). Same 10 color presets (`COLOR_PRESETS`) and same `EMOJI_SET` grid, copy-pasted between the two files rather than shared.
4. **Two `OriginMark` components with the same name, different domains**: `entities/room/ui/OriginMark.tsx` (message/member provenance — a security-relevant "not from this machine" mark, spec `chats-as-channels` §9) vs `entities/session/ui/OriginMark.tsx` (session-launch origin — CLI/API/scheduled). They share a name, a "· label" pattern, and a size prop, but render structurally different information from different schemas (`AuthorOrigin` vs `SessionOrigin`). Not mergeable as-is, but the shared name across two entity modules is a real footgun for anyone doing an import-by-autocomplete during the consolidation — worth renaming one (e.g. `SessionOriginMark`) even if they stay separate.
5. **`AgentIdentity` (entities/agent) vs `RuntimeIdentity` (entities/runtime)**: same shape (icon/avatar + formatted text, single-line vs tooltip-only variants), different subject (agent identity vs runtime/model identity). Not the same domain, but the pattern (`Identity` = glyph + name composition, `Mark` = icon-only/tooltip variant) recurs three times independently (`AgentIdentity`/no-Mark-variant, `RuntimeIdentity`/`RuntimeMark`, session `OriginMark`/no-Identity-variant) with no shared base component — a candidate for a generic `<IdentityLockup icon name detail variant="inline|stacked|icon-only">` in `shared/ui` that each entity configures.
6. **`RoomMemberRow`'s inline face-resolution comment vs `MemberList`'s** — both independently implement "prefer the agent's own manifest face, then the author record's cached emoji/color, then a letter" and both hand-roll the same `IdentityAvatar` call shape (`color`, `emoji`, `fallback={initialOf(...)}`, conditional `badge`). Two duplicate implementations of "resolve one room member's face" sitting one file apart from each other (`room-management/ui/RoomMemberRow.tsx:185-194` and `entities/room/ui/MemberList.tsx:86-100`), with the shape/badge decision made differently in each (RoomMemberRow adds a `Bot` badge for agents and no shape; MemberList adds no agent badge and no shape). This is the pair most worth reconciling first, since fixing it fixes the sharpest violation in (b).

## (d) How "managed by" / agent ownership is shown today

**It isn't — there is no such concept anywhere in the client or the shared schemas.** Confirmed by:

- `packages/shared/src/mesh-schemas.ts` has no `managedBy`, `parentId`, `ownerId`, `reportsTo`, or hierarchy field on `AgentManifest`/`TopologyAgent`. The only grouping concept is `namespace` (`mesh-schemas.ts:300,457,514-517`) — a project-directory-derived string used for cross-agent messaging permissions, not a management/ownership relationship.
- `AgentHealthDetail.tsx` (the `/agents?view=topology` detail panel — the closest thing to an "agent profile" surface) shows status, last-seen, last-event, runtime, registered-at, and capabilities (`:87-136`). No manager, no owning agent, no team/hierarchy field.
- `AgentNode.tsx`'s topology cards show namespace colour as a left border (`resolveBorderColor`, `:42-44`) and relay/task badges — again, no manager attribution.
- No component anywhere (agent cards, chat, session views, mesh/directory views, room member sheet) renders an "agent X is managed by agent Y" relationship, a supervisor chip, or a hierarchy breadcrumb.
- The one adjacent concept that exists is **room membership provenance** (`RoomMemberRow`'s `OriginMark`, `authorRef.origin`) — who a _message_ came from — which is unrelated to agent-to-agent management.

**Implication for the consolidation plan:** "an agent's manager is always visible" is not a UI-consistency fix, it is new information architecture — there is no `managedBy` field to surface yet. That will need a schema addition (`AgentManifest` or `TopologyAgent`) before any component work, and a place to put it: the two natural existing slots are `IdentityHoverCard`'s fact-chip row (`identity-hover-card.tsx:133-151`, already has an `agent` info block with `runtime`/`model`/`working`) and `AgentHealthDetail`'s field list (`AgentHealthDetail.tsx:94-135`).

## Summary for the consolidation

- **Real, working convention**: `IdentityAvatar`'s `shape`/`variant`/`badge` triple, fully correct in exactly 2 places (`MessageAuthorAvatar`, `identity-hover-card`) out of ~20+ agent-rendering call sites.
- **Root cause**: `AgentAvatar` (the base every non-chat agent surface builds on) never sets `shape`/`variant`, so the violation is inherited by construction rather than repeated by hand each time.
- **Sharpest violations** (agent and human compared directly, in one view, and still shape-identical): `RoomMemberRow.tsx:185-194` and `MemberList.tsx:86-100`.
- **Highest-leverage fix**: give `IdentityAvatar` (or `AgentAvatar`) a `kind`-driven default so `shape="square"`/`variant="fill"`/`badge=<Bot/>` happen automatically for agents, rather than being opt-in per call site.
- **Managed-by**: doesn't exist yet, anywhere — schema work, not just UI work.
- **Merge candidates ranked by payoff**: (1) `AgentAvatar` → fold into `IdentityAvatar` variants, (2) `RoomMemberRow`/`MemberList` face-resolution unify, (3) `AgentPicker`/`AgentCommandItem` single-select row unify, (4) the two color/emoji override pickers (`AvatarPickerPanel` vs `IdentityTab`'s inline pickers) deduplicate their shared `COLOR_PRESETS`/`EMOJI_SET` UI.
