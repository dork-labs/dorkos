## 2. Remediation advice that is harmful at scale

**Cost model.** One push costs 19-25 Actions jobs (§0). On the Team plan the pool is 60 concurrent jobs, and a queue entry costs about 19-20 jobs (inventory headline 6). If 20 agents act on the same stimulus (for example a flaky browser shard that ejects the whole batch, or a systemic red), a single "push" remedy puts **about 400-500 jobs** in line. That is 7-8 full refills of the pool, each pinned for the 15-36 min that `test` shards and `credential-free-build` run, so **roughly 1.5-3 hours of saturated runners**. The merge queue's own builds wait behind it, which is how the 08-23 backlog formed (PLAN §4.9 point 3).

### Quantified: what to tell an agent on `EJECTED(failed_checks)`

- **85%** (209/247, 30 days) of failed-check ejections were re-queued with no new commit and then merged. In 7 days it was 77% (T02 A3). Unchanged re-entry took a median of 23 min (p90 2.1 h). An ejected PR spends a median of 2.1 h in the queue against 26 min for a PR that is never ejected.
- **Acting on every ejection** (push or rerun): 85% of the time it is wasted. Each wasted push costs about 20-25 jobs, plus 14-38 min of PR checks (T02 B2, p50/p90) before the PR may re-enter. That is _slower_ than merge-tail's ≤10-min re-arm and adds load for every other PR.
- **Doing nothing** on the first ejection: in the 15% of real cases the PR is re-queued once more and fails again. That wastes one queue build (about 30 min, about 19 jobs) and forces a rebuild of the entries behind it.
- **Recommendation.** On the first `failed_checks` ejection: do nothing to the branch. merge-tail re-queues it. While waiting, check cheaply and locally: if the failing merge-group job belongs to a package this PR touches, run that package's tests locally (`pnpm vitest run <path>`). Act only if they reproduce. On the **second ejection by the same job with no commit in between**, investigate as a real failure (`EJECTED_REPEAT`). The threshold (2) should come from the collector's measured P(real | k-th ejection by the same job), kept in `ci/config.yaml`, not hardcoded. Note the tail: #1284 was ejected 17 times for failed checks. Something should have escalated long before that, and the watcher is where it can.
- The median unchanged re-entry is 23 min against a 10-min merge-tail tick. So either merge-tail skips ejected PRs for a while (for example a red advisory check) or the cron is delayed under load (05 Q6: schedules "can be delayed … may be dropped"). The collector should attribute this. It is part of `wasted-queue-builds` hours.

## 3. Changes the CI Steward plan requires, phase by phase

### Phase 0 (foundation)

Skill:

1. **New section, "Pipeline-touching PRs need a ledger entry".** The trigger is the coverage path set; **link** `.claude/rules/ci-pipeline.md` rather than copying the list. Run `/ci:record` before the squash, so the entry rides the one commit. Kinds are `experiment`, `incident-fix` and `hygiene`. Never hand-write `verified`, `failed` or `inconclusive` (the validity check rejects them). Coverage is advisory for its first 7 days, then blocking via the allowlist expiry. Codex does not get the rule projected (PLAN follow-up J), so the skill carries the must-know sentences: "a pipeline change needs a hypothesis" and "ratchet releases block review by default".
2. **Delete** SKILL:284-300 (strict / up to date), :350-379 (BEHIND and "nobody arms"), :398-400 (the 4-check list). Replace "ask the repo" (:385-390) with the rules-API command, and after phase 0 retires classic protection, with `ci/required-checks.json` / `ci-steward census`, which is the "docs that can't drift" principle. Fix `--squash` at :292 and :510.
3. **Rewrite the arming paragraph** to state today's truth: merge-tail arms any green, unheld, thread-free PR within 10 min. Arming at creation is fine. Until phase 2, the review and the threads bind only PRs that merge-tail arms, so the pre-PR adversarial review is the real gate.
4. State the new invariant: **no admin merges, ever, from an agent** (the phase-0 PreToolUse guard on bare `--admin` and on `PUT /pulls/{n}/merge`).
5. Add `.agents/skills/creating-pull-requests/**` to the coverage paths (and the census atlas). This skill and watcher are how every agent acts on CI, so changing them is a pipeline change.

Watcher: 6. Fix 1.10 to 1.14 now: the dead `STALLED_IN_QUEUE`, `cancel` / zero checks, outdated-thread parity, the precedence of armed + threads, and `ERR` blindness. None depends on the steward.

Also: fix the stale `merge-tail.yml` and `should-arm-automerge.sh` headers (1.17) **before** they become fenced.

### Phase 1 (observe)

7. **`/ci:status` is the first stop for any red.** Replace SKILL:424-430's manual "does it fail on main's last few commits" procedure and :659-661's "check githubstatus" with `/ci:status` (constraint, health, open incident, standing reds). Keep githubstatus as step two.
8. **The local time-wrap and the 10-min tool ceiling.** 13-18% of agent pushes hit the ceiling (T02 D). The wrapper records a START with no END as killed. Skill text:
   - Run `git push` with the Bash `timeout: 600000`, or in the background.
   - After any push, confirm with `git ls-remote origin <branch>` (already SKILL:542-546).
   - A killed pre-push hook is data, not a reason for `--no-verify`, because `--no-verify` runs are invisible to the wrapper (PLAN §4.5). The one sanctioned `--no-verify` stays the fresh worktree with no `node_modules` (SKILL:579-581).
   - Never kill a leftover hook process by name (Hard Rule 7). SessionStart reports it as "running or killed".
9. Watcher: nothing required. Optionally print `/ci:status`'s constraint line once at start, so the agent knows whether the queue is healthy before it reads any event.

### Phase 1b (incident mode)

10. **`HELD(incident)` outranks every non-terminal state**, including `CONFLICTING` and `FAILING`, because every remedy for those pushes, and pushes are load. The sentinel cancels held PRs' runs only at freeze time (PLAN §4.9 L0 step 4), so a later push re-adds load. It is derived from the `ci-hold` label **or** from `queue-state.json` listing the PR. The label alone is not enough: an agent or a stale habit can remove it. Remedy: "Do nothing: no push, rerun, re-arm, relabel or dequeue. The sentinel re-arms held PRs oldest-first in waves (2, 5, all) when the breaker closes; the objective is p90 ≤ 45 min, the floor 2 h. You may stop watching." It exits with a distinct code (5) so the agent can end its turn. Secondary facts ride along: `HELD(incident since 14:05: systemic browser-test; also CONFLICTING)`. Rebasing **locally** is fine; pushing is not.
11. **`EJECTED(manual)` must check hold first.** A sentinel dequeue is a `manual` removal, and the actor is the operator's account either way, so `actor` cannot tell them apart. If the PR is held, report `HELD`. Otherwise: "someone dequeued this on purpose; find out why before re-arming."
12. **`PRIORITY`** (the `ci-priority` label): informational. "The sentinel re-runs your PR checks first and jumps it when green. Do not arm, push or relabel unless you are fixing the fix."
13. **WIP cap → `AWAITING_ARM_SLOT(pos/K)`**, when green, unarmed and refused a slot. Remedy: "The sentinel arms first-in, first-out; do nothing." This replaces `UNARMED_CLEAN` (1.9), which would otherwise tell every capped agent to merge directly.
14. **The refused-arm message.** The PreToolUse guard's text ("queue breaker open since HH:MM; your PR is re-armed automatically when it closes") must match the watcher's `HELD` remedy word for word, from one source. Codex has no PreToolUse hooks, so for Codex agents the watcher and the skill are the only channels.
15. **Break-glass in the skill:** "`/ci:break-glass` is the operator's lever. Never an agent default, never suggested by the watcher, never a response to your own PR being slow." No watcher token may ever contain `--admin`, `break-glass` or `jump` (a remedy-text fixture, §5).
16. **The STUCK_UNMERGEABLE recipe** is gated on GREEN plus a dwell (1.15).

### Phase 2 (enforce)

17. **The review table (SKILL:196-209) and labels (:256-282) are rewritten.** The review is a required context, red on ≥ 1 important finding, re-runs on `synchronize` scoped to the delta, and has a `merge_group` pass-through job. `re-review` becomes "same-SHA re-review, which can flip red to green only by retracting each prior finding by id". SKILL:674-678 ("non-blocking") is inverted. `skip-review` must be retired or made to fail rather than skip (§6.8).
18. **New watcher events** (§5):
    - `REVIEW_RED(important n)`. Remedy: fix and push; the new SHA re-reviews automatically, so no label is needed. If a finding is wrong, answer it on its thread with evidence, then add `re-review`. The same-SHA pass must retract it by id. **Never push an empty or cosmetic commit to get a fresh roll.**
    - `REVIEW_INFRA(class)`. Remedy: do nothing; merge-tail re-dispatches with 10/20/40…120-min backoff. Report `review-recovery`.
    - `REVIEW_FORK`. See 20.
19. **Ratchet advisory → `RATCHET(<pkg>: -n tests)`**, read from the PR advisory comment (or its check output). Remedy: "Restore the tests, or if the drop is intended, `/ci:record --release <ratchet> <pkg> <value> "<specific reason>"`. The review blocks vague reasons. The release must be ≤ 14 days old at queue time and is spent once; `/ci:record --release` can re-stamp it. Otherwise the queue ejects you in about 30 min." A merge-group ratchet ejection should surface as `EJECTED(failed_checks: test — ratchet <pkg>)`, not as a generic failure, and **never** as "do nothing, it's probably flaky". Ratchet failures are deterministic, so the 85% rule must exclude them.
20. **Fork PRs.** Per PLAN follow-up L, a fork PR fails the required review deterministically, classified `fork`. Under the plan's rules nothing can merge it: break-glass is incident-only and pipeline-only. The skill needs an adoption path: a maintainer agent pushes the contributor's commits to a same-repo branch with `Co-authored-by`, opens a PR, and closes the fork PR with a note per `meta/user-care.md`. The watcher reports `REVIEW_FORK` with that remedy.

## 4. Should the watcher join `packages/ci-steward`?

**Yes, as the per-PR half of one classifier. Keep a thin shim at the old path.**

Why:

- **Three classifiers already disagree about the same PR**: `watch-prs.sh` classify(), `should-arm-automerge.sh` (merge-tail's decision), and soon the sentinel's held and backlog accounting. They disagree on outdated threads (1.12), cancelled and zero checks (1.11), hold labels and drafts (1.9), and `CHANGES_REQUESTED` (the watcher ignores `reviewDecision`). Each disagreement is an agent waiting on a PR that the bot will never touch, or acting on a PR the bot is about to handle.
- **The fence.** Once the watcher tells 20 agents to stand down, it is part of the incident control loop. A `ci-improve-tick` that edits `HELD`'s remedy or precedence defeats the breaker. `packages/ci-steward/**` is fenced (PLAN §4.7) and the skill's `scripts/` is not.
- **One poller, many readers.** The sentinel already fetches every open PR's queue and timeline state every 5-10 min. Publishing per-PR states in `queue-state.json` lets watchers read one file (one REST call, or `git cat-file` after a fetch) instead of N agents polling GraphQL on the operator's shared budget (§0, §2).

Shape:

- `packages/ci-steward/src/pr-state.ts`: a pure `classifyPr(snapshot, queueState, config) → {token, args, actor, remedy, exit}`. `should-arm` becomes `classifyPr(...).armable` with its SKIP slug. The 27 `test-should-arm-automerge.sh` fixtures and TEST's fixtures become one shared JSON corpus that both the bash shims and vitest run.
- **Two layers, one vocabulary file** (`src/states.ts`): `QueueState` = GREEN / AMBER / RED / RECOVERING (the sentinel) and `PrState` (the tokens in §5). Each PrState names its **actor** (`you`, `merge-tail`, `sentinel`, `operator`). This is the column that tells an agent "not your move". The skill's vocabulary table is generated from it, and the census fails when the skill's table drifts.
- **The dependency budget.** The per-PR classifier and `watch` entrypoint must run from a fresh worktree with no `node_modules` (the SKILL:562-581 gotcha). That means node built-ins only: no `zod` or `yaml` on that path. Thresholds come from a JSON the collector writes, or are embedded. The bash shim `watch-prs.sh` stays for one release and execs `node --experimental-strip-types <primary-checkout>/packages/ci-steward/src/cli.ts pr-state --watch …`. If the engine is unreachable, it fails loudly (exit 4 "WATCHER DIED: engine unavailable") rather than falling back to a second classifier that would drift.
- **Phase 5** (plugin): `pr-state`, the watcher and a generic "landing PRs under ci-steward" skill move with the engine. The DorkOS skill keeps the repo-specific parts (Linear closing words, changelog fragments, worktree janitor).

## 6. What the plan gets wrong or misses, from the PR author's side

1. **How an agent learns it is held, mid-session.** The plan relies on the SessionStart line, the PreToolUse guard, the `ci-hold` label and the watcher. A running session sees SessionStart only once, and the guard only when it tries to arm. Codex has no hooks at all. So the **watcher is the only in-session channel**, and the plan gives it one token. It needs everything in §3 items 10-14, and `queue-state.json` must carry per-PR entries (held since, signal, wave position), not just the global state.
2. **How long to wait, and when to stop watching.** The plan has no watch-termination policy. Lead time is p50 58 min, p90 3 h, and an ejected PR takes p90 **19.7 h** in the queue. DorkOS parks background work at a 4 h ceiling (memory `project_dorkos_session_process_kills_20260915`), and every Monitor event is a full-context model wakeup. The tail is already automated (merge-tail re-queues; the sentinel releases held PRs), so the default should be **hand off at "queued and green" (`HANDED_OFF`)**. That cuts watching to about created → first queue entry (p50 16-23 min, p90 75 min-2 h, T02 A2). Informational tokens stay behind `--verbose`. The plan's cost line (§8, "15 runner-minutes a day") should also count watcher API calls and agent wakeups.
3. **A shared API budget.** Watchers, `MERGE_TAIL_TOKEN` (the operator's PAT) and the local sentinel (the operator's `gh`) share one user's GraphQL budget. The sentinel is starved exactly when watchers are busiest. Mitigation: watchers read sentinel-published state (§4); phase 0's replacement of `MERGE_TAIL_TOKEN` by a GitHub App gives merge-tail its own budget; and the sentinel should have a reserved or separate credential.
4. **The WIP cap is undefined against arm-at-creation.** 647 of 779 PRs arm at open, median 0 min. If K counts "armed-unmerged", slots fill with PRs whose PR checks have not finished (median 17 min, p90 80 min from arm to first queue entry), which starves green PRs. Define K over _queued plus armed-and-green_. Say who re-arms after a push disarms a capped PR (the sentinel, FIFO by first-green time?). Say whether the guard enforces the cap in GREEN or only in AMBER.
5. **Label churn triggers required-check runs.** `changelog-fragment-check.yml:55-56` runs on `labeled` and `unlabeled`, and `fragment-present` is required. Freezing 20 PRs with `ci-hold` and releasing them starts about 40 extra runs at the starved moment. The skip-changelog race (memory) shows that label-event runs can leave a stale red on the SHA. Measure it in the 1b dry run. Do not "fix" it with a job-level `if:` that skips: a skipped run satisfies a required context.
6. **The required review can be satisfied by a skipped run.** `claude-code-review.yml`'s job `if:` skips on `labeled` events for any label except `re-review`, on `skip-review` and on drafts. Memory already records a no-op twin whose skipped `review` check sometimes wins the rollup. Once `review` is required, adding `ci-hold`, `hold` or `review:light` to a PR with a red review may post a **skipped** `review` check-run on the same SHA and satisfy the context. That bypass is likely but unverified; prove it on a fixture PR before phase 2. Fix it by making the required context a separate always-running gate job that reads the latest real verdict for the head SHA, and by retiring `skip-review`. The plan closed this hole for forks only (§5, follow-up L).
7. **The same-SHA rule is bypassed by a trivial commit.** PLAN §5 fences re-rolls "on the same SHA". An empty or whitespace commit is a new SHA, and the scoped re-review sees an empty delta "plus prior findings" with no retraction requirement. Findings must carry forward across SHAs until their lines change or they are retracted by id. The same tree-identical commits must be excluded from the collector's "real catch" and `wasted-queue-builds` derivations (§2), or the watcher's historical remedy keeps polluting them.
8. **`ci-priority` has no preconditions.** Break-glass has five mechanical ones. `ci-priority` makes the sentinel jump the PR with admin credentials, so any agent that can label can jump the queue, which rebuilds up to 5 groups (05 Q1). Mirror the break-glass diff and ledger preconditions (a pipeline-only diff, `kind: incident-fix`), and say who may run `/ci:incident fix`.
9. **"Local-only by construction" is not "operator-only".** Agents run on the operator's machine with the operator's admin `gh` session. After phase 0, break-glass, jump and ruleset edits are local-only, so they are available to every local agent. The Claude PreToolUse guard is the only barrier: Codex bypasses it, and so does raw `curl` with `gh auth token`. Consider a separate admin credential that agents' default `gh` config does not hold, or an interactive confirmation.
10. **Other actors that arm or rerun are not covered by the freeze:**
    - the flow plugin's auto-merge recovery ladder (`retry-ci` and `merge` dispositions, `marketplace/plugins/flow/scripts/gates-policy.ts:130-137`), with autonomy on in the installed copy;
    - `/app:upgrade`'s own arming (`.claude/commands/app/upgrade.md:606-609`);
    - `@claude` via `claude.yml`, which has `contents: write`.

    Each must read `queue-state.json` or honor `ci-hold`.

11. **Deterministic failures need an exemption from "wait and re-queue".** Ratchet ejections and the census and ledger steps inside `typecheck` never pass on retry. merge-tail will re-queue them forever, and each attempt burns a queue build. Should-arm, or the sentinel, should not re-arm a PR whose last ejection is classified deterministic until a new commit lands.
12. **`STUCK_UNMERGEABLE`, `STALLED_IN_QUEUE` and ejection reasons belong in the collector's population.** The watcher sees them first. Report per-PR states to the data branch (via the sentinel), so the weekly report can measure how often agents hit each state and how long each lasted. That is the "self-monitoring" loop applied to the author's experience, which the SLO table currently ignores. `lead-time` is measured, but the author-facing stall classes are not.
13. **The skill is a pipeline control surface but sits outside the plan.** PLAN §4.8 lists the rule, the guide and the `stewarding-ci-pipeline` skill, but not `creating-pull-requests`, which is what 20 agents actually read when their PR is red. Put it in the coverage paths (§3 item 5) and its watcher in the fence (§4). The plan's phase 1b and phase 2 exit gates should include "the watcher fixtures for the new states pass".
