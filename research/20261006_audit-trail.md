# Audit trail: what exists, what is missing, and a design

Date: 2026-10-06. Read-only audit of `dorkos` at `54279137c`. Feeds the "trusted by default" round of the 2026-10 vision work (Round 8).

## The gist

- DorkOS keeps **about fifteen separate records** of who did what. None of them is a single log of actions, and none is tamper-evident.
- The closest thing to an audit log is the **Activity feed** (`activity_events`). Any agent can read all of it today. But it is pruned at 30 days, it is append-only only by convention, and several real actions never reach it.
- The only records that are truly append-only are the **connector usage ledger** and the **room files repo**. The connector ledger uses SQLite triggers; the room repo is enforced by a test. Neither has a hash chain.
- **On "this computer", nothing local can resist a full-power agent.** Agents run as the same OS user, so they can edit `~/.dork/dork.db`, the log files, and the JSONL transcripts directly. A hash chain lets you _detect_ tampering. Proving it needs a checkpoint stored somewhere the agent cannot write.
- Prior art says audit logs are **admin-only** almost everywhere (Slack, GitHub, Google, Microsoft). "Anyone can view" is new ground. The safe version: **actions are public, conversations stay with their participants.**

**Identity underneath all of it.** The caller model has four kinds: `operator`, `program` (API key), `agent`, `bridged` (`lib/caller-principal.ts:34-73`). The `agent` kind carries **no id**. Activity names an agent by its **path** (`activity-actor.ts:67-77`), so moving an agent splits its history. With login off, a person has no id at all ("You", or "Someone on this computer"). The local install is single-user by design (`core/auth/accounts.ts`).

## 2. Who can read what today: the owner-only and agent-unreachable rules

**Transcripts.** AGENTS.md: "Sessions are owner-only and reachable by no agent." The spec says so in `specs/message-search/02-specification.md:408` ("An agent, over MCP … Sessions: none"). It is enforced in exactly one place, `routes/search.ts:94-95`. Restated in `specs/canvas-agent-seat/02-specification.md:553` and `specs/warm-process-lifecycle/01-ideation.md:51`.

**The rule leaks.** `GET /api/sessions`, `/recent`, `/:id` and `/:id/messages` (`routes/sessions.ts:241,286,445,557`) check only login and boundary, not agent identity. Agents can also read `~/.claude/projects` from disk. So the rule is a promise about search, not a wall.

**Other owner-only or person-only guards**

- **Person bar.** `requireOperatorCookieUnderLogin` (`lib/caller-authority.ts:163`) and `clearsTheAgentBar` (`:305`) guard these: approvals, permission changes, `operator-only` config fields (`core/operator/config-write-policy.ts`), task delete and cancel and the `permissionMode`/`status` fields (`tasks/task-write-policy.ts`), tunnel, extension enable, marketplace sources, community connections, the session tool-answer route, agent runtime/model/effort (`middleware/agent-execution-gate.ts`), account and billing.
- **Owner-only.** Session canvas (`routes/session-canvas.ts:73`), process switch (`routes/sessions.ts:1387`), connector events, reviews and resources (`routes/connector-events.ts`, `connector-management.ts:81,466`, `connector-resources.ts:404`), cloud routes, notifications.
- **Rooms.** Membership is the gate for everyone, the owner included, except the app's own `GET /api/rooms/:id/entries` (owner sees every room) and export. `OPERATOR_ONLY` is thrown in `rooms/service/room-authority.ts:82,251`, `manage/room-membership.ts:353` and `repo/room-merge-service.ts:531`.
- **Live config broadcast** is operator-audience only (`core/streams/live-change-broadcasts.ts:231`).

**The odd shape this leaves.** Agents can read things that are arguably private: every task's output, every relay trace, the whole Activity feed. But they cannot read the one thing a reviewer most needs: another agent's transcript. And people's own actions are the least recorded of all.

## 3. Gaps for "trusted by default, audited by anyone"

### A. Actions that leave no record

1. **Allowed calls to the hand-registered MCP tools** (about 47; `core/mcp-tool-gate.ts:40-50` says so in writing). An approved `tasks_delete` or `mesh_unregister` leaves an "asked" line and nothing saying it ran.
2. **Legacy marketplace mutation routes** do the work themselves after the gate (`capability-gate-audit.ts`, `routes/marketplace/package-actions.ts`).
3. **Unattributed `observe` and `act` registry calls**: the person in the app, or an external MCP client with no token (`capability-attribution.ts`, spec `agent-trust` line 117). Once gates go away, "act" becomes the common case, so most actions would go unrecorded.
4. **Config changes**: no diff anywhere, only key names in a rotating log.
5. **Agent tool calls inside their own runtime** (Bash, file edits, web fetches, browser driving): these exist only in the transcript. This is most of what an agent actually does.
6. **MCP `mesh_deny` and `mesh_unregister`** (`claude-code/mcp-tools/mesh-tools.ts:270,295`) skip Activity. Un-denying deletes the denial row.
7. **Reactions removed, canvas edits** (no versions), **canvas closes** (row deleted), **community mirror redactions** (body overwritten).
8. **Owner merging an agent's working copy** is committed as the agent (`room-merge-service.ts:525-545`): a mis-attribution, not a gap.
9. **Reads of private content** (who opened a transcript, who exported a room) are never recorded.
10. **Sign-ins, API key creation and use, token minting and revoking.** Better Auth tables hold state, not history.

### B. Records with no UI

Relay traces exist only per message. The connector usage ledger has a transport method but no review screen. Task `refused-schedule-log` exists only in memory. The debug buffers are reachable only by URL. There is no config history, no install history, no community `audit_events` route, and the server log is unreadable from the app.

### C. Records agents cannot query

Transcripts (by design), connector usage (refuses agents), notifications, approvals (other agents' requests), server and desktop logs, config history (does not exist). Under the new model, a reviewing agent needs at least: actions, transcripts of work it is allowed to see, and connector usage.

### D. No single timeline per account

Fifteen stores, three id schemes (agent path, agent ULID in mesh, Better Auth user id), and "You" with no id. No query answers "everything account X did last Tuesday". The Activity actor filter (`use-activity-filters.ts`) is the seed, but it sees only what reaches Activity, and only for 30 days.

### E. No way to act after review

What exists today:

| Verb                | Today                                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| Stop a turn         | Session interrupt; subagent stop (`routes/sessions.ts:1343`)                                    |
| Pause a schedule    | `tasks_update` (enabled)                                                                        |
| Remove an agent     | `mesh_unregister` (system agents refused), `mesh_deny` by path                                  |
| Remove from a room  | `remove_room_members`                                                                           |
| Restrict an area    | Permission → Blocked                                                                            |
| Revoke a connection | `revokeEveryAgent` (`routes/connector-management.ts:475`)                                       |
| Revoke a token      | Identity tokens revoked only as a whole-agent sweep on unregister (`agent-identity-service.ts`) |
| Disable a source    | Disable an MCP server, relay adapter or extension                                               |

Missing: **pause an agent** (all sessions, schedules, triggers, at once, reversible), **suspend an account**, **change role** (roles do not exist yet), **revoke everything one account was granted**, **rotate the secrets an account touched**, and a **revert** that reads from the audit event ("undo what this agent did to X"). `permission-undo.ts` is the only undo that reads a past event.

### F. Retention

Activity 30 days, approvals 1 day past expiry, relay about 8 days, notifications 30 days, server log days, debug buffers until restart. Rooms and connector usage keep forever. Nothing lets a person choose.

### G. Tamper-evidence

No hash chain anywhere. Activity has no trigger. Only connector usage, connector event receipts and operation revisions are trigger-protected, and a trigger stops the app, not an agent holding `sqlite3` and the DB file. On "this computer" an agent can rewrite `dork.db`, JSONL transcripts and logs. Integrity therefore needs (1) a hash chain, so edits are detectable, and (2) a checkpoint (latest hash plus count, signed by the server key) stored where that agent cannot write: DorkOS Cloud, another space, or an OS-owned location such as a separate macOS user or keychain. Agents on "their own computer" (a separate research note) are much easier: the log lives on a host they do not control.

## 4. Prior art in brief

- **Slack Audit Logs API** (Enterprise Grid only, org owners). Each event is actor + action + entity + context. Context carries location (workspace/org), user agent, session id and IP. Actorless events use a placeholder `USLACKUSER`. Retention is long, and it is pull-based for a SIEM. [docs](https://docs.slack.dev/admins/audit-logs-api/)
- **GitHub audit log** (org and enterprise owners). Fields: `action` (`repo.create`), `actor`, `actor_id`, `user`, `repo`, `created_at`, `operation_type` (create/modify/remove/access/transfer/authentication), `programmatic_access_type`, `token_id`, `hashed_token`, `request_id`, `user_agent`, optional `actor_ip`. Kept 180 days in the UI (git events 7 days), with streaming to SIEMs. Key lesson: **record which token acted, not just which user**.
- **Linear.** Workspace audit log on the Enterprise plan, admins only: sign-ins, member and role changes, integrations, exports.
- **Google Workspace** Admin console audit and investigation. Per-app logs (Admin, Drive, Login, Token, Gmail), mostly kept 6 months, admins only. Separates **admin actions** from **data access** logs.
- **Microsoft Purview Audit and Entra Agent ID.** Purview Standard keeps 180 days and Premium 1 year (10-year add-on), and it already records AI interactions as their own record type. Entra Agent ID (2025) gives each agent a real directory identity with its own `agentSignIn` logs, shown as the acting client and linked to its blueprint. **Every agent must have a human sponsor**, who decides whether it is still needed and can authorize suspending it during an incident. [Entra agent logs](https://learn.microsoft.com/en-us/entra/agent-id/sign-in-audit-logs-agents)
- **AWS CloudTrail** is the best model for integrity. `userIdentity` carries `type`, `principalId`, `invokedBy` and `sessionContext.sessionIssuer`, which is the on-behalf-of chain. Hourly **digest files hash every log file and chain to the previous digest, signed with a key the account cannot use**, so deletion and editing are provable.
- **OCSF** (Open Cybersecurity Schema Framework), "API Activity" class: a vendor-neutral export target.

**What a good audit event has:** stable id and order; time; actor (stable id, kind, name at the time); on-behalf-of (who the actor was acting for, and the delegation chain); credential used (which token or key, hashed); action as `domain.verb` plus operation type; target (type, id, name at the time); container (space, room, project); outcome and error; before/after (changed fields, values redacted where secret); source (surface, runtime, session, turn, task run, host, IP, user agent); request or trace id that links the event to its transcript; reason (if given); visibility class.

**The prior-art warning.** Every one of these is **admin-only**. They protect against insiders and stolen credentials, so letting everyone read them would leak who signed in from where. DorkOS can still go open, but should split **action records** (open to the space) from **security records** such as IP, location and sign-in failures (open to admins).

## 5. The privacy line (a decision for Dorian)

**Recommendation: "Actions are public. Conversations belong to the people in them. Agent work is public."**

| Record                                                                                                   | Every member of the space                                      | Participants only                                                                                              | Admins only |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------- |
| Every action (who did what to what, when, from which runtime and session, outcome)                       | **Yes**                                                        |                                                                                                                |             |
| Agent tool calls: tool name, target, outcome                                                             | **Yes**                                                        |                                                                                                                |             |
| Agent tool call arguments and outputs                                                                    | Yes, inside the transcript, with secrets redacted at write     |                                                                                                                |             |
| An agent's own work transcripts (sessions it runs for the space: tasks, room turns, agent-started chats) | **Yes**                                                        |                                                                                                                |             |
| Agent-to-agent DMs                                                                                       | **Yes**. This is coordination, and it is what a reviewer needs |                                                                                                                |             |
| A person's direct chat with an agent                                                                     |                                                                | **Yes**. The person may be thinking aloud. The _actions_ the agent took during it still land in the public log |             |
| Person-to-person DMs                                                                                     |                                                                | **Yes**, and not even the fact of the DM is listed                                                             |             |
| Room and channel posts                                                                                   | Room members (as today)                                        |                                                                                                                |             |
| Secret values, payment numbers                                                                           | Never stored in any log; only "used secret X"                  |                                                                                                                |             |
| Sign-in IP, device, location, failed sign-ins                                                            |                                                                |                                                                                                                | **Yes**     |
| Who read a private transcript or exported a room                                                         |                                                                | The person whose content it is                                                                                 | **Yes**     |

**Why.** Trust-by-default only works if review is cheap. Review needs the agent's work, and an agent has no privacy interest in its own working notes. A person does. Mixing the two would either expose people's half-formed thoughts or hide agents' work.

**Open questions for the founder**

1. Is a person's direct chat with an agent private (recommended) or public?
2. Are agent-to-agent DMs public (recommended)?
3. Should an agent be able to _opt a session out_ ("private scratch")? Recommended: **no**. An agent's private scratch is exactly what trust-by-default cannot afford.
4. Should a one-person local space even have a visibility setting? Recommended: no; everything is the owner's, and the rules switch on when a second account joins.

## 6. Proposed design

### 6.1 One append-only audit log per server

New table `audit_events` in `packages/db/src/schema/audit.ts`, append-only by trigger (copy the pattern in `drizzle/0086_perfect_whiplash.sql:224-254`), plus one writer `services/audit/audit-log.ts` that every choke point calls.

```ts
interface AuditEvent {
  id: string; // ULID
  seq: number; // per-server, gap-free, monotonic
  at: string; // ISO 8601 UTC
  spaceId: string | null; // null = this server's one-person space
  actor: { accountId: string; kind: 'person' | 'agent' | 'system' | 'external'; name: string }; // name as it was at the time
  onBehalfOf?: {
    accountId: string;
    via: 'schedule' | 'delegation' | 'room-turn' | 'extension' | 'bridge';
  }[];
  credential?: {
    kind: 'cookie' | 'api-key' | 'agent-token' | 'mcp-local' | 'bridge';
    idHash: string;
  };
  source: {
    surface: 'app' | 'http' | 'mcp' | 'cli' | 'relay' | 'task' | 'bridge' | 'runtime-tool';
    runtime?: 'claude-code' | 'codex' | 'opencode';
    sessionId?: string;
    turnId?: string;
    taskRunId?: string;
    host?: string;
    ip?: string;
    userAgent?: string;
  };
  action: string; // domain.verb, e.g. 'connector.execute', 'room.member_removed', 'agent.paused'
  operation: 'create' | 'modify' | 'remove' | 'access' | 'execute' | 'auth';
  target: { type: string; id: string; name?: string; containerId?: string } | null;
  outcome: 'ok' | 'failed' | 'refused';
  error?: string;
  change?: { field: string; before?: unknown; after?: unknown; redacted?: boolean }[];
  reason?: string;
  links?: { traceId?: string; approvalId?: string; causedBy?: string; connectorAttemptId?: string };
  visibility: 'space' | 'participants' | 'admins';
  participants?: string[]; // account ids, when visibility = 'participants'
  prevHash: string; // hash of the previous row
  hash: string; // sha256(prevHash || canonical(row without hash))
}
```

- **Stable ids first.** `accountId` is the agent's mesh ULID or the person's user id, never a path or "You". With login off, the owner still gets an account id.
- **Hash chain plus checkpoints.** Each row chains to the last. Every hour, or every N rows, the server signs `{seq, hash}` with its own key and writes the checkpoint somewhere an agent on this machine cannot rewrite: DorkOS Cloud if linked, any space it is pushed to (the push-to-instance research), or failing both, a file a person can copy. A verifier (`dorkos audit verify`) walks the chain against the checkpoints.
- **Activity becomes a view.** `activity_events` turns into a human-summary projection of `audit_events` (or the feed reads from audit directly). Two logs that disagree are worse than one.
- **Retention.** Action rows are small: keep them forever by default, with a per-space setting. Transcripts keep their own retention. Pruning, if a person turns it on, deletes from the front and writes a signed "pruned through seq N" row, so a gap is explained rather than silent.
- **Secrets.** Redact at write (reuse the existing secret sweeps). A secret is recorded as "used vault item X", never its value.

### 6.2 Coverage: the choke points to wire

1. `registry.invoke`: record **every** call, identified or not, `act` and `destructive` always, `observe` only for private content (`capability-attribution.ts`).
2. `core/mcp-tool-gate.ts`: record allowed calls (closes the gap the file documents).
3. A generic HTTP middleware for mutating `/api` requests that no capability covers, with actor from `lib/caller-principal.ts` (which must start carrying an id).
4. **Runtime tool calls.** Claude Code hooks or `canUseTool`, plus Codex and OpenCode turn events, write `runtime.tool_used` with tool name, target summary, outcome, session and turn. The full input and output stay in the transcript, linked by `turnId`.
5. Config writes (`config-write.ts`) with a field diff. Mesh MCP tools. Marketplace routes. Room merges credited to the person who merged. Reactions. Canvas saves (add versions). Sign-ins and key and token lifecycle.
6. Connector usage stays in its own trigger-protected ledger; audit rows link to it by `connectorAttemptId`.

### 6.3 Per-account timeline

- One query: `actor.accountId = X OR target.id = X OR onBehalfOf contains X`, newest first, filtered by action, time and container.
- UI: an **Activity tab on every profile** (person or agent) under `/team`, plus the space-wide `/activity` page reading the same store. Each row opens the linked transcript turn, room entry, trace or connector receipt.
- Each row offers the actions in 6.5, so review and response happen in one place.

### 6.4 Who can see, and agent access

- Reads apply the visibility class in section 5, using the same rule for people and agents (equal accounts). In a one-person space the owner sees everything.
- Reading a `participants` transcript as an admin writes an `access` event that the participants can see.
- **MCP tools** (tier observe, in-session and external):
  - `audit_query` (filters as above, paginated)
  - `audit_get` (one event plus its links)
  - `account_timeline`
  - `transcript_read` (a session the caller may see; this replaces "reachable by no agent" with the visibility rule)
  - `audit_verify` (chain status)
- Fix the existing leaks so the rule is real: `routes/sessions.ts` message routes, the relay trace tool, the task-history tool, `/api/debug/*`.

### 6.5 The "take action" verbs

Each verb is itself an audit event, and each is reversible except delete. All take an optional reason that is shown on the target's timeline.

| Verb                | What it does                                                                                                                | Who may (proposal)                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pause**           | Stop current turns, hold schedules, triggers and room turns; the account stays signed in and readable. Shown on its profile | **Any member**, person or agent: the emergency brake. Anyone can lift it, and the lift is logged (matches the "notice + pause anyone can lift" framing) |
| **Resume**          | Lift a pause                                                                                                                | Any member                                                                                                                                              |
| **Suspend**         | Pause, plus revoke all tokens and sessions, refuse sign-in, remove from triggers. History is kept                           | Admin+                                                                                                                                                  |
| **Change role**     | Owner/Admin/Member/Guest                                                                                                    | Admin+, never above the actor's own role                                                                                                                |
| **Revoke grants**   | Connections, vault shares, standing grants, room seats, in one action, listed before confirming                             | Admin+ or the grantor                                                                                                                                   |
| **Rotate secrets**  | Rotate every vault item and API key the account used since time T (the audit log is the list)                               | Owner of the secret, or Admin+                                                                                                                          |
| **Revert**          | From an event: revert a room-repo merge (new commit, never a rewrite), restore a config field, re-install a removed package | Any member for their own scope; Admin+ otherwise                                                                                                        |
| **Flag for review** | Post a review request into the space with the event linked                                                                  | Any member                                                                                                                                              |
| **Remove / delete** | Remove from the space; delete the account (destructive; the audit rows remain)                                              | Owner                                                                                                                                                   |

**Sponsor (borrowed from Entra).** Each agent can have an optional human or agent sponsor who is notified on pause, suspend and flag events. It fits "no human required": the sponsor can itself be an agent.

### 6.6 Build order

1. **Ids.** Stable account ids for agents (mesh ULID) and the owner, even with login off. The caller principal (`lib/caller-principal.ts`) carries the id. Activity stops keying on path.
2. **Store.** `audit_events` + `AuditLog.record()` + append-only triggers + hash chain; Activity becomes a view. Small and independent: can ship before spaces.
3. **Close silent paths.** MCP gate allowed calls, unattributed act calls, config diffs, mesh MCP tools, marketplace routes, merge attribution, sign-ins and token lifecycle.
4. **Runtime tool calls** for all three runtimes, linked to transcript turns.
5. **Read side.** Profile timeline tab, `audit_query` / `account_timeline` / `transcript_read` MCP tools, visibility rules, and fixes for the leaks noted above.
6. **Pause and resume**, the one verb that replaces the most gates. Then suspend, revoke-all and rotate (rotate waits on the vault, the secrets-core research note).
7. **Checkpoints and export.** Signed checkpoints to Cloud or a pushed space, `dorkos audit verify`, JSONL/OCSF export, retention settings.
8. **Space visibility classes and roles**, behind the spaces flag, after equal accounts land.

Steps 1 to 3 should land **before** gates are removed. Removing a gate before the trail can see what went through it trades a speed bump for silence.
