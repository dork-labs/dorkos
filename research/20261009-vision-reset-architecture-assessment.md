## What changes in my recommendation

DorkOS is a workspace for people and agents, built for founders. The architectural unit is the workspace that holds conversations, tools, documents and access. An agent's identity, its engine and the computer executing it need separate lifetimes. A laptop and a hosted installation should be ways to run the same program.

The October 4 recommendation to preserve separate local execution and permanently agent-free Community servers is **superseded as a target**. [ADR 261006-235238](../decisions/261006-235238-one-dorkos-server-in-every-size.md) accepts Express → Hono → one program and one app, with no required Cloud account for local use. Separate servers still describe the reviewed implementation. The migration must preserve tenant authority, local ownership, optional Cloud contracts and failure recovery; changing the HTTP framework alone does not do that.

The strongest existing design choices remain useful: ports around execution and external services, server-held credentials, explicit spending choices, durable acceptance before delivery, rebuildable derived state, and approved executable code. The new direction makes these contracts more valuable. It also raises the priority of common work admission, readable action evidence and execution ownership above cosmetic interface splitting.

## Recommended architecture

Use one workspace core with explicit domain owners: membership/access, conversations, work admission, action evidence, projects, documents and installed contributions. HTTP, CLI, MCP and future APIs call the same commands. A command carries the authenticated actor, target workspace, origin, current authority and operation identity; it produces a domain result rather than owning a response socket.

Keep persistence and execution placement explicit. Local SQLite/files and hosted PostgreSQL/blob stores need equivalent domain invariants, not an enormous generic database abstraction. `AgentRuntime` selects an engine; it should not decide where an agent belongs or whether a caller may spend money. A future execution-host binding holds the one active executor, credentials it may use and its ownership generation. Local co-location remains a valid deployment.

Cloud stays optional. Its closed control plane continues behind public contracts for account, managed service and hosting operations. A shared app does not require publishing private Cloud internals, moving all data into Cloud, or making the public app depend on a private build.

The [target diagram](../contributing/diagrams/architecture/vision-reset-target.mmd) is a design recommendation aligned with accepted decisions. Its command core, persistence ports and execution fencing are proposed implementation seams, not completed interfaces.

## Ranked improvements

### 1. Finish action evidence, privacy and intervention before widening trust

Continue **DOR-2738 → DOR-2739**. Stable actors and a hash chain are a good foundation, but a hash chain proves integrity of recorded events, not completeness. [Audit writes](../apps/server/src/services/audit/audit-log.ts) can fail without blocking the action; [trail recording](../apps/server/src/services/audit/audit-trail.ts) skips an uninitialized recorder. The product needs an explicit, observable policy for unavailable audit storage.

Build an effect inventory across routes, MCP, runtime tools, Connections and executable contributions: actor/origin → current authority → durable record → permitted reader → cancellation/pause outcome. Private person chats must remain private across transcript, events, tasks, debug, search and audit readers. Recheck authority when delayed work commits, not only when it was accepted. An agent's trusted status cannot promote a stranger's message or package code.

**Bounded acceptance:** tests through the real entry points prove outsider-origin work cannot gain authority, private payloads stay hidden, and pause/revocation prevents the selected delayed effects. Audit failures are observable and their effect policy is specified. Preserve current caps until the owning migration has this evidence.

### 2. Give proactive work one admission and lifetime contract

Continue **DOR-2783/2784/2788**, reusing the implemented **DOR-2786/2787** engine/runtime and **DOR-2778** decision port. First-run defaults and model choice belong to their current owners. The platform beat runner should gather in code, triage only changed work, and start a real turn through core launch/admission services. It should not become another execution engine inside the scheduler or an extension.

One accepted beat needs a stable operation ID, event deduplication, exclusive ownership, back-off, cancellation/pause, an audit outcome and batching per recipient. A decision model recommends; it never grants tool access. Triage's payer and the work turn's payer are distinct: the accepted behavior uses DorkOS credits for triage even with another runtime. **The no-credit/accountless/own-key case is still an explicit product decision**, not permission to invent a paid fallback. Keep all paid test gates intact.

**Bounded acceptance:** deterministic fake-clock and disposable-store cases cover duplicate wakes, restart during triage/turn, revoked work, no-credit refusal/selected behavior, and no repeated escalation. Quiet beats are visible in the action record. Existing runtime refusal must never silently switch payer.

### 3. Prove safe terminal ownership, then use it for agent placement

Continue the existing **DOR-2482** design/laboratory; keep **DOR-2483/2484** startup/retention scopes separate. [Admin restart/reset](../apps/server/src/routes/admin.ts) still starts a successor after cleanup rejects. Root cleanup releases the instance lock without a whole-writer handoff receipt. Doe refuses to close its SQLite when an interrupted owner remains unconfirmed, but the caller must honor that refusal.

**Bounded acceptance:** a refusing Doe-like owner, disposable database and fake delete/lock/spawn ports prove that uncertainty cannot authorize deletion, resource closure or successor execution. One terminal operation wins concurrent requests. Preserve the original startup error through cleanup failure. For later agent moves, specify execution epochs, revoke/acknowledge/transfer and an uncertain old host; prove two fake hosts cannot run the same agent. Closing an SSE stream is not executor fencing.

### 4. Converge workspace domains behind the planned Hono migration

Follow **DOR-2742**, then the accepted **DOR-2743 → DOR-2754 → DOR-2744** dependencies. DOR-2742 is already In Progress with a route-by-route bridge plan in PR #2696. Do not open a competing rewrite. Its middleware-chain, route-census and frozen contract checks protect the framework move. Domain consolidation needs additional evidence for transactions, tenant filtering and post-commit events across both stores.

**Timing discrepancy:** the canonical roadmap and accepted server ADR place convergence after launch. The founder's decision record says to move as soon as possible, and PR #2696 assumes the Hono move starts now while explicitly asking the operator to settle timing and the extension-router bridge. Keep the existing owner planning; do not treat this assessment as approval to change the launch cut or extension author contract. Starting framework preparation and completing server convergence are separate milestones.

First consolidate one command/invariant cohort, such as membership-qualified conversation posting, behind the future shared workspace core. Keep host administration, tenant membership and Owner-only front-door settings distinct. Then migrate a bounded agent-to-agent message path to conversation acceptance plus delivery receipts; preserve crash-after-accept, duplicate and retry behavior before retiring Maildir/subject routing.

**Bounded acceptance:** the same domain cases pass against both persistence implementations; every entry path derives a current actor/tenant; one request runs one middleware chain; one accepted message is visible in the conversation without claiming exactly-once external effects. Historical data and tools have an explicit migration path.

### 5. Make business work and executable packages portable without losing trust

Follow **DOR-2755**, **DOR-2758/2759**, and later execution/drive work in **DOR-2748**. A business project can contain goals, tasks and several repositories; the existing Git project registry remains an execution binding. One plugin manifest should inventory its skills, agents, mini apps, connections and executable components while retaining approval scope, isolation, digest/version and uninstall ownership.

**Bounded acceptance:** deterministic import/update/uninstall cases preserve content ownership and refuse inherited executable approval. Business project IDs survive checkout relocation and do not grant filesystem access. Reuse the shipped marketplace transaction and extension lifecycle instead of replacing them with a parallel installer.

## Sequence and handoff

Before launch, finish the existing audit/trust programme and runtime/onboarding/heartbeat chain, coordinate official-space acceptance and managed-remote delivery, and keep the bounded lifecycle laboratory moving. Hono planning has started; preserve its existing owner's staged plan while the timing discrepancy above is settled. Avoid racing shared composition or authority files.

After launch, preserve the canonical order: Hono/server convergence; actor/access model; programmable APIs; conversation/Relay unification; business projects/goals; agent outside accounts and infrastructure; one plugin/mini-app model; portable execution and project drives; live documents. The ranked risks above explain what must hold during that order, not a replacement launch schedule.

Keep **DOR-2344** as the coordination umbrella and this [roadmap](../plans/architecture-improvement-roadmap.md) as architectural rationale. **Do not fold it entirely into DOR-2742:** audit, proactive work, effect ownership, package trust and recovery span more than the HTTP/server migration. Existing projects and their sessions own implementation. No new broad architecture project or duplicate issue set is needed.

The current diagrams remain source-backed implementation views. The target view is visibly planned. Source, published package, configured runtime, release and live deployment are different evidence levels. Preserve Cloud retirement's full-production-release-without-rollback prerequisite and paid test gates throughout.
