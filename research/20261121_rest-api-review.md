# REST API deep review, November 21, 2026

**Reviewed source:** `8c118b8d7f49f9c47673333e77aa26cf559cdaca`, the tip of `origin/main` on 2026-11-21 (VERSION `0.140.0`). Asked for by the operator in #proj-dork-architecture on 2026-11-21, 19:29 CT, with two questions: how easy is the API to **build** (a server developer adding or changing an endpoint), and how good is it to **consume** (an outside developer, and our own web client). This document answers both, inventories every duplicate it could find, proposes a target shape, and lays out a migration that respects the 20-minor upgrade floor. It builds on the [architecture target design](20261121_architecture-target-design.md) (W7, "one source of truth, many projections", DOR-4973) and on the REST leg that report's lead filed the same evening (DOR-4977, children A1 to A6). Every change is marked **proposed** and the big ones are drafted as ADRs for `/adr:create`; the two questions the report put to the operator were decided by Dorian on 2026-11-21 at 20:50 CT (§8), and everything else stays proposed.

**Method.** Read-only. The OpenAPI document `docs/api/openapi.json` was walked with small scripts for every count below; the route mounts in `apps/server/src/http/hono-api.ts` and the files they reference were read by hand; the capability registry, its three projections and the generic invoke route were read in full; four helper traces (aliases, shapes, the build walkthrough, the cross-cutting census) were checked at the paths they cite. Linear was read on 2026-11-21 (DOR-4966 and its W1 to W7 children; DOR-4977 and its A1 to A6 children; a search of open DOR issues for API, OpenAPI, SDK, GraphQL, pagination, versioning and deprecation). No build, typecheck, test, paid run or deployment was run. **Current** means true at the reviewed commit; **proposed** means this document's suggestion.

## The short answer

**Building it (question 1).** Measured on eight real merges, adding one endpoint touched a median of 10 distinct places and 38.5 files (the largest: 16 places, 68 files). Walked by hand for one realistic read, the documented way costs 21 hand-written files, 2 generated ones, 2 ratchet tests that break and 3 new tests, and three of those places are copies of the same fact: the route handler, the Zod schema in `packages/shared`, a `registerPath` block in an 8,658-line hand-kept registry, the generated document and its 475 generated site pages, a method on a `Transport` interface of more than 500 methods, the matching `HttpTransport` factory, the mock transport, a client hook, and the tests for each. The registry ADR (`260723-050219`) promised one definition that projects everywhere; today that holds for MCP and the CLI and **not for HTTP**: of 475 operations, 21 come from capabilities, and those 21 are documentation pointers to hand-written routes, 15 of them (every projected path that has a parameter) with their path parameters missing from the document, and 9 of them with no route behind them at all. The honest grade is: not DRY, and not intuitive, because the three guides for adding an endpoint describe three different procedures. The target design's W7 is the right fix; this document says what the `http` surface has to carry for it to be real.

**Consuming it (question 2).** An outside developer finds a large, mostly consistent local API with no front door: the document has no `operationId`, no `securitySchemes`, an `info` block that says `0.2.0` and "Claude Code sessions", 49 tags for 56 prefixes, 48 alias groups (15 true duplicates carrying 21 redundant operations, 33 near-duplicates and vocabulary collisions), verbs on 157 paths in six competing spellings, 46 path-parameter names, 18 error body shapes plus "no body" across 1,209 declared error responses, 60 operations with no error response at all, ten pagination styles on the 20% of lists that page, 273 served operations (37.8% of what the server answers) that are not in the document, the RPC endpoint the CLI rides and the global event stream among them, and 9 documented paths that no route serves. The event streams that carry most of the app's state have a careful prose contract (`docs/integrations/sse-protocol.mdx`, the one place in the repo that promises any API stability) and no machine-readable one. Inside one resource the API is usually good: Zod-typed bodies, camelCase, ISO timestamps, sensible status codes. Across resources it is a federation of 56 small APIs that grew one PR at a time.

**The top five changes (proposed).**

1. **Make the capability the one definition of an HTTP operation** (W7, A1): the `http` surface grows path parameters, responses (including errors), pagination and visibility, a generic mount serves it, and the hand-kept registry shrinks to overrides and then disappears. One `defineCapability` yields the route, the OpenAPI entry, the MCP tool, the CLI verb and the generated client method.
2. **One error contract** (A2): an RFC 9457 `Problem` with a stable code list, aligned field for field with `packages/cloud-api`'s `ProblemSchema`, sent by one helper, declared on every operation.
3. **Publish the contract** (A3, A1 census): `operationId` on every operation, `securitySchemes` for the cookie, the API key and the agent header, `info.version` from `VERSION`, every mounted group in the document or allowlisted with a reason, the invoke endpoint and the event streams documented; then a generated TypeScript client the web client uses (A4).
4. **Normalise resources under a stability policy** (A5 under A6): one path per action, one parameter name per resource, nouns for collections, cursor pagination on every list, each alias deprecated with a `Sunset` date before it goes.
5. **A typed event contract**: one event vocabulary in `packages/shared`, `seq` and replay on every stream that carries state, documented beside the REST paths, and a 202 pattern that names the event a caller waits for.

### 2.3 Is it DRY? Is it intuitive? (current)

What is already DRY, and worth keeping: one Zod schema in `packages/shared` feeds server validation, the TypeScript types and, through a registration, the document; one `defineCapability` feeds both MCP servers, the catalog, the CLI, the tier and permission gate and Activity; the route census is a self-updating ratchet (`census:update`), not a hand list (the mount count beside it is a hand-bumped literal).

What is repeated by hand:

- **Wiring a route group is four places** (the route file, three edits in `hono-api.ts`, a startup step) plus two ratchets.
- **One client method is seven places** before a hook (the shared slice, `transport-slices.ts`, the `package.json` export, the `*-methods.ts`, two edits in `http-transport.ts`, the mock slice).
- **One MCP tool is three hard-coded counts and two census tables** in five directories, plus the optional skill text and docs that name tools.
- **Response shapes are mirrored** where a domain's OpenAPI file declares its own: `services/core/config/backups-openapi.ts:22-41` (Zod) and `packages/shared/src/transport-backups.ts:14-37` (a TypeScript interface) describe the same object, with a comment to "change both together".
- **OpenAPI registration has three coexisting styles** (inline in `openapi-registry.ts`; a domain file called from `openapi/domains.ts`; a domain file called directly at `openapi-registry.ts:8638`) plus the capability projection, and `contributing/api-reference.md`'s endpoint sections are a fourth, prose copy.
- **Visibility is re-derived per route**: "owner or this agent" is written three ways in three route files.

The three guides disagree with each other and with the code:

- `contributing/api-reference.md` ("How Schemas Work", line 12, and "Adding a New Endpoint", lines 27-42): define schemas in one of "three schema files" (`packages/shared` exports 161 subpaths now), register the path in `openapi-registry.ts` by hand, regenerate twice. It does not mention capabilities.

## 3. Consuming the API (question 2)

### 3.1 Does it make sense as a whole? (current)

Read top-down, the document is 56 prefixes under 49 tags. The seams show where the product's language moved and the API did not:

- **Agents** live under `/api/agents` (20 paths), `/api/team` (2), `/api/profile` (4), `/api/mesh` (7), `/api/discovery` and `/api/agents/create`; tags `Agent`, `Agents`, `Team`, `Profile`, `Mesh`.
- **Connections** (the product noun since ADR `260804-021140`) live under `/api/connectors` (50 paths) and `/api/community-connections` (4); tags `Connectors`, `Connections`, `Access`.
- **Chats** (the product noun) live under `/api/sessions` (31), `/api/session-relay` (12), `/api/session-locations` (2), `/api/direct-chats` (2) and `/api/sessions/running`; the document's `info` still says "sessions".
- **Spaces** (the product noun since ADR `261018-124422`) live under `/api/communities` and `/api/community-connections`, by that ADR's own D5 (wire names stay `community`); the document does not say so.
- **The same thing twice**: `GET /api/capabilities` is the per-runtime feature matrix (`routes/capabilities.ts:1-9`) and `GET /api/capabilities/catalog` is the registry catalog; nothing in the document tells them apart.

### 3.8 Auth, as the API presents it (current)

The mechanism is careful and the document says nothing about it. Every request runs one chain (`http/api-chain.ts:10-25` numbers 13 steps in its own table; the gates mounted inside them, read in order at `:131-251`, are): terminal admission, the managed-host guard, the Remote Access switch, the service-worker guard, CORS over one origin policy, `nosniff`, the `/api` host guard (a DNS-rebinding defence that is inert once login is on), the Wi-Fi level, Better Auth and the signed webhook ingress, body parsing, the `/mcp` bad-key throttle, **the session gate**, agent identity, the person-session refusal, the audit actor and the audit fallback. The gate classifies each request (`lib/request-classifier.ts`: `this-computer`, `other-device`, `relayed`, `hub`, `agent-computer`) and decides `open`, `credential`, `agent` (a local agent computer) or `refused` (`services/core/auth/gate-policy.ts:74-87`). Two credentials pass it: the Better Auth session cookie, valid only on the route it was minted on, and a per-user API key as `Authorization: Bearer` (`services/core/auth/session-gate.ts:261-300`). A refusal is `401 { error: 'Unauthorized', code: 'AUTH_REQUIRED', signInWith? }`.

### 3.10 Long-running work, 202, idempotency, discoverability, SDK, contract tests (current)

**202 means two things.** Seventeen operations answer `202`. Six are trigger-only, with the result riding a stream: `POST /api/sessions/{id}/messages` answers `{ sessionId, messageId, outcome, queuePosition }` and the turn arrives as `turn_start … turn_end` on the chat stream, with the same `outcome` on `queue_update` so a client can match its own send (`routes/sessions.ts:823-891`, `routes/session-message-receipt.ts:5-15`); room entries, reactions, threads, command intents and UI actions work the same way. Eight are "a person must approve": `POST /api/marketplace/packages/{name}/install`, `/marketplace/updates`, `/held-back/{name}/review`, `/dev-links`, `POST /api/agents/create`, `POST /api/connectors/executions` (whose `202` body is `{}`), `…/cli/executions`, and the capability invoke route's `approval_required`. Three are "accepted, look elsewhere" (`POST /api/sessions/{id}/continue`, `POST /api/local-browser/sign-in/done`, a `PATCH /api/sessions/{id}` whose permission change waits for the next turn). The `428` family (98 responses) is a fourth asynchronous shape: a held action the person finishes at `/api/step-up/{heldActionId}/*`. Nothing in the document says which `202` is which.

**Idempotency.** An `Idempotency-Key` header is read by two routes, both attachment uploads; five operations take an `idempotencyKey` field in the body. PUT is used for whole-value settings (28 operations); creations and triggers are POST (222). Message sends and room posts mint a new id on every call. Destructive capability calls are made retry-safe by the approval token: the approval binds to a SHA-256 of the exact input, is single-use and expires, and the retry presents it as `X-DorkOS-Approval` (`services/core/capabilities/approval-required-payload.ts:6-36`, `services/core/approvals/approval-input-hash.ts:1-28`), which is a stronger form of intent binding than an idempotency key. Ungated POSTs have nothing equivalent.

**Discoverability.** `/api/docs` (Scalar) and `/api/openapi.json` on every install; 475 generated MDX pages plus a 22-line landing page under `docs/api/`; `docs/integrations/sse-protocol.mdx`, `building-integrations.mdx`, `mcp-server.mdx`, `docs/guides/a2a-integration.mdx`, `cli-usage.mdx` for outsiders; `contributing/api-reference.md` (1,767 lines, hand-kept, partly stale: it still documents `POST /api/agents` at line 500, an operation the document does not have) for contributors. `GET /api/capabilities/catalog` is the live self-description agents use and the only place the invoke contract is described. No page says what is stable.

**SDK and clients.** No generated client anywhere (no `openapi-typescript`, `openapi-fetch`, `orval` or `@hey-api` dependency). The web client's contract is the hand-written `Transport` (§1) implemented by 54 `HttpTransport` factories; `docs/integrations/building-integrations.mdx:178-210` tells outsiders to implement `Transport` over `fetch()` by hand. The CLI has its own `api-client.ts`; the e2e suite and the scripts have their own calls; the Cloud side has the thin typed client in `packages/cloud-api/src/client.ts`, which is the shape the local API lacks.

**Contract tests.** `openapi-fresh` (required) regenerates the document and the pages and fails on drift. The route census pins the 793 `METHOD /path` entries the real server answers against a committed baseline (`http/route-census/census.ts`, `http/__tests__/route-census.test.ts`), so adding or removing a route is a visible diff. 27 `*.contract.test.ts` files under `http/__tests__/contract/` and the `api-chain-matrix` snapshot pin the chain's answers cell by cell. The runtime and capability conformance suites pin MCP parity, tiers and descriptions. ## 4. The target shape (proposed)

Everything in this section is proposed. It keeps what already holds: Hono with one chain (ADR `261009-192542`), the capability registry as the unit of agent action (ADR `260723-050219`), approvals bound to the exact action shown (ADR `260725-133221`), runtime-owned transcripts (ADR-0310), the frozen outside names for spaces (ADR `261018-124422` D5), and the public contract pattern `packages/cloud-api` already uses on the other side of the wire.

### 4.1 Principles

1. **One definition per operation.** A capability is the only way to declare something the API does. Its `http` surface is complete enough to **serve** the route, not only to describe it. The hand-kept registry becomes an override file for the few shapes a capability cannot express, and then nothing.
2. **Three projections of one thing, named plainly.** REST paths are the resource projection; `POST /api/capabilities/{id}/invoke` is the RPC projection; MCP tools and `dorkos call` are the agent projection. A caller may use any; all three run `registry.invoke`, so the tier gate, the permission area, the audit record and the approval binding are the same. This is the capability-first promise **Dorian decided on 2026-11-21** (§8): both the REST paths and the invoke endpoint are documented projections.
3. **One error, one page, one stream shape.** Every failure is a `Problem`; every list pages by cursor; every event stream carries the same envelope with a `seq`.
4. **The document is the contract.** `operationId`, `securitySchemes`, `x-stability`, declared errors, declared streams; a census fails when a mounted route is not in it; a generated client is built from it and used by the web client, so drift is a compile error.
5. **Change with notice.** Nothing stable goes away without `deprecated: true`, a `Sunset` header and a changelog line, for a window a person outside the repo can plan around.

### 4.3 Naming rules (proposed)

- Plural nouns for collections; `{resourceId}` named for its resource (`{agentId}`, `{chatId}`, `{roomId}`); never a bare `{id}` on a nested path.
- Verbs only as sub-resources of a thing that cannot be a plain update: `POST /api/agents/{agentId}/pause` stays; `POST /x/{id}/remove` becomes `DELETE /x/{id}`; `POST /x/create` becomes `POST /x`.
- Kebab-case path segments, camelCase query and body fields, `UPPER_SNAKE` codes.
- Filters as query parameters with one spelling each: `q` for free text, `state` for lifecycle, `kind` for subtype, `since`/`until` for time, `limit`/`cursor` for paging.
- Timestamps as ISO 8601 strings with `format: date-time`; durations in milliseconds with an `Ms` suffix; ids opaque strings.
- `201` with the created body; `204` for a delete with nothing to say; `202` only with a correlation id and the event name that completes it.

### 4.4 One error contract (proposed)

```json
{
  "type": "https://dorkos.ai/problems/not-found",
  "title": "Not found",
  "status": 404,
  "detail": "No agent with that id.",
  "code": "not_found",
  "instance": "req_01HX…",
  "retryAfterMs": 1500
}
```

`application/problem+json`, RFC 9457. The fields and the code list are the ones `packages/cloud-api/src/problem.ts:32-78,103-156` already publishes for the Cloud side (`code`, `status`, `title`, `detail`, `instance`, `retryAfterMs`, and its optional extensions), plus RFC 9457's `type`, which the Cloud shape leaves out and the local one adds, so one client parses both. Local-only codes (`SESSION_LOCKED`, `RUNTIME_NOT_AVAILABLE`, `UNKNOWN_CAPABILITY`, the approval refusals) join one list in `packages/shared`, lower-snake like the Cloud ones, with the old spellings accepted on the way in for one window. Validation failures carry `issues` (Zod's flattened form) as an extension. The capability gate's `approval_required` payload stays a **202 body**, not an error; its refusal becomes a `Problem` with `code: forbidden` and the gate's wording in `detail`. The space server's `{ code, message }` (target design S2) converges on the same shape through `packages/http-kit`, the shared HTTP kit the target design proposes and DOR-4954 would build (it does not exist yet).

### 4.5 Pagination (proposed)

Every list operation takes `limit` (default and maximum declared in the schema) and `cursor` (opaque), and answers `{ items: T[], nextCursor: string | null }`. Nothing else: no `offset`, no `page`, no `before`/`after` seq pairs except on event streams, where `seq` is the cursor. A list that cannot page (a small fixed set such as models or runtimes) declares `x-unbounded: true` with a reason, and a census test keeps that list short.

### 4.6 Auth in the document (proposed)

`components.securitySchemes`: `sessionCookie` (the Better Auth cookie the app uses when login is on), `apiKey` (`Authorization: Bearer`, the personal key the CLI already presents, `packages/cli/src/lib/api-client.ts:9-26`), `agentIdentity` (`X-DorkOS-Agent`, additive, never a key), `instanceToken` for `/mcp`. Every operation lists which apply; an owner-only operation says so in a one-line `x-audience: owner | person | agent | any`, read from the capability's area and tier, so the public pages can say who may call it. The docs landing page (`docs/api/index.mdx:16-18`) gains the two paragraphs it is missing: how to mint a key and which header carries it.

### 4.7 The event contract (proposed)

One `DorkOsEvent` envelope in `packages/shared`: `{ seq, at, type, payload }` with `type` from one union that every stream shares, documented in the same OpenAPI document as `text/event-stream` responses whose schema is the union (OpenAPI 3.1 allows it; an AsyncAPI document can be generated from the same union later). Every stream that carries state supports `Last-Event-ID` replay from a bounded buffer, as `GET /api/sessions/{id}/events` does today. The prose contract in `docs/integrations/sse-protocol.mdx` stays the human page and is generated, section by section, from the same union where it lists event names. The per-domain streams that duplicate `/api/events` are deprecated under §4.9.

### 4.8 Long-running work (proposed)

`202 Accepted` always answers with `{ operationId, event }`: the id to correlate and the event `type` on `/api/events` or the chat stream that reports the outcome. `POST /api/sessions/{id}/messages` already behaves this way in substance; the document should say so. Writes that may be retried declare `idempotent: true` in the capability and accept `Idempotency-Key`; the approval token already binds a destructive retry to its exact input (`tier-enforcement.ts`), which is the stronger form of the same idea.

### 4.9 Stability and deprecation (proposed)

- Every operation carries `x-stability: stable | preview | internal`. `internal` operations (test control, the extension host's own bridge, admin) are served but left out of the published document and the site; `preview` ones are published with a banner.
- A stable operation changes only additively. To remove or rename one: mark it `deprecated: true` in the capability (which projects to the document, the MCP annotation and the CLI help), send `Deprecation: true` and `Sunset: <date>` headers on every answer (RFC 8594), write the changelog line, and remove it only after the sunset.
- **The window.** The upgrade floor is 20 minors, which at today's cadence is about five weeks (§1). That is too short for a person who wrote a script against the API. **Decided by Dorian on 2026-11-21:** the sunset is **the later of 20 minors and 90 days** from the release that marked it deprecated; the `@deprecated since 0.x, remove in 0.y` lint rule computes `0.y` from the same rule (§8).
- `info.version` is `VERSION`; the document carries `x-contract-revision`, a counter bumped only when a stable operation changes, so a client can tell "new build" from "new contract".
- No `/v1` prefix on the local API. The Cloud contract uses `/v1` because it has many servers and clients at different versions; the local API has one server per install and a document that names its own version, so a prefix would only double every path for the window. If the day comes that a breaking change cannot be staged, `/api/v2` is still available.

### 4.10 Generated client and SDK (proposed)

A `packages/api-client` generated from the document (A4) with one method per `operationId`, the `Problem` type as the error, and the event union for streams. `HttpTransport`'s 54 factories become one adapter over it, slice by slice; `Transport` itself splits into domain slices (DOR-4932). The CLI's `api-client.ts` and the e2e helpers use the same package, so no second hand-written client exists in the repo. Publishing it to npm is a later, separate decision; the first value is inside the repo.

### 4.11 Capability-first authoring: what one definition must carry (proposed)

For principle 1 to be true, `CapabilitySurfaces.http` grows from two fields to a route description:

```ts
http: {
  method: 'get',
  path: '/api/agents/{agentId}/chats',
  params: { agentId: 'agentId' },        // path segment → input field
  query: ['limit', 'cursor', 'state'],    // input fields read from the query (GET)
  success: 200,                           // 200 | 201 | 202 | 204
  errors: ['not_found', 'forbidden'],     // Problem codes this operation can answer
  page: { items: 'items', cursor: 'nextCursor' },
  stability: 'stable',
  audience: 'any',
  idempotent: true,
}
```

A generic mount (`routes/capability-http.ts`, proposed) registers one Hono handler per capability with an `http` surface: it merges path, query and body into the input, calls `registry.invoke` with the request facts exactly as `routes/agent-pause.ts:55-84` does today, and answers with the result, a `Problem`, or the 202 approval payload. The projection registers path parameters, the declared errors and the page shape. The hand route for that path is deleted in the same change, and the composition throws if both exist (it already throws on a document collision, `openapi-projection.ts:86-92`). Visibility rules (the owner reads everything, an agent reads its own) are expressed once, as the capability's `area` and a `visibleTo` predicate the registry runs before `invoke`, which is also what W4 needs.

### 4.12 Contract tests and censuses (proposed)

- **Mounted means documented**: a test joins the route census the server already serves (`http/route-census/census.ts`, 793 entries in its committed baseline) with the operations in the document, and fails on a served route absent from the document unless it is `internal`. The census half exists; only the join is new. **This is now DOR-4996**, the API lint gate the guardrails lead filed on 2026-11-22 at Dorian's direction: one ratchet script in the `own-mocks` shape (`scripts/check-api-lint.ts`, a baseline that may only fall, per rule per route group) covering `operationId`, verb segments, one parameter name per resource, the shared error schema on every 4xx/5xx, cursor paging on list operations, the served-equals-documented join in both directions, and a `registerPath` count per hand file that may only fall. It rides `typecheck` with a CI ledger entry. The ESLint rule that new routes go through the capability helper waits for the generic mount (§4.11); the hand-registry ratchet is the stand-in. Dorian's order for the whole theme: guardrails first (DOR-4996), then the work graph (W1 to W4), then the migration of old routes area by area (DOR-4978, DOR-4982).
- **Documented means served**: a test starts the app with the test runtime and sends one request per operation in the document, asserting the status is not 404 and the error body, when any, is a `Problem`.
- **One id each**: no duplicate `operationId`; every stable operation has `x-stability`; every `deprecated` operation has a sunset.
- **Client parity**: the generated client compiles against the document in the build; `openapi-fresh` already fails on drift.

## 6. Proposed ADR drafts (not decisions)

### ADR draft A: the HTTP API is a projection of capabilities (amends `260723-050219`, feeds DOR-4973)

_Context._ The registry ADR promised that one `defineCapability` yields every agent-facing surface. For HTTP it yields a document entry only, and only when a hand route also exists; 390 of 475 operations are hand-documented, 15 of the 21 projected entries omit their path parameters, and 9 of them document paths no route serves. Three authoring paths coexist and the guides describe each as the only one.
_Decision._ We will make the capability the single definition of an HTTP operation (capability-first, **decided by Dorian 2026-11-21**: the REST paths and the invoke endpoint are both documented projections): the `http` surface carries path parameters, query fields, the success code, the error codes, the page shape, stability and audience; one generic mount serves every such surface through `registry.invoke`; the document, the MCP tool, the CLI verb and the generated client are projected from the same declaration; the hand-kept registry accepts no new paths and shrinks to zero domain by domain; a census fails when a mounted route is not projected (DOR-4996 is that census, as a ratchet, until the mount lands).
_Consequences._ Adding an endpoint is one definition plus tests; MCP, HTTP, CLI and the client agree by construction; routes that need a request shape a capability cannot express (multipart uploads, raw file bodies, the streams) are declared `internal` or `stream` on the surface and served by the few hand routes that remain, listed in one allowlist.

### ADR draft B: one error contract for every DorkOS HTTP surface (feeds DOR-4979)

_Context._ The local API answers failures in many shapes; the Cloud contract answers in one (`Problem`), and the space server in a third. A client writes three failure paths and an outside developer guesses.
_Decision._ We will answer every failure on every DorkOS-served HTTP surface (the app's API, the space server, the extension bridge's own errors) with RFC 9457 `application/problem+json`, with the field set and the code list shared with `packages/cloud-api`, sent only through the shared HTTP kit the target design proposes (`packages/http-kit`, DOR-4954); old shapes are accepted by the client for the deprecation window and never sent by new or touched routes.
_Consequences._ One parser in the client, the CLI and the SDK; a lint keeps `c.json({ error })` out of route files; codes become a published list with their own deprecation notes.

### ADR draft C: API stability and deprecation tied to the upgrade floor (feeds DOR-4983)

_Context._ DorkOS promises upgrades from 20 minors back and says nothing about its HTTP and event contracts; at today's cadence 20 minors is five weeks; nothing in the API is marked stable, preview or internal, and nothing has ever been deprecated with notice.
_Decision._ We will mark every operation `stable`, `preview` or `internal`; publish only the first two; change stable operations additively; deprecate with `deprecated: true`, `Deprecation` and `Sunset` headers and a changelog line; remove no sooner than the later of 20 minors and 90 days (**decided by Dorian 2026-11-21**, §8); and keep `info.version` equal to `VERSION`.
_Consequences._ Outside callers can plan; the `@deprecated since 0.x, remove in 0.y` rule gains a formula for `0.y`; the internal and test routes stop appearing to be promises.

### ADR draft D: one event contract (feeds DOR-4973's stream projection)

_Context._ Most of the app's state arrives over event streams whose envelopes and names are defined per stream and described nowhere a machine can read.
_Decision._ We will define one event envelope and one event-type union in `packages/shared`, project them into the OpenAPI document as the schema of every `text/event-stream` response, give every stateful stream `seq` and `Last-Event-ID` replay, and answer `202` only with the event that completes the work.
_Consequences._ A generated client gets typed events; per-domain streams that duplicate `/api/events` are deprecated under ADR C; GraphQL subscriptions, if they ever arrive, project from the same union.

## 8. Decisions for the operator (both decided 2026-11-21)

Fewer moving parts in the document, but the 390 hand entries stay hand entries and the W7 ADR's "never hand-built" cannot be kept. Recorded on DOR-4978 and DOR-4973.
