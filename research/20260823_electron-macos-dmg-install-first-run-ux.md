## Research Summary

DMG-with-drag-to-Applications is the near-universal distribution format for signed/notarized Mac apps in 2024–2026 (Slack, Discord, Chrome, VS Code, Cursor, Claude Desktop, Arc, Raycast, Linear all use it); none of them auto-move themselves via Electron's `app.moveToApplicationsFolder()` — that API exists, is well-documented, and is modeled directly on the older LetsMove/PFMoveApplication pattern, but adoption among major Electron apps is low and even opt-in users (Figma) report it misfiring. The mechanics of _why_ running from a DMG or `~/Downloads` breaks auto-update are well documented in Electron and Squirrel.Mac issue trackers: App Translocation puts the running bundle on a randomized, read-only mount, and Squirrel.Mac literally cannot `rename()` a new bundle into place there. Separately, Squirrel.Mac's own `rename()`-based install step can itself re-trigger translocation after a successful update — a second, distinct failure mode. On manual replacement while running, Unix inode semantics mean the old process keeps running fine from unlinked file handles, but Electron's `requestSingleInstanceLock()` means a second launch attempt just refocuses the _old_ still-running process rather than starting the new bundle — this is a confirmed, reported Electron behavior, not a hypothetical. On the staleness question: electron-builder's `DownloadedUpdateHelper` validates a cached/pending update by checksum and metadata equality only — it contains **no version-vs-running-app comparison** — and Squirrel.Mac's native staging (ShipIt) applies whatever is staged on next quit with no re-check of what's currently on disk, confirming that a stale staged update genuinely can downgrade an app that was manually overwritten with a newer version in the interim. electron-builder's DMG cosmetics (`background`, `contents`, `window`, `iconSize`) are well-specified, and electron-builder already defaults to putting `background.tiff`/`.png` inside a hidden `.background/` subfolder (not bare at the volume root) alongside `.VolumeIcon.icns` and `.fseventsd/` — matching the "hidden folder" convention the task asked about confirming, though a documented electron-builder bug means user-visible hidden-file toggling (Cmd+Shift+.) can still expose and disturb this layout.

## Key Findings

1. **DMG + drag-to-Applications is the standard, not the exception.** Every consumer-facing Mac app checked (Slack, Discord, Chrome, VS Code, Cursor, Claude Desktop, Arc, Raycast, Linear) ships a `.dmg` with a Finder window prompting the user to drag the app icon onto an `/Applications` alias. 1Password is the interesting split case: `.dmg` for individual/consumer downloads, but a separate `.pkg` specifically for MDM/enterprise fleet deployment (PKG lets a management tool escalate privileges and script the install; DMG deliberately requires the human drag gesture). No major consumer Electron/native app auto-moves itself into `/Applications` on first launch by default.

2. **`app.moveToApplicationsFolder()` is real, documented, and modeled on LetsMove — but rarely used by name-brand apps.** It throws no dialog by default (you must build your own with the `dialog` API), it quits and relaunches the app on success, and it ships a `conflictHandler` callback with two conflict types: `'exists'` (same-named app present, not running — default behavior trashes it) and `'existsAndRunning'` (default behavior focuses the running instance and quits the mover). Figma is one of the few examples found in the wild, and it has a documented history of prompting to move even when the app is already correctly placed — a known pitfall of self-detection logic, not the API itself.

3. **LetsMove (PFMoveApplication) is the original C/Objective-C pattern Electron's API is modeled on.** It moves the app if it isn't in _any_ `Applications` directory (user or system) or if it's nested inside another bundle — DMG-mounted and `~/Downloads` are both covered by that same "not properly installed" check, not special-cased separately. It shows a real alert dialog ("Move to Applications folder?"), strips the quarantine xattr after moving (to avoid a second Gatekeeper prompt), and falls back to `AuthorizationExecuteWithPrivileges()` for privileged copies when `/Applications` isn't user-writable. It explicitly does not work in sandboxed apps.

4. **Running from a mounted DMG or `~/Downloads` breaks auto-update for two independent, well-documented reasons.** (a) A DMG volume is inherently read-only — Squirrel.Mac/electron-updater's own error text is literally "Cannot update while running on a read-only volume. Please move the application and try again." (b) Even from `~/Downloads` off a real (writable) volume, unsigned/newly-downloaded apps get **App Translocation** (Gatekeeper path randomization): macOS mounts the bundle from a hidden, randomized, read-only DMG-like path, so the app's own `.app` location is neither where the user thinks it is nor writable — Squirrel.Mac cannot `rename()` a replacement bundle into that path at all.

5. **Electron ships `app.isInApplicationsFolder()` specifically to detect this class of failure**, and its absence from an app's startup logic is a confirmed, reported root cause of silent auto-update failure (electron/electron#41508: "Auto-updates not working on MacOS if app is not installed in Applications directory").

6. **Translocation can also happen _after_ a successful update**, a second, separate bug class: Squirrel.Mac's install step uses `rename(2)` to swap the bundle into `/Applications`, and that `rename()` call can itself cause the _next_ launch to be translocated even though the app was originally installed correctly (Squirrel/Squirrel.Mac#252). This is a known Squirrel.Mac limitation, not something DorkOS's app code causes — mitigation is detection + user messaging ("please reinstall from a fresh download"), not a code fix inside the app.

7. **Manually overwriting a running app is functionally safe but semantically confusing, due to Unix inode/lock semantics.** Finder's replace-while-running (drag new build over old, "Move to Trash" + copy) works at the filesystem level because Unix keeps open file descriptors valid against unlinked inodes — the running process keeps working normally on its already-open resources. The confusing part is Electron's `requestSingleInstanceLock()`: a second launch attempt (double-click, Dock, Spotlight) while the old process is still alive does **not** start the new bundle — it just triggers the `second-instance` event on the still-running old process, which typically just focuses its window. Electron's own issue tracker confirms this exact failure mode when different versions of the same app collide on the lock (electron/electron#30219, #35680). The only way to actually get the new bundle running is to fully quit the old process first (or the app has to detect and self-terminate).

8. **No major Electron app was found that detects "the bundle on disk is newer than my in-memory version" for an _out-of-band_ manual replacement** (as opposed to their own auto-updater's download-then-restart flow). Slack, VS Code, etc. all have "an update is ready, restart to apply" prompts — but those are for updates _they themselves_ downloaded and staged, not for detecting a third party having silently swapped the bundle on disk. This appears to be a genuine gap/edge case handled by convention (quit-and-relaunch naturally loads the new bundle) rather than by explicit detection code in any researched app.

9. **electron-updater's own pending-update cache validation is checksum/metadata-only, not version-aware.** `DownloadedUpdateHelper` (electron-builder source) validates a cached/staged update purely by SHA512 checksum and deep-equality of cached metadata against freshly-fetched update info; it clears the cache if the file is missing, the checksum mismatches, or `update-info.json` is corrupt — but it contains **no logic comparing the staged version against the currently-running app version**. Squirrel.Mac's native macOS staging path (ShipIt, invoked via `quitAndInstall()`) is documented in electron-builder's own code comments to "stage the update and apply it on relaunch after quit" with no re-check of what's on disk. This confirms the downgrade risk described in the task is real, not theoretical: if a user is auto-offered v1.2 while running v1.2, ignores it, manually installs v1.3 by hand, and the staged v1.2 update is still sitting in the pending cache, quitting can hand v1.3's on-disk bundle to a stale v1.2 installer.

10. **electron-builder's DMG cosmetics options are fully specified** — `dmg.background` (image path, default `build/background.tiff` or `build/background.png`), `dmg.backgroundColor` (fallback solid color, default `#ffffff`), `dmg.window` (`x`/`y`/`width`/`height`, y running bottom-to-top), `dmg.contents` (array of `{x, y, type, path}` items — `type: 'file'` for the app, `type: 'link'` with `path: '/Applications'` for the shortcut), and `dmg.iconSize` (default `80`). Standard background dimensions are 540×380 (1x) with a 1080×760 `@2x` variant recommended for Retina, per electron-builder's own icons documentation.

11. **electron-builder already puts DMG cosmetics in a hidden `.background/` subfolder by default, along with `.VolumeIcon.icns` and `.fseventsd/`** — matching (not contradicting) the "cleaner convention" the task asked about confirming. These are genuinely hidden (dotfile-prefixed) and only become visible in Finder when the user toggles hidden files (Cmd+Shift+.). There is a known, still-open electron-builder bug (#1160) where positioning these hidden items via `dmg.contents` works for `.VolumeIcon.icns` but not reliably for the `.background/` folder itself, so a user who has "show hidden files" on by default may see it awkwardly placed inside the DMG window.

### 2. `app.moveToApplicationsFolder()` — API contract, pitfalls, and lineage

**API contract** (from Electron's own docs, `docs/api/app.md`):

- Signature: `app.moveToApplicationsFolder([options])` → returns `boolean`.
- **No confirmation dialog by default.** If you want the user to confirm, you build it yourself with the `dialog` API — Electron gives you the mechanism, not the UX.
- **Relaunches on success.** "If the move is successful, your application will quit and relaunch." This means it must be called early (e.g., before creating windows) or you accept a full relaunch mid-session.
- **Conflict handling**: an optional `conflictHandler(conflictType)` callback, where `conflictType` is `'exists'` (same-named app present at destination, not running) or `'existsAndRunning'` (present and running). Returning `true` (or omitting the handler) applies the default: trash the existing app if not running; if running, that running instance takes focus and the mover quits itself instead. Returning `false` aborts the move.
- **Failure semantics**: returns `false` if the user cancels an authorization prompt; throws for any other failure. macOS-only.

**Pitfalls found in the wild:**

- Figma is one of the only mainstream apps observed using self-move logic, and its own community forum has reports of it prompting to move even when already correctly installed at `/Applications` — a self-detection bug, illustrating that the detection half (deciding _when_ to offer the move) is the fragile part, not the move mechanic itself.
- The API is a relatively late (electron/electron#10142, with conflict-handling added later in #18916) addition and mirrors LetsMove's shape closely enough that the conflict semantics (`exists` / `existsAndRunning`) read as a near-direct port of LetsMove's own "already there and running vs. not running" branch.

**LetsMove / PFMoveApplication (the pattern it's modeled on):**

- Written by Andy Kim (Potion Factory), public-domain, Objective-C. Call `PFMoveToApplicationsFolderIfNecessary()` at the very top of `applicationWillFinishLaunching:`.
- **Trigger condition is broad, not DMG-specific**: it checks whether the app is in _any_ Applications directory (`NSApplicationDirectory`, checked across all domains — user `~/Applications` and system `/Applications`) — if not, or if it's nested inside another app bundle, it offers to move. Whether that "not in Applications" location happens to be a mounted DMG or `~/Downloads` is incidental to the same check (disk-image detection uses `ContainingDiskImageDevice()` specifically to phrase the dialog copy — e.g., mentioning "uncluttering your Downloads folder" — but the underlying trigger is the same "not in Applications" test either way).
- **Dialog shown**: title varies ("Move to Applications folder?" vs. "...in your Home folder?" depending on whether `~/Applications` exists), body explains the app can move itself, buttons are "Move to Applications Folder" / "Do Not Move" (Escape = don't move), plus a "don't ask again" checkbox. If the destination isn't user-writable, the copy explicitly warns an admin password will be required.
- **Relaunch**: yes, waits for the original process to fully exit before launching the moved copy (`Relaunch()`).
- **Existing app at destination**: if running, focuses it and exits the mover; otherwise trashes the old copy first.
- **Gatekeeper/Translocation interaction**: strips the `com.apple.quarantine` extended attribute post-move specifically to avoid a second "are you sure you want to open this" Gatekeeper dialog; uses an AppleScript fallback for trashing the old copy in App-Translocation scenarios (documented as needed as of Sierra); uses the deprecated `AuthorizationExecuteWithPrivileges()` when a privileged copy is required. It's explicitly documented as **not working inside sandboxed apps**.

**When do these patterns actually trigger?** Both Electron's API and LetsMove trigger on "not currently in an Applications directory" as the single, general condition — mounted-DMG and `~/Downloads` are just the two most common ways an app ends up not-in-Applications; there's no separate "am I on a DMG volume" special case distinct from "am I in `/Applications`."

### 3. Why running from a mounted DMG or `~/Downloads` is actively harmful

Two distinct, independently-documented failure mechanisms converge here:

**(a) The DMG volume is genuinely read-only.** electron-builder/electron-updater's own error text, verbatim from real bug reports, is: _"Cannot update while running on a read-only volume. Please move the application and try again."_ If the running app's install target is a mounted `.dmg`, there is no filesystem write path for Squirrel.Mac to install anything, full stop.

**(b) App Translocation makes even `~/Downloads` non-writable and the path unpredictable**, independent of any DMG. This is macOS's "Gatekeeper path randomization" (macOS 10.12+): when the OS sees an app bundle carrying the `com.apple.quarantine` extended attribute (i.e., downloaded from the internet and not yet moved), double-clicking it causes the OS to mount a hidden, randomized, **read-only** disk image containing just that bundle and run it from there — not from the path the user sees in Finder. The translocated path looks like `/private/var/folders/.../AppTranslocation/<random-uuid>/d/YourApp.app`. Squirrel.Mac cannot `rename()` a new bundle into a read-only, randomly-relocated mount — there's no stable, writable path to install into. **The fix that clears translocation is simply moving the bundle** (e.g., to `/Applications`) — the act of moving clears the state that triggered translocation in the first place; deleting the quarantine xattr directly (`xattr -d com.apple.quarantine`) also prevents it from ever triggering.

Given this, **detecting "app is not in `/Applications`" is the single highest-leverage guardrail** for a signed, auto-updating Electron app: `app.isInApplicationsFolder()` exists in Electron precisely for this. Its absence from an app's startup path is a confirmed, reported root cause of silent 100%-failure auto-update (electron/electron#41508, "Auto-updates not working on MacOS if app is not installed in Applications directory") — exactly the class of bug that produced the 10-day silent auto-update failure referenced in the task. The mitigation pattern industry apps converge on: check `isInApplicationsFolder()` at launch; if false, either offer `moveToApplicationsFolder()` with a confirmation dialog, or at minimum surface an in-app banner/warning that auto-updates will not work until the app is moved.

**A second, separate translocation failure mode exists even for correctly-installed apps**: Squirrel/Squirrel.Mac#252 documents that Squirrel.Mac's own install mechanism can cause **re-translocation after a successful update**, because its bundle-swap uses `rename(2)`, and that syscall's interaction with the quarantine/translocation subsystem can leave the _next_ launch translocated even though the app was originally installed at `/Applications` and had never been translocated before. This is a Squirrel.Mac-level limitation, not something app code introduces, and there is no clean code-level fix documented — mitigation is detection (same `isInApplicationsFolder()` check, run on every launch, not just first launch) plus user messaging to reinstall from a fresh DMG if it recurs.

### 4. Manually replacing a running app in `/Applications`

**Finder behavior**: dragging a new `.app` onto the old one (or into the same folder with the same name) while the old process is running is generally allowed by Finder — it will trash/replace the old bundle and copy the new one in, without requiring the running process to quit first. This is standard Unix filesystem behavior: the directory entry (the name `/Applications/YourApp.app`) and the actual inode backing the _running_ process's already-open files are decoupled once opened. Removing/replacing the directory entry doesn't invalidate file descriptors the running process already holds; those stay valid and readable until the process's reference count on them drops to zero (i.e., until it exits). **In practice this means: the running (old) process keeps working completely normally** on its already-loaded code and resources — it neither crashes nor silently reloads new code, because it never re-reads the (now-different) files at that path unless it explicitly does so (e.g., relaunching a helper binary by path).

**Single-instance-lock consequence (the important gotcha)**: Electron apps that call `app.requestSingleInstanceLock()` acquire an OS-level lock tied to the running _process_, not to bundle _content_. If a user replaces the on-disk bundle with a newer build while the old process is still alive, and then double-clicks the app again (Dock, Spotlight, Finder) expecting to launch the new version, what actually happens is: the _new_ process starts, immediately loses the single-instance-lock race to the still-running old process, fires `second-instance` on the **old** process, and then quits itself — the user just sees the old app's window come to focus, with zero indication that a newer build exists on disk. Electron's own issue tracker confirms this exact class of confusion (electron/electron#30219 — `"second-instance"` fires even when the second instance is a different app/version; electron/electron#35680 — lock can behave unexpectedly across versions). **The only way to actually run the new bundle is to fully quit the old process first** (Cmd+Q, or the app must detect the mismatch and self-terminate).

**Does anything detect "the bundle on disk is newer than me" and prompt to restart?** No concrete example was found of an app doing this for _out-of-band_ manual replacement specifically (as distinct from its own auto-updater's normal "update downloaded, restart to apply" flow, which Slack, VS Code, and virtually every auto-updating Electron app do implement for updates _they_ fetched and staged themselves). This appears to be treated as an edge case handled by convention — the expectation is the user fully quits before relaunching, or the app's own update mechanism (not manual file replacement) is the sanctioned path — rather than something any researched app builds explicit detection for. For a menu-bar/tray-resident app (windows closed but process alive, as flagged in the task), this same lock behavior applies identically: the tray icon keeps running the old build until the process is explicitly quit.

### 5. Stale staged updates and downgrade-on-quit risk

This risk is **confirmed as architecturally real**, not hypothetical, based on direct inspection of electron-builder's electron-updater source:

- **`DownloadedUpdateHelper`** (the class managing the on-disk "pending" update cache) stores the downloaded update file plus an `update-info.json` (filename, SHA512, admin-rights flag) in a `pending` subdirectory of the updater's cache dir. Its validation (`getValidCachedUpdateFile` / `validateDownloadedPath`) checks only: (1) does the metadata match what the server currently reports via deep-equality, and (2) does the file's actual SHA512 match the recorded one. **There is no comparison of the staged version against the currently-installed/running app version anywhere in this class.**
- **On macOS specifically**, `MacUpdater` documents in its own code comments that both `'onQuit'` and `'onNextLaunch'` `autoInstallOnAppQuit`/`autoInstallEvent` settings map to the _same_ native behavior: "Squirrel.Mac already stages the downloaded update natively (ShipIt) and applies it when the app is relaunched after a normal quit, without spawning a killable detached installer process." No re-check of the currently-installed bundle's version happens at that native staging/apply step.
- **Concrete failure sequence**: app is running v1.2.0; auto-updater silently downloads v1.2.1 and stages it (ShipIt/pending-cache) but the user hasn't quit yet; separately, the user (or an operator) manually replaces `/Applications/YourApp.app` with a freshly-built v1.3.0; the user then quits the still-running v1.2.0 process — Squirrel.Mac's staged install proceeds and overwrites the just-installed v1.3.0 bundle with the stale v1.2.1 payload. **This is a real downgrade-on-quit path**, not a theoretical one, given the absence of version-aware validation at the native staging layer.

**Recommended hygiene** (synthesized from the above, since no single canonical "official fix" document was found): on app startup, compare `app.getVersion()` (the version now actually running, which reflects whatever bundle is on disk) against any pending/staged update's recorded version; if the running version is already `>=` the staged version, proactively clear the updater's pending cache directory before calling any `checkForUpdates()`/`quitAndInstall()` path, so a stale staged payload can never be re-applied. This is the same spirit as electron-updater's own server-side re-validation loop (re-fetching `latest-mac.yml` and re-validating on next launch) — just applied defensively at the client cache layer too, since the native macOS staging path (ShipIt) itself performs no such check.

### 6. DMG cosmetics via electron-builder

**Full option set** (`dmg` key in electron-builder config, `DmgOptions` interface):

| Option            | Purpose                                                                                                                       | Default                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `background`      | Path to background image (PNG or TIFF) shown in the Finder window                                                             | `build/background.tiff` or `build/background.png`                                     |
| `backgroundColor` | Fallback solid color if no background image                                                                                   | `#ffffff`                                                                             |
| `window`          | `{x, y, width, height}` of the Finder window; y runs bottom-to-top                                                            | none (Finder auto-positions)                                                          |
| `contents`        | Array of `{x, y, type, path}` — icon placement; `x`/`y` are the icon's _center_, at 1x scale, and don't account for the label | none required (electron-builder auto-generates app + `/Applications` link if omitted) |
| `iconSize`        | Pixel size of icons shown in the DMG window                                                                                   | `80`                                                                                  |
| `iconTextSize`    | Label font size under icons                                                                                                   | `12`                                                                                  |
| `icon`            | Volume icon (`.icns`) shown for the mounted disk in Finder                                                                    | `build/icon.icns`                                                                     |
| `title`           | Volume name as mounted                                                                                                        | `${productName} ${version}`                                                           |
| `format`          | Compression: `UDZO`, `ULFO`, `ULMO`, `UDBZ`, `UDRO`, `UDRW`                                                                   | `UDZO`                                                                                |
| `filesystem`      | `APFS` or `HFS+`                                                                                                              | `APFS`                                                                                |
| `sign`            | Whether to sign the DMG container itself                                                                                      | `false`                                                                               |
| `internetEnabled` | Whether the DMG auto-extracts/auto-ejects on first open (legacy "internet-enabled disk image" behavior)                       | `false`                                                                               |

**Recommended background image specs**: 540×380 px at 1x, with a 1080×760 px `@2x` variant for Retina — electron-builder's own icons documentation states this directly and recommends supplying both `background.png` and `background@2x.png`. The classic native-macOS alternative (used by tools like `create-dmg`/`appdmg` and documented in Apple's own High-Resolution guidelines) is a **single multi-representation TIFF** combining a 72-dpi (1x) and 144-dpi (2x) image via `tiffutil -cathidpicheck standard.png retina.png -out background.tiff` — Finder then auto-selects the right representation per display, and getting the DPI tagging right matters: anything other than 72 dpi on the base image reportedly renders distorted on macOS. electron-builder accepts either approach (a pre-combined `background.tiff`, or the separate `background.png`/`background@2x.png` pair) — both are documented as valid, so the choice is a build-pipeline convenience call, not a compatibility one.

**Hidden dotfiles at the volume root, confirmed by direct source/issue inspection**: electron-builder's generated DMGs already contain `.background/` (folder, holding the background image), `.VolumeIcon.icns`, and `.fseventsd/` at the volume root by default — all genuinely hidden (dotfile-prefixed) and invisible in Finder unless the user has toggled "Show Hidden Files" (Cmd+Shift+.). **This means electron-builder already follows the "hidden `.background/` folder" convention the task asked about confirming as cleaner** — it is not a bare `.background.tiff` sitting loose at the volume root; the image lives inside a dedicated hidden subfolder. The one open wrinkle (electron-userland/electron-builder#1160, still unresolved) is that positioning these hidden items via `dmg.contents` reliably works for `.VolumeIcon.icns` but not for the `.background/` folder itself — so a developer/user with hidden files visible by default may see `.background/` awkwardly placed in the DMG window rather than tucked out of view, since electron-builder doesn't currently expose a clean way to position it off-screen the way some other DMG-building tools (e.g., `appdmg`) attempted to.

## Research Gaps & Limitations

- No concrete real-world example was found of an app explicitly detecting "the on-disk bundle is newer than my running in-memory version" for an _out-of-band_ manual replacement (as opposed to the app's own auto-updater flow). This may genuinely not exist as a pattern anyone ships, rather than being an oversight of this research — worth treating as an open design question for DorkOS's desktop app rather than assuming a reference implementation exists to copy.
- The precise, currently-shipping electron-updater behavior described in some secondary summaries ("re-validates the cached installer... verifies the pending version is still an installable change... newer than the running app") could not be traced to a specific line of source across all updater classes in the time available — it appears to describe the JS-level `checkForUpdates()` re-fetch/re-validate loop against the _update server's_ manifest, not a check of the _locally staged_ file's version against whatever is currently on disk. The direct source read of `DownloadedUpdateHelper.ts` and `MacUpdater.ts` found no local version-vs-disk check; this distinction matters for the implementation plan and should be verified against the exact electron-updater version DorkOS pins before relying on it.
- Whether electron-builder's `background@2x.png` convention is actually auto-detected today (vs. still being the unresolved feature request in electron-userland/electron-builder#1506) was not conclusively confirmed — the Icons & Images docs describe it as recommended practice, but the linked GitHub issue reads as a still-open ask referencing `appdmg`'s prior support for the same convention. Treat the single multi-representation TIFF (`tiffutil -cathidpicheck`) as the more conservative, definitely-supported path if precise Retina rendering is a hard requirement.
- Direct fetch of electron-builder's `dmg.html`/`configuration/dmg` doc pages failed (empty response / 404); the DmgOptions table in this report was reconstructed from the `DmgOptions` interface reference page and the Icons & Images doc instead, which are consistent with each other but were not cross-checked against the primary `dmg.html` guide page.

## Contradictions & Disputes

- One general-purpose search summary (not traceable to a specific source URL) claimed electron-updater "verifies the pending version is still an installable change (newer than the running app...)" before applying an update. Direct inspection of `DownloadedUpdateHelper.ts` and `MacUpdater.ts` source did not surface this logic locally — the check that does exist is checksum/metadata equality against the _server's_ current manifest, fetched fresh on each `checkForUpdates()` call, which is a different mechanism than "does the locally staged installer's version exceed what's currently on disk." Treat the downgrade risk in Question 5 as real and unmitigated by electron-updater/Squirrel.Mac's native staging path unless DorkOS's specific pinned version is independently verified to add such a check.
- Whether `background@2x.png` auto-detection is currently shipped in electron-builder (vs. a long-standing open feature request) is ambiguous across sources — the official Icons & Images doc recommends it as if implemented, while GitHub issue #1506 (requesting exactly this) shows no visible resolution in the content fetched. This is a good item to verify empirically (build a test DMG with both files present and inspect the resulting `.DS_Store`) before depending on it.
