# 261002-221210. Codex and OpenCode run on credits through their own request format, offered only once it is served

## Status

Accepted (DOR-2633, spec `dorkos-account-by-default` decision D7). It amends ADR `261001-000811`, which declared credits for Claude Code alone and left the other two runtimes "to join with their own protocols later". Everything that ADR settles (who chooses, fail closed, the kill switch, the token lifecycle, the three conformance negatives) holds unchanged for both.

## Context

Codex and OpenCode each speak a different vendor format, and neither has an account list the way Claude Code does. Codex 0.154 speaks only the responses format: its CLI refuses `wire_api = "chat"` outright. OpenCode speaks chat completions through a provider package it bundles. The credits service has a chat-completions route, but nobody has checked it against OpenCode's requests, and it has no responses route yet. OpenCode also runs every session through one shared sidecar process, in which a project's plugin can read the environment.

## Decision

**The token says which formats are served, and silence means Anthropic only.** The minted token gains an optional `served` list of request formats, named by their endpoint fields (`anthropicMessages`, `openaiChat`, `openaiResponses`, the `InferenceFormatSchema` names), and `endpoints` gains an optional `openaiResponses` base. The list is typed as plain strings and read for the names this app knows: a format a newer service lists must never make the token fail to parse. A format is served only when the token lists it AND carries its endpoint. A token that lists nothing, and no token at all, count as serving `anthropicMessages` only, which is exactly what every token did before. So an old service never starts a format by leaving the field out. A runtime's `credits` capability names its format (`anthropic-messages`, `openai-chat-completions`, `openai-responses`) and its scope. A runtime counts as wired only when it declares credits AND its format is served (`creditsRuntimeWired`). Every offer reads that answer: the status report, "Use credits for", a runtime card's Runs on choice, filling the gaps on a new link (which waits, bounded, for the link's first token so it sees what that token serves), and the route that records a choice. A runtime whose recorded choice is credits keeps its row and its Runs on choice even while credits cannot reach it, so it can always be turned off. Codex and OpenCode declare credits now and are offered nothing until the service lists their formats. A launch in a format that is not served is refused as `not-supported`, never sent to another endpoint. The service lists chat completions only once its chat route has been checked against OpenCode's request shape.

**Codex: a home of its own, a provider entry per turn.** A Codex turn on credits runs with `CODEX_HOME` set to `<dorkHome>/runtimes/codex/credits`, never the person's `~/.codex`. The CLI is handed a `dorkos-credits` model provider as `--config` overrides (endpoint, `wire_api = "responses"`, `env_key` naming the token's variable, `requires_openai_auth = false`). The token rides only the environment, under a variable named fresh for every turn. Nothing of the person's `OPENAI_*` or `CODEX_*` reaches the turn. Their `config.toml`, sign-in and `OPENAI_BASE_URL` are never read or written; that also means a credits conversation does not get their own MCP servers, global `AGENTS.md` or profiles from `~/.codex` (DorkOS's own tools are passed per turn as before). The credits home trusts no folder, so Codex reads no project `.codex/config.toml` there; in a folder it did trust, the provider on the command line still wins (proved against the binary). The credits home holds no sign-in, so a turn that lost its token sends nothing at all. Which side a thread is on is read off the disk: its rollout lives in exactly one home, so a conversation stays on whatever paid for it (the rule of ADR `260801-204127`). A new thread follows Codex's recorded default. Codex has no account hint per send, so its Runs on choice is that default.

**OpenCode: credits are a mode of its one sidecar.** OpenCode's recorded choice decides what the whole sidecar boots on. On credits, it boots with the credits provider and no other one: `enabled_providers` is pinned to `dorkos-credits`, and its endpoint and key are set, all merged last through `OPENCODE_CONFIG_CONTENT`, which outranks every config file. **The token never enters OpenCode's process.** OpenCode substitutes `{env:NAME}` and `{file:PATH}` in a project's own `opencode.json` too, and can send the result to a remote MCP server in a header, so anything secret in the sidecar could leave the machine with no code run (reproduced against the binary with a fixed variable name; on Linux `{file:/proc/self/environ}` reads the whole environment). So the credits provider points at the **credits relay**, a DorkOS-owned endpoint on 127.0.0.1 and a port of its own (never the server's, which a tunnel may expose), with a key drawn fresh for every boot and revoked when that sidecar stops. The relay checks the key, adds the real token, and forwards only to the credits endpoint for that format, on a fixed set of paths (`POST /chat/completions`, `GET /models`), dropping the query and every header but the content ones. It streams the answer through, caps the body size and the request time, logs no body, key or token, and refuses (401, `credits_unavailable`) with nothing sent upstream when the key is wrong or credits cannot pay right now. What a project's config can reach is the relay key, which opens nothing off this machine. A new token needs no restart: the relay always sends the current one. Unlink ends every relayed request at once. The person's provider keys and `OPENAI_BASE_URL` are left out. On their own sign-in, it boots exactly as before, with no credits variable. A change of the choice recycles the sidecar, the way a new power source already does. That moves every conversation, and the copy says so (`scope: 'runtime'`). **A switch never ends or re-bills a running turn.** The route that records the choice refuses to switch OpenCode while any of its turns is running, and says so. A switch that arrives some other way (Undo all, a new link) waits: the sidecar is recycled only when no turn is running, and a turn that asks for the other side meanwhile is refused with nothing sent ("OpenCode is still finishing a reply on …"). A turn counts as running from its first step, before the sidecar is prepared for it, so nothing restarts under a turn that is still setting up. A sidecar kept for running turns while only its model list moved is not restarted under them. On credits with no live token, the sidecar boots able to pay for nothing and every turn is refused; it never falls back to the person's providers. Unlink and a new link recycle it at once. The models it offers are the ones the service lists for the link (`GET /v1/inference/models`). A turn keeps the session's model when it is one of those, else it takes the first that can call tools.

**What this does not protect against**, the same as ADR `261001-000811` says for Claude Code. Code a credits turn runs (an MCP server, a command, an OpenCode plugin in a project on credits) can read the token from its own environment. On OpenCode, that code can use the relay key from this machine while the boot lasts; it cannot carry anything usable away, because the token is not in its process.

**Codex does not use the relay.** A Codex turn is its own short-lived process in a home DorkOS owns, and that home trusts no folder, so Codex reads no project config at all and no config file can reach its environment. Only code the turn runs could, which is the case above. Its token rides a variable named fresh for every turn, so even a folder Codex did trust could not name it.

## Consequences

### Positive

- The service turns OpenCode or Codex on by listing its format, with no app release. Until then nothing offers it, and Claude Code works exactly as before on a token that lists nothing.
- Neither runtime's own configuration is touched, and neither can bill the person's own sign-in on a credits turn. Both are proved against the real binaries with fake local servers (`credits-provider.binary.test.ts`, `credits-mode.binary.test.ts`): a project's config cannot redirect the token, and a project's own provider is never reached on credits.
- Both pass `runtimeConformance` with the credits negatives wired, not waived.

### Negative

- OpenCode on credits is all or nothing for the runtime, and it cannot be switched while it is in the middle of a reply.
- A Codex conversation started on credits cannot move to the person's own sign-in. Its refusal offers "Start a new conversation on your Codex sign-in" instead of a retry that would be refused again.
- OpenCode reads the model list when the sidecar boots on credits. A model the service adds later appears after its next recycle.
- The OpenCode binary proof runs only where `opencode` is installed (not in CI). The Codex one runs wherever the SDK's vendored binary is installed.
- The relay is one more component on the money path: a small loopback server DorkOS starts when OpenCode is enabled. If it cannot start, OpenCode on credits can pay for nothing and refuses.
