# Harness Sync — Testing Plan

**Status:** v3, 2026-09-07 — reviewed alongside the contract across three adversarial rounds (consensus reached); tracked in Linear as DOR-1841…DOR-1858: one item per line of §11 with line 3 split into three (DOR-1844 scanner + parity, DOR-1845 inventory + honest drops, DOR-1846 vendor facts + coverage walk), plus the docs item (DOR-1841) and the manifest cleanup (DOR-1858) — 18 in all.

Companion to `meta/harness-sync-capabilities.md` (the contract). This is how the tests get built: what each tier proves, where it lives, what oracle it uses, and the order. Changes from v1 are marked **[v2]**, from v2 **[v3]**; the markers stay so a reader can see which decisions the review changed.

## 0. The bar every new test has to clear

Two rules from `REVIEW.md` and `.claude/rules/testing.md`, restated for this surface because the existing suite is strong on shape and weak on truth:

1. **Seeded-defect proof.** A test for a gap in §14 must **fail on `main` today** before the fix lands, and the PR shows both runs. The CLI test file already carries the warning in two places: an exit-code-only assertion "passed throughout the life of the bug" (`harness-sync.test.ts:171`), and the snapshot helper's docstring (`:40-49`) — "an in-place rewrite of a file that already existed would pass it. No check-mode path can reach such a rewrite today; if one ever can, this helper has to start hashing contents." HK-11 is exactly that rewrite; the helper predicted its own blind spot. **[v2]**
2. **The oracle is the reader, not the writer.** Where a row says "the harness reads X", the assertion is "given this tree, the harness's documented read paths and identity rule discover X", never "a file exists at X". File-shape assertions stay for ownership and idempotency properties (§9), where the file IS the property.
3. **Nothing zero-subject.** A test that parses a document, walks a directory or enumerates a list asserts **how many things it found** before asserting anything about them (`REVIEW.md` §"zero-subject pass"). **[v2]**

Plus the repo's standing rules: real temp dirs (`mkdtempSync`), no `node:fs` mocks in the engine package, `pnpm vitest run <path>` per file, every case's purpose in its title.

## 2. T1 — vendor facts, inventory, path lists (the load-bearing piece, re-scoped) **[v2]**

v1 proposed six hand-written per-harness "readers" — a simulation of each vendor's discovery. The review's objection stands: six models of six moving products, calibrated only by an H tier that is line 11 of 14, would be an uncalibrated model standing as a CI gate, which is the `REVIEW.md` "guard that enumerates from a literal list" shape. What the assertions actually need is smaller and repo-local:

**(a) `vendor-facts.ts`** — one dated, quoted record per harness × artifact kind: read paths (project, user), precedence, identity/name rule, symlink behaviour, live-reload behaviour, the doc URL, the date fetched, and `verified: 'docs' | 'binary'`. This is §1 as data. `vendor-facts.test.ts` asserts every cell §1 shows is present with a date, and that no harness the engine targets (`HARNESS_IDS`) is missing a skills row. When a vendor changes, this file is where the change is recorded — the twin of `contributing/harness-sync.md` §3's re-vendor checklist for hook maps.

**(b) `inventory/`** — one scanner over a **source** tree, per artifact kind: skills (following symlinks, keeping `__` names — the two things `scanSkillDirs` refuses), commands, hooks (all three Claude settings files), subagents, rules, MCP config. Repo-local ground truth, no vendor knowledge. It feeds two consumers: the **completeness assertion** (every inventoried artifact appears in exactly one of `plan.actions` for each enabled harness, `plan.drops`, or `plan.warnings` — the check that fails today for §8's four kinds and SK-13's two silences) and VC-01's **`unmanaged`** (inventory of the harness-native dirs minus what the plan manages = adoptable).

**(c) per-harness path walk** derived from (a). Each facts row carries `walk: 'ascend-to-repo-root' | 'ascend-to-worktree' | 'descend-recursive' | 'fixed'`, `identity: 'dir' | 'frontmatter'`, `nameRegex`, `nameMustMatchDir`, `onInvalidName: 'skip' | 'warn-and-load' | 'unknown'`, `dedupe: 'by-realpath' | 'by-name' | 'unknown'`. One shared walker implements the three static walks; `harnessCoverage(harness, treeAfterApply)` returns **`{ discovered, uncertain }`** — an artifact lands in `uncertain` whenever its outcome depends on a cell that is `unknown` (a `pkg__name` dir on a harness whose `onInvalidName` is unknown; a skill reachable twice on a harness whose `dedupe` is unknown). Assertions read "`discovered ⊇ canonical` **and** `uncertain` is empty", so an unknown fails loudly instead of being guessed. That is what keeps the facts table from becoming the confident-and-wrong guard. **[v3]** SK-06 and SK-09's _flags_ are pure data; SK-09's and SK-12's _outcomes_ stay `unknown` until T6 calibrates them. **Claude Code's lazy nested tier is out of scope for `harnessCoverage()`**: it ascends AND loads nested `.claude/skills` on file touch under a directory-qualified name, which no static walk models; SK-15 stays a `—` row with a T6 item rather than a fourth enum value pretending otherwise.

Full readers, if ever, only for harnesses T6 can calibrate, and only after T6 has run once.

## 3. T0 — properties **[v2: the generator decision]**

`fast-check` is in no `package.json`, not in `pnpm-lock.yaml`, and the monorepo has no property test anywhere. Two ways to close this, and the plan picks one:

- **Add `fast-check` as a devDependency of `@dorkos/harness` only.** Pros: shrinking (a failing generated repo is minimised to the smallest repro, which is the whole value for HK-11-shaped bugs), a mature generator DSL, MIT, no runtime footprint. Cons: a new paradigm in a repo that has none, and a dependency add the operator has to approve (the upgrade-wave memory says every new dependency is a deliberate decision).
- **Hand-rolled seeded generator** (`mulberry32` + a small combinator set) in `__tests__/properties/gen.ts`. Pros: zero dependencies, follows "study existing patterns". Cons: no shrinking, so a failure is a 6-skill 3-plugin repo you read by hand; and the combinators get rewritten badly.

**Decision: add `fast-check`, scoped to the harness package, with the reason in the PR — shrinking is the feature, and HK-11 is the argument.** If the operator declines, the fallback is the seeded generator with `numRuns` kept low and the failing seed printed. Either way this is line 1's PR, not a silent assumption.

Generator `arbRepo()` produces a `Tree` with: 0–6 authored skills (small name alphabet so collisions happen; some as symlinked sources; some with `__`), 0–3 plugins (skills, tasks, commands, hooks with random events incl. unmappable ones and `__proto__`, some scheduled, some with `${CLAUDE_PLUGIN_ROOT}`), an optional `AGENTS.md`, optional hooks in each of the three Claude settings files, a random enabled-harness subset (including `[]`), and **hostile occupants**: a real dir or file at 0–2 random projection targets, a dangling symlink at 0–1 (both managed targets and generate/scaffold targets), a hand-written file at 0–1 generated hook targets (with and without a marker), a user hook group in `settings.local.json`.

Properties (each one `fc.assert`):

- **P1 idempotent:** `apply(project(t))` twice → identical tree after the first; `check` clean after the first.
- **P2 inventory ⇔ ownership** **[v2 — rewritten; v1's "check ⇔ apply" was vacuous against SK-10 and threw on AP-05]:** after `apply` + sweep, every path under a projection dir that matches the engine's ownership predicate (a symlink in `.claude/skills` / `.agents/skills`; a marker-bearing file under the command dirs; a marker-bearing generated hook file; a sentinel-tagged settings group) resolves to a source the **current** plan names. An orphan is a failure with the path in the counterexample. This is the property that catches SK-10.
- **P2b check never throws:** `checkPlan` returns for every generated tree, dangling links included (AP-05).
- **P3 conflict never destroys:** for every occupant staged, its bytes are identical after apply, and it appears in `conflicts` — or in `applied` only if it was already correct. (Fails today for a marker-less `.codex/hooks.json` — HK-11.)
- **P4 sweep touches only what it wrote:** run apply, then randomly delete sources/plugins, re-project + sweep; every path the sweep removed was created by an earlier apply (tracked by a ledger the test keeps), never by the generator's "user" side, and never for a harness outside the manifest; a generated file and its `.dorkos-generated` sidecar are swept together or not at all, and a generated file whose bytes no longer match its sidecar is a conflict, never swept **[v3]**. **[v4, DOR-1923] At global scope the same ledger extends to `<dorkHome>/skills`, and a removal must additionally satisfy clause 3 of the ownership predicate**: the link's own text, resolved lexically, is inside `<dorkHome>/plugins`. A person's hand-authored `__`-named directory, their own symlink into a directory they wrote, a link into a lookalike neighbour, and one of ours two levels down all survive; a dangling link left by an uninstalled package does not.
- **P5 determinism:** `project(t)` twice → deep-equal plans; generate content byte-equal.
- **P6 completeness:** T1(b)'s nothing-silent assertion.
- **P7 provenance ⇒ gitignore:** every `installed`/`adopted` action's target matches an `EPHEMERAL_GITIGNORE_PATTERNS` glob or lies under a self-ignoring `.gitignore` the plan also writes.
- **P8 project scope [v2 — written for the first time in DOR-1923; v1 was a line in this plan and no test]:** every action in a plan built by `project()` carries `scope` absent or `'project'`, its `target` and `source` are repo-relative POSIX strings, and each resolves inside `repoRoot`. No path built from a `dorkHome` appears in any of them — asserted against a generated repo whose dork home really holds a global package, so the claim is about a plan that has SEEN one. As strong as v1; only its subject is named.
- **P8b global roots [new, DOR-1923]:** every action in a plan built by `buildGlobalPlan` carries `scope: 'global'` and an absolute `target`, and that target resolves inside one of the plan's declared roots and inside no other directory. A root passed as absent produces no action beneath it, and the counterexample prints the offending target and the root set.
- **P8c global kinds [new, DOR-1923]:** no entry in a global plan has `kind: 'generate'`, `kind: 'scaffold'` or `kind: 'merge'`. Every global entry is `symlink`, `native` or `drop`. The rule "never generate at user scope" has no other enforcement, and `buildPlan` running every stage unconditionally is the ordinary way it would be lost.
- **P9a source exists** **[v2]:** every `native` action's `source` exists in the tree. **P9b source reachable** **[v3]:** every `native` action's source is discoverable by `harnessCoverage(harness, tree)` — which is what catches OpenCode's installed-skill `native` (its source exists under `.dork/plugins`; nothing links it where OpenCode reads). P9b needs T1(a)+(c), which is why they ship in line 3.

## 4. T2 — journeys (the fixture DSL and the exact-diff assertion)

`packages/harness/src/__tests__/journeys/stage.ts`:

```ts
const repo = await stageRepo({
  claude: { skills: ['a', 'b'], commands: ['deploy'], rules: ['api.md'], agents: ['reviewer'],
            settingsHooks: { Stop: [...] }, settingsLocalHooks: { PreToolUse: [...] },
            mcpJson: {...}, rootClaudeMd: '# Project' },
  codex:  { hooksJson: {...}, configToml: '[mcp_servers.x]\n…' },
  cursor: { hooksJson: {...} },
  opencode: { skills: ['c'], commands: ['ship'], opencodeJson: {...} },
  agents: { skills: ['d'], symlinkedSkills: { e: '../../vendor/e' }, agentsMd: true },
  plugins: [{ name: 'flow', scope: 'project', skills: ['capture'], scheduled: ['drain'],
              commands: ['capture'], hooks: { Stop: [{ command: 'node ${CLAUDE_PLUGIN_ROOT}/x.mjs' }] } }],
  git: true,                      // git init + commit, so rename/symlink behaviour is real
  gitignore: ['.agents/'],        // optional, for AP-15
});
const before = snapshot(repo.root);            // path → { kind, sha256 | linkText }
… run the journey's steps (project/apply/CLI/runAutoProjection) …
const after = snapshot(repo.root);
expect(diff(before, after)).toEqual({ added: [...], changed: [...], removed: [...] });   // EXACT, not ⊇
expect(harnessCoverage('codex', after).skills).toEqual(new Set([...]));
```

The exact diff is the point: a journey lists every path the run may add, change or remove, so an unexpected write (HK-11, a stray `.gitignore`) is a red, not an unnoticed side effect. `snapshot` hashes file content and records link text; it ignores `.git/` internals. **The hashing is what the CLI test's helper said it would one day need** (§0.1).

One file per journey, named `jNN-<slug>.test.ts`, its `describe` `J-NN — <title>`, and every `it` titled with the row ids it pins (`J-03, IN-03: …`). J-12 (concurrency), J-13 (room worktree) and J-15 (Codex palette parity — asserts `scanSkillCommands` and the `dorkos://skills` resource against `harnessCoverage('codex', …)`) are seam journeys and live under `apps/server`.

**Built (DOR-1848).** `stageRepo` lives in `packages/harness/src/__tests__/journeys/stage-repo.ts` beside the snapshot half, and the pair is exported from the package as `@dorkos/harness/journeys` — a test-only entry point (`tsconfig.build.json` excludes `__tests__`, so nothing here reaches `dist/`), because half the journeys need the server seam and live in `apps/server/src/services/harness/__tests__/journeys/`. `snapshot`/`diff` kept their existing names, `snapshotTree`/`diffSnapshots`; thin aliases would have been two names for one function. J-01, J-03 and J-14 run against the engine; J-04, J-08 and J-11 run through `runAutoProjection` and the agent-workspace boot pass. The generator's `materialise` in `__tests__/properties/arb-repo.ts` stayed separate: its `RepoSpec` is twenty booleans of hostile occupants a journey never wants, and it can express neither `.cursor/`, `.opencode/`, `opencode.json`, `.codex/config.toml`, a real `git init`, nor a symlinked skill source — sharing one materialiser would have contorted both.

Named expectation for **J-02 today**: the expected diff is what the engine SHOULD do (all three hand-written hooks files — `.codex/`, `.cursor/`, `.github/hooks/` — untouched, a conflict naming each). It fails on `main` by showing three files removed, the Copilot one for a harness the manifest never enabled — the seeded-defect run for HK-11 and AP-07.

## 6. T4 — CLI additions

- Summary counts include `merge` (VC-02); harness-agnostic drops are printed under a "plugin layers" heading, not `codex:` (VC-02).
- `--fix` on a J-02 fixture prints the HK-11 conflict line naming each file and the way out (move the hooks into `.claude/settings.json`, or delete the file); a sidecar-matched file is regenerated silently.
- `--check` on a dangling generate target prints a drift line, exit 1, no stack (AP-05).
- **Withhold, loudly** (D5) **[v3]**: `--fix` withholds an unapproved package's hooks, projects everything else, prints a terminal block per package naming each command and the exact re-run, counts them in the summary (`2 hooks withheld`), and exits **0**; `--strict` exits 1 on any withheld hook; `--allow-hooks <pkg>` installs and **records** the same `<pkg>@<digest>` entry into `harness.approvedHooks` the card writes (assert the store, not just the file); a durable refusal in `harness.refusedHooks` (same digest key) is honoured and printed, and expires when the digest changes; `dorkos harness hooks --list` and `--revoke <pkg>` round-trip the store.
- `.codex/hooks.json` is written as `{ description, hooks }` and a `.dorkos-generated` sidecar lands beside every generated file; a hand-edited generated file (bytes ≠ sidecar digest) is a conflict (HK-01, HK-11) **[v3]**.
- The stale-drop text for Cursor/Gemini/Copilot authored skills is gone and replaced by `native` counts (SK-05); `SessionEnd` maps to Codex (HK-13).
- A manifest carrying a retired key (`skillWrappers`, `commandMappings`, `instructionProjections`, `skillBundles`) gets one named line per key, in `--check` and `--fix` alike, and no exit-code change; `hookPolicies` is honoured per harness — `none` or `native` on Codex/Cursor/Copilot writes no hooks file and drops each contributing source naming the manifest, and a file the engine wrote there before becomes a sidecar-guarded orphan the sweep removes (DOR-1858).
- A repo with an unenabled harness present prints "`.cursor/` found; Cursor is not enabled — add it to `.agents/harness.manifest.json` or run `--fix --enable cursor`" (TR-11). `--enable` is the one path that writes the manifest, which ADR-0302 otherwise scaffolds and never generates: an explicit flag, a minimal key-add that preserves key order and formatting, stated in the ADR amendment **[v3]**.

## 7. T5 — Windows **[v2: separate advisory workflow]**

`test` is a required, four-way-sharded merge-queue check; putting a new OS inside it, path-filtered, is the shape AGENTS.md's site-build lesson warns about (a path-filtered required check reports nothing and stalls the queue). So: a new `harness-windows.yml` on `windows-latest`, triggered on `pull_request` **and `merge_group`** from day one, scope decided inside the job (skip unless `packages/harness` or `packages/cli` is affected), advisory now, promotable to required later without a deadlock. It runs `pnpm vitest run packages/harness packages/cli/src/__tests__/harness-sync.test.ts`. Expect drive-letter `realpath` normalisation to need fixing; that is the point. Plus the J-10 half: clone a fixture with `git -c core.symlinks=false` and assert every authored symlink is reported as a conflict with the one-line explanation.

## 8. T6 — H, the real-harness smoke **[v2: oracle hierarchy and money rule]**

**Shape.** `scripts/harness-smoke/run.sh <harness>` builds a fixture repo (through the same DSL, exported as a small CLI), applies the projection, then asks the harness to prove it discovered each artifact. Gated by **both** a flag and an instrument, per the repo's money rule: `DORKOS_HARNESS_SMOKE=1` is the decision, and the run refuses unless the harness's own credential is explicitly named (`DORKOS_HARNESS_SMOKE_CLAUDE=<key or 'login'>`, and likewise per harness) — an ambient sign-in is never picked up silently, because "a fake key is not a safe way to run the Anthropic one: the test server inherits your `claude` sign-in and bills that instead". A per-run ceiling (`--max-usd`, default 0.25) and a printed cost line where the harness reports one. A missing binary is a **skip that says so**. Scope for the first year: **Claude Code, Codex, OpenCode** — the three DorkOS runs — because the other three need paid accounts the operator may not hold. Runs nightly on the operator's machine beside `pnpm evals:local`, and by hand before a release.

**Oracle hierarchy — v1 had it backwards.** A uuid in a skill body proves a model read a file, not that a harness loaded a skill: every one of these agents can `cat` the path the prompt names, and most load only the description at startup anyway. So:

1. **Listing (primary, non-model where it exists).** Claude Code: the SDK `query()` `system/init` message carries `slash_commands`, which lists project skills as commands — the same probe the claude-code runtime's warm-up already reads; assert `/x`, `/pkg__x`, `/pkg:x` appear. Codex: `$` completion has no non-interactive surface (verify whether `codex app-server` exposes a skills list); until then Codex's listing is the model probe below. OpenCode: its server exposes config and agent listings (verify whether skills are on it). Gemini `/skills list`, Copilot `/skills` — deferred with the harness.
2. **Activation side effect (for hooks, and for skills whose body instructs one).** The projected hook writes a file with a nonce; the fixture skill's body says "run `touch <nonce-path>` and nothing else". The oracle is the file. A model cannot fake a hook firing, and a skill that _loaded_ (rather than was `cat`-ed) is the one whose instructions the harness injected — proved by running the probe with the harness's file-read tools **denied** (`--disallowedTools Read,Bash(cat*)` on Claude; the equivalent sandbox flag on Codex/OpenCode) so the only route to the instruction is the harness's own injection.
3. **Sentinel in output (corroboration only, never the verdict).** Kept because it is cheap and catches gross failures, demoted because it cannot distinguish reading from loading.

**Per harness, straight from §1**: Claude Code — `/x` and `/pkg__x` listed; a wrapper listed as `/pkg:x`; skill beats command on a shared leaf (CM-05); `@../AGENTS.md` pulls the body; a `_dorkosHarness`-tagged hook still fires (re-validate what was validated on CLI 2.1.197). Codex — `pkg__x` under its **frontmatter** name; duplicate frontmatter names both appear (SK-06); `.codex/hooks.json` `Stop` fires in a trusted project and not in an untrusted one (HK-10); `SessionEnd` fires once HK-13 lands. OpenCode — `pkg__x` loads, warns or is skipped (SK-09); `/pkg-x` invokes; a skill reachable from both dirs appears once (SK-12); `CLAUDE.md` fallback with no `AGENTS.md`. **Plus the calibration diff**: T1(c)'s `harnessCoverage(harness, tree)` against the binary's listing on the same fixture; a disagreement is the finding.
